# Вопросы для собеседования: React Native (Middle/Senior)

Вопросы с ответами, разделены по темам. Там, где уместно, помечена разница в глубине ответа между Middle и Senior.

## 1. JavaScript / TypeScript

**Event loop: микро- vs макротаски, порядок выполнения `Promise.then`, `setTimeout`, `queueMicrotask`.**
Макротаски (task queue) — `setTimeout`, `setInterval`, I/O, UI-события. Микротаски (microtask queue) — `Promise.then/catch/finally`, `queueMicrotask`, `MutationObserver` (в вебе). После каждой макротаски движок полностью опустошает очередь микротасков, прежде чем взять следующую макротаску. Поэтому `Promise.resolve().then(cb)` выполнится раньше `setTimeout(cb, 0)`, даже если оба поставлены в очередь "одновременно".

**`Promise.all` vs `allSettled` vs `race` vs `any`.**
- `all` — резолвится, когда все промисы выполнены; реджектится при первом же реджекте (fail-fast).
- `allSettled` — всегда резолвится массивом статусов (`fulfilled`/`rejected`) для каждого промиса, удобно когда нужны все результаты независимо от ошибок.
- `race` — резолвится/реджектится по первому завершившемуся промису (неважно, успех или ошибка).
- `any` — резолвится по первому успешному; реджектится только если все реджектнулись (`AggregateError`).

**Замыкания — пример утечки памяти в RN.**
Классический случай: подписка на event emitter (например, Firebase listener или `Keyboard.addListener`) внутри `useEffect`, где callback захватывает в замыкании large state/props, а cleanup не отписывается. Компонент размонтируется, но listener жив и держит ссылку на весь замкнутый scope → утечка. Фикс — возвращать `unsubscribe` из `useEffect` и вызывать его в cleanup.

**Прототипное наследование vs классы.**
Классы в JS — синтаксический сахар над прототипным наследованием: методы класса кладутся в `Class.prototype`, `extends` выставляет `__proto__` цепочку. Разница с "настоящими" ОО-языками: наследование в JS всегда через делегирование к прототипу в рантайме, а не копирование структуры при компиляции.

**TypeScript: generics, `Partial`/`Pick`/`Omit`/`Record`, discriminated unions.**
- Generics — параметризация типов (`function identity<T>(x: T): T`), даёт типобезопасность без потери переиспользуемости.
- `Partial<T>` — все поля опциональны; `Pick<T, K>` — выбрать подмножество полей; `Omit<T, K>` — исключить поля; `Record<K, V>` — объект с ключами `K` и значениями `V`.
- Discriminated union — union типов с общим "тег"-полем (`type: 'loading' | 'success' | 'error'`), позволяет TS сужать тип в `switch`/`if` по этому полю (narrowing).

**Senior: conditional types, `infer`, типизация полиморфного API-слоя.**
Conditional types (`T extends U ? X : Y`) вместе с `infer` позволяют вытаскивать типы из других типов, например `type Awaited<T> = T extends Promise<infer U> ? U : T`. Для RTK Query это используется, чтобы типизировать `ResultType`/`QueryArg` эндпоинтов автоматически, вывести тип ответа хука `useGetXQuery` без ручного дублирования интерфейсов.

**`interface` vs `type`.**
`interface` — декларативно расширяем (declaration merging), лучше для публичных API объектов/классов. `type` — может описывать union/intersection/mapped types, primitives — то, что `interface` не может. Практика: `interface` для форм объектов, которые могут расширяться библиотеками; `type` для всего остального, особенно union.

**`strict: true` — что включает.**
Комбинация флагов: `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `alwaysStrict`. Самые болезненные при миграции — `strictNullChecks` (заставляет явно обрабатывать `null`/`undefined` везде) и `noImplicitAny` (требует типизировать всё, что раньше молча было `any`).

## 2. React — основы и глубже

**Reconciliation / Fiber, зачем нужен `key`.**
Fiber — это внутренняя структура данных React (linked list "единиц работы"), которая заменила рекурсивный stack-based reconciler в React 15. Она позволяет прерывать/возобновлять рендер (для concurrent features), разбивая работу на приоритизируемые единицы. При сравнении списков детей React матчит элементы по `key`: без стабильного `key` (или с `index` в качестве key при переупорядочивании списка) React может неправильно сматчить старые/новые элементы, что приводит к потере state (например, значение в `TextInput` "прыгает" на другой элемент) или лишним ре-маунтам.

**`useEffect` vs `useLayoutEffect`.**
`useEffect` выполняется асинхронно после отрисовки кадра на экране (после того, как браузер/RN отрисовал). `useLayoutEffect` выполняется синхронно после DOM-мутаций, но до того как экран обновится визуально — блокирует paint. Нужен, когда эффект должен синхронно измерить/поменять layout до того, как пользователь увидит "мигание" (например, измерить размер элемента и тут же поправить позицию). В RN своя специфика — там нет браузерного paint в том же смысле, но `useLayoutEffect` всё равно синхронизирован с commit-фазой React, до того как изменения долетят до нативного UI.

**Контроль ре-рендеров: `React.memo`, `useMemo`, `useCallback`.**
`React.memo` — оборачивает компонент, делает shallow compare пропсов между рендерами; если пропсы равны по ссылке/примитиву — рендер компонента пропускается. `useMemo` мемоизирует значение между рендерами (пересчитывается только если изменились зависимости). `useCallback` — то же самое, но для функций (чтобы не создавать новую ссылку на каждый рендер и не ломать `React.memo` у детей). Важно: shallow compare — значит объекты/массивы/функции без мемоизации всегда "новые" по ссылке.

**Senior: React Compiler.**
React Compiler автоматически вставляет мемоизацию на этапе сборки (babel plugin), анализируя граф зависимостей компонента, — в большинстве случаев ручные `useMemo`/`useCallback` становятся избыточны и даже вредны (лишний код, риск неправильно указанных deps). Ручная мемоизация всё ещё нужна в редких случаях: когда стабильность ссылки нужна для внешней библиотеки, которая сама не под контролем компилятора (например, `useCallback` для колбэка, передаваемого в нативный модуль или в сторонний хук вне React-рендера), либо когда нужен мемо для дорогого вычисления, требующего ручного контроля инвалидации.

**Context API — почему любое изменение value триггерит ре-рендер, паттерны борьбы.**
`Context.Provider` при изменении `value` ре-рендерит все компоненты, вызывающие `useContext` этого контекста — независимо от того, какую часть value они реально используют, потому что React сравнивает `value` целиком по ссылке (Object.is). Паттерны: разделять один большой контекст на несколько маленьких по domain; выносить часто меняющиеся значения в отдельный контекст от редко меняющихся; мемоизировать `value` объекта (`useMemo`); для сложных случаев — сторонние решения (`use-context-selector`) или просто перейти на state-менеджер с селекторами (Redux/Zustand), которые ре-рендерят только подписчиков конкретного среза.

**Controlled vs uncontrolled компоненты.**
Controlled — значение поля хранится в state React и передаётся через `value`/`onChangeText`, React — единственный источник правды. Uncontrolled — значение хранится в самом нативном компоненте (DOM/native view), доступ через ref (`defaultValue` + `ref.current`). В RN формах обычно используют controlled через Formik (значения в Formik state) — это даёт валидацию на каждое изменение, но может быть дороже по ре-рендерам на больших формах, где uncontrolled + `onBlur`-валидация иногда выгоднее.

**Error Boundaries.**
Классовый компонент с `static getDerivedStateFromError`/`componentDidCatch`, ловит ошибки рендера в дереве детей и показывает fallback UI вместо краша всего приложения. НЕ ловит: ошибки в event handlers (там обычный `try/catch`), ошибки в асинхронном коде (`setTimeout`, промисы вне рендера), ошибки на стороне сервера (SSR), ошибки в самом Error Boundary. В проекте на Sentry обычно `ErrorBoundary` из `@sentry/react-native` заворачивает `App.tsx`, чтобы одновременно показывать fallback и репортить в Sentry.

## 3. React Native — платформенная специфика

**New Architecture: Fabric, TurboModules, JSI.**
- **JSI (JavaScript Interface)** — C++ прослойка, которая даёт JS-движку прямые, синхронные ссылки на нативные объекты/методы, без сериализации в JSON и без асинхронного моста. Это фундамент, на котором построены Fabric и TurboModules.
- **Fabric** — новый рендерер UI, работает через JSI: layout (Yoga) и создание нод происходит с прямым доступом к C++ core, поддерживает синхронный layout-эффект и concurrent-фичи React 18.
- **TurboModules** — замена старым Native Modules: модули грузятся лениво (только при первом обращении, а не все сразу при старте), вызовы идут напрямую через JSI, а не через асинхронную JSON-сериализованную очередь моста.
Старый мост — все вызовы JS↔Native сериализовались в JSON-строки и шли асинхронно через очередь батчей, что было узким местом для высокочастотных операций (скролл, жесты, анимации).

**Hermes vs JSC.**
Hermes — JS-движок от Meta, оптимизированный под мобильные устройства: компилирует JS в байткод заранее (ahead-of-time, на этапе сборки), а не парсит/JIT-компилирует JS на устройстве при каждом запуске — это резко уменьшает TTI (time to interactive) и memory footprint. JSC (JavaScriptCore) — движок Safari/WebKit, JIT-компиляция на устройстве, исторически дефолтный в RN, но медленнее стартует и потребляет больше памяти на слабых Android-устройствах.

**Metro bundler vs Webpack.**
Metro заточен под мобильную специфику: быстрый инкрементальный ребилд (кэширование по хэшам файлов), fast refresh "из коробки", единый bundle-граф без сложного code-splitting (в отличие от Webpack, где code splitting и множество chunk'ов — стандартная практика для веба). Resolver/transformer в Metro конфигурируется через `metro.config.js` — например, `react-native-svg-transformer` перехватывает импорт `.svg` и превращает его в React-компонент на этапе трансформации, а не в рантайме.

**Managed vs bare Expo workflow.**
Managed — весь нативный код скрыт, работаешь только с Expo SDK и JS, сборки идут через EAS; ограничение — нельзя добавить произвольный нативный модуль без "prebuild"/eject. Bare — `android/`/`ios/` директории закоммичены и редактируются напрямую, доступны любые нативные модули и кастомный нативный код, но теряется часть "магии" managed workflow (нужно вручную поддерживать нативные проекты). Bare обязателен, когда нужен нативный модуль/SDK без Expo-конфиг-плагина, кастомные пермишены/entitlements, глубокая интеграция с native SDK (например, специфичный push-провайдер, кастомный Android widget).

**Нативный модуль (старый бридж vs TurboModules/JSI).**
Старый способ: на Android — класс extends `ReactContextBaseJavaModule`, методы аннотированы `@ReactMethod`, регистрируются в `ReactPackage`; на iOS — класс с макросами `RCT_EXPORT_MODULE`/`RCT_EXPORT_METHOD`. Вызов идёт асинхронно через мост (JSON-сериализация аргументов). Новый способ (TurboModules) — модуль описывается через Codegen (spec на TS/Flow), генерируется нативный интерфейс, вызовы идут через JSI напрямую (могут быть синхронными), модуль подгружается лениво при первом обращении из JS, а не грузится весь пакет модулей на старте.

**Senior: JSI напрямую.**
Библиотеки типа `react-native-reanimated` или `react-native-mmkv` регистрируют в JSI C++ функции/объекты, которые JS может вызывать синхронно, без похода через асинхронную очередь моста. Это критично для случаев, где нужен ответ в том же тике — например, чтение значения из MMKV storage синхронно при рендере, или обновление transform-стилей на UI-потоке на каждый кадр жеста без похода через JS thread.

**`Platform.OS`, платформенные файлы.**
`Platform.OS === 'ios' | 'android'` для точечных различий внутри компонента; `.ios.tsx`/`.android.tsx` — когда реализация экрана/компонента для платформ расходится настолько, что удобнее держать два файла (Metro сам резолвит нужный при бандлинге). Разделение на файлы стоит делать, когда различий много (полдесятка `if`/`Platform.select` подряд) — иначе это лишний оверинжиниринг, и лучше оставить `Platform.select` внутри одного файла.

**Deep linking.**
Требует конфигурации на нативном уровне: `AndroidManifest.xml` (intent-filter с `scheme`/`host`, или App Links с `autoVerify` для `https`-схем) и `Info.plist` (`CFBundleURLTypes` для custom scheme, Associated Domains — для Universal Links). На JS-стороне React Navigation принимает `linking` prop с маппингом `path → route`, обрабатывает как холодный старт по ссылке (`Linking.getInitialURL`), так и переход в уже открытом приложении (`Linking.addEventListener`).

**Push-уведомления: foreground/background/killed.**
- Foreground — приложение открыто, обработчик получает сообщение напрямую в JS (`onMessage`), нужно самому показать локальное уведомление, иначе система его не покажет.
- Background — приложение свёрнуто; ОС сама показывает уведомление (data-only сообщения обрабатываются через `setBackgroundMessageHandler`).
- Killed — приложение полностью закрыто; на Android background handler всё равно может сработать (регистрируется в `index.js` до `AppRegistry.registerComponent`), на iOS есть более жёсткие ограничения (silent push может не разбудить приложение, если пользователь force-quit).

**`patch-package`.**
Позволяет закоммитить diff прямо поверх зависимости в `node_modules`, чтобы пропатчить баг библиотеки без форка. Патч хранится в `patches/` и применяется автоматически через `postinstall`. Риск: при апдейте версии пропатченного пакета патч может перестать применяться "тихо" (или конфликтовать) — нужно ревьюить `patches/` при каждом апдейте зависимостей и убеждаться, что патч ещё нужен/применяется.

## 4. Производительность

**Три потока: JS thread, UI/Main thread, native modules thread.**
- **JS thread** — выполняет весь JS-код (компоненты, бизнес-логика, обработка событий). Если он занят долгим синхронным вычислением — блокируются анимации/жесты, если они завязаны на JS thread.
- **UI/Main thread (native)** — рисует нативные view, обрабатывает жесты на native-уровне.
- **Shadow/layout thread** — считает layout через Yoga (flexbox-движок) отдельно от UI thread.
- **Native modules thread** — выполняет нативные вызовы, которые не должны блокировать UI (например, файловый I/O).
Типичная блокировка — тяжёлый `JSON.parse` большого ответа API или несложная, но частая обработка на JS thread во время скролла/анимации, из-за чего кадры начинают дропаться (jank), если анимация не вынесена на UI thread через Reanimated.

**Диагностика лишних ре-рендеров.**
React DevTools Profiler показывает, какие компоненты рендерились и почему ("why did this render" — Highlight Updates). Flipper с React DevTools плагином — то же самое, но в контексте RN-приложения на устройстве. `why-did-you-render` — библиотека, которая патчит React и логирует в консоль причину каждого лишнего ре-рендера конкретного компонента (какой проп/state изменился по ссылке, хотя по значению не изменился).

**`FlatList` vs `FlashList`.**
`FlatList` рендерит/анрендерит элементы за пределами viewport (`windowSize`), но при инициализации всё равно может тормозить на больших списках из-за пересчёта layout. `FlashList` (Shopify) использует recycling — переиспользует уже смонтированные view-инстансы вместо unmount/mount при скролле (аналогично `RecyclerView`/`UICollectionView` под капотом), что даёт значительно более стабильный FPS на длинных/сложных списках. Общие оптимизации для обоих: `keyExtractor` со стабильным ключом, `getItemLayout` (если высота элемента известна заранее — убирает необходимость измерять layout асинхронно), `removeClippedSubviews` на Android, избегание inline-функций в `renderItem` (создают новую ссылку каждый рендер).

**Bundle size.**
Hermes bytecode прекомпилируется на этапе сборки — уменьшает размер по сравнению с сырым JS + убирает runtime-парсинг. Inline requires (`enableInlineRequires` в Metro) откладывают `require()` модуля до первого реального использования вместо загрузки всего графа при старте. Lazy loading экранов — через `React.lazy`/динамический import для тяжёлых, редко посещаемых экранов, чтобы не тащить их код в стартовый бандл.

**Reanimated vs Animated API.**
`Animated` API в старой архитектуре по умолчанию гонит обновления через мост на каждый кадр (если не включен `useNativeDriver`, что тоже ограничено — не все свойства поддерживает). `Reanimated` компилирует "worklets" — функции, которые исполняются прямо на UI-потоке (через JSI), без похода в JS thread на каждый кадр жеста/анимации — поэтому анимации остаются плавными даже если JS thread в этот момент занят чем-то тяжёлым.

**Senior: профилирование через Systrace/Perfetto/Instruments.**
Systrace/Perfetto (Android) — системные трейсы, показывающие активность по потокам (JS, UI, GPU) с точностью до кадра, помогают найти, какой поток "не успевает" за 16мс/кадр (для 60fps). Instruments (iOS, Time Profiler/Allocations) — находит CPU hotspots и memory leaks на нативном уровне, полезно когда узкое место не в JS, а, например, в перерасчёте нативного layout или в тяжёлой отрисовке.

**Оптимизация изображений.**
Кэширование (на диске и в памяти) — `react-native-fast-image` даёт агрессивный кэш из коробки в отличие от стандартного `Image`. Правильный `resizeMode` и загрузка изображения в разрешении, близком к реально отображаемому (не грузить 4K картинку под превью 100×100). Форматы — WebP вместо PNG/JPEG там, где поддерживается, для уменьшения веса.

**Memory leaks.**
Частые источники: подписки на Firebase listeners/event emitters без `unsubscribe` в cleanup; `setInterval`/`setTimeout` без `clearInterval`/`clearTimeout` при размонтировании; замыкания в долгоживущих объектах (синглтоны, глобальные обработчики), которые держат ссылку на компонент/большой state. Диагностика — через памяти-профайлер (Xcode Instruments Allocations, Android Studio Memory Profiler) или просто повторный вход/выход с экрана с наблюдением за ростом heap.

## 5. State management

**Redux Toolkit vs Context vs Zustand.**
Redux Toolkit — предсказуемый unidirectional flow, мощный DevTools (time-travel debugging), встроенная борьба с boilerplate (`createSlice`, `createAsyncThunk`), но требует Provider на верхнем уровне и определённой дисциплины по структуре. Context — простой, встроенный в React, но без селекторов любое изменение value ре-рендерит всех потребителей (см. раздел 2) — плохо масштабируется на часто меняющийся большой state. Zustand — минималистичный, без Provider, с селекторами из коробки (подписка только на нужный кусок state), меньше boilerplate чем Redux, но менее строгая структура и меньше "из коробки" (нет автоматической нормализации, DevTools интеграция скромнее).

**RTK Query vs классические thunks/axios.**
RTK Query генерирует хуки (`useGetXQuery`) с автоматическим кэшированием по ключу запроса, дедупликацией параллельных одинаковых запросов, инвалидацией через `tags` (запрос помечен `providesTags`, мутация — `invalidatesTags`, при инвалидации RTKQ сам рефетчит нужные запросы). `refetchOnFocus`/`refetchOnReconnect` — автоматический рефетч при возврате фокуса на экран/восстановлении сети. Классические thunks + axios — полный контроль, но всё кэширование/дедупликация/инвалидация нужно писать руками, что на практике часто выливается в дублирующийся boilerplate по каждому домену.

**Senior: нормализация состояния через `createEntityAdapter`.**
`createEntityAdapter` хранит сущности в форме `{ ids: [], entities: { [id]: entity } }` вместо массивов — даёт O(1) доступ по id, встроенные CRUD-редьюсеры (`addOne`, `updateOne`, `removeMany`), и, что важнее, единый источник правды для сущности, если она используется в нескольких местах (например, один и тот же `event` в списке и на экране деталей) — обновление происходит в одном месте вместо синхронизации дублей по разным срезам state.

**`redux-persist`.**
Персистить стоит только то, что должно пережить перезапуск приложения и не устареет мгновенно — токен авторизации, языковые/тема-настройки, возможно "черновики" форм. НЕ стоит персистить серверные данные, которые и так кэшируются через RTK Query (дублирование источника правды), или часто меняющийся UI-state. Миграции — `redux-persist` поддерживает `version` + `migrate` функцию, которая при смене структуры персистируемого state трансформирует старые сохранённые данные в новую форму, иначе после апдейта приложения можно получить краш из-за несовместимой формы state.

**Prop drilling без глобального стейта.**
Composition (передавать `children`/render props вместо пробрасывания данных через N уровней), локальные Context для конкретного поддерева (например, `FormContext` только внутри формы), кастомные хуки, инкапсулирующие связанные state+логику рядом с местом использования — часто "проблема" prop drilling на самом деле сигнал, что компонент нужно разбить иначе (поднять состояние ближе к точке использования, а не растягивать на всё дерево).

## 6. Навигация

**React Navigation: stack/tab/drawer.**
Stack navigator — экраны кладутся друг на друга (push/pop), типичная навигация "вперёд/назад". Tab — параллельные "ветки" с сохранением состояния между переключениями (по умолчанию не размонтируются). Drawer — боковое меню поверх/сбоку от контента. Экраны монтируются лениво при первом переходе; `initialRouteName` задаёт стартовый экран навигатора (в проекте — переключение между `TabNavigation`/`SignInOnboarding` в зависимости от наличия токена).

**Типобезопасная передача параметров.**
Определяется `type RootStackParamList = { Home: undefined; EventDetails: { eventId: string } }`, стек типизируется как `createNativeStackNavigator<RootStackParamList>()`, а `useNavigation`/`useRoute` параметризуются этим типом — TS тогда не даст вызвать `navigate('EventDetails')` без обязательного `eventId` или с параметром неверного типа.

**Deep linking конфигурация.**
`linking` prop у `NavigationContainer`: `{ prefixes: ['myapp://', 'https://myapp.com'], config: { screens: { EventDetails: 'event/:id' } } }`. React Navigation сам матчит URL по этой конфигурации и строит нужный стек экранов, включая случай холодного старта по ссылке.

**Senior: производительность навигации.**
`react-native-screens` заменяет JS-based view-контейнеры на нативные экраны (`UIViewController`/`Fragment`), что даёт нативную производительность переходов и позволяет ОС выгружать невидимые экраны из памяти. Lazy mounting табов (`lazy: true` в tab navigator) — экран таба монтируется только при первом посещении, а не сразу все табы при старте приложения.

## 7. Тестирование

**Jest + React Native Testing Library.**
Философия RNTL — тестировать то, что видит/делает пользователь (по тексту, роли, testID), а не внутреннюю реализацию (state/пропсы конкретного компонента) — так тесты не ломаются при рефакторинге, если поведение не изменилось. Нативные модули мокаются через `jest.mock` (часто уже есть готовые моки в `jest-setup` для Firebase, AsyncStorage и т.д. — `@react-native-firebase` и подобные библиотеки обычно поставляют собственные jest-моки).

**Snapshot-тесты.**
Плюс — быстро ловят неожиданные изменения в выводе рендера. Риск — легко превращаются в "формальность": разработчик видит упавший снэпшот, не разбирается, а просто жмёт `--updateSnapshot`, и тест перестаёт что-либо реально проверять. Разумно использовать точечно (например, для чистых presentational-компонентов), не как основной вид теста.

**E2E: Detox/Maestro.**
Detox — "серый ящик", синхронизируется с состоянием приложения (ждёт, пока JS thread/анимации/сетевые запросы утихнут) — надёжнее, но сложнее в настройке и требует пересборки приложения под тесты. Maestro — "чёрный ящик", проще в написании (YAML-флоу), не требует специальной сборки, но менее строгие гарантии синхронизации. Оправданы для критичных пользовательских путей (регистрация, оплата, покупка билета) — полное покрытие E2E дорого поддерживать на каждый чих.

**Senior: тестовая пирамида для мобильного проекта.**
Основа — unit-тесты (чистая логика, редьюсеры, хелперы, хуки без сложных side effects) — быстрые, дешёвые, много. Средний слой — integration-тесты компонентов через RNTL (экран + его хуки + моки API). Верх — немного E2E-тестов на самые критичные флоу (checkout, авторизация). Соотношение примерно повторяет классическую пирамиду — много unit, меньше integration, минимум дорогих E2E.

## 8. Архитектура и организация кода

**Layer-based vs feature-based структура.**
Layer-based (`screens/`, `components/`, `store/`, ...) — понятен новичкам, но на большом проекте логика одной фичи размазана по десятку папок, сложно понять границы фичи и что можно удалить при её выпиливании. Feature-based (`features/<domain>/{screens,components,hooks,helpers}`) — всё, что относится к фиче, живёт рядом, легче поддерживать границы и удалять фичу целиком. Часто используется гибрид: `shared/` для действительно кросс-фичевого кода + `features/` для доменной логики (именно так организован этот проект).

**Миграция JS → TS в живом проекте.**
Постепенно, файл за файлом, без "стоп-конвейера": включить `allowJs` + `checkJs: false`, мигрировать по мере правок (трогаешь файл — переводишь в TS), держать `.tsc-baseline` (снапшот текущих ошибок) и в CI/гейте проверять, что PR не добавляет НОВЫХ ошибок сверх baseline — так typecheck не блокирует работу над legacy-кодом, но не даёт множить проблему. Постепенно повышать строгость (`strict` по частям, а не сразу весь флаг) там, где это не парализует разработку.

**i18n + RTL — грабли.**
Зеркалирование layout при переходе на RTL-язык (иврит/арабский) — `flexDirection: 'row'` визуально зеркалится системой автоматически при `I18nManager.isRTL`, но абсолютное позиционирование (`left`/`right` вместо `start`/`end`) — нет, и это частый источник багов с "уехавшими" элементами. Смена языка на RTL/LTR обычно требует `I18nManager.forceRTL()` + полный рестарт JS-рантайма (`RNRestart` или аналог), потому что RTL-флаг читается один раз при старте нативного слоя — просто сменить строку локали недостаточно.

**Senior: проектирование API-слоя под смену backend contract.**
Через DTO-мапперы/адаптеры на границе API-слоя: RTK Query эндпоинт возвращает "сырой" ответ backend, но `transformResponse` превращает его в стабильную доменную модель, которой пользуется остальное приложение. Если backend меняет форму ответа — правится только маппер в одном месте, а не все места использования по всему коду.

**Path aliases — синхронизация.**
Алиасы должны совпадать в `babel.config.js` (`module-resolver`, реальный резолвинг при сборке/Metro), `tsconfig.json` (`paths`, чтобы TS понимал импорты при тайпчеке) и `.eslintrc` (import resolver, чтобы ESLint не ругался "module not found"). Рассинхрон — типичная причина, когда "TS видит модуль, но в рантайме падает" или наоборот.

**Feature flags / поэтапный rollout на мобилке.**
Сложнее, чем в вебе: нет мгновенного отката (нельзя просто "перевыкатить" — пользователи должны обновить приложение из стора, а апрув в сторе занимает время). Поэтому фича-флаги на сервере (remote config) — способ выключить сломанную фичу без нового релиза; staged rollout в сторах (постепенный % пользователей) — способ ограничить blast radius бага до полной раскатки.

## 9. CI/CD и релизы

**Fastlane / EAS Build.**
Fastlane — автоматизация локальной/CI сборки и деплоя в App Store Connect/Google Play (сборка, подпись, загрузка, скриншоты, метаданные) через Ruby-скрипты (`Fastfile`). EAS Build — облачная сборка от Expo, снимает необходимость держать macOS-раннер для iOS-сборок самостоятельно, интегрируется с Expo-экосистемой (EAS Update для OTA).

**Code push / OTA обновления.**
Можно обновить без ревью в сторе: JS bundle + ассеты (то, что не трогает нативный код) — через CodePush или EAS Update. Нельзя: любые изменения в нативном коде, новые нативные зависимости, изменения пермишенов — это требует полноценного релиза через стор с ревью.

**Версионирование.**
Android — `versionCode` (внутренний целочисленный, должен монотонно расти для каждого нового билда) и `versionName` (человекочитаемая строка, например "2.3.1"). iOS — `CFBundleVersion` (build number, должен расти для каждой загрузки в App Store Connect) и `CFBundleShortVersionString` (marketing version).

**Senior: staged rollout, canary, откат.**
Staged rollout — выкатка на % пользователей (например, Google Play Console позволяет 5% → 20% → 50% → 100%), мониторя crash rate на каждом этапе перед увеличением процента. Canary — похожая идея для внутреннего/бета-контура перед публичным релизом. Откат в проде при обнаруженном краше: остановить rollout (не давать проценту расти дальше), при возможности откатить через remote feature flag сломанную фичу, при критичности — hotfix-релиз с ускоренным ревью (expedited review есть у обоих сторов для критичных багов).

## 10. Дебаг и мониторинг в проде

**Sentry/Crashlytics — символикация.**
JS-стектрейсы в проде минифицированы/обфусцированы (Hermes bytecode вообще не содержит оригинальных имён) — для читаемого стектрейса нужно загружать source maps (для JS) и debug-символы/dSYM (для нативного iOS-кода)/mapping.txt (ProGuard/R8 на Android) в Sentry/Crashlytics при каждой сборке, обычно как шаг CI сразу после сборки релиза.

**JS-краш vs нативный краш.**
JS-краш — необработанное исключение в JS-коде, стектрейс будет содержать JS-файлы/функции (после символикации — читаемые имена компонентов/хелперов). Нативный краш — сегфолт/исключение на уровне Java/Kotlin/Swift/Objective-C/C++, стектрейс будет содержать нативные классы/методы, часто требует dSYM/ProGuard mapping отдельно от JS source maps, и может вообще не всплыть в JS error boundary, потому что процесс приложения крашится целиком, а не просто JS-рантайм.

**Отладка через Flipper/Chrome DevTools/Hermes debugger.**
Flipper — универсальный дебаг-хаб (сеть, layout inspector, React DevTools, логи, база данных AsyncStorage) для RN-приложения на устройстве/симуляторе. Chrome DevTools/Hermes debugger — отладка непосредственно JS-кода (breakpoints, консоль, профайлер памяти/CPU) через `chrome://inspect` при подключении к Hermes debugger сокету, либо через встроенный RN DevTools (с New Architecture — своя более прямая интеграция без прокси через Chrome).

**Senior: алертинг и метрики.**
Crash-free rate (% сессий/пользователей без краша) — ключевая метрика здоровья релиза, обычно отслеживается по каждой версии отдельно, с алертом при падении ниже порога после релиза. ANR rate (Application Not Responding) на Android — доля случаев, когда UI thread завис на 5+ секунд, тоже метрика per-release. Обе метрики завязывают на staged rollout — если crash-free/ANR ухудшается на первых процентах раскатки, rollout нужно останавливать до фикса.

## Практические задания (live coding)

1. **Написать кастомный хук `useDebounce`/`useThrottle`.**
```ts
function useDebounce<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(id);
  }, [value, delayMs]);
  return debounced;
}
```
Ключевые моменты для оценки: очистка таймера в cleanup (иначе устаревшие вызовы "стреляют" после нового ввода), корректные зависимости эффекта.

2. **`useAsync`/`useFetch` с loading/error/data.**
Ожидается: состояние из трёх полей (или discriminated union `{status:'idle'|'loading'|'success'|'error', data?, error?}`), защита от установки state после размонтирования (или AbortController для отмены запроса), обработка гонки (устаревший ответ не должен перезаписать более свежий — сравнение через флаг/ref текущего запроса или `AbortController`).

3. **Найти причину лишних ре-рендеров в данном компоненте.**
Смотреть на: инлайн-объекты/функции в пропсах без мемоизации, нестабильный `key` в списках, контекст с широким value без разделения, отсутствие `React.memo` там, где родитель ре-рендерится часто, а дочерний компонент — тяжёлый и с теми же пропсами.

4. **Infinite scroll с пагинацией на `FlatList`/`FlashList`.**
Ожидается: `onEndReached` + `onEndReachedThreshold`, защита от повторного вызова во время уже идущей загрузки (флаг `isFetchingNextPage`), `ListFooterComponent` со спиннером, корректный `keyExtractor`, в идеале — интеграция с RTK Query `fetchMore`/infinite query паттерном вместо ручного стейта страниц.

5. **Нативный модуль-обёртка (или мок).**
Ожидается понимание контракта: экспортируемые методы, Promise-based API в JS, обработка ошибок через reject с кодом ошибки, и — для Senior — понимание разницы вызова через старый мост (асинхронно всегда) vs TurboModule (может быть синхронным через JSI).

6. **Senior: слой абстракции над FCM + APNs с единым JS API.**
Ожидается дизайн интерфейса типа `registerForPushNotifications(): Promise<Token>`, `onMessage(handler)`, `onBackgroundMessage(handler)`, который на Android резолвится в `@react-native-firebase/messaging`, а особенности iOS (permission prompt, silent push ограничения) инкапсулированы за тем же API — обсуждение, как обрабатывать платформенные различия без утечки деталей в вызывающий код.

7. **Senior: ревью PR с race condition в async-коде.**
Классический пример — поиск с debounce, где ответ на предыдущий (уже неактуальный) запрос приходит позже ответа на последний запрос и перезаписывает результат устаревшими данными. Фикс — AbortController на предыдущий запрос при новом вызове, либо сравнение id/timestamp запроса перед записью в state, либо RTK Query (который это решает "из коробки" через кэш по ключу запроса).

## Вопросы про опыт (behavioral, но технические)

Ожидаемая структура сильного ответа (по методике STAR): конкретная ситуация → что именно делал → какой инструмент/подход применил → измеримый результат.

- **Самый сложный performance-баг.** Хороший ответ называет конкретный симптом (дропы FPS, ANR, медленный TTI), инструмент диагностики (Profiler/Systrace/Instruments), найденную причину и измеримое улучшение (например, "с 40fps до стабильных 60fps на списке из 500 элементов после перехода на FlashList").
- **Нативный модуль vs существующая библиотека.** Критерии выбора: покрывает ли существующая библиотека нужный функционал, насколько активно поддерживается, стоимость поддержки собственного нативного кода (два языка — Kotlin/Swift — вместо одного JS), риск при апдейтах RN/ОС.
- **Миграция на New Architecture.** Типичные проблемы: сторонние библиотеки без поддержки Fabric/TurboModules на момент миграции, необходимость аудита всех нативных модулей, регрессии в специфичных边ge-кейсах layout из-за другого движка рендеринга.
- **Процесс код-ревью и тестирования в команде.** Ожидается говорить про конкретные практики: gate на CI (typecheck/lint/тесты перед мержем), стандарты по покрытию для новых фич, ревью-чеклисты под мобильную специфику (проверка на обеих платформах, проверка на RTL, проверка на реальном устройстве не только симуляторе).
