## 1. Целевая аудитория

Разработчик, который **уже умеет самостоятельно создавать React Native приложения** и работал на коммерческих проектах, но хочет:

- систематизировать знания, накопленные практикой;
- освежить фундамент JavaScript / TypeScript / React;
- закрыть пробелы в теории, которые не всплывают в ежедневной работе;
- понять внутреннее устройство React и React Native;
- глубже разобраться в performance;
- понимать native layer, а не обходить его;
- научиться принимать архитектурные решения и обосновывать их;
- перейти от «умею реализовать» к «понимаю почему и умею спроектировать».

**Это не курс Junior → Middle → Senior.** Это курс Experienced React Native Developer → Senior React Native Engineer.

### Кому курс не подходит

- Тем, кто изучает React Native с нуля: здесь нет обучения базовому синтаксису и нет пошагового «сделай первый экран».
- Тем, кто ищет готовые рецепты без объяснения причин: курс построен вокруг trade-offs, а не вокруг «правильных» ответов.
- Тем, кто хочет только подготовиться к собеседованию: для этого в репозитории есть отдельный банк вопросов (`V1.md`, `V2.md`, `V3.md`).

## 2. Уровень на входе

Входной уровень описывается не через «знаю синтаксис», а через способности. Разработчик должен уметь без помощи:

- поднять новый RN-проект и запустить его на обеих платформах;
- написать экран со списком, формой и навигацией между экранами;
- подключить REST API, обработать загрузку и ошибку;
- подключить стороннюю библиотеку, включая ту, что требует нативной линковки;
- прочитать чужой код проекта и внести в него изменение;
- собрать релизную сборку хотя бы под одну платформу;
- пользоваться git в команде.

Если что-то из этого списка вызывает затруднение — сначала практика, потом курс.

### Чего курс не требует на входе

- Опыта написания нативных модулей на Kotlin/Swift.
- Понимания устройства Fabric, TurboModules, JSI.
- Опыта настройки CI/CD, мониторинга, staged rollout.
- Глубокого TypeScript (conditional types, `infer`).
- Умения профилировать приложение.

## 3. Результат на выходе

Результат формулируется как проверяемые утверждения, а не как список тем.

**Диагностика и performance**

- Локализую дроп FPS до конкретного слоя (JS thread / UI thread / rendering / images / native) и доказываю замерами, а не предположениями.
- Читаю вывод Profiler, Perfetto/Systrace, Instruments и делаю из него вывод о причине.
- Нахожу утечку памяти и объясняю, какое замыкание или подписка её держит.

**Данные и сеть**

- Проектирую refresh-token flow, корректный при 10 параллельных 401.
- Разделяю клиентский стейт и серверный кэш и обосновываю, где лежит каждая единица данных.
- Проектирую offline-first поток с очередью мутаций, optimistic updates и разрешением конфликтов.

**Архитектура**

- Предлагаю план изменения архитектуры для приложения из 40 feature-модулей, с этапами, рисками и критерием отката.
- Обосновываю выбор между layer-based и feature-based структурой под конкретный контекст команды.
- Решаю, нужен ли проекту собственный нативный модуль, и считаю стоимость этого решения.

**Native и production**

- Пишу нативный модуль (TurboModule) и понимаю, чем он отличается от вызова через старый мост.
- Выстраиваю релизный процесс: подпись, версионирование, staged rollout, откат.
- Настраиваю symbolication и отличаю JS-краш от нативного по отчёту.

**Senior reasoning**

- Провожу threat modeling для мобильного приложения и выбираю mitigation осознанно, с пониманием его границ.
- Прохожу system design сессию и защищаю решение через trade-offs.
- Пишу ADR и postmortem так, чтобы по ним можно было принять решение без меня.

## 4. Философия курса

Курс не отвечает на вопрос «что такое X». Он отвечает на вопросы:

- **Почему X?** — какую проблему решает, что было до него.
- **Как X работает внутри?** — механизм, а не API.
- **Когда X не подходит?** — границы применимости.
- **Какие альтернативы?** — и чем они хуже или лучше именно здесь.
- **Какие последствия у решения?** — для производительности, поддержки, команды, релизов.
- **Как найти проблему?** — методика, а не список причин.

Три правила, которые действуют на всём протяжении курса:

1. **Фундамент не пропускается, но и не растягивается.** Базовые темы присутствуют как REFRESH — компактно, с акцентом на грани и ошибки, а не на синтаксис.
2. **Ни одна тема не живёт изолированно.** У каждой темы есть явная связь с уже изученным и с тем, что будет дальше.
3. **Количество уроков — следствие содержания.** Не дробим искусственно, не склеиваем разные сложные концепции ради уменьшения счёта, объединяем только тесно связанные простые темы, Senior-темы оставляем отдельными уроками. Ориентир — approximately 130–150 lessons, и это **soft target**: курс не укладывается в число насильно. Если содержание требует больше уроков, их становится больше.

## 5. Уровни уроков: REFRESH / DEEP DIVE / SENIOR

### 🟢 REFRESH

Быстро обновить то, что разработчик, скорее всего, уже знает. Формат фиксированный:

```
краткий refresh  →  короткая проверка понимания  →  RN relevance
```

- **Refresh** — суть, без обучения с нуля, с акцентом на грани и неочевидные случаи.
- **Проверка понимания** — 3–5 вопросов или микро-задача; цель не оценка, а обнаружение пробела.
- **RN relevance** — где именно эта база бьёт в React Native. Без этой части урок превращается в beginner-материал.

Тесно связанные простые темы можно объединять в один урок. Объём 🟢-урока — минимальный достаточный.

### 🟡 DEEP DIVE

Разобраться в механизме и причинах. Обязателен шаблон из семи углов (раздел 6). Это основной уровень курса.

### 🔴 SENIOR

Внутреннее устройство, trade-offs, архитектурные последствия, принятие решений. Такой урок почти всегда содержит сценарий с неполными данными и требует обоснованного выбора, а не воспроизведения ответа.

**Правило:** не делать каждый урок 🔴 искусственно. Ориентировочное распределение — 🟢 ≈ 20 %, 🟡 ≈ 50 %, 🔴 ≈ 30 %, и оно подчинено содержанию, а не наоборот.

### Пример применения уровней к одной теме: `map()`

| Уровень | Содержание |
|---|---|
| 🟢 | синтаксис, callback, return, новый массив |
| 🟡 | references, mutation, object identity, immutability |
| 🔴 | влияние на React rendering, memoization, referential equality, performance |

Отдельного большого beginner-урока «что такое map» не существует.

## 6. Семь углов разбора темы

Обязательный шаблон для 🟡 и 🔴 уроков:

1. **Что это?** — определение, короткое.
2. **Как это работает?** — механизм внутри.
3. **Почему это важно?** — какую проблему решает.
4. **Где это используется в React Native?** — конкретные места платформы.
5. **Какие ошибки обычно совершают разработчики?** — типичные грабли с объяснением причины.
6. **Какие trade-offs существуют?** — цена решения.
7. **Как эта тема связана с другими частями системы?** — ссылки назад и вперёд по курсу.

Если на угол 7 нечего сказать — тема, скорее всего, поставлена не в тот блок.

## 7. Этапы курса

### 01 — JavaScript Refresh & Internals

**Цель:** вернуть и достроить модель языка, на которую опираются блоки 03, 05 и 06. Без неё разговор о referential equality, ре-рендерах и утечках памяти превращается в заучивание рецептов.

**🟢 Refresh (отдельные темы, формат Refresh → проверка → RN relevance)**

| Тема | RN relevance (пример акцента) |
|---|---|
| variables и scope | почему `var` в старом коде ломает замыкания в циклах |
| data types | что реально переходит через bridge и почему только сериализуемое |
| coercion и сравнения | `==` в условиях рендера, falsy `0` в `{count && <View/>}` |
| objects | shallow copy и почему `setState` «не сработал» |
| arrays | идентичность массива как источник ре-рендера списка |
| array methods | `map`/`filter`/`reduce` и новые ссылки на каждый рендер |
| destructuring | деструктуризация пропсов и потеря мемоизации |
| spread/rest | `...props` и неявная передача лишнего в нативный компонент |
| modern JS syntax | optional chaining, nullish, logical assignment; поддержка в Hermes |
| modules | ESM vs CJS, как это видит Metro, barrel-файлы и их цена |
| error handling | `try/catch` и асинхронность, почему ошибка «потерялась» |

**🟡/🔴 Deep Dive (отдельные уроки)**

references · immutability · closures · execution context · `this` · prototypes vs классы · promises · async/await · event loop · microtasks/macrotasks · memory · garbage collection

**Prerequisites:** нет.

---

### 02 — TypeScript for Experienced Developers

**Цель:** использовать систему типов как инструмент проектирования, а не как аннотации поверх готового кода.

🟢 базовые типы, generics, утилитарные типы (`Partial` / `Pick` / `Omit` / `Record`)
🟡 discriminated unions и narrowing · `interface` vs `type` · `strict` по флагам, что именно включает каждый
🔴 conditional types и `infer` · типизация полиморфного API-слоя · типобезопасность на границах системы (навигация, API, нативные модули)

**Prerequisites:** 01.

---

### 03 — React Deep Dive

**Цель:** понять, что React делает между вызовом `setState` и появлением пикселя, и научиться на это влиять осознанно.

🟡 reconciliation и Fiber · роль `key` · **путь обновления: setState → update queue → batching → scheduling → render → commit** · правила хуков и зависимостей · `useEffect` vs `useLayoutEffect` · referential equality · `memo` / `useMemo` / `useCallback` · Context и его цена, паттерны дробления · controlled vs uncontrolled · Error Boundaries
🔴 Suspense и concurrent features · React Compiler: что он убирает и где ручная мемоизация всё ещё нужна

> **Урок про путь обновления — переходный урок курса JavaScript → React → React Native.** Он отвечает на вопрос, почему вызов `setState` не означает немедленный рендер: обновление попадает в очередь, несколько обновлений батчатся в один рендер, React планирует работу и может её прервать, render-фаза чистая и прерываемая, commit-фаза синхронная. Опирается на очереди задач и микротасков из блока 01 и на reconciliation; готовит блок 05, где «лишний рендер» и «долгий commit» — разные проблемы с разными инструментами.

**Prerequisites:** 01 (references, closures, immutability), 02.

---

### 04 — React Native Core, Internals & Application

**Цель:** перестать воспринимать RN как «React, который рисует нативно», и увидеть систему из потоков, движка, бандлера и нативного слоя.

**Internals** (в порядке изучения)
🔴 **New Architecture: JSI, Fabric, TurboModules** — современная архитектура RN, идёт первой
🟡 Legacy Architecture и Bridge — исторический контекст для чтения старого production-кода
🟡 Shadow Tree и Yoga · Metro: resolver, граф модулей, бандл · **Hermes как JS engine** (bytecode и precompilation, GC движка, profiling, startup/TTI) · **build types: Debug → Debug Optimized → Release**
🔴 **Почему движок имеет значение; JSC как edge case**

> **New Architecture — современная архитектура React Native, а не один из двух равнозначных вариантов.** Для нового проекта выбора между Legacy и New Architecture нет, поэтому урок про актуальное устройство идёт первым, а legacy — вторым, как контекст.
>
> **Не «Bridge 2.0».** Нельзя оставлять модель «был старый мост, стал новый мост». JSI — прямой интерфейс между JS и native, допускающий синхронные вызовы и работу с нативными объектами по ссылке; Fabric — другой рендер-пайплайн с другим владением Shadow Tree; TurboModules — другой контракт модулей с ленивой инициализацией. Обязательный подраздел: «какие интуиции из старой модели здесь не работают» («любой вызов в native асинхронен», «данные всегда сериализуются в JSON», «UI обновляется только из конца очереди»).
>
> **Legacy-урок** разбирает модель JS↔native взаимодействия той архитектуры: передачу аргументов и результатов, callbacks и events, сериализацию и конвертацию данных **как свойство той модели, а не как определение Bridge**, и её ограничения — из которых и выросли JSI, Fabric и TurboModules.
>
> **Hermes — основной движок современного RN**, JSC — специальный/legacy/edge case, а не равнозначная альтернатива. Поэтому второй Hermes-урок отвечает не на «что выбрать», а на «почему движок вообще имеет значение»: startup, память, bytecode вместо парсинга на устройстве, отладка, совместимость, профиль производительности.
>
> **Build types.** `Debug → Debug Optimized → Release`. Обычная Debug-сборка даёт искажённое представление о производительности (dev-проверки, отсутствие оптимизаций, инструментирование), Release плохо подходит для отладки; Debug Optimized — промежуточный тип, сохраняющий отладку без основных искажений.

**Application**
🟢 Expo managed vs bare workflow · `Platform.OS` и платформенные файлы
🟡 стилизация и её нативная проекция · **Accessibility in React Native** (semantics, accessibility props, VoiceOver, TalkBack, focus management, dynamic type, accessibility testing) · `patch-package` и стратегия апгрейдов RN

**Navigation** (внутри этого блока, отдельного блока Navigation в курсе нет)
🟡 Stack · Tabs · nested navigation · params и их типизация · navigation lifecycle · deep linking basics

> **Не дублировать:** влияние навигации на performance — блок 05; deep linking + push + навигация от серверных событий — блок 07.

**Prerequisites:** 03.

### 05 — Performance

**Цель:** заменить набор советов методикой: от симптома к слою, от слоя к замеру, от замера к решению.

🟡 **модель исполнения: JS thread, UI/main thread, render/native work** · бюджет кадра · диагностика лишних ре-рендеров · списки: `FlatList` → `FlashList`, рециклинг, типичные ошибки `keyExtractor`/`getItemLayout` · изображения: декодирование, кэш, размеры · bundle size и TTI · Reanimated и Gesture Handler: worklets на UI thread · утечки памяти в RN · производительность навигации (монтирование экранов, lazy/freeze, тяжёлые экраны в табах)
🔴 профилирование: React Profiler, Perfetto/Systrace, Instruments · методика performance investigation «симптом → слой → замер → гипотеза → проверка»

> **Терминология потоков.** Урок сознательно не называется «три потока» и не вводит модель «в RN ровно три потока». Состав потоков зависит от версии RN, движка и платформы, а названия в инструментах измерения не совпадают с названиями в документации. Поэтому разговор о JS thread, UI/main thread и render/native work обязательно привязывается к трём вещам:
>
> 1. **к архитектуре** — что меняется между старым bridge и Fabric: где выполняется layout, кто владеет Shadow Tree, что происходит синхронно;
> 2. **к инструментам измерения** — какой инструмент показывает какой слой (React Profiler / Perfetto / Instruments / FPS-монитор) и как читать их вывод;
> 3. **к бюджету кадра** — чем «поток занят» отличается от «кадр не успел».

**Prerequisites:** 03, 04.

### 06 — State Management & Data (client state)

**Цель:** научиться решать, где живёт каждая единица состояния, и платить за это осознанно. Блок отвечает за клиентское состояние; серверные данные — блок 07.

🟡 что считать состоянием · local vs shared vs server state и граница с блоком 07 · Context vs Redux Toolkit vs Zustand как решение под контекст, а не как вкус · immutability в редьюсерах (возврат к 01) · селекторы и их мемоизация (возврат к 03) · персистентность: `redux-persist`, миграции схемы · prop drilling без глобального стейта
🔴 нормализация через `createEntityAdapter`
🔴 **завершающий урок блока: «Client State vs Server State: где проходит граница»** — разбор с клиентской стороны: что принадлежит приложению, что является копией чужих данных, кто владеет истиной, что произойдёт при расхождении

**Prerequisites:** 03, 05 (чтобы цена ре-рендеров была уже понятна).

### 07 — Networking & Distributed Data

**Цель:** увидеть приложение как клиента распределённой системы: ненадёжная сеть, устаревшие данные, параллельные запросы, конфликты.

🟡 **вводный урок блока: «Server State как распределённые данные»** — продолжение границы из блока 06 с противоположной стороны: данные устаревают в момент получения, приходят не по порядку, существуют в нескольких копиях, и клиент не владеет истиной
🟡 HTTP-слой и единый client · ошибки, retry, backoff, таймауты · authentication и authorization · access token и refresh token · session management · TanStack Query / RTK Query как кэш · инвалидация · пагинация и infinite query · race conditions и отмена запросов · WebSocket и server events · deep linking + push + навигация от серверного события
🔴 refresh-token flow при параллельных 401 · offline-first: очередь мутаций, optimistic updates, откат · конфликты и синхронизация

**Prerequisites:** 01 (promises, event loop), 06.

### 08 — Architecture

### 10 — Production & Tooling

**Цель:** довести приложение до пользователя и узнать о проблеме раньше, чем о ней напишут в отзывах.

🟡 схемы сборки и подпись · версионирование (версия приложения, build number, версия бандла) · Fastlane / EAS Build · CI-пайплайн · OTA-обновления: что они дают и где заканчиваются · Sentry / Crashlytics и symbolication · JS-краш vs нативный краш · метрики и алертинг
🔴 **совместимость JS-бандла и нативного бинарника** · staged rollout, canary, критерий и механика откатa · production security: threat → mitigation → limitations → trade-offs → decision для secure storage, certificate pinning, secrets, obfuscation, app hardening

> **Совместимость — отдельный 🔴-урок, а не примечание к OTA.** OTA обновляет JS и assets, но **не произвольный нативный код**, и это одна из реально болезненных production-проблем RN.
>
> ```
> JS bundle  ↔  native binary  ↔  native modules
> ```
>
> Разбирается: что происходит, когда бандл ожидает нативный модуль, которого нет в установленном бинарнике; версионирование как контракт между бандлом и бинарником; что принципиально нельзя катить через OTA (изменение нативных зависимостей, разрешений, версии RN); когда store-релиз обязателен; как не отправить несовместимый бандл в прод и как откатывать уже отправленный.

> Security-практики в этом блоке не подаются как обязательный чек-лист. Каждая рассматривается как ответ на конкретную угрозу, с явными границами применимости и ценой. См. раздел 15.

**Prerequisites:** 08, 09.

### 11 — Testing

**Цель:** собрать из тестов, которые уже появлялись в проекте, осознанную стратегию: что тестировать, чем, на каком уровне и чего не тестировать вовсе.

🟡 что тестировать в мобильном приложении · Jest и React Native Testing Library · тестирование хуков и асинхронного кода · мокирование нативных модулей · snapshot-тесты: где польза, где шум · **E2E: что он проверяет и чего стоит** · тесты как gate в CI
🔴 тестовая пирамида под мобильный проект · стратегия тестирования в продакшене (мониторинг как часть тестирования, canary как эксперимент)

> **E2E не подаётся как выбор между Detox и Maestro.** Ось урока — не инструменты, а вопросы: что E2E проверяет такого, чего принципиально не проверяет integration test · где его место в пирамиде · полная стоимость (время прогона, инфраструктура, поддержка, время разработчика на разбор падений) · стабильность и флаки как системная проблема, а не как дефект конкретного теста · когда достаточно integration tests · когда E2E действительно оправдан. Detox и Maestro разбираются как реализации с разной ценой и разными ограничениями, а не как равнозначные альтернативы «что лучше».

> Тестирование вводится постепенно с самого начала курса; этот блок даёт систему. См. раздел 16.

**Prerequisites:** 03, 06, 07 (есть что тестировать), 10 (есть куда встраивать).

### Checkpoint после каждого блока

Checkpoint проверяет не запоминание терминов, а способность применять знания. Формат — задача или сценарий с неполными данными, где нужно обосновать решение. Примеры формулировок:

## 15. Security Map

Security — cross-cutting concern. Отдельного крупного самостоятельного этапа нет: каждая тема изучается там, где у неё есть контекст.

| Блок | Security-темы |
|---|---|
| **07 Networking** | authentication · authorization · access token · refresh token · session management |
| **09 Native** | platform permissions · нативные security-возможности платформы (Keychain / Keystore, biometrics) |
| **10 Production** | secure storage · certificate pinning · secrets · obfuscation · app hardening · production security |
| **12 Senior** | threat modeling · security architecture · security trade-offs |

### Как подаётся материал

Security-практики **не формулируются как обязательный чек-лист**. Ни certificate pinning, ни obfuscation, ни app hardening не вводятся фразой «так нужно делать». Каждая тема разбирается по схеме:

```
threat  →  mitigation  →  limitations  →  trade-offs  →  decision
```

- **threat** — от чего конкретно защищаемся, кто атакующий, что он получает в случае успеха;
- **mitigation** — как эта практика противодействует именно этой угрозе;
- **limitations** — чего она не делает и против кого не работает;
- **trade-offs** — цена: сложность сборки, отладки, релизов, риск сломать приложение в поле, влияние на команду;
- **decision** — в каком контексте практику стоит внедрять, в каком — нет, и по какому признаку это решается.

Пример этой схемы для certificate pinning: угроза — MITM на недоверенной сети и перехват трафика; mitigation — привязка к сертификату или публичному ключу; limitations — не защищает от скомпрометированного устройства и от reverse engineering самого приложения; trade-offs — риск полной неработоспособности приложения при ротации сертификата, усложнённая отладка, необходимость плана обновления pin; decision — оправдан там, где цена перехвата высока, и только при наличии процесса ротации.

Задача раздела — чтобы выпускник курса мог обосновать и внедрение, и **отказ** от внедрения.
