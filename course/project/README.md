# RN Academy — сквозной проект курса

**Статус:** код не написан, зафиксированы стадии и правила роста

Один **небольшой longitudinal-проект**, который эволюционирует вместе с курсом. Рабочее название — **RN Academy**: приложение для прохождения курсов с уроками, прогрессом и материалами для офлайн-чтения. Домен выбран так, чтобы в нём естественно появились списки, формы, медиа, авторизация, кэш, офлайн и нативные возможности — но только тогда, когда соответствующая тема изучена.

> **Проект не является вторым полноценным production-продуктом.** Его задача — дать материал для применения изученного, а не вырасти в приложение, которое не стыдно выложить в стор. Из этого следует: минимум экранов, минимум фич, никакой проработки продуктовых деталей, UI ровно настолько, насколько нужно для темы. Если стадия требует добавить функциональность только ради «полноты продукта» — её не добавляют.
>
> Проект нужен для: применения материала · постепенного усложнения · архитектурных решений · performance-экспериментов · тестирования · networking · native integration · production-практик. Всё, что не служит одной из этих целей, в проект не попадает.

## Главное правило

**Архитектура усложняется только после того, как тема изучена.** Заранее ничего не проектируется: на ранних стадиях это просто код, и это нормально. Рефакторинг в feature-based структуру — не «исправление ошибки», а стадия P7, к которой проект должен прийти естественным путём.

Из этого следует:

- на P1 нет React — только модули домена;
- на P3 нет навигации — только компоненты;
- на P6 появляется кэш, а не «сразу правильный слой данных»;
- каждый рефакторинг на поздней стадии — учебный материал сам по себе: разработчик видит, из чего выросла необходимость.

## Стадии

| Стадия | Блоки | Что появляется в проекте | Тесты (Testing Progression) |
|---|---|---|---|
| **P1** | 01 | чистые JS-модули домена без UI: сущности курса, урока, прогресса; функции отбора и агрегации; иммутабельные обновления прогресса; обработка ошибок разбора входных данных | базовый unit test |
| **P2** | 02 | типизированный домен: состояние урока как discriminated union, типы как контракт между модулями | TypeScript / logic tests |
| **P3** | 03 | React-слой: экран списка и экран урока, состояние экрана, мемоизация по необходимости, Error Boundary | React component tests |
| **P4** | 04 | React Native: навигация (табы + стек), app shell, платформенные различия, accessibility | RN integration tests |
| **P5** | 05 | длинный список уроков на рециклинге, изображения, анимации и жесты в бюджете кадра | performance-related tests, где уместно |
| **P6** | 06–07 | клиентский стейт и персистентность; API, authentication с refresh-токеном, кэш, пагинация, офлайн-чтение материалов | API / data tests |
| **P7** | 08–10 | рефакторинг в feature-based структуру с границами модулей; нативная фича (например, биометрический вход или загрузка файлов); релизный пайплайн, symbolication, мониторинг | E2E |
| **P8+** | 11–12 | тестовый контур целиком и его ревизия; capstone | production testing strategy |

## Что проект даёт курсу

| Блок | Что проект делает очевидным |
|---|---|
| 01 | иммутабельность и ссылки видны на реальных данных, без React |
| 02 | невозможное состояние урока перестаёт компилироваться |
| 03 | цена ре-рендера видна на списке из реальных элементов |
| 04 | deep link до урока через вложенную навигацию |
| 05 | один и тот же экран до и после работы над производительностью, с замерами |
| 06 | черновик ответа, прогресс и серверные данные — три разные природы данных на одном экране |
| 07 | офлайн-чтение и отправка прогресса из офлайна с откатом |
| 08 | проект достаточно большой, чтобы границы модулей были нужны, а не декоративны |
| 09 | нативная фича с полным контрактом и обработкой отказа в разрешении |
| 10 | релиз, откат, читаемый стектрейс из продакшена |
| 11 | накопленные тесты, которые нужно привести в систему |
| 12 | система, которую можно спроектировать заново и защитить решение |

## Упражнения вне проекта

Проект не покрывает всё: часть навыков тренируется на отдельном материале, где нужен готовый «чужой» код.

| Тип | Что тренирует | Блоки |
|---|---|---|
| Debugging exercises | методика поиска причины | 03, 05, 09, 10 |
| Performance exercises | «симптом → слой → замер → гипотеза» | 05, 06, 07 |
| Architecture case studies | решение при неполных данных | 08, 09, 12 |
| Code review exercises | видеть последствия, а не стиль | 03, 07, 08, 11, 12 |
| Refactoring exercises | изменение без остановки разработки | 06, 08, 11, 12 |
| System design exercises | проектирование и защита решения | 07, 12 |

## Чего в проекте нет

- Не создаётся заранее сложная структура папок, DI-контейнер или слой абстракций «на будущее».
- Не добавляются зависимости до того, как изучена тема, которую они решают.
- Не пишется «правильная» архитектура с первой стадии — это лишило бы блок 08 материала.
