# 3.6 `useEffect` vs `useLayoutEffect` — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **что пользователь видит между commit и показом** и сколько синхронной работы стоит на пути к кадру.

---

**1. Подсказка позиционируется по высоте якоря через `useEffect` + `setState`. Что видит пользователь на New Architecture, и что изменится с `useLayoutEffect`?**

<details>
<summary>Ответ</summary>

С `useEffect`:

1. первый рендер с начальной позицией (например, `top = 0`) — commit — **кадр показан**;
2. эффект измеряет якорь и ставит `setTop`;
3. повторный рендер и commit — кадр с правильной позицией.

Пользователь видит подсказку на один кадр в неверном месте, затем она «прыгает». Это и есть мигание.

С `useLayoutEffect`: измерение и `setState` происходят внутри commit, до показа; React синхронно выполняет повторный рендер и commit; показывается только кадр с правильной позицией. В New Architecture это работает именно так, потому что layout доступен из JS синхронно — документация RN рекомендует `useLayoutEffect` как место для измерений.

Цена: два рендера и два commit до первого показа, вся эта работа на пути к кадру.

**Ответ «разницы нет, `setState` всё равно асинхронный»** вскрывает незнание того, что обновления из layout-эффекта обрабатываются синхронно до показа.

**Ответ «надо использовать `onLayout`»** — в старой архитектуре это был единственный путь, и он давал тот же прыжок: событие приходило после показа. В New Architecture `onLayout` нужен для отслеживания изменений размера, а не для первого позиционирования.
</details>

---

**2. Почему тяжёлый расчёт в `useLayoutEffect` хуже, чем в `useEffect`, даже если общее время работы одинаковое?**

<details>
<summary>Ответ</summary>

Потому что важно не общее время, а **на каком пути** оно стоит.

`useLayoutEffect` — часть commit, а commit синхронный и непрерываемый (3.3). Пока layout-эффекты не закончились, результат не показан: в RN новое Shadow Tree не передано на монтирование, и пользователь не видит отклика на своё действие. 30 мс в layout-эффекте — это 30 мс дополнительной задержки отклика, всегда.

`useEffect` для обычного обновления выполняется после commit, отдельной задачей: кадр с результатом уже ушёл на показ, и расчёт занимает поток, когда пользователь уже видит отклик. Работа та же, но задержка отклика — нет.

Оговорка: после нажатия пассивные эффекты React выполняет сразу в конце commit — и тогда тяжёлый `useEffect` тоже задерживает следующую работу на JS-потоке. Это ещё одна причина выносить тяжёлые вычисления из эффектов вообще: в мемоизированное вычисление при рендере (3.11), в переход (3.17) или за пределы JS-потока.

**Ответ «`useLayoutEffect` медленнее»** неточен: он не медленнее, он блокирует показ.

**Ответ «одинаково, работа та же»** вскрывает отсутствие модели «путь к кадру». Без неё невозможно объяснить, почему одинаковый код ощущается по-разному.
</details>

---

**3. Родитель и ребёнок, у каждого есть и `useLayoutEffect`, и `useEffect`. В каком порядке они выполнятся при монтировании, и что из этого следует для родителя, который измеряет ребёнка?**

<details>
<summary>Ответ</summary>

```
render родителя → render ребёнка
—— commit ——
layout-эффект ребёнка → layout-эффект родителя
—— показ ——
эффект ребёнка → эффект родителя
```

Все layout-эффекты выполняются раньше всех пассивных; внутри каждого вида — дети раньше родителей (3.4).

Следствие для измерений: к моменту layout-эффекта родителя host-узлы ребёнка уже созданы, ref на них заполнены, и layout-эффекты ребёнка уже выполнены. Если ребёнок в своём layout-эффекте поставил `setState`, меняющий собственный размер, — этот повторный рендер произойдёт синхронно, но уже после текущего прохода layout-эффектов. Родитель, измеряющий ребёнка, в первом проходе увидит размер **до** изменения, а правильный — во втором. Отсюда правило: цепочки «ребёнок меняет размер в layout-эффекте, родитель измеряет его в layout-эффекте» стоит избегать — каждое звено добавляет синхронный повторный рендер.

**Ответ «родитель первым, потому что он рендерится первым»** вскрывает перенос порядка рендера на порядок эффектов.
</details>

---

**4. Код аналитики «экран показан» стоит в `useEffect`. Аналитик утверждает, что событие иногда отправляется до того, как пользователь увидел экран. Возможно ли это?**

<details>
<summary>Ответ</summary>

Возможно, и это не ошибка React. `useEffect` гарантирует, что эффект не блокирует показ там, где React может себе это позволить, но **не гарантирует**, что кадр уже показан.

Если экран появился в результате нажатия (дискретное событие), React выполняет пассивные эффекты сразу в конце commit, синхронно, — это проверено экспериментом на React 19.2. В RN к этому добавляется путь от commit до появления на экране: новое Shadow Tree ещё нужно смонтировать на UI-потоке. Событие аналитики может уйти раньше, чем пиксели появились.

Что делать: решить, что именно измеряется. Если «экран открыт» — событие навигации (4.17) или момент commit — честный сигнал, и `useEffect` подходит. Если «пользователь увидел содержимое» — это метрика отрисовки, и её измеряют средствами, привязанными к показу кадра (5.6, 10.8), а не выбором вида эффекта.

**Ответ «перенести в `useLayoutEffect`, он точно после отрисовки»** вскрывает обратное понимание: layout-эффект выполняется **до** показа.

**Ответ «невозможно, `useEffect` всегда после отрисовки»** вскрывает упрощённую модель, которую опровергает поведение после нажатий.
</details>

## Задание — подсказка, не выходящая за край экрана

**Дано.** Кнопка «?» рядом с заголовком урока открывает подсказку над кнопкой. Требования: подсказка не выходит за правый край экрана; при первом показе нет видимого прыжка.

Текущая реализация:

```jsx
function HintBubble({ anchorX, text }) {
  const [left, setLeft] = useState(anchorX);

  return (
    <View
      style={{ position: 'absolute', left, bottom: 40 }}
      onLayout={(e) => {
        const width = e.nativeEvent.layout.width;
        const screenWidth = Dimensions.get('window').width;
        if (anchorX + width > screenWidth) setLeft(screenWidth - width - 8);
      }}
    >
      <Text>{text}</Text>
    </View>
  );
}
```

QA сообщает: «на длинном тексте подсказка на мгновение вылезает за край, потом отскакивает».

**Требуется.**

1. Объяснить, почему текущая реализация даёт прыжок, по шагам commit и показа.
2. Переписать на `useLayoutEffect` с измерением. Сказать, сколько рендеров и commit произойдёт до первого показа.
3. Решить, нужен ли `onLayout` после переписывания, и если да — для чего.
4. Подсказки появляются и в ячейках списка уроков (по одной на ячейку, видны все сразу). Применить ли тот же приём там? Обосновать.

---

<details>
<summary>Разбор</summary>

**1. Почему прыжок.**

`onLayout` — событие, которое приходит после того, как layout вычислен и применён. Последовательность:

1. рендер с `left = anchorX`, commit;
2. кадр показан — подсказка выходит за край;
3. приходит `onLayout` с шириной, `setLeft` ставит обновление;
4. повторный рендер, commit, кадр с правильной позицией.

Между шагами 2 и 4 пользователь видит неверную позицию. В старой архитектуре это было неизбежно: синхронного доступа к layout не было. В New Architecture от этого можно уйти.

**2. Переписывание.**

```jsx
function HintBubble({ anchorX, text }) {
  const ref = useRef(null);
  const [left, setLeft] = useState(anchorX);

  useLayoutEffect(() => {
    const { width } = ref.current.getBoundingClientRect();   // RN 0.82+
    const screenWidth = Dimensions.get('window').width;
    setLeft(anchorX + width > screenWidth ? screenWidth - width - 8 : anchorX);
  }, [anchorX, text]);

  return (
    <View ref={ref} style={{ position: 'absolute', left, bottom: 40 }}>
      <Text>{text}</Text>
    </View>
  );
}
```

В версиях до 0.82 вместо `getBoundingClientRect()` — `ref.current.measure((x, y, width) => ...)`; в New Architecture документация RN так же рекомендует вызывать его в `useLayoutEffect`.

До первого показа: **два рендера и два commit**. Рендер с `left = anchorX` → commit → layout-эффект измеряет и ставит `setLeft` → синхронный повторный рендер → commit → показ. Если подсказка помещается, `setLeft(anchorX)` равен текущему значению, React отказывается от обновления, и рендер один.

Зависимости `[anchorX, text]` честные: при смене текста или якоря ширина меняется, и измерение должно повториться. Чтение `Dimensions` внутри эффекта — не зависимость: это не реактивное значение React. Если подсказка должна реагировать на поворот экрана, ширина экрана берётся из `useWindowDimensions()` и становится зависимостью.

**3. Нужен ли `onLayout`.**

Для первого показа — нет. Но `useLayoutEffect` выполняется только когда изменились зависимости. Если размер подсказки может измениться **без** изменения `text` и `anchorX` — пользователь увеличил системный шрифт, изменилась ширина экрана, а `Dimensions` не в зависимостях, — эффект не перезапустится. Поворот закрывается `useWindowDimensions()` в зависимостях. Для остального `onLayout` остаётся правильным инструментом: он сообщает об **изменении** размера после первого показа, и небольшой прыжок в этом редком случае приемлем. Итог: `useLayoutEffect` — для первого показа, `onLayout` — для последующих изменений, если они возможны, пока подсказка видна.

**4. Подсказки в ячейках списка.**

Нет, не тем же приёмом. Каждая ячейка с `useLayoutEffect` и `setState` добавляет к монтированию списка синхронное измерение и синхронный повторный рендер. Двадцать видимых ячеек — двадцать повторных рендеров до показа первого кадра списка, и вся эта работа стоит на пути к показу.

Альтернативы, по убыванию предпочтения:

- **знать размер заранее** — ограничить ширину подсказки (`maxWidth`) и вычислить позицию при рендере без измерения;
- **показывать подсказку по действию** — тогда измеряется одна подсказка, а не двадцать;
- **принять прыжок** через `onLayout` для редкого случая длинного текста у края — если это действительно редкость.

Общий вывод: `useLayoutEffect` оправдан для одиночного элемента, появляющегося по действию пользователя, и почти никогда — для массового случая.

**Вклад в проект (P3).** Подсказка к уроку в RN Academy позиционируется измерением в `useLayoutEffect`; правило проекта: `useLayoutEffect` — только когда эффект читает layout и меняет текущий кадр, во всех остальных местах — `useEffect`.
</details>
