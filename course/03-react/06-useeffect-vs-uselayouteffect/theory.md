# 3.6 `useEffect` vs `useLayoutEffect` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «чем отличаются два хука» — а на вопрос, **в какой момент commit выполняется каждый из них, что пользователь видит до и после, и чем платится синхронность**.

---

## 1. Что это

Оба хука регистрируют эффект с одинаковой сигнатурой: функция, необязательная очистка, массив зависимостей. Различаются они **моментом выполнения**:

- **`useLayoutEffect`** — внутри commit, после того как изменения применены к host-узлам, но **до** того, как результат будет показан пользователю;
- **`useEffect`** — после commit; для обычных обновлений — отдельной задачей, когда кадр, как правило, уже показан.

Третий вид, **`useInsertionEffect`**, выполняется ещё раньше — до мутаций host-дерева. Он предназначен для библиотек CSS-in-JS, вставляющих стили в документ; в RN такой задачи нет, и этот хук практически не встречается.

### Ключевая формулировка урока

> **`useLayoutEffect` выполняется в commit до того, как результат увидит пользователь, и блокирует показ, пока не закончит. `useEffect` выполняется после — и именно поэтому почти всегда правильный выбор.**

---

## 2. Как это работает

### Место в commit

Из 3.3, с акцентом на два вида эффектов:

```
render (вызов компонентов, reconciliation)
—— commit, синхронно ——
  мутации host-узлов, обновление ref
  очистки layout-эффектов → layout-эффекты         ← useLayoutEffect
  переключение деревьев
—— показ результата ——
  очистки пассивных эффектов → пассивные эффекты   ← useEffect
```

Порядок внутри каждого вида — тот же, что в 3.4: дети раньше родителей, все очистки раньше всех запусков.

### `setState` в `useLayoutEffect`

Главное свойство layout-эффекта: обновление состояния, поставленное в нём, React обрабатывает **синхронно, в том же commit-цикле**, до показа. Промежуточный результат пользователь не увидит.

```jsx
function Tooltip({ anchorRef, text }) {
  const [top, setTop] = useState(0);
  const ref = useRef(null);

  useLayoutEffect(() => {
    const anchor = anchorRef.current.getBoundingClientRect();
    const own = ref.current.getBoundingClientRect();
    setTop(anchor.top - own.height);  // повторный рендер до показа
  }, [anchorRef, text]);              // (система координат упрощена)

  return <View ref={ref} style={{ position: 'absolute', top }}>…</View>;
}
```

Последовательность (проверена логированием на React 19.2):

```
render (top = 0)
layout-эффект: измерение, setTop(…)
пассивные эффекты первого рендера — React выполняет их принудительно,
  прежде чем начать синхронный повторный рендер
render (top = измеренное значение)
commit
—— показ ——
```

Пользователь видит подсказку сразу на правильном месте. Цена — два рендера и два commit до показа одного кадра.

С `useEffect` на месте `useLayoutEffect` последовательность другая: первый commit (с `top = 0`) показывается, затем выполняется эффект, затем повторный рендер и commit с правильной позицией. Документация React описывает этот случай как мигание: на экране на один кадр появляется подсказка в неверном месте.

### Когда пассивные эффекты выполняются сразу

`useEffect` не всегда отделён от commit отдельной задачей. Эксперимент на React 19.2 показывает два режима:

- обновление **по умолчанию** (таймер, ответ сети) — пассивные эффекты выполняются в отдельной задаче, позже: успевают выполниться микротаски, поставленные в commit;
- обновление **от дискретного события** (нажатие) — пассивные эффекты выполняются сразу в конце commit, синхронно.

Второе — сознательное решение React: результат нажатия и реакция на него не должны разделяться чужой работой. Практически это значит одно: **`useEffect` не гарантирует, что кадр уже показан.** Он гарантирует только, что эффект не блокирует показ там, где React может себе это позволить. Если код должен выполниться **именно до** показа — это `useLayoutEffect`; если важно **именно после** — это задача другого механизма (`requestAnimationFrame`, событие завершения анимации), а не выбор вида эффекта.

### Когда нужен `useLayoutEffect`

Одно содержательное правило: **эффект читает результат layout и меняет то, что будет показано в этом же кадре.** Типовые случаи:

- позиционирование подсказки, поповера, выпадающего меню по размеру и положению якоря;
- автоскролл к элементу, чьё положение известно только после layout;
- подгонка размера одного элемента под измеренный размер другого;
- синхронизация с императивным API, которое должно увидеть изменения до показа (например, переключение режима нативного view до первого кадра с новым содержимым).

Всё остальное — подписки, запросы, аналитика, запись в хранилище, таймеры — `useEffect`.

---

## 3. Почему это важно

**Неверный выбор виден пользователю или ощущается им.** `useEffect` для позиционирования даёт мигание: элемент на кадр появляется не там. `useLayoutEffect` для тяжёлой работы даёт задержку: кадр с результатом нажатия показывается позже, потому что commit не закончится, пока не выполнятся все layout-эффекты.

**Layout-эффект — часть commit, а commit не прерывается.** Всё, что выполняется в `useLayoutEffect`, добавляется к времени между нажатием и откликом без возможности уступить поток (3.1, 3.3). Это прямой вклад в бюджет кадра (5.2): 10 мс в layout-эффекте — это 10 мс, на которые сдвигается показ, сколько бы ни было свободного времени потом.

**Повторный рендер в layout-эффекте удваивает стоимость commit.** Синхронный повторный рендер — это ещё один проход render и ещё один commit до показа. Для одного тултипа это незаметно; для `useLayoutEffect` с `setState` в ячейке списка из пятидесяти элементов — это пятьдесят синхронных повторных рендеров при монтировании.

## 4. Где это в React Native

### Синхронный layout в New Architecture

Это самое заметное практическое изменение, которое New Architecture принесла в эту тему. В Fabric layout вычисляется в C++ и доступен из JS синхронно, поэтому в `useLayoutEffect` можно измерить view и обновить состояние в том же commit — пользователь не увидит промежуточного положения. Документация RN (раздел New Architecture, «Measuring the Layout») прямо рекомендует вызывать измерения в `useLayoutEffect`: так получаются самые свежие значения и изменения применяются в том же кадре.

Методы измерения на ref нативного компонента:

- **`measure(callback)`** — позиция и размер, включая координаты в окне просмотра;
- **`measureInWindow(callback)`** — позиция и размер в окне;
- **`getBoundingClientRect()`** — с RN 0.82 нативные компоненты отдают через ref DOM-подобные узлы с подмножеством DOM API, включая этот метод.

Все они доступны только на host-компонентах, у составного компонента без собственного нативного view их нет (3.9).

### `onLayout` и «прыгающий» тултип старой архитектуры

В старой архитектуре синхронного доступа к layout не было, и единственным путём было событие `onLayout`. Оно приходило асинхронно, после того как кадр с исходной позицией уже показан; `setState` в его обработчике давал второй кадр с правильной позицией. Отсюда характерный дефект старого кода — подсказки и поповеры, «прыгающие» на место.

`onLayout` остаётся полезным и сейчас — как подписка на **изменения** размера (поворот экрана, изменение шрифта, раскрытие содержимого). Но для «измерить и поставить на место при появлении» в New Architecture правильный инструмент — `useLayoutEffect`.

### Блокировка кадра в RN

Commit в RN заканчивается передачей нового Shadow Tree на монтирование (4.3). Пока JS-поток выполняет layout-эффекты, этой передачи нет: результат нажатия не уходит на UI-поток. Анимации, работающие на UI-потоке (нативный драйвер Animated, Reanimated), продолжают идти, но всё, что зависит от JS-потока, — ждёт.

## 5. Типичные ошибки

**«`useLayoutEffect` быстрее».** Возникает из того, что он выполняется раньше. Он не быстрее — он **блокирует**: работа та же, но выполняется на пути к показу кадра. Перевод эффектов на `useLayoutEffect` «для скорости» делает интерфейс медленнее в ощущении.

**Позиционирование через `useEffect` + `setState`.** Возникает по умолчанию: `useEffect` — первый хук, о котором вспоминают. Результат — мигание на кадр. Признак: эффект читает размер или позицию узла и пишет в состояние, влияющее на стиль.

**Запрос данных или подписка в `useLayoutEffect`.** Возникает из переноса «раз эффект важный, пусть выполнится раньше». Запрос не вернётся быстрее, а синхронная часть эффекта задержит показ. Подписке тоже незачем быть синхронной.

**«`onLayout` и `useLayoutEffect` — одно и то же».** Возникает из похожих названий. `onLayout` — событие, приходящее после layout, в старой архитектуре — асинхронно, после показа. `useLayoutEffect` — эффект commit до показа. В New Architecture они дают разные моменты и разные гарантии.

**Ожидание, что `useEffect` всегда выполняется после показа.** Возникает из упрощённой формулировки «после отрисовки». После нажатия пассивные эффекты выполняются сразу в конце commit. Код, который рассчитывает «пользователь уже видит результат» внутри `useEffect`, может ошибаться.

**Тяжёлый `useLayoutEffect` в ячейке списка.** Возникает при переносе одиночного приёма (измерить элемент) на список. Каждая ячейка добавляет синхронную работу и, если есть `setState`, синхронный повторный рендер к монтированию списка.

## 6. Trade-offs

### Отсутствие промежуточного кадра против блокировки показа

`useLayoutEffect` покупает визуальную корректность — промежуточного кадра нет — ценой задержки показа на всё время своей работы и повторного рендера. Для одиночного элемента, появляющегося по действию пользователя, это почти всегда выгодно: лишние миллисекунды незаметны, а прыжок элемента заметен. Для массовых случаев (ячейки списка, частые обновления) — почти никогда: суммарная задержка становится видимой.

### Измерение против заранее известного размера

Самый дешёвый `useLayoutEffect` — тот, которого нет. Если размер элемента можно знать заранее (фиксированная высота строки, известная высота шапки), позиционирование вычисляется при рендере, без измерения. В списках это и есть смысл `getItemLayout` (5.4): заранее известный размер избавляет от измерений вообще.

### `useEffect` как выбор по умолчанию

Правило «по умолчанию `useEffect`, `useLayoutEffect` — когда эффект читает layout и меняет текущий кадр» иногда даёт мигание, которое заметят на ревью или в QA. Обратное правило «по умолчанию `useLayoutEffect`» даёт задержки, которые не заметит никто, пока приложение не начнёт «ощущаться медленным». Первую ошибку легко найти и исправить точечно, вторую — нет.
