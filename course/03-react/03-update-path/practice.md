# 3.3 Путь обновления — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать **шаг пути** — очередь, батч, render, commit, — на котором происходит то, о чём спрашивают.

---

**1. Почему `console.log(count)` сразу после `setCount(count + 1)` выводит старое значение — даже если подождать `setTimeout(..., 0)` внутри того же обработчика?**

<details>
<summary>Ответ</summary>

Потому что `count` — локальная константа текущего вызова функции компонента. `setCount` не присваивает ей ничего: он записывает обновление в очередь на fiber и просит React запланировать рендер. Новое значение появится как `count` в **следующем** вызове компонента.

```jsx
function onPress() {
  setCount(count + 1);
  setTimeout(() => console.log(count), 0);   // всё равно старое
}
```

Ожидание через `setTimeout` не помогает: к моменту срабатывания таймера рендер, скорее всего, уже произошёл, но колбэк таймера — замыкание **этого** вызова компонента (1.14), и в нём `count` навсегда старый. Новое значение существует в другом вызове функции, в другом замыкании.

Что делать, если новое значение нужно сразу: вычислить его явно (`const next = count + 1; setCount(next); use(next)`) — или, если реакция должна произойти после того, как экран обновится, перенести её туда, где новое состояние уже есть.

**Ответ «потому что `setState` асинхронный»** — частично верно, но вводит в заблуждение. Даже если бы рендер произошёл синхронно внутри `setCount`, переменная `count` в текущем вызове не изменилась бы: это `const`. Причина не во времени, а в том, что состояние — не переменная.

**Ответ «надо использовать `await setCount(...)`»** вскрывает модель «`setState` возвращает промис». Он возвращает `undefined`, и `await` лишь откладывает продолжение в микротаск, ничего не меняя в замыкании.
</details>

---

**2. Обработчик ставит `setLoading(true)`, ждёт запрос, затем вызывает `setData(d)` и `setLoading(false)`. Сколько рендеров и какие состояния видит пользователь?**

<details>
<summary>Ответ</summary>

Два рендера:

1. `{ loading: true, data: старое }` — обновление из синхронной части обработчика, до `await`. Задача нажатия заканчивается на `await`, и React обрабатывает очередь.
2. `{ loading: false, data: d }` — оба обновления из продолжения после `await` попадают в один батч.

Промежуточного состояния `{ loading: true, data: d }` или `{ loading: false, data: старое }` пользователь не увидит: два последних обновления поставлены в одной задаче и обработаны вместе. Это проверяется логированием рендеров на React 19.2.

Два рендера здесь — правильное поведение, а не потеря производительности: пользователь должен увидеть индикатор загрузки.

**Ответ «три рендера, по одному на `setState`»** вскрывает модель до батчинга.

**Ответ «один рендер, React батчит всю функцию»** вскрывает непонимание того, что `await` делит функцию на две части (1.19). Батч — на то, что встало в очередь до её обработки, а не на функцию.

**Ответ «два, но могут быть три, если запрос быстрый»** вскрывает неуверенность в границе батча. Три не будет никогда: два последних обновления поставлены подряд, без `await` между ними. Скорость запроса влияет на другое: если промис уже выполнен (ответ из кэша), продолжение — микротаск, который при обновлении по умолчанию успевает раньше обработки очереди, и тогда рендер может быть **один** (проверено на React 19.2; в обработчике нажатия — всё равно два). Поэтому корректный экран не опирается на то, что индикатор загрузки обязательно будет показан.
</details>

**3. Чем render-фаза отличается от commit-фазы, и почему побочный эффект допустим только во второй?**

<details>
<summary>Ответ</summary>

**Render** — React вызывает функции компонентов и сравнивает результат с текущим деревом (3.1). Ни один host-узел не меняется: работа идёт над work-in-progress деревом. Её результат может быть выброшен — переход прерван срочным обновлением, компонент приостановился в Suspense, в dev StrictMode вызывает функцию компонента дважды. Для переходов эта фаза прерываема.

**Commit** — React применяет результат: мутирует host-узлы, обновляет ref, запускает layout-эффекты, переключает деревья, запускает пассивные эффекты. Фаза синхронная и непрерываемая: частично применённое изменение было бы видно пользователю.

Побочный эффект в render-фазе выполнится, даже если рендер выброшен, и может выполниться больше одного раза. В commit-фазе эффекты выполняются ровно для того результата, который применён к экрану, и в паре с очисткой (3.4). Поэтому подписка, запрос, аналитика, мутация внешнего объекта — в эффекте или в обработчике, но не в теле компонента.

**Ответ «render — это отрисовка, commit — сохранение»** вскрывает обыденное значение слова «рендер». Отрисовки на render-фазе нет вообще.

**Ответ «побочные эффекты в render замедляют рендер»** подменяет корректность производительностью.
</details>

**4. В RN-проекте, начатом на React 17, вокруг обработки ответа сети стоит `unstable_batchedUpdates`. Нужен ли он сейчас, и что он делал раньше?**

<details>
<summary>Ответ</summary>

Раньше: до React 18 (и в RN со старой архитектурой) обновления батчились только внутри обработчиков событий React. В колбэке сети каждый `setState` синхронно давал отдельный рендер — три `setState` в `.then` давали три рендера и два промежуточных состояния на экране. `unstable_batchedUpdates(() => { ... })` заставлял React обработать обновления внутри колбэка одним рендером.

Сейчас: с конкурентным корнем, то есть в New Architecture, обновления батчатся в любой задаче — в таймерах, промисах, колбэках нативных модулей. С RN 0.82 другой архитектуры нет, и `unstable_batchedUpdates` ничего не добавляет. Удалять его можно, но это не исправление ошибки, а уборка: поведение не изменится.

Важнее найти другие следы старого поведения: состояние экрана, сведённое в один объект «чтобы был один рендер», и `flushSync`-подобные обходы. Объединение состояний должно решаться по смыслу переходов (3.8), а не по числу рендеров.

**Ответ «нужен, иначе будет несколько рендеров»** вскрывает модель React 17.

**Ответ «это API для производительности, его стоит добавить везде»** вскрывает непонимание того, что батчинг сейчас автоматический.
</details>

## Задание — предсказать число рендеров

**Дано.** Компонент с двумя полями состояния и логом рендеров. Начальное состояние `a = 0`, `b = 0`.

```jsx
function Counter() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);
  console.log(`render a=${a} b=${b}`);
  // ... обработчики ниже вызываются по очереди, каждый в отдельной задаче
}
```

```jsx
// H1 — колбэк таймера
setA(1); setB(1);

// H2 — продолжение промиса
Promise.resolve().then(() => { setA(2); setB(2); });

// H3 — асинхронная функция
setA(3); await sleep(5); setA(4); setB(4);

// H4 — три обновления подряд, сейчас a = 4
setA(a + 1); setA(a + 1); setA(a + 1);

// H5 — три функциональных обновления подряд
setA((x) => x + 1); setA((x) => x + 1); setA((x) => x + 1);

// H6 — значение, равное текущему (a уже 8), трижды, каждый раз в отдельной задаче
setA(8);   // задача 1
setA(8);   // задача 2
setA(8);   // задача 3
```

**Требуется.**

1. Для каждого обработчика записать, сколько раз выполнится `console.log` и какие значения он покажет.
2. Для H3 объяснить, где проходит граница батча.
3. Для H6 объяснить, почему ответ не «ни одного рендера» во всех трёх задачах.
4. Перенести вывод на RN: какой из обработчиков в RN-проекте со старой архитектурой дал бы другой результат и почему.

---

<details>
<summary>Разбор</summary>

Результаты получены экспериментом на React 19.2 (`createRoot`, dev-сборка без StrictMode).

**1. Число рендеров и значения.**

| Обработчик | Рендеров | Лог |
|---|---|---|
| H1 | 1 | `a=1 b=1` |
| H2 | 1 | `a=2 b=2` |
| H3 | 2 | `a=3 b=2`, затем `a=4 b=4` |
| H4 | 1 | `a=5 b=4` |
| H5 | 1 | `a=8 b=4` |
| H6 | 1, затем 0, затем 0 | `a=8 b=4` один раз |

H1 и H2: обновления в одной задаче — один батч, вне зависимости от того, таймер это или промис.

H4: все три вызова вычислены из одного и того же `a = 4`, в очереди три раза «установить 5». Один рендер, `a = 5`.

H5: в очереди три функции, каждая применяется к результату предыдущей: 5 → 6 → 7 → 8. Один рендер, `a = 8`.

**2. Граница в H3.** `setA(3)` выполняется в синхронной части; на `await` функция возвращает управление, задача заканчивается, React обрабатывает очередь — первый рендер `a=3 b=2`. Продолжение после `sleep` выполняется позже — когда сработает таймер, — и там `setA(4)` и `setB(4)` батчатся между собой: второй рендер `a=4 b=4`. Граница — `await` промиса, который действительно ждёт, а не конец функции. С уже выполненным промисом вместо `sleep` в колбэке таймера рендер был бы один (см. «Тонкость» в теории).

**3. Почему H6 даёт один рендер.** React старается отказаться от обновления **до** рендера: если очередь fiber пуста, он вычисляет новое состояние сразу при вызове `setA` и, если оно равно текущему по `Object.is`, не планирует работу вовсе. Но сразу после серии обновлений fiber может ещё нести служебные пометки о недавней работе, и тогда ранняя проверка невозможна: React вызывает компонент, применяет очередь, видит то же значение и только после этого отказывается от рендера потомков и эффектов. Отсюда один «лишний» вызов `Counter` в первой задаче H6 и ни одного — во второй и третьей.

Практический вывод: «`setState` тем же значением не вызывает рендер» верно для потомков и эффектов, но не гарантирует, что сам компонент не будет вызван ещё раз. Документация React описывает ровно это поведение. Поэтому функция компонента обязана быть чистой — даже вызов, который ничего не изменит, должен быть безвредным.

**4. Перенос на RN.** В New Architecture результат тот же: конкурентный корень, автоматический батчинг. В старой архитектуре (RN до 0.82 с выключенной New Architecture) корень был legacy, и батчились только обновления внутри обработчиков событий React. Вне обработчика каждый `setState` синхронно давал рендер прямо внутри вызова. Тот же сценарий на legacy-корне (React 17, `ReactDOM.render`) даёт:

- **H1** — два рендера: `a=1 b=0`, затем `a=1 b=1` — колбэк таймера не обработчик события;
- **H2** — два, по той же причине;
- **H3** — три: `a=3 b=2`, `a=4 b=2`, `a=4 b=4`;
- **H4** — два: `a=5`, затем ещё один вызов компонента с тем же `a=5` — второй `setA(5)` пришёл, когда ранняя проверка равенства была невозможна (тот же механизм, что в H6), а третий отброшен сразу;
- **H5** — три: `a=6`, `a=7`, `a=8` — каждое функциональное обновление применяется и рендерится отдельно.

Промежуточные состояния (`a=1 b=0`, `a=4 b=2`) пользователь мог увидеть на экране. Отсюда следы в старом коде — `unstable_batchedUpdates` и объединённые состояния. Читая такой код, полезно помнить, что он решал проблему, которой в RN 0.82+ больше нет.

**Вклад в проект (P3).** Обработчик «отметить урок пройденным» в RN Academy ставит обновления прогресса и состояния экрана в одной задаче, без `await` между ними; тест компонента проверяет счётчиком, что нажатие даёт один рендер до запроса и один после.
</details>
