# 3.3 Путь обновления — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает на вопрос, который опытный разработчик обычно обходит практикой: **почему вызов `setState` не означает немедленный рендер, и что происходит между вызовом и изменением экрана**.

```
setState  →  update queue  →  batching  →  scheduling  →  render  →  commit
```

---

## 1. Что это

Путь обновления — последовательность шагов, через которую проходит каждый вызов `setState` (или `dispatch`, или изменение контекста), прежде чем пользователь увидит результат:

- **update queue** — обновление записывается в очередь на fiber;
- **batching** — обновления, поставленные вместе, обрабатываются одним рендером;
- **scheduling** — React назначает работе приоритет и решает, когда её выполнять;
- **render phase** — React вызывает функции компонентов и сравнивает результат с текущим деревом;
- **commit phase** — React применяет изменения к host-узлам и запускает эффекты.

### Ключевая формулировка урока

> **`setState` не меняет состояние — он ставит обновление в очередь и просит React запланировать работу. Новое значение появится только в следующем вызове компонента.**

---

## 2. Как это работает

### Шаг 1. Update queue

```jsx
function LessonHeader() {
  const [count, setCount] = useState(0);

  function onPress() {
    setCount(count + 1);
    console.log(count);   // 0 — не 1
  }
}
```

`setCount` не присваивает значение переменной `count`. Он создаёт объект обновления и добавляет его в очередь хука на fiber (3.1). Переменная `count` — локальная константа текущего вызова функции компонента; она не изменится до конца этого вызова никогда. Новое значение появится как значение `count` в **следующем** вызове `LessonHeader`, когда React применит очередь.

Отсюда же разница двух форм:

```jsx
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);        // в очереди три раза «установить 1» → результат 1

setCount((c) => c + 1);
setCount((c) => c + 1);
setCount((c) => c + 1);     // в очереди три функции, каждая получает результат предыдущей → 3
```

Значение-аргумент вычислено **сейчас**, из замыкания текущего рендера (1.14). Функция-аргумент будет вызвана **потом**, при обработке очереди, с результатом предыдущего обновления. Функциональная форма нужна, когда новое значение зависит от предыдущего, а обновлений несколько или они происходят в долгоживущем колбэке.

### Шаг 2. Batching

Обновления, поставленные в одной задаче (1.20), React обрабатывает **одним** рендером:

```jsx
function onPress() {
  setStatus('done');
  setProgress(100);
  setToast('Урок пройден');   // три обновления → один рендер
}
```

Механизм — тот, что разобран в 1.21: React не рендерит синхронно на каждый `setState`, а планирует обработку очереди на момент, когда текущая синхронная работа закончится. Всё, что успело встать в очередь до этого момента, обработается вместе.

**Что батчится в React 18 и 19** (корень, созданный через `createRoot`, — в RN это любой корень New Architecture):

| Где вызван `setState` | Один рендер? |
|---|---|
| обработчик события | да |
| `setTimeout`, `setInterval` | да |
| `.then` промиса | да |
| колбэк нативного модуля, слушатель emitter | да |
| до и после `await` запроса в одной функции | **нет** — два отдельных прохода |

Последняя строка — главная граница на практике. `await` делит функцию на две части (1.19): синхронную часть до `await` и продолжение, которое выполнится микротаском, когда промис разрешится (1.21). Если промис действительно ждёт — сеть, таймер, нативный модуль, — к моменту продолжения задача давно закончилась, и React успел обработать то, что было поставлено до `await`.

```jsx
async function onSubmit() {
  setLoading(true);               // задача нажатия → рендер №1
  const data = await api.save();
  setData(data);                  // продолжение → рендер №2
  setLoading(false);              //   (вместе с предыдущим)
}
```

Рендеров два: `loading: true` и `{ data, loading: false }`. Обновления внутри продолжения после `await` батчатся между собой — но не с теми, что были до `await`. Всё это проверено логированием на React 19.2.

**Тонкость: промис, который уже выполнен.** Точное правило — не «`await` всегда граница», а «в один батч попадает всё, что встало в очередь до того, как React её обработал». Когда это происходит, зависит от приоритета (шаг 3): обновление от нажатия React обрабатывает в ближайшем микротаске, обновление по умолчанию — отдельной задачей планировщика. Поэтому `await` уже выполненного промиса (ответ из кэша в памяти, `await Promise.resolve()`) ведёт себя по-разному. Эксперимент на React 19.2:

| Где | Код | Рендеров |
|---|---|---|
| колбэк таймера | `setA(1); await cached; setB(1)` | **один** — продолжение-микротаск успело до задачи планировщика |
| обработчик нажатия | `setA(1); await cached; setB(1)` | два — микротаск React был поставлен раньше продолжения |

Опираться на это при проектировании не нужно — это деталь планирования, а не контракт. Практический вывод другой: число рендеров асинхронного обработчика зависит от того, ждёт ли промис на самом деле. Код, который «всегда даёт два рендера» с сетью, может давать один с кэшем — и наоборот. Поэтому корректность экрана не должна зависеть от числа рендеров: промежуточное состояние (`loading: true`) должно быть допустимым и тогда, когда его не видно, и тогда, когда видно.

**Раньше было иначе.** До React 18 (и в RN со старой архитектурой) обновления батчились только внутри обработчиков событий React. В `setTimeout` или `.then` каждый `setState` давал отдельный синхронный рендер. Отсюда в старом коде `unstable_batchedUpdates` (его по-прежнему экспортирует `react-native`) и привычка объединять состояния в один объект «чтобы был один рендер». С New Architecture это не нужно.

**`flushSync`** — выход из группировки: обновление внутри колбэка `flushSync` рендерится и коммитится синхронно, до возврата из функции. Это API `react-dom`; в публичном API `react-native` его нет, и в RN-коде необходимость в нём почти не возникает — синхронное измерение после обновления делается через `useLayoutEffect` (3.6).

### Шаг 3. Scheduling

Каждое обновление получает **lane** — приоритет, зависящий от того, откуда оно пришло:

- **дискретное событие** (нажатие, ввод символа) — синхронный приоритет;
- **непрерывное событие** (прокрутка, перемещение пальца) — высокий;
- **по умолчанию** (таймер, ответ сети, всё остальное) — обычный;
- **переход** (`startTransition`) — низкий и прерываемый;
- **idle** — самый низкий.

Планировщик React выполняет работу в порядке приоритетов: обновление от нажатия обработается раньше, чем начатый переход, и может прервать его (3.17). Обновления с одинаковым lane обрабатываются вместе — это и есть батчинг с точки зрения планировщика.

Важно, что планировщик **не прерывает выполняющийся JavaScript**: если обработчик нажатия считает 300 мс, решать про приоритеты некому, пока он не закончится (1.20).

### Шаг 4. Render phase

React обходит дерево fiber, начиная с корня, и для каждого компонента, которому нужно обновиться:

1. применяет очередь обновлений — вычисляет новое состояние;
2. вызывает функцию компонента с новыми пропсами и состоянием;
3. сравнивает возвращённые элементы с текущими детьми (reconciliation, 3.1) и помечает, что изменить в commit.

Какие компоненты вызываются: тот, у которого есть обновление, и **все его потомки** — независимо от того, изменились ли их пропсы, — пока не встретится компонент, который может пропустить работу (`memo` с равными пропсами, 3.11). Ни один host-узел на этой фазе не меняется: работа идёт над work-in-progress деревом.

Свойства render-фазы:

- **чистая** — функция компонента не должна менять ничего вне себя: результат может быть выброшен (3.1), а в dev StrictMode вызывает её дважды (3.4);
- **прерываемая — только для переходов** — синхронные обновления проходят дерево до конца (3.1);
- **может не дойти до экрана** — вызов компонента не означает, что пользователь увидит результат.

### Шаг 5. Commit phase

Когда дерево готово, React коммитит его — **синхронно и без прерываний**, потому что частично применённый результат был бы виден пользователю. Порядок внутри commit:

1. **мутации** — изменения применяются к host-узлам; ref на узлы обновляются;
2. **layout-эффекты** — очистки и запуски `useLayoutEffect`; обновления состояния, поставленные здесь, обрабатываются синхронно, до показа (3.6);
3. **переключение деревьев** — work-in-progress становится current;
4. **пассивные эффекты** — `useEffect`. Для обновлений по умолчанию (таймер, ответ сети) React выполняет их позже, отдельной задачей, обычно после того, как кадр показан. Для обновлений от дискретного события (нажатие) — сразу в конце того же commit: так результат нажатия и реакция на него не разделяются чужой работой. Оба поведения проверены экспериментом на React 19.2.

Подробно порядок эффектов разбирается в 3.4, а различие двух видов эффектов — в 3.6.

### Bailout: обновление, которого не было

```jsx
setStatus('done');   // а status уже 'done'
```

Если новое значение равно текущему по `Object.is`, React отказывается от обновления: потомки не рендерятся, эффекты не запускаются. Тонкость: React не всегда может проверить равенство заранее. Если у fiber уже есть необработанные обновления, React вызовет функцию компонента ещё раз, обнаружит то же состояние и только тогда откажется от работы с потомками. Документация React прямо оговаривает этот случай, и эксперимент его подтверждает: первый `setState` с тем же значением после серии обновлений даёт один дополнительный вызов компонента, следующие — ни одного.

Обратная сторона того же правила: мутированный объект, переданный в `setState`, — **тот же объект**, и обновление будет отброшено (3.10).

## 3. Почему это важно

**Чтение состояния «сразу после» — источник целого класса ошибок.** Код, который ставит обновление и тут же читает переменную состояния, всегда видит старое значение. Отправка формы со старыми данными, проверка «если список пуст» сразу после добавления элемента, логирование «нового» значения — всё это одна и та же ошибка модели.

**Число рендеров предсказуемо по коду.** Батчинг не случайность: границы — задача и `await` промиса, который действительно ждёт. Зная их, по коду обработчика можно сказать, сколько раз отрисуется экран и какие промежуточные состояния увидит пользователь. Промежуточное состояние — это не только производительность: «загрузка закончилась, а данных ещё нет» на один кадр — видимый дефект.

**Две фазы — две разные проблемы производительности.** «Лишний рендер» — работа render-фазы: React вызвал компоненты, результат которых не изменился. «Долгий commit» — работа commit-фазы: применение мутаций к host-узлам, layout, синхронные эффекты. Это разные инструменты измерения и разные решения: мемоизация (3.11) лечит первое и никак не влияет на второе. Блок 05 построен на этом различии.

## 4. Где это в React Native

### Render на JS-потоке, commit — на стыке потоков

В New Architecture render-фаза полностью выполняется на JS-потоке, включая создание и клонирование узлов Shadow Tree через JSI. Commit передаёт новое дерево Fabric: он вычисляет layout (Yoga) и планирует монтирование изменений в нативные view на UI-потоке (4.1, 4.3). Отсюда:

- **лишний рендер** — нагрузка на JS-поток; виден в React Profiler (5.10) как время рендера компонентов;
- **долгий commit** — может включать дорогой layout и монтирование нативных view; виден в системном профайлере (Perfetto, Instruments), и мемоизация его не лечит.

### Автоматический батчинг — свойство New Architecture

Батчинг вне обработчиков событий (в таймерах, промисах, колбэках нативных модулей) работает с конкурентным корнем, который в RN появился вместе с New Architecture. Начиная с RN 0.82 другой архитектуры нет. Но в кодовых базах, начатых до перехода, встречаются следы старого поведения:

- `unstable_batchedUpdates` вокруг колбэков сети или нативных событий — теперь лишний;
- состояние экрана, сведённое в один `useState` с объектом «чтобы не было двух рендеров» — теперь это решение должно приниматься по смыслу (3.8), а не ради числа рендеров;
- комментарии «здесь два рендера, это нормально» у кода, который теперь даёт один.

### Колбэки нативных модулей и emitter'ов

Обновления из слушателя `AppState`, `Keyboard` или нативного emitter'а получают приоритет по умолчанию и батчатся в пределах одного колбэка. Если колбэк вызывается много раз подряд (события прокрутки, датчики), каждый вызов — отдельная задача и отдельный рендер. Это уже вопрос частоты событий, а не батчинга (5.2, 5.7).

### `await` в обработчике — самый частый случай двух рендеров

Типичный RN-обработчик «показать индикатор → запрос → показать результат» с настоящим сетевым запросом даёт минимум два рендера, и это правильно: пользователь должен увидеть индикатор. Ошибка — пытаться «сэкономить» рендер, не показав индикатор, или ожидать, что обновления до и после `await` объединятся. Обратная ошибка — опираться на то, что индикатор обязательно мелькнёт: если ответ пришёл из кэша, рендер может быть один.

## 5. Типичные ошибки

**Чтение состояния сразу после `setState`.** Возникает из модели «`setState` — это присваивание». Код, который после `setItems([...items, x])` проверяет `items.length`, видит старый массив. Исправление — использовать вычисленное значение, а не перечитывать состояние: `const next = [...items, x]; setItems(next); check(next)`.

**Три `setN(n + 1)` подряд.** Возникает из того же: ожидание, что каждый вызов увидит результат предыдущего. Все три вычислены из одного и того же `n`. Функциональная форма — правильный инструмент, когда обновление зависит от предыдущего значения.

**«`setState` синхронный в обработчиках и асинхронный в остальных местах».** Устаревшая модель времён React 17, усиленная советами из старых статей. В React 18+ `setState` везде одинаков: ставит обновление в очередь. Различается только приоритет.

**Ожидание, что обновления до и после `await` объединятся.** Возникает из модели «батчинг на всю функцию». В батч попадает то, что встало в очередь до её обработки; `await` промиса, который ждёт сеть или таймер, отодвигает продолжение далеко за этот момент.

**`setState` в теле компонента.** Возникает при попытке синхронизировать состояние с пропсом «прямо здесь». Безусловный `setState` при рендере вызывает рендер, который снова вызывает `setState`, — React останавливает это ошибкой о слишком большом числе повторных рендеров. Есть один допустимый вариант — условное обновление **своего** состояния при смене пропса (3.7), но и он чаще всего заменяется ключом.

**«Render — это отрисовка на экране».** Возникает из слова «рендер» в обычном смысле. Render — вызов функций компонентов; экран меняется только в commit. Без этого различия нельзя объяснить, почему компонент «отрендерился», а на экране ничего не изменилось.

**«`useEffect` выполняется сразу после рендера».** Возникает из названия «эффект после рендера». Между вызовом компонента и эффектом — вся оставшаяся render-фаза, commit и обычно показ кадра (3.4, 3.6).

## 6. Trade-offs

### Батчинг: меньше рендеров, отложенная наблюдаемость

Батчинг экономит работу: десять обновлений в обработчике стоят одного рендера. Цена — состояние наблюдаемо только «после»: в момент вызова `setState` ни переменная, ни экран ещё не изменились. Для кода, которому нужно действовать на основе нового состояния, правильный путь — вычислить новое значение явно или перенести действие туда, где новое состояние уже есть (следующий рендер или эффект).

### `flushSync` и `useLayoutEffect`: синхронность за счёт отзывчивости

Синхронный рендер нужен редко: когда сразу после обновления требуется прочитать результат с экрана (размер, позицию) или когда сторонний императивный код должен увидеть изменение немедленно. Он платит лишним рендером (обновление вырвано из группы) и блокировкой: пока синхронный рендер и commit не закончатся, поток занят. В RN эту задачу решает `useLayoutEffect` (3.6), а не `flushSync`.

### Приоритеты: отзывчивость против предсказуемости

Планирование по приоритетам позволяет срочному обновлению обогнать несрочное. Цена — порядок применения обновлений из разных источников перестаёт совпадать с порядком вызовов: переход, начатый раньше, может закоммититься позже нажатия. Пока все обновления синхронные, этой разницы не видно; она становится заметной в 3.17.

## 7. Связи с другими частями системы

**Опирается на:**

- **1.20 Event loop** — задача выполняется до конца, и пока она выполняется, не происходит ничего другого, включая рендер;
- **1.21 Microtasks и macrotasks** — механизм, на котором стоит батчинг: обработка откладывается до конца текущей синхронной работы. Урок 1.21 оставил вопрос «что именно React группирует и что гарантировано» открытым — ответ: при конкурентном корне группируется всё, что встало в очередь до её обработки; на практике граница — `await` промиса, который действительно ждёт, а гарантией число рендеров не является;
