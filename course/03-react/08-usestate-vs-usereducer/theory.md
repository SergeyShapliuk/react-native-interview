# 3.8 `useState` vs `useReducer` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «какой хук удобнее», а на вопрос, **что считать единицей изменения состояния — значение или переход**, и что из этого следует для корректности экрана.

---

## 1. Что это

**`useState`** хранит значение и даёт функцию, которая его заменяет: `setStatus('loading')`. Единица изменения — **новое значение поля**.

**`useReducer`** хранит значение и даёт `dispatch`, который принимает **действие** — описание того, что произошло. Новое значение вычисляет редьюсер — чистая функция `(state, action) => state`:

```js
const [state, dispatch] = useReducer(reducer, initialState);
dispatch({ type: 'refresh' });
```

Единица изменения — **переход**: из какого состояния, по какому событию, в какое.

Внутри React оба хука устроены одинаково — `useState` реализован как `useReducer` со встроенным редьюсером «заменить значение». Разница не в механизме, а в том, где лежит логика перехода: у вызывающего (`useState`) или в одном месте (`useReducer`).

### Ключевая формулировка урока

> **`useState` описывает значения, `useReducer` — переходы. Когда не все переходы между состояниями экрана разрешены, редьюсер делает это явным, а набор `useState` — нет.**

---

## 2. Как это работает

### Несколько связанных `useState` расходятся

Экран списка уроков с pull-to-refresh и подгрузкой страниц, написанный «как обычно»:

```jsx
const [items, setItems] = useState([]);
const [isLoading, setIsLoading] = useState(false);
const [isRefreshing, setIsRefreshing] = useState(false);
const [isLoadingMore, setIsLoadingMore] = useState(false);
const [error, setError] = useState(null);
```

Четыре флага состояния — шестнадцать комбинаций. Осмысленных из них пять: ничего не происходит, первая загрузка, обновление, подгрузка, ошибка. Остальные одиннадцать — «загрузка и ошибка одновременно», «обновление и подгрузка», «первая загрузка при уже показанном списке» — **выразимы**: ничто в коде не мешает их получить. Каждый обработчик сам расставляет флаги, и стоит одному забыть сбросить `error` или `isLoadingMore`, экран попадает в комбинацию, которую никто не проектировал: крутится спиннер поверх сообщения об ошибке, подгрузка запускается во время обновления.

Батчинг (3.3) тут не помогает: он объединяет обновления в один рендер, но не проверяет, что получившаяся комбинация имеет смысл.

### Редьюсер как список допустимых переходов

Тот же экран, состояние описано типом из 2.5:

```ts
type ListState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; items: Lesson[]; page: number; hasMore: boolean }
  | { status: 'refreshing'; items: Lesson[]; page: number; hasMore: boolean }
  | { status: 'loadingMore'; items: Lesson[]; page: number; hasMore: boolean };

type ListAction =
  | { type: 'load' }
  | { type: 'loaded'; items: Lesson[]; hasMore: boolean }
  | { type: 'failed'; error: string }
  | { type: 'refresh' }
  | { type: 'loadMore' }
  | { type: 'moreLoaded'; items: Lesson[]; hasMore: boolean };
```

Тип уже исключил комбинации: «загрузка с ошибкой» не компилируется. Редьюсер добавляет второе — **какие переходы разрешены**:

```ts
function listReducer(state: ListState, action: ListAction): ListState {
  switch (action.type) {
    case 'load':
      return state.status === 'idle' || state.status === 'error'
        ? { status: 'loading' }
        : state;
    case 'refresh':
      return state.status === 'success'
        ? { ...state, status: 'refreshing' }
        : state;
    case 'loadMore':
      return state.status === 'success' && state.hasMore
        ? { ...state, status: 'loadingMore' }
        : state;
    case 'loaded':
      return state.status === 'loading' || state.status === 'refreshing'
        ? { status: 'success', items: action.items, page: 1, hasMore: action.hasMore }
        : state;
    case 'moreLoaded':
      return state.status === 'loadingMore'
        ? { status: 'success', items: [...state.items, ...action.items],
            page: state.page + 1, hasMore: action.hasMore }
        : state;
    case 'failed':
      if (state.status === 'loading') return { status: 'error', error: action.error };
      if (state.status === 'refreshing' || state.status === 'loadingMore') {
        return { ...state, status: 'success' };     // список остаётся, ошибка — в тосте
      }
      return state;
  }
}
```

Что изменилось:

- **«подгрузка во время обновления» недостижима**: `loadMore` из состояния `refreshing` возвращает то же состояние. Не нужно помнить об этом в каждом обработчике — правило записано один раз;
- **ответ, пришедший не вовремя, игнорируется**: `moreLoaded` в состоянии `refreshing` (пользователь потянул обновление, пока шла подгрузка) ничего не меняет;
- **ошибка обновления не стирает список**: переход из `refreshing` по `failed` описан явно, и это решение видно в одном месте.

Возврат **того же объекта** `state` для запрещённого перехода — не небрежность: `Object.is` даёт `true`, и React отказывается от рендера потомков (3.3). Код проверен компилятором TypeScript в строгом режиме и запуском.

### Действие описывает, что произошло

Сравните:

```js
dispatch({ type: 'setStatus', status: 'loadingMore' });   // приказ «присвой»
dispatch({ type: 'loadMore' });                            // событие «пользователь доскроллил»
```

Первое — `useState`, переодетый в редьюсер: логика перехода снова у вызывающего, и редьюсер не может ничего запретить. Второе позволяет редьюсеру решить, что делать с этим событием в текущем состоянии. Именование действий как событий («что произошло») — главное отличие полезного редьюсера от церемонии.

### Функциональная форма `setState` — другой инструмент

```js
setCount((c) => c + 1);
```

Функциональная форма решает одну проблему: значение из замыкания устарело (1.14, 3.3), а новое должно вычисляться из актуального. Она не собирает логику в одном месте и не запрещает ни одного перехода: каждый вызывающий передаёт свою функцию. Эти инструменты регулярно путают, потому что оба «получают предыдущее состояние».

### Стабильный `dispatch`

`dispatch` не меняется между рендерами — это проверено на React 19.2 и гарантировано документацией. Следствия: его не нужно указывать в зависимостях эффектов (3.5), не нужно оборачивать в `useCallback` перед передачей в `memo`-компонент (3.11), и его можно передать глубоко через контекст, не вызывая рендеров (3.14). Обработчик, который только вызывает `dispatch`, тоже не зависит ни от чего реактивного.

### Редьюсер — чистая функция

Отсюда два следствия.

**Тест без рендера.** Редьюсер тестируется как обычная функция — без React, без моков, без таймеров:

```js
test('подгрузка во время обновления игнорируется', () => {
  const refreshing = { status: 'refreshing', items: [a], page: 1, hasMore: true };
  expect(listReducer(refreshing, { type: 'loadMore' })).toBe(refreshing);
});
```

Логика переходов экрана — самая хрупкая его часть — покрывается быстрыми тестами, которые не ломаются при изменении разметки.

**Двойной вызов в StrictMode.** В dev React вызывает редьюсер дважды на каждое действие (проверено на React 19.2), как и функцию компонента (3.4). Побочный эффект в редьюсере — запрос, аналитика, мутация входного состояния — проявится дважды. Редьюсер вычисляет следующее состояние и больше ничего не делает.

---

## 3. Почему это важно

**Невозможные комбинации — источник дефектов, которые не воспроизводятся.** Состояние «загрузка и ошибка» возникает при определённой последовательности событий: ошибка, потом повтор, потом быстрое обновление. Такие дефекты проходят ручное тестирование и появляются в отчётах как «иногда спиннер не исчезает». Редьюсер делает комбинацию недостижимой, а не просто маловероятной.

**Логика переходов становится видимой.** В варианте с флагами ответ на вопрос «что будет, если потянуть обновление во время подгрузки» разбросан по трём обработчикам. В редьюсере он в одной строке. Это меняет ревью: проверяется таблица переходов, а не каждая точка вызова.

**Ответы, пришедшие не вовремя, — норма в мобильном приложении.** Сеть медленная, пользователь нетерпелив, запросы перекрываются. Редьюсер, который игнорирует `moreLoaded` вне `loadingMore`, закрывает часть гонок на уровне состояния — до того, как ими займётся блок 07.

## 4. Где это в React Native

### Экран со списком

Типовой RN-экран почти никогда не ограничивается «загрузка / данные / ошибка». Добавляются pull-to-refresh (`RefreshControl`), подгрузка при достижении конца (`onEndReached`), пустое состояние, ошибка подгрузки, которая не должна стирать список. На флагах это пять-шесть булевых значений и десятки комбинаций; в редьюсере — шесть состояний и таблица переходов.

Особенно важно для `onEndReached`: `FlatList` может вызвать его несколько раз подряд, в том числе во время обновления. Редьюсер, у которого `loadMore` разрешён только из `success` с `hasMore`, отсекает лишние вызовы без отдельных флагов «уже загружаю».

### Форма со связанными полями

Форма, где поля зависят друг от друга: выбор курса сбрасывает выбор урока, переключение «оплата картой / наличными» меняет набор обязательных полей, отправка блокирует редактирование. На `useState` каждое такое правило — отдельный код в каждом обработчике. В редьюсере — действие `courseSelected`, которое само сбрасывает урок, и действие `submitStarted`, после которого `fieldChanged` игнорируется.

### Плеер урока

`idle → loading → playing ⇄ paused → ended`, плюс `buffering` и `error`. Переходы здесь важнее значений: `pause` из `loading` не имеет смысла, `play` из `ended` означает перезапуск. Классический случай для редьюсера.

## 5. Типичные ошибки

**Редьюсер с одним действием `set`.** `dispatch({ type: 'set', field: 'status', value: 'loading' })`. Возникает, когда `useReducer` выбирают «потому что состояние сложное», не меняя модели. Получается `useState` с лишним слоем: логика переходов по-прежнему у вызывающего, запретить нечего.

**Мутация состояния в редьюсере.** `state.items.push(...); return state;` Возникает из привычки к изменяемым структурам. Возвращается тот же объект — React отказывается от обновления (3.3, 3.10), экран не меняется. В StrictMode мутация выполняется дважды. Подробно об иммутабельных обновлениях — 6.4.

**Побочный эффект в редьюсере.** Запрос «раз уж перешли в `loading`». Возникает из желания держать всё рядом. Редьюсер вызывается при рендере, может вызываться дважды и не должен знать о сети. Запрос — в обработчике, который отправляет действие, или в эффекте, синхронизирующем с сервером.

**«Функциональная форма `setState` даёт то же самое».** Возникает из того, что обе формы получают предыдущее значение. Функциональная форма не централизует логику и ничего не запрещает.

**Редьюсер для одного независимого значения.** `useReducer` для флага «меню раскрыто». Возникает из правила «редьюсер — лучшая практика». Здесь нет переходов, которые нужно запрещать, и косвенность не окупается.

**«Редьюсер — это Redux».** Возникает из того, что термин пришёл оттуда. `useReducer` — локальное состояние компонента; к глобальному стору, middleware и селекторам он отношения не имеет (6.3, 6.4).

## 6. Trade-offs

### Больше кода против явных переходов

Редьюсер для экрана списка — это тип состояния, тип действий и функция на 40 строк вместо пяти `useState`. На простом состоянии (одно-два независимых значения) это чистая потеря. Порог, за которым редьюсер окупается: **значения связаны, и не все их комбинации осмысленны**. Не «много состояния», а «есть переходы, которые нужно запрещать».

### Косвенность при чтении

Чтобы понять, что делает кнопка, в варианте с редьюсером нужно открыть редьюсер и найти действие. Для команды, не привыкшей к этой модели, это замедляет чтение. Компенсация — имена действий как событий (`refreshRequested`, а не `setRefreshing`) и таблица переходов в одном месте, которую легче проверить на ревью, чем разбросанные обработчики.

### Где лежит логика: компонент, редьюсер, домен

Редьюсер внутри файла компонента — логика экрана. Если те же переходы нужны в двух экранах или в тестах домена, редьюсер выносится в отдельный модуль как чистая функция. Это шаг в сторону слоёв из блока 08; на P3 достаточно того, что редьюсер тестируется без рендера.
