# 3.8 `useState` vs `useReducer` — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **какие переходы разрешены и где это записано**, а не «редьюсер — для сложного состояния».

---

**1. Экран со списком хранит `isLoading`, `isRefreshing`, `isLoadingMore` и `error`. Какие комбинации не имеют смысла, и как редьюсер их исключает — тип или функция?**

<details>
<summary>Ответ</summary>

Четыре значения (три флага и наличие ошибки) дают шестнадцать комбинаций. Осмысленных пять: покой, первая загрузка, обновление, подгрузка, ошибка первой загрузки. Бессмысленные — любые два флага загрузки одновременно (первая загрузка и обновление, обновление и подгрузка…), загрузка вместе с ошибкой, первая загрузка при уже показанном списке.

Исключение работает на двух уровнях, и их полезно различать:

- **тип** (discriminated union, 2.5) делает бессмысленные **комбинации** невыразимыми: состояния `{ status: 'loading', error }` не существует, оно не компилируется;
- **редьюсер** делает бессмысленные **переходы** невыполнимыми: из `refreshing` действие `loadMore` возвращает то же состояние, ответ `moreLoaded` вне `loadingMore` игнорируется.

Тип без редьюсера допускает любой переход между допустимыми состояниями — обработчик может перевести экран из `refreshing` прямо в `loadingMore`. Редьюсер без типа может случайно вернуть бессмысленную комбинацию. Вместе они закрывают оба класса ошибок.

**Ответ «редьюсер просто удобнее, когда флагов много»** вскрывает выбор по количеству, а не по связности.

**Ответ «достаточно аккуратно сбрасывать флаги в обработчиках»** — работает до первого нового обработчика или первого ответа, пришедшего не вовремя.
</details>

---

**2. В редьюсере при переходе в `loading` вызывается `analytics.track('list_load')`. В dev аналитика получает два события на одно нажатие. Почему, и где этот вызов должен быть?**

<details>
<summary>Ответ</summary>

В StrictMode React в dev вызывает редьюсер дважды на каждое действие — проверено на React 19.2. Это та же проверка, что двойной вызов функции компонента и инициализаторов (3.4): редьюсер обязан быть чистым, и двойной вызов это проверяет.

Дело не только в StrictMode. Редьюсер вызывается при обработке очереди, то есть в render-фазе, и в общем случае React может вызвать его повторно или выбросить результат (3.3, 3.17). Поэтому любой побочный эффект в нём — некорректен и в release.

Правильное место — там, где происходит событие: в обработчике, который вызывает `dispatch({ type: 'load' })`. Если событие аналитики должно отражать **фактический** переход (а не попытку, которую редьюсер может отклонить), обработчик может проверить текущее состояние перед отправкой — или переход фиксируется эффектом, синхронизирующим аналитику с `state.status`, если это действительно синхронизация.

**Ответ «это особенность dev, в release будет одно событие»** — верно про release, но это и есть признак: код корректен только при условии, которое React не обещает.
</details>

---

**3. Чем `setCount((c) => c + 1)` отличается от `dispatch({ type: 'increment' })`, если оба получают предыдущее значение?**

<details>
<summary>Ответ</summary>

Обе формы решают проблему устаревшего значения: новое вычисляется из актуального на момент обработки очереди, а не из замыкания (1.14, 3.3).

Различие — в том, где лежит логика перехода:

- **функциональный `setState`** — логика у вызывающего. Каждое место вызова передаёт свою функцию; ничто не мешает в одном месте написать `c + 1`, а в другом `c - 1` при условии, которого нет в первом. Запретить переход нельзя: функция вызывающего возвращает то, что возвращает;
- **`dispatch`** — вызывающий сообщает, что произошло, а решение принимает редьюсер — одна функция, в одном месте, с полной картиной: текущее состояние и все возможные события.

Для счётчика разницы почти нет. Для экрана со списком это разница между «правила разбросаны по обработчикам» и «правила в одной таблице, которую можно протестировать без рендера».

**Ответ «это одно и то же, `useState` — это `useReducer` внутри»** — верно про реализацию React, неверно про модель кода. Механизм один, место логики — разное.
</details>

---

**4. Когда `useReducer` проигрывает `useState`?**

<details>
<summary>Ответ</summary>

Когда переходов, которые нужно запрещать, нет:

- **одно независимое значение** — раскрыто ли меню, текст поля поиска, выбранная вкладка. Любое значение допустимо из любого состояния, редьюсер сведётся к `set`;
- **несколько независимых значений** — фильтр и сортировка, которые не влияют друг на друга. Редьюсер объединит их искусственно, и каждое действие будет менять одно поле;
- **значение, которое полностью определяется вызывающим** — контролируемое поле формы без связей с другими полями.

Во всех этих случаях редьюсер добавляет тип действий, функцию и косвенность при чтении, ничего не давая взамен. Признак правильного выбора `useReducer`: можно назвать хотя бы одну пару «состояние + событие», для которой ответ — «ничего не делать», или событие, которое меняет несколько значений согласованно.

**Ответ «никогда, редьюсер всегда лучше масштабируется»** вскрывает выбор инструмента по правилу, а не по задаче.
</details>

## Задание — экран на четырёх флагах

**Дано.** Экран списка курсов RN Academy. В блоке 02 (2.5) его состояние уже было описано discriminated union на уровне типов; в коде экрана по-прежнему флаги.

```jsx
function CoursesScreen() {
  const [courses, setCourses] = useState([]);
  const [isLoading, setIsLoading] = useState(false);
  const [isRefreshing, setIsRefreshing] = useState(false);
  const [isLoadingMore, setIsLoadingMore] = useState(false);
  const [error, setError] = useState(null);
  const [page, setPage] = useState(1);

  async function load() {
    setIsLoading(true);
    try {
      const res = await api.courses(1);
      setCourses(res.items);
    } catch (e) {
      setError(e.message);
    }
    setIsLoading(false);
  }

  async function refresh() {
    setIsRefreshing(true);
    const res = await api.courses(1);
    setCourses(res.items);
    setPage(1);
    setIsRefreshing(false);
  }

  async function loadMore() {
    if (isLoadingMore) return;
    setIsLoadingMore(true);
    const res = await api.courses(page + 1);
    setCourses([...courses, ...res.items]);
    setPage(page + 1);
    setIsLoadingMore(false);
  }

  useEffect(() => { load(); }, []);
  // FlatList с refreshing={isRefreshing}, onRefresh={refresh}, onEndReached={loadMore}
}
```

QA сообщает: «после ошибки и повторной загрузки сообщение об ошибке висит под списком», «если потянуть обновление во время подгрузки, в списке появляются дубли», «при ошибке обновления индикатор не исчезает».

**Требуется.**

1. Для каждой жалобы найти причину в коде.
2. Перевести состояние на `useReducer` с типом из 2.5. Назвать действия как события.
3. Показать, какие из шестнадцати комбинаций флагов стали недостижимыми и какие переходы редьюсер отклоняет.
4. Написать три теста редьюсера без рендера, по одному на каждую жалобу QA.

---

<details>
<summary>Разбор</summary>

**1. Причины.**

*Ошибка висит после повторной загрузки.* `load` ставит `error` при неудаче, но нигде его не сбрасывает. Повторная загрузка успешна, `courses` заполнен, `error` остался.

*Дубли после обновления во время подгрузки.* `refresh` и `loadMore` не знают друг о друге. Подгрузка стартовала со страницей `page + 1` и старым `courses` в замыкании; обновление заменило список первой страницей; ответ подгрузки пришёл позже и выполнил `setCourses([...courses, ...res.items])` — со **старым** списком из замыкания. Результат — старый список плюс вторая страница, а первая страница из обновления потеряна. Если ответы придут в другом порядке — дубли страницы.

*Индикатор обновления не исчезает.* В `refresh` нет `try/finally`: исключение из `api.courses` прерывает функцию до `setIsRefreshing(false)`.

**2. Редьюсер.**

Тип состояния и действий — из теории урока (`ListState`, `ListAction`). Экран:

```jsx
function CoursesScreen() {
  const [state, dispatch] = useReducer(listReducer, { status: 'idle' });

  async function load() {
    dispatch({ type: 'load' });
    try {
      const res = await api.courses(1);
      dispatch({ type: 'loaded', items: res.items, hasMore: res.hasMore });
    } catch (e) {
      dispatch({ type: 'failed', error: e.message });
    }
  }

  async function refresh() {
    dispatch({ type: 'refresh' });
    try {
      const res = await api.courses(1);
      dispatch({ type: 'loaded', items: res.items, hasMore: res.hasMore });
    } catch (e) {
      dispatch({ type: 'failed', error: e.message });
    }
  }

  async function loadMore() {
    if (state.status !== 'success' || !state.hasMore) return;
    dispatch({ type: 'loadMore' });
    try {
      const res = await api.courses(state.page + 1);
      dispatch({ type: 'moreLoaded', items: res.items, hasMore: res.hasMore });
    } catch (e) {
      dispatch({ type: 'failed', error: e.message });
    }
  }

  useEffect(() => { load(); }, []);   // загрузка при показе экрана — синхронизация с сервером (3.7)
}
```

Проверка в `loadMore` до `dispatch` нужна, чтобы не отправлять лишний запрос; но **корректность** не зависит от неё: даже если запрос ушёл, редьюсер отклонит `moreLoaded` вне `loadingMore`. Гонки запросов и отмена — блок 07; здесь редьюсер закрывает их последствия для состояния.

Ошибка обновления и подгрузки не стирает список — переход `failed` из `refreshing` и `loadingMore` возвращает `success` с прежними данными; сообщение показывается тостом в обработчике. Это решение записано в одном месте редьюсера.

**3. Что стало недостижимым.**

Комбинации флагов, которые больше не выражаются: любые два или три флага загрузки одновременно, любой флаг загрузки вместе с ошибкой, ошибка при показанном после успешного повтора списке. Из шестнадцати комбинаций остались пять осмысленных состояний плюс `idle` — каждое отдельным вариантом типа.

Переходы, которые редьюсер отклоняет (возвращает то же состояние):

| Состояние | Событие | Почему отклонено |
|---|---|---|
| `refreshing` | `loadMore` | подгрузка во время обновления даёт дубли |
| `loadingMore` | `refresh` | решение проекта: дождаться подгрузки (можно решить и иначе — но в одном месте) |
| `refreshing` | `moreLoaded` | ответ устаревшей подгрузки |
| `loading` | `refresh`, `loadMore` | данных ещё нет |
| `success` без `hasMore` | `loadMore` | `onEndReached` вызывается повторно у конца списка |

**4. Тесты.**

```js
const a = { id: 'a', title: 'A' };
const b = { id: 'b', title: 'B' };

test('успешный повтор после ошибки не оставляет ошибку', () => {
  const failed = listReducer({ status: 'loading' }, { type: 'failed', error: 'offline' });
  const retry = listReducer(failed, { type: 'load' });
  const ok = listReducer(retry, { type: 'loaded', items: [a], hasMore: false });
  expect(ok).toEqual({ status: 'success', items: [a], page: 1, hasMore: false });
});

test('ответ подгрузки во время обновления игнорируется', () => {
  const refreshing = { status: 'refreshing', items: [a], page: 2, hasMore: true };
  expect(listReducer(refreshing, { type: 'moreLoaded', items: [b], hasMore: true })).toBe(refreshing);
  expect(listReducer(refreshing, { type: 'loadMore' })).toBe(refreshing);
});

test('ошибка обновления возвращает список и снимает индикатор', () => {
  const refreshing = { status: 'refreshing', items: [a], page: 1, hasMore: true };
  const after = listReducer(refreshing, { type: 'failed', error: 'timeout' });
  expect(after.status).toBe('success');
  expect(after.items).toEqual([a]);
});
```

`toBe` во втором тесте проверяет не только равенство, но и **тот же объект**: редьюсер вернул исходное состояние, и React откажется от рендера (3.3).

Ни один тест не рендерит компонент, не мокает сеть и не ждёт таймеров. Третья жалоба QA (`try/finally`) в коде экрана исправлена отдельно — `failed` теперь отправляется на любой ошибке, — но **поведение** при ошибке зафиксировано тестом редьюсера.

**Вклад в проект (P3).** Состояние экрана списка курсов RN Academy — редьюсер над discriminated union из P2; таблица переходов покрыта unit-тестами без рендера. Это первый тест P3 и пример того, что логику React-слоя можно тестировать без React.
</details>
