# 3.1 Reconciliation и Fiber — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что такое Virtual DOM» — а на вопрос, **по какому признаку React решает, что компонент «тот же», и почему от этого зависит, сохранится ли его состояние**.

---

## 1. Что это

В работе React участвуют три разные сущности, и большая часть путаницы вокруг рендера возникает от того, что их называют одним словом «компонент».

**Элемент** — то, что возвращает JSX. Обычный неизменяемый объект-описание:

```js
<LessonCard title="Closures" />
// ≈ { type: LessonCard, key: null, props: { title: 'Closures' } }
```

Элемент ничего не хранит и ничего не умеет. Каждый рендер создаёт новые элементы.

**Fiber** — внутренний узел дерева React, который живёт **между** рендерами. В нём лежит всё, что у компонента «постоянного»: состояние хуков, очередь обновлений, ссылка на host-узел, флаги эффектов. Когда говорят «состояние компонента», имеют в виду состояние, записанное на fiber.

**Host-узел** — то, что видит платформа. В вебе это DOM-элемент, в React Native — узел Shadow Tree, из которого затем получается нативный view (4.3). Host-узлы есть только у host-компонентов (`View`, `Text`, `TextInput`); у ваших компонентов их нет.

**Reconciliation** — процесс, в котором React сопоставляет новое дерево элементов с текущим деревом fiber и решает для каждой позиции: переиспользовать узел, обновить его или создать заново.

### Ключевая формулировка урока

> **Состояние принадлежит не функции компонента, а позиции в дереве. Тип элемента и его место — это всё, по чему React узнаёт «тот же» компонент.**

---

## 2. Как это работает

### Fiber как узел и как единица работы

Упрощённо fiber — это объект с такими полями:

```
type            — функция компонента, класс или строка host-компонента
key             — ключ среди соседей (3.2)
memoizedState   — связный список хуков этого компонента (3.5)
updateQueue     — поставленные, но ещё не применённые обновления (3.3)
stateNode       — host-узел (для host-компонентов)
child / sibling / return — связи с первым ребёнком, соседом и родителем
alternate       — парный fiber из другого дерева
flags, lanes    — что нужно сделать в commit и с каким приоритетом
```

Связи `child / sibling / return` превращают дерево в структуру, которую можно обходить **без рекурсии**: обход — это цикл, который берёт текущий fiber, обрабатывает его и переходит к следующему. Именно это делает fiber **единицей работы**: между любыми двумя итерациями цикла React может остановиться, проверить, не пора ли уступить поток, и потом продолжить с того же места.

До Fiber (React 15 и раньше) рендер был рекурсивным вызовом функций. Рекурсию нельзя приостановить посередине: стек вызовов существует только пока она идёт. Большое дерево занимало поток до конца — это ровно та ситуация из 1.20, когда одна длинная задача блокирует обработку всех событий.

### Два дерева

React держит два дерева fiber одновременно:

- **current** — то, что сейчас отображено;
- **work-in-progress** — то, что строится в ходе рендера.

Каждый fiber current-дерева связан полем `alternate` со своей парой в work-in-progress. Рендер заполняет work-in-progress, не трогая current; если рендер прерван или выброшен, экран это никак не затрагивает. Когда работа закончена, commit применяет изменения к host-узлам и переключает указатель корня: work-in-progress становится current.

Отсюда важное следствие для 3.3 и 3.17: **рендер может не дойти до экрана.** Функция компонента может быть вызвана, а её результат — выброшен.

### Эвристики сравнения

Оптимальное сравнение двух произвольных деревьев стоит порядка O(n³). React вместо этого использует две эвристики, которые дают линейное время:

**1. Разные типы — разные деревья.** Если на той же позиции стоит элемент другого `type`, React не пытается сравнивать содержимое: старое поддерево размонтируется целиком, вместе со всем состоянием, новое монтируется с нуля.

```jsx
{isEditing ? <LessonEditor /> : <LessonView />}
```

При переключении `LessonView` размонтируется, `LessonEditor` монтируется. Даже если внутри у них одинаковые дочерние компоненты, их состояние не сохранится: поддерево другого типа — другое поддерево.

**2. Соседи сопоставляются по `key`, а без ключа — по индексу.** Внутри одного родителя React сопоставляет детей нового рендера с детьми старого: по `key`, если он есть, иначе по порядковому номеру. Это тема 3.2.

Тот же `type` на той же позиции — тот же fiber: React вызывает компонент с новыми пропсами, и состояние сохраняется.

### Что такое «позиция»

Позиция — это место среди детей родителя. Важная деталь: `false`, `null` и `undefined` **занимают место**, хотя ничего не рисуют.

```jsx
<View>
  {showBanner && <Banner />}   {/* позиция 0: Banner или false */}
  <LessonForm />               {/* позиция 1 — всегда */}
</View>
```

Появление баннера не сдвигает форму: она остаётся на позиции 1, состояние сохраняется. А вот так — сдвигает:

```jsx
if (showBanner) {
  return <View><Banner /><LessonForm /></View>;   // форма на позиции 1
}
return <View><LessonForm /></View>;               // форма на позиции 0
```

Две разные «формы» дерева: при переключении `LessonForm` оказывается на другой позиции, и React видит на месте старой формы `Banner` другого типа. Форма размонтируется и монтируется заново — введённый текст пропадает.

### Прерываемость: что прерывается на самом деле

Fiber сделал прерываемость **возможной**, но не сделал её **поведением по умолчанию**. В React 18 и 19 рендер идёт одним из двух циклов:

- **синхронный** — обходит дерево до конца, не уступая поток. Так рендерятся обновления от дискретных событий (нажатие, ввод) и обновления по умолчанию;
- **конкурентный** — после каждой единицы работы проверяет, не истёк ли отведённый отрезок времени (порядка 5 мс), и при необходимости уступает поток. Так рендерятся переходы (`startTransition`), отложенные значения (`useDeferredValue`) и повторные попытки после Suspense.

Как приоритет назначается обновлению и что React делает с прерванной работой — 3.3 и 3.17. Здесь важно одно: **фраза «с Fiber рендер прерываемый» верна только для части обновлений.**

## 3. Почему это важно

**Состояние живёт по правилам reconciliation, а не по правилам JavaScript.** Функция компонента не хранит ничего: при каждом вызове её локальные переменные создаются заново. Сохранится ли `useState` — решает не код компонента, а то, найдёт ли React на той же позиции элемент того же типа. Разработчик, который этого не видит, сталкивается с «магией»: состояние иногда сбрасывается, иногда — нет, и связи с кодом компонента не видно.

**Сброс состояния — это не перерисовка, а уничтожение.** Размонтирование поддерева — это очистка всех его эффектов, потеря всех ref и создание всех host-узлов заново. Разница между «обновить» и «пересоздать» — одна из самых крупных по цене в React, и решает её именно reconciliation.

**Прерываемость определяет, что разрешено делать при рендере.** Раз рендер может быть выброшен или повторён, функция компонента обязана быть чистой: побочный эффект, выполненный в выброшенном рендере, останется в мире, хотя рендера «не было». Это правило — главное следствие Fiber для повседневного кода (3.3, 3.4).

## 4. Где это в React Native

### Render на JS-потоке, результат — на UI-потоке

Вся работа reconciliation происходит на JS-потоке. В New Architecture host-узлами являются узлы Shadow Tree: при рендере React создаёт и клонирует их через JSI, при commit — передаёт новое дерево Fabric. Fabric вычисляет layout (Yoga, в C++) и планирует применение мутаций к нативным view, которое выполняется на UI-потоке (4.1, 4.3). Нативная сторона не видит ни ваших компонентов, ни их состояния — только итоговое дерево host-узлов.

Отсюда практический вывод: **всё, что разбирается в этом блоке, — работа JS-потока.** Когда в блоке 05 будет нужно отделить «медленный рендер» от «медленного применения к нативным view», граница пройдёт ровно по фазам этого урока.

### Сброс поддерева в RN дороже

В вебе пересоздание поддерева — это пересоздание DOM-узлов. В RN — уничтожение и создание нативных view: изображения декодируются заново, `TextInput` теряет фокус, текст и позицию курсора, `ScrollView` — позицию прокрутки, видеоплеер — буфер. Ошибка, которая в веб-приложении выглядит как лишняя работа, в RN выглядит как дефект поведения: «список прыгает наверх», «клавиатура закрывается при вводе».

### Где это встречается

- **Компонент, объявленный внутри компонента.** Частый случай — `renderItem`-компонент или «маленький помощник», объявленный в теле экрана. Подробно — угол 5.
- **Экран с условной обёрткой.** «Если идёт загрузка — обернуть содержимое в `View` с оверлеем» меняет форму дерева, и всё содержимое перемонтируется при каждой загрузке.
- **Платформенное ветвление через разные компоненты** (`Platform.OS === 'ios' ? <IOSHeader /> : <AndroidHeader />`) — нормально, пока ветка не меняется во время жизни экрана.

## 5. Типичные ошибки

**Компонент, объявленный внутри другого компонента.**

```jsx
function LessonList({ lessons }) {
  function Row({ lesson }) {               // новая функция на каждый рендер
    const [expanded, setExpanded] = useState(false);
    return <Pressable onPress={() => setExpanded(!expanded)}>...</Pressable>;
  }
  return lessons.map((l) => <Row key={l.id} lesson={l} />);
}
```

`Row` — новая функция при каждом рендере `LessonList`, то есть новый `type`. Для React это «на позиции стоял элемент типа A, теперь стоит элемент типа B»: все строки размонтируются и монтируются заново, раскрытые строки сворачиваются. Возникает из желания держать помощника рядом с местом использования и из того, что на первом рендере всё работает. Исправление — объявить `Row` на верхнем уровне модуля и передать нужное через пропсы.

**Условный рендер, меняющий форму дерева.** Ранний `return` с другой обёрткой, оборачивание содержимого в `View` по условию. Возникает потому, что на уровне кода это выглядит как «то же самое плюс баннер». Исправление — держать форму дерева постоянной: условное содержимое через `&&` на своей позиции, обёртку — всегда, меняя только её стиль.

**«React сравнивает предыдущий экран с новым».** Возникает из упрощённого объяснения Virtual DOM. React сравнивает **элементы с fiber**, а не host-узлы с host-узлами, и не смотрит на содержимое поддерева другого типа вообще. Отсюда неверные ожидания: «внутри одинаковые компоненты, значит, состояние сохранится».

**«Fiber — это архитектура рендеринга RN».** Возникает из одновременного появления терминов Fiber и Fabric. Fiber — алгоритм React, одинаковый для веба и RN. Fabric — рендерер RN, принимающий результат этого алгоритма. Смешение мешает в блоке 04: проблемы Fabric не решаются изменениями в компонентах, и наоборот.

**«С Fiber весь рендер прерываемый, поэтому длинный рендер не блокирует UI».** Возникает из описаний Fiber как «прерываемого рендеринга». Обновления от нажатий и по умолчанию рендерятся синхронно, до конца. Длинный рендер после нажатия блокирует JS-поток ровно так же, как в React 15.

## 6. Trade-offs

### Эвристика вместо оптимального сравнения

React платит за линейное время тем, что перекладывает часть работы на разработчика: **стабильные типы и стабильные ключи — обязанность автора кода.** Алгоритм не попытается понять, что `LessonEditor` и `LessonView` — «почти одно и то же», и не догадается, что элементы списка переставлены, если ключей нет. Взамен сравнение предсказуемо: правило «другой тип — другое поддерево» можно применить, читая код, без запуска профайлера.

### Сброс через смену типа как инструмент

Та же эвристика работает и как инструмент: если поддерево **нужно** пересоздать — например, форму при смене редактируемой сущности, — смена типа или ключа (3.2) делает это без единой строки кода сброса. Цена — полная стоимость монтирования поддерева, включая нативные view в RN. Это не бесплатно, и на тяжёлом поддереве сброс через ключ может оказаться дороже, чем точечный сброс состояния (3.7).

### Прерываемость против простоты модели

Прерываемый рендер даёт отзывчивость, но отбирает гарантию «если функция компонента вызвана, её результат будет на экране». Всё, что опиралось на эту гарантию — побочные эффекты при рендере, подсчёт рендеров в переменной модуля, подписка в теле компонента, — становится ошибкой. React сделал прерываемость опциональной (только для переходов) именно потому, что эта цена реальна.
