# 3.1 Reconciliation и Fiber — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **что React сопоставил с чем** — тип, позицию, ключ, — а не процитировать определение Virtual DOM.

---

**1. Компонент `Row` объявлен внутри тела `LessonList`. Почему раскрытые строки сворачиваются при каждом рендере списка, хотя ключи стабильные?**

<details>
<summary>Ответ</summary>

Потому что при каждом рендере `LessonList` выражение `function Row() {...}` создаёт **новую функцию**, а функция компонента — это `type` элемента. На позиции, где в прошлом рендере стоял элемент типа `Row₁`, теперь стоит элемент типа `Row₂`. Для React это разные типы, и действует первая эвристика: старое поддерево размонтируется целиком, новое монтируется с нуля.

Ключи здесь ни при чём: `key` сопоставляет соседей **одного типа**. Сначала React сравнивает тип, и при несовпадении до ключа дело не доходит.

Проверяется в эксперименте: эффект с логом в `Row` показывает «размонтирован / смонтирован» для каждой строки при любом изменении состояния `LessonList`.

В RN цена выше, чем просто сброс `expanded`: нативные view строк уничтожаются и создаются заново, картинки декодируются повторно, а если в строке был `TextInput` — он теряет фокус и закрывает клавиатуру.

**Ответ «из-за того, что функция `Row` пересоздаётся, она медленнее»** вскрывает модель «пересоздание функции стоит производительности». Создание функции дёшево; дорого то, что React из-за нового `type` уничтожает поддерево.

**Ответ «надо обернуть `Row` в `useCallback` или `useMemo`»** — формально стабилизирует тип, но маскирует причину и нарушает модель: компонент, объявленный в рендере, остаётся зависимым от замыкания родителя. Правильное исправление — объявить `Row` на верхнем уровне модуля.

**Ответ «из-за ключей»** вскрывает неверный порядок проверок: ключ проверяется после типа.
</details>

**2. Сравните два варианта. В каком из них `LessonForm` сохраняет введённый текст при появлении баннера?**

```jsx
// A
<View>
  {showBanner && <Banner />}
  <LessonForm />
</View>

// B
if (showBanner) return <View><Banner /><LessonForm /></View>;
return <View><LessonForm /></View>;
```

<details>
<summary>Ответ</summary>

В варианте **A** — сохраняет. `false` занимает позицию 0 так же, как `Banner`: дети родителя — это массив из двух элементов в обоих случаях, и `LessonForm` всегда на позиции 1. Тип и позиция совпадают, fiber тот же, состояние сохраняется.

В варианте **B** — теряет. Без баннера `LessonForm` — единственный ребёнок, на позиции 0. С баннером на позиции 0 стоит `Banner` — элемент другого типа, — а `LessonForm` переехал на позицию 1, где раньше не было ничего. React размонтирует старую форму и смонтирует новую.

Различие проверяется логом в эффекте `LessonForm`: в варианте B при каждом переключении видно размонтирование.

**Ответ «одинаково, потому что `LessonForm` присутствует в обоих JSX»** вскрывает модель «React ищет такой же компонент где-нибудь в дереве». React не ищет: он сравнивает позицию с позицией.

**Ответ «в варианте A тоже теряет, потому что меняется количество элементов»** вскрывает незнание того, что `false` и `null` занимают место среди детей. Эта деталь — основа приёма «условное содержимое на постоянной позиции».

**Ответ «нужно добавить `key` форме»** — в варианте B ключ действительно поможет (`key` на обоих `LessonForm` даст сопоставление по ключу, а не по позиции), но это лечение формы дерева ключом, а не исправление формы. Вариант A проще и не требует знать про это.
</details>

**3. «С появлением Fiber рендер стал прерываемым, поэтому тяжёлый рендер после нажатия кнопки больше не блокирует интерфейс». Что в этом утверждении верно, а что нет?**

<details>
<summary>Ответ</summary>

Верно, что Fiber сделал прерываемость **возможной**: обход дерева — это цикл по единицам работы, и между итерациями React может уступить поток, чего рекурсивный рендер React 15 не умел.

Неверно, что прерываемость — поведение по умолчанию. В React 18 и 19 обновления от дискретных событий (нажатие, ввод текста) и обновления по умолчанию рендерятся **синхронным** циклом: он обходит всё дерево до конца, не уступая поток. Прерываемым циклом рендерятся только переходы (`startTransition`, `useTransition`), отложенные значения (`useDeferredValue`) и повторы после Suspense.

Отсюда практический вывод: тяжёлый рендер, вызванный `setState` в `onPress`, блокирует JS-поток так же, как блокировал бы в React 15. Чтобы React мог его прерывать, обновление нужно явно пометить переходом — и даже тогда прерывание возможно только **между** компонентами: функция одного компонента, работающая 200 мс, не прерывается внутри (3.17).

**Ответ «да, всё верно»** вскрывает знакомство с Fiber по анонсам, а не по поведению. Опасная модель: с ней не ищут причину подвисания после нажатия.

**Ответ «Fiber прерываемый, но RN — нет»** вскрывает смешение Fiber и Fabric. Правило одинаково для веба и RN; RN лишь добавляет, что commit и монтирование нативных view не прерываются ни в каком режиме.
</details>

**4. Почему функция компонента обязана быть чистой — и при чём здесь два дерева fiber?**

<details>
<summary>Ответ</summary>

React строит work-in-progress дерево, не трогая current, и только в commit переключает их. Между началом рендера и commit работа может быть выброшена: переход прерван более срочным обновлением, компонент приостановился в Suspense, в dev StrictMode вызывает функцию компонента дважды и использует один из результатов.

Значит, **вызов функции компонента не означает, что её результат появится на экране**. Если функция при вызове делает что-то в мире — отправляет аналитику, мутирует объект модуля, подписывается на emitter, — это действие останется, даже если рендер выброшен. Аналитика посчитает просмотр, которого не было; подписка останется без очистки, потому что эффекта, который её снимет, не будет.

Поэтому всё, что меняет мир, выносится из тела компонента: в обработчики событий (действие пользователя) или в эффекты (синхронизация после commit, 3.4, 3.7).

**Ответ «чистота нужна для производительности»** вскрывает подмену причины. Чистота нужна для **корректности** при выброшенном или повторённом рендере.

**Ответ «функция вызывается только когда что-то изменилось, поэтому один раз на изменение»** вскрывает модель «рендер = коммит». Число вызовов функции компонента React не гарантирует вообще.
</details>

## Задание — экран урока, теряющий состояние

**Дано.** Экран урока RN Academy. Жалобы пользователей: «при загрузке следующей части урока сворачиваются раскрытые блоки» и «пока сохраняется заметка, введённый текст пропадает».

```jsx
export function LessonScreen({ lesson, isSaving, onSaveNote }) {
  function Section({ section }) {
    const [expanded, setExpanded] = useState(false);
    return (
      <View>
        <Pressable onPress={() => setExpanded((e) => !e)}>
          <Text>{section.title}</Text>
        </Pressable>
        {expanded && <Text>{section.body}</Text>}
      </View>
    );
  }

  const content = (
    <>
      {lesson.sections.map((s) => <Section key={s.id} section={s} />)}
      <NoteInput onSubmit={onSaveNote} />
    </>
  );

  if (isSaving) {
    return (
      <View style={styles.overlayHost}>
        {content}
        <ActivityIndicator style={styles.overlay} />
      </View>
    );
  }
  return content;
}
```

`NoteInput` — компонент с локальным состоянием введённого текста.

**Требуется.**

1. Для каждой из двух жалоб назвать по шагам, что React сопоставил с чем и почему состояние сброшено.
2. Указать, какая из жалоб воспроизводится при **любом** рендере `LessonScreen`, а какая — только при определённом изменении пропсов.
3. Исправить код, не добавляя `key` ради сохранения состояния и не поднимая состояние выше.
4. Сформулировать два правила проекта, которые не дали бы этим дефектам появиться.

---

<details>
<summary>Разбор</summary>

**1. Что сопоставлено с чем.**

*Сворачиваются блоки.* `Section` объявлен внутри `LessonScreen`, поэтому при каждом рендере экрана создаётся новая функция — новый `type`. Ключи у секций стабильные, но сопоставление начинается с типа: на позиции, где был элемент типа `Section₁` с ключом `s1`, теперь элемент типа `Section₂` с ключом `s1`. Тип не совпал — поддерево размонтировано, `expanded` вернулся к `false`.

*Пропадает текст заметки.* При `isSaving === false` экран возвращает фрагмент: дети корня — секции и `NoteInput` на верхнем уровне. При `isSaving === true` возвращается `View`, внутри которого фрагмент с теми же детьми и индикатор. На месте фрагмента в корне теперь стоит `View` — элемент другого типа. Всё поддерево, включая `NoteInput`, размонтируется и монтируется внутри новой обёртки; состояние введённого текста теряется. Когда сохранение закончится, форма поменяется обратно — и снова с полным перемонтированием.

**2. Когда воспроизводится.**

Сворачивание секций — при **любом** рендере `LessonScreen`: смене `lesson`, `isSaving`, `onSaveNote`, рендере родителя. Нового `type` достаточно, чтобы сбросить всё.

Пропажа текста — только при переключении `isSaving`. Это объясняет, почему вторую жалобу сложнее воспроизвести: она привязана к моменту сохранения. Заметим, что при переключении `isSaving` сворачиваются и секции — но они сворачиваются в этот момент по обеим причинам сразу.

**3. Исправление.**

```jsx
function Section({ section }) {
  const [expanded, setExpanded] = useState(false);
  return (
    <View>
      <Pressable onPress={() => setExpanded((e) => !e)}>
        <Text>{section.title}</Text>
      </Pressable>
      {expanded && <Text>{section.body}</Text>}
    </View>
  );
}

export function LessonScreen({ lesson, isSaving, onSaveNote }) {
  return (
    <View style={styles.overlayHost}>
      {lesson.sections.map((s) => <Section key={s.id} section={s} />)}
      <NoteInput onSubmit={onSaveNote} />
      {isSaving && <ActivityIndicator style={styles.overlay} />}
    </View>
  );
}
```

Два изменения, по одному на причину:

- `Section` объявлен на верхнем уровне модуля — тип стабилен между рендерами;
- форма дерева постоянна: обёртка `View` есть всегда, индикатор занимает свою позицию через `&&` и при отсутствии оставляет там `false`. `NoteInput` всегда на одной позиции внутри одной обёртки.

Почему не `key`: ключ на `NoteInput` в обеих ветках формально сохранил бы его состояние при смене обёртки — нет, не сохранил бы. Ключ сопоставляет соседей **внутри одного родителя**, а здесь меняется сам родитель (фрагмент против `View`). Состояние не переносится между родителями никаким ключом. Это хорошая проверка модели: ключ — не глобальный идентификатор.

Проверка исправления: лог в эффекте `Section` и `NoteInput` не показывает размонтирования ни при смене `isSaving`, ни при рендере родителя.

**4. Правила проекта.**

- Компоненты объявляются только на верхнем уровне модуля. Помощник, которому нужны данные родителя, получает их через пропсы. Это же правило проверяет `eslint-plugin-react-hooks` 7 (правило `static-components`) и React Compiler (3.18).
- Условие меняет содержимое позиции, а не форму дерева: условные части рендерятся через `&&` или тернарный оператор на постоянной позиции, обёртки не появляются и не исчезают по условию — меняется их стиль.

**Вклад в проект (P3).** Экран урока RN Academy получает постоянную форму дерева; правило «компоненты только на верхнем уровне модуля» записано в правилах проекта и проверяется линтером.
</details>
