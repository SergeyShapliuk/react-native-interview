# 3.7 Когда эффект не нужен — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок строится не вокруг API, а вокруг одного вопроса: **синхронизирует ли этот эффект React с чем-то вне React?** Если нет — эффекта быть не должно.

---

## 1. Что это

Эффект в React — механизм с узким назначением: после commit привести **внешнюю систему** в соответствие с тем, что отрендерил React, и в очистке отменить это соответствие (3.4). Внешняя система — всё, что не знает о React и не обновится само: нативный модуль, подписка на событие ОС, таймер, сетевое соединение, императивный API библиотеки, хранилище.

На практике эффект используют шире — как способ «отреагировать на изменение» чего угодно. Значительная часть таких эффектов не синхронизирует ничего внешнего: они берут одно состояние React и записывают в другое состояние React. Такой эффект — лишний: он добавляет рендер, кадр с рассогласованными данными и место, где логика расходится.

### Ключевая формулировка урока

> **Эффект — это синхронизация React с системой, которая ничего не знает о React. Всё остальное — вычисление при рендере, обработка события или новый экземпляр компонента.**

---

## 2. Как это работает

### Цена лишнего эффекта

Возьмём фильтрацию списка уроков по строке поиска, сделанную через эффект:

```jsx
function LessonSearch({ lessons }) {
  const [query, setQuery] = useState('');
  const [filtered, setFiltered] = useState(lessons);

  useEffect(() => {
    setFiltered(lessons.filter((l) => l.title.includes(query)));
  }, [lessons, query]);
}
```

Что происходит при вводе символа (проверено логированием на React 19.2):

```
render: query = "re", filtered = старый список (4 элемента)   ← commit
эффект: setFiltered(...)
render: query = "re", filtered = новый список (2 элемента)    ← commit
```

Два рендера на каждый символ вместо одного, и между ними — commit, в котором `query` уже новый, а `filtered` ещё старый. Это не теоретическое рассогласование: любой код, читающий оба значения в этом рендере, увидит несогласованную пару. При монтировании — то же: лишний рендер сразу после первого.

Без эффекта:

```jsx
function LessonSearch({ lessons }) {
  const [query, setQuery] = useState('');
  const filtered = lessons.filter((l) => l.title.includes(query));
}
```

Один рендер, и `filtered` всегда соответствует `query` — потому что вычисляется из него в том же вызове функции. Если вычисление дорогое — это повод для `useMemo` (3.11), а не для эффекта.

Линтер 7-й версии ловит прямолинейный случай правилом `set-state-in-effect` (входит в `recommended`): «Calling setState synchronously within an effect can trigger cascading renders».

### Восемь шаблонов

**1. Производное значение.** Значение, которое вычисляется из пропсов и состояния, вычисляется при рендере. Отдельное состояние для него — копия, которая отстаёт на рендер. Примеры: отфильтрованный список, сумма корзины, «форма валидна», полное имя из имени и фамилии, количество непрочитанных.

**2. Сброс всего состояния при смене пропса — `key`.**

```jsx
// было
useEffect(() => { setDraft(''); setErrors({}); }, [lessonId]);

// стало
<LessonNoteForm key={lessonId} lessonId={lessonId} />
```

«Другой урок» — это другой экземпляр формы (3.2). Ключ сбрасывает всё, включая состояние вложенных компонентов, и без кадра, в котором новый урок показан со старым черновиком.

**3. Корректировка части состояния при смене пропса — при рендере.** Если ключ сбрасывает слишком много (тяжёлое поддерево, нужно сохранить часть состояния), React допускает обновление **собственного** состояния прямо при рендере, по условию:

```jsx
function LessonPlayer({ lessonId }) {
  const [position, setPosition] = useState(0);
  const [prevLessonId, setPrevLessonId] = useState(lessonId);

  if (lessonId !== prevLessonId) {
    setPrevLessonId(lessonId);
    setPosition(0);
  }
}
```

React видит обновление во время рендера, выбрасывает текущий результат и сразу вызывает компонент снова, ещё до commit и до рендера детей. Кадра с рассогласованием нет, лишнего commit нет. Эксперимент на React 19.2 показывает два вызова компонента и один commit. Приём рабочий, но читается хуже ключа, поэтому используется, только когда ключ не подходит.

**4. Событие — в обработчике.** То, что произошло из-за действия пользователя, принадлежит обработчику этого действия:

```jsx
// было
useEffect(() => {
  if (status === 'done') api.markCompleted(lessonId);
}, [status]);

// стало
function onFinish() {
  setStatus('done');
  api.markCompleted(lessonId);
}
```

Разница видна, когда то же состояние меняется из другого места. Вариант с эффектом отправит запрос при **любом** переходе в `done`: при восстановлении экрана из хранилища, при получении состояния с сервера, при повторном монтировании. Вопрос, который различает два случая: «это произошло потому, что компонент показан с этими данными, или потому, что пользователь что-то сделал?» Первое — эффект, второе — обработчик.

**5. Цепочки эффектов.**

```jsx
useEffect(() => { if (answer) setScore(score + 1); }, [answer]);
useEffect(() => { if (score >= 10) setLevel(level + 1); }, [score]);
useEffect(() => { if (level > 3) setShowCongrats(true); }, [level]);
```

Каждое звено — отдельный рендер и commit. Изменение `answer` даёт до четырёх рендеров с промежуточными состояниями на экране. Добавление пятого звена или изменение порядка ломает логику, потому что связь между шагами выражена порядком срабатывания, а не кодом. Замена — вычислить всё в обработчике, где произошло событие (или в редьюсере, 3.8), и поставить обновления разом.

**6. «Пропс в стейт».**

```jsx
function LessonTitle({ title }) {
  const [value, setValue] = useState(title);
  useEffect(() => { setValue(title); }, [title]);
}
```

Копия пропса в состоянии, которую эффект подтягивает к оригиналу. Отстаёт на рендер, а если её ещё и редактируют локально — расходится с оригиналом ровно тогда, когда это сложнее всего воспроизвести. Если значение только отображается — используется пропс. Если редактируется — это вопрос «кто владеет значением» (3.15): либо контролируемый компонент, либо локальный черновик, сбрасываемый ключом.

**7. Уведомление родителя.**

```jsx
useEffect(() => { onChange(value); }, [value]);
```

Родитель узнаёт об изменении на рендер позже, а его `setState` в ответ запускает ещё один проход по дереву. Замена — вызвать `onChange` в том же обработчике, где меняется `value`; ещё лучше — поднять состояние в родителя, если оно ему нужно.

**8. Синхронизация с внешней системой — единственное оправданное применение.** Подписка на событие, таймер, императивный API, нативный модуль, соединение. Признак: у эффекта есть осмысленная очистка, которая **отменяет** то, что он сделал во внешнем мире. Эффект без очистки, который только вызывает `setState`, — почти всегда один из шаблонов 1–7.

Запрос данных — тоже синхронизация («данные на экране соответствуют `lessonId`»), но с гонками, отменой и кэшем; это тема блока 07.

### Вопрос для каждого эффекта

```
Что внешнее этот эффект синхронизирует с React?
    ├── ничего, он пишет одно состояние из другого     → вычисление при рендере (1)
    ├── ничего, он сбрасывает состояние при смене пропса → key (2) или корректировка при рендере (3)
    ├── ничего, он реагирует на действие пользователя   → обработчик (4, 5, 7)
    ├── ничего, он копирует пропс                       → использовать пропс или решить, кто владеет (6)
    └── подписку, таймер, нативный API, соединение      → эффект с очисткой (8)
```

## 3. Почему это важно

**Лишний эффект — это лишний рендер и лишний commit.** Каждый `setState` в эффекте — это рендер после commit: ещё один проход по поддереву и ещё один commit. На экране со списком в RN — ещё одна передача Shadow Tree на UI-поток. Это прямая стоимость, которую мемоизация не убирает: рендер вызван не родителем, а самим компонентом.

**Лишний эффект — это кадр с рассогласованными данными.** Между commit с новым исходным значением и commit с обновлённым производным пользователь может увидеть несогласованную пару: строку поиска, не соответствующую списку; новый урок со старым черновиком.

**Лишний эффект прячет причинно-следственную связь.** В обработчике видно: «нажатие → три обновления». В цепочке эффектов связь размазана по коду и выражена порядком срабатывания. Такой код трудно читать, трудно менять и легко сломать добавлением ещё одного эффекта.

**Удаление эффекта решает проблемы зависимостей.** Значительная часть проблем из 3.5 — подавленный линтер, лишние перезапуски, stale closure — относится к эффектам, которых не должно быть. Нет эффекта — нет массива зависимостей.

## 4. Где это в React Native

### Где граница проходит отчётливо

**Настоящие внешние системы — эффект на своём месте:**

- `AppState` — приложение ушло в фон или вернулось;
- `Keyboard` — показ и скрытие клавиатуры, её высота;
- `Dimensions` — изменение размеров окна (хотя для чтения проще `useWindowDimensions`, который сам является такой подпиской);
- `Linking` — входящие ссылки;
- `BackHandler` — аппаратная кнопка «назад» на Android;
- слушатели нативных emitter'ов: загрузка, геолокация, Bluetooth, плеер;
- подписка на состояние сети.

У всех них есть объект подписки и `remove()` — осмысленная очистка, отменяющая то, что сделал эффект.

**Не внешние системы — эффект лишний:**

- фильтрация и сортировка списка по строке поиска или выбранной вкладке;
- пересчёт итоговой суммы, количества, процента прохождения;
- «скопировать `route.params` в состояние экрана» — параметры навигации уже доступны при рендере;
- валидация формы по введённым значениям;
- «при смене урока очистить форму» — ключ.

### `route.params` в состояние

Частный и очень частый RN-случай шаблона 6:

```jsx
function LessonScreen({ route }) {
  const [lessonId, setLessonId] = useState(null);
  useEffect(() => { setLessonId(route.params.lessonId); }, [route.params.lessonId]);
}
```

Первый рендер экрана идёт с `lessonId = null` — пустой экран или спиннер на кадр, хотя идентификатор известен с самого начала. Параметры читаются при рендере: `const { lessonId } = route.params`.

### Эффект, привязанный к монтированию экрана

Из 3.4: экран в стеке остаётся смонтированным. Эффект «при открытии экрана отправить событие» срабатывает при монтировании, а не при каждом показе. Это часто как раз шаблон 4: событие «экран показан» принадлежит навигационному событию фокуса (4.17), а не эффекту.

## 5. Типичные ошибки

**«Эффект нужен, чтобы отреагировать на изменение состояния».** Возникает из модели «эффект = наблюдатель». React уже реагирует на изменение состояния — рендером. Всё, что можно вычислить из нового состояния, вычисляется в этом рендере.

**«Производное состояние кэширует вычисление».** Возникает из желания не считать на каждый рендер. Эффект не кэширует — он пересчитывает на каждое изменение зависимостей, плюс добавляет рендер. Кэширование по зависимостям — это `useMemo` (3.11), и только если вычисление действительно дорогое.

**Действие пользователя в эффекте.** Возникает потому, что «состояние изменилось → нужно что-то сделать» выглядит естественно. Ломается, когда то же состояние приходит из другого источника — восстановление, сервер, повторное монтирование, StrictMode (3.4).

**Цепочка эффектов как «реактивный» поток.** Возникает при постепенном наращивании: к работающему эффекту добавляют ещё один, реагирующий на его результат. Каждое звено по отдельности выглядит разумно.

**«Запрос данных — не синхронизация, значит, эффект не нужен».** Обратная ошибка. Загрузка данных для показанного экрана — синхронизация с сервером, и эффект для неё уместен; проблема не в эффекте, а в гонках, отмене и кэше, которые нужно решать (блок 07). Отказ от эффекта здесь обычно означает перенос загрузки в обработчик, после чего данные не загружаются при восстановлении экрана.

**Сохранение эффекта «на всякий случай» при рефакторинге.** Возникает из осторожности: эффект работал, удалять страшно. Признак лишнего эффекта проверяется вопросом урока, а не опытом «вроде не мешает».

## 6. Trade-offs

### Вычисление при рендере выполняется на каждый рендер

Цена шаблона 1: фильтрация выполняется на каждый рендер компонента, даже если `lessons` и `query` не изменились — например, при рендере родителя. Для списка из сотен элементов это микросекунды, и эффект с лишним рендером обходится дороже. Для действительно дорогого вычисления (тысячи элементов, сложная агрегация) — `useMemo` с теми же зависимостями: результат кэшируется, рендер остаётся один. Это вопрос 3.11, а не повод вернуть эффект.

### Ключ против корректировки при рендере

Ключ прост и надёжен, но пересоздаёт всё поддерево: в RN — нативные view, изображения, позицию прокрутки. Корректировка при рендере сохраняет поддерево и сбрасывает только нужное, но читается хуже и требует хранить «предыдущее значение» в состоянии. Выбор — по стоимости поддерева и по тому, что именно нужно сохранить.

### Обработчик против эффекта для событий

Перенос действия в обработчик делает поведение точным («отправляем, когда пользователь нажал»), но требует, чтобы все пути к этому действию проходили через обработчик. Если состояние может стать `done` десятью способами, и в каждом нужно действие, — это повод собрать переходы в одном месте (редьюсер, 3.8, или доменная функция), а не вернуть эффект.

## 7. Связи с другими частями системы

**Опирается на:**

- **3.2 Роль `key`** — ключ как способ сказать «другой экземпляр»;
- **3.3 Путь обновления** — `setState` в эффекте — это новый рендер после commit; `setState` при рендере — повтор до commit;
- **3.4 Lifecycle и StrictMode** — эффект и очистка — пара для внешней системы; StrictMode вскрывает эффекты, которые «делают действие»;
- **3.5 Правила хуков и зависимостей** — удалённый эффект не имеет массива зависимостей, который можно сломать.

**Готовит:**

- **3.11 Мемоизация** — `useMemo` для дорогого производного значения вместо эффекта;
- **3.12 Кастомные хуки** — хук-обёртка над внешней системой как правильная упаковка оставшихся эффектов;
- **4.17 Navigation lifecycle** — события фокуса вместо эффектов «при открытии экрана»;
- **6.1 Что считать состоянием** — производное значение не является состоянием;
- **07 Networking** — запрос как синхронизация, с гонками и отменой;
- **5.8 Утечки** — эффекты, которые остаются, обязаны иметь очистку.

**Цепочка, которую этот урок открывает:**

```
3.4 эффект и очистка — пара для внешней системы
    ↓
3.7 если внешней системы нет — эффекта нет
    ↓
3.11 дорогое вычисление при рендере  ·  6.1 что считать состоянием  ·  07 запросы как синхронизация
```

> **Не дублировать:** мемоизация дорогого производного значения — 3.11; запросы, гонки, отмена — блок 07; утечки — 5.8; что считать состоянием — 6.1.
