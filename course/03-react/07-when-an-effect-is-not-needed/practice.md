# 3.7 Когда эффект не нужен — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ начинается с вопроса урока: **что внешнее этот эффект синхронизирует с React?**

---

**1. `const [filtered, setFiltered] = useState(lessons)` плюс эффект на `[lessons, query]`, вызывающий `setFiltered`. Сколько рендеров на один введённый символ, и что показывает экран между ними?**

<details>
<summary>Ответ</summary>

Два рендера и два commit.

1. `setQuery` в обработчике ввода → рендер с новым `query` и **старым** `filtered` → commit;
2. эффект видит изменившийся `query`, вызывает `setFiltered` → рендер с согласованной парой → commit.

Между ними — commit, в котором строка поиска уже новая, а список ещё старый. Пользователь может увидеть этот кадр; любой код, читающий `query` и `filtered` вместе в первом рендере, получит несогласованную пару. Это проверено логированием на React 19.2. При монтировании — то же: лишний рендер сразу после первого.

Исправление — вычислить при рендере: `const filtered = lessons.filter(...)`. Один рендер, `filtered` всегда соответствует `query`. Если фильтрация дорогая — `useMemo` с теми же зависимостями (3.11).

**Ответ «один, React батчит обновления»** вскрывает смешение: батчинг объединяет обновления **одной задачи**. Обновление из эффекта ставится после commit первого рендера — это следующий рендер.

**Ответ «эффект кэширует фильтрацию, поэтому быстрее»** вскрывает модель «производное состояние = кэш». Эффект пересчитывает на каждое изменение и добавляет рендер.
</details>

---

**2. Форму заметки нужно очищать при смене `lessonId`. Сравните три способа: эффект, `key`, корректировку при рендере. Когда какой?**

<details>
<summary>Ответ</summary>

**Эффект** (`useEffect(() => { setDraft(''); setErrors({}); }, [lessonId])`) — худший вариант. Первый рендер после смены урока показывает новый урок со старым черновиком; сброс приходит вторым рендером. Сбрасывается только перечисленное: новое поле, добавленное позже, «перетечёт» между уроками. Состояние вложенных компонентов не сбрасывается вообще.

**`key={lessonId}`** — вариант по умолчанию. Новый экземпляр формы: всё состояние, включая вложенные компоненты, начинается заново; кадра со старым черновиком нет. Цена — полное перемонтирование поддерева.

**Корректировка при рендере** — когда ключ сбрасывает слишком много:

```jsx
const [prevLessonId, setPrevLessonId] = useState(lessonId);
if (lessonId !== prevLessonId) {
  setPrevLessonId(lessonId);
  setDraft('');
}
```

React выбрасывает результат текущего вызова и вызывает компонент снова, до commit — кадра с рассогласованием нет. Подходит, если в форме есть тяжёлая часть, которую не нужно пересоздавать (например, превью видео урока), или часть состояния должна пережить смену урока (выбранный режим редактора).

**Ответ «эффект — это нормально, так все делают»** не отвечает на вопрос урока: эффект ничего внешнего не синхронизирует.

**Ответ «`setState` при рендере запрещён»** верен для безусловного обновления и для обновления **чужого** состояния. Условное обновление собственного состояния — документированный приём.
</details>

**3. POST «урок пройден» отправляется эффектом при `status === 'done'`. Что сломается при восстановлении состояния экрана из хранилища?**

<details>
<summary>Ответ</summary>

Эффект не знает, **почему** `status` стал `done`. Он срабатывает при любом рендере, в котором `status === 'done'` после изменения или при монтировании:

- экран восстановлен из персистентного состояния с уже пройденным уроком — POST уходит повторно;
- состояние пришло с сервера (урок пройден на другом устройстве) — POST уходит обратно на сервер;
- экран перемонтирован (смена ключа, возврат после размонтирования) — повторный POST;
- в dev со StrictMode — два POST при монтировании.

Сервер может быть идемпотентным и пережить это, но аналитика, начисление баллов или уведомления — нет.

Событие «пользователь прошёл урок» происходит в обработчике действия пользователя — там POST и должен отправляться. Если путей к завершению несколько, их объединяют в одной функции или в редьюсере (3.8), а не возвращают эффект.

**Ответ «добавить флаг `sent` в ref»** вскрывает лечение симптома: флаг не переживает перемонтирование и не различает «пройден сейчас» и «был пройден раньше».

**Ответ «проверять в эффекте предыдущее значение `status`»** — уже лучше, но это попытка восстановить в эффекте информацию, которая была в обработчике бесплатно.
</details>

**4. Какие из этих эффектов в RN-экране оправданы? Для неоправданных назвать замену.**

```jsx
// A
useEffect(() => {
  const sub = Keyboard.addListener('keyboardDidShow', (e) => setKbHeight(e.endCoordinates.height));
  return () => sub.remove();
}, []);

// B
useEffect(() => { setLessonId(route.params.lessonId); }, [route.params.lessonId]);

// C
useEffect(() => { setProgress(completed.length / lessons.length); }, [completed, lessons]);

// D
useEffect(() => {
  const id = setInterval(() => setElapsed((s) => s + 1), 1000);
  return () => clearInterval(id);
}, []);

// E
useEffect(() => { onProgressChange(progress); }, [progress]);
```

<details>
<summary>Ответ</summary>

- **A — оправдан.** `Keyboard` — внешняя система; подписка с осмысленной очисткой.
- **B — лишний.** «Пропс в стейт»: параметры навигации доступны при рендере. Замена — `const { lessonId } = route.params`. Сейчас первый рендер экрана идёт с `lessonId = null`.
- **C — лишний.** Производное значение. Замена — `const progress = completed.length / lessons.length` при рендере.
- **D — оправдан.** Таймер — внешняя система, очистка снимает его. Функциональное обновление делает `[]` честным (3.5).
- **E — лишний.** Уведомление родителя. Замена — вызвать `onProgressChange` там, где меняется то, из чего вычисляется прогресс (обработчик завершения урока), или поднять состояние в родителя. После того как C стал вычислением, E уже некуда цепляться: `progress` не состояние.

Признак, который работает на всех пяти: у A и D есть очистка, отменяющая действие во внешнем мире; у B, C и E очистки нет и быть не может — они только пишут одно состояние React из другого.

**Ответ «D лишний, таймер можно сделать иначе»** — таймер действительно можно вынести в хук, но он остаётся эффектом: `setInterval` — внешняя по отношению к React система.
</details>

## Задание — экран с пятью эффектами

**Дано.** Экран прохождения теста к уроку в RN Academy.

```jsx
function QuizScreen({ route, onFinished }) {
  const [quizId, setQuizId] = useState(null);
  const [answers, setAnswers] = useState({});
  const [score, setScore] = useState(0);
  const [passed, setPassed] = useState(false);
  const [isBackground, setIsBackground] = useState(false);
  const quiz = useQuiz(quizId);   // загружает тест по id

  // 1
  useEffect(() => {
    setQuizId(route.params.quizId);
  }, [route.params.quizId]);

  // 2
  useEffect(() => {
    if (!quiz) return;
    setScore(quiz.questions.filter((q) => answers[q.id] === q.correct).length);
  }, [answers, quiz]);

  // 3
  useEffect(() => {
    if (quiz) setPassed(score >= quiz.passScore);
  }, [score, quiz]);

  // 4
  useEffect(() => {
    if (passed) {
      api.submitQuiz(quizId, answers);
      onFinished(quizId);
    }
  }, [passed]);

  // 5
  useEffect(() => {
    const sub = AppState.addEventListener('change', (s) => setIsBackground(s !== 'active'));
    return () => sub.remove();
  }, []);

  function answer(questionId, value) {
    setAnswers((prev) => ({ ...prev, [questionId]: value }));
  }

  // ...
}
```

**Требуется.**

1. Для каждого эффекта ответить на вопрос урока и назвать шаблон.
2. Удалить эффекты, которые не синхронизируют ничего внешнего, и для каждого назвать замену: вычисление при рендере, `key`, обработчик события или ничего.
3. Посчитать, сколько рендеров давал исходный код на один ответ, который делает тест пройденным, и сколько — исправленный.
4. Найти дефект поведения (не производительности), который исходный код имел из-за эффектов и который исчез после исправления.

---

<details>
<summary>Разбор</summary>

**1. Эффект за эффектом.**

1. Ничего внешнего — копирует `route.params` в состояние (шаблон 6, «пропс в стейт»).
2. Ничего внешнего — производное значение (шаблон 1).
3. Ничего внешнего — производное значение, и вместе со вторым образует цепочку (шаблоны 1 и 5).
4. Ничего внешнего не **синхронизирует** — реагирует на состояние действием: отправка ответов и уведомление родителя (шаблоны 4 и 7).
5. `AppState` — внешняя система, подписка с очисткой (шаблон 8). Оправдан.

**2. Исправление.**

```jsx
function QuizScreen({ route, onFinished }) {
  const { quizId } = route.params;              // было: эффект 1
  const [answers, setAnswers] = useState({});
  const [isBackground, setIsBackground] = useState(false);
  const quiz = useQuiz(quizId);

  // было: эффекты 2 и 3 — вычисление при рендере
  const score = quiz
    ? quiz.questions.filter((q) => answers[q.id] === q.correct).length
    : 0;
  const passed = quiz ? score >= quiz.passScore : false;

  // эффект 5 остаётся: синхронизация с AppState
  useEffect(() => {
    const sub = AppState.addEventListener('change', (s) => setIsBackground(s !== 'active'));
    return () => sub.remove();
  }, []);

  // было: эффект 4 — обработчик события
  function answer(questionId, value) {
    const next = { ...answers, [questionId]: value };
    setAnswers(next);
    const nextScore = quiz.questions.filter((q) => next[q.id] === q.correct).length;
    if (!passed && nextScore >= quiz.passScore) {
      api.submitQuiz(quizId, next);
      onFinished(quizId);
    }
  }
}
```

Замены:

| Эффект | Замена |
|---|---|
| 1 | чтение `route.params` при рендере |
| 2 | вычисление при рендере |
| 3 | вычисление при рендере |
| 4 | обработчик `answer` — событие «пользователь ответил так, что тест пройден» |
| 5 | остаётся |

Вычисление `nextScore` в обработчике дублирует формулу рендера — её стоит вынести в чистую функцию домена `scoreOf(quiz, answers)` и вызывать в обоих местах. Это заодно делает её тестируемой без рендера. Если путей к прохождению станет больше (таймаут, пропуск вопроса), переходы собираются в редьюсер (3.8).

Если экран может получить другой `quizId` без размонтирования (переход с теста на тест через `navigation.setParams`), ответы предыдущего теста нужно сбросить. Это не повод вернуть эффект: `key={quizId}` на содержимом экрана или корректировка при рендере (шаблоны 2 и 3).

**3. Число рендеров на решающий ответ.**

Исходный код: `setAnswers` → рендер №1 (`answers` новые, `score` старый) → эффект 2 → `setScore` → рендер №2 (`score` новый, `passed` старый) → эффект 3 → `setPassed` → рендер №3 → эффект 4 → `onFinished` в родителе → его рендер. **Три рендера экрана** с двумя кадрами рассогласования плюс рендер родителя, вызванный из эффекта. При монтировании — ещё два лишних: эффект 1 и цепочка от загрузки `quiz`.

Исправленный: `setAnswers` и `onFinished` в одном обработчике — **один рендер** экрана, рендер родителя попадает в тот же батч (3.3).

**4. Дефект поведения.**

Эффект 4 зависел только от `passed` и читал `quizId` и `answers` из замыкания, с подавленной по сути зависимостью. Но главное — он срабатывал при **любом** переходе `passed` в `true`, а не при ответе пользователя. Сценарии:

- пользователь прошёл тест, изменил уже засчитанный ответ на неверный (`passed` → `false`), затем обратно на верный — `submitQuiz` и `onFinished` вызываются **второй раз**;
- если ответы восстанавливаются из черновика (а это следующая задача в бэклоге), экран при монтировании сразу получает `passed = true` и отправляет тест без действия пользователя.

В исправленном коде отправка происходит только в обработчике ответа и только при переходе из «не пройден» в «пройден»: условие `!passed && nextScore >= quiz.passScore` проверяет именно переход.

**Вклад в проект (P3).** Эффекты слоя P3 RN Academy пересмотрены по вопросу урока; у каждого оставшегося эффекта в комментарии названа внешняя система, с которой он синхронизирует. Формула прохождения теста вынесена в домен как чистая функция с unit-тестом.
</details>
