# 3.9 Refs: `useRef`, ref как пропс, `useImperativeHandle` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Ось урока — **почему изменение `ref.current` не вызывает рендер**, и что из этого следует: когда ref правильный инструмент, а когда он ломает согласованность экрана.

---

## 1. Что это

**`useRef(initial)`** возвращает объект `{ current: initial }`, который React хранит на fiber и отдаёт **тот же самый объект** при каждом рендере компонента. Поле `current` можно читать и менять как угодно.

**Ref на узел** — тот же объект, переданный в пропс `ref` host-компонента (`<View ref={viewRef} />`). React записывает в `current` ссылку на узел при commit и `null` — при размонтировании.

**`useImperativeHandle(ref, create, deps)`** — способ отдать через ref не узел, а объект, который создаёт сам компонент: узкий набор методов.

### Ключевая формулировка урока

> **Ref — это ячейка, живущая между рендерами, о которой React ничего не знает. Изменение ячейки не ставит обновление в очередь, поэтому то, что влияет на экран, в ref не хранится.**

---

## 2. Как это работает

### Почему запись в ref не вызывает рендер

Сравним два хука, хранящих значение между рендерами:

| | `useState` | `useRef` |
|---|---|---|
| где хранится | на fiber | на fiber |
| как меняется | `setState` → обновление в очередь (3.3) | присваивание `ref.current = x` |
| знает ли React об изменении | да — планирует рендер | нет |
| когда новое значение видно | в следующем рендере | сразу, в любом коде, читающем `current` |

`ref.current = x` — обычное присваивание поля объекта. Оно не проходит через очередь обновлений, поэтому React не знает, что что-то изменилось, и не планирует работу. В этом весь смысл ref: значение живёт между рендерами, но его изменение рендера не стоит.

Это же определяет границу применения. Если значение влияет на то, что видно на экране, хранить его в ref — значит гарантировать, что экран с ним разойдётся: значение изменилось, а рендера, который бы это показал, не было.

### Первое законное применение: значение, не влияющее на разметку

То, что нужно помнить между рендерами, но что не отображается:

- **идентификатор таймера или подписки** — чтобы отменить его из обработчика:

  ```jsx
  const timerRef = useRef(null);
  function startAutoplay() {
    timerRef.current = setInterval(next, 5000);
  }
  function stopAutoplay() {
    clearInterval(timerRef.current);
  }
  ```

- **флаг «запрос устарел»** или `AbortController` текущего запроса;
- **предыдущее значение пропса** для сравнения в эффекте;
- **актуальное значение для долгоживущего колбэка** — продолжение 1.14: слушатель создан один раз, но должен видеть последние пропсы. В React 19.2 для колбэков из эффектов эту задачу решает `useEffectEvent` (3.5); ref остаётся для колбэков, которые передаются наружу или вызываются не из эффекта;
- **экземпляр императивного объекта** — плеер, анимация, клиент:

  ```jsx
  const playerRef = useRef(null);
  if (playerRef.current === null) {
    playerRef.current = createPlayer();   // ленивая инициализация — единственное
  }                                       // допустимое обращение к ref при рендере
  ```

### Не читать и не писать ref при рендере

Рендер должен быть чистым (3.1, 3.3): функция компонента может быть вызвана несколько раз и результат может быть выброшен. Запись в ref при рендере — побочный эффект: в StrictMode ref-объект один на оба вызова, и `renders.current++` на первом рендере даёт `2` (проверено на React 19.2, 3.4). Чтение ref при рендере делает результат зависимым от значения, изменение которого рендера не вызывает: разметка покажет то, что было в ref на момент **последнего** рендера, а не текущее значение.

Правило `react-hooks/refs` в `eslint-plugin-react-hooks` 7 отмечает оба случая ошибкой «Cannot access refs during render». Ленивая инициализация по шаблону `if (ref.current === null) ref.current = ...` правилом разрешена.

Где читать и писать: в обработчиках событий и в эффектах.

### Второе законное применение: доступ к узлу

```jsx
const inputRef = useRef(null);
// ...
<TextInput ref={inputRef} />
<Button title="Написать заметку" onPress={() => inputRef.current?.focus()} />
```

Когда ref заполняется:

- **при рендере** — `inputRef.current === null`: узла ещё нет, commit не произошёл (3.4);
- **в commit**, на шаге мутаций — React записывает узел в `current`;
- **к layout-эффектам** — ref уже заполнен; здесь можно измерять (3.6);
- **при размонтировании** — React записывает `null`.

Ref указывает на **host-узел**. Методы измерения и императивные методы есть только у host-компонентов (`View`, `TextInput`, `ScrollView`). Ref на собственный функциональный компонент ничего не даст, пока компонент сам не решит, что отдать.

### Пропуск ref через свой компонент

**React 19 (RN 0.78 и новее)** — `ref` является обычным пропсом функционального компонента:

```jsx
function NoteInput({ ref, ...props }) {
  return <TextInput ref={ref} {...props} />;
}
```

**React 18 и старше** — `ref` не доходил до компонента как пропс, и для пропуска нужен был `forwardRef`:

```jsx
const NoteInput = forwardRef(function NoteInput(props, ref) {
  return <TextInput ref={ref} {...props} />;
});
```

В React 19 `forwardRef` работает, но для нового кода не нужен; в существующих кодовых базах и библиотеках он будет встречаться ещё долго. Типизация обоих вариантов — 2.14.

### Ref-колбэк и его очистка

Вместо объекта в `ref` можно передать функцию. React вызовет её с узлом при commit. В React 19 функция может вернуть очистку — она будет вызвана, когда узел уходит или колбэк меняется:

```jsx
<View
  ref={(node) => {
    const sub = visibility.observe(node, onVisible);
    return () => sub.unobserve();
  }}
/>
```

Ref-колбэк, созданный при рендере, — новая функция на каждый рендер, и React будет вызывать очистку и колбэк заново после каждого commit. Если это дорого, колбэк стабилизируется `useCallback` (3.11). В StrictMode React 19 вызывает цикл «колбэк → очистка → колбэк» при монтировании так же, как для эффектов (3.4).

### `useImperativeHandle`: узкий контракт вместо узла

Компонент плеера внутри использует нативный плеер, но наружу хочет отдать только три метода:

```jsx
function VideoPlayer({ ref, uri }) {
  const nativeRef = useRef(null);

  useImperativeHandle(ref, () => ({
    play: () => nativeRef.current?.play(),
    pause: () => nativeRef.current?.pause(),
    seek: (sec) => nativeRef.current?.seekTo(sec),
  }), []);

  return <NativeVideo ref={nativeRef} source={{ uri }} />;
}
```

Вызывающий получает в `ref.current` объект с тремя методами — не нативный узел. Внутренний `nativeRef` остаётся деталью реализации: замена библиотеки плеера не затронет вызывающих, пока три метода работают. Объект handle создаётся при commit и пересоздаётся при изменении зависимостей — по тем же правилам, что эффект (3.5).

## 3. Почему это важно

**Ref — единственный способ хранить изменяемое значение между рендерами без рендера.** Без него таймеры, подписки, отмена запросов и императивные объекты превращаются либо в состояние (лишние рендеры на каждое изменение), либо в переменные модуля (общие для всех экземпляров компонента — ошибка, которую трудно заметить, пока экземпляр один).

**Ref вместо состояния — источник рассинхронизации.** Значение в ref изменилось, рендера не было — экран показывает старое. Следующий рендер по другой причине внезапно покажет новое. Дефект выглядит как «обновляется не сразу, а при следующем действии».

**Императивный доступ к узлу — неизбежная часть работы с платформой.** Фокус, прокрутка, измерение, воспроизведение не выражаются пропсами без потерь: «сфокусироваться сейчас» — событие, а не состояние. Ref — граница, через которую декларативный React вызывает императивную платформу.

**Handle — это публичный API компонента.** То, что компонент отдаёт через ref, использует вызывающий код; изменение handle ломает вызывающих так же, как изменение пропсов. Узкий handle — меньше обязательств.

## 4. Где это в React Native

Здесь ref перестаёт быть темой «про DOM» — для RN-разработчика это ежедневная работа.

**Измерения.** `measure`, `measureInWindow` на ref host-компонента; с RN 0.82 нативные компоненты отдают через ref DOM-подобные узлы с подмножеством DOM API — `getBoundingClientRect()`, `parentNode`, `children` и другие. Место измерения — `useLayoutEffect` (3.6).

**Прокрутка.** `scrollTo`, `scrollToEnd` у `ScrollView`; `scrollToIndex`, `scrollToOffset` у `FlatList`. «Прокрутить к текущему уроку» — событие, а не состояние; `scrollToIndex` к тому же требует знать размеры элементов (`getItemLayout`, 5.4).

**Фокус.** `focus`, `blur`, `clear`, `isFocused` у `TextInput`. Переход фокуса на следующее поле формы по `onSubmitEditing` — классический ref.

**Animated ref.** В Reanimated `useAnimatedRef` даёт ref, с которым работают worklets на UI-потоке — например, `scrollTo` из worklet без возврата в JS (5.7).

**Нативный компонент, у которого метод есть, а пропса нет.** Видео (`seek`), карта (`animateToRegion`), камера (`takePicture`) — команды нативному view. Такие методы в Fabric описываются как команды компонента (09), а из JS вызываются через ref.

**`setNativeProps`** — способ менять пропсы нативного view через ref в обход рендера. В старом коде встречается для анимаций и полей ввода; документация RN 0.87 держит его в разделе Legacy Architecture. Для нового кода правильный путь — состояние, Animated или Reanimated: изменение в обход рендера расходится с тем, что React считает текущими пропсами, и следующий рендер его перезапишет.

## 5. Типичные ошибки

**Ref как «состояние без лишних рендеров».** Возникает из желания оптимизировать: «счётчик меняется часто, пусть не рендерит». Если значение видно на экране, экран с ним разойдётся. Если не видно — это действительно ref, но тогда вопрос был не в оптимизации.

**`ref.current` в массиве зависимостей.** Возникает из желания сделать эффект реактивным к ref. Массив сравнивается только при рендере, а изменение `ref.current` рендера не вызывает: эффект не узнает об изменении, пока рендер не случится по другой причине. Линтер: «Mutable values like 'r.current' aren't valid dependencies because mutating them doesn't re-render the component». Если нужно узнать, когда узел появился, — ref-колбэк.

**Обращение к ref узла при рендере.** Возникает из модели «узел существует, пока компонент на экране». При первом рендере узла нет — commit ещё не был. Измерения и вызовы — в эффекте или обработчике.

**«`forwardRef` обязателен для передачи ref».** Возникает из опыта React 18. В React 19 `ref` — обычный пропс; `forwardRef` нужен только для совместимости.

**«Ref на компонент даёт доступ к его состоянию».** Возникает из модели классовых компонентов, где ref давал экземпляр со всеми полями. У функционального компонента экземпляра нет; ref даёт только то, что компонент отдал явно — узел или handle.

**Отдать наружу весь внутренний узел.** Возникает из простоты: пробросить `ref` до внутреннего `TextInput`. Вызывающий получает все методы узла и начинает ими пользоваться; замена внутреннего компонента ломает вызывающих. Если наружу нужно два метода — `useImperativeHandle`.

**Модульная переменная вместо ref.** `let timer;` на уровне модуля вместо `useRef`. Возникает, когда компонент пока используется в одном экземпляре. Второй экземпляр на экране перезапишет таймер первого.

## 6. Trade-offs

### Актуальное значение против согласованного снимка

Тот же выбор, что в 1.14 и 3.5. Замыкание даёт согласованный снимок: обработчик работает с данными того рендера, который видел пользователь. Ref даёт актуальное значение на момент вызова: долгоживущий слушатель видит последние пропсы. Цена ref — два чтения `current` в одной функции могут дать разные значения, если между ними `await`. Это не упрощение, а другой контракт, и выбирать его стоит только там, где актуальность важнее согласованности.

### Императивный handle против декларативных пропсов

`ref.current.play()` против `<Player playing={isPlaying} />`. Декларативный вариант проще тестировать и отлаживать: состояние видно, его можно сохранить и восстановить. Императивный точнее выражает события («перемотать на 30 секунд», «сфокусироваться сейчас»), которые плохо ложатся на состояние. Хорошее правило: состояние, которое должно пережить перемонтирование или быть видно другим компонентам, — пропсом; одноразовое действие — методом handle.

### Узкий handle против полного узла

Полный узел ничего не стоит при написании и дорого стоит при изменении: любой метод, однажды использованный снаружи, становится частью контракта. Узкий handle требует написать обёртку и решить, что отдавать, — и оставляет свободу менять реализацию.
