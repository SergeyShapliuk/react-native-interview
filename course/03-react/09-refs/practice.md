# 3.9 Refs — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **проходит ли изменение через очередь обновлений** и что из этого видит экран.

---

**1. Счётчик нажатий хранится в `useRef` и выводится в `<Text>`. Что увидит пользователь?**

```jsx
function LikeButton() {
  const likes = useRef(0);
  return (
    <Pressable onPress={() => { likes.current += 1; }}>
      <Text>{likes.current}</Text>
    </Pressable>
  );
}
```

<details>
<summary>Ответ</summary>

Пользователь будет видеть `0`, сколько бы ни нажимал. `likes.current += 1` — присваивание поля объекта, которое не проходит через очередь обновлений (3.3): React не знает об изменении и не планирует рендер. `<Text>` показывает значение на момент последнего рендера.

Хуже того: как только компонент отрендерится по другой причине (рендер родителя, смена темы), на экране внезапно появится накопленное число — например, `7`. Дефект выглядит как «обновляется не сразу, а при каком-то другом действии», и связь с ref неочевидна.

Линтер 7-й версии ловит это статически — чтение `likes.current` при рендере: «Cannot access refs during render».

Исправление — `useState`: значение влияет на экран, значит, это состояние.

**Ответ «увидит 1, 2, 3 — ref же меняется»** вскрывает модель «React следит за значениями». React узнаёт об изменениях только через `setState`, `dispatch` и контекст.

**Ответ «ref лучше, потому что не вызывает лишних рендеров»** — рендер здесь не лишний: экран обязан показать новое число.
</details>

---

**2. Почему эффект с `[ref.current]` в зависимостях не срабатывает, когда ref меняется?**

<details>
<summary>Ответ</summary>

Массив зависимостей сравнивается **только при рендере**: после каждого рендера React сравнивает новые значения с прошлыми (3.5). Изменение `ref.current` рендера не вызывает, поэтому сравнения не происходит — эффект не узнает об изменении, пока компонент не отрендерится по другой причине. Тогда он сработает, но с опозданием и по случайному поводу.

Отдельно: значение `ref.current` попадает в массив в момент рендера, когда ref на узел ещё не заполнен (заполнение — в commit, 3.4). Эффект с `[nodeRef.current]` на первом рендере видит `null` в массиве.

Линтер предупреждает: «Mutable values like 'r.current' aren't valid dependencies because mutating them doesn't re-render the component».

Что делать в зависимости от задачи:

- нужно узнать, когда узел появился или сменился, — ref-колбэк (`ref={(node) => {...}}`), в React 19 с очисткой;
- значение должно вызывать реакцию — значит, это состояние, а не ref.

**Ответ «ref нужно обернуть в `useMemo`»** вскрывает поиск способа сделать ref реактивным, когда нужно другое средство.
</details>

---

**3. Компонент плеера отдаёт наружу ref на внутренний нативный узел видео. Почему лучше отдать handle из трёх методов, и что изменится для вызывающих при замене библиотеки плеера?**

<details>
<summary>Ответ</summary>

Ref на внутренний узел делает **весь** API нативного компонента частью публичного контракта плеера. Вызывающие начинают использовать то, что нашли: `seekTo`, `presentFullscreenPlayer`, специфичные для библиотеки методы, а иногда и поля. Замена библиотеки ломает каждое такое место — и найти их можно только поиском по коду.

Handle через `useImperativeHandle`:

```jsx
useImperativeHandle(ref, () => ({
  play: () => nativeRef.current?.play(),
  pause: () => nativeRef.current?.pause(),
  seek: (sec) => nativeRef.current?.seekTo(sec),
}), []);
```

фиксирует контракт: три метода, именованные в терминах предметной области. Замена библиотеки меняет три строки внутри плеера; вызывающие не меняются. Тип handle объявляется отдельно и экспортируется (2.14) — это документ контракта.

Цена: handle нужно написать и поддерживать, и каждая новая потребность вызывающих — это решение о расширении контракта. Для плеера, используемого в десятке экранов, это выгодно; для одноразовой обёртки над `TextInput`, которую использует одна форма, пробросить ref проще и честнее.

**Ответ «ref на узел удобнее, можно вызвать что угодно»** — именно это «что угодно» и становится проблемой.
</details>

---

**4. Обработчик `onPress` запускает автопрокрутку карусели уроков через `setInterval`. Где хранить идентификатор интервала — в состоянии, в ref или в переменной модуля?**

<details>
<summary>Ответ</summary>

В ref.

- **Состояние** — идентификатор не отображается, а `setState` вызвал бы рендер ради значения, которого никто не видит. К тому же в обработчике «стоп» значение из замыкания может оказаться устаревшим.
- **Переменная модуля** (`let timer;`) — общая для всех экземпляров компонента. Две карусели на экране перезапишут таймер друг друга: остановка одной остановит другую, а первый таймер останется без ссылки и будет работать до конца сессии.
- **Ref** — своё значение у каждого экземпляра, изменение не вызывает рендера, обработчики читают актуальное значение.

```jsx
const timerRef = useRef(null);

function startAutoplay() {
  clearInterval(timerRef.current);
  timerRef.current = setInterval(next, 5000);
}

useEffect(() => () => clearInterval(timerRef.current), []);   // остановить при размонтировании
```

Очистка в эффекте — обязательная часть: интервал — внешняя система, и при размонтировании он должен быть снят (3.4, 3.7).

**Ответ «в состоянии, так правильнее в React»** вскрывает правило «всё в состоянии» без критерия. Критерий урока: влияет ли значение на разметку.
</details>

## Задание — экран урока с тремя императивными действиями

**Дано.** Экран урока RN Academy:

- кнопка «Добавить заметку» должна поставить фокус в поле заметки внизу экрана;
- при открытии экрана список уроков в боковой панели прокручивается к текущему уроку;
- плеер урока управляется кнопками экрана: «Пауза» и «−10 секунд».

Текущая реализация:

```jsx
function LessonScreen({ lessons, currentIndex, uri }) {
  const [shouldFocus, setShouldFocus] = useState(false);
  const [playing, setPlaying] = useState(true);
  const [seekTo, setSeekTo] = useState(null);
  const listRef = useRef(null);

  if (listRef.current) {
    listRef.current.scrollToIndex({ index: currentIndex });
  }

  return (
    <>
      <FlatList ref={listRef} data={lessons} /* ... */ />
      <Player uri={uri} playing={playing} seekTo={seekTo} />
      <Button title="Пауза" onPress={() => setPlaying(false)} />
      <Button title="−10 с" onPress={() => setSeekTo(Date.now())} />
      <Button title="Добавить заметку" onPress={() => setShouldFocus(true)} />
      <NoteInput autoFocus={shouldFocus} />
    </>
  );
}
```

**Требуется.**

1. Найти, что в этом коде не работает или работает случайно, и объяснить через механизм ref и рендера.
2. Переписать три действия. Для каждого объяснить, почему выбран ref (или почему оставлено состояние).
3. Описать императивный контракт `Player` и решить, какие из его возможностей остаются пропсами.

---

<details>
<summary>Разбор</summary>

**1. Что не так.**

*Прокрутка при рендере.* `listRef.current.scrollToIndex` вызывается в теле компонента. При первом рендере `listRef.current === null` — commit ещё не был, прокрутки нет. При следующих рендерах прокрутка вызывается **на каждый** рендер, например при каждой паузе плеера, — список дёргается к текущему уроку, даже если пользователь его прокрутил. Плюс это побочный эффект при рендере, который в StrictMode выполнится дважды. Линтер: «Cannot access refs during render».

*Фокус через `autoFocus`.* `autoFocus` действует при монтировании поля. Поле уже смонтировано с `autoFocus={false}`; смена пропса на `true` фокус не ставит. Если бы и ставила — второе нажатие ничего не изменит: `shouldFocus` уже `true`, обновление отброшено (3.3).

*Перемотка через состояние-метку.* `seekTo={Date.now()}` — попытка выразить **событие** «перемотай сейчас» через состояние. `Player` должен сравнивать метки в эффекте и вычислять, что делать; смысл действия («−10 секунд») потерян в пути — `Player` получает время нажатия, а не величину перемотки. При перемонтировании плеера с сохранённым `seekTo` он может перемотать повторно.

**2. Переписывание.**

```jsx
function LessonScreen({ lessons, currentIndex, uri }) {
  const listRef = useRef(null);
  const noteRef = useRef(null);
  const playerRef = useRef(null);
  const [playing, setPlaying] = useState(true);

  useEffect(() => {
    listRef.current?.scrollToIndex({ index: currentIndex, animated: false });
  }, [currentIndex]);

  return (
    <>
      <FlatList ref={listRef} data={lessons} getItemLayout={getLessonItemLayout} /* ... */ />
      <Player ref={playerRef} uri={uri} playing={playing} onPlayingChange={setPlaying} />
      <Button title={playing ? 'Пауза' : 'Играть'} onPress={() => setPlaying((p) => !p)} />
      <Button title="−10 с" onPress={() => playerRef.current?.seekBy(-10)} />
      <Button title="Добавить заметку" onPress={() => noteRef.current?.focus()} />
      <NoteInput ref={noteRef} />
    </>
  );
}
```

- **Прокрутка** — ref списка, вызов в эффекте с зависимостью `currentIndex`: «список прокручен к текущему уроку» синхронизируется при открытии и при смене урока, а не при каждом рендере. `getItemLayout` нужен `scrollToIndex`, чтобы прокрутить к ещё не отрендеренному элементу (5.4).
- **Фокус** — ref на поле, вызов `focus()` в обработчике. Фокус — событие, а не состояние: «сфокусироваться сейчас» при каждом нажатии. `NoteInput` в React 19 принимает `ref` как пропс и передаёт его в `TextInput`.
- **Перемотка** — метод handle плеера в обработчике. Событие с параметром (`-10`) выражается вызовом напрямую.

**3. Контракт `Player`.**

```ts
type PlayerHandle = {
  seekBy(sec: number): void;
  seekTo(sec: number): void;
};
```

```jsx
function Player({ ref, uri, playing, onPlayingChange }) {
  const nativeRef = useRef(null);
  useImperativeHandle(ref, () => ({
    seekBy: (sec) => nativeRef.current?.seekBy(sec),
    seekTo: (sec) => nativeRef.current?.seekTo(sec),
  }), []);
  return <NativeVideo ref={nativeRef} source={{ uri }} paused={!playing} onPlaybackStateChange={(s) => onPlayingChange(s === 'playing')} />;
}
```

Что осталось пропсом: **`playing`**. Воспроизведение или пауза — состояние: оно должно отображаться (иконка кнопки), переживать перемонтирование плеера и быть доступным другим частям экрана (например, приглушить фоновую музыку). Плеер сообщает о внешних изменениях (пауза из системных контролов, конец ролика) через `onPlayingChange`, и состояние экрана остаётся источником истины.

Что стало методом handle: **перемотка**. Это одноразовое действие с параметром; выражение через состояние потребовало бы меток времени и сравнения в эффекте.

Внутренний `nativeRef` наружу не отдаётся: контракт — два метода в терминах урока, а не API библиотеки видео.

**Сравнение с контрактом из 2.14.** В 2.14 handle плеера включал `play()` и `pause()` — тогда решался вопрос типов, а не того, что выражать состоянием. С механикой ref на руках контракт пересмотрен: воспроизведение стало пропсом, потому что это состояние, а в handle остались только действия. Это нормальная эволюция контракта: на P2 он описывал форму, на P3 — поведение.

**Вклад в проект (P3).** Плеер урока RN Academy получает реализацию и пересмотренный контракт: воспроизведение — пропс, перемотка — методы handle. Прокрутка к текущему уроку и фокус поля заметки — через ref в эффекте и обработчике соответственно.
</details>
