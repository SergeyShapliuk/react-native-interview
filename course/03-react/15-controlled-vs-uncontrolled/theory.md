# 3.15 Controlled vs uncontrolled — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что правильнее — `value` или `defaultValue`» — а на вопрос, **где живёт значение поля, что стоит каждый символ в каждом режиме и где один режим перестаёт справляться**.

---

## 1. Что это

**Controlled-поле** — значение поля задаётся пропсом `value` из состояния React, а каждое изменение приходит в обработчик и записывается обратно в состояние:

```jsx
const [title, setTitle] = useState('');
<TextInput value={title} onChangeText={setTitle} />
```

Источник истины — состояние React. Поле показывает то, что сказал React.

**Uncontrolled-поле** — поле хранит значение само; React задаёт только начальное (`defaultValue`) и узнаёт текущее, когда ему сообщат или когда он спросит:

```jsx
const textRef = useRef('');
<TextInput defaultValue={note.text} onChangeText={(t) => { textRef.current = t; }} />
```

Источник истины — нативное поле. React не рендерится на ввод.

### Ключевая формулировка урока

> **В controlled-форме источник истины — состояние React, и каждый символ проходит полный круг через рендер. В uncontrolled — источник истины нативное поле, и React узнаёт значение, только когда спросит или когда ему сообщат.**

---

## 2. Как это работает

### Круг controlled-поля

На каждый символ:

```
пользователь нажал клавишу
    → нативное поле показывает символ
    → событие onChangeText уходит в JS
    → setTitle(...) — обновление в очереди (3.3)
    → рендер компонента, владеющего состоянием, и всех его потомков
    → commit: новое значение value уходит в нативное поле
```

Важная деталь RN: символ появляется в нативном поле **сразу**, до того как JS что-либо узнал. Controlled-значение — это не то, что рисует символ, а **подтверждение** из JS. В `TextInput` RN 0.87 значение из JS применяется командой нативному полю (`setTextAndSelection`) из layout-эффекта самого `TextInput`, и команда сопровождается счётчиком событий, — так нативная сторона отличает актуальное подтверждение от устаревшего, если пользователь успел ввести ещё символы.

Пока JS лишь повторяет введённое (`setTitle(text)`), подтверждение совпадает с тем, что уже на экране, и круг незаметен. Как только JS **меняет** значение — обрезает, фильтрует, форматирует, — пользователь видит свой символ, затем замену. Окно между ними — время круга: на загруженном JS-потоке это видимое мерцание и прыжки курсора.

### Цена controlled: рендер того, кто владеет состоянием

Сам по себе controlled-ввод не дорогой: рендер маленького компонента с одним полем стоит микросекунды. Дорого становится, когда состояние поля лежит **высоко**:

```jsx
function LessonFormScreen() {
  const [form, setForm] = useState({ title: '', description: '', tags: '', /* ... 20 полей */ });
  return (
    <ScrollView>
      <Field label="Название" value={form.title} onChangeText={(t) => setForm({ ...form, title: t })} />
      {/* ... ещё 19 полей ... */}
      <LessonPreview form={form} />
    </ScrollView>
  );
}
```

Каждый символ в любом поле — новый объект `form`, рендер экрана, всех двадцати полей и превью. Стрелки `onChangeText` новые на каждый рендер, поэтому даже `memo` на `Field` не помог бы (3.10).

Снижают цену три приёма:

- **состояние ближе к полю** — каждое поле или группа полей владеет своим значением, а наверх уходит только итог (при отправке или с debounce) — «опустить состояние вниз» из 3.11;
- **`memo` на строках формы** со стабильным обработчиком, получающим имя поля: `onChange={updateField}` и внутри `updateField(name, value)` через функциональное обновление;
- **деление формы** — шаги, вкладки, секции, у каждой своё состояние.

### Uncontrolled в RN: как узнать значение

У ref `TextInput` в RN 0.87 есть методы `focus`, `blur`, `clear`, `isFocused`, `setSelection` — но **нет метода чтения текущего текста**. Поэтому «неконтролируемое поле, значение которого читается при отправке» в RN почти всегда выглядит так: `defaultValue` для начального значения и `onChangeText`, записывающий текст в ref без рендера (3.9):

```jsx
function NoteEditor({ note, onSave }) {
  const textRef = useRef(note.text);
  return (
    <>
      <TextInput
        multiline
        defaultValue={note.text}
        onChangeText={(t) => { textRef.current = t; }}
      />
      <Button title="Сохранить" onPress={() => onSave(textRef.current)} />
    </>
  );
}
```

Ввод не вызывает ни одного рендера. React узнаёт текст в момент сохранения.

### Сброс неконтролируемого поля

`defaultValue` — начальное значение. Документированного способа «обновить поле через изменение `defaultValue`» нет, и полагаться на это нельзя. Для сброса:

- **`key`** — новый экземпляр поля с новым `defaultValue` (3.2): `<NoteEditor key={note.id} note={note} />`;
- **`ref.current.clear()`** — очистить поле императивно, например после отправки сообщения.

### Где uncontrolled не справляется

Всё, что требует **реакции на каждый символ**:

- **маска** (телефон, карта, дата) — значение нужно преобразовать при вводе;
- **зависимые поля** — выбор страны меняет формат индекса; ввод в одном поле включает другое;
- **валидация на лету** — сообщение об ошибке под полем по мере ввода;
- **счётчик символов, кнопка, активная только при непустом поле** — UI зависит от значения.

Для них нужен controlled-режим — или гибрид: значение в ref, плюс отдельное маленькое состояние только для того, что влияет на UI (например, `isEmpty`), обновляемое лишь при его изменении.

### Библиотеки форм

Библиотеки форм в React-экосистеме по сути выбирают режим за вас. Одни строятся вокруг неконтролируемых полей и подписок (значение живёт вне состояния React, рендерится только то, что подписано на изменившееся поле), другие — вокруг controlled-состояния формы. Выбирая библиотеку, полезно понимать, какую модель она реализует: от этого зависит, что рендерится на символ и как реализуется маска.

---

## 3. Почему это важно

**Форма — самое частое место, где RN-приложение ощущается медленным.** Ввод — непрерывное действие с частотой нескольких событий в секунду, и каждая лишняя миллисекунда рендера на символ складывается в «клавиатура не успевает». Длинная форма с состоянием в корне экрана на медленном Android — классическая жалоба.

**Режим определяет, что вообще возможно.** Маска, валидация на лету, зависимые поля — controlled. Длинный текст без реакции на ввод — uncontrolled дешевле. Это не вопрос вкуса, а свойство задачи, и выбирать его нужно для каждого поля, а не для формы целиком.

**Неверный режим даёт дефекты, а не только медлительность.** Форматирование в controlled-поле на загруженном потоке — мерцание и прыжки курсора. `defaultValue`, которое «должно было обновиться», — устаревший текст в поле. Сброс формы без ключа — черновик предыдущей сущности.

## 4. Где это в React Native

### `TextInput` — нативное поле

Ввод текста, курсор, выделение, автозамена, предиктивный ввод — всё это нативная сторона. JS получает события и может отправлять значения обратно. Отсюда двойственность controlled-режима в RN, которой нет в вебе в такой явной форме: поле **уже** показало символ, а JS его подтверждает или заменяет. Автозамена и предиктивный ввод на нативной стороне добавляют свои изменения, которые тоже проходят через этот круг.

### Маски и форматирование

Номер телефона, сумма с разделителями, номер карты. Форматирование в `onChangeText` с записью результата в `value` — работающий подход, но с видимой ценой на загруженном JS-потоке. Варианты снизить её:

- держать поле, его состояние и форматирование в маленьком компоненте, чтобы круг был коротким;
- не форматировать на каждый символ то, что можно отформатировать по `onBlur` (сумма с разделителями тысяч);
- для сложных масок — специализированные библиотеки полей, которые выполняют преобразование ближе к нативной стороне.

### Поиск

Строка поиска — естественный controlled-случай: значение нужно для запроса и часто для кнопки очистки. Цену снижают не отказом от controlled, а отделением ввода от тяжёлой работы: поле отзывается мгновенно, а запрос или фильтрация — по отложенному значению (`useDebouncedValue`, 3.12; `useDeferredValue`, 3.17).

### Длинный текст

Заметка, комментарий, описание — текст, на который UI не реагирует до сохранения. Uncontrolled с ref: ни одного рендера на ввод, и многострочное поле с большим текстом не гоняет его через JS на каждый символ туда и обратно.

## 5. Типичные ошибки

**Состояние всей формы в корне экрана.** Возникает из естественного желания «держать данные формы в одном месте». Каждый символ рендерит весь экран. Данные в одном месте нужны при отправке — собрать их можно и из состояний полей или ref.

**«Controlled — правильно, uncontrolled — костыль».** Возникает из документации React для веба, где controlled-подход рекомендуется как основной. Это рекомендация удобства, а не корректности; в RN, где поле нативное, неконтролируемый режим часто и проще, и дешевле.

**«Controlled-поле дорогое само по себе».** Обратная ошибка. Дорого то, что рендерится вместе с полем. Controlled-поле в маленьком компоненте стоит почти ничего.

**Форматирование в `onChangeText` с полем в большом компоненте.** Возникает, когда маску добавляют к уже существующей форме. Длинный круг плюс замена значения — мерцание и прыгающий курсор.

**`defaultValue` как способ обновлять поле.** Возникает из ожидания, что новый пропс «перетечёт» в поле. Для сброса — `key` или `clear()`.

**`value` из пропсов без `onChangeText`, записывающего обратно.** Возникает при «контролируемом» поле, которое забыли подключить. Пользователь вводит символ, поле его показывает, затем JS возвращает прежнее значение — символ исчезает.

**Чтение текста из ref поля.** Возникает из веб-опыта (`input.value`). У ref `TextInput` такого метода нет — значение нужно сохранять в `onChangeText`.

---

## 6. Trade-offs

### Контроль против стоимости рендера

Controlled даёт полный контроль: маски, валидация на лету, зависимые поля, сброс и программная подстановка значения через обычное состояние. Платит рендером на каждый символ — от микросекунд до заметных задержек, в зависимости от того, где лежит состояние. Uncontrolled бесплатен по рендерам и теряет возможность реагировать на ввод.

### Выбор на поле, а не на форму

Разумная форма — смешанная: поле поиска controlled, маска телефона controlled в маленьком компоненте, комментарий uncontrolled, итоговые данные собираются при отправке. Правило «все поля controlled» или «все uncontrolled» почти всегда переплачивает где-то.

### Своя форма против библиотеки

Своя форма на `useState` или `useReducer` (3.8) прозрачна и достаточна для пяти полей. На двадцати полях с валидацией, зависимостями и асинхронными проверками своя реализация превращается в самописную библиотеку форм. Выбор библиотеки — выбор модели (controlled-состояние или подписки на неконтролируемые поля) и её цены.
