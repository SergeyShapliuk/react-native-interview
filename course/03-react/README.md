## Цель блока

Понять, что React делает между вызовом `setState` и появлением пикселя, и научиться на это влиять осознанно — вместо расстановки `memo` по интуиции.

Блок держится на одном сдвиге: **компонент — это не объект, который живёт на экране, а функция, которую React вызывает, когда сам решит.** Всё остальное следует отсюда: состояние хранится не в компоненте, а в узле дерева React; эффект — это не «код после рендера», а синхронизация с внешней системой; лишний рендер — это лишний вызов функции, и его причина всегда читается по коду.

Версии, на которые опирается блок: **React 19.2** (шаблон React Native 0.87 ставит 19.2.3), React Compiler 1.0, `eslint-plugin-react-hooks` 7. Примеры проверены на React 19.2.3 с `react-dom` в jsdom; там, где поведение RN-рендерера отличается, это сказано явно.

# Часть 1 — Модель рендера (3.1–3.4)

## 3.1 Reconciliation и Fiber 🟡

**Цель.** Видеть за компонентом узел дерева React, который живёт между рендерами, и понимать, по каким правилам React решает, переиспользовать узел или создать новый.

**Prerequisites.** 1.12 (references), 1.20 (event loop: почему нельзя занять поток надолго).

> **Ключевая формулировка урока.** Состояние принадлежит не функции компонента, а позиции в дереве. Тип элемента и его место — это всё, по чему React узнаёт «тот же» компонент.

**Содержание (по семи углам).** Элемент как описание (объект `{ type, props, key }`) против fiber как рабочей единицы с состоянием, очередью обновлений и эффектами · два дерева — current и work-in-progress — и почему commit сводится к переключению указателя · эвристики reconciliation: другой `type` на той же позиции — размонтирование поддерева целиком; тот же `type` — обновление пропсов; соседи сопоставляются по `key` или по индексу · почему понадобилась прерываемая работа: рекурсивный рендер занимал поток до конца, fiber позволяет остановиться после любой единицы работы · что прерываемость не означает: в React 19 по умолчанию синхронными остаются обновления от дискретных событий, прерываемыми — переходы (`startTransition`) и отложенные значения (3.17) · где в RN: render-фаза выполняется на JS-потоке, её результат — дерево host-компонентов, которое Fabric превращает в Shadow Tree (4.3) · ошибки: компонент, объявленный внутри другого компонента (новый `type` на каждый рендер, состояние сбрасывается); условный рендер, меняющий позицию соседей; «React сравнивает DOM/нативные view» · trade-offs: эвристика O(n) вместо оптимального сравнения деревьев и цена, которую за неё платит разработчик (стабильные типы и ключи) · связи: 3.2 ключи, 3.3 фазы, 3.17 прерываемость, 4.1 и 4.3 Fabric и Shadow Tree.

**RN relevance.** Вся работа reconciliation происходит на JS-потоке, и нативная сторона видит только её результат: Fabric получает новое неизменяемое дерево host-компонентов и вычисляет мутации. Поэтому сброс состояния из-за смены `type` в RN стоит дороже, чем кажется: размонтированное поддерево — это уничтоженные и заново созданные нативные view, включая изображения, которые нужно снова декодировать, и `TextInput`, потерявший фокус и введённый текст.

**Типичные заблуждения.** «Компонент хранит своё состояние» · «Fiber — это новая архитектура рендеринга нативных view» (это алгоритм React, а не RN; Fabric — другое) · «с Fiber любой рендер прерываемый» · «React сравнивает предыдущий и новый экран».

**Проверка понимания.** 1) Почему компонент `Row`, объявленный внутри тела списка, теряет состояние при каждом рендере, хотя ключи стабильные? 2) `{showBanner && <Banner />}<LessonForm />` против раннего `return` с другой формой дерева — в каком варианте форма сохранит введённый текст? 3) Какие обновления в React 19 прерываемы, а какие нет? 4) Почему функция компонента обязана быть чистой и при чём здесь два дерева fiber?

**Практика.** Экран урока с условным баннером, сдвигающим соседей, и с компонентом, объявленным внутри родителя. Найти, где состояние сбрасывается, объяснить через позицию и тип, исправить без `key`-хаков.

**Связи вперёд.** 3.2 ключи · 3.3 render и commit · 3.17 concurrent rendering · 4.1 New Architecture · 4.3 Shadow Tree и Yoga.

**RN Academy (P3).** На P3 появляется React-слой: экран списка курсов и экран урока. Правило проекта: компоненты объявляются только на верхнем уровне модуля.

**Из банка вопросов.** V3 §2 «reconciliation / Fiber» (`deep dive`).

## 3.2 Роль `key` 🟡

**Цель.** Понимать `key` как идентичность элемента среди соседей и предсказывать, что ломается при нестабильном ключе.

**Prerequisites.** 3.1, 1.5 (идентичность массивов).

> **Ключевая формулировка урока.** `key` отвечает не на вопрос «нужно ли перерисовать», а на вопрос «это тот же экземпляр или другой». Состояние, ref и нативный view следуют за ключом.

**Содержание (по семи углам).** Что делает `key` в списке: сопоставление соседей между рендерами · `index` как ключ: корректен для статичного списка, ломается при вставке в начало, удалении, сортировке — состояние и неконтролируемое значение остаются на позиции, а данные уезжают · случайный ключ (`Math.random()`, новый `id` на каждый рендер) — полное перемонтирование каждый раз · `key` вне списка: сброс состояния компонента сменой ключа (`<LessonForm key={lessonId} />`) · `key` на фрагменте · где в RN: `keyExtractor` у `FlatList`, `TextInput` в строке списка, анимированные строки, рециклинг в FlashList (ключ и переиспользование view — разные механизмы) · ошибки: «ключ нужен для производительности», ключ из индекса при сортировке, составной ключ из изменяемых полей · trade-offs: сброс через `key` проще эффекта и дороже по работе (полное перемонтирование поддерева) · связи: 3.7 сброс состояния без эффекта, 5.4 списки и рециклинг.

**RN relevance.** Классический симптом — значение в `TextInput` «прыгает» на соседнюю строку после удаления элемента из списка: состояние осталось на позиции, а данные сдвинулись. Второй — анимация удаления проигрывается не на той строке. `keyExtractor` у `FlatList` — это тот же `key`, и `String(index)` там повторяет ту же ошибку.

**Типичные заблуждения.** «`key` нужен, чтобы убрать предупреждение» · «`index` — нормальный ключ, если элементы не удаляются» (сортировка и вставка в начало тоже ломают) · «ключ должен быть уникальным глобально» (только среди соседей) · «новый ключ — это просто перерисовка».

**Проверка понимания.** 1) Список из трёх строк с `TextInput`, ключ — индекс; пользователь ввёл текст во вторую строку и удалил первую. Что увидит? 2) Чем `key={lessonId}` на форме отличается от эффекта, очищающего поля при смене `lessonId`? 3) Почему `key={Math.random()}` хуже, чем отсутствие ключа?

**Практика.** Список заметок с полем ввода и удалением; воспроизвести перескок значения, объяснить по шагам reconciliation, исправить ключом и проверить сортировку.

**Связи вперёд.** 3.7 сброс состояния через `key` · 3.15 неконтролируемые поля · 5.4 списки, `keyExtractor`, рециклинг.

**RN Academy (P3).** Ключи списка уроков — идентификаторы из домена; форма заметки к уроку сбрасывается ключом при смене урока.

## 3.3 Путь обновления: setState → update queue → batching → scheduling → render → commit 🟡

```
setState  →  update queue  →  batching  →  scheduling  →  render  →  commit
```

**Цель.** Пройти путь от `setState` до изменения экрана по шагам и объяснять, почему два обновления дали один рендер, а иногда два.

**Prerequisites.** 1.20 (event loop), 1.21 (микротаски), 3.1.

> **Ключевая формулировка урока.** `setState` не меняет состояние — он ставит обновление в очередь и просит React запланировать работу. Новое значение появится только в следующем вызове компонента.

**Содержание (по семи углам).**

- **update queue** — обновление не применяется сразу, оно ставится в очередь на fiber; внутри того же обработчика переменная состояния сохраняет старое значение;
- **функциональное обновление** — `setN(n => n + 1)` применяется к результату предыдущего обновления в очереди, `setN(n + 1)` — к значению из замыкания;
- **batching** — обновления, вставшие в очередь до её обработки, дают один рендер; в React 18+ это верно для обработчиков, таймеров, промисов и нативных событий, а на практике граница — `await` промиса, который действительно ждёт (с уже выполненным промисом результат зависит от приоритета, и число рендеров не является гарантией); `flushSync` как способ выйти из группировки — API `react-dom`, в RN его нет;
- **scheduling** — React назначает обновлению приоритет (lane) и решает, когда выполнять работу; дискретное событие — синхронно, переход — прерываемо (3.17);
- **render phase** — вызов функций компонентов и reconciliation; чистая, для переходов — прерываемая, а результат может быть выброшен, поэтому побочные эффекты здесь запрещены;
- **commit phase** — применение результата: мутации host-дерева, затем `useLayoutEffect`, затем, позже, `useEffect`; синхронная и непрерываемая;
- **bailout** — `setState` с тем же значением по `Object.is` не даёт рендера потомков, но сам компонент может быть вызван ещё раз, прежде чем React откажется от работы.

Где в RN: render на JS-потоке; commit в Fabric создаёт новое Shadow Tree и передаёт его на UI-поток для монтирования (4.3) · ошибки: чтение состояния сразу после `setState`; три `setN(n + 1)` подряд; `setState` в теле рендера; «`useEffect` выполняется сразу после рендера» · trade-offs: батчинг экономит рендеры и делает состояние наблюдаемым только «после», `flushSync` возвращает синхронность и платит лишним рендером и блокировкой · связи: 1.20–1.21 (механизм), 3.4 (lifecycle), 3.6 (момент эффектов), 3.17 (приоритеты), 5.2 (бюджет кадра).

**RN relevance.** Автоматическая группировка обновлений вне обработчиков событий (в таймерах, промисах, колбэках нативных модулей) работает с конкурентным корнем, то есть с New Architecture; с RN 0.82 другой архитектуры нет, но в старом коде встречаются костыли под старое поведение — `unstable_batchedUpdates` и ручное объединение состояний. Второе: «лишний рендер» и «долгий commit» в RN — разные проблемы. Первое — работа JS-потока, видна в React Profiler; второе — применение мутаций к нативным view и layout, видно в системном профайлере (5.10). Этот урок даёт словарь, без которого блок 05 не читается.

**Типичные заблуждения.** «`setState` синхронный в обработчиках и асинхронный в остальных местах» · «каждый `setState` даёт рендер» · «после `await` обновления тоже группируются с теми, что были до него» · «render — это отрисовка на экране».

**Проверка понимания.** 1) Почему `console.log(count)` сразу после `setCount(count + 1)` выводит старое значение? 2) Обработчик вызывает `setLoading(true)`, ждёт запрос, затем `setData(d); setLoading(false)`. Сколько рендеров и почему? 3) Чем render-фаза отличается от commit-фазы и почему побочный эффект допустим только во второй?

**Практика.** Предсказать число рендеров и значения для пяти обработчиков (последовательные `setState`, функциональная форма, `await` посередине, `flushSync`, `setState` того же значения), затем проверить логированием.

## 3.4 Lifecycle компонента и StrictMode 🟡

**Цель.** Знать порядок выполнения и очистки эффектов на всех этапах жизни компонента и читать двойной вызов в StrictMode как диагностику.

**Prerequisites.** 3.3, 1.14 (closures), 1.22 (что держит ссылку).

> **Ключевая формулировка урока.** Эффект и его очистка — пара, описывающая одно и то же состояние внешней системы, а не «начало» и «конец» компонента. Очистка вызывается перед каждым следующим запуском эффекта, а не только при размонтировании.

**Содержание (по семи углам).** Классовые методы жизненного цикла в функциональной модели не исчезли — они перераспределились между рендером, эффектом и функцией очистки:

- **mount** — рендер, commit, затем эффекты; дочерние эффекты выполняются раньше родительских; обращение к узлу до commit бессмысленно;
- **update** — рендер происходит всегда, эффект — только при изменении зависимостей; сначала очищаются все эффекты, которые будут перезапущены, потом запускаются новые;
- **unmount** — очистка всех эффектов; что гарантировано выполнится, а что нет (асинхронный колбэк, уже улетевший в очередь, не отменится сам);
- **StrictMode в dev** — двойной вызов функции компонента, инициализаторов `useState` и `useMemo`, а также цикл «эффект → очистка → эффект» и то же для ref-колбэков (React 19); что именно этот повтор вскрывает: неидемпотентную подписку, запрос без отмены, мутацию внешнего объекта или ref в теле рендера.

Ошибки: «эффект с `[]` выполняется один раз», «очистка — это `componentWillUnmount`», борьба со StrictMode через флаг `didRun` в ref · trade-offs: StrictMode стоит двойной работы в dev и шумного лога, взамен находит ошибки, которые иначе проявятся только при реальном переиспользовании состояния · связи: 3.5 зависимости, 3.6 порядок двух видов эффектов, 4.17 navigation lifecycle, 5.8 утечки.

**RN relevance.** `StrictMode` в RN-проекте включается явно — шаблон RN 0.87 его не добавляет, корень приложения оборачивается вручную, — и там, где он включён, «эффект отработал дважды» становится одним из самых частых вопросов команды. Практическое решение: включать осознанно и чинить то, что он вскрыл. Второй момент — **размонтирование компонента не равно уходу с экрана**: в стековой навигации экран остаётся смонтированным под новым, его эффекты не очищаются, таймеры идут, подписки получают события. Здесь фиксируется только граница этого различия; navigation lifecycle — 4.17.

**Типичные заблуждения.** «Очистка выполняется только при размонтировании» · «StrictMode — баг, его нужно выключить» · «двойной вызов бывает и в release» · «уход со стекового экрана размонтирует компонент».

**Проверка понимания.** 1) Эффект подписывается на emitter без очистки; что покажет StrictMode и что случится в release? 2) В каком порядке выполнятся эффекты родителя и ребёнка при монтировании и очистки при размонтировании? 3) Почему счётчик в `ref.current++` в теле компонента в StrictMode покажет 2 на первом рендере?

**Практика.** Компонент с подпиской, таймером и запросом, который в StrictMode ведёт себя неверно; найти неидемпотентную часть каждого эффекта и исправить без отключения StrictMode.

**Связи вперёд.** 3.5 зависимости · 3.6 `useLayoutEffect` · 3.7 когда эффект не нужен · 4.17 navigation lifecycle · 5.8 утечки памяти.

**RN Academy (P3).** Корень приложения оборачивается в `StrictMode`; всё, что он вскрыл в слое P3, исправляется, а не подавляется.

## 3.5 Правила хуков и зависимостей 🟡

**Цель.** Выводить правила хуков из того, как React хранит состояние, и писать массив зависимостей, который не врёт.

**Prerequisites.** 3.1, 3.4, 1.14 (closures, stale closure).

> **Ключевая формулировка урока.** React узнаёт хук по порядковому номеру вызова, а не по имени. Массив зависимостей — не список «когда перезапускать», а перечень всех значений из рендера, которые эффект читает.

**Содержание (по семи углам).** Хуки как связный список на fiber: почему условный вызов, вызов в цикле или после раннего `return` сдвигает соответствие · правила: только на верхнем уровне, только из компонентов и хуков · массив зависимостей: сравнение по `Object.is` поэлементно · «честный» массив — всё реактивное, что читается внутри; что не нужно указывать (сеттер `useState`, `dispatch`, ref-объект, значения вне компонента) · как уменьшить зависимости, не соврав: функциональное обновление, перенос функции внутрь эффекта или наружу компонента, примитив вместо объекта, `useEffectEvent` (React 19.2) для «прочитать актуальное, не реагируя на изменение» · `eslint-plugin-react-hooks` 7: `rules-of-hooks`, `exhaustive-deps` и почему их предупреждение нельзя глушить комментарием · `async`-функция в эффекте · ошибки: пустой массив «чтобы выполнилось один раз», объект или функция из рендера в зависимостях, подавление линтера · trade-offs: честные зависимости иногда дают частые перезапуски, и выбор между перезапуском, ref (3.9) и `useEffectEvent` — это выбор между снимком и актуальным значением (1.14) · связи: 3.9 ref как актуальное значение, 3.10 почему объект в deps меняется каждый рендер, 3.12 правила внутри кастомного хука, 5.8 утечки.

**RN relevance.** Типовые случаи: подписка на `AppState` или нативный emitter, которой нужен актуальный обработчик, но которую нельзя переподписывать на каждый рендер; `setInterval` для таймера урока, читающий устаревшее состояние; эффект с объектом `route.params` в зависимостях, перезапускающийся при каждом рендере экрана. Все три лечатся не подавлением линтера, а одним из приёмов урока.

**Типичные заблуждения.** «Пустой массив — значит, эффект не зависит ни от чего» · «зависимости — это триггеры, их выбираю я» · «линтер перестраховывается» · «`useCallback` решает проблему зависимостей».

**Проверка понимания.** 1) Почему `if (!user) return null;` перед `useState` ломает компонент, хотя в большинстве рендеров всё работает? 2) Эффект с `setInterval(() => setSeconds(seconds + 1), 1000)` и `[]` — что покажет экран и как исправить, не добавляя `seconds` в зависимости? 3) Чем `useEffectEvent` отличается от ref с последним обработчиком и почему функцию из него нельзя передавать в пропсы?

**Практика.** Три эффекта с подавленным `exhaustive-deps`: восстановить честные зависимости и для каждого выбрать способ уменьшить их, не возвращая ложь в массив.

**Связи вперёд.** 3.9 refs · 3.10 referential equality · 3.12 кастомные хуки · 3.18 компилятор и правила линтера · 5.8 утечки · 09 подписки на нативные события.

## 3.6 `useEffect` vs `useLayoutEffect` 🟡

**Цель.** Выбирать вид эффекта по моменту, в который он должен выполниться, и знать, чем платит синхронный вариант.

**Prerequisites.** 3.3, 3.4.

> **Ключевая формулировка урока.** `useLayoutEffect` выполняется в commit до того, как результат увидит пользователь, и блокирует показ, пока не закончит. `useEffect` выполняется после — и именно поэтому почти всегда правильный выбор.

**Содержание (по семи углам).** Порядок внутри commit: мутации host-дерева → layout-эффекты (и их очистки) → показ → пассивные эффекты · обновление состояния в `useLayoutEffect` обрабатывается синхронно, до показа: промежуточный кадр не виден · когда нужен `useLayoutEffect`: измерить размер или позицию и сразу применить результат (тултип, автоскролл, позиционирование поповера) · `useInsertionEffect` — только для библиотек CSS-in-JS, в RN почти не встречается · цена: блокирует показ кадра, тяжёлая работа в нём — прямой вклад в задержку отклика · ошибки: `useLayoutEffect` «чтобы быстрее», запрос данных в layout-эффекте, `setState` в `useEffect` для позиционирования (мигание) · trade-offs: синхронность против отзывчивости · связи: 3.9 ref на узел, 5.2 бюджет кадра, 4.3 layout в Shadow Tree.

**RN relevance.** В New Architecture layout доступен синхронно: в `useLayoutEffect` можно измерить view (`measure`, `measureInWindow`, а с RN 0.82 — `getBoundingClientRect()` у ref на нативный компонент) и обновить состояние в том же commit, так что пользователь не увидит промежуточного положения. В старой архитектуре единственным путём был `onLayout`, и обновление по нему применялось после того, как предыдущий кадр уже показан — отсюда «прыгающие» тултипы в старом коде. Документация RN прямо рекомендует `useLayoutEffect` как место для измерений.

**Типичные заблуждения.** «`useLayoutEffect` быстрее» · «`useEffect` выполняется после отрисовки на экране, поэтому мигает всегда» · «`onLayout` и `useLayoutEffect` — одно и то же».

**Проверка понимания.** 1) Тултип позиционируется по размеру якоря через `useEffect` + `setState`. Что видит пользователь и что изменится с `useLayoutEffect`? 2) Почему тяжёлый расчёт в `useLayoutEffect` хуже, чем в `useEffect`? 3) В каком порядке выполнятся layout- и пассивные эффекты родителя и ребёнка при монтировании и что из этого следует для измерений? 4) Гарантирует ли `useEffect`, что кадр уже показан?

**Практика.** Подсказка над кнопкой, которая должна не выходить за край экрана: реализовать через `onLayout`, затем через `useLayoutEffect` с измерением, сравнить число кадров с неверной позицией.

**Связи вперёд.** 3.9 refs и измерения · 4.3 Shadow Tree и Yoga · 5.2 бюджет кадра · 5.10 профилирование.

**RN Academy (P3).** Всплывающая подсказка к уроку позиционируется измерением в `useLayoutEffect`; во всех остальных местах проекта — `useEffect`.

## 3.7 Когда эффект не нужен 🟡

**Цель.** Смотреть на эффект и отвечать, синхронизирует ли он React с чем-то внешним; если нет — удалять его, не заменяя ничем или заменяя вычислением, ключом или обработчиком.

**Prerequisites.** 3.2, 3.3, 3.4, 3.5.

> **Ключевая формулировка урока.** Эффект — это синхронизация React с системой, которая ничего не знает о React. Всё остальное — вычисление при рендере, обработка события или новый экземпляр компонента.

**Содержание (по семи углам).** Самый ценный урок блока для разработчика, который пишет на React каждый день: типовой экран содержит несколько эффектов, и значительная их часть удаляется без замены.

- **производное значение вместо состояния плюс эффекта** — значение, вычисляемое из пропсов и состояния, вычисляется при рендере; отдельное состояние добавляет лишний рендер и окно рассогласования;
- **сброс состояния через `key`** — «при смене пропса очистить форму» — это другой экземпляр компонента (3.2);
- **корректировка части состояния при смене пропса** — сравнение с предыдущим значением прямо в рендере, если `key` сбрасывает слишком много;
- **обработка события в обработчике** — то, что произошло из-за действия пользователя, принадлежит обработчику, а не эффекту, который «заметит» изменение постфактум;
- **цепочки эффектов** — каждое звено даёт дополнительный рендер, порядок ломается при добавлении нового звена;
- **«записать пропс в стейт»** — копия, расходящаяся с оригиналом;
- **уведомить родителя об изменении** — вызвать колбэк в том же обработчике, а не эффектом;
- **синхронизация с внешней системой** — единственное оправданное применение.

Правило линтера 7-й версии, которое ловит часть таких эффектов (`set-state-in-effect`, входит в `recommended`) · trade-offs: вычисление при рендере выполняется на каждый рендер — если оно дорогое, это вопрос 3.11, а не повод вернуть эффект · связи: 3.2 `key`, 3.11 мемоизация, 07 запросы и гонки, 5.8 утечки.

**RN relevance.** Граница проходит отчётливо: `AppState`, `Dimensions`, `Keyboard`, слушатели нативных emitter'ов, подписка на изменение сети — настоящие внешние системы, и эффект с парной очисткой на своём месте. Фильтрация списка по строке поиска, пересчёт суммы формы, «скопировать `route.params` в состояние экрана» — нет: это вычисление при рендере, и эффект там создаёт лишний кадр и рассогласование.

**Типичные заблуждения.** «Эффект нужен, чтобы отреагировать на изменение состояния» · «производное состояние кэширует вычисление» · «эффект после `setState` — нормальный способ вызвать колбэк родителя» · «запрос данных — не синхронизация» (синхронизация, но с гонками — блок 07).

**Проверка понимания.** 1) `const [filtered, setFiltered] = useState([])` + эффект на `[items, query]`: сколько рендеров на один ввод символа и что показывает экран между ними? 2) Форма должна очищаться при смене `lessonId`: чем `key` лучше эффекта и когда он хуже? 3) POST-запрос «урок пройден» отправляется эффектом при `status === 'done'` — что сломается при восстановлении состояния из хранилища?

**Практика.** Экран с пятью эффектами: удалить те, что не синхронизируют ничего внешнего, и для каждого назвать замену.

**Связи вперёд.** 3.11 мемоизация производных значений · 3.12 хуки-обёртки над внешними системами · 4.17 navigation lifecycle · 6.1 что считать состоянием · 07 запросы, гонки и отмена · 5.8 утечки.

**RN Academy (P3).** Ревью эффектов слоя P3: у каждого оставшегося эффекта в комментарии названа внешняя система, с которой он синхронизирует.

## 3.8 `useState` vs `useReducer` 🟡

**Цель.** Выбирать между хуками по тому, что считать единицей изменения — значение или переход, и показывать, какие комбинации состояния стали невыразимыми.

**Prerequisites.** 3.3, 2.5 (discriminated unions).

> **Ключевая формулировка урока.** `useState` описывает значения, `useReducer` — переходы. Когда не все переходы между состояниями экрана разрешены, редьюсер делает это явным, а набор `useState` — нет.

**Содержание (по семи углам).**

- **несколько связанных `useState` расходятся** — каждый обновляется отдельно, промежуточные комбинации («загрузка и ошибка одновременно») выразимы; редьюсер делает такую комбинацию недостижимой, если её нет среди переходов;
- **редьюсер как список допустимых переходов** — действие описывает, что произошло, а не какое поле присвоить; логика перехода собрана в одном месте;
- **функциональная форма `setState`** — решает только проблему устаревшего значения, но не даёт ни централизации, ни запрета невозможных комбинаций;
- **тестируемость** — редьюсер это чистая функция `(state, action) => state`, тестируется без рендера, моков и таймеров;
- **стабильность `dispatch`** — не меняется между рендерами, его не нужно указывать в зависимостях и мемоизировать;
- **цена** — больше кода на простом состоянии, косвенность при чтении, порог, ниже которого `useState` честно лучше.

Ошибки: редьюсер как `setField(name, value)` с одним действием; мутация состояния в редьюсере; побочные эффекты в редьюсере (в StrictMode он вызывается дважды) · связи: 2.5 тип состояния, 3.4 двойной вызов, 6.4 редьюсеры Redux.

**RN relevance.** Два типовых случая: форма с валидацией, где поля связаны, и состояние экрана `idle / loading / success / error`, которое в RN почти всегда усложняется pull-to-refresh и подгрузкой следующей страницы — на `useState` это четыре булевых флага и шестнадцать комбинаций, из которых осмысленны пять.

**Типичные заблуждения.** «`useReducer` — для сложного состояния, `useState` — для простого» (критерий — переходы, а не размер) · «редьюсер — это Redux» · «функциональная форма `setState` даёт то же самое» · «в редьюсере можно отправить запрос».

**Проверка понимания.** 1) Какие из шестнадцати комбинаций `isLoading / isRefreshing / isLoadingMore / error` не имеют смысла и как редьюсер их исключает? 2) Почему побочный эффект в редьюсере обнаружится в StrictMode? 3) Когда `useReducer` проигрывает `useState`?

**Практика.** Состояние экрана на четырёх булевых флагах перевести на `useReducer` с состоянием-объединением из 2.5; показать, какие комбинации стали недостижимыми; покрыть редьюсер тестом без рендера.

**Связи вперёд.** 3.12 `useAsync` на редьюсере · 6.1 что считать состоянием · 6.4 редьюсеры и иммутабельность · 6.8 нормализация · 07 состояние запроса.

## 3.9 Refs: `useRef`, ref как пропс, `useImperativeHandle` 🟡

**Цель.** Решать, когда значение должно быть ref, а когда состоянием, и объяснять, почему запись в `ref.current` не вызывает рендер.

**Prerequisites.** 3.3, 3.6, 1.14 (closures).

> **Ключевая формулировка урока.** Ref — это ячейка, живущая между рендерами, о которой React ничего не знает. Изменение ячейки не ставит обновление в очередь, поэтому то, что влияет на экран, в ref не хранится.

**Содержание (по семи углам).** Ref разбирается вскоре после `useLayoutEffect` не случайно: это два инструмента одной ситуации — когда декларативной модели недостаточно.

- **хранить то, что не влияет на разметку** — идентификатор таймера, предыдущее значение, флаг «запрос отменён», актуальное значение для долгоживущего колбэка (продолжение 1.14);
- **не читать и не писать ref при рендере** — кроме ленивой инициализации; рендер должен быть чистым (3.3), а StrictMode покажет запись в ref дважды (3.4);
- **доступ к узлу** — ref на host-компонент заполняется в commit; в React 19 (RN 0.78+) `ref` — обычный пропс функционального компонента, `forwardRef` нужен для React 18 и встречается в существующем коде; ref-колбэк и его функция очистки (React 19);
- **`useImperativeHandle`** — отдать наружу узкий контракт вместо всего узла;
- **не использовать ref вместо состояния** — если значение видно на экране, ref даст рассинхронизацию.

Ошибки: ref как «состояние без лишних рендеров», `ref.current` в зависимостях эффекта, обращение к ref узла в теле рендера · trade-offs: ref даёт актуальное значение и теряет согласованный снимок (1.14); императивный handle — публичный API, который придётся поддерживать · связи: 3.5 `useEffectEvent` как альтернатива ref для колбэков, 3.15 неконтролируемый ввод, 5.4 `scrollToIndex`, 09 нативные компоненты.

**RN relevance.** Здесь ref перестаёт быть темой «про DOM»: `measure` и `measureInWindow` (с RN 0.82 также DOM-подобные методы вроде `getBoundingClientRect()`), `scrollTo` и `scrollToIndex` у списка, `focus` и `blur` у `TextInput`, animated ref в Reanimated, ref на нативный компонент, у которого императивный метод есть, а пропса нет. Для RN-разработчика это ежедневная работа.

**Типичные заблуждения.** «Ref — это способ хранить состояние без рендера» · «`ref.current` можно указать в зависимостях» · «`forwardRef` обязателен для передачи ref» · «ref на компонент даёт доступ к его внутреннему состоянию».

**Проверка понимания.** 1) Счётчик нажатий хранится в ref и выводится на экран — что увидит пользователь? 2) Почему `ref.current` в массиве зависимостей не делает эффект реактивным? 3) Что отдать наружу из компонента плеера: ref на внутренний нативный узел или handle из трёх методов — и почему?

**Практика.** Экран урока: фокус на поле заметки по кнопке, прокрутка списка к текущему уроку, плеер с императивным handle; для каждого места объяснить, почему здесь ref, а не состояние.

**Связи вперёд.** 3.12 хуки с ref внутри · 3.15 неконтролируемые поля · 5.4 `scrollToIndex` и `getItemLayout` · 5.7 Reanimated · 09 императивные контракты нативных компонентов.

# Часть 3 — Ре-рендеры и структура компонентов (3.10–3.16)

## 3.10 Referential equality 🟡

**Цель.** Знать, где и каким алгоритмом React сравнивает значения, и называть причину лишнего рендера по коду.

**Prerequisites.** 1.4, 1.12 (references), 1.13 (immutability), 3.3.

> **Ключевая формулировка урока.** React нигде не сравнивает содержимое. Он сравнивает ссылки — через `Object.is` для состояния и зависимостей и поверхностно, по ключам, для пропсов `memo`.

**Содержание (по семи углам).** Четыре места сравнения: `setState` (bailout по `Object.is`), массив зависимостей (`Object.is` поэлементно), `memo` (shallow compare пропсов), `value` контекста (`Object.is`) · почему компонент рендерится: изменилось его состояние, рендерится родитель, изменился контекст — и только в первом и третьем случае он «сам виноват» · ре-рендер родителя рендерит всех детей независимо от пропсов, пока ребёнок не обёрнут в `memo` · что даёт новую ссылку на каждый рендер: литерал объекта и массива, стрелка, `map`/`filter`, `style={{...}}`, `{...props}` · shallow compare: один уровень, порядок и число ключей · где ограничение: вложенный объект с тем же содержимым — другой, мутированный объект — тот же · ошибки: мутация состояния и «setState не сработал», глубокое сравнение как решение · trade-offs: ссылочное сравнение дёшево и требует иммутабельности; глубокое — дорогое и непредсказуемое · связи: 1.12, 3.11, 3.14, 6.5 селекторы.

**RN relevance.** `style={{ padding: 8 }}`, `contentContainerStyle={{...}}`, `renderItem={() => ...}`, `data={items.filter(...)}` у `FlatList` — новые ссылки на каждый рендер. Сами по себе они ничего не стоят; дорого становится, когда получатель — `memo`-компонент, `PureComponent` (каким внутри является `VirtualizedList`) или зависимость эффекта. Отсюда главный навык урока: по коду назвать, какая ссылка меняется и кто это замечает.

**Типичные заблуждения.** «Компонент рендерится, только если изменились его пропсы» · «React сравнивает пропсы всегда» · «одинаковые объекты равны» · «`style` из `StyleSheet.create` и литерал — одно и то же для сравнения».

**Проверка понимания.** 1) Родитель меняет своё состояние; ребёнок не получает пропсов. Отрендерится ли ребёнок и почему? 2) `memo`-компонент получает `options={{ compact: true }}` — сработает ли мемоизация? 3) Состояние-массив мутировано через `push` и передано в `setItems` — что произойдёт?

**Практика.** Компонент на ~80 строк: перечислить все места, где на каждый рендер создаётся новая ссылка, и для каждого сказать, замечает ли это кто-нибудь.

## 3.11 `memo` / `useMemo` / `useCallback` 🟡

**Цель.** Решать, где мемоизация нужна, а где вредна, и обосновывать оба случая.

**Prerequisites.** 3.10.

> **Ключевая формулировка урока.** Мемоизация — это не оптимизация сама по себе, а обещание стабильной ссылки. Она окупается, только если кто-то эту стабильность проверяет: `memo`-компонент, зависимость эффекта или дорогое вычисление.

**Содержание (по семи углам).** `memo` — пропускает рендер при поверхностно равных пропсах; кастомный компаратор и его опасность · `useMemo` — кэш одного значения по зависимостям: для дорогого вычисления и для стабильной ссылки, которую кто-то сравнивает · `useCallback` — `useMemo` для функции · цепочка: `useCallback` без `memo` у получателя ничего не даёт; `memo` без стабильных пропсов ничего не даёт; `children` как пропс ломает `memo` · стоимость: сравнение зависимостей на каждый рендер, память, читаемость, ложные зависимости · альтернативы до мемоизации: опустить состояние вниз, поднять содержимое вверх через `children` (3.13) · мемоизация — подсказка, а не гарантия · ошибки: `useCallback` на всё, `useMemo` для дешёвого `filter` на десяти элементах, `memo` на компоненте, принимающем `children` · trade-offs: стоимость рендера против стоимости сравнения и поддержки · связи: 3.13, 3.18 компилятор, 5.3, 5.4.

**RN relevance.** Главное место, где мемоизация в RN окупается почти всегда, — ячейка списка: `renderItem` вызывается для каждого видимого элемента, и `memo` на компоненте ячейки плюс стабильный обработчик убирают перерисовку всех строк при изменении одной. Второе — пропсы, уходящие в нативные компоненты с дорогим применением (карты, видео). Обратный случай — `useCallback` на обработчике `Pressable`, который никто не сравнивает.

**Типичные заблуждения.** «`useCallback` предотвращает пересоздание функции» (функция создаётся всё равно, возвращается старая) · «`memo` на всех компонентах не повредит» · «`useMemo` гарантирует, что значение не пересчитается» · «мемоизация нужна, если компонент рендерится часто».

**Проверка понимания.** 1) `onPress` обёрнут в `useCallback`, а `Button` — не `memo`. Что изменилось? 2) `memo`-компонент принимает `children` — сработает ли мемоизация? 3) Назовите три случая, когда `useMemo` оправдан.

**Практика.** PR, где мемоизация расставлена «на всякий случай»: для каждого места сказать, полезно оно, бесполезно или вредно, и почему.

**Связи вперёд.** 3.13 композиция как альтернатива · 3.14 мемоизация `value` контекста · 3.18 React Compiler · 5.3 профилирование · 5.4 ячейки списка · 6.5 мемоизированные селекторы.

## 3.12 Кастомные хуки как единица переиспользования 🟡

**Цель.** Проектировать контракт кастомного хука: что он возвращает, что в нём стабильно по ссылке и почему логика не вынесена в обычную функцию.

**Prerequisites.** 3.5, 3.9, 3.11, 2.14 (типизация возврата хука).

> **Ключевая формулировка урока.** Хук переиспользует логику, а не состояние. Два вызова одного хука — два независимых состояния.

**Содержание (по семи углам).** Урок отвечает на вопрос, который обычно решается по аналогии: что именно переиспользует хук.

- **состояние не разделяется** — два вызова дают два независимых состояния; хук — не способ сделать общие данные;
- **правила хуков действуют внутри хука** — хук не создаёт нового уровня, он разворачивается в тело компонента;
- **именование** — префикс `use` включает проверки линтера и компилятора и сообщает читателю, что вызов нельзя поставить под условие;
- **контракт возвращаемого значения** — кортеж, когда значений два и имена даёт вызывающий; объект, когда значений больше; стабильность возвращаемых функций по ссылке как часть контракта;
- **когда хук не нужен** — если логика не использует ни состояния, ни эффектов, ни других хуков, это обычная функция;
- **хук-обёртка над внешней системой** — эффект с очисткой внутри, значение наружу.

Ошибки: хук для общего состояния, хук-«мешок» на весь экран, нестабильные функции в возврате, хук без `use` · trade-offs: хук скрывает эффекты — вызывающий не видит, что подписался на emitter · связи: 3.19 подписка на внешний стор, 07 запросы, 09 обёртка нативного модуля.

**RN relevance.** Типовой набор, который в RN-проекте возникает сам: `useAppState`, `useKeyboardHeight`, `useDebounce`, обёртка над нативным модулем, превращающая императивный emitter в значение. На этот урок опираются упражнения блока — `useDebounce` / `useThrottle` и `useAsync` / `useFetch`.

**Типичные заблуждения.** «Хук — способ поделиться состоянием между компонентами» · «любую функцию в компоненте стоит сделать хуком» · «префикс `use` — соглашение об именах» · «возвращаемые функции стабильны сами по себе».

**Проверка понимания.** 1) Два компонента вызывают `useCart()`; один добавил товар — увидит ли второй? 2) Почему `formatPrice` не должна быть `useFormatPrice`? 3) `useDebounce` возвращает функцию, которая меняется каждый рендер, — что сломается у вызывающего?

**Практика.** `useDebounce` и `useThrottle` с явным контрактом; `useAsync` на редьюсере из 3.8 — базовая версия без гонок.

**Связи вперёд.** 3.19 `useSyncExternalStore` · 6.3 общий стейт · 07 запросы, гонки и отмена · 09 обёртка нативного модуля · 11.3 тестирование хуков.

**RN Academy (P3).** `useLessonProgress` из контракта 2.14 получает реализацию; `useDebounce` используется в поиске по курсам.

## 3.13 Composition: `children`, render props, compound components 🟡

**Цель.** Убирать пробрасывание пропсов композицией и объяснять, почему здесь не понадобился стор.

**Prerequisites.** 3.1, 3.10, 3.11.

> **Ключевая формулировка урока.** Пропс пробрасывается через три уровня не потому, что нужно глобальное состояние, а потому, что дерево собрано не в том месте. Элемент, созданный там, где данные уже есть, никуда их не пробрасывает.

**Содержание (по семи углам).**

- **`children` как способ не знать о содержимом** — обёртка не получает пропсы для содержимого, а элементы `children` не перерисовываются при изменении состояния обёртки: они созданы выше и приходят той же ссылкой; если родитель пересоздал `children`, обёртка перерисуется вместе с ними;
- **слоты** — несколько пропсов-элементов (`header`, `footer`) вместо одного `children`;
- **render props** — когда содержимое зависит от внутреннего состояния контейнера; большая часть таких случаев закрыта хуками (3.12), уместными они остаются для списков с рендером элемента, слотов и анимационных обёрток;
- **compound components** — `<Tabs>` и `<Tabs.Item>`, связанные неявным контрактом через локальный контекст; контракт не виден в сигнатуре и должен быть описан;
- **HOC** — читать его нужно уметь, для нового кода почти всегда проигрывает хуку или композиции.

Ошибки: Context вместо композиции, `React.Children.map` и `cloneElement` для передачи пропсов, `memo` на обёртке с `children` · trade-offs: композиция поднимает сборку дерева вверх, и родительский компонент становится крупнее · связи: 3.14, 6.7, 08.

**RN relevance.** Обёртки экранов (safe area, скролл, состояние загрузки), layout-компоненты, собственная дизайн-система — компоненты, которые должны работать с любым содержимым. В RN это ощутимо и по производительности: правильно поставленный `children` не перерисовывается при изменении состояния обёртки — например, при каждом кадре анимации шапки, управляемой состоянием.

**Типичные заблуждения.** «Prop drilling лечится контекстом или стором» · «`children` всегда перерисовываются вместе с родителем» · «render props устарели» · «compound components работают через `cloneElement`».

**Проверка понимания.** 1) Почему `<ScreenLayout>{content}</ScreenLayout>` не перерисовывает `content` при изменении состояния `ScreenLayout`? 2) Когда render prop лучше хука? 3) Чем платит compound component за удобный синтаксис?

**Практика.** Пропс `user`, пробрасываемый через три уровня, убрать композицией через `children` и слоты — без стора и без контекста.

**Связи вперёд.** 3.14 Context · 6.7 prop drilling без глобального стейта · 08 публичный API UI-модуля.

## 3.14 Context и его цена 🟡

**Цель.** Объяснять, почему любое изменение `value` рендерит всех подписчиков, и дробить контекст под частоту изменений.

**Prerequisites.** 3.10, 3.11, 3.13.

> **Ключевая формулировка урока.** Context — механизм доставки, а не управления состоянием. Подписчик рендерится при любом изменении `value` по `Object.is`, и `memo` между провайдером и подписчиком этого не останавливает.

**Содержание (по семи углам).** Как работает: провайдер сравнивает `value` по `Object.is` и помечает всех потребителей · подписка на весь `value`: компонент, читающий одно поле, рендерится при изменении любого · `memo` не защищает потребителя, он защищает только промежуточные компоненты · объект `value`, созданный в рендере провайдера, — новый на каждый рендер · паттерны дробления: разделить значение и сеттеры (сеттеры не меняются), разделить по частоте изменений, опустить провайдер ниже, мемоизировать `value` · `use(Context)` в React 19 — то же чтение, допускающее условный вызов · когда Context — правильный выбор: редко меняющиеся значения (тема, локаль, сессия, зависимости) · ошибки: «Context как стор», один `AppContext` на всё, частые обновления через контекст · trade-offs: дробление уменьшает рендеры и умножает провайдеры · связи: 3.19 подписка с селектором, 6.3 Context vs Redux vs Zustand.

**RN relevance.** Тема, локаль, безопасные отступы (`react-native-safe-area-context` разделяет insets и frame на разные контексты именно ради этого), сессия — хорошие кандидаты. Позиция скролла, прогресс воспроизведения, введённый текст — плохие: каждое изменение рендерит всех потребителей, а в RN это дерево экрана со списками.

**Типичные заблуждения.** «Context — это state management» · «`memo` защищает от рендера при изменении контекста» · «потребитель рендерится, только если изменилось поле, которое он читает» · «`useMemo` на `value` решает всё».

**Проверка понимания.** 1) Провайдер отдаёт `{ user, setUser }` литералом; родитель провайдера рендерится — что происходит с потребителями? 2) Почему разделение на `StateContext` и `DispatchContext` уменьшает число рендеров? 3) Когда Context проигрывает внешнему стору с селекторами?

## 3.15 Controlled vs uncontrolled 🟡

**Цель.** Выбирать между контролируемым и неконтролируемым вводом по цене и требованиям экрана.

**Prerequisites.** 3.3, 3.9, 3.11.

> **Ключевая формулировка урока.** В controlled-форме источник истины — состояние React, и каждый символ проходит полный круг через рендер. В uncontrolled — источник истины нативное поле, и React узнаёт значение, только когда спросит.

**Содержание (по семи углам).** Controlled: `value` + `onChangeText`, каждый ввод — `setState` и рендер; валидация и форматирование на лету · uncontrolled: `defaultValue` + ref или чтение при отправке · смешанные случаи: `value`, временами равный `undefined`, и `defaultValue` как попытка обновлять поле · цена controlled на большом экране: рендер всей формы на каждый символ, если состояние наверху · как снижать цену: состояние поля в поле, `memo` на строках, деление формы · где границы uncontrolled: маска, зависимые поля, сброс формы (ключ, 3.2) · библиотеки форм как выбор режима · ошибки: состояние всей формы в корне экрана, controlled без необходимости, форматирование в `onChangeText` с прыгающим курсором · trade-offs: контроль и валидация против стоимости рендера · связи: 3.2, 3.9, 5.3.

**RN relevance.** В RN `TextInput` — нативное поле, и символ появляется в нём сразу, до того как JS что-либо узнал. Controlled-значение — это подтверждение из JS, которое приходит после круга «событие → рендер → команда нативному полю»; `TextInput` в RN 0.87 сопровождает такие команды счётчиком событий, чтобы нативная сторона отбрасывала устаревшие. Пока JS лишь повторяет введённое, круг незаметен. Как только JS **меняет** значение (маска, запрет символов), пользователь видит свой символ, а затем замену — и чем загруженнее JS-поток, тем дольше это окно: мерцание и прыжки курсора.

**Типичные заблуждения.** «Controlled — правильно, uncontrolled — костыль» · «controlled-поле дорогое само по себе» · «`defaultValue` — способ обновлять поле».

**Проверка понимания.** 1) Форма из 20 полей в состоянии корня экрана — сколько компонентов рендерится на символ? 2) Почему маска телефона плохо реализуется на uncontrolled-поле? 3) Как сбросить uncontrolled-форму при смене сущности?

**Практика.** Форма заметки: одно и то же поле в двух режимах; замерить число рендеров на ввод и решить, какой режим нужен каждому полю.

**Связи вперёд.** 5.3 диагностика ре-рендеров · 4.10 `TextInput` и стилизация · 08 формы и валидация на уровне архитектуры.

**RN Academy (P3).** Форма заметки к уроку: поиск — controlled с `useDebounce`, длинный текст заметки — uncontrolled с чтением по сохранению.

**Из банка вопросов.** V3 §2 «controlled vs uncontrolled» (`lesson`).

## 3.16 Error Boundaries 🟡

**Цель.** Понимать, какие ошибки Error Boundary перехватывает, а какие не увидит принципиально, и расставлять границы по смыслу экрана.

**Prerequisites.** 1.11 (error handling), 3.3, 3.4.

> **Ключевая формулировка урока.** Error Boundary ловит ошибки, брошенные, когда React сам выполняет ваш код: рендер, методы жизненного цикла, синхронное тело эффектов. Всё, что вызывает рантайм — обработчики, таймеры, продолжения промисов, — проходит мимо.

**Содержание (по семи углам).** Классовый компонент с `getDerivedStateFromError` и `componentDidCatch`; функционального аналога нет · что ловится: рендер, конструкторы, синхронные тела эффектов и их очисток · что не ловится: обработчики событий, `setTimeout`, продолжение после `await`, ошибки внутри самого boundary, ошибки на верхнем уровне модуля · способ довести асинхронную ошибку до boundary: `setState(() => { throw error })` · что происходит без boundary: React размонтирует всё дерево корня · `onCaughtError` / `onUncaughtError` у корня (React 19) · расстановка: корень приложения, экран, независимые виджеты; сброс через `key` или `resetKeys` · ошибки: один boundary на всё приложение, boundary как замена обработки ошибок в асинхронном коде · trade-offs: мелкие границы сохраняют больше экрана и усложняют восстановление · связи: 1.11, 07 сетевые ошибки, 10.6 crash reporting.

**RN relevance.** Рендерер RN 0.87 передаёт непойманную ошибку рендера в `ExceptionsManager` как **фатальную**, а пойманную границей — как нефатальную. Без boundary ошибка рендера в release по умолчанию закрывает приложение (JS-краш, 10.7), в dev — красный экран LogBox, который выглядит одинаково драматично в обоих случаях и маскирует разницу. Граница на уровне экрана оставляет работающей навигацию: пользователь может вернуться назад. Ошибки нативного кода и JS-ошибки вне React (колбэк нативного модуля, глобальный обработчик) идут в `ErrorUtils` и crash reporting — блок 10.

**Типичные заблуждения.** «Error Boundary ловит все ошибки компонента» · «ошибка в `onPress` попадёт в boundary» · «ошибка в `useEffect` не ловится» · «можно написать boundary на хуках».

**Проверка понимания.** 1) Какие из пяти ошибок (рендер, тело `useEffect`, `onPress`, `setTimeout` в эффекте, `await` в обработчике) поймает boundary? 2) Как довести ошибку асинхронной загрузки до ближайшего boundary? 3) Где поставить границы на экране урока с плеером, заметками и списком следующих уроков?

**Практика.** Расставить границы на экране урока, реализовать fallback с повтором через сброс ключа, проверить каждый из пяти видов ошибок.

**Связи вперёд.** 3.17 Suspense и границы загрузки · 7.3 сетевые ошибки · 10.6 Sentry / Crashlytics · 12.10 postmortem.

**RN Academy (P3).** Boundary на корне и на каждом экране; fallback с повтором; ошибки асинхронной загрузки доводятся до boundary явно.

# Часть 4 — Concurrent React (3.17–3.19)

## 3.17 Suspense и concurrent features 🔴

**Цель.** Понимать, как приоритизация меняет модель рендера, и решать, где переход или отложенное значение даёт выигрыш, а где маскирует медленный код.

**Prerequisites.** 3.1, 3.3, 3.16, 1.20.

> **Ключевая формулировка урока.** Concurrent rendering — это не параллельность, а право React бросить начатый рендер ради более срочного. Отсюда новая гарантия (интерфейс отвечает) и новая цена (рендер может не дойти до экрана, и компонент обязан это переживать).

**Содержание (по семи углам).** Lanes и приоритеты: дискретное событие, непрерывное, по умолчанию, переход · `startTransition` / `useTransition`: срочное обновление поля и несрочное обновление списка; `isPending` · `useDeferredValue` — отложенная копия значения · time slicing: React уступает поток между единицами работы, но не внутри одной функции компонента · Suspense: компонент «приостанавливает» рендер, ближайшая граница показывает fallback; `use(promise)` в React 19 и требование к кэшированию промиса · переход не показывает fallback для уже видимого содержимого · `<Activity>` (React 19.2): скрытое поддерево сохраняет состояние, эффекты которого отключены · ошибки: transition как лечение медленного рендера, промис, созданный при рендере, для `use` · trade-offs: отзывчивость против сложности модели и прерванной работы · связи: 3.19 tearing, 3.16 границы, 5.2, 07 данные.

**RN relevance.** Concurrent features в RN доступны только с New Architecture — с 0.82 это любое приложение. Типовые применения: фильтрация длинного списка при вводе (поле срочно, список — переход), переключение тяжёлых табов. Предел: time slicing не помогает, если медленна одна ячейка или нативная сторона — прерываемым является только рендер на JS-потоке, но не commit и не монтирование нативных view. Suspense для загрузки данных в RN используется через библиотеки (TanStack Query, Relay); собственная реализация на `use` требует кэша промисов.

**Типичные заблуждения.** «Concurrent — значит многопоточный» · «`startTransition` делает код быстрее» · «любой `setState` теперь прерываемый» · «Suspense — это лоадер».

**Проверка понимания.** 1) Почему переход не помогает, если медленен один компонент на 200 мс? 2) Что видит пользователь, если обновление, вызвавшее приостановку, обёрнуто в переход, и если нет? 3) Почему `use(fetchLessons())` в теле компонента зацикливается?

**Практика.** Поиск по 2000 урокам: сравнить ввод без перехода, с `useTransition` и с `useDeferredValue`; объяснить, где выигрыш и где его нет.

## 3.18 React Compiler 🔴

**Цель.** Понимать, что React Compiler убирает из кода, на каких допущениях он работает и где ручная мемоизация и ручной контроль всё ещё нужны.

**Prerequisites.** 3.5, 3.10, 3.11.

> **Ключевая формулировка урока.** Компилятор не делает рендер быстрее — он автоматически делает то, что делали `memo`, `useMemo` и `useCallback`, и только для кода, который соблюдает правила React. Код, который их нарушает, компилятор пропускает молча.

**Содержание (по семи углам).** Что делает: анализ потока данных компонента и гранулярная мемоизация JSX, значений и колбэков через кэш на fiber · что даёт: стабильные ссылки без ручной работы, мемоизацию, которую вручную не пишут (ветки JSX, промежуточные значения) · допущения: чистый рендер, иммутабельность пропсов и состояния, правила хуков · что происходит при нарушении: компонент пропускается без ошибки сборки · `eslint-plugin-react-hooks` 7 как линтер компилятора · где ручная работа остаётся: стабильность для внешних API и эффектов, где важна семантическая гарантия; дорогие вычисления вне компонентов; библиотеки, несовместимые с компилятором; `"use no memo"` как выход · ошибки: «с компилятором можно мутировать», удаление ручной мемоизации до проверки · trade-offs: меньше кода и ошибок мемоизации против менее наглядного поведения и зависимости от правил · связи: 3.11, 3.5, 5.3.

**RN relevance.** Компилятор — Babel-плагин и работает в RN так же, как в вебе; Expo SDK 54 включает его в новых проектах. В RN он особенно заметен на ячейках списков и стилях: инлайн-объекты `style` и стрелки в `renderItem` перестают быть новыми ссылками. Важно: стабильные ссылки не отменяют рециклинг и правильные ключи (5.4) и не ускоряют нативный commit.

**Типичные заблуждения.** «Компилятор оптимизирует всё» · «после компилятора `memo` не нужен нигде» · «компилятор сообщит о проблеме ошибкой сборки» · «компилятор меняет поведение рендера».

**Проверка понимания.** 1) Компонент мутирует пропс в рендере — что сделает компилятор? 2) Почему `useMemo` для значения, от которого зависит эффект с запросом, иногда стоит оставить и с компилятором? 3) Как проверить, что компонент скомпилирован?

## 3.19 `useSyncExternalStore` и tearing 🔴

**Цель.** Объяснять, что такое tearing и почему подписка на внешний стор требует отдельного API, а не `useEffect` + `setState`.

**Prerequisites.** 3.3, 3.12, 3.14, 3.17.

> **Ключевая формулировка урока.** Прерываемый рендер может прочитать внешний источник дважды — до и после его изменения. `useSyncExternalStore` гарантирует, что один рендер видит одну версию, и платит за это синхронностью.

**Содержание (по семи углам).** Урок закрывает блок и связывает 3.17 с выбором инструмента состояния в 6.3.

**Tearing** — один рендер показывает данные из двух версий внешнего источника: часть компонентов прочитала старое значение, часть — новое, потому что рендер был прерван, а стор изменился. В синхронной модели этого не возникало, поэтому подписка через `useEffect` + `setState` долгие годы работала.

Разбирается: контракт `subscribe` / `getSnapshot` и какую гарантию даёт хук (обновление из стора, изменившегося во время рендера, перезапускает рендер синхронно); почему `getSnapshot`, возвращающий новый объект на каждый вызов, приводит к бесконечному циклу; зачем нужен `getServerSnapshot` и почему в RN он почти не встречается; селектор поверх снимка; почему Zustand и React Redux перешли на этот API; как написать свою подписку на нативный emitter · ошибки: новый объект в `getSnapshot`, `subscribe` в теле компонента, `useEffect` + `setState` для изменяемого внешнего источника · trade-offs: синхронность против преимуществ переходов — обновление из внешнего стора не может быть переходом · связи: 3.12, 3.14, 6.3, 09.

**RN relevance.** Внешних источников в RN больше, чем в вебе: нативные модули с состоянием (сеть, ориентация, аудиоплеер), MMKV, собственные сторы. Хук-обёртка над нативным emitter через `useSyncExternalStore` — правильный способ отдать такое состояние в React без tearing и без лишнего рендера с устаревшим значением при монтировании.

**Типичные заблуждения.** «`useEffect` + `setState` — то же самое» · «tearing невозможен в однопоточном JS» · «`getSnapshot` может возвращать новый объект с теми же данными» · «внешний стор работает с переходами так же, как состояние».

**Проверка понимания.** 1) Как tearing возникает в однопоточном JS? 2) Почему `getSnapshot: () => ({ ...state })` ломает приложение? 3) В каком сценарии подписка через `useState` + `useEffect` навсегда покажет устаревшее значение даже без concurrent rendering? 4) Что теряет обновление из внешнего стора по сравнению с `setState` в переходе?

**Практика.** Стор состояния сети над эмулированным нативным emitter: одна ленивая нативная подписка на приложение, хук через `useSyncExternalStore`, селектор «офлайн ли» для ячеек списка и тест стора без React.

**Связи вперёд.** 6.3 Context vs Redux Toolkit vs Zustand · 6.5 цена селекторов · 09 подписки на нативные события.

**RN Academy (P3).** Состояние «онлайн / офлайн» — хук над эмулированным emitter через `useSyncExternalStore`; реальный нативный источник подключается в P4.
