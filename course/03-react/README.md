### Урок 3.3 — мост JavaScript → React → React Native

```
setState  →  update queue  →  batching  →  scheduling  →  render  →  commit
```

Урок отвечает на вопрос, который опытный разработчик обычно обходит практикой: **почему вызов `setState` не означает немедленный рендер**.

- **update queue** — обновление не применяется сразу, оно ставится в очередь на компонент;
- **batching** — несколько обновлений в одном «такте» дают один рендер; что попадает в один batch, а что нет;
- **scheduling** — React решает, когда выполнять работу, и может её прервать и переупорядочить (связь с concurrent features в 3.17);
- **render phase** — вызов функций компонентов и вычисление результата; чистая и прерываемая, поэтому побочные эффекты здесь запрещены;
- **commit phase** — применение результата; синхронная и непрерываемая, поэтому именно здесь работает `useLayoutEffect`;
- связь с **reconciliation** (3.1): render-фаза — это и есть место, где работает алгоритм сравнения, а `key` влияет на его результат.

Урок опирается на очереди задач и микротасков из блока 01 (1.20, 1.21) — batching становится понятен только после них — и готовит блок 05: «лишний рендер» и «долгий commit» — разные проблемы с разными инструментами и разными решениями. Поэтому это **ключевой переходный урок курса**: JavaScript → React → React Native.

### Урок 3.4 — lifecycle компонента и StrictMode

Урок стоит сразу после пути обновления: 3.3 отвечает, что происходит внутри одного обновления, 3.4 — что происходит с компонентом на протяжении его жизни. Классовые методы жизненного цикла в функциональной модели не исчезли, они перераспределились между рендером, эффектом и его функцией очистки, и именно это перераспределение обычно остаётся непроговорённым.

- **mount** — первый рендер, затем commit, затем эффекты; что доступно в каждый момент и почему обращение к узлу до commit бессмысленно;
- **update** — рендер происходит, а эффект выполняется только при изменении зависимостей; очередной эффект выполняется **после** очистки предыдущего, а не вместо неё;
- **cleanup** — функция очистки вызывается не только при размонтировании: она вызывается перед каждым следующим запуском того же эффекта. Отсюда правило: эффект и его очистка — пара, описывающая одно и то же состояние внешней системы, а не «начало» и «конец» компонента;
- **unmount** — очистка всех эффектов; что гарантировано выполнится, а что нет (асинхронный колбэк, уже улетевший в очередь, не отменится сам).

**StrictMode в dev** монтирует компонент, размонтирует и монтирует снова, вызывая рендер и эффекты дважды. Это не баг инструмента и не то, с чем нужно бороться выключением: двойной вызов вскрывает конкретный класс ошибок — неидемпотентную подписку (слушатель добавлен дважды, снят один раз), запрос без отмены (два ответа гонятся за один `setState`), мутацию внешнего объекта прямо в теле компонента. Код, корректный при повторном монтировании, корректен и при реальном переиспользовании состояния.

**RN relevance.** `StrictMode` в RN-проекте включается явно, оборачиванием корня приложения, — и там, где он включён, «эффект отработал дважды» оказывается одним из самых частых вопросов разработчика. Отсюда же практическое решение: включать его осознанно и чинить то, что он вскрыл, а не выключать обратно. Второй практический момент — **размонтирование компонента не равно уходу с экрана**: в стековой навигации экран остаётся смонтированным под новым, его эффекты не очищаются, таймеры продолжают идти, подписки продолжают получать события. Здесь фиксируется только граница этого различия; сам navigation lifecycle разбирается в 4.17.

> **Не дублировать:** правила зависимостей и «честный» массив deps — 3.5; разница между `useEffect` и `useLayoutEffect` по моменту выполнения — 3.6; navigation lifecycle и «экран жив, но не виден» — 4.17.

### Урок 3.7 — когда эффект не нужен

Самый ценный урок блока для разработчика, который уже пишет на React каждый день: типовой экран в продакшене содержит несколько эффектов, и значительная их часть удаляется без замены. Урок строится не вокруг API, а вокруг вопроса **«синхронизирует ли этот эффект React с чем-то вне React»**. Если нет — эффекта быть не должно.

- **производное значение вместо состояния плюс эффекта** — если значение вычисляется из пропсов и состояния, оно вычисляется прямо при рендере; хранение его в отдельном состоянии добавляет лишний рендер и окно, в котором данные рассогласованы;
- **сброс состояния через `key`** — «при смене пропса очистить форму» — это не эффект, это другой экземпляр компонента; прямое продолжение 3.2;
- **обработка события в обработчике** — то, что произошло из-за действия пользователя, принадлежит обработчику, а не эффекту, который «заметит» изменение состояния постфактум; разница видна, когда одно и то же состояние меняется из двух мест;
- **цепочки эффектов** — эффект меняет состояние, которое запускает следующий эффект; каждое звено даёт дополнительный рендер, а порядок звеньев не гарантирован и ломается при добавлении третьего;
- **«записать пропс в стейт»** — копия, которая расходится с оригиналом ровно тогда, когда это сложнее всего воспроизвести;
- **синхронизация с внешней системой** — единственное оправданное применение: подписка, таймер, императивный API, который ничего не знает о React.

**RN relevance.** Граница проходит отчётливо: `AppState`, `Dimensions`, `Keyboard`, слушатели нативных emitter'ов, подписка на изменение сети — это настоящие внешние системы, и эффект с парной очисткой здесь на своём месте. Фильтрация списка по строке поиска, пересчёт итоговой суммы формы, «скопировать `route.params` в состояние экрана» — нет: это вычисление при рендере, и эффект там создаёт лишний кадр и рассогласование.

> **Не дублировать:** мемоизация производного значения, когда вычисление действительно дорогое, — 3.11; запросы данных, гонки и отмена — блок 07; утечки от неснятых подписок — 5.8.

### Урок 3.8 — `useState` vs `useReducer`

Вопрос урока — не «какой хук удобнее», а **что считать единицей изменения: значение или переход**. Когда экран имеет несколько состояний, между которыми разрешены не все переходы, редьюсер описывает это явно, а набор `useState` — нет.

- **несколько связанных `useState` расходятся** — потому что каждый обновляется отдельно, и промежуточные комбинации («загрузка и ошибка одновременно», «данные есть, но и спиннер крутится») выразимы; редьюсер делает такую комбинацию недостижимой, если её нет среди переходов;
- **редьюсер как список допустимых переходов** — действие описывает, что произошло, а не какое поле присвоить; вся логика перехода собрана в одном месте, а не размазана по обработчикам;
- **функциональная форма `setState`** — решает только проблему устаревшего значения внутри замыкания, но не даёт ни централизации логики, ни запрета на невозможные комбинации; это разные инструменты, и их регулярно путают;
- **тестируемость** — редьюсер это чистая функция `(state, action) => state`, которая тестируется без рендера, без моков и без таймеров;
- **цена** — больше кода на простом состоянии, косвенность при чтении (чтобы понять, что делает кнопка, нужно перейти к редьюсеру), и порог, ниже которого `useState` честно лучше.

**RN relevance.** Два типовых случая: состояние формы с валидацией, где поля связаны между собой, и состояние экрана `idle / loading / success / error`, которое в RN почти всегда усложняется ещё и pull-to-refresh и подгрузкой следующей страницы — на `useState` это превращается в четыре булевых флага и шестнадцать комбинаций, из которых осмысленны пять.

> **Не дублировать:** иммутабельность в редьюсерах Redux и нормализация — 6.4 и 6.8; что вообще считать состоянием, а что производным значением, — 6.1; описание состояния через discriminated union — 2.5. Здесь только React API и выбор между двумя хуками.

### Урок 3.9 — refs как императивный escape hatch

Ref разбирается вскоре после `useLayoutEffect` (3.6) не случайно: это два инструмента одной и той же ситуации — когда декларативной модели недостаточно и нужно обратиться к узлу напрямую.

Ось урока — **почему изменение `ref.current` не вызывает рендер**, и что из этого следует: ref это ячейка, живущая между рендерами, а не состояние. Отсюда два законных применения и одно незаконное:

- **хранить то, что не влияет на разметку** — идентификатор таймера, предыдущее значение, флаг «запрос уже отменён», актуальное значение для колбэка с устаревшим замыканием (прямое продолжение 1.14);
- **доступ к узлу** — пропуск ref через свой компонент: в React 19 (RN 0.78+) `ref` — обычный пропс функционального компонента, а `forwardRef` нужен только для React 18 и встречается в существующем коде; `useImperativeHandle` как способ отдать наружу узкий контракт вместо всего узла;
- **не использовать ref вместо состояния** — если значение влияет на то, что видно на экране, ref приведёт к рассинхронизации разметки и данных.

**RN relevance** — здесь ref перестаёт быть темой «про DOM»: `measure` и `measureInWindow` на нативном узле, `scrollTo` и `scrollToIndex` у списка, `focus` и `blur` у `TextInput`, animated ref в Reanimated, ref на нативный компонент, у которого императивный метод есть, а пропса — нет. Для RN-разработчика это ежедневная работа, а не краевой случай.

> **Не дублировать:** устаревшее замыкание и выбор «ref или зависимость» разбираются в 1.14 и 3.5 — здесь только механизм ref. Утечки через ref на нативный узел — блок 05.

### Урок 3.12 — кастомные хуки как единица переиспользования

Урок отвечает на вопрос, который обычно решается по аналогии: **что именно переиспользует хук**. Хук переиспользует логику — подписки, вычисления, работу с состоянием — и ничего не говорит о разметке. Это отличает его от композиции компонентов (3.13), которая решает обратную задачу.

- **состояние не разделяется** — два вызова одного хука дают два независимых состояния; хук это не способ сделать общие данные, и попытка использовать его так приводит к рассинхронизации копий;
- **правила хуков действуют внутри хука** — тот же запрет на условный вызов, те же зависимости; хук не создаёт нового уровня, он разворачивается в тело компонента;
- **именование** — префикс `use` не косметика: он включает проверки линтера и сообщает читателю, что вызов нельзя поставить под условие;
- **контракт возвращаемого значения** — кортеж, когда значений два и имена даёт вызывающая сторона (`const [value, setValue] = ...`); объект, когда значений больше или они необязательны; стабильность возвращаемых функций по ссылке как часть контракта, а не деталь реализации;
- **когда хук не нужен** — если логика не использует ни состояния, ни эффектов, ни других хуков, это обычная функция, и оборачивание её в хук только ограничивает места вызова.

**RN relevance.** Типовой набор, который в RN-проекте возникает сам: `useAppState`, `useKeyboardHeight`, `useDebounce`, обёртка над нативным модулем, превращающая императивный emitter в значение. На этот урок опираются упражнения блока — `useDebounce` / `useThrottle` и `useAsync` / `useFetch`.

> **Не дублировать:** типизация кастомного хука и вывод типа возвращаемого кортежа — 2.14; гонки, отмена запроса и кэширование — блок 07; механика подписки на внешний стор — 3.19.

### Урок 3.13 — composition: `children`, render props, compound components

Урок про механизм, который чаще всего пропускают и сразу заводят стор: **пропс пробрасывается через три уровня не потому, что нужно глобальное состояние, а потому, что дерево собрано не в том месте**.

- **`children` как способ не знать о содержимом** — компонент, принимающий `children`, не получает пропсы для них, а сами элементы `children` не перерисовываются при изменении состояния этого компонента: они созданы выше и приходят той же ссылкой. Если же родитель пересоздал `children`, обёртка перерисуется вместе с ними. Это же убирает и значительную часть prop drilling, потому что элемент создаётся там, где данные уже есть;
- **render props** — когда содержимое зависит от внутреннего состояния контейнера; сегодня большая часть таких случаев закрыта кастомными хуками (3.12), и уместными они остаются там, где контейнер управляет ещё и разметкой: списки с рендером элемента, компоненты с несколькими слотами, анимационные обёртки;
- **compound components** — `<Tabs>` и `<Tabs.Item>`, связанные неявным контрактом через локальный контекст; цена — контракт не виден в сигнатуре пропсов и не проверяется компилятором, поэтому он должен быть описан явно;
- **HOC** — остаётся в коде проектов и читать его надо уметь, но для нового кода почти всегда проигрывает хуку или композиции: непрозрачные пропсы, конфликт имён, лишний уровень в дереве, испорченный стек в DevTools.

**RN relevance.** Обёртки экранов (safe area, скролл, состояние загрузки), layout-компоненты, собственная дизайн-система: компоненты, которые должны работать с любым содержимым и ничего о нём не знать. В RN это ощутимо и по производительности — правильно поставленный `children` не перерисовывается при изменении состояния обёртки.

> **Обязательная граница:** выбор между «композиция или стор» — решение про состояние, и оно принимается в уроке 6.7. Здесь только механизм композиции.

> **Не дублировать:** 6.7 (решение о способе доставки состояния); цена Context и дробление провайдеров — 3.14; стабильность ссылок на элементы — 3.10.

### Урок 3.19 — `useSyncExternalStore` и tearing

Урок закрывает блок и связывает 3.17 (concurrent) с выбором инструмента состояния в 6.3.

**Tearing** — ситуация, когда один рендер показывает данные из двух разных версий внешнего источника: часть компонентов успела прочитать старое значение, часть — новое, потому что рендер был прерван, а стор за это время изменился. В синхронной модели рендера такого не возникало, поэтому подписка «вручную» через `useEffect` + `setState` долгие годы работала.

Разбирается: какую именно гарантию даёт `useSyncExternalStore` и чем он платит (чтение синхронное, значит снимок обязан быть стабильным по ссылке); почему `getSnapshot`, возвращающий новый объект на каждый вызов, приводит к бесконечному циклу; зачем нужен `getServerSnapshot` и почему в RN он почти не встречается; почему библиотеки состояния (Zustand, Redux) перешли на этот API внутри себя — и что из этого следует для разработчика, который пишет свою подписку на нативный emitter или на внешний источник.

> **Не дублировать:** выбор между Context, Redux Toolkit и Zustand — урок 6.3; цена селекторов — 6.5. Здесь только механизм подписки и причина, по которой он понадобился.

- Прохожу путь от `setState` до изменения экрана по шагам и объясняю, почему два обновления дали один рендер.
- Называю причину лишнего рендера по коду, не запуская профайлер.
- Решаю, где мемоизация нужна, а где вредна, и обосновываю оба случая.
- Объясняю, что сломается без стабильного `key` — вплоть до «значение в `TextInput` прыгнуло на другой элемент».
- Объясняю порядок выполнения и очистки эффектов и почему cleanup вызывается перед следующим эффектом, а не только при размонтировании.
- Читаю двойной вызов эффекта в StrictMode как диагностику и называю, какую именно ошибку он вскрыл.
- Смотрю на эффект и отвечаю, синхронизирует ли он что-то внешнее; если нет — убираю его, не заменяя ничем.
- Выбираю между `useState` и `useReducer` по тому, важны ли переходы, и показываю, какие комбинации состояния перестали быть выразимыми.
- Проектирую контракт кастомного хука: что он возвращает, что в нём стабильно по ссылке и почему логика не вынесена в обычную функцию.
- Убираю пробрасывание пропсов композицией и объясняю, почему здесь не понадобился стор.
- Понимаю, какие ошибки Error Boundary не увидит, и что с ними делать.
- Решаю, когда значение должно быть ref, а когда состоянием, и объясняю, почему запись в `ref.current` не вызывает рендер.
- Объясняю, что такое tearing, и почему подписка на внешний стор требует отдельного API, а не `useEffect` + `setState`.

## Checkpoint

Дан компонент на ~150 строк: инлайн-объекты в пропсах, контекст с широким `value`, список с `index` в качестве ключа, несколько эффектов с неполными зависимостями. Перечислить **все** причины лишних рендеров и доказать каждую рассуждением по коду. Затем предложить изменения, отсортированные по «выигрыш / риск», и отдельно отметить те места, где `React.memo` не поможет.

Отдельным пунктом: указать эффекты, которые удаляются без замены, и для каждого назвать, чем он заменён — вычислением при рендере, `key`, обработчиком события или ничем.

## Упражнения

- **Debugging exercise:** компонент с лишними ре-рендерами — найти причины без профайлера. К этому же компоненту возврат в блоке 05, уже с профайлером.
- **Code review exercise:** PR, где мемоизация расставлена «на всякий случай» — объяснить, что из этого бесполезно и почему.
- **Refactoring exercise:** экран с пятью эффектами — удалить те, что не синхронизируют ничего внешнего, и для каждого назвать замену (3.7).
- **Refactoring exercise:** состояние экрана на четырёх булевых флагах перевести на `useReducer` и показать, какие комбинации стали недостижимыми (3.8, продолжение упражнения с discriminated union из блока 02).
- **Refactoring exercise:** пропс, пробрасываемый через три уровня, убрать композицией через `children` — без стора и без контекста (3.13).
- **Exercise:** кастомный хук `useDebounce` / `useThrottle` (из банка вопросов) — с явным контрактом возвращаемого значения и стабильностью ссылок (3.12).
- **Exercise:** `useAsync` / `useFetch` с loading / error / data — базовая версия на `useReducer`; полноценная работа с гонками и отменой переносится в блок 07.
- **Debugging exercise:** компонент, который ломается при двойном монтировании в StrictMode — найти неидемпотентную часть (3.4).
