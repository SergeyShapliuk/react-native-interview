# 3.2 Роль `key` — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует проследить, **какой fiber получил какие пропсы**, а не повторить «ключи должны быть уникальными».

---

**1. Список из трёх строк A, B, C, ключ — индекс. У каждой строки локальное состояние черновика. Пользователь ввёл текст в строку B и удалил строку A. Что он увидит и почему?**

<details>
<summary>Ответ</summary>

Он увидит черновик из B в строке **C**, а строку B — пустой.

По шагам:

```
до:     key=0 → A [ ]      key=1 → B [текст]      key=2 → C [ ]
после:  key=0 → B [ ]      key=1 → C [текст]
```

После удаления данных стало две строки, и React сопоставляет их по ключам `0` и `1`. Fiber с ключом `0` (бывший A, черновик пустой) получил пропсы B. Fiber с ключом `1` (бывший B, черновик с текстом) получил пропсы C. Fiber с ключом `2` размонтирован — хотя удаляли A.

Состояние осталось на позициях, данные сдвинулись. Это проверяется экспериментом за минуту, и поведение одинаково для веба и RN — с той разницей, что в RN неконтролируемый `TextInput` хранит текст в нативном view, который тоже следует за ключом.

**Ответ «ничего не изменится, React перерисует строки с новыми данными»** вскрывает модель «состояние принадлежит данным». Состояние принадлежит fiber, а fiber выбирается по ключу.

**Ответ «текст исчезнет совсем»** вскрывает ожидание, что React заметит удаление и сбросит всё. Он не заметит: с ключами-индексами удаление первого элемента для React выглядит как «изменились пропсы у первых двух и удалён третий».

**Ответ «будет предупреждение в консоли»** неверен: предупреждение выдаётся при отсутствии ключей или дубликатах, а `key={index}` — полноценный уникальный ключ.
</details>

---

**2. Форму заметки нужно очищать при смене урока. Чем `<NoteForm key={lessonId} />` отличается от эффекта, очищающего поля при смене `lessonId`?**

<details>
<summary>Ответ</summary>

Ключ создаёт **новый экземпляр** формы: старый fiber размонтирован, новый смонтирован с начальным состоянием. Сбрасывается всё сразу: каждое поле, ошибки валидации, ref, состояние вложенных компонентов, фокус — без единой строки кода сброса.

Эффект делает другое:

```jsx
useEffect(() => {
  setText('');
  setError(null);
}, [lessonId]);
```

Он срабатывает **после** рендера с новым `lessonId`. Значит, есть один кадр, в котором показан новый урок со старым черновиком, затем второй рендер с очищенными полями. К тому же эффект сбрасывает только то, что в нём перечислено: добавили поле — забыли добавить в эффект — черновик «перетекает» в другой урок. И вложенные компоненты со своим состоянием эффект не сбросит вообще.

Когда ключ хуже: если поддерево тяжёлое (плеер, длинный список), полное перемонтирование стоит дорого, и сбросить нужно не всё. Тогда — точечный сброс части состояния при рендере (3.7), но не эффект.

**Ответ «это одно и то же, просто ключ короче»** вскрывает непонимание того, что ключ меняет экземпляр, а не значения.

**Ответ «эффект правильнее, ключ — хак»** вскрывает модель «ключ — только для списков». Ключ — документированный способ сказать «здесь другой экземпляр».
</details>

---

**3. Почему `key={Math.random()}` хуже, чем отсутствие ключа?**

<details>
<summary>Ответ</summary>

Без ключа React сопоставляет детей по индексу: при каждом рендере родителя строки **обновляются** — тот же fiber получает новые пропсы. Состояние держится на позициях (что неверно при удалении, но хотя бы стабильно при обычном рендере).

Случайный ключ меняется на каждом рендере. Для React каждый рендер — «все старые элементы исчезли, появились новые»: все строки размонтируются и монтируются заново. Эксперимент: три строки, три рендера родителя — девять монтирований. Каждое монтирование — это очистка и запуск всех эффектов, обнуление состояния и ref, а в RN ещё и уничтожение и создание нативных view с повторным декодированием изображений.

То есть случайный ключ ломает и корректность (состояние теряется на любом рендере, а не только при удалении), и производительность.

**Ответ «одинаково, ключи же уникальные»** вскрывает понимание ключа как «уникальной метки», а не как идентичности между рендерами. Ключ обязан быть **стабильным**, уникальность — второе требование.
</details>

**4. В FlashList ключи строк — идентификаторы из данных, но состояние «раскрыто» у ячейки после прокрутки оказывается у другого элемента. Ключи же правильные — почему?**

<details>
<summary>Ответ</summary>

Потому что FlashList **рециклирует** ячейки: экземпляр компонента ячейки, ушедший за пределы экрана, переиспользуется для нового элемента — получает новые пропсы, но сохраняет своё локальное состояние. Это сознательный обход механизма ключа ради того, чтобы не монтировать ячейки при прокрутке.

Ключ и рециклинг — разные механизмы. Ключ говорит «этот элемент данных — тот же», рециклинг говорит «этот экземпляр можно отдать другому элементу». В рециклирующем списке модель «состояние следует за ключом» не работает, и состояние ячейки становится обязанностью автора: хранить его вне ячейки (по идентификатору элемента) или сбрасывать при смене элемента. Конкретные инструменты — 5.4.

**Ответ «значит, ключи всё-таки неправильные»** вскрывает перенос модели обычного списка на рециклирующий.

**Ответ «это баг FlashList»** вскрывает незнание того, за счёт чего рециклинг экономит работу.
</details>

## Задание — список заметок, где текст «уезжает»

**Дано.** Экран заметок к уроку. Жалобы: «после удаления заметки текст, который я редактировал, оказался в другой заметке», «после сортировки по дате отметки "важное" перепутались», «при обновлении списка с сервера все поля мигают».

```jsx
function NotesScreen() {
  const [notes, setNotes] = useState([]);

  async function refresh() {
    const raw = await api.loadNotes();
    setNotes(raw.map((n) => ({ ...n, localId: Math.random().toString(36) })));
  }

  function sortByDate() {
    setNotes(notes.sort((a, b) => b.createdAt - a.createdAt));
  }

  return (
    <FlatList
      data={notes}
      keyExtractor={(_, index) => String(index)}
      renderItem={({ item }) => (
        <NoteRow note={item} onDelete={() => setNotes(notes.filter((n) => n !== item))} />
      )}
      ListHeaderComponent={<Button title="По дате" onPress={sortByDate} />}
    />
  );
}

function NoteRow({ note, onDelete }) {
  const [important, setImportant] = useState(note.important);
  return (
    <View>
      <TextInput defaultValue={note.text} />
      <Switch value={important} onValueChange={setImportant} />
      <Button title="Удалить" onPress={onDelete} />
    </View>
  );
}
```

**Требуется.**

1. Для каждой из трёх жалоб найти причину в коде и объяснить, что React сопоставил с чем.
2. Найти в коде ещё одну ошибку, не связанную с ключами напрямую, но мешающую сортировке работать.
3. Исправить код. Отдельно объяснить, почему `localId` из `Math.random()` не годится, даже если использовать его в `keyExtractor`.

---

<details>
<summary>Разбор</summary>

**1. Причины жалоб.**

*Текст уезжает после удаления.* `keyExtractor` возвращает индекс. `TextInput` неконтролируемый: текст живёт в нативном поле, то есть в host-узле, который принадлежит fiber строки. После удаления заметки выше по списку данные сдвигаются на позицию вверх, а fiber с ключами `0, 1, 2...` остаются на местах — вместе с нативными полями. Редактируемый текст оказывается в строке, которая теперь показывает другую заметку. Размонтирована при этом последняя строка, а не удалённая.

*Отметки «важное» перепутались после сортировки.* `important` — локальное состояние `NoteRow`, инициализированное из пропса один раз при монтировании. При сортировке ключи-индексы не меняются, fiber остаются на позициях и сохраняют своё `important`, а заметки переставлены. Состояние осталось на местах, данные переехали.

*Поля мигают при обновлении с сервера.* Здесь важна связь с `localId`: ключи-индексы при обновлении как раз стабильны. Мигание появится, если кто-то «исправит» `keyExtractor` на `item.localId` — тогда при каждом `refresh` все ключи новые, и все строки перемонтируются: нативные поля пересоздаются, теряют фокус и текст. Жалоба описывает ровно то, что случилось после первой попытки исправления, — типичная ситуация, когда неверная починка ключа заменяет одну ошибку другой.

**2. Ошибка, мешающая сортировке.**

`notes.sort(...)` сортирует массив **на месте** и возвращает тот же массив. `setNotes` получает ту же ссылку, `Object.is(old, new)` — `true`, React отказывается от обновления (3.3, 3.10). Сортировка «иногда работает» только потому, что что-то другое вызывает рендер, и тогда `FlatList` видит уже мутированный массив. Исправление — `[...notes].sort(...)`: копия создаётся до сортировки (1.5; `toSorted` короче, но его доступность зависит от конфигурации Hermes). Сюда же: `onDelete` и `sortByDate` читают `notes` из замыкания рендера — надёжнее функциональная форма `setNotes((prev) => ...)`.

**3. Исправление.**

```jsx
function NotesScreen() {
  const [notes, setNotes] = useState([]);

  async function refresh() {
    setNotes(await api.loadNotes());          // id приходит с сервера
  }

  function sortByDate() {
    setNotes((prev) => [...prev].sort((a, b) => b.createdAt - a.createdAt));
  }

  const deleteNote = useCallback(
    (id) => setNotes((prev) => prev.filter((n) => n.id !== id)),
    [],
  );

  return (
    <FlatList
      data={notes}
      keyExtractor={(note) => note.id}
      renderItem={({ item }) => <NoteRow note={item} onDelete={deleteNote} />}
      ListHeaderComponent={<Button title="По дате" onPress={sortByDate} />}
    />
  );
}

function NoteRow({ note, onDelete }) {
  const [important, setImportant] = useState(note.important);
  return (
    <View>
      <TextInput defaultValue={note.text} />
      <Switch value={important} onValueChange={setImportant} />
      <Button title="Удалить" onPress={() => onDelete(note.id)} />
    </View>
  );
}
```

Ключ — серверный `id`: стабилен между рендерами и между загрузками, и состояние, нативное поле и отметка следуют за заметкой при удалении и сортировке.

**Почему `localId` из `Math.random()` не годится.** Он стабилен в пределах одного ответа, но генерируется заново при каждом `refresh`. Для React каждая загрузка — полностью новый набор элементов: все строки перемонтируются, редактируемый текст пропадает, фокус и клавиатура теряются. Идентификатор должен идентифицировать **сущность**, а не конкретную загрузку. Если сервер не присылает `id`, его нужно присвоить при создании сущности (на клиенте — при создании черновика) и хранить вместе с ней, а не вычислять при получении.

Оставшийся вопрос, который стоит назвать, но не решать здесь: `important` как локальная копия пропса расходится с данными, если сервер вернёт новое значение для той же заметки. Это «записать пропс в стейт» — тема 3.7. А если список переведут на FlashList, локальное состояние строки начнёт переезжать уже из-за рециклинга — 5.4.

**Вклад в проект (P3).** Списки RN Academy используют ключи из доменных идентификаторов; правило «ключ — идентичность сущности, не позиции и не загрузки» записано в правилах проекта.
</details>
