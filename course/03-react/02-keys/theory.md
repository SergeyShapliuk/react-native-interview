# 3.2 Роль `key` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как убрать предупреждение о ключах» — а на вопрос, **за чем следует состояние компонента, когда список меняется**.

---

## 1. Что это

**`key`** — специальный атрибут элемента, по которому React сопоставляет детей одного родителя между рендерами. Это не пропс: компонент его не получает, и прочитать `props.key` нельзя.

В 3.1 было сформулировано правило: тот же `type` на той же позиции — тот же fiber. `key` меняет вторую половину правила: **среди соседей с ключами позицией считается ключ, а не порядковый номер.**

```jsx
{lessons.map((lesson) => (
  <LessonRow key={lesson.id} lesson={lesson} />
))}
```

### Ключевая формулировка урока

> **`key` отвечает не на вопрос «нужно ли перерисовать», а на вопрос «это тот же экземпляр или другой». Состояние, ref и нативный view следуют за ключом.**

---

## 2. Как это работает

### Сопоставление детей

Когда у родителя меняются дети, React сопоставляет новый список элементов со старым списком fiber:

- **с ключами** — по ключу: элемент с ключом `b` получает fiber, у которого был ключ `b`, где бы он ни стоял раньше. Переставленный элемент **перемещается** вместе со своим состоянием. Элемент с ключом, которого раньше не было, монтируется; fiber, чьего ключа больше нет, размонтируется;
- **без ключей** — по индексу: первый новый элемент получает первый старый fiber, второй — второй, и так далее. Состояние остаётся **на месте**, а данные (пропсы) приходят новые.

Тип при этом проверяется по-прежнему: совпадение ключа при разном `type` даёт размонтирование и монтирование (3.1).

### Что происходит при `index` в качестве ключа

`key={index}` — это то же, что отсутствие ключа, только без предупреждения. Рассмотрим список из трёх строк, каждая со своим локальным состоянием черновика:

```
до:     key=0 → A [ ]        key=1 → B [заметка]      key=2 → C [ ]
удалили A
после:  key=0 → B [ ]        key=1 → C [заметка]
```

Удаление первого элемента сдвинуло данные на позицию вверх, а состояние осталось привязанным к ключам `0` и `1`. Fiber с ключом `1` (бывший B) получил пропсы C — и черновик «заметка» теперь показан в строке C. Fiber с ключом `2` размонтирован, хотя удалили A.

С ключом из идентификатора:

```
до:     key=a → A [ ]        key=b → B [заметка]      key=c → C [ ]
удалили A
после:  key=b → B [заметка]  key=c → C [ ]
```

Размонтирован именно A, B и C сохранили свои состояния. Оба сценария проверены экспериментом на React 19.2.

Те же рассуждения применимы к **вставке в начало** (каждая строка получает состояние той, что раньше стояла на её месте, а последняя монтируется заново) и к **сортировке** (состояние остаётся на местах, данные переставляются).

### `index` корректен, когда…

…список никогда не меняет порядок и состав за время жизни родителя **и** у элементов нет собственного состояния, ref или анимаций. Статичный список пунктов меню, набор звёзд рейтинга. Как только появляется удаление, вставка не в конец или сортировка, `index` перестаёт быть идентичностью.

### Случайный ключ

```jsx
{items.map((item) => <Row key={Math.random()} item={item} />)}
```

Ключ, меняющийся на каждый рендер, говорит React: «все элементы новые». Каждый рендер родителя размонтирует все строки и монтирует их заново — со всеми эффектами, ref и нативными view. Это хуже отсутствия ключа: без ключа состояние хотя бы держится на позиции. То же самое происходит с ключом, вычисленным из нового объекта (`key={JSON.stringify(item)}` при изменении любого поля) или с идентификатором, который генерируется при каждой загрузке данных.

### Ключ вне списка: сброс состояния

Ключ работает у любого элемента, не только в `map`. Смена ключа — это «на этой позиции теперь другой экземпляр»:

```jsx
<LessonNoteForm key={lessonId} lessonId={lessonId} />
```

При смене `lessonId` форма размонтируется и монтируется заново: черновик, ошибки валидации, фокус — всё начинается с нуля. Без единой строки кода сброса и без эффекта, который «заметит» смену пропса. Как этот приём заменяет эффекты — 3.7.

### Ключ на фрагменте

Если элемент списка — несколько соседних узлов без обёртки, ключ ставится на фрагмент в полной форме:

```jsx
{sections.map((s) => (
  <Fragment key={s.id}>
    <SectionHeader section={s} />
    <SectionBody section={s} />
  </Fragment>
))}
```

Короткая запись `<>...</>` ключ не принимает.

### Уникальность — среди соседей

Ключ должен быть уникальным только среди детей одного родителя. Два списка на одном экране могут использовать одни и те же идентификаторы. Обратное тоже верно: ключ не переносит состояние **между родителями** — элемент с тем же ключом, оказавшийся в другом родителе, будет смонтирован заново.

---

## 3. Почему это важно

**Ошибка ключа — это ошибка данных, а не производительности.** Неверный ключ не замедляет приложение заметно — он показывает пользователю чужие данные: черновик не в той строке, отмеченный чекбокс не у того элемента, анимация удаления не на той строке. Такие дефекты трудно воспроизвести: они проявляются только при определённой последовательности действий (ввести, затем удалить выше).

**Ключ — инструмент управления временем жизни.** То же самое свойство, которое ломает список с `index`, делает ключ самым простым способом сбросить состояние поддерева. Понимание ключа как идентичности даёт оба навыка сразу.

**Ключ определяет, что делает рендерер.** Перемещение по ключу — это перемещение существующего host-узла; смена ключа — уничтожение и создание. В RN это разница между переносом нативного view и пересозданием view с изображениями, фокусом и прокруткой.

---

## 4. Где это в React Native

### `keyExtractor` у `FlatList`

`FlatList` и `SectionList` сами ставят ключи ячейкам, и `keyExtractor` — это тот же `key`. Поведение по умолчанию (`@react-native/virtualized-lists` 0.87): взять `item.key`, если есть, иначе `item.id`, иначе `String(index)`. Последний вариант — тот же `index` как ключ, со всеми последствиями. Поэтому `keyExtractor={(_, i) => String(i)}` — не «явная настройка», а та же ошибка, записанная руками.

Ключ в `FlatList` важен вдвойне: по нему список ещё и отслеживает ячейки при виртуализации, и нестабильный ключ даёт перемонтирование ячеек при каждом обновлении данных — с мерцанием изображений.

### `TextInput` в строке списка

Классический симптом урока: значение в поле ввода «прыгает» на соседнюю строку после удаления элемента. Если `TextInput` неконтролируемый, текст хранится в нативном поле — то есть в нативном view, который следует за ключом. С ключом из индекса нативное поле остаётся на позиции, а строка, к которой оно относилось, уехала.

### Анимации

Анимация удаления или появления (`LayoutAnimation`, `entering`/`exiting` в Reanimated) привязана к экземпляру. С неверным ключом исчезает не та строка, которую удалили, а последняя — потому что именно её fiber размонтирован.

### Ключ и рециклинг — разные механизмы

FlashList и другие рециклирующие списки переиспользуют **одни и те же** экземпляры компонентов ячеек для разных элементов данных: ячейка, ушедшая за экран, получает пропсы нового элемента. Это сознательный обход того, что делает ключ, ради производительности. Следствие: локальное состояние ячейки в рециклирующем списке «переезжает» на другой элемент **даже с правильным ключом**. Как с этим работать — 5.4; здесь важно не переносить на FlashList ожидание «состояние следует за ключом».

## 5. Типичные ошибки

**`index` как ключ в изменяемом списке.** Возникает потому, что предупреждение исчезает, и на первом прогоне ничего не ломается: дефект виден только после удаления или вставки не в конец, и только если у строки есть состояние. Исправление — идентификатор из данных.

**«Ключ нужен для производительности».** Возникает из того, что о ключах часто рассказывают в контексте оптимизации списков. Ключ — прежде всего корректность: какой экземпляр соответствует каким данным. Производительность — следствие: верный ключ позволяет перемещать узлы вместо пересоздания.

**Ключ из изменяемого поля.** `key={lesson.title}` или составной ключ из названия и статуса. Возникает, когда у данных нет идентификатора, и берут «что-нибудь уникальное». При переименовании урока строка перемонтируется, при совпадении названий ключи дублируются. Если идентификатора нет, его нужно создать **при получении данных** и сохранить вместе с ними, а не вычислять при рендере.

**Генерация идентификатора при рендере.** `key={uuid()}` или `items.map((x) => ({ ...x, id: uuid() }))` внутри компонента. Возникает из попытки «дать данным id» в последнем возможном месте. Эффект тот же, что у случайного ключа: всё перемонтируется на каждом рендере.

**Ожидание, что ключ переносит состояние между родителями.** Возникает из модели «ключ — глобальный идентификатор». Ключ сравнивается только среди соседей; перенос элемента в другую ветку дерева — монтирование заново.

**Ожидание, что ключ спасёт состояние ячейки в рециклирующем списке.** Возникает из переноса модели обычного списка на FlashList. Рециклинг переиспользует экземпляр для другого элемента, и ключ этого не отменяет.

## 6. Trade-offs

### Сброс через ключ против точечного сброса

`key={lessonId}` сбрасывает **всё** поддерево: состояние, ref, эффекты, нативные view. Это просто и надёжно — невозможно забыть сбросить одно из полей. Цена — полная стоимость монтирования. Для формы из пяти полей она незаметна; для поддерева с видеоплеером или длинным списком — это повторная загрузка и потеря прокрутки. Тогда правильнее сбросить только нужную часть состояния (3.7), а тяжёлую часть оставить.

### `index` против идентификатора

Идентификатор требует, чтобы он был у данных. Иногда его нужно создать — при получении ответа сервера или при создании черновика на клиенте, — и это работа на уровне модели данных, а не компонента. `index` бесплатен и корректен ровно для статичных списков без состояния. Решение принимается не по удобству, а по вопросу: может ли этот список измениться иначе, чем добавлением в конец, пока экран открыт?

### Ключ против рециклинга

Обычный список с правильными ключами даёт корректность «из коробки» и платит монтированием ячеек при прокрутке. Рециклирующий список экономит монтирование и перекладывает корректность на автора ячейки: состояние в ячейке становится обязанностью сбрасывать. Это trade-off блока 05; здесь достаточно знать, что он существует.
