# 3.19 `useSyncExternalStore` и tearing — theory

> 🔴 SENIOR. Семь углов разбора с акцентом на trade-offs. Урок закрывает блок: он отвечает на вопрос, **что ломается в подписке на внешний источник, когда рендер становится прерываемым**, и почему для этого понадобился отдельный хук.

---

## 1. Что это

**Внешний стор** — любое изменяемое состояние, которое живёт вне React: модуль с переменной и списком подписчиков, стор Zustand или Redux, нативный модуль с состоянием (сеть, ориентация, плеер), хранилище вроде MMKV. React о его изменениях не знает, пока ему не сообщат.

**Tearing** («разрыв») — ситуация, когда один закоммиченный экран показывает данные из **двух разных версий** внешнего стора: часть компонентов прочитала старое значение, часть — новое.

**`useSyncExternalStore(subscribe, getSnapshot)`** — хук React 18+, который подписывает компонент на внешний стор так, что один рендер всегда видит одну версию данных.

```js
const isOnline = useSyncExternalStore(networkStore.subscribe, networkStore.getSnapshot);
```

### Ключевая формулировка урока

> **Прерываемый рендер может прочитать внешний источник дважды — до и после его изменения. `useSyncExternalStore` гарантирует, что один рендер видит одну версию, и платит за это синхронностью.**

---

## 2. Как это работает

### Как tearing возникает в однопоточном JS

В синхронной модели рендер проходит всё дерево одним непрерывным куском (3.1). Пока он идёт, никакой другой код не выполняется — значит, внешний стор не может измениться посреди рендера. Все компоненты читают одну и ту же версию.

Прерываемый рендер (3.17) уступает поток между компонентами. В этих паузах выполняются другие задачи — таймеры, ответы сети, события нативных модулей, — и любая из них может изменить внешний стор. Компоненты, отрендеренные до паузы, прочитали старое значение; компоненты после паузы — новое. Затем commit применяет всё вместе.

Эксперимент на React 19.2: переход рендерит 200 компонентов, каждый читает значение стора напрямую (`store.get()` в теле), стор меняется с `0` на `1` через 15 мс после начала рендера. Закоммиченный результат:

```
прямое чтение:          35 компонентов показывают 0, 165 — 1
useSyncExternalStore:   200 компонентов показывают 1
```

Экран с прямым чтением **закоммичен разорванным** — и останется таким, пока что-нибудь не вызовет следующий рендер. С `useSyncExternalStore` React обнаружил, что снимок изменился во время рендера, и отрендерил заново, синхронно, — все компоненты увидели одну версию.

### Два дефекта подписки через `useEffect` + `setState`

Долгие годы подписка на внешний стор писалась так:

```js
function useNetworkStatus() {
  const [status, setStatus] = useState(networkStore.get());
  useEffect(() => networkStore.subscribe(() => setStatus(networkStore.get())), []);
  return status;
}
```

У неё два дефекта.

**Изменение между рендером и подпиской.** Значение прочитано при рендере, подписка создана в эффекте — после commit, а для обычных обновлений и после показа кадра (3.6). Если стор изменился в этом окне, подписчик ещё не существовал, событие потеряно. Эксперимент: стор меняется из layout-эффекта соседнего компонента, то есть после рендера, но до пассивных эффектов. Наивная реализация навсегда осталась со старым значением; `useSyncExternalStore` отрендерил компонент повторно с новым. Исправить это в ручной реализации можно — перечитать значение в эффекте при подписке, — но это то, о чём легко забыть, и это всё равно даёт лишний рендер со старым значением.

**Tearing при прерываемом рендере.** Каждый компонент держит свою копию в `useState`. В переходе одни компоненты получили обновление копии раньше, другие позже, а при прямом чтении в рендере — как в эксперименте выше. Ручная реализация не может это исправить в принципе: она не знает, что рендер был прерван.

### Контракт `subscribe` / `getSnapshot`

```js
function createNetworkStore() {
  let status = 'online';
  const listeners = new Set();
  return {
    subscribe(listener) {                 // подписать, вернуть отписку
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
    getSnapshot() {                       // вернуть текущий снимок
      return status;
    },
    set(next) {
      status = next;
      listeners.forEach((l) => l());
    },
  };
}
```

Что делает React с этими двумя функциями:

- **`getSnapshot` вызывается при рендере** — значение компонента берётся из снимка, а не из копии в состоянии;
- **если рендер был прерываемым, перед commit React вызывает `getSnapshot` ещё раз** и сравнивает с прочитанным при рендере (`Object.is`). Если отличается — стор изменился в паузе рендера, и React рендерит заново **синхронно**, отказываясь от прерываемости. Синхронный рендер такой проверки не требует: в нём пауз нет;
- **`subscribe` вызывается после commit**, и React сразу проверяет, не изменился ли снимок с момента рендера, — это закрывает первый дефект ручной подписки;
- **при событии стора** React вызывает `getSnapshot` и рендерит компонент, только если снимок изменился по `Object.is`.

`subscribe` должен быть стабильной функцией: новая функция на каждый рендер приводит к отписке и повторной подписке после каждого рендера. Методы стора, объявленные вне компонента, стабильны по построению.

### `getSnapshot` обязан быть стабильным

```js
getSnapshot: () => ({ ...state })        // новый объект на каждый вызов
```

React вызывает `getSnapshot` несколько раз и сравнивает результаты. Новый объект — всегда «не равно»: React решает, что стор изменился, рендерит снова, снова получает новый объект — и так до ошибки. Эксперимент на React 19.2:

```
The result of getSnapshot should be cached to avoid an infinite loop
Maximum update depth exceeded
```

Правило: пока стор не изменился, `getSnapshot` возвращает **тот же** объект. Стор, хранящий состояние иммутабельно (новый объект на каждое изменение, 1.13), удовлетворяет этому автоматически: снимок — это ссылка на текущее состояние.

### Селектор

Компоненту обычно нужна часть состояния стора. Селектор применяется к снимку:

```js
const progress = useSyncExternalStore(
  playerStore.subscribe,
  () => playerStore.getSnapshot().progress,    // примитив — стабилен по значению
);
```

Если селектор возвращает примитив, всё просто: компонент рендерится, только когда изменилось выбранное значение. Если селектор возвращает новый объект или массив (`state.lessons.filter(...)`), получится тот же бесконечный цикл, что выше. Поэтому библиотеки (React Redux, Zustand) поверх `useSyncExternalStore` добавляют мемоизацию селектора и функцию сравнения результата. Цена и правила селекторов — 6.5.

### `getServerSnapshot`

Третий аргумент — снимок для серверного рендера и гидратации: на сервере стор клиента недоступен, и нужно значение, совпадающее с тем, что было отрендерено на сервере. В RN серверного рендера нет, и этот аргумент почти не встречается.

### Обновление из внешнего стора не может быть переходом

Обновление, пришедшее из `subscribe`, React обрабатывает как синхронное — именно это и гарантирует отсутствие tearing. Обернуть изменение стора в `startTransition` бессмысленно: для компонентов, подписанных через `useSyncExternalStore`, оно всё равно будет синхронным. Если стор изменился во время перехода, React переключается на синхронный рендер.

Это и есть цена: **внешний стор отказывается от преимуществ concurrent rendering** для своих подписчиков. Значение, которое должно обновляться переходом (фильтр длинного списка), держат в состоянии React, а не во внешнем сторе — или используют `useDeferredValue` поверх значения из стора (3.17).

## 3. Почему это важно

**Каждый, кто пишет подписку, пишет её на этот случай.** Хук-обёртка над нативным emitter (3.12), свой маленький стор, подписка на кэш — всё это внешние сторы. Ручная подписка через эффект содержит дефект с ранним изменением всегда, а tearing — как только в приложении появляются переходы.

**Библиотеки состояния сделали этот выбор за вас.** React Redux (с версии 8) и Zustand подписывают компоненты через `useSyncExternalStore`. Понимание механизма объясняет их поведение: почему селектор, возвращающий новый объект, вызывает бесконечные рендеры или предупреждения; почему обновления стора не становятся переходами; почему Context, у которого нет селекторов, рендерит всех подписчиков (3.14).

**Tearing — дефект, который почти невозможно отладить постфактум.** Он проявляется под нагрузкой, при совпадении во времени события и прерванного рендера, и выглядит как «на экране противоречивые данные». Единственная надёжная защита — правильный способ подписки с самого начала.

## 4. Где это в React Native

### Внешних источников в RN больше

- **нативные модули с состоянием** — сеть (онлайн/офлайн, тип соединения), ориентация, состояние аудиоплеера, Bluetooth, геолокация;
- **синхронные хранилища** — MMKV и подобные: значение читается синхронно и может измениться из другого места приложения;
- **собственные сторы** — модуль с состоянием сессии, очередью загрузок, флагами;
- **сторы библиотек** — Zustand, Redux, кэш TanStack Query.

### Хук-обёртка над нативным emitter

Хук из 3.12, переписанный правильно:

```js
let current = 'unknown';
const listeners = new Set();
let nativeSub = null;

const networkStore = {
  subscribe(listener) {
    listeners.add(listener);
    if (nativeSub === null) {                       // первый подписчик — подписаться на модуль
      nativeSub = NetworkModule.addListener('change', (status) => {
        current = status;
        listeners.forEach((l) => l());
      });
    }
    return () => {
      listeners.delete(listener);
      if (listeners.size === 0) {                   // последний ушёл — снять нативную подписку
        nativeSub.remove();
        nativeSub = null;
      }
    };
  },
  getSnapshot() {
    return current;
  },
};

export function useNetworkStatus() {
  return useSyncExternalStore(networkStore.subscribe, networkStore.getSnapshot);
}
```

Подписка на нативный emitter — одна на всё приложение, а не одна на каждый компонент: компоненты подписываются на стор, а стор — на нативный модуль, лениво, при первом подписчике, и снимает подписку при последнем. На верхнем уровне модуля побочных эффектов нет (1.10). Жизненный цикл нативных подписок подробно — блок 09.

Начальное значение `'unknown'` — честное: до первого события нативного модуля состояние сети неизвестно. Если модуль позволяет прочитать текущее значение синхронно, его читают при создании стора.

### Чего не делать в RN

- **подписка на нативный emitter в каждом компоненте через `useEffect`** — N подписок вместо одной, каждая с дефектом раннего изменения;
- **`getSnapshot`, собирающий объект из нескольких нативных значений** — `{ isOnline, type }` на каждый вызов — бесконечный цикл; объект нужно пересоздавать только в обработчике события;
- **изменяемое состояние модуля, прочитанное прямо в рендере** — это и есть прямое чтение из эксперимента: tearing при первом же переходе.

## 5. Типичные ошибки

**«`useEffect` + `setState` — то же самое».** Возникает потому, что так подписывались годами, и в синхронной модели это почти работало. Два дефекта: изменение между рендером и подпиской теряется; при прерываемом рендере возможен tearing.

**«Tearing невозможен в однопоточном JS».** Возникает из смешения «один поток» и «один непрерывный кусок работы». Прерываемый рендер уступает поток, и в паузах выполняется код, меняющий стор.

**Новый объект в `getSnapshot`.** Возникает из привычки возвращать «копию для безопасности». Результат — бесконечный цикл рендеров.

**Селектор, возвращающий новый массив, в голом `useSyncExternalStore`.** Та же ошибка в другой форме. Нужна мемоизация селектора или библиотечный хук с функцией сравнения.

**`subscribe`, объявленный в теле компонента.** Новая функция на каждый рендер — переподписка после каждого рендера.

**Ожидание, что обновление стора можно сделать переходом.** Для подписчиков `useSyncExternalStore` оно синхронное.

**Внешний стор там, где хватает состояния React.** Возникает из моды на сторы. Состояние, нужное одному экрану, живёт в нём (3.8); внешний стор нужен, когда источник действительно внешний или общий.

## 6. Trade-offs

### Синхронность против преимуществ concurrent rendering

`useSyncExternalStore` гарантирует согласованность ценой синхронных обновлений: изменение стора, пришедшее во время перехода, превращает переход в синхронный рендер. Для данных, которые меняются редко или должны быть согласованы (сеть, сессия, корзина), это правильная цена. Для данных, обновление которых нужно делать прерываемым, — состояние React и переходы.

### Свой стор против библиотеки

Свой стор на 20 строк с `useSyncExternalStore` прозрачен и достаточен для одного-двух источников (сеть, ориентация). Для состояния приложения с селекторами, devtools, middleware и персистентностью — библиотека, которая делает то же поверх того же хука, но решает задачи сравнения селекторов, батчинга уведомлений и отладки. Выбор между ними — урок 6.3.

### Context против внешнего стора

Context — доставка значения из состояния React, без селекторов: каждый потребитель рендерится при изменении `value` (3.14), зато обновления могут быть переходами. Внешний стор — подписка с селектором: компонент рендерится, только если изменилась его часть, но обновления синхронные. Частые изменения, читаемые частично, — стор; редкие, читаемые целиком, — Context.
