# 3.19 `useSyncExternalStore` и tearing — practice

## Проверка понимания

Вопросы уровня собеседования на Senior. Правильный ответ требует назвать, **когда компонент прочитал стор, когда подписался и что произошло между этими моментами**.

---

**1. Как tearing возникает в однопоточном JS?**

<details>
<summary>Ответ</summary>

Однопоточность гарантирует, что два куска JS не выполняются одновременно, но не гарантирует, что рендер — **один** кусок.

В синхронном рендере React обходит дерево непрерывно, и внешний стор не может измениться посреди обхода: нет кода, который мог бы его изменить. В прерываемом рендере (переход, отложенное значение, 3.17) React уступает поток между компонентами. В паузах выполняются таймеры, ответы сети, события нативных модулей — и они меняют стор. Компоненты до паузы прочитали старое значение, после паузы — новое, а commit применяет результат целиком.

Эксперимент на React 19.2: 200 компонентов в переходе читают стор напрямую, стор меняется через 15 мс после начала рендера — закоммичено 35 значений `0` и 165 значений `1`. С `useSyncExternalStore` — 200 значений `1`.

**Ответ «невозможен, JS однопоточный»** вскрывает смешение «один поток» и «одна непрерывная задача».

**Ответ «возможен, если стор меняется в другом потоке»** — нативная сторона может менять своё состояние в другом потоке, но в JS оно приходит событием, то есть задачей на JS-потоке — в паузе рендера.
</details>

---

**2. Почему `getSnapshot: () => ({ ...state })` ломает приложение?**

<details>
<summary>Ответ</summary>

React вызывает `getSnapshot` несколько раз за рендер — при чтении, перед commit для проверки согласованности, после подписки — и сравнивает результаты через `Object.is`. Новый объект на каждый вызов — всегда «не равно». React считает, что стор изменился, рендерит снова, снова получает новый объект, и так до остановки. Эксперимент на React 19.2:

```
The result of getSnapshot should be cached to avoid an infinite loop
Maximum update depth exceeded
```

`getSnapshot` обязан возвращать **тот же** объект, пока стор не изменился. Стор с иммутабельным состоянием (новый объект только при изменении, 1.13) даёт это автоматически: снимок — ссылка на текущее состояние. Если компоненту нужна производная структура, её либо вычисляют в компоненте (с `useMemo`, 3.11), либо используют селектор с мемоизацией и функцией сравнения — как в библиотеках (6.5).

**Ответ «копия защищает от мутаций»** — защищает ценой бесконечного цикла; защита от мутаций — иммутабельность самого стора.
</details>

---

**3. Хук подписки написан через `useState(store.get())` и `useEffect(() => store.subscribe(...), [])`. В каком сценарии он навсегда покажет устаревшее значение, даже без concurrent rendering?**

<details>
<summary>Ответ</summary>

Когда стор меняется **между рендером и подпиской**. Значение прочитано при рендере; подписка создана в пассивном эффекте — после commit, обычно после показа кадра (3.6). Если в этом окне что-то изменило стор (layout-эффект другого компонента, синхронный колбэк нативного модуля, задача, выполнившаяся до пассивных эффектов), событие ушло, когда подписчика ещё не было. Компонент остаётся со старым значением до следующего события стора — а оно может не прийти никогда.

Эксперимент на React 19.2: стор меняется из layout-эффекта соседнего компонента. Наивная реализация осталась с `online` навсегда; `useSyncExternalStore` после подписки проверил снимок, увидел `offline` и отрендерил компонент повторно.

Ручное исправление — перечитать стор в эффекте сразу после подписки (`setStatus(store.get())`) — работает, но даёт рендер со старым значением и не решает tearing при прерываемом рендере.

**Ответ «такого не бывает, эффект выполняется сразу после рендера»** вскрывает модель «эффект = продолжение рендера» (3.3, 3.6).
</details>

---

**4. Команда хочет обновлять фильтр списка из внешнего стора через `startTransition`, чтобы ввод оставался отзывчивым. Что произойдёт?**

<details>
<summary>Ответ</summary>

Ничего из ожидаемого: для компонентов, подписанных через `useSyncExternalStore`, обновление стора обрабатывается синхронно независимо от `startTransition`. Это не ограничение реализации, а цена гарантии: прерываемый рендер с внешним стором — как раз условие tearing. Если стор меняется во время перехода, React переключается на синхронный рендер.

Варианты:

- **держать фильтр в состоянии React** — тогда его обновление можно сделать переходом (3.17);
- **отложить значение после чтения** — `const deferredFilter = useDeferredValue(filterFromStore)`: подписка синхронна, а тяжёлый рендер списка — от отложенной копии;
- **решить, что фильтр вообще не принадлежит внешнему стору** — если он нужен одному экрану, это локальное состояние (6.1).

**Ответ «переход сработает, это же обычный `setState`»** вскрывает незнание того, что изменение стора — не `setState`.
</details>

## Задание — хук над эмулированным нативным emitter

**Дано.** Нативного модуля сети в P3 ещё нет, поэтому он эмулируется:

```js
// fakeNetworkModule.js
const handlers = new Set();
export const FakeNetworkModule = {
  addListener(event, handler) {
    handlers.add(handler);
    return { remove: () => handlers.delete(handler) };
  },
  emit(status) { handlers.forEach((h) => h(status)); },   // для тестов и dev-меню
};
```

Текущий хук в RN Academy:

```js
export function useNetworkStatus() {
  const [status, setStatus] = useState('unknown');
  useEffect(() => {
    const sub = FakeNetworkModule.addListener('change', setStatus);
    return () => sub.remove();
  }, []);
  return status;
}
```

Хук вызывают шапка, баннер «Нет сети», кнопка загрузки урока и каждая ячейка списка уроков (иконка «доступен офлайн»).

**Требуется.**

1. Найти дефекты текущего хука: число нативных подписок, поведение при монтировании, поведение при переходах.
2. Переписать на стор с `useSyncExternalStore`: одна нативная подписка на приложение, ленивая, без побочных эффектов на уровне модуля.
3. Ячейкам списка нужен не статус, а булево «офлайн ли». Добавить селектор так, чтобы ячейки не рендерились при смене `wifi` на `cellular`.
4. Написать тест стора без React: подписка, отписка последнего подписчика снимает нативную подписку, `getSnapshot` возвращает то же значение между событиями.

---

<details>
<summary>Разбор</summary>

**1. Дефекты.**

- **N нативных подписок.** Каждый вызов хука — свой `addListener`. Шапка, баннер, кнопка и каждая видимая ячейка — десятки слушателей одного события. В реальном нативном модуле это десятки обращений к нативной стороне при монтировании списка.
- **`'unknown'` при каждом монтировании.** Каждый новый компонент начинает с `'unknown'`, даже если статус давно известен: новая ячейка при прокрутке покажет «неизвестно», пока не придёт следующее событие сети — возможно, никогда. Это дефект «изменение до подписки» в предельной форме: всё, что было до монтирования, потеряно.
- **Разные копии статуса.** У каждого компонента своя копия в `useState`. В переходе (например, переключение вкладок списка переходом) одни копии обновятся в прерванном рендере, другие нет — баннер «Нет сети» может соседствовать с активной кнопкой загрузки.

**2. Стор.**

```js
// networkStore.js
import { FakeNetworkModule } from './fakeNetworkModule';

let current = 'unknown';
const listeners = new Set();
let nativeSub = null;

export const networkStore = {
  subscribe(listener) {
    listeners.add(listener);
    if (nativeSub === null) {
      nativeSub = FakeNetworkModule.addListener('change', (status) => {
        if (status === current) return;            // не уведомлять без изменения
        current = status;
        listeners.forEach((l) => l());
      });
    }
    return () => {
      listeners.delete(listener);
      if (listeners.size === 0) {
        nativeSub.remove();
        nativeSub = null;
      }
    };
  },
  getSnapshot() {
    return current;
  },
};

export function useNetworkStatus() {
  return useSyncExternalStore(networkStore.subscribe, networkStore.getSnapshot);
}
```

Что изменилось:

- одна нативная подписка на всё приложение, создаётся при первом подписчике и снимается при последнем; на уровне модуля — только объявления (1.10);
- статус хранится в одном месте и переживает монтирование новых компонентов: новая ячейка сразу получает текущее значение;
- все компоненты читают один снимок — tearing невозможен;
- `subscribe` и `getSnapshot` — методы объекта модуля, стабильны по построению.

Оговорка, которую стоит записать в контракт: когда последний подписчик ушёл, стор перестаёт получать события, и `current` может устареть. Если реальный модуль умеет отдавать текущее значение синхронно, его стоит читать при повторной подписке; если нет — сбрасывать в `'unknown'`. Решение зависит от модуля и принимается в P4 с реальным источником.

**3. Селектор для ячеек.**

```js
export function useIsOffline() {
  return useSyncExternalStore(
    networkStore.subscribe,
    () => networkStore.getSnapshot() === 'offline',
  );
}
```

Селектор возвращает примитив: `true` или `false`. При смене `wifi` на `cellular` снимок селектора остаётся `false`, `Object.is(false, false)` — ячейки не рендерятся. Новые объекты здесь не создаются, поэтому мемоизация селектора не нужна; если бы селектор возвращал объект (`{ isOffline, type }`), понадобились бы мемоизация и сравнение, как в библиотеках (6.5).

**4. Тест стора.**

```js
import { FakeNetworkModule } from './fakeNetworkModule';
import { networkStore } from './networkStore';

test('одна нативная подписка, снимается с последним подписчиком', () => {
  const spy = jest.spyOn(FakeNetworkModule, 'addListener');
  const unsubA = networkStore.subscribe(() => {});
  const unsubB = networkStore.subscribe(() => {});
  expect(spy).toHaveBeenCalledTimes(1);

  unsubA();
  unsubB();
  const unsubC = networkStore.subscribe(() => {});
  expect(spy).toHaveBeenCalledTimes(2);           // переподписка после ухода всех
  unsubC();
});

test('снимок стабилен между событиями и меняется по событию', () => {
  const listener = jest.fn();
  const unsub = networkStore.subscribe(listener);
  FakeNetworkModule.emit('offline');
  const a = networkStore.getSnapshot();
  const b = networkStore.getSnapshot();
  expect(a).toBe('offline');
  expect(a).toBe(b);
  FakeNetworkModule.emit('offline');             // повтор того же статуса
  expect(listener).toHaveBeenCalledTimes(1);
  unsub();
});
```

Тесты не рендерят ни одного компонента: стор — обычный модуль с контрактом `subscribe` / `getSnapshot`. Поведение хука поверх него гарантирует React; тест компонента в P3 проверяет лишь, что баннер появляется после `emit('offline')`.

**Вклад в проект (P3).** В RN Academy состояние сети — внешний стор с одной ленивой нативной подпиской и хуками `useNetworkStatus` и `useIsOffline` поверх `useSyncExternalStore`. Эмулированный модуль заменяется реальным в P4 без изменения хуков; контракт стора и решение о значении после ухода всех подписчиков записаны в README модуля.
</details>
