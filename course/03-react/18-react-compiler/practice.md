# 3.18 React Compiler — practice

## Проверка понимания

Вопросы уровня собеседования на Senior. Правильный ответ требует сказать, **скомпилирована ли функция** и что именно в ней мемоизировано, — а не «компилятор всё сделает».

---

**1. Компонент мутирует пропс при рендере: `lesson.viewed = true`. Что сделает компилятор, и что увидит команда?**

<details>
<summary>Ответ</summary>

Компилятор обнаружит мутацию значения, пришедшего извне (пропсы неизменяемы по правилам React), и **не скомпилирует** функцию: она останется в исходном виде, без кэша. Проверено на `babel-plugin-react-compiler` 1.0 — событие `CompileError` с причиной «This value cannot be modified».

Сборка при этом **пройдёт успешно**. Команда не увидит ничего, если не смотрит:

- в линтер — `eslint-plugin-react-hooks` 7 подсветит то же нарушение правилом `immutability`;
- в лог компилятора (опция `logger` плагина);
- в React DevTools — у компонента не будет отметки скомпилированного.

Последствие: компонент работает как раньше, но без оптимизации, которую от компилятора ждут. Если ручную мемоизацию вокруг него удалили «потому что теперь есть компилятор», компонент стал медленнее, чем до внедрения.

**Ответ «компилятор выдаст ошибку сборки»** — не по умолчанию.

**Ответ «компилятор исправит мутацию»** — компилятор не переписывает логику, он только добавляет кэш там, где код соблюдает правила.
</details>

---

**2. Список уроков, строка — обычный компонент без `memo`. Включили компилятор. Пользователь отмечает один урок пройденным. Сколько строк отрендерится?**

<details>
<summary>Ответ</summary>

**Все видимые.** Проверено экспериментом на React 19.2: при изменении одного элемента массива с компилятором рендерятся все строки — так же, как без него.

Механизм: компилятор мемоизирует выражение `lessons.map((l) => <LessonRow lesson={l} ... />)` целиком по зависимости `lessons`. Отметка урока даёт новый массив (иммутабельное обновление, 1.13), выражение выполняется заново и создаёт новые элементы **для всех** строк — включая неизменённые, чьи объекты `lesson` те же. Компоненты строк не обёрнуты в `memo`, их пропсы не сравниваются — они рендерятся.

Где компилятор помог: при изменении **постороннего** состояния экрана (ввод в поиск, смена вкладки) строки больше не рендерятся — массив тот же, закэшированные элементы те же, React их пропускает. В эксперименте: без компилятора — обе строки, с компилятором — ни одной.

Чтобы при изменении одного урока рендерилась одна строка, нужен `memo` на компоненте строки — как в 3.11. С компилятором его пропсы (колбэки, стили) уже стабильны, так что `memo` сработает без ручных `useCallback`.

**Ответ «одна, компилятор мемоизирует каждую строку»** вскрывает модель «компилятор = `memo` на всех компонентах».
</details>

---

**3. Почему `useMemo` для объекта, от которого зависит эффект с запросом, иногда стоит оставить и с компилятором — или, лучше, переписать эффект?**

<details>
<summary>Ответ</summary>

Потому что у этой мемоизации **семантическая** роль: эффект должен перезапускаться (и отправлять запрос) только при изменении данных, а не при каждом рендере.

Компилятор мемоизирует объект так же, как `useMemo`, и в типичном случае результат будет тем же. Но мемоизация — это оптимизация, а не гарантия (3.11): ни ручной `useMemo`, ни компилятор не обещают, что значение никогда не пересоздастся. Корректность, опирающаяся на это, хрупка в обоих вариантах. К тому же, если компонент окажется нескомпилированным из-за нарушения где-то в теле, а ручной `useMemo` удалён, — запрос начнёт уходить на каждый рендер.

Лучшее решение — не опираться на стабильность объекта вообще: в зависимостях эффекта примитивы (`[lessonId, lang]`), объект собирается внутри эффекта (3.5). Тогда корректность не зависит ни от `useMemo`, ни от компилятора.

**Ответ «с компилятором `useMemo` не нужен никогда»** вскрывает смешение «мемоизация для скорости» и «стабильность для корректности».
</details>

---

**4. Как проверить, что компилятор действительно компилирует экраны проекта?**

<details>
<summary>Ответ</summary>

Три независимых способа:

- **линтер** — `eslint-plugin-react-hooks` 7 с конфигурацией `recommended`: его правила показывают нарушения, из-за которых функция будет пропущена. Чистый линтер — почти все компоненты скомпилированы;
- **лог компилятора** — опция `logger` у плагина получает события `CompileSuccess`, `CompileError`, `CompileSkip` с именем функции и причиной. Можно собрать отчёт по всему проекту при сборке;
- **React DevTools** — скомпилированные компоненты помечены отметкой в дереве компонентов.

Дополнительно — посмотреть результат трансформации одного файла: импорт `react/compiler-runtime` и вызов `_c(N)` в теле означают, что функция скомпилирована.

И главное — **замер**: компиляция без измеримого выигрыша на целевых сценариях не является результатом (5.10).
</details>

## Задание — включение компилятора в слое P3

**Дано.** Слой P3 RN Academy после 3.11: ячейка списка уроков — `memo` со стабильными `renderItem` и `onToggle` через `useCallback`; экран поиска с `useMemo` на результатах; контекст сессии с мемоизированным `value`. Команда хочет включить компилятор и «удалить всю ручную мемоизацию».

Лог компилятора после включения:

```
CompileSuccess  LessonListScreen
CompileSuccess  LessonRow
CompileSuccess  SearchScreen
CompileError    LessonPlayer      Cannot access refs during render
CompileError    NotesEditor       This value cannot be modified
CompileSuccess  SessionProvider
CompileSkip     legacyFormatter
```

**Требуется.**

1. Для каждого `CompileError` сказать, что, скорее всего, нарушено и что делать: исправить, исключить через `"use no memo"` или оставить.
2. Для каждого места ручной мемоизации решить: удалить, оставить или переписать — и обосновать.
3. Описать, что замерить до и после, чтобы решение «включаем» было обоснованным.
4. Сформулировать правило проекта о мемоизации после включения компилятора.

---

<details>
<summary>Разбор</summary>

**1. Ошибки компиляции.**

- **`LessonPlayer` — «Cannot access refs during render».** В теле компонента читается или пишется `ref.current` — например, текущая позиция воспроизведения выводится из ref, или `renders.current++`. Это нарушение и без компилятора (3.9): значение в ref не вызывает рендер, разметка расходится с ним. Исправить: то, что отображается, — в состояние; чтение ref — в обработчики и эффекты. После исправления компонент скомпилируется.
- **`NotesEditor` — «This value cannot be modified».** Мутация пропса или состояния: например, `note.text = value` вместо нового объекта, или `push` в массив из состояния. Это нарушение иммутабельности (1.13, 3.10), из-за которого и без компилятора возможны потерянные обновления. Исправить.
- **`legacyFormatter` — `CompileSkip`.** Обычная функция, не компонент и не хук: компилятор её и не должен компилировать. Ничего не делать.

`"use no memo"` здесь не нужен ни для чего: обе ошибки — реальные дефекты, которые стоит исправить. Директива — для случаев, когда исправление невозможно сейчас (например, несовместимая библиотека), и с комментарием о причине.

**2. Ручная мемоизация.**

| Место | Решение | Почему |
|---|---|---|
| `useCallback` для `onToggle` и `renderItem` в `LessonListScreen` | можно удалить | компонент скомпилирован; компилятор сохранит стабильность ссылок. Удалять после замера, не до |
| `memo` на `LessonRow` | **оставить** | при изменении одного урока без `memo` рендерятся все видимые строки и с компилятором (эксперимент урока) |
| `useMemo` на результатах поиска | можно удалить | скомпилированный `SearchScreen` закэширует вычисление по тем же зависимостям; если фильтрация вызывается вне компонента (в модуле), — остаётся там |
| `useMemo` на `value` в `SessionProvider` | можно удалить | компонент скомпилирован, `value` будет стабилен при тех же зависимостях |
| мемоизация в `LessonPlayer` и `NotesEditor` | **оставить до исправления** | компоненты не скомпилированы; удаление мемоизации сейчас ухудшит их |
| `useMemo`, на котором держится эффект с запросом (если есть) | **переписать эффект** | семантическая стабильность не должна зависеть от мемоизации (вопрос 3) |

Общий принцип: удалять ручную мемоизацию можно только в **скомпилированных** компонентах и только там, где её роль — скорость, а не корректность.

**3. Замер.**

На одном и том же слабом Android-устройстве, в release-сборке, до и после включения (подробная методика — 5.10):

- ввод в поиск — число рендеров `LessonRow` на символ и время срочного рендера;
- отметка одного урока — число рендеров строк;
- открытие экрана урока — время до первого кадра;
- размер бандла (рантайм компилятора и дополнительный код кэша незначительны, но это стоит видеть).

Ожидание по итогам урока: ввод в поиск — меньше рендеров строк (стабильные ссылки), отметка урока — без изменений (там работает `memo`, а не компилятор), открытие экрана — без существенных изменений.

**4. Правило проекта.**

> После включения React Compiler ручные `useMemo` и `useCallback` в **скомпилированных** компонентах не добавляются ради производительности. `memo` остаётся на ячейках списков и компонентах, получающих элементы коллекций. Стабильность, от которой зависит корректность (эффекты с побочными действиями), обеспечивается примитивами в зависимостях, а не мемоизацией. Нарушения правил React, отмеченные `eslint-plugin-react-hooks` 7, исправляются, а не подавляются; `"use no memo"` — только с комментарием о причине. Отчёт компилятора о пропущенных функциях проверяется в CI.

**Вклад в проект (P3).** В RN Academy включён React Compiler после ручной мемоизации из 3.11; исправлены `LessonPlayer` и `NotesEditor`, из-за которых компилятор их пропускал; `memo` на ячейках оставлен; результат сравнения до и после и список решений по каждому месту ручной мемоизации записаны в README слоя.
</details>
