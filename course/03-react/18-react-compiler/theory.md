# 3.18 React Compiler — theory

> 🔴 SENIOR. Семь углов разбора с акцентом на trade-offs. Урок отвечает не на вопрос «как подключить компилятор» — а на вопрос, **что именно он делает с кодом, на каких допущениях, и что остаётся на ответственности разработчика**.

---

## 1. Что это

**React Compiler** — инструмент сборки, который анализирует компоненты и хуки и автоматически добавляет мемоизацию: значения, колбэки и JSX пересоздаются только при изменении того, от чего они зависят. Версия 1.0 вышла в октябре 2025 года и объявлена готовой для production; работает с React и React Native.

Технически это Babel-плагин (`babel-plugin-react-compiler`): он переводит код компонента во внутреннее представление, анализирует потоки данных и изменяемость и генерирует код с кэшем.

### Ключевая формулировка урока

> **Компилятор не делает рендер быстрее — он автоматически делает то, что делали `useMemo` и `useCallback`, и только для кода, который соблюдает правила React. Код, который их нарушает, компилятор пропускает молча.**

---

## 2. Как это работает

### Что получается после компиляции

Исходный компонент:

```jsx
function LessonRow({ lesson, onOpen }) {
  const style = { padding: 8, opacity: lesson.done ? 0.5 : 1 };
  return (
    <Pressable style={style} onPress={() => onOpen(lesson.id)}>
      <Text>{lesson.title}</Text>
    </Pressable>
  );
}
```

Результат `babel-plugin-react-compiler` 1.0 (сокращено):

```js
import { c as _c } from 'react/compiler-runtime';

function LessonRow(t0) {
  const $ = _c(11);                              // кэш на 11 ячеек, хранится на fiber
  const { lesson, onOpen } = t0;
  const t1 = lesson.done ? 0.5 : 1;
  let t2;
  if ($[0] !== t1) {                             // стиль пересоздаётся, только если изменилась прозрачность
    t2 = { padding: 8, opacity: t1 };
    $[0] = t1; $[1] = t2;
  } else {
    t2 = $[1];
  }
  let t3;
  if ($[2] !== lesson.id || $[3] !== onOpen) {   // колбэк — только при смене id или onOpen
    t3 = () => onOpen(lesson.id);
    /* ... */
  }
  // ... так же для <Text> и <Pressable>
}
```

Что видно:

- **гранулярность — выражение, а не компонент.** Каждый объект, функция и JSX-элемент кэшируется отдельно со своими зависимостями. Компилятор мемоизирует то, что вручную не мемоизирует никто: промежуточные значения, отдельные ветки JSX;
- **зависимости выведены точно** — `lesson.done`, а не весь `lesson`; ошибиться в массиве зависимостей нельзя, его нет;
- **кэш хранится на fiber**, как состояние хуков (3.5) — через `react/compiler-runtime` (React 19; для React 17 и 18 нужен отдельный пакет рантайма).

### Чего компилятор не делает

**Не оборачивает компоненты в `memo`.** Скомпилированный компонент по-прежнему вызывается, когда рендерится родитель. Выигрыш получается иначе: скомпилированный **родитель** возвращает тот же объект JSX-элемента ребёнка, если пропсы ребёнка не изменились, — и React пропускает ребёнка так же, как пропускает `children` с той же ссылкой (3.13).

Эксперимент на React 19.2 со списком из двух строк, где строка — обычный компонент без `memo`:

| Изменение | Без компилятора | С компилятором |
|---|---|---|
| посторонний пропс экрана (`q`) | рендерятся обе строки | не рендерится ни одна |
| изменён один урок в массиве | рендерятся обе строки | рендерятся **обе** строки |

Во втором случае массив `lessons` новый, и `lessons.map(...)` выполняется заново — элементы **всех** строк созданы заново, включая неизменённые. Компилятор мемоизирует выражение `map` целиком по зависимости `lessons`, а не каждую строку отдельно. Чтобы при изменении одного урока рендерилась одна строка, нужен `memo` на компоненте строки — как и без компилятора (3.11).

**Не ускоряет рендер и commit.** Если функция компонента дорогая, она остаётся дорогой при каждом вызове; компилятор только реже её вызывает. Commit и монтирование нативных view (3.3) он не затрагивает вовсе.

### Допущения

Компилятор опирается на **правила React** — те же, что разбирались в блоке:

- **рендер чистый** (3.1, 3.3) — функция компонента не меняет ничего вне себя;
- **пропсы и состояние неизменяемы** (3.10) — их не мутируют, а заменяют;
- **ref не читаются и не пишутся при рендере** (3.9);
- **правила хуков** (3.5) — порядок, верхний уровень, префикс `use`.

Если анализ показывает нарушение, компилятор **не компилирует функцию** — оставляет её как есть. Проверено на `babel-plugin-react-compiler` 1.0:

```jsx
function Mutates({ lesson }) {
  lesson.viewed = true;                 // CompileError: This value cannot be modified
  return <Text>{lesson.title}</Text>;
}

function ReadsRef({ lesson }) {
  const r = useRef(0);
  r.current++;                          // CompileError: Cannot access refs during render
  return <Text>{lesson.title}</Text>;
}
```

Обе функции остались нескомпилированными, **сборка при этом прошла успешно**. Это поведение по умолчанию: компилятор не ломает сборку из-за нарушений, а пропускает функцию. Увидеть пропуск можно только линтером, логом компилятора или в DevTools (у скомпилированных компонентов есть отметка).

### Линтер компилятора

`eslint-plugin-react-hooks` 7 содержит правила, основанные на том же анализе: `immutability`, `refs`, `purity`, `globals`, `set-state-in-render`, `static-components`, `preserve-manual-memoization` и другие (большая часть — в конфигурации `recommended`). Они показывают в редакторе ровно те нарушения, из-за которых компилятор пропустит функцию. Практически: включить линтер 7-й версии и довести код до чистого состояния **до** включения компилятора — тогда пропусков почти не будет.

### Выход из компиляции

Директива `"use no memo"` в начале функции исключает её из компиляции. Это инструмент временного обхода — для компонента, где компилятор выявил проблему, которую пока не исправить, или где поведение после компиляции нужно сравнить с исходным. Постоянное использование — признак кода, нарушающего правила React.

### Ручная мемоизация и компилятор

Существующие `useMemo` и `useCallback` компилятор учитывает и сохраняет. Правило `preserve-manual-memoization` предупреждает, если компилятор не может гарантировать, что ручная мемоизация сохранится с теми же зависимостями. Удалять ручную мемоизацию сразу после включения компилятора не обязательно и не всегда безопасно: часть её может быть нужна по семантике (ниже).

---

## 3. Почему это важно

**Ручная мемоизация — источник ошибок и шума.** Урок 3.11 показал: большая часть ручных `useCallback` бесполезна, а там, где нужна, легко ошибиться в зависимостях или забыть одно звено цепочки. Компилятор снимает этот класс работы целиком — для кода, который соблюдает правила.

**Компилятор делает правила React обязательными на практике.** Раньше нарушение правил (мутация пропса, запись в ref при рендере) «работало» и проявлялось редко. С компилятором такой код молча теряет оптимизацию, а линтер 7-й версии подсвечивает его как ошибку. Команда, внедряющая компилятор, фактически внедряет правила React.

**Молчаливый пропуск опасен ожиданием.** «У нас включён компилятор, мемоизация не нужна» — и при этом половина экранов не скомпилирована из-за нарушений. Без контроля пропусков ожидаемого выигрыша нет, а ручную мемоизацию уже удалили.

## 4. Где это в React Native

### Подключение

Компилятор — Babel-плагин и работает в RN так же, как в вебе: через `babel.config.js` поверх `@react-native/babel-preset`. Состояние на сегодня:

- **Expo SDK 54** включает компилятор в новых проектах;
- **шаблон RN 0.87** (`@react-native-community/template`) компилятор не подключает: `babel.config.js` содержит только пресет RN. Подключение — решение команды;
- **`@react-native/eslint-config` 0.87** уже зависит от `eslint-plugin-react-hooks` 7 — линтер, основанный на анализе компилятора, приходит вместе с конфигурацией RN.

### Где выигрыш заметен

- **инлайн-стили и стрелки в ячейках** — `style={{...}}`, `onPress={() => ...}` перестают быть новыми ссылками на каждый рендер;
- **`renderItem` и пропсы `FlatList`** — функция `renderItem`, объявленная в компоненте, становится стабильной; `FlatList` и его ячейки (`PureComponent`, 3.10) пропускают лишнюю работу;
- **обёртки дизайн-системы** — пропсы, которые раньше требовали `useMemo` у вызывающего.

### Где не поможет

- **виртуализация и рециклинг** (5.4) — компилятор не уменьшает число монтируемых view;
- **commit и Fabric** — монтирование нативных view, layout, передача Shadow Tree;
- **анимации** — значения Reanimated живут вне рендера React (5.7);
- **изменение одного элемента большого списка** — без `memo` на ячейке рендерятся все видимые ячейки (эксперимент выше).

### Библиотеки

Некоторые библиотеки нарушают допущения компилятора: возвращают изменяемые объекты, ожидают мутаций, читают ref при рендере. Правило `incompatible-library` в линтере отмечает известные несовместимые API. Компонент, использующий такую библиотеку, компилятор пропустит или нужно исключить его вручную.

## 5. Типичные ошибки

**«Компилятор оптимизирует всё».** Возникает из маркетинговых формулировок. Он мемоизирует внутри компонентов, соблюдающих правила; нарушающие пропускает; рендер и commit не ускоряет.

**«После компилятора `memo` не нужен нигде».** Возникает из того, что компилятор действительно убирает большую часть ручной мемоизации. Ячейка списка при изменении одного элемента массива по-прежнему выигрывает от `memo` — проверено экспериментом.

**«Компилятор сообщит о проблеме ошибкой сборки».** По умолчанию — нет: функция просто не компилируется. Проблемы видны в линтере и в логах.

**«С компилятором можно мутировать — он разберётся».** Обратное: мутация — причина пропуска компиляции.

**Удаление ручной мемоизации сразу после включения.** Возникает из желания «почистить». Часть мемоизации может быть нужна по семантике, а не для скорости, и часть компонентов может оказаться нескомпилированной.

**«Компилятор меняет поведение рендера».** Корректный по правилам код ведёт себя так же; меняется только частота пересоздания значений. Если поведение изменилось — код опирался на что-то, что правила запрещают (например, на то, что объект пересоздаётся каждый рендер).

## 6. Trade-offs

### Меньше кода против наглядности

С компилятором исходный код компонента проще: нет `useMemo`, `useCallback`, массивов зависимостей. Цена — мемоизация невидима. Чтобы понять, почему компонент рендерится или не рендерится, нужно знать, скомпилирован ли он и что компилятор посчитал зависимостями. Отладка «почему не обновилось» иногда требует смотреть скомпилированный код.

### Где ручная работа остаётся

- **семантическая стабильность** — значение, от которого зависит эффект с побочным действием (запрос, подписка), должно меняться только при изменении данных. Компилятор мемоизирует так же, как `useMemo`, — это оптимизация, а не гарантия (3.11). Надёжнее примитивы в зависимостях эффекта (3.5);
- **`memo` на ячейках больших списков** — для случая изменения одного элемента массива;
- **дорогие вычисления вне компонентов** — модульные функции, селекторы стора (6.5): компилятор работает только с компонентами и хуками;
- **внешние сторы** — подписка с селектором и сравнение результата — забота `useSyncExternalStore` и библиотеки (3.19), а не компилятора.

### Решение о внедрении

Компилятор — изменение сборки всего приложения. Для существующего проекта разумный порядок:

1. линтер 7-й версии и исправление нарушений правил;
2. включение компилятора — при необходимости постепенно (плагин поддерживает режимы выбора компилируемых файлов);
3. проверка пропусков по логу и DevTools;
4. замер (5.10) на тех же сценариях, что до включения;
5. удаление ручной мемоизации — только там, где замер и анализ показывают, что она не нужна по семантике.
