# 3.17 Suspense и concurrent features — practice

## Проверка понимания

Вопросы уровня собеседования на Senior. Правильный ответ требует назвать, **какая работа прерываема, какая нет**, и что пользователь видит в каждый момент.

---

**1. Экран поиска: поле ввода и список из 300 результатов. Один компонент `ResultRow` тратит 1 мс на рендер. Другой экран: одна диаграмма прогресса, которая тратит 200 мс. В каком случае `useTransition` поможет, а в каком нет?**

<details>
<summary>Ответ</summary>

**Список — поможет.** 300 строк по 1 мс — 300 единиц работы. В прерываемом цикле React уступает поток между ними примерно каждые 5 мс, проверяет, не пришёл ли новый ввод, и если пришёл — бросает устаревший рендер списка и рендерит поле срочно. Поле отзывается на каждый символ, список догоняет.

**Диаграмма — не поможет.** 200 мс — это одна единица работы: функция одного компонента. Уступить внутри обычного JS-вызова React не может (1.20). Переход отложит начало этих 200 мс, но когда они начнутся, ввод будет ждать до конца. Решение — удешевить вычисление: мемоизировать по входным данным (3.11), вынести расчёт из рендера, упростить или разбить на компоненты.

Общий принцип: time slicing работает между компонентами, а не внутри одного.

**Ответ «поможет в обоих случаях, переход же прерываемый»** вскрывает модель «React прерывает любой JS».

**Ответ «не поможет ни в одном, JS однопоточный»** вскрывает обратное: однопоточность не мешает чередовать работу между единицами.
</details>

---

**2. Переход между уроками: компонент урока приостанавливается на загрузке. Что видит пользователь, если обновление `lessonId` обычное, и если оно обёрнуто в `startTransition`?**

<details>
<summary>Ответ</summary>

**Обычное обновление.** Ближайшая граница `<Suspense>` сразу заменяет содержимое на fallback: старый урок исчезает, показывается скелетон. Когда данные готовы, React показывает новый урок — причём уже показанный fallback он держит около 300 мс, чтобы не мигать (в эксперименте на React 19.2 данные пришли через 50 мс, урок появился через ~320 мс).

**Переход.** React не прячет уже показанное: старый урок остаётся на экране, `isPending` — `true` (можно показать индикатор или приглушить содержимое), и когда новый урок готов — экран переключается сразу на него. Скелетона нет. Проверено: через 10 мс после переключения на экране старый урок с пометкой ожидания, после загрузки — новый.

Выбор зависит от того, что честнее для пользователя: при навигации к **другой** сущности старое содержимое может ввести в заблуждение (пользователь нажал «урок 3», а видит урок 2), и тогда нужен явный индикатор. При обновлении той же сущности переход почти всегда лучше.

**Ответ «одинаково, Suspense всегда показывает fallback»** вскрывает незнание связи Suspense и переходов.
</details>

---

**3. Почему `use(fetchLesson(lessonId))` в теле компонента оставляет экран в fallback навсегда?**

<details>
<summary>Ответ</summary>

`fetchLesson(lessonId)` создаёт **новый** промис при каждом вызове компонента. `use` приостанавливает рендер на этом промисе. Когда он выполнится, React рендерит компонент снова — и компонент создаёт ещё один новый промис, на котором снова приостанавливается. Значение, которое ждали, так и не прочитано: каждый рендер ждёт свой собственный промис. Эксперимент на React 19.2: граница остаётся в fallback бесконечно.

`use` требует **стабильный** промис: созданный вне рендера и закэшированный по ключу, чтобы повторный рендер получил тот же уже выполненный промис. Это делают библиотеки данных (TanStack Query, Relay) или фреймворк; собственный кэш для серверных данных — со всеми вопросами инвалидации и ошибок — тема 7.7.

**Ответ «надо обернуть в `useMemo`»** — частично работает, но `useMemo` не гарантия (3.11): React может сбросить кэш, и, кроме того, при первой приостановке компонент ещё не смонтирован, и его `useMemo` не сохраняется между попытками. Кэш должен жить вне компонента.
</details>

---

**4. После добавления `useDeferredValue` в поиск ввод всё так же тормозит. Что проверить?**

<details>
<summary>Ответ</summary>

Что тяжёлая часть **действительно рендерится только от отложенной копии** и пропускает работу при срочном рендере:

```jsx
const deferred = useDeferredValue(query);
const results = useMemo(() => filterCourses(courses, deferred), [courses, deferred]);
return <ResultsList results={results} />;        // ResultsList — memo
```

Срочный рендер с новым `query` и старым `deferred` должен быть дешёвым: `useMemo` возвращает прежний результат, `memo`-список пропускает рендер. Если же список читает `query` напрямую, или `filterCourses` вызывается без мемоизации, или `ResultsList` не `memo` — срочный рендер делает всю тяжёлую работу, и отложенное значение только добавляет второй рендер.

Дальше — проверить, что тяжёлая работа вообще в render-фазе. Если тормозит монтирование нативных view (сотни строк без виртуализации) или commit, отложенное значение не поможет: это не прерывается (5.4, 5.10).

**Ответ «`useDeferredValue` не работает в RN»** — работает с New Architecture; дело в устройстве дерева.
</details>

## Задание — поиск по 2000 урокам: решение при неполных данных

**Дано.** Экран «Все уроки» RN Academy: поле поиска и `FlatList` с результатами. На слабом Android при вводе символы появляются с задержкой. Профайлера пока нет (это блок 05). Есть код:

```jsx
function AllLessonsScreen({ lessons }) {          // ~2000 уроков
  const [query, setQuery] = useState('');
  const results = lessons.filter((l) =>
    normalize(l.title).includes(normalize(query)) ||
    l.tags.some((t) => normalize(t).includes(normalize(query))),
  );
  return (
    <>
      <TextInput value={query} onChangeText={setQuery} />
      <Text>{results.length} уроков</Text>
      <FlatList
        data={results}
        renderItem={({ item }) => <LessonRow lesson={item} />}
        keyExtractor={(l) => l.id}
      />
    </>
  );
}
```

`normalize` приводит строку к нижнему регистру и убирает диакритику. `LessonRow` не `memo`.

Команда предлагает: «добавим `useTransition`, и всё».

**Требуется.**

1. По коду оценить, из чего состоит работа на один символ и какая её часть прерываема.
2. Сравнить три варианта: без изменений, `useTransition`, `useDeferredValue`. Для каждого — что увидит пользователь.
3. Принять решение и записать его в виде короткого ADR-абзаца: что выбрано, почему, чего это не решает и что нужно проверить замером в блоке 05.

---

<details>
<summary>Разбор</summary>

**1. Работа на один символ.**

- **фильтрация** — 2000 уроков, на каждом `normalize` заголовка и всех тегов, плюс `normalize(query)` заново на каждой проверке. Это один синхронный вызов в теле `AllLessonsScreen` — **непрерываемая** работа. Порядок величины: десятки тысяч вызовов `normalize` на символ;
- **рендер `FlatList`** — новый `data` и новый `renderItem` (3.10): список рендерится, видимые ячейки вызывают `renderItem` заново, `LessonRow` без `memo` рендерятся все видимые (порядка 10–20). Это несколько единиц работы — **прерываемы**, если обновление помечено переходом;
- **commit и монтирование** — для изменившихся видимых строк; **непрерываемо**.

Предварительный вывод: основная стоимость, скорее всего, в фильтрации — а она в одной функции и при переходе не прерывается.

**2. Три варианта.**

| Вариант | Что видит пользователь |
|---|---|
| без изменений | каждый символ — синхронный рендер с полной фильтрацией; следующий символ ждёт; поле «запаздывает» |
| `useTransition` (фильтр — переходом) | поле обновляется срочно — **но только если** фильтрация вынесена из срочного рендера. В исходном коде `results` вычисляется в теле компонента из `query`, который обновляется срочно — переход ничего не меняет. Нужно хранить отдельное состояние `filter` и вычислять от него, а сама фильтрация остаётся одним непрерываемым куском внутри перехода: при начале рендера перехода поле на это время всё равно замирает |
| `useDeferredValue` | то же условие: фильтрация от отложенной копии и мемоизирована по ней; срочный рендер дешёвый, фоновый — тяжёлый и не прерывается внутри фильтрации |

Ни один вариант не убирает главную стоимость — фильтрацию. Они лишь переносят её в фоновый рендер, где она всё так же блокирует поток на время своего выполнения.

**3. Решение.**

```jsx
function AllLessonsScreen({ lessons }) {
  const index = useMemo(() => buildIndex(lessons), [lessons]);   // нормализованные заголовки и теги
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const results = useMemo(() => search(index, normalize(deferredQuery)), [index, deferredQuery]);
  const renderItem = useCallback(({ item }) => <LessonRow lesson={item} />, []);
  const isStale = query !== deferredQuery;

  return (
    <>
      <TextInput value={query} onChangeText={setQuery} />
      <Text>{results.length} уроков{isStale ? '…' : ''}</Text>
      <FlatList data={results} renderItem={renderItem} keyExtractor={(l) => l.id} style={isStale && styles.dim} />
    </>
  );
}
```

`LessonRow` обёрнут в `memo`. Если список уроков не меняется за время жизни приложения, индекс можно строить и вне компонента — при загрузке данных.

ADR-абзац:

> **Решение.** Поиск по урокам: нормализация заголовков и тегов вынесена в индекс, который строится один раз при изменении списка (`useMemo` по `lessons`); фильтрация идёт по отложенной копии запроса (`useDeferredValue`) и мемоизирована по ней; строки списка — `memo` со стабильным `renderItem`. **Почему не только `useTransition`:** основная стоимость — фильтрация в одной функции, а переход не прерывает работу внутри одной функции; без удешевления фильтрации переход лишь откладывает блокировку. **Чего это не решает:** если монтирование строк или commit окажутся заметными, нужна работа со списком (размер окна, `getItemLayout`, рециклинг — 5.4). **Что проверить в блоке 05:** время фильтрации до и после индекса; время срочного рендера при вводе; есть ли длинные задачи на JS-потоке во время фонового рендера; на том же слабом Android-устройстве, в release-сборке.

Главное в решении — порядок: сначала сделать дорогую работу дешёвой (индекс, мемоизация), затем сделать оставшуюся прерываемой (отложенное значение). Переход без первого шага — маскировка.

**Вклад в проект (P3).** Поиск по курсам RN Academy использует индекс, отложенное значение и мемоизированный список; решение и его границы записаны в README модуля поиска. В блоке 05 этот экран — первый кандидат для замера.
</details>
