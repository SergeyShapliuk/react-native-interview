# 3.17 Suspense и concurrent features — theory

> 🔴 SENIOR. Семь углов разбора с акцентом на trade-offs. Урок отвечает не на вопрос «как использовать `useTransition`» — а на вопрос, **что меняется в модели рендера, когда React получает право бросить начатую работу**, и где это даёт выигрыш, а где маскирует проблему.

---

## 1. Что это

**Concurrent rendering** — режим, в котором React может начать рендер, прервать его ради более срочного обновления, а затем продолжить или начать заново. Возможность заложена в Fiber (3.1); включается она не для всех обновлений, а для тех, что явно помечены несрочными.

Инструменты:

- **`startTransition(fn)` / `useTransition()`** — обновления внутри `fn` становятся переходом: несрочными и прерываемыми; `useTransition` дополнительно даёт флаг `isPending`;
- **`useDeferredValue(value)`** — отложенная копия значения: сначала компонент рендерится со старой копией, затем, в фоне и прерываемо, — с новой;
- **Suspense** — компонент может «приостановиться», пока чего-то не хватает (данных, кода); ближайшая граница `<Suspense>` показывает fallback;
- **`use(promise)`** (React 19) — чтение значения промиса при рендере с приостановкой, пока промис не выполнен;
- **`<Activity mode="hidden">`** (React 19.2) — скрыть поддерево, сохранив его состояние.

### Ключевая формулировка урока

> **Concurrent rendering — это не параллельность, а право React бросить начатый рендер ради более срочного. Отсюда новая гарантия (интерфейс отвечает) и новая цена (рендер может не дойти до экрана, и компонент обязан это переживать).**

## 2. Как это работает

### Приоритеты

В 3.3 было показано, что каждое обновление получает lane — приоритет. Для этого урока важна граница между двумя группами:

- **срочные** — дискретные события (нажатие, ввод), непрерывные (прокрутка), обновления по умолчанию (таймер, ответ сети). Рендерятся синхронным циклом, до конца, без уступок;
- **несрочные** — переходы и отложенные значения. Рендерятся прерываемым циклом: после каждой единицы работы React проверяет, не истёк ли отведённый отрезок (порядка 5 мс), и если пришло что-то срочное — бросает текущую работу.

Когда срочное обновление приходит посреди перехода, React:

1. останавливает рендер перехода (work-in-progress дерево не закоммичено, экран не тронут — 3.1);
2. рендерит и коммитит срочное обновление;
3. начинает переход заново — уже с учётом нового состояния.

Брошенная работа просто исчезает. Поэтому функция компонента может быть вызвана несколько раз ради одного показанного результата, и любой побочный эффект при рендере здесь проявляется в release, а не только в StrictMode (3.4).

### `useTransition`

```jsx
function CourseSearch({ courses }) {
  const [query, setQuery] = useState('');
  const [filter, setFilter] = useState('');
  const [isPending, startTransition] = useTransition();

  function onChangeText(text) {
    setQuery(text);                               // срочно: поле ввода
    startTransition(() => setFilter(text));       // несрочно: список
  }

  return (
    <>
      <TextInput value={query} onChangeText={onChangeText} />
      {isPending && <ActivityIndicator />}
      <CourseList courses={courses} filter={filter} />
    </>
  );
}
```

Поле обновляется срочно и всегда отзывчиво. Список — переходом: если пользователь вводит быстрее, чем список успевает отрендериться, React бросает устаревший рендер списка и начинает с новым фильтром. `isPending` — `true`, пока переход не закоммичен.

### `useDeferredValue`

Тот же эффект, когда у вас нет доступа к месту обновления — например, значение пришло пропсом:

```jsx
function CourseList({ query }) {
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;
  return <List data={filterCourses(deferredQuery)} style={isStale && styles.dim} />;
}
```

Эксперимент на React 19.2: при быстром вводе «a», «ab» компонент рендерится срочно с `query = "a"` и старой отложенной копией, затем с `query = "ab"` и снова старой копией, и только затем — фоновый рендер с `"ab"`. Промежуточное значение `"a"` в отложенной копии так и не отрисовано: его фоновый рендер был вытеснен новым вводом.

Чтобы отложенное значение давало выигрыш, дорогая часть должна рендериться **от отложенной копии** и пропускать работу, когда копия не изменилась: `memo` на тяжёлом компоненте или `useMemo` на вычислении (3.11). Иначе срочный рендер с новым `query` всё равно пересчитает всё.

### Time slicing: где проходит граница

React уступает поток **между** единицами работы — то есть между компонентами. Внутри функции одного компонента уступить нельзя: это обычный JS-вызов, и пока он выполняется, ничего другого не происходит (1.20).

Следствия:

- список из 2000 дешёвых строк — переход помогает: React рендерит пачками и уступает между ними;
- один компонент, считающий 200 мс в теле функции, — переход **не помогает**: 200 мс без уступок, ввод ждёт. Решение — сделать вычисление дешевле, вынести его, мемоизировать или разбить;
- **commit не прерывается вообще** (3.3): мутации host-дерева и layout-эффекты — синхронно.

### Suspense

Компонент приостанавливается, когда при рендере ему не хватает данных: он «бросает» промис (так устроены `use`, `lazy` и библиотеки данных). React ищет ближайшую границу `<Suspense>` и показывает её fallback вместо поддерева, а когда промис выполнится — пробует рендер снова.

```jsx
<Suspense fallback={<LessonSkeleton />}>
  <LessonContent lessonId={lessonId} />
</Suspense>
```

Три наблюдаемые детали (проверено на React 19.2):

**Переход не прячет уже показанное.** Если обновление, вызвавшее приостановку, — обычное, граница сразу показывает fallback вместо старого содержимого. Если это переход — React оставляет на экране **старое** содержимое (с `isPending = true`) и переключает, когда новое готово. Это главная связь Suspense и переходов: навигация между уроками переходом не мигает скелетоном.

**Fallback троттлится.** Если fallback уже показан, React держит его ещё порядка 300 мс, даже если данные пришли раньше: в эксперименте данные готовы через 50 мс, содержимое появилось через ~320 мс. Это сделано против мигания fallback/содержимое при быстрых ответах — и это деталь реализации, на точное число опираться нельзя.

**Граница загрузки рядом с границей ошибки.** Отклонённый промис — ошибка рендера, её ловит Error Boundary (3.16). Обычная пара — `<ErrorBoundary><Suspense>…</Suspense></ErrorBoundary>`.

### `use(promise)` и кэш промисов

```jsx
function LessonContent({ lessonId }) {
  const lesson = use(fetchLesson(lessonId));   // ошибка: новый промис на каждый рендер
}
```

Каждый рендер создаёт **новый** промис. Компонент приостанавливается на нём; когда промис выполнится, React рендерит компонент снова — и тот создаёт ещё один промис. Эксперимент: граница остаётся в fallback бесконечно. Промис для `use` должен быть **стабильным**: создан вне рендера и закэширован по ключу (`lessonId`). На практике это делает библиотека данных (TanStack Query, Relay), фреймворк или собственный кэш; писать такой кэш для серверных данных — задача блока 07.

### `<Activity>` (React 19.2)

```jsx
<Activity mode={tab === 'notes' ? 'visible' : 'hidden'}>
  <NotesTab />
</Activity>
```

Скрытое поддерево **сохраняет состояние**, но его **эффекты очищаются**, а обновления рендерятся с низшим приоритетом. При показе эффекты запускаются снова. Эксперимент в react-dom: при скрытии — очистка эффекта, при показе — повторный запуск, состояние (`n = 1`) сохранено. Это ещё одна причина, по которой эффекты обязаны быть парой «эффект — очистка» (3.4): `<Activity>` делает то же, что StrictMode, но в release. Поддержка в конкретном рендерере и навигационных библиотеках — вопрос версии; в RN похожую задачу для экранов решают навигационные библиотеки своими средствами (5.9).

## 3. Почему это важно

**Отзывчивость при тяжёлом рендере.** Без переходов любой `setState` рендерится до конца: ввод в поле, вызывающий перерисовку длинного списка, блокирует следующий символ. С переходом поле отзывается всегда, а список догоняет.

**Модель «рендер = результат на экране» больше не верна.** Компонент может быть вызван, его результат выброшен, рендер начат заново. Всё, что опиралось на «если функция вызвана, она будет показана», — подсчёт в переменных модуля, подписки в теле компонента, мутации внешних объектов, запись в ref при рендере, — становится дефектом, проявляющимся в release, нестабильно и под нагрузкой.

**Внешние источники данных требуют отдельного API.** Если рендер может прерваться, внешний стор может измениться между двумя частями одного рендера. Это tearing — тема 3.19, и причина, по которой библиотеки состояния перешли на `useSyncExternalStore`.

**Переход легко принять за оптимизацию.** `startTransition` не делает рендер быстрее — он делает его прерываемым и откладывает. Медленный компонент остаётся медленным; пользователь просто дольше видит старые данные. Если переход «помог», это повод проверить, не спрятана ли за ним проблема, которую нужно решать (3.11, блок 05).

## 4. Где это в React Native

### Только New Architecture

Concurrent features в RN работают только с New Architecture: старый рендерер не поддерживал конкурентный корень. С RN 0.82 другой архитектуры нет, и переходы, `useDeferredValue` и Suspense доступны в любом приложении.

### Типовые применения

- **поиск по длинному списку** — поле срочно, фильтрация и рендер списка — отложенно;
- **переключение тяжёлых табов или вкладок экрана** — нажатие подсвечивает вкладку сразу, содержимое строится переходом;
- **переход между уроками в рамках одного экрана** — старый урок остаётся на экране с индикатором, пока новый не готов, вместо скелетона на каждый переход.

### Предел: что не прерывается

Прерываемым является **только render на JS-потоке**. Не прерываются:

- **commit** — в RN это передача нового Shadow Tree в Fabric (4.3);
- **layout и монтирование нативных view** — работа Fabric и UI-потока;
- **одна долгая функция компонента** — обычный JS-вызов.

Если экран тормозит из-за монтирования сотен нативных view или из-за одной тяжёлой ячейки, переход не поможет. Здесь нужны виртуализация (5.4), мемоизация (3.11) и замер, показывающий, какой слой занят (5.1, 5.10).

### Suspense для данных

Suspense для серверных данных в RN используется через библиотеки с поддержкой Suspense — например, TanStack Query (`useSuspenseQuery`) или Relay. Они решают главную проблему `use` — кэш промисов, дедупликацию, инвалидацию (7.7). Собственная реализация на `use` оправдана редко.

## 5. Типичные ошибки

**«Concurrent — значит многопоточный».** Возникает из слова «конкурентный». JS-поток один; React чередует работу и бросает ненужную. Ничего не выполняется параллельно.

**«`startTransition` делает код быстрее».** Возникает из того, что после добавления перехода интерфейс «перестал тормозить». Быстрее не стало — стало прерываемо: ввод отвечает, результат появляется позже.

**«Любой `setState` теперь прерываемый».** Возникает из описаний React 18 как «конкурентного». Срочные обновления рендерятся синхронно, как и раньше.

**Переход как лечение медленного компонента.** Возникает потому, что переход скрывает симптом. Один компонент на 200 мс не прерывается; переход только откладывает блокировку.

**Промис, созданный при рендере, для `use`.** Возникает из аналогии с `await`. Новый промис на каждый рендер — бесконечный fallback.

**`useDeferredValue` без мемоизации тяжёлой части.** Возникает из ожидания, что хук «сам ускорит». Если тяжёлый компонент рендерится и от нового значения, и от старого — выигрыша нет.

**«Suspense — это лоадер».** Возникает из того, что fallback выглядит как индикатор загрузки. Suspense — механизм координации: какое поддерево ждать, что показать, когда заменить, и как не мигать при переходе.

**Побочные эффекты при рендере «потому что StrictMode выключен».** При конкурентном рендере брошенная работа — нормальная часть release-поведения.

## 6. Trade-offs

### Отзывчивость против свежести

Переход и отложенное значение покупают отзывчивость ввода ценой того, что часть интерфейса показывает **устаревшие** данные, пока новые не готовы. Для поиска это приемлемо (с индикатором `isPending` или приглушением). Для данных, где устаревание опасно — сумма к оплате, статус заказа, — нет: пользователь может принять решение по старым данным.

### Прерываемость против простоты модели

Конкурентный рендер требует от всего кода чистого рендера, парных эффектов и правильной подписки на внешние источники. Команда, чей код этому не соответствует, получает от переходов нестабильные дефекты. Порядок внедрения: сначала StrictMode и исправление того, что он вскрыл (3.4), потом переходы.

### Suspense против явных состояний загрузки

Suspense убирает из компонентов ручные ветки `if (loading)` и координирует загрузку нескольких частей. Цена — данные должны приходить через кэш, поддерживающий Suspense, а поток управления становится менее явным: состояние загрузки видно не в компоненте, а в расположении границ. Явное состояние (редьюсер, 3.8) проще читать и отлаживать; Suspense выигрывает, когда частей много и их загрузку нужно согласовать.

### Решение при неполных данных

Типичная ситуация: «экран поиска тормозит при вводе, давайте добавим `useTransition`». Данных, почему он тормозит, нет. Порядок рассуждения:

1. что именно медленно — рендер многих дешёвых компонентов или один дорогой? (3.10, без профайлера — по коду; с профайлером — 5.3);
2. если много дешёвых — переход или отложенное значение помогут, при условии мемоизации тяжёлой части;
3. если один дорогой — переход не поможет; нужно удешевить вычисление;
4. если медленно монтирование нативных view — переход не поможет; нужна виртуализация.

Переход — решение для первого случая и маскировка для остальных.
