# 3.5 Правила хуков и зависимостей — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **что эффект читает и какую версию значения он видит**, а не «что добавить в массив, чтобы линтер замолчал».

---

**1. Почему ранний `return` перед `useState` ломает компонент, хотя в большинстве рендеров всё работает?**

```jsx
function LessonProgress({ lesson }) {
  if (!lesson) return <Placeholder />;
  const [expanded, setExpanded] = useState(false);
  // ...
}
```

<details>
<summary>Ответ</summary>

React хранит хуки компонента на fiber как список в порядке вызова и сопоставляет вызовы с узлами списка по номеру. Имени у хука нет.

Пока `lesson` есть в каждом рендере, вызов один, и всё работает. Сломается переход между состояниями: компонент смонтирован без урока (ноль хуков), потом урок пришёл (один хук) — React видит больше хуков, чем при прошлом рендере, и бросает ошибку. Обратный переход (урок пропал) тоже ошибка — хуков меньше, чем ожидалось.

Это объясняет, почему дефект проходит ручное тестирование: при открытии экрана с уже загруженным уроком переход не случается. Он случается, например, когда урок загружается асинхронно и первый рендер идёт без него.

Исправление — проверку ниже всех хуков либо разделить на два компонента:

```jsx
function LessonProgress({ lesson }) {
  if (!lesson) return <Placeholder />;
  return <LessonProgressBody lesson={lesson} />;
}
```

Линтер `rules-of-hooks` ловит исходный вариант статически: «React Hook "useState" is called conditionally… Did you accidentally call a React Hook after an early return?»

**Ответ «хуки нельзя вызывать в условиях — так сказано в документации»** — правило названо, причина нет. Без причины не получится распознать нарушение, когда условие выглядит иначе (цикл, вложенная функция, `try`).

**Ответ «состояние потеряется»** неточен: компонент получит ошибку, а не пустое состояние. Молчаливая подмена состояния возможна, когда меняется порядок, а не число хуков.
</details>

**2. Таймер урока показывает `1` и останавливается. Как исправить, не добавляя `seconds` в зависимости, и почему это исправление честное?**

```jsx
useEffect(() => {
  const id = setInterval(() => setSeconds(seconds + 1), 1000);
  return () => clearInterval(id);
}, []);
```

<details>
<summary>Ответ</summary>

Эффект создан в первом рендере и навсегда видит `seconds = 0` — это замыкание того рендера (1.14). Каждую секунду интервал ставит «установить 1»: первый раз значение меняется, дальше — нет (и React отказывается от рендера по `Object.is`).

Исправление — функциональное обновление:

```jsx
useEffect(() => {
  const id = setInterval(() => setSeconds((s) => s + 1), 1000);
  return () => clearInterval(id);
}, []);
```

Почему честно: эффект **больше не читает** `seconds`. Предыдущее значение React передаёт в функцию при обработке очереди (3.3). Массив `[]` теперь описывает правду — эффект не зависит ни от чего реактивного, — и линтер с этим согласен.

Добавить `seconds` в зависимости тоже честно, но хуже: интервал будет пересоздаваться каждую секунду, а при неровном рендере тики начнут смещаться.

**Ответ «добавить `// eslint-disable-next-line`»** не исправляет ошибку: массив был и остаётся враньём, таймер так же стоит на `1`.

**Ответ «хранить секунды в ref»** вскрывает подмену: значение выводится на экран, а изменение ref не вызывает рендер (3.9).
</details>

**3. Экран подписан на `AppState`, обработчик отправляет аналитику с текущим `screenName`. При честных зависимостях подписка пересоздаётся при каждой смене `screenName`. Чем `useEffectEvent` отличается от ref с последним обработчиком, и почему функцию из него нельзя передать в пропсы?**

<details>
<summary>Ответ</summary>

Оба способа решают одну задачу: долгоживущий слушатель читает **актуальное** значение на момент события, а сама подписка не зависит от этого значения.

```jsx
// React 19.2
const onChange = useEffectEvent((state) => track(state, screenName));
useEffect(() => {
  const sub = AppState.addEventListener('change', onChange);
  return () => sub.remove();
}, []);

// до React 19.2
const onChangeRef = useRef(null);
useEffect(() => { onChangeRef.current = (state) => track(state, screenName); });
useEffect(() => {
  const sub = AppState.addEventListener('change', (s) => onChangeRef.current(s));
  return () => sub.remove();
}, []);
```

Различия:

- **намерение выражено явно.** `useEffectEvent` говорит читателю и линтеру: «эта функция — часть эффекта, но не его зависимость». Вариант с ref выглядит как обычный ref, и намерение приходится восстанавливать;
- **линтер понимает `useEffectEvent`**: он не требует указать функцию в зависимостях и запрещает её неправильное использование;
- **меньше кода**, нет отдельного эффекта, обновляющего ref.

Почему нельзя передать в пропсы: ссылка на функцию из `useEffectEvent` меняется на каждый рендер (проверено на React 19.2), а её смысл — «прочитать последние значения изнутри эффекта этого компонента». Переданная дочернему компоненту, она станет нестабильной зависимостью у получателя и создаст иллюзию стабильного колбэка. Линтер это запрещает: «can only be called from Effects and Effect Events in the same component. It cannot be assigned to a variable or passed down». Для колбэка в пропсах нужна обычная функция — со стабилизацией через `useCallback`, если получатель её сравнивает (3.11).

**Ответ «`useEffectEvent` — то же, что `useCallback` без зависимостей»** вскрывает смешение. `useCallback(fn, [])` вернёт стабильную функцию, которая видит значения **первого** рендера — тот самый stale closure.

**Ответ «можно просто не указывать `screenName` в зависимостях»** — тоже stale closure: аналитика будет отправляться с первым именем экрана.
</details>

**4. Эффект загрузки урока перезапускается на каждый рендер экрана. Найдите причину и исправьте, не подавляя линтер.**

```jsx
function LessonScreen({ route }) {
  const options = { id: route.params.lessonId, lang: locale };
  useEffect(() => {
    loadLesson(options);
  }, [options]);
}
```

<details>
<summary>Ответ</summary>

`options` — объект, созданный в теле компонента. Каждый рендер создаёт новый объект, `Object.is(старый, новый)` — `false`, эффект перезапускается. Линтер предупреждает именно об этом: «The 'options' object makes the dependencies of useEffect Hook change on every render. Move it inside the useEffect callback».

Исправление — зависимостями сделать примитивы, а объект собрать внутри эффекта:

```jsx
function LessonScreen({ route }) {
  const lessonId = route.params.lessonId;
  useEffect(() => {
    loadLesson({ id: lessonId, lang: locale });
  }, [lessonId, locale]);
}
```

Теперь эффект перезапускается ровно тогда, когда меняется то, что он читает. Если `locale` — константа модуля или значение из контекста, линтер сам подскажет, нужна ли она в массиве.

`useMemo` для `options` тоже сработает, но это лишний слой: объект нужен только эффекту, и его место внутри эффекта. `useMemo` оправдан, когда тот же объект используется ещё где-то — например, передаётся в `memo`-компонент (3.11).

**Ответ «заменить `[options]` на `[]`»** вскрывает выбор зависимостей вместо поиска: эффект перестанет реагировать на смену урока.

**Ответ «заменить на `[route.params]`»** — сдвигает проблему: объект параметров тоже может быть новым на каждый рендер.
</details>

## Задание — три подавленных `exhaustive-deps`

**Дано.** В экране урока RN Academy три эффекта, у каждого стоит `// eslint-disable-next-line react-hooks/exhaustive-deps`. Комментарии в коде — объяснения автора, почему линтер подавлен.

```jsx
function LessonScreen({ lessonId, userId, onComplete }) {
  const [position, setPosition] = useState(0);
  const [lesson, setLesson] = useState(null);

  // «не хочу перезагружать урок при смене userId»
  useEffect(() => {
    api.loadLesson(lessonId, userId).then(setLesson);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [lessonId]);

  // «иначе переподписывается при каждом изменении position»
  useEffect(() => {
    const sub = AppState.addEventListener('change', (state) => {
      if (state === 'background') api.savePosition(lessonId, position);
    });
    return () => sub.remove();
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [lessonId]);

  // «onComplete меняется при каждом рендере родителя»
  useEffect(() => {
    if (lesson && position >= lesson.duration) onComplete(lessonId);
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, [position, lesson]);
}
```

**Требуется.**

1. Для каждого эффекта назвать, какое значение пропущено и какой дефект это даёт.
2. Для каждого выбрать способ уменьшить зависимости, не возвращая ложь в массив, и объяснить выбор через вопрос «пересинхронизировать или только прочитать».
3. Один из трёх эффектов, вероятно, не должен быть эффектом вообще. Какой и почему?

---

<details>
<summary>Разбор</summary>

**1. Пропущенные значения и дефекты.**

*Первый эффект* читает `userId`, но не указывает его. Если пользователь сменится без смены урока (выход и вход под другим аккаунтом, переключение профилей), урок останется загруженным для старого пользователя: с его прогрессом и доступом. Автор считал `userId` «неважным», но эффект его **читает** — значит, результат от него зависит.

*Второй эффект* читает `position`, но не указывает её. Слушатель создан при смене урока и видит позицию на тот момент — обычно `0`. При уходе приложения в фон сохраняется позиция начала урока, а не текущая. Дефект тихий: пользователь возвращается в начало урока и думает, что приложение «не запомнило».

*Третий эффект* читает `onComplete` и `lessonId`. С пропущенным `onComplete` вызывается колбэк из старого рендера родителя — если родитель изменил логику (другой обработчик в зависимости от состояния), вызовется устаревшая версия.

**2. Способы.**

*Первый эффект — пересинхронизировать.* При смене пользователя урок **нужно** загрузить заново: это другой результат запроса. Значит, `userId` — честная зависимость:

```jsx
useEffect(() => {
  let cancelled = false;
  api.loadLesson(lessonId, userId).then((l) => { if (!cancelled) setLesson(l); });
  return () => { cancelled = true; };
}, [lessonId, userId]);
```

Отмена добавлена потому, что теперь эффект может перезапуститься до прихода ответа (3.4). Страх автора «лишней перезагрузки» относился к ситуации, которой не бывает: если `userId` не меняется, перезапуска нет.

*Второй эффект — только прочитать.* Подписку на `AppState` при смене позиции пересоздавать незачем: синхронизация с `AppState` от позиции не зависит, позиция нужна только в момент события. Это ровно случай `useEffectEvent`:

```jsx
const onAppStateChange = useEffectEvent((state) => {
  if (state === 'background') api.savePosition(lessonId, position);
});

useEffect(() => {
  const sub = AppState.addEventListener('change', onAppStateChange);
  return () => sub.remove();
}, []);
```

Массив `[]` честный: функция из `useEffectEvent` не зависимость, а `lessonId` и `position` она читает в момент вызова. Для кода на React до 19.2 — ref с последним обработчиком (3.9).

*Третий эффект — см. пункт 3.*

**3. Эффект, который не должен быть эффектом.**

Третий. Он не синхронизирует React ни с какой внешней системой: он **реагирует на изменение состояния** вызовом колбэка родителя. Событие «урок завершён» происходит в момент, когда позиция дошла до конца, — то есть там, где позиция меняется. Правильное место — обработчик, который обновляет позицию:

```jsx
function handleProgress(nextPosition) {
  setPosition(nextPosition);
  if (lesson && nextPosition >= lesson.duration) onComplete(lessonId);
}
```

Проблема с `onComplete` в зависимостях исчезает вместе с эффектом. Исчезает и скрытый дефект исходного кода: эффект вызывал `onComplete` **на каждое** изменение позиции после конца урока и при каждой перезагрузке `lesson` с уже пройденной позицией — например, при восстановлении экрана. Подробно о таких эффектах — 3.7.

**Вклад в проект (P3).** В RN Academy включён `eslint-plugin-react-hooks` с конфигурацией `recommended`; подавление `exhaustive-deps` допускается только с комментарием, объясняющим, почему ни один из приёмов урока не применим. В слое P3 таких мест нет.
</details>
