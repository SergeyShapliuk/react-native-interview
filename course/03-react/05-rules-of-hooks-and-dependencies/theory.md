# 3.5 Правила хуков и зависимостей — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «какие правила у хуков» — а на вопрос, **из какого устройства React эти правила следуют и почему массив зависимостей нельзя «подобрать»**.

---

## 1. Что это

**Правила хуков** — два ограничения на место вызова:

1. хуки вызываются только на верхнем уровне функции — не в условии, не в цикле, не во вложенной функции, не после раннего `return`;
2. хуки вызываются только из функций-компонентов и из других хуков.

**Массив зависимостей** — второй аргумент `useEffect`, `useLayoutEffect`, `useMemo`, `useCallback`, `useImperativeHandle`. По нему React решает, выполнить ли эффект заново (или пересчитать значение).

Оба правила проверяет `eslint-plugin-react-hooks`: `rules-of-hooks` (ошибка) и `exhaustive-deps` (предупреждение).

### Ключевая формулировка урока

> **React узнаёт хук по порядковому номеру вызова, а не по имени. Массив зависимостей — не список «когда перезапускать», а перечень всех значений из рендера, которые эффект читает.**

---

## 2. Как это работает

### Хуки — это список на fiber

В 3.1 было показано, что состояние компонента хранится на fiber, в поле `memoizedState`. Для функционального компонента это **связный список** — по одному узлу на каждый вызов хука в порядке вызова:

```jsx
function LessonScreen() {
  const [tab, setTab] = useState('text');        // узел 1
  const [note, setNote] = useState('');          // узел 2
  useEffect(() => { /* ... */ }, [tab]);         // узел 3
  const total = useMemo(() => count(), []);      // узел 4
}
```

У хука нет имени или ключа. При следующем рендере React идёт по списку параллельно с вызовами: первый вызов `useState` получает узел 1, второй — узел 2. Переменная, которой присвоен результат, React не видит вообще.

Отсюда первое правило. Если вызов хука стоит под условием, число и порядок вызовов меняются между рендерами:

```jsx
function Profile({ user }) {
  if (!user) return null;                // ранний return
  const [tab, setTab] = useState('info');
}
```

Рендер с `user = null` вызывает ноль хуков, рендер с пользователем — один. Если компонент смонтировался без пользователя, а потом получил его, React обнаружит больше хуков, чем было, и бросит ошибку («Rendered more hooks than during the previous render»). Когда меняется не число, а порядок хуков одного вида, ошибки может не быть: хук молча получит состояние **соседа**; в dev React предупредит о смене порядка хуков, в release не скажет ничего. Линтер ловит всё это статически:

```
React Hook "useState" is called conditionally. React Hooks must be called in the exact
same order in every component render. Did you accidentally call a React Hook after an
early return?
```

Второе правило следует из того же: хук работает только тогда, когда React в данный момент рендерит компонент и знает, на какой fiber записывать. Вызов хука из обычной функции вне рендера не к чему привязать.

### Как сравниваются зависимости

После рендера React сравнивает новый массив зависимостей с предыдущим **поэлементно через `Object.is`**. Если все элементы равны — эффект пропускается. Если хоть один отличается — очистка предыдущего запуска и новый запуск (3.4).

Три формы:

| Запись | Когда выполняется эффект |
|---|---|
| без массива | после каждого commit этого компонента |
| `[]` | один раз на монтирование |
| `[a, b]` | на монтирование и когда `a` или `b` изменились по `Object.is` |

`Object.is` сравнивает ссылки (3.10). Объект, массив или функция, созданные при рендере, — **новые на каждый рендер**, и эффект с такой зависимостью перезапускается каждый раз.

### «Честный» массив

Эффект — замыкание рендера, в котором создан (1.14). Он видит пропсы, состояние и всё, что вычислено из них, **в том виде, в каком они были в этом рендере**. Массив зависимостей говорит React: «перезапусти меня, когда изменится то, что я видел».

Честный массив — **все реактивные значения, которые эффект читает**: пропсы, состояние, контекст и всё, что вычислено из них в теле компонента. Если значение пропущено, эффект продолжит видеть его старую версию — это и есть stale closure (1.14).

```jsx
useEffect(() => {
  const id = setInterval(() => setSeconds(seconds + 1), 1000);
  return () => clearInterval(id);
}, []);     // эффект читает seconds, но не указывает его
```

Эффект создан в первом рендере и видит `seconds = 0` навсегда. Каждую секунду он ставит «установить 1». Экран покажет `1` и остановится. Линтер:

```
React Hook useEffect has a missing dependency: 'seconds'. Either include it or remove
the dependency array. You can also do a functional update 'setSeconds(s => ...)' if
you only need 'seconds' in the 'setSeconds' call
```

Ключевой сдвиг урока: **зависимости не выбирают — их находят.** Вопрос не «когда я хочу, чтобы эффект перезапускался», а «что эффект читает». Если ответ на второй вопрос не устраивает, менять надо код эффекта, а не массив.

### Что указывать не нужно

- **сеттер `useState` и `dispatch` `useReducer`** — React гарантирует, что они стабильны между рендерами;
- **ref-объект из `useRef`** — сам объект стабилен (но `ref.current` — не реактивное значение, указывать его в массиве бессмысленно, 3.9);
- **значения вне компонента** — константы модуля, импортированные функции;
- **функцию из `useEffectEvent`** — она специально не является зависимостью (ниже).

Линтер знает об этих исключениях, но только когда видит их происхождение. Сеттер, пришедший **через пропсы**, для линтера обычное значение, и его нужно указать.

### Как уменьшить зависимости, не соврав

Пять приёмов, каждый — изменение кода эффекта, а не массива.

**1. Функциональное обновление.** Если значение нужно только чтобы вычислить следующее:

```jsx
useEffect(() => {
  const id = setInterval(() => setSeconds((s) => s + 1), 1000);
  return () => clearInterval(id);
}, []);     // честно: эффект больше не читает seconds
```

**2. Функцию — внутрь эффекта.** Функция, объявленная в теле компонента, — новая на каждый рендер. Если её использует только эффект, её место внутри эффекта; тогда зависимостями становятся значения, которые она читает:

```jsx
useEffect(() => {
  function buildQuery() { return { lessonId, lang }; }
  load(buildQuery());
}, [lessonId, lang]);
```

**3. Функцию — вне компонента.** Если она не читает ничего реактивного, ей не место в компоненте вообще.

**4. Примитив вместо объекта.** Объект из пропсов или вычисленный при рендере перезапускает эффект на каждый рендер. Если эффекту нужно одно поле, зависимостью должно быть поле:

```jsx
const lessonId = route.params.lessonId;
useEffect(() => { load(lessonId); }, [lessonId]);   // не [route.params]
```

Линтер распознаёт объект, созданный в теле, и подсказывает: «The 'options' object makes the dependencies of useEffect Hook change on every render. Move it inside the useEffect callback».

**5. `useEffectEvent` (React 19.2) — прочитать актуальное, не реагируя на изменение.** Типовая ситуация: эффект подписывается на событие, обработчику нужны свежие пропсы, но переподписываться при каждом их изменении нельзя или дорого:

```jsx
const onAppStateChange = useEffectEvent((state) => {
  analytics.track('app_state', { state, screen: screenName });   // всегда свежий screenName
});

useEffect(() => {
  const sub = AppState.addEventListener('change', onAppStateChange);
  return () => sub.remove();
}, []);     // честно: функция из useEffectEvent — не зависимость
```

`useEffectEvent` возвращает функцию, которая при вызове видит значения **последнего** рендера. Ссылка на неё меняется каждый рендер (проверено на React 19.2), поэтому её и нельзя указывать в зависимостях — и поэтому же есть ограничения: вызывать её можно только из эффектов того же компонента, нельзя передавать в пропсы и в другие хуки. Линтер это проверяет: «`onAppState` is a function created with React Hook "useEffectEvent", and can only be called from Effects and Effect Events in the same component. It cannot be assigned to a variable or passed down».

До React 19.2 ту же задачу решали ref с последним обработчиком (3.9). `useEffectEvent` делает то же и выражает намерение явно.

### `async` в эффекте

Функция эффекта должна возвращать либо ничего, либо функцию очистки. `async`-функция возвращает промис, поэтому `useEffect(async () => ...)` — ошибка. Асинхронная работа оформляется вложенной функцией с отменой в очистке:

```jsx
useEffect(() => {
  let cancelled = false;
  (async () => {
    const data = await api.loadLesson(lessonId);
    if (!cancelled) setLesson(data);
  })();
  return () => { cancelled = true; };
}, [lessonId]);
```

Зависимости асинхронного эффекта считаются так же: всё реактивное, что читается, включая код после `await`.

## 3. Почему это важно

**Нарушение правил хуков даёт ошибки, которые не воспроизводятся стабильно.** Условный хук работает, пока условие не изменилось во время жизни компонента. Это дефект, который проходит ручное тестирование и проявляется на редком переходе между состояниями.

**Пропущенная зависимость — это данные из прошлого.** Эффект отправляет запрос со старым идентификатором, подписка вызывает старый обработчик, таймер считает от старого значения. Ошибка выглядит не как падение, а как «иногда показывает не то», и её причина находится далеко от симптома.

**Лишняя зависимость — это лишняя работа и гонки.** Объект в зависимостях перезапускает эффект на каждый рендер: подписка снимается и создаётся заново, запрос отправляется заново, таймер сбрасывается. Для эффекта с запросом это ещё и гонка ответов (3.4, блок 07).

**Подавленный линтер — это решение, которое больше никто не проверит.** `// eslint-disable-next-line react-hooks/exhaustive-deps` фиксирует массив в том состоянии, в каком он был при написании. Следующий, кто добавит в эффект чтение нового пропса, не получит предупреждения.

## 4. Где это в React Native

### Подписка на системное событие с актуальным обработчиком

`AppState`, `Keyboard`, `Linking`, `BackHandler`, нативные emitter'ы. Обработчику нужны свежие пропсы или состояние, а переподписка на каждый рендер означает снятие и создание нативной подписки — лишнюю работу и окно, в котором событие может быть пропущено. Это основной случай для `useEffectEvent` (или ref в коде до React 19.2).

### Таймеры урока, опрос, анимации на JS

`setInterval` с чтением состояния — классический stale closure. Функциональное обновление решает его без зависимостей.

### `route.params` в зависимостях

Объект параметров экрана может быть новым на каждый рендер в зависимости от навигационной библиотеки и способа передачи. Эффект с `[route.params]` в лучшем случае перезапускается чаще нужного, в худшем — на каждый рендер. Зависимостью должно быть конкретное поле: `route.params.lessonId`.

### Обёртки над нативными модулями

Обёртка над нативным модулем часто принимает объект опций: `startTracking({ accuracy, interval })`. Если опции собираются в теле компонента, эффект перезапускает нативный трекинг на каждый рендер. Примитивы в зависимостях или объект, собранный внутри эффекта, решают это.

## 5. Типичные ошибки

**Пустой массив «чтобы выполнилось один раз».** Возникает из модели «зависимости — это триггеры, которые выбираю я». Эффект, читающий пропсы, с `[]` навсегда видит их первые значения. Если эффект действительно должен выполниться один раз за жизнь приложения, ему место вне компонента (3.4).

**Подавление `exhaustive-deps`.** Возникает, когда честный массив даёт нежелательный перезапуск, и самый быстрый способ его убрать — комментарий. Правильный ответ — один из пяти приёмов урока: эффект меняется так, чтобы честный массив стал таким, какой нужен.

**Объект или функция из рендера в зависимостях.** Возникает потому, что линтер требует их указать, и их указывают «как есть». Результат — перезапуск на каждый рендер. Решения — перенести внутрь эффекта, взять примитивы или, если значение действительно нужно стабилизировать, `useMemo`/`useCallback` (3.11).

**«`useCallback` решает проблему зависимостей».** Возникает из того, что `useCallback` стабилизирует ссылку. Но у `useCallback` свои зависимости, и если они меняются часто, меняется и ссылка. Это перенос проблемы на уровень выше, а не её решение. Если функция нужна только эффекту — она должна быть внутри эффекта.

**Условный хук «потому что так короче».** Ранний `return` перед хуками — самый частый случай. Возникает при добавлении проверки «нет данных — ничего не показывать» в начало существующего компонента. Исправление — перенести проверку ниже всех хуков или вынести содержимое в отдельный компонент, который рендерится только при наличии данных.

**`ref.current` в зависимостях.** Возникает из желания сделать эффект реактивным к ref. Изменение `ref.current` не вызывает рендер, а массив сравнивается только при рендере — поэтому эффект не узнает об изменении (3.9).

## 6. Trade-offs

### Перезапуск, ref или `useEffectEvent`: снимок против актуального значения

Когда эффект читает часто меняющееся значение, есть три варианта, и выбор между ними — тот же выбор, что в 1.14:

| | Значение в зависимостях | `useEffectEvent` / ref |
|---|---|---|
| что видит эффект | значение своего рендера | значение последнего рендера на момент вызова |
| цена изменения значения | перезапуск эффекта: очистка и новый запуск | ничего не перезапускается |
| согласованность | высокая: эффект и его очистка видят одно и то же | ниже: значение может смениться между двумя вызовами |
| где правильно | эффект **должен** перезапуститься при изменении (новый `lessonId` — новая подписка) | значение нужно только **прочитать** в момент события |

Критерий выбора: если при изменении значения внешнюю систему нужно **пересинхронизировать** — это зависимость. Если значение нужно только **использовать** в момент события, а синхронизация от него не зависит — это `useEffectEvent`.

### Честность против числа перезапусков

Честный массив иногда даёт больше перезапусков, чем хотелось бы. Это сигнал не к подавлению линтера, а к пересмотру эффекта: возможно, он делает две вещи, и их нужно разделить на два эффекта с разными зависимостями; возможно, часть логики — вычисление при рендере (3.7) или обработчик события.

### Линтер как часть сборки

`exhaustive-deps` по умолчанию — предупреждение, а не ошибка. Команды, которые переводят его в ошибку в CI, платят тем, что каждое исключение требует обоснования. Взамен массив зависимостей перестаёт быть местом, где копятся устаревшие решения. В 7-й версии плагина к этим правилам добавились правила компилятора (3.18) — они ловят нарушения, которые ломают автоматическую мемоизацию.

## 7. Связи с другими частями системы

**Опирается на:**

- **3.1 Reconciliation и Fiber** — хуки живут на fiber, и порядок — единственное, что их связывает с вызовами;
- **3.4 Lifecycle и StrictMode** — зависимости определяют, когда очистка и новый запуск;
- **1.14 Closures** — эффект видит значения своего рендера; пропущенная зависимость — это stale closure; выбор между снимком и актуальным значением.

**Готовит:**

- **3.7 Когда эффект не нужен** — часть проблем с зависимостями исчезает вместе с эффектом;
- **3.9 Refs** — ref как способ хранить актуальное значение и почему `ref.current` не зависимость;
- **3.10 Referential equality** — почему объект и функция в зависимостях меняются на каждый рендер;
- **3.11 Мемоизация** — `useMemo` и `useCallback` как способ стабилизировать зависимость и их цена;
- **3.12 Кастомные хуки** — правила действуют внутри хука, а стабильность возвращаемых функций — часть его контракта;
- **3.18 React Compiler** — правила хуков как условие, при котором компилятор вообще работает;
- **5.8 утечки**, **09 подписки на нативные события**.
