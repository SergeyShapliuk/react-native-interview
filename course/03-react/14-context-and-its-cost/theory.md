# 3.14 Context и его цена — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как создать контекст» — а на вопрос, **кого рендерит изменение `value`, почему `memo` от этого не защищает и как устроить контексты, чтобы платить только за нужные рендеры**.

---

## 1. Что это

**Context** — механизм, позволяющий компоненту прочитать значение, предоставленное выше по дереву, без передачи через пропсы каждого промежуточного уровня:

```jsx
const ThemeContext = createContext('light');

<ThemeContext.Provider value={theme}>   {/* в React 19 можно и <ThemeContext value={theme}> */}
  <App />
</ThemeContext.Provider>

function LessonTitle() {
  const theme = useContext(ThemeContext);
}
```

Провайдер ставит значение для своего поддерева, потребитель читает ближайшее значение выше себя.

Context ничего не хранит и ничем не управляет: значение лежит в состоянии компонента-провайдера (или где-то ещё), а контекст только **доставляет** его вниз.

### Ключевая формулировка урока

> **Context — механизм доставки, а не управления состоянием. Подписчик рендерится при любом изменении `value` по `Object.is`, и `memo` между провайдером и подписчиком этого не останавливает.**

---

## 2. Как это работает

### Сравнение `value` и рендер потребителей

Когда провайдер рендерится, React сравнивает новый `value` с прошлым через `Object.is` (3.10). Если отличается — React находит **всех** потребителей этого контекста в поддереве и помечает их к рендеру.

Два важных следствия:

**Подписка — на весь `value`.** Компонент, читающий из `{ user, theme, setUser }` только `theme`, рендерится при изменении `user`. React не знает, какое поле компонент использует; он знает только, что компонент читает контекст, `value` которого изменился. Проверено на React 19.2: при смене `user` компонент, читающий из широкого контекста только `theme`, рендерится.

**`memo` не защищает потребителя.** `memo` останавливает рендер, пришедший **от родителя** (третья причина из 3.10). Контекст — **вторая** причина: потребитель помечается напрямую, мимо промежуточных компонентов. Проверено: `memo`-компонент, читающий контекст, рендерится при новом `value`, а `memo`-компонент между провайдером и потребителем, сам контекст не читающий, — нет.

```
Provider (value изменился)
  └── Middle (memo, контекст не читает) — пропускает рендер
        └── Consumer (memo, читает контекст) — рендерится всё равно
```

То есть `memo` защищает **промежуточные** компоненты, но не тех, кто читает контекст.

### `value`-литерал

```jsx
function SessionProvider({ children }) {
  const [user, setUser] = useState(null);
  return (
    <SessionContext.Provider value={{ user, setUser }}>
      {children}
    </SessionContext.Provider>
  );
}
```

`{ user, setUser }` — новый объект на каждый рендер `SessionProvider`. Если провайдер рендерится по любой причине — его родитель отрендерился, изменилось другое состояние провайдера, — `Object.is` даёт «не равно», и все потребители рендерятся, даже если `user` тот же. Проверено: изменение постороннего состояния компонента-провайдера рендерит всех потребителей широкого контекста.

Заметим, что `children` провайдера при этом не рендерятся сами по себе (3.13) — рендерятся именно **потребители** внутри них. Это и делает контекст дешевле пропсов «в среднем» и дороже «в худшем случае»: остальное дерево не трогается, но каждый потребитель — да, где бы он ни был.

### Четыре способа дробления

**1. Мемоизировать `value`.**

```jsx
const value = useMemo(() => ({ user, setUser }), [user]);
```

Убирает рендеры потребителей от посторонних рендеров провайдера. Не помогает от изменения самого `user`.

**2. Разделить значения и действия.**

```jsx
const SessionStateContext = createContext(null);
const SessionActionsContext = createContext(null);

function SessionProvider({ children }) {
  const [user, setUser] = useState(null);
  const actions = useMemo(() => ({ setUser, logout: () => setUser(null) }), []);
  return (
    <SessionStateContext.Provider value={user}>
      <SessionActionsContext.Provider value={actions}>{children}</SessionActionsContext.Provider>
    </SessionStateContext.Provider>
  );
}
```

Сеттер `useState` стабилен (3.10), поэтому объект действий не меняется никогда. Компоненты, которым нужны только действия (кнопка «Выйти»), читают `SessionActionsContext` и не рендерятся при изменении пользователя. Проверено: потребитель контекста действий не рендерится при смене значения. То же даёт `dispatch` из `useReducer` (3.8) — стабильный по гарантии.

**3. Разделить по частоте изменений.** Тема меняется раз в сессию, сессия — при входе и выходе, текущий урок — при переходах, прогресс воспроизведения — каждую секунду. Одно значение с ними всеми рендерит каждого потребителя каждую секунду. Отдельный контекст на каждую частоту — потребители платят только за то, что читают.

**4. Опустить провайдер ниже.** Контекст «текущий урок» нужен только экрану урока — провайдер ставится в экран урока, а не в корень приложения. Изменения затрагивают меньшее поддерево, и потребителей вне экрана просто нет.

### `use(Context)` в React 19

```jsx
function LessonBadge({ showProgress }) {
  if (!showProgress) return null;
  const progress = use(ProgressContext);   // условный вызов допустим
}
```

`use` читает контекст так же, как `useContext`, и подписывает компонент на него — но в отличие от хуков его **можно вызывать условно** и в циклах. Проверено на React 19.2: условный `use(Context)` не нарушает работу компонента. Цена та же: если вызов произошёл, компонент — потребитель и рендерится при изменении `value`.

### Когда Context — правильный выбор

Context хорош для значений, которые:

- нужны многим компонентам на разной глубине;
- **меняются редко** — каждое изменение рендерит всех потребителей;
- являются «окружением», а не данными предметной области: тема, локаль, текущий пользователь, настройки, зависимости (клиент API, логгер, навигация).

Context плох для значений, которые меняются часто или читаются частично: позиция скролла, ввод в форме, прогресс, большие коллекции, из которых каждый компонент берёт свою часть. Для них нужна подписка с выбором части (селектор) — `useSyncExternalStore` и внешний стор (3.19, 6.3).

---

## 3. Почему это важно

**Context — частая причина массовых рендеров.** Один широкий контекст в корне приложения, значение которого меняется при каждом действии, рендерит каждый экран, каждую строку списка, каждую кнопку, которая его читает. В отличие от пропсов, путь рендера не виден в коде экрана: потребитель может быть в любом месте дерева.

**`memo` не помогает, и это ломает интуицию.** Разработчик, привыкший лечить лишние рендеры `memo`, оборачивает компонент — и ничего не меняется. Без понимания того, что контекст — отдельная причина рендера, следующий шаг обычно — кастомный компаратор или отказ от `memo` как «не работающего».

**Context как стор — архитектурная ошибка.** Контекст не даёт ни подписки на часть значения, ни селекторов, ни инструментов отладки. Приложение, где всё состояние лежит в одном контексте, рендерит всё на каждое изменение и упирается в это при росте — и переписывается на стор под давлением.

## 4. Где это в React Native

### Хорошие кандидаты

- **Тема** — светлая или тёмная, меняется редко; `useColorScheme` из RN сам по себе подписка на системную тему.
- **Локаль и направление текста** — меняются раз в сессию.
- **Safe area** — `react-native-safe-area-context` (5.x) экспортирует **отдельные** `SafeAreaInsetsContext` и `SafeAreaFrameContext` и хуки `useSafeAreaInsets` и `useSafeAreaFrame`. Insets меняются при повороте экрана и показе системных панелей, frame — при изменении размера окна; компонентам, которым нужны только отступы, незачем рендериться при изменении размеров окна. Это и есть способ 3 — дробление по частоте, — сделанный авторами библиотеки.
- **Сессия** — пользователь меняется при входе и выходе.
- **Зависимости** — клиент API, логгер, хранилище: значение не меняется вообще, контекст используется как механизм внедрения (8.4).

### Плохие кандидаты

- **Позиция скролла** — меняется на каждом кадре прокрутки; в контексте она рендерит всех потребителей с частотой событий. Для анимаций по скроллу — Reanimated и shared values, которые не проходят через рендер React (5.7).
- **Прогресс воспроизведения видео** — каждую секунду или чаще.
- **Ввод в форме** — на каждый символ.
- **Большие коллекции** — список уроков в контексте, из которого каждая ячейка читает «свой» урок: изменение одного урока рендерит все ячейки, `memo` на них не помогает.

### Навигация

Библиотеки навигации используют контекст для передачи объекта навигации, параметров маршрута и состояния фокуса. Хуки вроде `useNavigation` и `useRoute` — потребители контекста. Компонент, читающий состояние навигации, рендерится при его изменении — это стоит помнить в тяжёлых экранах и ячейках списков (5.9).

## 5. Типичные ошибки

**Context как state management.** Возникает потому, что контекст — встроенный и «простой». Он не управляет состоянием, а только доставляет его; при росте приложения отсутствие селекторов делает каждое изменение глобальным рендером.

**Один `AppContext` на всё.** Тема, пользователь, корзина, настройки, флаги в одном объекте. Возникает из желания «одного места для всего». Каждое изменение любой части рендерит каждого потребителя любой части.

**`value`-литерал без `useMemo`.** Возникает потому, что `value={{ user, setUser }}` выглядит естественно. Каждый рендер провайдера — рендер всех потребителей, даже без изменения данных.

**`memo` на потребителе «от контекста».** Возникает из привычки лечить рендеры `memo`. Контекст — отдельная причина рендера, `memo` её не останавливает.

**«Потребитель рендерится, только если изменилось поле, которое он читает».** Возникает из модели «React отслеживает, что используется». Не отслеживает — подписка на весь `value`.

**`useMemo` на `value` как универсальное решение.** Возникает после того, как узнали про литерал. Мемоизация убирает рендеры от посторонних причин, но если в `value` лежат часто меняющиеся данные, потребители рендерятся на каждое их изменение. Решение — дробление, а не мемоизация.

---

## 6. Trade-offs

### Дробление против числа провайдеров

Каждый способ дробления добавляет провайдер, контекст и хук для чтения. Пять контекстов вокруг приложения — пять уровней обёрток, которые нужно поддерживать согласованными (действия одного контекста меняют значение другого). В какой-то момент это выглядит как самописный стор без инструментов отладки — и это сигнал, что состояние переросло контекст и пора принимать решение 6.3.

### Context против композиции

Если данные нужны одному компоненту в глубине, а промежуточные уровни — обёртки, композиция (3.13) решает задачу без подписки и без рендеров потребителей. Контекст оправдан, когда потребителей много и они разбросаны.

### Context против внешнего стора с селекторами

Внешний стор (Zustand, Redux через `useSyncExternalStore`, 3.19) даёт подписку на **часть** состояния: компонент рендерится, только когда изменился результат его селектора. Цена — зависимость, другой способ чтения и обновления, и селекторы, которые нужно писать правильно (6.5). Для редко меняющихся значений контекст проще; для часто меняющихся или читаемых частично — стор выигрывает.
