# 3.14 Context и его цена — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **изменился ли `value` по `Object.is`** и кто из компонентов — потребитель, а кто только промежуточный уровень.

---

**1. Провайдер отдаёт `value={{ user, setUser }}`. Родитель провайдера рендерится по причине, не связанной с пользователем. Что происходит с потребителями?**

<details>
<summary>Ответ</summary>

Все потребители рендерятся. Рендер родителя рендерит провайдер (3.10), провайдер создаёт новый литерал `{ user, setUser }`, `Object.is(старый, новый)` — `false`, и React помечает всех потребителей контекста к рендеру — даже тех, кто обёрнут в `memo`. Проверено на React 19.2: изменение постороннего состояния в компоненте-провайдере рендерит каждого потребителя широкого контекста, включая `memo`-компонент, читающий из него только сеттер.

Обычные дети провайдера при этом не рендерятся сами по себе, если пришли как `children` (3.13), — рендерятся именно потребители.

Исправление первого уровня — `useMemo` на `value` по `[user]`: тогда посторонний рендер провайдера не трогает потребителей. От изменения самого `user` это не спасает — для этого дробление (вопрос 2).

**Ответ «ничего, `user` не изменился»** вскрывает модель «React сравнивает содержимое `value`».
</details>

---

**2. Почему разделение на `SessionStateContext` и `SessionActionsContext` уменьшает число рендеров?**

<details>
<summary>Ответ</summary>

Потому что подписка — на весь `value` контекста, а не на поле. Компонент, которому нужно только действие (`logout` в кнопке выхода), при едином контексте рендерится при каждой смене пользователя, хотя действие не изменилось.

После разделения:

- `SessionActionsContext` содержит объект действий, мемоизированный с пустыми зависимостями: сеттер `useState` и `dispatch` стабильны (3.8, 3.10), значит, `value` этого контекста **не меняется никогда**;
- потребители только действий не рендерятся при смене пользователя;
- потребители состояния рендерятся, как и раньше.

Проверено на React 19.2: при смене пользователя рендерятся потребители контекста значения и широкого контекста, потребитель контекста действий — нет.

**Ответ «`memo` на кнопке выхода сделает то же самое»** вскрывает незнание того, что `memo` не защищает потребителя контекста.
</details>

---

**3. Компонент в `memo` читает контекст. Его родитель тоже в `memo` и контекст не читает. `value` изменился. Кто отрендерится?**

<details>
<summary>Ответ</summary>

Только компонент, читающий контекст. Родитель в `memo` пропустит рендер: его пропсы не изменились, а контекст он не читает. Потребитель отрендерится, потому что контекст — отдельная причина рендера (3.10): React помечает потребителей напрямую, мимо промежуточных компонентов. Проверено на React 19.2: промежуточный `memo`-компонент не рендерится, `memo`-потребитель — рендерится.

Вывод: `memo` защищает от рендера родителя, а не от контекста. Если потребитель дорогой и `value` меняется часто, нужно не `memo`, а уменьшить то, на что он подписан: отдельный контекст, примитивное значение или внешний стор с селектором (3.19).
</details>

---

**4. Когда Context проигрывает внешнему стору с селекторами?**

<details>
<summary>Ответ</summary>

Когда значение **меняется часто** или **читается частично**:

- позиция скролла, прогресс воспроизведения, ввод — каждое изменение рендерит всех потребителей с частотой события;
- коллекция, из которой каждый потребитель берёт свою часть (каждая ячейка — свой урок): изменение одного элемента рендерит все ячейки, `memo` не помогает.

Внешний стор с `useSyncExternalStore` и селектором рендерит компонент, только если изменился **результат его селектора** (3.19, 6.5). Цена — зависимость или собственный стор, синхронные обновления (переходом их не сделать) и селекторы, которые нужно писать правильно.

Context выигрывает для редко меняющихся значений, нужных многим: тема, локаль, сессия, зависимости. Само решение — урок 6.3.
</details>

## Задание — один широкий контекст экрана курса

**Дано.** Экран курса RN Academy получает всё через один контекст:

```jsx
const CourseContext = createContext(null);

function CourseProvider({ courseId, children }) {
  const [course, setCourse] = useState(null);
  const [filter, setFilter] = useState('all');
  const [playingLessonId, setPlayingLessonId] = useState(null);
  const [progressSec, setProgressSec] = useState(0);        // обновляется каждую секунду плеером
  const theme = useColorScheme();
  // ... загрузка курса ...
  return (
    <CourseContext.Provider
      value={{ course, filter, setFilter, playingLessonId, setPlayingLessonId, progressSec, setProgressSec, theme }}
    >
      {children}
    </CourseContext.Provider>
  );
}
```

Потребители: шапка (`course.title`, `theme`), переключатель фильтра (`filter`, `setFilter`), список уроков из 40 строк (каждая строка читает `course`, `filter`, `playingLessonId`, `theme`), мини-плеер (`playingLessonId`, `progressSec`, `setProgressSec`).

Жалоба: «пока играет урок, список подтормаживает при прокрутке».

**Требуется.**

1. Без профайлера, по коду и логам, определить, кто рендерится при изменении каждого поля. Объяснить жалобу.
2. Раздробить контекст так, чтобы каждый потребитель платил только за то, что читает. Решить, что из этого вообще не должно быть в контексте.
3. Показать, где `memo` на строке списка заработает после дробления и почему не работал до.

---

<details>
<summary>Разбор</summary>

**1. Кто рендерится.**

`value` — литерал, новый на каждый рендер провайдера; провайдер рендерится при изменении любого из своих состояний. Значит, при изменении **любого** поля рендерятся **все** потребители:

| Изменилось | Рендерятся |
|---|---|
| `progressSec` (каждую секунду) | шапка, фильтр, 40 строк (видимые), мини-плеер |
| `filter` | все |
| `playingLessonId` | все |
| `theme` | все |
| `course` | все |

Жалоба объясняется первой строкой: пока играет урок, каждую секунду рендерятся все видимые строки списка, шапка и фильтр — ради одного числа, которое читает только мини-плеер. Если строки тяжёлые (изображения, иконки), каждый такой рендер приходится на прокрутку. `memo` на строках не помогает: строки — потребители контекста.

Проверка логами: `console.log` в теле каждого потребителя и в провайдере; за 3 секунды воспроизведения — по три рендера каждой видимой строки.

**2. Дробление.**

```jsx
const CourseDataContext = createContext(null);       // course — меняется при загрузке
const CourseFilterContext = createContext(null);     // filter + setFilter
const PlaybackContext = createContext(null);         // playingLessonId — меняется при смене урока
const PlaybackActionsContext = createContext(null);  // сеттеры — не меняются никогда

function CourseProvider({ courseId, children }) {
  const [course, setCourse] = useState(null);
  const [filter, setFilter] = useState('all');
  const [playingLessonId, setPlayingLessonId] = useState(null);

  const filterValue = useMemo(() => ({ filter, setFilter }), [filter]);
  const actions = useMemo(() => ({ setPlayingLessonId }), []);

  return (
    <CourseDataContext.Provider value={course}>
      <CourseFilterContext.Provider value={filterValue}>
        <PlaybackContext.Provider value={playingLessonId}>
          <PlaybackActionsContext.Provider value={actions}>
            {children}
          </PlaybackActionsContext.Provider>
        </PlaybackContext.Provider>
      </CourseFilterContext.Provider>
    </CourseDataContext.Provider>
  );
}
```

Что убрано из контекста совсем:

- **`progressSec`** — меняется каждую секунду, нужен одному компоненту. Его место — состояние мини-плеера (или внешний стор плеера с селектором, 3.19, если прогресс нужен нескольким компонентам). Это главное исправление жалобы;
- **`theme`** — уже приходит из `useColorScheme()`, который сам является подпиской на системную тему; потребители вызывают его напрямую или через общий `ThemeContext` приложения, а не через контекст курса.

Теперь:

| Изменилось | Рендерятся |
|---|---|
| прогресс воспроизведения | только мини-плеер |
| `filter` | переключатель и строки, читающие фильтр |
| `playingLessonId` | мини-плеер и строки, читающие `PlaybackContext` |
| `course` | шапка и строки |

**3. `memo` на строках.**

До дробления `memo` на `LessonRow` не мог сработать: строка — потребитель контекста с новым `value` на каждый рендер провайдера.

После дробления можно пойти дальше: строке не нужен ни `course` целиком, ни `filter` — родитель списка уже отфильтровал уроки и передаёт строке её урок пропсом. А `playingLessonId` строке нужен только как булево «играет ли этот урок»:

```jsx
function LessonList() {
  const course = useContext(CourseDataContext);
  const { filter } = useContext(CourseFilterContext);
  const playingLessonId = useContext(PlaybackContext);
  const visible = useMemo(() => applyFilter(course.lessons, filter), [course, filter]);
  const renderItem = useCallback(
    ({ item }) => <LessonRow lesson={item} isPlaying={item.id === playingLessonId} />,
    [playingLessonId],
  );
  return <FlatList data={visible} renderItem={renderItem} keyExtractor={(l) => l.id} />;
}

const LessonRow = memo(function LessonRow({ lesson, isPlaying }) { /* ... */ });
```

Строки больше не читают контекст. При смене играющего урока `renderItem` новый, каждая видимая ячейка вызывает его, но `memo` строки сравнивает `lesson` (тот же объект) и `isPlaying` (примитив) — рендерятся **две** строки: та, что перестала играть, и та, что начала. Контекст читает один компонент — `LessonList`, — а дальше работает обычная механика пропсов и `memo` (3.10, 3.11).

**Вклад в проект (P3).** В RN Academy контексты темы и сессии разделены на уровне приложения; контекст курса раздроблен по частоте изменений; прогресс воспроизведения живёт в плеере, а не в контексте; строки списка не читают контекст и получают примитивы. Правило проекта: в контекст кладутся только значения, меняющиеся реже, чем раз в несколько секунд, и нужные нескольким удалённым друг от друга компонентам.
</details>
