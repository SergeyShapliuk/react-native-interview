# 3.13 Composition — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **где создан элемент** — это определяет и то, кто пробрасывает данные, и то, кто рендерится.

---

**1. Почему `<ScreenLayout>{content}</ScreenLayout>` не перерисовывает `content` при изменении состояния `ScreenLayout`?**

<details>
<summary>Ответ</summary>

Элемент `content` создан в рендере **родителя** `ScreenLayout` и пришёл к ней пропсом `children`. Когда `ScreenLayout` меняет своё состояние и рендерится, она возвращает тот же объект `children`, что получила. React сравнивает элемент на этой позиции с прошлым, видит **ту же ссылку** и не рендерит содержимое. Проверено на React 19.2: обёртка рендерится на каждое изменение своего состояния, переданное содержимое — ни разу.

Содержимое перерисуется, когда рендерится **родитель** — он создаёт элемент заново. Это правильно: если родитель рендерится, содержимое могло измениться.

Практический вывод: тяжёлое содержимое, переданное в обёртку с часто меняющимся состоянием (анимированная шапка, раскрывающийся блок, обёртка с таймером), не страдает от её рендеров — без единого `memo`.

**Ответ «потому что React сравнивает пропсы `content`»** вскрывает модель «сравнение пропсов всегда». Здесь не пропсы сравниваются, а сам элемент — тот же объект.

**Ответ «перерисует, `content` — её ребёнок»** вскрывает модель «ребёнок в JSX = ребёнок по рендеру».
</details>

**2. Когда render prop лучше кастомного хука, а когда хуже?**

<details>
<summary>Ответ</summary>

**Хук лучше**, когда переиспользуется только **логика** с состоянием: подписка, таймер, загрузка. `const height = useKeyboardHeight()` короче `<KeyboardHeight render={(h) => ...} />`, не добавляет уровня в дерево и не вкладывает JSX в функцию. Большая часть исторических render props закрыта хуками именно поэтому.

**Render prop лучше**, когда контейнер управляет **ещё и разметкой** — решает, где и сколько раз вызвать функцию:

- `renderItem` у списка — список решает, какие элементы видимы и в каком порядке; хук не может «отрендерить ячейку в нужном месте»;
- `renderEmpty`, `renderError` — контейнер решает, какой слот показать;
- анимационная обёртка, передающая содержимому анимированное значение и одновременно оборачивающая его в анимированный view.

Критерий: если контейнеру нужно только **вычислить данные** — хук; если ему нужно **разместить** результат функции в своей разметке — render prop.

**Ответ «render props устарели»** — неверно: `renderItem` — render prop, которым RN-разработчик пользуется каждый день.
</details>

**3. Чем платит compound component `<Tabs><Tabs.Item /></Tabs>` за удобный синтаксис?**

<details>
<summary>Ответ</summary>

Неявным контрактом. Связь `Tabs` и `Tabs.Item` идёт через локальный контекст, и она:

- **не видна в сигнатуре пропсов** — по типу `TabsItem` не понять, что он работает только внутри `Tabs`;
- **не проверяется компилятором** — `<Tabs.Item />` вне `Tabs` компилируется и падает в рантайме, когда `useContext` вернёт `null`;
- **не описывает инварианты** — уникальность `id`, наличие хотя бы одной вкладки, совпадение `initial` с одним из `id`.

Компенсации: хук `useTabsContext` с понятной ошибкой вместо `TypeError`, описание контракта в README компонента, проверка инвариантов в dev. Альтернатива с явным контрактом — `<Tabs items={[{ id, title }]} />`: проверяется компилятором, но не позволяет произвольную разметку между вкладками.

Вторая цена — контекст: каждое изменение активной вкладки рендерит всех потребителей `TabsContext` (3.14). Для пяти вкладок неважно, для сотни элементов списка — уже важно.

**Ответ «ничем, это лучший паттерн»** вскрывает незнание того, что контракт перенесён из типов в рантайм.
</details>

**4. Пропс `onLessonComplete` пробрасывается через `LessonScreen → LessonLayout → LessonFooter → CompleteButton`. Команда предлагает положить его в контекст. Что спросить перед этим?**

<details>
<summary>Ответ</summary>

Главный вопрос: **почему `CompleteButton` создаётся в `LessonFooter`, а не в `LessonScreen`**, где обработчик уже есть?

Если `LessonLayout` и `LessonFooter` — обёртки, отвечающие за расположение, — `CompleteButton` можно создать в `LessonScreen` и передать слотом:

```jsx
<LessonLayout footer={<LessonFooter action={<CompleteButton onPress={onLessonComplete} />} />}>
  ...
</LessonLayout>
```

Обёртки больше не знают об обработчике, контекст не нужен.

Контекст оправдан, если: потребителей много и они на разной глубине; обёртки не просто расставляют элементы, а сами решают, когда показывать кнопку; данные — «окружение», которое нужно всему поддереву (тема, сессия). Для одного обработчика, нужного одной кнопке, это редкость.

Само решение «композиция, контекст или стор» — урок 6.7; здесь важно, что вопрос «где собрано дерево» задаётся **первым**.
</details>

## Задание — убрать пробрасывание без стора и без контекста

**Дано.** Экран урока RN Academy. Пропс `user` идёт через три уровня, пропс `lesson` — через два, а шапка с анимацией сворачивания рендерит всё содержимое при каждом изменении позиции.

```jsx
function LessonScreen({ user, lesson }) {
  return <LessonLayout user={user} lesson={lesson} />;
}

function LessonLayout({ user, lesson }) {
  return (
    <View style={styles.screen}>
      <CollapsingHeader user={user} lesson={lesson} />
      <ScrollView>
        <LessonBody lesson={lesson} />
      </ScrollView>
    </View>
  );
}

function CollapsingHeader({ user, lesson }) {
  const [collapsed, setCollapsed] = useState(false);
  // collapsed меняется по событиям прокрутки
  return (
    <View style={collapsed ? styles.headerSmall : styles.headerLarge}>
      <Text>{lesson.title}</Text>
      <Avatar user={user} />
      <ProgressRing lessonId={lesson.id} userId={user.id} />
    </View>
  );
}
```

**Требуется.**

1. Найти, какие компоненты получают `user` и `lesson` только ради того, чтобы передать дальше.
2. Переписать экран композицией: `children` и слоты. Ни стора, ни контекста.
3. Объяснить, что изменилось в рендерах при сворачивании шапки, — без профайлера.
4. Назвать, какой из компонентов стал крупнее, и решить, приемлемо ли это.

---

<details>
<summary>Разбор</summary>

**1. Транзитные пропсы.**

- `LessonLayout` получает `user` только для `CollapsingHeader`; `lesson` — для `CollapsingHeader` и `LessonBody`. Сама она ни то, ни другое не использует — она отвечает за расположение;
- `CollapsingHeader` использует `lesson.title`, но `user` и `lesson.id` получает только для `Avatar` и `ProgressRing`. Её собственная ответственность — сворачивание.

**2. Композиция.**

```jsx
function LessonScreen({ user, lesson }) {
  return (
    <LessonLayout
      header={
        <CollapsingHeader title={lesson.title}>
          <Avatar user={user} />
          <ProgressRing lessonId={lesson.id} userId={user.id} />
        </CollapsingHeader>
      }
    >
      <LessonBody lesson={lesson} />
    </LessonLayout>
  );
}

function LessonLayout({ header, children }) {
  return (
    <View style={styles.screen}>
      {header}
      <ScrollView>{children}</ScrollView>
    </View>
  );
}

function CollapsingHeader({ title, children }) {
  const [collapsed, setCollapsed] = useState(false);
  return (
    <View style={collapsed ? styles.headerSmall : styles.headerLarge}>
      <Text>{title}</Text>
      {children}
    </View>
  );
}
```

`LessonLayout` знает только о расположении: слот шапки сверху, содержимое в скролле. `CollapsingHeader` знает о сворачивании и заголовке; аватар и прогресс получает готовыми. Данные пользователя и урока — только у `LessonScreen` и у компонентов, которые их действительно используют.

**3. Что изменилось в рендерах.**

До: изменение `collapsed` рендерит `CollapsingHeader` и всё, что она создаёт, — `Avatar` и `ProgressRing` (кольцо прогресса с SVG — заметно дорогой компонент). На каждое событие сворачивания и разворачивания.

После: `Avatar` и `ProgressRing` созданы в рендере `LessonScreen` и пришли в `CollapsingHeader` как `children`. Изменение `collapsed` рендерит `CollapsingHeader`, а `children` — та же ссылка, React их не рендерит. Тот же механизм проверен экспериментом на React 19.2.

`LessonBody` в обоих вариантах не рендерится от сворачивания шапки (она — сосед, а не потомок шапки). Но во втором варианте `LessonLayout` больше не получает `lesson`, и если `LessonScreen` рендерится по причине, не связанной с уроком, — это видно сразу, по одному месту.

**4. Кто стал крупнее.**

`LessonScreen`: он теперь собирает шапку, аватар и прогресс. Это приемлемо и даже правильно — это компонент экрана, у него есть данные, и именно в нём видно, из чего экран состоит. Обёртки (`LessonLayout`, `CollapsingHeader`) стали меньше и переиспользуемы: та же шапка подходит экрану курса, тот же layout — любому экрану с шапкой и скроллом.

Если сборка в `LessonScreen` станет громоздкой, выделяется компонент `LessonHeaderContent({ user, lesson })` с аватаром и прогрессом — он принимает данные, потому что использует их, а не передаёт дальше.

**Вклад в проект (P3).** В RN Academy появляется `ScreenLayout` со слотами `header` и `footer`, сворачиваемая шапка, принимающая содержимое через `children`, и `Tabs` курса как compound component с хуком-проверкой контекста и описанным контрактом. Пропсы в экранах P3 не пробрасываются через обёртки.
</details>
