# 3.13 Composition: `children`, render props, compound components — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок про механизм, который чаще всего пропускают и сразу заводят стор: **пропс пробрасывается через три уровня не потому, что нужно глобальное состояние, а потому, что дерево собрано не в том месте**.

---

## 1. Что это

**Композиция** — способ строить компонент из других компонентов, передавая ему готовые элементы, а не данные для их создания. Четыре формы:

- **`children`** — элементы, вложенные в JSX компонента, приходят пропсом `children`;
- **слоты** — несколько пропсов-элементов: `header`, `footer`, `emptyState`;
- **render props** — пропс-функция, которую компонент вызывает со своими данными и получает элементы;
- **compound components** — набор компонентов, работающих вместе через неявный общий контекст: `<Tabs>` и `<Tabs.Item>`.

Пятая форма — **HOC** (higher-order component), функция, принимающая компонент и возвращающая обёрнутый, — исторически решала ту же задачу и в новом коде почти не нужна.

### Ключевая формулировка урока

> **Пропс пробрасывается через три уровня не потому, что нужно глобальное состояние, а потому, что дерево собрано не в том месте. Элемент, созданный там, где данные уже есть, никуда их не пробрасывает.**

---

## 2. Как это работает

### Откуда берётся prop drilling

```jsx
function LessonScreen({ user }) {
  return <ScreenLayout user={user} />;
}
function ScreenLayout({ user }) {
  return <View><Header user={user} /><Content /></View>;
}
function Header({ user }) {
  return <View><Title /><Avatar user={user} /></View>;
}
```

`ScreenLayout` и `Header` получают `user` не потому, что он им нужен, а потому, что они **создают** `Avatar`, которому он нужен. Данные текут вниз вслед за местом, где пишется JSX.

Если `Avatar` создать там, где `user` уже есть, пробрасывать нечего:

```jsx
function LessonScreen({ user }) {
  return (
    <ScreenLayout header={<Header avatar={<Avatar user={user} />} />}>
      <Content />
    </ScreenLayout>
  );
}
function ScreenLayout({ header, children }) {
  return <View>{header}{children}</View>;
}
function Header({ avatar }) {
  return <View><Title />{avatar}</View>;
}
```

`ScreenLayout` и `Header` больше не знают о пользователе. Они знают только, **куда поставить** то, что им дали. Это не обход проблемы, а другое распределение ответственности: компонент, у которого есть данные, собирает дерево; компоненты-обёртки задают расположение.

### `children`: обёртка не знает о содержимом

Элемент — описание `{ type, props }`, созданное там, где написан JSX (3.1). Когда родитель пишет `<Card><LessonBody /></Card>`, элемент `<LessonBody />` создаётся **в рендере родителя** и передаётся `Card` пропсом `children`.

Отсюда важное следствие для производительности. Если `Card` меняет **своё** состояние и рендерится, она возвращает тот же `children`, который получила, — **ту же ссылку** на элемент. React видит, что элемент на этой позиции не изменился (тот же объект), и не рендерит `LessonBody`. Проверено на React 19.2: обёртка с собственным состоянием рендерится на каждое его изменение, переданный ей `children` — ни разу.

Если же рендерится **родитель**, он создаёт `<LessonBody />` заново — новый объект, — и `Card` перерисуется вместе с содержимым. Это правильно: содержимое могло измениться.

```
состояние обёртки изменилось  →  рендер обёртки, children — та же ссылка, не рендерятся
рендер родителя               →  новый элемент children, рендерятся вместе с обёрткой
```

Так композиция решает одну из задач мемоизации без единого `memo` (3.11): тяжёлое содержимое, переданное как `children`, не рендерится от изменений состояния обёртки.

### Слоты

Один `children` — одно место для содержимого. Если мест несколько, каждое получает свой пропс:

```jsx
<ScreenLayout
  header={<LessonHeader lesson={lesson} />}
  footer={<NextLessonButton lessonId={lesson.nextId} />}
>
  <LessonBody lesson={lesson} />
</ScreenLayout>
```

Слоты делают расположение частью контракта обёртки: «шапка сверху, подвал снизу, содержимое между ними со скроллом». Всё, что связано с данными, остаётся у вызывающего.

### Render props

Когда содержимое **зависит от внутреннего состояния контейнера**, готовый элемент передать нельзя — его нужно построить из данных, которые есть только у контейнера. Тогда передаётся функция:

```jsx
<FlatList
  data={lessons}
  renderItem={({ item, index }) => <LessonRow lesson={item} position={index + 1} />}
/>
```

`renderItem` — классический render prop: список знает, какие элементы видны и в каком порядке, вызывающий знает, как нарисовать элемент.

Большую часть исторических применений render props — «поделиться логикой с состоянием» (`<Mouse render={(pos) => ...}>`, `<Fetch render={(data) => ...}>`) — закрыли кастомные хуки (3.12): `const pos = useMouse()` проще и не добавляет уровня в дерево. Уместными render props остаются там, где контейнер управляет **ещё и разметкой**:

- списки и виртуализация — `renderItem`, `renderSectionHeader`;
- компоненты с несколькими слотами, зависящими от состояния — `renderEmpty`, `renderError`;
- анимационные обёртки, которые передают анимированное значение содержимому.

### Compound components

Набор компонентов, которые используются только вместе и обмениваются состоянием через **локальный контекст**:

```jsx
const TabsContext = createContext(null);

function Tabs({ initial, children }) {
  const [active, setActive] = useState(initial);
  const value = useMemo(() => ({ active, setActive }), [active]);
  return <TabsContext.Provider value={value}><View>{children}</View></TabsContext.Provider>;
}

function TabsItem({ id, title }) {
  const { active, setActive } = useContext(TabsContext);
  return (
    <Pressable onPress={() => setActive(id)} accessibilityState={{ selected: active === id }}>
      <Text style={active === id ? styles.activeTab : styles.tab}>{title}</Text>
    </Pressable>
  );
}

Tabs.Item = TabsItem;

<Tabs initial="text">
  <Tabs.Item id="text" title="Текст" />
  <Tabs.Item id="video" title="Видео" />
</Tabs>
```

Вызывающий собирает разметку свободно — порядок, обёртки, дополнительные элементы между вкладками, — а состояние вкладок общее. Это и сила, и цена паттерна: контракт («`Tabs.Item` работает только внутри `Tabs`», «`id` уникален») **не виден в сигнатуре пропсов** и не проверяется компилятором. `Tabs.Item` вне `Tabs` упадёт на деструктуризации `null` во время выполнения. Поэтому контракт compound component обязан быть описан явно — в комментарии, в README компонента, проверкой с понятной ошибкой:

```jsx
function useTabsContext() {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error('Tabs.Item должен использоваться внутри <Tabs>');
  return ctx;
}
```

Старая реализация того же паттерна — `React.Children.map(children, (child) => cloneElement(child, { active }))`. Она ломается, как только между `Tabs` и `Tabs.Item` появляется обёртка или фрагмент, и не видна в DevTools. Контекст этой проблемы не имеет.

### HOC

```jsx
const LessonScreenWithAuth = withAuth(withTheme(LessonScreen));
```

HOC оборачивает компонент и подмешивает пропсы. Его нужно уметь читать — он остаётся в старом коде и в библиотеках, — но для нового кода он почти всегда проигрывает хуку или композиции:

- **непрозрачные пропсы** — по коду `LessonScreen` не видно, откуда пришёл `user`;
- **конфликт имён** — два HOC, подмешивающих `loading`, перезаписывают друг друга;
- **лишний уровень в дереве** — и в DevTools, и в стеке ошибки;
- **проблемы со статикой и ref** — статические поля и ref не проходят через обёртку без дополнительной работы.

`const user = useAuth()` делает то же явно.

## 3. Почему это важно

**Prop drilling лечат не тем инструментом.** Типичная реакция на пропс, проброшенный через три уровня, — контекст или глобальный стор. Оба решают задачу «доставить данные», но платят своим: контекст — рендером всех потребителей (3.14), стор — связностью компонента с глобальным состоянием. Если проблема в том, где собрано дерево, — правильное решение изменить место сборки.

**Композиция — бесплатная оптимизация рендера.** Содержимое, переданное как `children`, не рендерится от изменений состояния обёртки. Это убирает целый класс лишних рендеров без `memo` и без поддержки стабильных ссылок.

**Компоненты с `children` переиспользуются.** Обёртка, не знающая о содержимом, работает с любым содержимым. Обёртка, которая сама создаёт `Avatar` из `user`, работает только там, где есть `user`.

## 4. Где это в React Native

### Обёртки экранов

Каждый экран RN-приложения проходит через одни и те же слои: safe area, фон, скролл, клавиатура, состояние загрузки или ошибки. Обёртка `ScreenLayout` со слотами берёт расположение на себя, а экран отдаёт ей готовые части:

```jsx
<ScreenLayout
  header={<LessonHeader lesson={lesson} />}
  footer={<NextLessonButton lessonId={lesson.nextId} />}
  scrollable
>
  <LessonBody lesson={lesson} />
</ScreenLayout>
```

### Анимированная шапка

Шапка, которая сжимается при прокрутке и хранит позицию прокрутки в состоянии, рендерится на каждое изменение позиции. Если содержимое шапки (заголовок, аватар, кнопки) создаётся **внутри** неё — рендерится и оно. Если передано как `children` — нет: проверено, шапка рендерится при каждом изменении своего состояния, содержимое — один раз. (Для анимаций на каждом кадре правильный инструмент — Reanimated, где значение вообще не проходит через состояние React, 5.7; но если состояние есть, композиция снижает его цену.)

### Дизайн-система

`Card`, `Section`, `ListItem`, `BottomSheet` — компоненты, которые должны принимать любое содержимое. Слоты (`left`, `right`, `title`, `subtitle`) вместо пропсов-данных (`iconName`, `badgeCount`) позволяют дизайн-системе не знать о предметной области приложения.

### Списки

`renderItem`, `ListHeaderComponent`, `ListEmptyComponent`, `ItemSeparatorComponent` у `FlatList` — render props и слоты в чистом виде. Понимание композиции объясняет и их цену: новый `renderItem` на каждый рендер — новый пропс для каждой ячейки (3.10, 3.11).

## 5. Типичные ошибки

**Context вместо композиции.** Возникает потому, что контекст — первое, что приходит в голову при слове «пробрасывание». Если данные нужны одному компоненту глубоко в дереве, а промежуточные компоненты — просто обёртки, композиция решает задачу без контекста и без рендера всех потребителей.

**`React.Children.map` и `cloneElement` для передачи пропсов детям.** Возникает из желания сделать compound component «без лишнего контекста». Ломается на фрагментах, условных детях и обёртках между родителем и ребёнком; контракт невидим и в DevTools.

**`memo` на обёртке, принимающей `children`.** Возникает из желания «защитить» обёртку. `children` — новый элемент на каждый рендер родителя, `memo` не срабатывает (3.11). Защищать нужно содержимое, а не обёртку — и чаще всего защита уже есть: содержимое не рендерится от состояния обёртки.

**Render prop там, где хватает хука.** `<WithKeyboard render={(height) => ...}>` вместо `const height = useKeyboardHeight()`. Возникает из старых кодовых баз. Лишний уровень в дереве и вложенность JSX без выгоды.

**Compound component без описанного контракта.** Возникает потому, что в момент написания контракт очевиден автору. Через полгода `Tabs.Item` используют вне `Tabs` и получают `TypeError` на деструктуризации.

**«`children` всегда перерисовываются вместе с родителем».** Возникает из модели «ребёнок в JSX = ребёнок по рендеру». Рендер определяется не вложенностью в JSX, а тем, где создан элемент.

## 6. Trade-offs

### Композиция поднимает сборку вверх

Компонент, у которого есть данные, становится крупнее: он собирает дерево, которое раньше собирали обёртки. В пределе экран превращается в одну большую функцию, создающую все элементы. Баланс: обёртки берут на себя **расположение**, экран — **данные**, а переиспользуемые части с данными становятся собственными компонентами (`LessonHeader lesson={lesson}`).

### Слоты против пропсов-данных

`<ListItem title="Урок 3" iconName="play" />` — короткий вызов, жёсткий контракт: дизайн-система знает про иконки и решает, как их рисовать. `<ListItem title={...} left={<PlayIcon />} />` — гибкий контракт, длиннее вызов, и дизайн-система не может гарантировать единообразие. Для базовых компонентов дизайн-системы обычно выбирают пропсы-данные для частых случаев и слоты для остальных.

### Неявный контракт compound components

Свобода разметки против проверяемости: `<Tabs items={[...]} />` проверяется компилятором и не даёт ничего вставить между вкладками; `<Tabs><Tabs.Item /></Tabs>` даёт свободу и переносит проверку в рантайм. Выбор зависит от того, насколько разнообразны реальные применения.

## 7. Связи с другими частями системы

**Опирается на:**

- **3.1 Reconciliation** — элемент как описание, созданное там, где написан JSX; тот же элемент на той же позиции не требует работы;
- **3.10 Referential equality** — элемент `children` — та же ссылка, пока родитель его не пересоздал;
- **3.11 Мемоизация** — композиция как альтернатива `memo`; `memo` на обёртке с `children` не работает;
- **3.12 Кастомные хуки** — что из render props заменено хуками.
