# 3.16 Error Boundaries — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как написать Error Boundary» — а на вопрос, **какие ошибки граница увидит, какие пройдут мимо и почему**, и что получит пользователь RN-приложения в каждом случае.

---

## 1. Что это

**Error Boundary** — компонент, который перехватывает ошибки, брошенные в его поддереве, и показывает вместо поддерева запасной UI (fallback).

Граница — классовый компонент с одним или двумя методами:

```jsx
class ErrorBoundary extends Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };                           // перейти в состояние ошибки
  }

  componentDidCatch(error, info) {
    reportError(error, info.componentStack);    // отправить в crash reporting
  }

  render() {
    if (this.state.error) return this.props.fallback(this.state.error);
    return this.props.children;
  }
}
```

Функционального аналога в React нет: хуки не умеют перехватывать ошибки дочернего дерева. На практике границу пишут один раз (или берут библиотеку `react-error-boundary`) и используют как обычный компонент.

### Ключевая формулировка урока

> **Error Boundary ловит ошибки, брошенные, когда React сам выполняет ваш код: рендер, методы жизненного цикла, синхронное тело эффектов и их очисток. Всё, что вызывает рантайм, — обработчики, таймеры, продолжения промисов — проходит мимо.**

---

## 2. Как это работает

### Что ловится

Граница видит ошибку, если она брошена **внутри работы, которую выполняет React**:

- **рендер** — функция компонента или метод `render` класса;
- **конструктор и методы жизненного цикла** классов;
- **синхронное тело эффектов** — `useEffect`, `useLayoutEffect`;
- **функции очистки эффектов**;
- **ref-колбэки**, вызываемые при commit.

Проверено на React 19.2: ошибка, брошенная в теле `useEffect`, и ошибка в функции очистки эффекта при размонтировании попадают в ближайшую границу, и она показывает fallback.

### Что не ловится

- **обработчики событий** — `onPress`, `onChangeText`. Их вызывает не рендер React, а система событий в ответ на действие пользователя; ошибка уходит в глобальный обработчик. Проверено: ошибка в обработчике нажатия не меняет UI границы;
- **асинхронный код** — колбэк `setTimeout`, продолжение после `await`, `.then` промиса, колбэк нативного модуля. Эффект мог **запустить** эту работу, но выполняет её рантайм позже, когда эффект давно закончился (1.11);
- **код на верхнем уровне модуля** — выполняется при загрузке бандла, до первого рендера (1.15);
- **ошибка в самой границе** — в её `render` или в fallback. Её поймает только граница выше.

Общий признак — тот же, что у `try/catch` в 1.11: граница видит только то, что выполняется **внутри** вызова, который React сделал сам.

### Как довести асинхронную ошибку до границы

Если ошибка асинхронной загрузки должна показать fallback экрана, её нужно передать в рендер. Штатный приём — бросить её из функции обновления состояния:

```jsx
const [, setState] = useState();

useEffect(() => {
  api.loadLesson(lessonId).catch((error) => {
    setState(() => { throw error; });     // функция-обновление вызывается при рендере
  });
}, [lessonId]);
```

Функция-обновление выполняется во время рендера (3.3), и брошенная в ней ошибка — ошибка рендера. Проверено: такая ошибка попадает в границу. Библиотеки загрузки данных и `react-error-boundary` (`useErrorBoundary`) делают то же самое под капотом. Альтернатива — хранить ошибку в состоянии и бросать её при рендере: `if (state.status === 'error') throw state.error`.

Но довести до границы стоит не каждую асинхронную ошибку. Ошибка сохранения заметки — тост и повтор, а не fallback вместо всего экрана (7.3).

### Что происходит без границы

Если ошибку рендера не поймала ни одна граница, React **очищает весь корень**: всё дерево размонтируется. Проверено: корень без границы после ошибки в рендере пуст. Это сознательное решение React: показывать частично сломанный интерфейс опаснее, чем не показывать ничего.

### `onCaughtError` и `onUncaughtError`

В React 19 корень принимает обработчики ошибок:

- **`onCaughtError`** — ошибка поймана границей;
- **`onUncaughtError`** — ошибка не поймана никем, корень очищен;
- **`onRecoverableError`** — React восстановился сам (например, повтором рендера).

Рендерер RN 0.87 подключает их сам, и это определяет поведение приложения:

- непойманная ошибка (`onUncaughtError`) передаётся в `ExceptionsManager` как **фатальная**;
- пойманная границей (`onCaughtError`) — как **нефатальная**;
- восстановимая — как предупреждение.

### Сброс границы

Граница в состоянии ошибки остаётся в нём, пока её не сбросить. Простейший сброс — ключ (3.2):

```jsx
const [attempt, setAttempt] = useState(0);

<ErrorBoundary
  key={attempt}
  fallback={() => <RetryView onRetry={() => setAttempt((a) => a + 1)} />}
>
  <LessonContent lessonId={lessonId} />
</ErrorBoundary>
```

Новый ключ — новый экземпляр границы и всего поддерева: повторный рендер, повторные эффекты, повторная загрузка. Библиотеки предлагают `resetKeys` — сброс при изменении указанных значений (например, при смене `lessonId`).

## 3. Почему это важно

**Без границ одна ошибка — это всё приложение.** Ошибка рендера в виджете рекомендаций на экране урока без границы очищает корень — пользователь теряет всё, включая навигацию. С границей на виджете — пропадает один виджет.

**Граница — не обработка ошибок.** Самое опасное заблуждение темы: «у нас есть Error Boundary, ошибки обработаны». Граница покрывает рендер и эффекты. Ошибки в обработчиках нажатий, в сетевых запросах, в колбэках нативных модулей — большая часть реальных ошибок приложения — проходят мимо неё. Для них нужна обработка в месте возникновения (1.11, 7.3) и глобальный обработчик с crash reporting (10.6).

**Граница определяет, что увидит пользователь.** Fallback — часть UX: что он показывает, можно ли из него уйти, можно ли повторить. Граница с пустым fallback на корне хуже, чем граница с кнопкой «Повторить» на экране.

## 4. Где это в React Native

### Release: фатальная ошибка против рабочего экрана

Как показано выше, в RN 0.87 непойманная ошибка рендера уходит в `ExceptionsManager` как фатальная. В dev это красный экран LogBox. В release фатальная JS-ошибка по умолчанию обрабатывается нативной стороной как краш — приложение закрывается, и в crash reporting это JS-краш (10.7). С границей на экране та же ошибка — нефатальная: экран показывает fallback, приложение работает, а ошибка всё равно попадает в отчёты через `componentDidCatch`.

### LogBox маскирует разницу в dev

В dev любая ошибка выглядит драматично — красный экран или уведомление LogBox. Разработчик видит ошибку, закрывает её и продолжает. Разница между «поймана границей» и «не поймана» в dev видна плохо, а в release это разница между fallback и закрытием приложения. Проверять расстановку границ стоит на release-сборке или явно — проверяя, что fallback появился.

### Где ставить границы

- **корень приложения** — последний рубеж: экран «что-то пошло не так» с перезапуском, вместо закрытия приложения;
- **каждый экран** (или навигатор) — ошибка на экране не ломает навигацию: пользователь может вернуться назад или уйти в другой таб. Граница внутри экрана, а не над навигатором — иначе fallback заменит и шапку с кнопкой «назад»;
- **независимые виджеты** — рекомендации, реклама, комментарии, карта: то, без чего экран остаётся полезным.

### Ошибки вне React

Колбэк нативного модуля, глобальный обработчик события, ошибка при загрузке бандла — идут в глобальный обработчик ошибок RN (`ErrorUtils`), минуя React. Crash reporting (Sentry, Crashlytics) подключается и туда, и в `componentDidCatch` границ — это тема 10.6.

## 5. Типичные ошибки

**«Error Boundary ловит все ошибки компонента».** Возникает из названия. Ловит ошибки, брошенные, когда React выполняет код компонента. Обработчики и асинхронность — нет.

**«Ошибка в `onPress` попадёт в границу».** Возникает из того, что обработчик написан внутри компонента. Место написания не важно — важно, кто вызывает.

**«Ошибка в `useEffect` не ловится».** Обратная ошибка, частая в старых статьях. Синхронное тело эффекта и очистка ловятся; не ловится асинхронная работа, которую эффект запустил.

**Одна граница на всё приложение.** Возникает, когда границу добавляют «чтобы не было красного экрана». Любая ошибка заменяет всё приложение на fallback — лучше, чем закрытие, но хуже, чем пропавший виджет.

**Граница над навигатором вместо внутри экрана.** Fallback заменяет шапку и таб-бар; пользователь не может уйти с экрана, который сломался.

**Граница как замена обработки ошибок.** Возникает из чувства «ошибки обработаны». Сетевая ошибка, которую довели до границы, показывает fallback всего экрана там, где достаточно было тоста.

**Fallback без выхода.** «Что-то пошло не так» без кнопки повтора и без навигации. Пользователь может только закрыть приложение.

## 6. Trade-offs

### Мелкие границы против крупных

Мелкие границы (вокруг каждого виджета) сохраняют больше работающего интерфейса и дают точнее локализованные отчёты. Цена — больше fallback-состояний, которые нужно спроектировать, и риск, что сломанный виджет «тихо» пропадает, и пользователь не понимает, что данных не хватает. Крупные границы проще, но каждая ошибка уносит больше UI. Обычный компромисс — корень, экраны и несколько явно независимых виджетов.

### Fallback против деградации

Граница показывает **другой** UI вместо поддерева. Иногда лучше деградировать внутри компонента: показать урок без блока рекомендаций, не пряча весь урок. Это обработка ошибки в компоненте (состояние `error` в редьюсере, 3.8), а не граница. Граница — для неожиданного; ожидаемые ошибки (сеть, нет данных) обрабатываются явно.

### Повтор через ключ против восстановления состояния

Сброс ключом пересоздаёт поддерево целиком — всё состояние внутри теряется, включая введённый текст. Если поддерево содержит пользовательский ввод, его стоит хранить выше границы, чтобы повтор не уничтожил работу пользователя.
