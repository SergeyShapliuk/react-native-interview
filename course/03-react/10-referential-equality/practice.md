# 3.10 Referential equality — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать **какая ссылка меняется и кто это замечает** — а не «надо обернуть в `memo`».

---

**1. Родитель меняет своё состояние. Ребёнок не получает никаких пропсов. Отрендерится ли ребёнок?**

<details>
<summary>Ответ</summary>

Да. Когда React рендерит компонент, он вызывает функции всех его потомков — независимо от пропсов. Пропсы без `memo` не сравниваются вообще. Проверено на React 19.2: компонент без пропсов рендерится при каждом изменении состояния родителя; тот же компонент, обёрнутый в `memo`, — нет.

Три причины рендера компонента: изменилось его состояние, изменился контекст, который он читает, рендерится его родитель. Здесь — третья.

Хорошо ли это? Чаще всего безразлично: функция компонента без пропсов обычно дешёвая. Если ребёнок дорогой — есть два решения, и `memo` не всегда первое: можно передать ребёнка родителю извне через `children` (3.13) — тогда он создаётся выше и не рендерится при изменении состояния родителя.

**Ответ «нет, у него не изменились пропсы»** вскрывает самую распространённую неверную модель — «React сравнивает пропсы всегда».

**Ответ «да, но только если ребёнок использует что-то из родителя»** вскрывает модель «React отслеживает, что компонент читает». React не отслеживает; рендер родителя рендерит детей.
</details>

---

**2. `memo`-компонент получает `options={{ compact: true }}`. Сработает ли мемоизация?**

<details>
<summary>Ответ</summary>

Нет. `{ compact: true }` — литерал объекта в теле родителя, новый объект на каждый рендер. Shallow compare пропсов `memo` сравнивает значение ключа `options` через `Object.is` — ссылки разные, результат «не равно», компонент рендерится. Проверено на React 19.2: `memo`-компонент с инлайн-объектом рендерится вместе с родителем, с примитивом `compact={true}` — нет.

`memo` здесь хуже, чем бесполезен: каждый рендер родителя он сравнивает пропсы и всё равно рендерит.

Исправления, по возрастанию стоимости:

- передать примитив: `compact={true}`;
- вынести объект в константу модуля, если он не зависит от рендера: `const COMPACT = { compact: true }`;
- `useMemo`, если объект зависит от пропсов или состояния (3.11).

**Ответ «сработает, содержимое объекта одинаковое»** вскрывает смешение равенства содержимого и идентичности (1.12).

**Ответ «нужен кастомный компаратор с глубоким сравнением»** — работает, но лечит симптом дорогим способом и ломается на функциях.
</details>

---

**3. Обработчик делает `lessons.push(newLesson); setLessons(lessons)`. Иногда новый урок появляется в счётчике, но не в списке. Как это возможно?**

<details>
<summary>Ответ</summary>

`push` мутирует массив, `setLessons` получает ту же ссылку, и `Object.is(prev, next)` — `true`. React отбрасывает обновление: сразу или после «лишнего» вызова компонента (3.3), результат которого тоже выбрасывается. В момент нажатия на экране не меняется ничего.

Но мутированный массив уже лежит в состоянии. Когда экран отрендерится **по любой другой причине** (ввод в поиск, смена вкладки, ответ сети), компонент экрана прочитает массив заново, и счётчик `<Text>{lessons.length}</Text>` покажет новый урок. А список — `memo`-компонент или `FlatList` (`PureComponent`) — получит **ту же ссылку**, сравнение даст «равно», и он не перерисуется. Проверено на React 19.2: после `push` + `setItems(тот же массив)` экран не изменился; после постороннего обновления счётчик показал 3, список — 2 элемента.

Отсюда «иногда»: всё зависит от того, что и когда ещё вызовет рендер экрана, — а это несколько действий спустя от настоящей причины.

Вывод: мутация делает поведение зависимым от деталей реализации React, которые с точки зрения кода случайны. Исправление — новый массив: `setLessons((prev) => [...prev, newLesson])` (1.13).

**Ответ «это баг React»** вскрывает непонимание контракта: React сравнивает ссылки и вправе отбросить обновление с той же ссылкой.

**Ответ «надо вызвать `setLessons([...lessons])` после `push`»** — исправляет симптом, оставляя мутацию: массив из замыкания мутирован, и другой код, держащий ту же ссылку, увидит изменение без рендера.
</details>

---

**4. Обёртка дизайн-системы `Card` обёрнута в `memo` и раскладывает `{...rest}` в `View`. На экране она рендерится при каждом рендере родителя. Где искать причину?**

<details>
<summary>Ответ</summary>

В месте вызова — в пропсах, которые получает `Card`. Shallow compare проверяет каждый ключ, и достаточно одного нового по ссылке значения, чтобы мемоизация не сработала. Кандидаты, по частоте:

- `style={{ ... }}` или `style={[styles.card, isActive && styles.active]}` — массив тоже новый на каждый рендер;
- `onPress={() => ...}` — стрелка;
- `children` — JSX-элементы, созданные в рендере родителя, — новые объекты на каждый рендер. `memo` на компоненте, принимающем `children`, почти никогда не срабатывает (3.11, 3.13);
- `{...props}` от родителя — если родитель сам получил объекты из своего родителя, созданные при рендере.

`{...rest}` внутри `Card` не причина: он влияет на то, что `Card` передаёт дальше, а не на сравнение пропсов самой `Card`.

Метод поиска без профайлера: выписать все пропсы в месте вызова и для каждого ответить, создаётся ли значение в теле родителя. Профайлер (5.3) покажет то же самое — «какие пропсы изменились» — и подтвердит гипотезу.

**Ответ «`memo` не работает с `{...rest}`»** вскрывает поиск причины в реализации компонента вместо места вызова.
</details>

## Задание — карта ре-рендеров экрана поиска

**Дано.** Экран поиска уроков RN Academy. Жалоба: «на старом Android ввод в поиск подтормаживает». Профайлер пока не используем — задача найти причины по коду.

```jsx
const ThemeContext = createContext(null);

function SearchScreen({ lessons, user }) {
  const [query, setQuery] = useState('');
  const [sort, setSort] = useState('title');

  const visible = lessons
    .filter((l) => l.title.toLowerCase().includes(query.toLowerCase()))
    .sort((a, b) => (a[sort] > b[sort] ? 1 : -1));

  function openLesson(id) {
    navigation.navigate('Lesson', { id });
  }

  return (
    <ThemeContext.Provider value={{ dark: user.prefersDark }}>
      <Header title="Поиск" user={user} />
      <SearchInput value={query} onChangeText={setQuery} style={{ margin: 16 }} />
      <SortPicker value={sort} onChange={setSort} options={['title', 'duration']} />
      <FlatList
        data={visible}
        keyExtractor={(l) => l.id}
        renderItem={({ item }) => (
          <LessonRow lesson={item} onPress={() => openLesson(item.id)} />
        )}
      />
      <Footer />
    </ThemeContext.Provider>
  );
}

const Header = memo(function Header({ title, user }) { /* ... */ });
const SortPicker = memo(function SortPicker({ value, onChange, options }) { /* ... */ });
function LessonRow({ lesson, onPress }) {
  const theme = useContext(ThemeContext);
  /* ... */
}
function Footer() { /* ... */ }
```

**Требуется.**

1. Для одного введённого символа перечислить все компоненты, которые отрендерятся, и для каждого назвать причину: состояние, контекст или родитель — и, если речь о `memo`/`PureComponent`, какой именно пропс сломал сравнение.
2. Отдельно найти скрытую мутацию в коде и объяснить, почему она пока «не мешает».
3. Отсортировать находки по вкладу в проблему. Исправления не писать — это 3.11; но для каждой находки сказать, нужна ли там вообще стабильная ссылка.

---

<details>
<summary>Разбор</summary>

**1. Что рендерится на один символ.**

`setQuery` меняет состояние `SearchScreen` — он рендерится сам (причина: состояние). Дальше — его поддерево:

| Компонент | Рендерится? | Причина |
|---|---|---|
| `ThemeContext.Provider` | `value` новый | литерал `{ dark: ... }` — новый объект; `Object.is` → не равно; **все потребители контекста** помечаются к рендеру |
| `Header` (`memo`) | нет | `title` — строковый литерал, `user` — пропс той же ссылкой; сравнение «равно». Header не читает контекст |
| `SearchInput` | да | родитель (без `memo`); к тому же `style` — новый объект |
| `SortPicker` (`memo`) | **да** | `options={['title', 'duration']}` — новый массив; `memo` сравнивает и всё равно рендерит |
| `FlatList` (`PureComponent`) | да | `data` — новый массив (`filter` + `sort`), `renderItem` и `keyExtractor` — новые функции |
| ячейки `CellRenderer` | все видимые | новый `renderItem` |
| `LessonRow` | все видимые | `renderItem` создал новые элементы; `LessonRow` не в `memo`; **и** читает контекст, `value` которого новый |
| `Footer` | да | родитель |

`LessonRow` рендерится по двум независимым причинам: даже если завернуть его в `memo` и стабилизировать `renderItem` и `onPress`, новый `value` контекста всё равно отрендерит каждую строку. Это классический случай, где `memo` не помогает (3.14).

**2. Скрытая мутация.**

`.sort()` мутирует массив, на котором вызван. Здесь он вызван на результате `filter` — это новый массив, поэтому `lessons` из пропсов не мутируется. «Пока не мешает» — потому что `filter` стоит перед `sort`. Если кто-то уберёт фильтрацию (например, при пустом запросе «показывать всё без фильтра»: `query ? lessons.filter(...) : lessons`), `sort` начнёт мутировать массив из пропсов — массив родителя, возможно, состояние или кэш. Тогда сортировка «протечёт» в другие экраны, а `setState` родителя с этим массивом начнёт отбрасываться (вопрос 3). Безопасная форма — `[...arr].sort(...)` (1.5).

**3. Вклад и нужна ли стабильная ссылка.**

1. **`value` контекста** — наибольший вклад: рендерит каждую видимую строку независимо от `memo`. Стабильная ссылка **нужна**: значение сравнивают все потребители. Решение (3.14): мемоизировать `value` по `user.prefersDark` или передавать примитив.
2. **`renderItem` + `LessonRow` без `memo` + `onPress` стрелкой** — второй по вкладу: все видимые строки на каждый символ. Стабильная ссылка **нужна** для `renderItem` и `onPress` — их сравнивают `CellRenderer` и (после исправления) `memo` строки.
3. **`data`** — новый массив оправдан: он действительно меняется при вводе. Стабилизировать его ссылку для неизменного `query` имеет смысл, только если экран рендерится по другим причинам; фильтрация 200 уроков — недорого. Дорогой может быть сортировка на каждый символ — это вопрос `useMemo` по `[lessons, sort]` (3.11).
4. **`options` у `SortPicker`** — `memo` не работает из-за массива-литерала. Стабильная ссылка **нужна** (иначе `memo` бесполезен), и самая дешёвая — константа модуля.
5. **`style` у `SearchInput`, `keyExtractor`** — новые ссылки, которые **никто не сравнивает** с пользой: `SearchInput` не в `memo`, `keyExtractor` влияет только на ре-рендер самого `FlatList`, который рендерится из-за `data` всё равно. Стабилизировать не нужно.
6. **`Footer`** — рендерится как ребёнок; если он дешёвый, это безразлично. Если дорогой — `memo` или вынос из-под состояния через `children` (3.13).

Итог по жалобе: на старом Android основная работа — рендер всех видимых `LessonRow` на каждый символ, и причин две: новый `value` контекста и новый `renderItem` без `memo` на строке. Эту гипотезу в блоке 05 подтвердят профайлером на этом же компоненте.

**Вклад в проект (P3).** Для экрана списка RN Academy составлена карта ре-рендеров при вводе в поиск: какие компоненты рендерятся и по какой из трёх причин. Карта станет входом для 3.11 (что стабилизировать) и для 5.3 (подтверждение профайлером).
</details>
