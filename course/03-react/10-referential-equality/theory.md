# 3.10 Referential equality — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «почему компонент перерисовывается слишком часто» — а на вопрос, **где именно React сравнивает значения, каким алгоритмом, и что из этого следует для причины каждого рендера**.

---

## 1. Что это

**Referential equality** — равенство по ссылке: два значения равны, если это **один и тот же** объект, а не объекты с одинаковым содержимым (1.12). React использует его везде, где решает, изменилось ли что-то.

Два алгоритма:

- **`Object.is(a, b)`** — почти то же, что `===`, с двумя отличиями: `Object.is(NaN, NaN)` — `true`, `Object.is(0, -0)` — `false`. Для объектов, массивов и функций — сравнение ссылок;
- **shallow compare** — сравнение двух объектов на один уровень вглубь: одинаковый набор ключей и `Object.is` для значения каждого ключа.

### Ключевая формулировка урока

> **React нигде не сравнивает содержимое. Он сравнивает ссылки — через `Object.is` для состояния, зависимостей и контекста и поверхностно, по ключам, для пропсов `memo`.**

---

## 2. Как это работает

### Четыре места сравнения

| Где | Алгоритм | Что следует из «равно» |
|---|---|---|
| `setState(next)` / `dispatch` | `Object.is(prev, next)` | обновление отбрасывается, потомки не рендерятся (3.3) |
| массив зависимостей | `Object.is` поэлементно | эффект не перезапускается, `useMemo`/`useCallback` возвращают прежнее (3.5) |
| пропсы `memo` / `PureComponent` | shallow compare | компонент пропускает рендер (3.11) |
| `value` у провайдера контекста | `Object.is(prev, next)` | потребители не помечаются к рендеру (3.14) |

Больше React нигде не сравнивает. В частности, **без `memo` пропсы не сравниваются вообще**.

### Почему компонент рендерится

Причин три:

1. **изменилось его состояние** — `setState` с новым по `Object.is` значением;
2. **изменился контекст, который он читает** — новый по `Object.is` `value` у ближайшего провайдера;
3. **рендерится его родитель.**

Третья причина — самая частая и самая недооценённая. Когда React рендерит компонент, он вызывает функции **всех** его потомков — независимо от того, изменились ли их пропсы, есть ли у них пропсы вообще. Проверено на React 19.2: родитель меняет своё состояние, ребёнок без пропсов рендерится вместе с ним.

```jsx
function LessonScreen() {
  const [query, setQuery] = useState('');
  return (
    <>
      <SearchInput value={query} onChange={setQuery} />
      <LessonHeader />          {/* без пропсов — рендерится на каждый символ */}
      <LessonList query={query} />
    </>
  );
}
```

Остановить распространение рендера вниз может только компонент, который умеет пропустить свою работу: обёрнутый в `memo` (или классовый `PureComponent`), у которого shallow compare пропсов дал «равно». Тогда пропускается и он, и всё его поддерево — кроме потомков, читающих изменившийся контекст.

Словосочетание «лишний рендер» на этом фоне означает: компонент вызван, а результат совпал с предыдущим. Сам по себе он не ошибка — React рассчитан на то, что функции компонентов дешёвые, и большая часть «лишних» рендеров не стоит ничего заметного. Проблемой он становится, когда поддерево большое, рендер частый или компонент дорогой — тогда вопрос «почему он рендерится» нужно уметь решать по коду.

### Что создаёт новую ссылку на каждый рендер

Любое выражение, создающее объект, массив или функцию в теле компонента:

```jsx
<LessonCard
  style={{ padding: 8 }}                       // новый объект
  tags={['react', 'rn']}                       // новый массив
  onPress={() => open(lesson.id)}              // новая функция
  lesson={{ ...lesson, progress }}             // новый объект
  items={lessons.filter((l) => l.done)}        // новый массив
  {...props}                                   // сами значения те же, но если в props — объекты из рендера родителя, они новые там
/>
```

Сами по себе новые ссылки ничего не стоят: создание объекта — наносекунды. Важно, **замечает ли кто-нибудь**, что ссылка новая:

- получатель — `memo`-компонент: его сравнение пропсов даст «не равно», мемоизация не сработает;
- значение попадает в массив зависимостей: эффект перезапустится, `useMemo` пересчитает;
- значение — `value` контекста: все потребители отрендерятся;
- значение уходит в `setState`: обновление не будет отброшено.

Если никто не замечает — новая ссылка безвредна. Главный навык урока: по коду назвать, **какая ссылка меняется и кто это замечает**.

### Что считается «тем же»

Стабильны между рендерами:

- примитивы с тем же значением (`'done'`, `42`, `true`);
- сеттеры `useState`, `dispatch`, объект `useRef` — гарантии React;
- значения, объявленные вне компонента: константы модуля, `StyleSheet.create(...)` на уровне модуля, импортированные функции;
- результат `useMemo` / `useCallback`, пока не изменились их зависимости (3.11);
- пропс, который родитель передал той же ссылкой;
- состояние, которое не менялось.

### Мутация: «`setState` не сработал»

```jsx
function onAdd(lesson) {
  items.push(lesson);
  setItems(items);        // та же ссылка
}
```

`Object.is(items, items)` — `true`. React отбрасывает обновление: потомки не рендерятся, эффекты с `items` в зависимостях не перезапускаются.

Иногда React при этом всё же вызывает компонент — когда ранняя проверка равенства невозможна (3.3), — но, обнаружив то же состояние, **выбрасывает результат вызова целиком**: экран не меняется, потомки не рендерятся. Проверено на React 19.2: компонент вызван, в его рендере `items.length === 3`, а на экране по-прежнему 2.

Настоящая проблема проявляется позже. Мутированный массив уже лежит в состоянии, и **следующий рендер по любой другой причине** его покажет — но не везде. Компонент, читающий массив сам, покажет 3 элемента; `memo`-компонент или `FlatList` (`PureComponent`), получивший ту же ссылку, пропустит рендер и останется с 2. Тот же эксперимент: после постороннего обновления счётчик показывает 3, список — 2 элемента. Экран рассогласован, и связь с исходным `push` не видна: он случился несколько действий назад.

Вывод не «мутация иногда работает», а **мутация делает поведение зависимым от деталей реализации React**. Иммутабельное обновление (1.13) — `setItems([...items, lesson])` — даёт новую ссылку, и всё дальнейшее предсказуемо.

### Ограничения shallow compare

Поверхностное сравнение пропсов — один уровень:

```jsx
<LessonCard lesson={lesson} />                    // ссылка lesson та же → равно
<LessonCard lesson={{ ...lesson }} />             // новая ссылка → не равно, хотя содержимое то же
<LessonCard meta={{ tags: lesson.tags }} />       // новая ссылка на обёртку → не равно
```

И в обратную сторону: если `lesson` мутирован (поле изменено на месте), ссылка та же — `memo` скажет «равно» и пропустит рендер, хотя данные изменились. Shallow compare корректен только для иммутабельных данных.

## 3. Почему это важно

**Причина рендера читается по коду.** Три причины, четыре места сравнения, один вопрос «какая ссылка меняется и кто это замечает» — этого достаточно, чтобы для любого компонента на экране назвать, почему он рендерится, не запуская профайлер. Профайлер (5.3) потом подтверждает или опровергает гипотезу, но гипотеза строится по коду.

**`memo` без понимания ссылок не работает.** Самая частая история: компонент обёрнут в `memo`, но рендерится так же часто, потому что получает инлайн-объект или стрелку. Без этого урока `memo` расставляют наугад и удивляются, что ничего не изменилось.

**Иммутабельность — не стиль, а условие корректности.** Весь механизм сравнения React построен на том, что изменённые данные — это новые объекты. Мутация ломает этот контракт тихо: обновление теряется сейчас, а позже проявляется наполовину — там, где ссылку никто не сравнивает.

## 4. Где это в React Native

### Инлайн-стили и пропсы списков

Типовой RN-код создаёт новые ссылки в каждом рендере:

```jsx
<FlatList
  data={lessons.filter((l) => !l.hidden)}
  renderItem={({ item }) => <LessonRow lesson={item} onPress={() => open(item.id)} />}
  contentContainerStyle={{ paddingBottom: 24 }}
  keyExtractor={(item) => item.id}
/>
```

Каждый рендер экрана даёт новый `data`, новый `renderItem`, новый объект стиля и новый `keyExtractor`. Кто это замечает? В `@react-native/virtualized-lists` 0.87 и `VirtualizedList`, и обёртка каждой ячейки (`CellRenderer`) — классовые `PureComponent`, сравнивающие пропсы поверхностно:

- новый `data` (или стиль, или `keyExtractor`) — список рендерится заново, но ячейки, получившие тот же элемент и тот же `renderItem`, пропускают работу;
- новый `renderItem` — каждая видимая ячейка получает новый пропс и вызывает его заново; `renderItem` создаёт новые элементы `LessonRow`, и если `LessonRow` не обёрнут в `memo`, рендерятся все видимые ячейки на каждый символ в поиске.

### `StyleSheet.create` против инлайн-объекта

```jsx
const styles = StyleSheet.create({ row: { padding: 8 } });   // уровень модуля
<View style={styles.row} />                                  // та же ссылка всегда
<View style={{ padding: 8 }} />                              // новая ссылка каждый рендер
```

Для host-компонента `View` новая ссылка стиля почти ничего не стоит: React передаст пропс в нативный слой, и нативная сторона увидит, что значения не изменились. Разница становится важной, когда стиль уходит в `memo`-компонент или в зависимость эффекта.

### `{...props}` в обёртках дизайн-системы

Обёртка, раскладывающая `{...rest}` в нативный компонент, передаёт дальше всё, что получила, — включая инлайн-объекты родителя. Если обёртка в `memo`, её сравнение будет «не равно» каждый раз, пока родитель создаёт новые объекты.

### Значения из навигации

`route.params` и объекты из хуков навигации могут быть новыми ссылками на каждый рендер в зависимости от библиотеки и способа передачи. В зависимостях и пропсах `memo`-компонентов надёжнее использовать примитивные поля, чем объект целиком (3.5).

## 5. Типичные ошибки

**«Компонент рендерится, только если изменились его пропсы».** Возникает из модели «React сравнивает пропсы всегда». Без `memo` пропсы не сравниваются: рендер родителя рендерит детей. Из этой ошибки растёт `memo` на всём подряд «чтобы проверялись пропсы».

**«Одинаковые объекты равны».** Возникает, когда равенство содержимого путают с идентичностью (1.12). `{ compact: true }` в двух рендерах — два разных объекта.

**Мутация состояния и `setState` с той же ссылкой.** `push`, `sort`, `splice`, присваивание поля — и `setState(sameRef)`. Возникает из привычки к изменяемым структурам и из того, что иногда «работает». Результат — потерянное или наполовину применённое обновление.

**Глубокое сравнение как решение.** Кастомный компаратор `memo` с `JSON.stringify` или deep-equal. Возникает из желания «сравнивать по-честному». Глубокое сравнение стоит пропорционально размеру данных на каждый рендер — часто дороже, чем сам рендер, — и ломается на функциях и циклических структурах.

**Новая ссылка как причина любой проблемы.** Обратная ошибка: стабилизировать каждую ссылку через `useMemo`/`useCallback`. Возникает после первого знакомства с темой. Новая ссылка, которую никто не сравнивает, безвредна; стабилизация стоит кода и памяти (3.11).

**«Ребёнок не рендерится, потому что у него нет пропсов».** Возникает из той же модели, что первая ошибка. Отсутствие пропсов не защищает: защищает `memo`.

## 6. Trade-offs

### Ссылочное сравнение против сравнения содержимого

React выбрал сравнение ссылок: оно стоит O(1) независимо от размера данных и не зависит от структуры. Цена — требование иммутабельности: изменённые данные должны быть новыми объектами, а неизменённые — сохранять ссылки. Это переносит работу на автора кода: аккуратные обновления (1.13), стабильные ссылки там, где их сравнивают. Сравнение содержимого сняло бы это требование — и сделало бы каждое сравнение пропорциональным размеру данных, а результат — зависимым от того, что считать «тем же» (функции, даты, `NaN`).

### Рендер против сравнения

Без `memo` React не тратит время на сравнение пропсов, но рендерит поддерево. С `memo` — тратит на сравнение и экономит рендер, если сравнение «равно». Если пропсы меняются почти всегда, `memo` — чистый проигрыш: сравнение каждый раз плюс рендер. Когда мемоизация окупается — тема 3.11.

### Структурное разделение

Иммутабельные обновления при правильном написании сохраняют ссылки на неизменённые части (1.13): обновление одного урока в массиве даёт новый массив и новый объект этого урока, а остальные уроки — те же объекты. Именно это делает `memo` на ячейках списка эффективным: ячейки неизменённых уроков получают те же ссылки и пропускают рендер. Цена — дисциплина обновлений и иногда нормализация данных (6.8).
