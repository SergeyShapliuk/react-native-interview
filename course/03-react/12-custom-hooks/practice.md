# 3.12 Кастомные хуки — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует сказать, **во что хук разворачивается в теле компонента** и что из его возврата увидит вызывающий.

---

**1. Шапка и экран корзины вызывают `useCart()`. В экране добавили товар. Увидит ли это шапка?**

```js
function useCart() {
  const [items, setItems] = useState([]);
  const add = (item) => setItems((prev) => [...prev, item]);
  return { items, add };
}
```

<details>
<summary>Ответ</summary>

Нет. Хук разворачивается в тело каждого вызывающего компонента: у шапки свой `useState`, у экрана — свой. Это два независимых состояния, связанных только тем, что их создаёт одинаковый код. Добавление в экране меняет состояние экрана; шапка показывает свой пустой массив.

Хук переиспользует **логику** (как хранить и менять корзину), а не **состояние**. Для общих данных нужен один источник: поднять состояние в общего родителя, контекст (3.14) или внешний стор (3.19, 6.3). Хук тогда становится способом **читать** общий источник — `useCart()` внутри делает `useContext(CartContext)` или `useSyncExternalStore(cartStore...)`.

**Ответ «увидит, хук один и тот же»** вскрывает модель «хук — это сервис-синглтон».

**Ответ «увидит, если вынести `useState` на уровень модуля»** — так нельзя: хук вне компонента не к чему привязать (3.5). А `let items` на уровне модуля не вызовет рендер ни у кого.
</details>

---

**2. В проекте есть `useFormatPrice(value)`, внутри — `Intl.NumberFormat` и шаблонная строка. Что с ним не так?**

<details>
<summary>Ответ</summary>

Это не хук: внутри нет ни состояния, ни эффектов, ни других хуков. Префикс `use` здесь только ограничивает:

- нельзя вызвать в обработчике (`onPress={() => share(useFormatPrice(x))}` — нарушение правил хуков);
- нельзя вызвать в цикле или условно;
- нельзя вызвать вне компонента — в доменной функции, в тесте без рендера, в обработчике уведомления.

При этом ничего не выиграно: функция вычисляется на каждый вызов так же, как обычная. Правильно — `formatPrice(value)` как обычная функция, а если создание `Intl.NumberFormat` дорого — форматтер создаётся один раз на уровне модуля.

Хук оправдан, если форматирование зависит от реактивных данных: например, `useFormatPrice` читает локаль и валюту из контекста. Тогда внутри есть `useContext`, и префикс — честный.

**Ответ «префикс `use` — это просто стиль»** вскрывает незнание того, что префикс включает проверки линтера и компилятора.
</details>

---

**3. `useDebouncedCallback` возвращает новую функцию на каждый рендер. Что сломается у вызывающего?**

<details>
<summary>Ответ</summary>

Зависит от того, где вызывающий использует функцию, — и в каждом случае ломается что-то своё:

- **в зависимостях эффекта** — эффект перезапускается на каждый рендер; если эффект подписывается на событие, подписка пересоздаётся постоянно;
- **в пропсе `memo`-компонента** — мемоизация не работает;
- **внутри самого debounce** — если таймер хранится в замыкании новой функции, а не в ref, каждый рендер создаёт новую debounced-функцию со своим таймером. Вызов из старой версии и вызов из новой не отменяют друг друга: debounce перестаёт работать, срабатывают оба.

Последний случай — самый коварный: хук выглядит работающим в изоляции (один рендер — один вызов), а в реальном экране, где ввод вызывает рендер на каждый символ, debounce не происходит вообще.

Правильный контракт: возвращаемая функция стабильна между рендерами (зависит только от задержки), таймер живёт в ref, актуальный колбэк читается через ref в момент срабатывания. Реализация — в разборе задания.

**Ответ «ничего, функция же вызывается правильно»** вскрывает проверку хука одним вызовом, а не в реальном цикле рендеров.
</details>

---

**4. Хук `useAsync(fn, deps)` передаёт `deps` во внутренний `useEffect`. Линтер внутри хука требует подавить предупреждение. Как не потерять проверку зависимостей?**

<details>
<summary>Ответ</summary>

Внутри хука линтер не может проверить массив, пришедший параметром: он не знает, что функция `fn` читает. Подавление там с комментарием о причине — одно из честных исключений (3.5).

Проверку переносят на **место вызова**: в конфигурации правила `exhaustive-deps` указывается

```js
'react-hooks/exhaustive-deps': ['warn', { additionalHooks: '^useAsync$' }]
```

Тогда у каждого вызова `useAsync(() => api.load(lessonId, lang), [lessonId])` линтер проверяет массив так же, как у `useEffect`, — проверено: «React Hook useAsync has a missing dependency: 'lang'».

Без этого массив на месте вызова остаётся непроверенным, и пропущенная зависимость даёт загрузку с устаревшими аргументами — ровно та ошибка, от которой линтер защищает в обычных эффектах.

**Ответ «подавить и забыть»** — массивы в местах вызова никто не проверит.
</details>

## Задание — `useDebounce` / `useThrottle` и `useAsync`

**Дано.** Поиск по курсам RN Academy отправляет запрос на каждый введённый символ; обработчик прокрутки списка пишет аналитику на каждое событие; экран урока загружает данные кодом, скопированным между тремя экранами.

**Требуется.**

1. Написать `useDebouncedValue(value, delayMs)` — значение, которое обновляется только после паузы во вводе.
2. Написать `useDebouncedCallback(fn, delayMs)` и `useThrottledCallback(fn, intervalMs)`. Явно сформулировать контракт: что стабильно по ссылке, какую версию `fn` вызывает таймер, что происходит при размонтировании.
3. Написать базовый `useAsync(fn, deps)` на редьюсере из 3.8: состояния `idle / pending / success / error`, устаревший ответ не перезаписывает новый. Гонки и отмену полностью не решать — это блок 07.
4. Для каждого хука ответить: почему это хук, а не обычная функция?

---

<details>
<summary>Разбор</summary>

Все реализации проверены на React 19.2 в StrictMode: поведение ниже — результат запуска.

**1. `useDebouncedValue`.**

```js
export function useDebouncedValue(value, delayMs) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(id);
  }, [value, delayMs]);
  return debounced;
}
```

Механизм — пара «эффект — очистка» (3.4): каждое изменение `value` очищает предыдущий таймер и ставит новый. Значение обновится, только когда `value` не меняется `delayMs`. При вводе «r», «re», «rea» с интервалом 10 мс и задержкой 30 мс `debounced` проходит путь `"" → "rea"`, минуя промежуточные. Таймер — внешняя система, поэтому здесь эффект на своём месте (3.7).

Использование:

```js
const [query, setQuery] = useState('');
const debouncedQuery = useDebouncedValue(query, 300);
const results = useAsync(() => api.searchCourses(debouncedQuery), [debouncedQuery]);
```

Поле ввода отзывается мгновенно (`query`), запрос уходит по `debouncedQuery`.

**2. `useDebouncedCallback` и `useThrottledCallback`.**

```js
export function useDebouncedCallback(fn, delayMs) {
  const fnRef = useRef(fn);
  const timerRef = useRef(null);

  useEffect(() => { fnRef.current = fn; });                         // последняя версия fn
  useEffect(() => () => clearTimeout(timerRef.current), []);        // отмена при размонтировании

  return useMemo(() => {
    const debounced = (...args) => {
      clearTimeout(timerRef.current);
      timerRef.current = setTimeout(() => fnRef.current(...args), delayMs);
    };
    debounced.cancel = () => clearTimeout(timerRef.current);
    return debounced;
  }, [delayMs]);
}

export function useThrottledCallback(fn, intervalMs) {
  const fnRef = useRef(fn);
  const lastRef = useRef(0);

  useEffect(() => { fnRef.current = fn; });

  return useCallback((...args) => {
    const now = Date.now();
    if (now - lastRef.current >= intervalMs) {
      lastRef.current = now;
      fnRef.current(...args);
    }
  }, [intervalMs]);
}
```

**Контракт, записанный явно:**

- **стабильность** — возвращаемая функция меняется только при смене задержки или интервала; её можно передавать в `memo`-компоненты и указывать в зависимостях;
- **какая версия `fn`** — таймер вызывает **последнюю** переданную `fn`, а не ту, что была при вызове debounced-функции. В эксперименте колбэк, вызванный через debounce, видел актуальное состояние на момент срабатывания. Это осознанный выбор «актуальное значение» из 1.14; если нужен снимок, аргументы передаются явно при вызове;
- **размонтирование** — ожидающий вызов debounce отменяется; throttle ничего не откладывает и отменять ему нечего;
- **`cancel`** — debounce можно отменить вручную, например при отправке формы.

Почему таймер в ref, а не в замыкании: функция стабильна, но таймер должен быть общим для всех её вызовов; почему `fnRef` обновляется в эффекте, а не при рендере: запись в ref при рендере — побочный эффект (3.9). В React 19.2 `useEffectEvent` для этого не подходит: функцию из него нельзя возвращать из хука и передавать дальше (3.5).

В эксперименте три быстрых вызова debounce дали один вызов с последним аргументом; шесть вызовов throttle с шагом 15 мс и интервалом 50 мс дали два вызова — с аргументами 0 и 3.

**3. `useAsync` на редьюсере.**

```js
function asyncReducer(state, action) {
  switch (action.type) {
    case 'started':  return { status: 'pending', data: state.data, error: null };
    case 'resolved': return { status: 'success', data: action.data, error: null };
    case 'rejected': return { status: 'error', data: state.data, error: action.error };
    default:         return state;
  }
}

export function useAsync(asyncFn, deps) {
  const [state, dispatch] = useReducer(asyncReducer, { status: 'idle', data: undefined, error: null });

  useEffect(() => {
    let ignore = false;
    dispatch({ type: 'started' });
    asyncFn().then(
      (data) => { if (!ignore) dispatch({ type: 'resolved', data }); },
      (error) => { if (!ignore) dispatch({ type: 'rejected', error }); },
    );
    return () => { ignore = true; };
    // deps приходят от вызывающего; проверяются на месте вызова через additionalHooks
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, deps);

  return state;
}
```

Решения:

- **редьюсер** делает невозможными комбинации «pending с ошибкой» и «success с ошибкой» (3.8); `data` сохраняется при повторной загрузке, чтобы экран не мигал пустым состоянием;
- **флаг `ignore`** в очистке — ответ на устаревший запрос не перезаписывает новый: при смене `id` с медленным первым запросом экран показал `lesson 2`, а не `lesson 1`, пришедший позже. В StrictMode первый из двух запросов при монтировании тоже игнорируется;
- **чего нет**: отмены самого запроса (`AbortController`), повторов, кэша, дедупликации одинаковых запросов с разных экранов. Это не недоработка, а граница: всё это — блок 07, и в реальном проекте эту роль берёт TanStack Query или RTK Query.

Конфигурация линтера проекта получает `additionalHooks: '^useAsync$'`.

**4. Почему это хуки.**

Все четыре используют хуки внутри: состояние (`useState`, `useReducer`), эффекты с очисткой (таймер, флаг устаревшего запроса), ref для таймера и актуального колбэка, мемоизацию возвращаемой функции. Обычная функция не может ни хранить состояние между рендерами, ни очистить таймер при размонтировании. Обратный пример из того же экрана — построение строки запроса из фильтров: чистая функция без хуков, её место — в домене.

**Вклад в проект (P3).** В RN Academy появляется набор инфраструктурных хуков с явными контрактами: `useDebouncedValue` в поиске по курсам, `useThrottledCallback` для аналитики прокрутки, `useAsync` для загрузки урока. `useLessonProgress` из контракта 2.14 получает реализацию с описанной стабильностью `save`. Хуки покрываются тестами на стадии P3, а переход `useAsync` на библиотеку кэша — решение блока 07.
</details>
