# 3.11 `memo` / `useMemo` / `useCallback` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как мемоизировать компонент» — а на вопрос, **в каких местах кода стабильная ссылка кому-то нужна, и чем мемоизация платит там, где не нужна**.

---

## 1. Что это

Три инструмента, решающие одну задачу — не делать работу заново, если входные данные не изменились:

- **`memo(Component, arePropsEqual?)`** — обёртка компонента: если пропсы поверхностно равны предыдущим (3.10), React пропускает рендер компонента и всего его поддерева (кроме потомков, читающих изменившийся контекст);
- **`useMemo(compute, deps)`** — кэш одного значения внутри компонента: `compute` вызывается заново, только когда изменились зависимости;
- **`useCallback(fn, deps)`** — то же для функции: возвращает прежнюю функцию, пока не изменились зависимости. Это ровно `useMemo(() => fn, deps)`.

### Ключевая формулировка урока

> **Мемоизация — это не оптимизация сама по себе, а обещание стабильной ссылки. Она окупается, только если кто-то эту стабильность проверяет: `memo`-компонент, зависимость эффекта или дорогое вычисление.**

---

## 2. Как это работает

### `memo`

```jsx
const LessonRow = memo(function LessonRow({ lesson, onToggle }) {
  /* ... */
});
```

Перед тем как вызвать `LessonRow`, React сравнивает новые пропсы с прошлыми: тот же набор ключей и `Object.is` для каждого значения. «Равно» — рендер пропускается, используется прошлый результат. «Не равно» — обычный рендер.

`memo` останавливает только **третью** причину рендера из 3.10 — рендер родителя. Собственное состояние и контекст рендерят компонент как обычно.

Второй аргумент — кастомный компаратор `(prev, next) => boolean`. Им можно, например, сравнивать только `lesson.id` и `lesson.done`. Опасность в том, что компаратор, вернувший «равно» при изменившемся пропсе, оставляет на экране старый результат — и делает это молча. Особенно коварен случай, когда игнорируется функция-пропс: компонент продолжает вызывать обработчик из старого рендера родителя со старыми значениями в замыкании (1.14).

### `useMemo`

```jsx
const sorted = useMemo(
  () => [...lessons].sort(byTitle),
  [lessons],
);
```

React хранит на fiber пару «зависимости — результат». При рендере сравнивает зависимости (`Object.is` поэлементно, 3.5); если равны — возвращает сохранённый результат, не вызывая функцию.

Две разные задачи, которые решает `useMemo`:

1. **дорогое вычисление** — не пересчитывать, если вход не изменился. Сортировка тысяч элементов, построение индекса, агрегация;
2. **стабильная ссылка** — вычисление дешёвое, но результат — объект или массив, который **кто-то сравнивает**: пропс `memo`-компонента, зависимость эффекта, `value` контекста.

Без одной из этих причин `useMemo` — лишняя работа.

### `useCallback`

```jsx
const onToggle = useCallback(
  (id) => setLessons((prev) => toggleDone(prev, id)),
  [],
);
```

Функция-стрелка **создаётся на каждый рендер** всё равно — это выражение в теле компонента. `useCallback` не предотвращает создание; он **возвращает прежнюю** функцию, если зависимости не изменились, а новую выбрасывает. Польза одна — стабильная ссылка для того, кто её сравнивает.

Функциональное обновление внутри (`setLessons((prev) => ...)`) — то, что позволяет оставить массив пустым честно (3.5): колбэк не читает `lessons`.

### Цепочка: мемоизация работает только целиком

Проверено на React 19.2:

- **`useCallback` без `memo` у получателя** — получатель рендерится вместе с родителем, его пропсы не сравниваются. Стабильная ссылка никому не нужна;
- **`memo` без стабильных пропсов** — сравнение каждый раз даёт «не равно», компонент рендерится, и вдобавок тратится время на сравнение;
- **`memo` на компоненте, принимающем `children`** — JSX-элементы, созданные в рендере родителя, — новые объекты на каждый рендер. Сравнение `children` всегда «не равно», `memo` не срабатывает;
- **всё вместе** — `memo` на ячейке, стабильный обработчик, иммутабельные обновления со структурным разделением (1.13): при изменении одного элемента из трёх рендерится одна ячейка.

```
memo на получателе  +  стабильные пропсы  +  неизменённые данные — те же объекты
        ↑                     ↑                              ↑
   кто сравнивает    useMemo / useCallback /         иммутабельные обновления
                     константы модуля / примитивы
```

Если не хватает любого звена — мемоизация не работает, а её стоимость остаётся.

### Альтернативы до мемоизации

Часто лишний рендер убирается изменением **структуры** дерева, без единого `memo`:

**Опустить состояние вниз.** Если состояние нужно только части экрана, его место — в компоненте этой части:

```jsx
// было: каждый символ рендерит весь экран
function LessonScreen() {
  const [note, setNote] = useState('');
  return <><HeavyPlayer /><NoteInput value={note} onChange={setNote} /></>;
}

// стало: каждый символ рендерит только NoteEditor
function LessonScreen() {
  return <><HeavyPlayer /><NoteEditor /></>;
}
function NoteEditor() {
  const [note, setNote] = useState('');
  return <NoteInput value={note} onChange={setNote} />;
}
```

**Поднять содержимое вверх через `children`.** Если обёртка со своим состоянием должна содержать тяжёлое поддерево, поддерево создаётся выше и передаётся как `children` — тогда оно не рендерится при изменении состояния обёртки (3.13).

Оба приёма бесплатны по рантайму и не требуют следить за стабильностью ссылок.

### Подсказка, а не гарантия

Документация React формулирует `useMemo` как оптимизацию производительности, а не семантическую гарантию: React вправе сбросить кэш (например, для экранов вне видимости в будущих возможностях) и вызвать функцию заново. Отсюда правило: код должен быть **корректен без мемоизации** и только быстрее с ней. Если корректность зависит от того, что значение не пересоздаётся — например, эффект с запросом не должен перезапускаться, — это повод пересмотреть эффект (3.5, 3.7), а не опираться на `useMemo`.

## 3. Почему это важно

**Мемоизация наугад не ускоряет и усложняет.** `useCallback` на каждом обработчике, `useMemo` на каждом вычислении, `memo` на каждом компоненте — типичный результат «оптимизации по чек-листу». Большая часть этих вызовов не работает (нет того, кто сравнивает) и стоит: сравнения зависимостей на каждый рендер, память под кэш, зависимости, которые нужно поддерживать честными, и код, который труднее читать.

**Там, где мемоизация нужна, без неё заметно.** Ячейки списка, тяжёлые поддеревья, дорогие вычисления при частых рендерах — здесь отсутствие мемоизации даёт реальные потерянные кадры. Задача не «мемоизировать меньше» или «больше», а «там, где кто-то сравнивает».

**Ложная мемоизация маскирует проблемы.** Кастомный компаратор, игнорирующий часть пропсов, и `useMemo`, на который опирается корректность, создают дефекты, которые проявляются редко и выглядят как «устаревшие данные».

## 4. Где это в React Native

### Ячейка списка — главное место

`FlatList` вызывает `renderItem` для каждой видимой ячейки при каждом изменении `renderItem` (3.10). Если компонент ячейки не в `memo`, любое обновление экрана рендерит все видимые строки. Работающая комбинация:

```jsx
const LessonRow = memo(function LessonRow({ lesson, onToggle }) {
  return (
    <Pressable onPress={() => onToggle(lesson.id)}>
      <Text>{lesson.title}</Text>
    </Pressable>
  );
});

function LessonList({ lessons, setLessons }) {
  const onToggle = useCallback(
    (id) => setLessons((prev) => prev.map((l) => (l.id === id ? { ...l, done: !l.done } : l))),
    [setLessons],
  );
  const renderItem = useCallback(
    ({ item }) => <LessonRow lesson={item} onToggle={onToggle} />,
    [onToggle],
  );
  return <FlatList data={lessons} renderItem={renderItem} keyExtractor={(l) => l.id} />;
}
```

Три звена: `memo` на `LessonRow`; стабильные `onToggle` и `renderItem`; иммутабельное обновление, при котором неизменённые уроки остаются теми же объектами. Стрелка `() => onToggle(lesson.id)` внутри `LessonRow` — новая на каждый рендер **ячейки**, но её никто не сравнивает: `Pressable` не `memo`. Это нормально.

Списки и рециклинг подробно — 5.4: там к этому добавляются `getItemLayout`, размер окна и FlashList.

### Пропсы дорогих нативных компонентов

Карта с маркерами, видеоплеер, график: компоненты, у которых применение новых пропсов к нативному view стоит заметно. Новый массив маркеров на каждый рендер экрана — это пересчёт и пересылка маркеров в нативный слой. `useMemo` на массиве маркеров с честными зависимостями — оправдан.

### Обработчики `Pressable` и `Button`

`useCallback` на `onPress` встроенного `Pressable` — классический пример бесполезной мемоизации: `Pressable` не `memo`, его пропсы не сравниваются, рендер не сэкономлен.

### Стили

`StyleSheet.create` на уровне модуля даёт стабильные ссылки бесплатно. Динамический стиль, зависящий от состояния, — `useMemo`, только если он уходит в `memo`-компонент; для host-компонента новый объект стиля почти ничего не стоит (3.10).

## 5. Типичные ошибки

**«`useCallback` предотвращает пересоздание функции».** Возникает из названия. Функция создаётся при каждом рендере; `useCallback` возвращает старую. Выигрыш только у того, кто сравнивает ссылку.

**`useCallback` на всё.** Возникает из правила «так быстрее». Без `memo` у получателя и без использования в зависимостях — чистые потери: сравнение зависимостей, память, и массив зависимостей, который нужно поддерживать честным (3.5).

**`useMemo` для дешёвого вычисления.** `useMemo(() => items.filter(x => x.done), [items])` на двадцати элементах. Возникает из ощущения, что «вычисление при каждом рендере — плохо». Фильтрация двадцати элементов стоит меньше, чем сравнение зависимостей плюс хранение кэша. Правило документации React: мемоизировать, если вычисление заметно (порядка миллисекунды и больше) — и проверять замером, а не на глаз.

**`memo` на компоненте, принимающем `children`.** Возникает из желания «защитить обёртку». `children` — новые элементы каждый рендер; `memo` не срабатывает никогда.

**Кастомный компаратор, игнорирующий функции.** `(prev, next) => prev.lesson.id === next.lesson.id`. Возникает из желания «сделать `memo` наконец работающим». Компонент вызывает устаревшие обработчики и показывает устаревшие данные.

**Мемоизация вместо исправления структуры.** `memo` на тяжёлом соседе вместо того, чтобы опустить состояние в компонент, которому оно нужно. Возникает потому, что `memo` — локальная правка, а перестройка дерева — нет. Структурное решение обычно проще и надёжнее.

**Корректность, зависящая от `useMemo`.** Объект из `useMemo` в зависимостях эффекта с запросом, «чтобы запрос не повторялся». Возникает, когда `useMemo` используют как семантическую гарантию. Если кэш сбросится, запрос повторится; правильнее — примитивы в зависимостях (3.5).

## 6. Trade-offs

### Стоимость рендера против стоимости сравнения и поддержки

У мемоизации три цены:

- **рантайм** — сравнение пропсов или зависимостей на каждый рендер, хранение кэша;
- **сопровождение** — каждая мемоизация добавляет массив зависимостей, который должен оставаться честным; ошибка в нём даёт stale closure или бесполезную мемоизацию;
- **читаемость** — компонент, обёрнутый в три уровня `useCallback`, труднее читать и менять.

Выгода одна — пропущенная работа. Мемоизация окупается, когда пропущенная работа заметно больше суммы цен: большое поддерево, частый рендер, дорогое вычисление. Где это так, решает не правило, а рассуждение по коду (3.10) и замер (5.3).

### Ручная мемоизация против структуры

Структурные приёмы (состояние ниже, содержимое выше через `children`) бесплатны в рантайме, но меняют форму дерева и иногда — API компонентов. Ручная мемоизация локальна, но хрупка. В команде разумно сначала спрашивать «можно ли так устроить дерево, чтобы этот рендер не происходил», и только потом — «как его пропустить».

### Ручная мемоизация против компилятора

React Compiler (3.18) мемоизирует автоматически и гранулярнее, чем это делают руками. С ним большая часть ручных `useMemo`/`useCallback` становится избыточной. Но компилятор работает только с кодом, соблюдающим правила React, и не отменяет понимания: где стабильность ссылки нужна для корректности, а не только для скорости, — решение остаётся за автором.
