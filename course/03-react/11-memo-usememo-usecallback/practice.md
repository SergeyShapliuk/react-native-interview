# 3.11 `memo` / `useMemo` / `useCallback` — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **кто сравнивает эту ссылку**, — если никто, мемоизация бесполезна.

---

**1. `onPress` обёрнут в `useCallback`, а компонент `Button`, который его получает, — не `memo`. Что изменилось после добавления `useCallback`?**

<details>
<summary>Ответ</summary>

Ничего полезного. `Button` рендерится вместе с родителем независимо от пропсов: без `memo` пропсы не сравниваются (3.10). Стабильная ссылка `onPress` никому не нужна. Проверено на React 19.2: `Button` с мемоизированным колбэком рендерится при каждом изменении состояния родителя.

Что добавилось: на каждый рендер — создание стрелки (как и раньше), сравнение массива зависимостей, хранение функции на fiber, и массив зависимостей, который нужно держать честным. Если в нём пропущено значение — обработчик начнёт видеть устаревшие данные (3.5).

Когда `useCallback` здесь оправдан: `Button` обёрнут в `memo` и дорогой; или `onPress` используется ещё и как зависимость эффекта.

**Ответ «функция больше не пересоздаётся»** вскрывает понимание `useCallback` по названию. Создаётся каждый раз; возвращается старая.

**Ответ «это всё равно лучше, на всякий случай»** — не лучше: работа добавлена, выигрыша нет, а поддерживать зависимости теперь нужно.
</details>

---

**2. `memo`-компонент `Section` принимает `children`. Сработает ли мемоизация?**

```jsx
<Section title="Урок 3">
  <LessonBody lesson={lesson} />
</Section>
```

<details>
<summary>Ответ</summary>

Почти никогда. `children` — пропс, и его значение — JSX-элемент `<LessonBody ... />`, созданный в рендере родителя. Каждый рендер родителя создаёт новый объект элемента, сравнение `children` через `Object.is` даёт «не равно». Проверено на React 19.2: `memo`-обёртка со статичным `children` рендерится вместе с родителем.

Что делать, если `Section` действительно дорогая:

- мемоизировать сам элемент в родителе: `const body = useMemo(() => <LessonBody lesson={lesson} />, [lesson])` — работает, но редко оправдан;
- чаще — пересмотреть, что дорого: если дорог `LessonBody`, `memo` нужен ему, а не обёртке. `LessonBody` с той же ссылкой `lesson` пропустит рендер, даже если `Section` отрендерилась.

**Ответ «да, `children` не меняются»** вскрывает смешение «то же содержимое JSX» и «тот же объект элемента».
</details>

**3. Назовите три случая, когда `useMemo` оправдан, и один, когда он маскирует проблему.**

<details>
<summary>Ответ</summary>

Оправдан:

1. **дорогое вычисление при частом рендере** — сортировка и группировка сотен или тысяч элементов, построение индекса поиска. Критерий из документации React — порядка миллисекунды и больше на рендер, подтверждённое замером;
2. **объект или массив в пропсе `memo`-компонента** — без стабильной ссылки `memo` получателя не работает. Например, массив маркеров для карты;
3. **значение `value` провайдера контекста** — иначе каждый рендер провайдера рендерит всех потребителей (3.14).

Маскирует проблему: **объект в зависимостях эффекта с побочным действием**, обёрнутый в `useMemo`, «чтобы эффект не перезапускался». `useMemo` — подсказка, а не гарантия: React вправе пересчитать значение, и тогда эффект перезапустится. Корректность не должна зависеть от мемоизации; правильнее — примитивы в зависимостях или эффект, собирающий объект внутри (3.5).

**Ответ «для любого вычисления в рендере»** вскрывает модель «вычисление в рендере — это плохо». Дешёвые вычисления дешевле сравнения зависимостей.
</details>

**4. В списке 200 уроков переключение отметки «пройдено» у одного урока рендерит все видимые строки. `LessonRow` обёрнут в `memo`. Что ещё нужно проверить?**

<details>
<summary>Ответ</summary>

Остальные звенья цепочки — мемоизация работает только целиком:

1. **стабильность пропсов `LessonRow`** — обработчик `onToggle` должен быть стабильным (`useCallback` с функциональным обновлением внутри), а не стрелкой в `renderItem`. Никаких инлайн-объектов в пропсах строки (`style={{...}}`, `meta={{...}}`);
2. **стабильность `renderItem`** — новый `renderItem` заставляет каждую видимую ячейку вызвать его заново (3.10); сам вызов недорогой, если `LessonRow` — `memo` со стабильными пропсами, но лучше стабилизировать;
3. **иммутабельное обновление со структурным разделением** — `prev.map((l) => l.id === id ? { ...l, done: !l.done } : l)`: изменённый урок — новый объект, остальные — те же. Если обновление делает глубокую копию всего списка (`structuredClone`, `JSON.parse(JSON.stringify(...))`) или нормализатор пересоздаёт все объекты, каждая строка получит новый `lesson` и отрендерится;
4. **контекст** — если `LessonRow` читает контекст, `value` которого меняется вместе со списком, `memo` не поможет (3.14).

Проверено на React 19.2: при `memo` на строке, стабильном колбэке и структурном разделении переключение одного элемента из трёх рендерит одну строку.

**Ответ «значит, `memo` не работает в RN»** вскрывает отказ от поиска недостающего звена.
</details>

## Задание — code review: мемоизация «на всякий случай»

**Дано.** PR в RN Academy с описанием «оптимизировал производительность экрана курса». Изменения — только добавленные `memo`, `useMemo` и `useCallback`.

```jsx
const CourseHeader = memo(function CourseHeader({ course, onBack }) { /* ... */ });

const ProgressBar = memo(function ProgressBar({ value }) { /* ... */ });

const LessonRow = memo(
  function LessonRow({ lesson, onOpen }) { /* ... */ },
  (prev, next) => prev.lesson.id === next.lesson.id,
);

const Card = memo(function Card({ children, style }) { /* ... */ });

function CourseScreen({ course, lessons, navigation }) {
  const [filter, setFilter] = useState('all');

  const onBack = useCallback(() => navigation.goBack(), [navigation]);

  const title = useMemo(() => course.title.toUpperCase(), [course.title]);

  const progress = useMemo(
    () => lessons.filter((l) => l.done).length / lessons.length,
    [lessons],
  );

  const visible = useMemo(
    () => (filter === 'all' ? lessons : lessons.filter((l) => l.done === (filter === 'done'))),
    [lessons, filter],
  );

  const onOpen = useCallback((id) => navigation.navigate('Lesson', { id }), [navigation]);

  const onFilterAll = useCallback(() => setFilter('all'), []);

  const cardStyle = useMemo(() => ({ padding: 16 }), []);

  return (
    <>
      <CourseHeader course={course} onBack={onBack} />
      <Text>{title}</Text>
      <ProgressBar value={progress} />
      <Pressable onPress={onFilterAll}><Text>Все</Text></Pressable>
      <Card style={cardStyle}>
        <Text>{course.description}</Text>
      </Card>
      <FlatList
        data={visible}
        renderItem={({ item }) => <LessonRow lesson={item} onOpen={onOpen} />}
        keyExtractor={(l) => l.id}
      />
    </>
  );
}
```

**Требуется.**

1. Для каждой мемоизации в PR вынести вердикт: **полезна**, **бесполезна** или **вредна** — и обосновать через вопрос «кто сравнивает эту ссылку».
2. Найти место, где мемоизации не хватает, чтобы полезные мемоизации заработали.
3. Написать комментарий к PR — три-пять предложений для автора, без перечисления всех пунктов.

---

<details>
<summary>Разбор</summary>

**1. Вердикты.**

| Мемоизация | Вердикт | Почему |
|---|---|---|
| `memo(CourseHeader)` + `useCallback(onBack)` | полезна, если `CourseHeader` нетривиален | `CourseHeader` сравнивает `course` (пропс той же ссылкой) и `onBack` (стабилен) → при смене фильтра пропускает рендер. Работает только вместе: без `useCallback` `memo` не срабатывал бы |
| `memo(ProgressBar)` | полезна, но дёшево и без неё | `value` — число, примитив; смена фильтра не меняет прогресс → пропуск рендера. Если `ProgressBar` простой, выигрыш микроскопический |
| `useMemo(title)` | бесполезна | `toUpperCase` короткой строки дешевле сравнения зависимостей; результат — примитив, уходит в `Text` (не `memo`) |
| `useMemo(progress)` | бесполезна по скорости, безвредна | `filter` по десяткам уроков дёшев; результат — число, и `ProgressBar` сравнит его одинаково без `useMemo` |
| `useMemo(visible)` | полезна | `data` у `FlatList` — его сравнивает `PureComponent`; без `useMemo` любой рендер экрана давал бы новый массив. Вычисление тоже может быть заметным на длинном курсе |
| `useCallback(onOpen)` | полезна | уходит в `memo`-компонент `LessonRow` — но см. пункт 2 и компаратор ниже |
| `useCallback(onFilterAll)` | бесполезна | получатель — `Pressable`, не `memo`; ссылку никто не сравнивает |
| `memo(Card)` + `useMemo(cardStyle)` | бесполезна | `Card` принимает `children` — новый элемент `<Text>` каждый рендер; `memo` не срабатывает никогда, и стабилизация `style` ничего не меняет |
| компаратор `LessonRow` | **вредна** | сравнивает только `lesson.id`: переключение `done`, переименование урока, новый `onOpen` — всё игнорируется. Строка показывает устаревшие данные и вызывает обработчик из старого рендера |

**2. Чего не хватает.**

`renderItem` — стрелка в JSX, новая на каждый рендер. `CellRenderer` в `VirtualizedList` сравнивает его и при каждом рендере экрана вызывает `renderItem` для всех видимых ячеек заново (3.10). С корректным `memo` на `LessonRow` (без компаратора) строки пропустили бы рендер благодаря стабильным `lesson` и `onOpen` — но вызов `renderItem` и сравнение пропсов на каждой ячейке остаются. Стабильный `renderItem` через `useCallback` с `[onOpen]` убирает и это.

Удаление вредного компаратора — обязательная часть: после него `LessonRow` сравнивает пропсы по умолчанию (shallow), и с иммутабельными обновлениями урока всё работает корректно и быстро. Компаратор, по-видимому, был добавлен, потому что `memo` «не срабатывал» — из-за нестабильного `renderItem` и `onOpen` в предыдущей версии. Он лечил симптом ценой корректности.

**3. Комментарий к PR.**

> Спасибо за PR. Из девяти мемоизаций работают четыре: `CourseHeader` с `onBack`, `visible` и `onOpen` для списка, отчасти `ProgressBar` — их стоит оставить. `title`, `progress`, `onFilterAll` и пара `Card` + `cardStyle` ничего не экономят (результат никто не сравнивает, а `Card` принимает `children` — её `memo` не срабатывает), предлагаю убрать, чтобы не поддерживать лишние массивы зависимостей. Компаратор у `LessonRow` нужно удалить обязательно: он игнорирует всё, кроме `id`, и строка будет показывать устаревший `done` и вызывать старый обработчик. Вместо него — стабилизировать `renderItem` через `useCallback`, тогда стандартное сравнение `memo` заработает само. И было бы здорово приложить замер до/после (5.3) — без него «оптимизация» остаётся гипотезой.

**Вклад в проект (P3).** В RN Academy ячейка списка уроков — `memo` со стабильными `renderItem` и обработчиками, без кастомного компаратора; правило проекта — мемоизация только там, где можно назвать, кто сравнивает ссылку. Пара `memo` + `useCallback` на ячейке станет точкой сравнения, когда в 3.18 будет включён React Compiler.
</details>
