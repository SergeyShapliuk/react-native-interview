# 3.4 Lifecycle компонента и StrictMode — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **какое состояние внешней системы описывает эффект** и что его очистка снимает, — а не «где здесь `componentDidMount`».

---

**1. Эффект подписывается на emitter прогресса загрузки и не возвращает очистку. Что покажет StrictMode в dev и что произойдёт в release?**

```jsx
useEffect(() => {
  downloadEmitter.addListener('progress', (p) => setProgress(p));
}, []);
```

<details>
<summary>Ответ</summary>

**В dev со StrictMode** при монтировании выполняется цикл «эффект → очистка → эффект». Очистки нет, поэтому после монтирования на emitter висят **два** слушателя. Каждое событие прогресса вызывает `setProgress` дважды — с одним и тем же значением, так что на экране этого не видно. Видно, если в слушателе есть что-то кроме `setProgress`: лог, аналитика, вибрация на 100 %. Двойной лог и есть сигнал.

**В release** двойного запуска нет, и на первом открытии экрана всё работает. Дефект проявляется позже: экран размонтируется (ушли назад), слушатель остаётся на emitter'е и удерживает замыкание с `setProgress` и всем, что оно захватило (1.22). При следующем открытии экрана добавляется второй слушатель, при третьем — третий. Утечка растёт с каждым открытием, а события обрабатываются слушателями размонтированных экземпляров.

Исправление — пара:

```jsx
useEffect(() => {
  const sub = downloadEmitter.addListener('progress', setProgress);
  return () => sub.remove();
}, []);
```

StrictMode в этом сценарии показывает в момент разработки то, что в release проявится только после нескольких открытий экрана.

**Ответ «в release всё нормально, двойной вызов — особенность dev»** вскрывает восприятие StrictMode как шума. Двойной вызов в dev — модель того, что произойдёт при повторном монтировании в release.

**Ответ «ничего, потому что `[]` — эффект выполнится один раз»** вскрывает модель «`[]` = один раз за жизнь приложения».
</details>

---

**2. Родитель и ребёнок, у обоих `useEffect` с очисткой, зависящий от одного пропса `lessonId`. В каком порядке выполнится всё при монтировании и при смене `lessonId`?**

<details>
<summary>Ответ</summary>

**Монтирование:**

```
render родителя → render ребёнка → commit
эффект ребёнка → эффект родителя
```

Рендер сверху вниз, эффекты снизу вверх: родитель в своём эффекте видит детей полностью смонтированными.

**Смена `lessonId`:**

```
render родителя → render ребёнка → commit
очистка ребёнка (старый lessonId) → очистка родителя (старый lessonId)
эффект ребёнка (новый lessonId) → эффект родителя (новый lessonId)
```

Сначала все очистки, затем все запуски. Очистки видят **старый** `lessonId` — они замыкания предыдущего рендера (1.14), и это правильно: снять нужно ту подписку, которая была создана со старым аргументом.

Порядок проверен экспериментом на React 19.2. При наличии `useLayoutEffect` тот же порядок выполняется для layout-эффектов раньше, внутри commit, а пассивные — после (3.6).

**Ответ «очистка вызывается только при размонтировании, при смене `lessonId` просто запустится новый эффект»** вскрывает модель «очистка = `componentWillUnmount`». С ней получается вторая подписка поверх первой.

**Ответ «очистка видит новый `lessonId`»** вскрывает модель «эффект читает текущие значения». Эффект и очистка — снимки своего рендера.
</details>

---

**3. В теле компонента написано `renders.current += 1`, и значение выводится в эффекте. В StrictMode первое монтирование показывает `2`. Почему, и что это говорит о коде?**

<details>
<summary>Ответ</summary>

StrictMode в dev вызывает функцию компонента дважды на один рендер. Ref-объект при этом **один и тот же** — он хранится на fiber, а не создаётся в вызове функции. Оба вызова инкрементируют одно и то же `current`, и к моменту эффекта там `2`. Проверено экспериментом на React 19.2.

Что это говорит о коде: запись в ref при рендере — побочный эффект в render-фазе. В release двойного вызова нет, но рендер может быть вызван и не дойти до экрана (переход прерван, приостановка в Suspense, 3.17) — и счётчик снова разойдётся с числом показанных рендеров. StrictMode здесь не ломает код, а показывает, что код зависит от числа вызовов функции, которое React не гарантирует.

Если нужно посчитать рендеры для диагностики — инкремент в эффекте без зависимостей (выполняется на каждый commit) или React Profiler (5.10). Правило линтера `react-hooks/refs` в 7-й версии отмечает чтение и запись `ref.current` при рендере.

**Ответ «это баг StrictMode, в release будет 1»** — верно про release, но вывод неверный: код корректен только при условии, которое React не обещает.

**Ответ «ref пересоздаётся при каждом рендере»** вскрывает непонимание того, где живёт ref (3.9). Если бы ref пересоздавался, значение было бы `1`.
</details>

**4. На экране урока эффект с `[]` запускает `setInterval`, обновляющий таймер прохождения, и очищает его. Пользователь перешёл вперёд на экран теста. Таймер урока продолжает считать. Это ошибка в эффекте?**

<details>
<summary>Ответ</summary>

Нет, эффект корректен: интервал создан при монтировании и будет снят при размонтировании. Ошибка — в ожидании, что уход вперёд размонтирует экран.

В стековой навигации экран урока остаётся смонтированным под экраном теста: его не удалили из стека. Эффекты не очищаются, интервал продолжает работать, `setState` продолжает вызывать рендеры невидимого экрана. Очистка выполнится, только когда экран удалят из стека — по кнопке «назад» или при сбросе навигации.

Если таймер должен идти только пока урок **виден**, сигнал «смонтирован» — неверный сигнал. Нужен сигнал фокуса экрана из навигации, и это тема 4.17. Здесь важно различие: **время жизни компонента и время видимости экрана — разные вещи**, и `useEffect` привязан к первому.

**Ответ «надо добавить очистку»** вскрывает поиск ошибки в эффекте, где её нет.

**Ответ «экран размонтировался, но интервал не снят из-за замыкания»** вскрывает модель «переход вперёд = размонтирование».
</details>

## Задание — компонент, ломающийся в StrictMode

**Дано.** Компонент заметок урока. После включения `StrictMode` на корне приложения команда получила три жалобы из dev-сборки: «каждое сохранение заметки отправляется дважды», «в списке заметок иногда показывается заметка от предыдущего урока», «счётчик просмотров урока растёт на два».

```jsx
let viewedLessons = [];

function LessonNotes({ lessonId }) {
  viewedLessons.push(lessonId);
  const [notes, setNotes] = useState([]);
  const [draft, setDraft] = useState('');

  useEffect(() => {
    api.trackView(lessonId);
  }, [lessonId]);

  useEffect(() => {
    api.loadNotes(lessonId).then(setNotes);
  }, [lessonId]);

  useEffect(() => {
    const sub = Keyboard.addListener('keyboardDidHide', () => {
      if (draft) api.saveNote(lessonId, draft);
    });
  }, [lessonId, draft]);

  return /* ... */;
}
```

**Требуется.**

1. Для каждой жалобы найти код, который её вызывает, и назвать класс ошибки из урока.
2. Для каждой определить: это дефект, который проявится и в release, или поведение, которое в release выглядит корректно. Если проявится — при каком сценарии.
3. Исправить компонент, не выключая StrictMode и не используя флаг «уже выполнено» в ref.

---

<details>
<summary>Разбор</summary>

**1. Причины.**

*Сохранение отправляется дважды.* Третий эффект подписывается на `keyboardDidHide` без очистки. Это **неидемпотентная подписка**. В StrictMode цикл «эффект → очистка → эффект» оставляет двух слушателей уже при монтировании. Хуже того: эффект зависит от `draft`, и каждый введённый символ добавляет ещё одного слушателя, каждый со своим замкнутым `draft`. После ввода «привет» висит семь слушателей, и при скрытии клавиатуры отправляются все промежуточные черновики.

*Заметка от предыдущего урока.* Второй эффект — **запрос без отмены**. При смене `lessonId` запрос для нового урока отправлен, но ответ на старый может прийти позже и перезаписать список. В StrictMode при монтировании уходят два одинаковых запроса — это не меняет данных, но делает гонку видимой в сетевом логе.

*Счётчик просмотров растёт на два.* Две причины. Первая — `viewedLessons.push` в теле компонента: **мутация внешнего объекта в render-фазе**, двойной рендер добавляет запись дважды. Вторая — эффект `trackView`: это **эффект, который делает действие, а не синхронизирует**, и в StrictMode он выполняется дважды.

**2. Проявится ли в release.**

- Подписка без очистки — **проявится**, и сильнее, чем в dev: на каждый символ черновика добавляется слушатель, при скрытии клавиатуры уходит серия запросов. После ухода с экрана слушатели остаются и сохраняют заметки уже размонтированного компонента.
- Запрос без отмены — **проявится** при быстром переключении уроков на медленной сети: показан список не того урока.
- `viewedLessons.push` при рендере — **проявится** при любом рендере, который не дошёл до экрана (переходы, Suspense), и при каждом обычном ре-рендере: массив растёт на каждый рендер, а не на каждый просмотр. Уже без StrictMode счётчик неверен — StrictMode лишь сделал это заметным с первого рендера.
- `trackView` в эффекте — в release отправится один раз на монтирование. Но монтирований на «один просмотр» может быть несколько: возврат на экран, смена ключа, Fast Refresh в dev. Сам вопрос «что считать просмотром» — это вопрос события, а не синхронизации.

**3. Исправление.**

```jsx
function LessonNotes({ lessonId }) {
  const [notes, setNotes] = useState([]);
  const [draft, setDraft] = useState('');

  // загрузка: эффект синхронизирует список с lessonId и отменяет устаревший ответ
  useEffect(() => {
    let cancelled = false;
    api.loadNotes(lessonId).then((loaded) => {
      if (!cancelled) setNotes(loaded);
    });
    return () => {
      cancelled = true;
    };
  }, [lessonId]);

  // подписка: пара «добавить — снять», последний черновик читается в момент события
  const draftRef = useRef(draft);
  useEffect(() => {
    draftRef.current = draft;
  });
  useEffect(() => {
    const sub = Keyboard.addListener('keyboardDidHide', () => {
      if (draftRef.current) api.saveNote(lessonId, draftRef.current);
    });
    return () => sub.remove();
  }, [lessonId]);

  return /* ... */;
}
```

Что сделано и почему:

- **`viewedLessons.push` удалён из тела.** Если список просмотренных уроков нужен, он обновляется в момент события «урок открыт» — в обработчике навигации, — а не при рендере.
- **`trackView` вынесен из компонента.** Просмотр — событие, а не состояние, с которым нужно синхронизироваться. Он отправляется туда, где происходит событие: в обработчик перехода на урок или в событие фокуса экрана (4.17). Эффект, который должен выполниться «ровно один раз на просмотр», — признак того, что код не принадлежит эффекту (3.7).
- **Загрузка получила отмену.** Флаг `cancelled` в замыкании эффекта: очистка предыдущего запуска помечает его ответ как устаревший. В StrictMode первый ответ игнорируется, при смене урока ответ на старый урок не перезапишет новый. Полная работа с гонками и `AbortController` — блок 07.
- **Подписка стала парой и перестала зависеть от `draft`.** Слушатель снимается в очистке. Чтобы не переподписываться на каждый символ, актуальный черновик читается через ref, который обновляется после каждого commit. Это приём «актуальное значение для долгоживущего колбэка» (1.14, 3.9); в React 19.2 то же решает `useEffectEvent` — разбор в 3.5.

Проверка: в StrictMode лог показывает один слушатель после монтирования, один запрос сохранения на скрытие клавиатуры, отсутствие устаревших списков при быстром переключении `lessonId`.

**Вклад в проект (P3).** Корень RN Academy обёрнут в `StrictMode`. Всё, что он вскрыл в слое P3, исправлено парами «эффект — очистка» и выносом действий в обработчики; флаги «уже выполнено» запрещены правилами проекта.
</details>
