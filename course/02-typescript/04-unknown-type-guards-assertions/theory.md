# 2.4 `unknown` vs `any`, type guards, assertion functions — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «чем `unknown` отличается от `any`» — а на вопрос, **откуда компилятор знает тип значения в конкретной строке и что из этого знания следует в рантайме.**

---

## 1. Что это

**`any`** — тип, для которого проверки отключены. Значению типа `any` разрешено любое обращение, и само оно присваивается чему угодно без возражений.

**`unknown`** — тип, про который известно только то, что значение существует. Обращаться к нему нельзя до того, как тип сужен.

```ts
declare const a: any;
declare const u: unknown;

a.lesson.title.trim();   // компилируется
u.lesson;                // 'u' is of type 'unknown'
```

Оба описывают одну и ту же ситуацию — «что здесь лежит, неизвестно». Разница в том, кто обязан разобраться: при `any` никто, при `unknown` — автор кода, и компилятор это требование предъявляет.

**Narrowing (сужение типа)** — уточнение типа значения на участке кода, выведенное компилятором из проверок, которые этот участок проходит. Не объявление и не приведение: сужение есть следствие потока управления.

**Type guard (предикат типа)** — функция с возвращаемым типом `x is T`. Если она вернула `true`, компилятор считает аргумент типом `T`.

**Assertion function (функция-утверждение)** — функция с возвращаемым типом `asserts x is T`. Она не возвращает признак, а либо завершается нормально, либо бросает; после нормального завершения аргумент считается типом `T`.

**`as`** — type assertion (утверждение типа). Запись `value as T` сообщает компилятору, каким считать тип выражения, и не делает ничего больше.

### Ключевая формулировка урока

> **`as` — это не проверка, а приказ компилятору молчать. Единственное, что `as` меняет в рантайме, — ничего.**

Из неё выводится весь урок: `unknown` ставит вопрос «кто проверит», предикат и assertion function — два способа ответить, `as` — способ отказаться отвечать.

---

## 2. Как это работает

### Сужение выводится из потока управления

**Control flow analysis (анализ потока управления)** — проход компилятора по возможным путям выполнения с отслеживанием того, что на каждом пути уже известно о типе. Проверка сужает тип не в месте проверки, а в той ветке, куда она ведёт.

```ts
function format(x: string | number) {
  if (typeof x === 'number') {
    return x.toFixed(2);   // здесь number
  }
  return x.trim();         // здесь string: другого члена union не осталось
}
```

Во второй строке `x` сужен без всякой проверки: ветка достижима только тогда, когда первое условие ложно. Отсюда практическое следствие — ранний `return` сужает тип для всего остатка функции, и это дешевле вложенных `if`.

Проверки, которые компилятор понимает без дополнительных объявлений:

| Проверка | Что сужает |
|---|---|
| `typeof x === 'string'` | примитивы |
| `x === null`, `x == null` | `null` и `undefined` |
| `'id' in x` | объектные типы по наличию свойства |
| `x instanceof Error` | по классу |
| `x.kind === 'done'` | union по полю с литеральным типом |
| `Array.isArray(x)` | массив — это встроенный предикат |

### `unknown` требует сузить до конкретного типа

Для `unknown` одной проверки обычно не хватает: `typeof u === 'object'` даёт `object | null`, а не вашу сущность.

```ts
function isLesson(x: unknown): x is Lesson {
  return typeof x === 'object' && x !== null && 'id' in x && 'title' in x;
}
```

Три шага обязательны и именно в этом порядке: `typeof` отсекает примитивы, `!== null` отсекает `null` (у которого `typeof` тоже `'object'` — 1.3), и только после этого разрешён `in`, потому что он требует объектного операнда.

### Компилятор верит предикату на слово

Тело предиката не проверяется на соответствие заявленному типу. Компилятор принимает утверждение `x is Lesson` как данность.

```ts
function isLesson(x: unknown): x is Lesson {
  return typeof x === 'object';   // компилируется, хотя проверка неполна
}
```

Это не недосмотр: доказать соответствие произвольного кода типу компилятор не может, поэтому доверяет сигнатуре. Практическое следствие важнее формулировки — **неверный предикат хуже отсутствующего**. Отсутствие предиката оставляет `unknown`, и ошибка видна в месте использования. Неверный предикат выдаёт гарантию, которой нет, и переносит ошибку в рантайм.

### Assertion function влияет на поток, а не на ветку

Предикат возвращает `boolean`, и сужение действует внутри ветки. Assertion function сужает тип **после своего вызова** и до конца области видимости.

```ts
function assertLesson(x: unknown): asserts x is Lesson {
  if (!isLesson(x)) throw new Error('не Lesson');
}

function render(raw: unknown) {
  assertLesson(raw);
  return raw.title;   // Lesson — без if
}
```

Два требования, которые легко нарушить. Первое: функция обязана бросать на несоответствии — иначе сигнатура лжёт, и дальше код работает с непроверенным значением как с проверенным. Второе: сужение через `asserts` работает только тогда, когда у вызываемого значения есть явная аннотация типа, — assertion function, присвоенная в переменную без типа, сужение теряет.

Выбор между предикатом и assertion function — вопрос о том, кто отвечает за неудачу. Предикат отдаёт решение вызывающему: ветка `else` существует, и в ней можно вернуть значение по умолчанию. Assertion function принимает решение сама — бросает исключение, и вызывающий об альтернативе не знает.

### `as` и двойное приведение

`as` допускает приведение только между типами, у которых есть пересечение. Когда компилятор отказывается, в код приходит `as unknown as T`:

```ts
const n = '5' as unknown as number;   // компилируется, в рантайме строка
```

Запись читается однозначно: «я не могу обосновать это приведение даже формально». В продуктовом коде она почти всегда означает, что тип описан неверно либо проверка не написана. Законное исключение — обход неточных сторонних типов (2.9), и такое место заслуживает комментария с причиной.

## 3. Почему это важно

Тип в TypeScript — утверждение о коде, а не о данных. Внутри кодовой базы утверждение проверено компилятором. На входе — ответ сервера, значение из хранилища, аргумент нативного колбэка — не проверено ничего, и именно в этой точке решается, во что превратится несоответствие.

Три исхода одного и того же несоответствия:

- **`as`** — приложение продолжает работать с неверной моделью и падает позже, в случайном месте, с сообщением вида «cannot read property of undefined». Стек указывает на компонент, а причина лежит в разборе ответа, иногда экраном раньше;
- **предикат** — несоответствие обнаружено там, где данные вошли в приложение, и у вызывающего есть ветка для этого случая;
- **assertion function** — несоответствие обнаружено там же и превращено в исключение, которое ловит слой выше.

Разница не в строгости, а в расстоянии между причиной и симптомом. Поэтому `unknown` на границе полезен: он делает это расстояние нулевым, принудительно.

## 4. Где это в React Native

### `JSON.parse` и ответ сервера

`JSON.parse` объявлен возвращающим `any`, и аннотация переменной здесь ничего не проверяет:

```ts
const lesson: Lesson = JSON.parse(raw);   // проверки нет, any присвоился
```

Эта строка выглядит как типизированный код и им не является. Разница с `JSON.parse(raw) as Lesson` только стилистическая: оба варианта — утверждение автора. Корректный вход — объявить результат `unknown` и дальше сужать:

```ts
const parsed: unknown = JSON.parse(raw);
if (!isLesson(parsed)) return null;
```

### `AsyncStorage`

`getItem` возвращает `string | null`, и этот union компилятор заставит разобрать. Дальше начинается то же самое: строка разбирается `JSON.parse`, и проверка заканчивается ровно там. Усугубляет дело то, что в хранилище лежат данные, записанные **предыдущей версией приложения**: форма могла измениться после обновления, и никакой тип об этом не знает.

### Колбэки нативных модулей

Значение, пришедшее из нативного слоя, типизировано ровно так, как его описал автор модуля в `.d.ts` или в спецификации. Для библиотеки без типов это `any`, для библиотеки с неточными типами — тип, не соответствующий реальности. Проверять приходится на стороне JS: граница между языками компилятором не покрывается в принципе.

### `catch`

Переменная в `catch` имеет тип `unknown` при включённом `useUnknownInCatchVariables`, который входит в `strict` (2.8). Это ровно тот случай, где `unknown` уместен: бросить в JavaScript можно что угодно, не только `Error`.

```ts
try {
  await submit();
} catch (e) {
  const message = e instanceof Error ? e.message : String(e);
}
```

Привычка писать `catch (e: any)` и сразу обращаться к `e.response.status` приводит к падению внутри обработчика ошибки — то есть к потере исходной ошибки, а в продакшене это означает отсутствие информации о причине (1.11).

### Параметры навигации

Параметры экрана приходят из места, которое компилятор не связывает с текущим экраном: из другого экрана, из deep link, из push-уведомления. Типизация `ParamList` описывает контракт, но при переходе по внешней ссылке значения формируются вне приложения — и там `unknown` честнее объявленного типа.

## 5. Типичные ошибки

**Предикат проверяет одно поле из восьми.** Пишется за минуту, выглядит как проверка и даёт компилятору полную гарантию по всем восьми полям. Причина не в лени: поля, которых «обычно не бывает» в ответе, не проверяются именно потому, что их обычно не бывает. Правило простое — предикат обязан проверять то, на что опирается код; если проверяется меньше, об этом нужен комментарий, а не молчание.

**`as` вместо предиката.** Возникает из того, что `as` убирает ошибку компилятора мгновенно, а предикат надо писать. Ошибка исчезает, несоответствие остаётся. Признак при чтении диффа: `as` рядом с `JSON.parse`, `getItem`, `route.params` или аргументом колбэка.

**`any` в сигнатуре экспортируемой функции.** Один `any` на входе публичной функции отключает проверки у всех вызывающих. Причина — `any` ставится как «пока так, потом уточню», а уточнение не происходит, потому что код работает.

**Truthy-проверка вместо проверки на существование.** `if (!value) return` отсекает не только `null` и `undefined`, но и `0`, пустую строку и `false` (1.3). Для прогресса урока, равного нулю, это превращается в молчаливое «данных нет».

**Предикат, забывший про `null`.** `typeof x === 'object'` пропускает `null`, после чего `'id' in x` падает в рантайме — внутри самой проверки.

**Assertion function, которая не бросает.** Возвращает `false` или пишет в лог и продолжает. Сигнатура обещает, что после вызова тип известен; без `throw` обещание ложно, и дальше работает код с непроверенным значением.

## 6. Trade-offs

### Предикат нужно писать и поддерживать

Предикат — код, дублирующий форму типа. Поле добавили в тип, предикат о нём не узнал, компилятор не напомнил. Через несколько месяцев предикат и тип расходятся, и проверка перестаёт покрывать то, ради чего написана. Это не аргумент против предикатов, а точное описание их границы: они стоят ровно столько, сколько стоит их поддержка.

Схема (2.12) снимает именно эту проблему: форма описывается один раз, тип выводится из неё, проверка выполняется ей же. Цена — зависимость, размер бандла и время на старте.

### Проверка стоит времени и кода

Полная проверка массива из нескольких сотен элементов — работа на JS-потоке. На границе одного экрана это обычно незаметно, при разборе большого кэша на старте — заметно (05). Поэтому решение «что проверять» принимается по данным, а не по принципу: ключевые поля, от которых зависит отображение, против всех полей целиком.

### `unknown` делает код длиннее

Переход с `any` на `unknown` на границе добавляет проверки в каждое место, которое раньше компилировалось молча. Это и есть цена, которую урок предлагает заплатить: длина кода растёт на границе и падает в местах использования, где больше не нужны защитные `?.` и `??` на всякий случай.

### Предикат против assertion function

Предикат оставляет вызывающему ветку и подходит там, где у несоответствия есть разумное продолжение — показать пустой экран, взять значение по умолчанию, пропустить элемент списка. Assertion function короче на стороне вызова и подходит там, где продолжать нельзя. Она же жёстче связывает модуль с политикой обработки ошибок: бросает исключение, которое кто-то обязан поймать (7.3).
