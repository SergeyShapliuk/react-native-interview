# 2.1 Базовые типы и вывод типов — theory

> 🟢 REFRESH. Задача урока — не перечислить `string`, `number`, `boolean`, а зафиксировать, где аннотация добавляет компилятору информацию, а где отбирает её.

## Refresh

### Вывод типа — не догадка, а правило

**Type inference (вывод типа)** — определение типа значения компилятором из самого выражения, без аннотации. Правила фиксированы, поэтому выведенный тип предсказуем. Два источника, нужных в этом уроке: тип переменной выводится из **инициализирующего значения**, тип возвращаемого значения функции — из **всех** выражений `return`.

```ts
const title = 'Основы JSI';   // "Основы JSI" — литеральный тип
let progress = 0;             // number

function pick(items: string[]) {
  if (items.length === 0) return null;
  return items[0];
}
// выведено: string | null — из обоих return
```

Аннотация здесь ничего не добавила бы: `const title: string = 'Основы JSI'` не уточняет тип, а **расширяет** его с `"Основы JSI"` до `string`.

### Литеральные типы и widening

**Literal type (литеральный тип)** — тип из ровно одного значения: `"up"`, `42`, `true`. **Widening (расширение типа)** — замена литерального типа базовым (`"up"` → `string`), которую компилятор выполняет там, где значение может измениться.

```ts
const direction = 'up';   // "up"
let cursor = 'up';        // string — widening
```

`const` переприсваивать нельзя — литеральный тип сохраняется. `let` можно, и тип расширяется до того, что вообще допустимо присвоить. Видно это на первом вызове функции с union-параметром:

```ts
type Direction = 'up' | 'down';
function scroll(d: Direction) {}

const a = 'up';
let b = 'up';

scroll(a); // ок
scroll(b); // Argument of type 'string' is not assignable to parameter of type 'Direction'
```

Ошибка относится не к значению, а к типу переменной: в `b` сейчас лежит `'up'`, но компилятор обязан учитывать все будущие присваивания.

Widening срабатывает и в объектных литералах — поля объекта изменяемы:

```ts
const config = { direction: 'up' }; // { direction: string }
scroll(config.direction);           // ошибка
```

### `as const`

`as const` запрещает widening: литералы остаются литералами, поля и элементы становятся `readonly`.

```ts
const config = { direction: 'up' } as const; // { readonly direction: "up" }
scroll(config.direction);                     // ок

const directions = ['up', 'down'] as const;   // readonly ["up", "down"]
```

`as const` действует только при компиляции. В собранном бандле это обычный объект: `readonly` проверяет компилятор, а не рантайм. Иммутабельность в рантайме — отдельная задача (1.13).

Массив под `as const` становится кортежем. **Tuple (кортеж)** — тип с зафиксированной длиной, где тип привязан к позиции: у `[string, number]` элемент 0 — `string`, элемент 1 — `number`, тогда как у `(string | number)[]` любой элемент — `string | number`. Поэтому пару вроде `[value, setValue]` типизирует только кортеж.

### Union и что с ним можно делать сразу

**Union (объединение типов)** `A | B` — значение одного из перечисленных типов. Разрешены только операции, допустимые **для каждого** члена:

```ts
function label(x: string | number) {
  x.toFixed(2);      // ошибка: toFixed нет у string
  return String(x);  // ок: принимает и то, и другое
}
```

Полный доступ открывает проверка, по которой компилятор определит ветвь: `if (typeof x === 'number') return x.toFixed(2);` — внутри ветки `x` имеет тип `number`. Простейшие проверки (`typeof`, сравнение с литералом, `=== null`) работают без дополнительных объявлений.

> **Не дублировать:** механизм сужения в общем виде — предикаты `x is T`, assertion functions, `unknown` — предмет 2.4; discriminated union как способ сделать невозможное состояние невыразимым — 2.5. Здесь нужен только факт: над union доступно пересечение возможностей.

Самый частый практический union — `T | null` и `T | undefined`: при `strictNullChecks` это настоящие члены объединения, и обращение к полю без проверки не компилируется. Разбор флагов — 2.8.

### Аннотация возвращаемого типа как инструмент проектирования

Без аннотации тип выводится из тела: тело — источник истины, сигнатура — следствие. С аннотацией направление меняется: сигнатура — утверждение, тело проверяется на соответствие.

```ts
function findLesson(id: string, lessons: Lesson[]) {
  const found = lessons.find((l) => l.id === id);
  if (!found) return;   // забыли, что контракт обещает null
  return found;
}
// выведено Lesson | undefined — ошибки нет, она всплывёт у вызывающего
```

С аннотацией `: Lesson | null` та же строка `return` не компилируется, и сообщение указывает на место, где сделана ошибка.

Выведенный тип всегда «правильный» — он описывает то, что код делает. Аннотация описывает то, что код **должен** делать, и поэтому способна разойтись с телом. Это расхождение и есть польза: без аннотации правка в середине функции молча меняет её контракт.

Отсюда рабочее правило: аннотируется публичная граница модуля — экспортируемые функции, пропсы, формы данных на входе и выходе; внутри полагаемся на вывод.

### `void` и `never`

**`void`** — «возвращаемое значение не предназначено для использования». Это не тип `undefined`: `() => void` принимает функцию, возвращающую любое значение, — оно игнорируется, поэтому `items.forEach((x) => set.add(x))` компилируется, хотя `add` возвращает `Set`.

**`never`** — «значения этого типа не существует». Функция с таким возвращаемым типом не завершается нормально: `function fail(m: string): never { throw new Error(m); }`.

Разница в одной фразе: `void` — функция завершилась и вернула ненужное значение; `never` — функция не завершилась. Следствие для 2.5: `never` возникает как тип переменной в недостижимой по типам ветке, и на этом строится проверка полноты разбора union.

### Неявный `any` и `any` как дыра

**`any`** отключает проверки для значения: разрешено любое обращение и любое присваивание. Поэтому ошибка не остаётся локальной — `any` присваивается чему угодно и обнаруживается там, где типы выглядят строгими.

```ts
const raw: any = JSON.parse(payload);
const lesson: Lesson = raw;  // проверки нет
lesson.title.trim();         // падает в рантайме, если title отсутствует
```

Отдельный случай — **неявный** `any`: параметр без аннотации и без контекста, из которого тип выводится. Параметры — это вход, выводить их не из чего, поэтому аннотация параметра почти всегда обязательна, а флаг `noImplicitAny` делает пропуск ошибкой.

> **Не дублировать:** почему `unknown` — корректная замена `any` на границе и как перейти от него к конкретному типу — 2.4. Здесь фиксируется только факт: `any` не локален.

## RN relevance

### Пропсы: аннотируем вход, не аннотируем внутренности

Пропсы — публичная граница, их тип пишется явно. Внутри компонента аннотации в основном лишние:

```ts
type LessonCardProps = {
  title: string;
  state: 'locked' | 'available' | 'done';
  onPress: (id: string) => void;
};

function LessonCard({ title, state, onPress }: LessonCardProps) {
  const [expanded, setExpanded] = useState(false); // boolean выведен
}
```

Литеральный union в `state` — ровно то, из-за чего `state="Done"` с опечаткой не компилируется. Замена его на `string` оставляет проверку «это строка» и ничего больше.

> **Не дублировать:** типизация компонентов и хуков целиком — пропсы с детьми, `ref`, возврат кастомного хука — предмет 2.14 (кастомные хуки как приём — 3.12).

### `AsyncStorage` и ответ `fetch`

`getItem` возвращает `string | null`, `JSON.parse` и `response.json()` — `any`. Union на входе компилятор заставляет разобрать, `any` на выходе — нет:

```ts
const stored = await AsyncStorage.getItem('progress');
if (stored === null) return initialProgress; // проверка настоящая: иначе со string | null не работать
return JSON.parse(stored) as Progress;       // утверждение, которое никто не проверял
```

Вторая строка — обещание разработчика: структура в хранилище могла быть записана предыдущей версией приложения, и тип о ней не знает.

У `fetch` то же самое, но аннотация переменной там всё же полезна: `const data: LessonDto = await response.json()` — единственное место, где форма ответа вообще появляется в коде. Проверки по-прежнему нет, однако дальше поле-опечатка уже не скомпилируется. Это лучше, чем оставить `any`, и слабее валидации. Решение — 2.12, обобщение на все границы — 2.13.

### Параметры навигации и платформенные карты

Имена маршрутов собираются в одном месте, а читаются в другом, и `as const` здесь определяет, работает ли типизированный `navigate`:

```ts
const routes = { lesson: 'Lesson', courseList: 'CourseList' } as const;
navigate(routes.lesson, { lessonId }); // "Lesson", а не string
```

Без `as const` оба значения расширяются до `string`, и несуществующий маршрут перестаёт отличаться от существующего. Аннотация `Record<string, string>` даёт тот же результат с другой стороны: она проверяет форму и стирает ключи, после чего `routes.lessson` компилируется и возвращает `undefined` в рантайме.

> Тип обращения по неизвестному ключу здесь — `string`: при обычном `strict` компилятор не учитывает, что ключа может не быть. Отдельный флаг `noUncheckedIndexedAccess` даёт в этом месте `string | undefined` и требует проверки; он не входит в `strict` и разбирается в 2.8. Точные литеральные ключи решают задачу раньше: при `as const` опечатка не компилируется вовсе.

Так же устроены стили вне `StyleSheet.create`: литералы `'row'`, `'absolute'`, `'center'` в типах RN объявлены как union, а вынесенный в переменную объектный литерал расширяет их до `string` — и `const layout = { flexDirection: 'row' }` перестаёт подходить под `FlexDirection` в `style`.

### Обработчики событий

Здесь аннотация чаще всего лишняя, а дописанная вручную — хуже выведенной:

```ts
<TextInput onChangeText={(text) => setQuery(text)} />
```

`text` типизирован как `string` потому, что тип берётся из `onChangeText`, — это **contextual typing (контекстный вывод)**: тип параметра определяется местом, куда функция передаётся. Вынесите обработчик в переменную без аннотации — контекста не станет, и `noImplicitAny` сработает.

С `onScroll` добавляется вторая причина: выведенный параметр — `NativeSyntheticEvent<NativeScrollEvent>`, и описанный вручную как `{ nativeEvent: { contentOffset: { y: number } } }` теряет остальные поля и привязывается к форме, которая может не совпасть с версией RN.

## Типичные заблуждения

**«Аннотация всегда лучше вывода.»** Возникает из опыта языков, где аннотация — единственный способ сообщить тип. В TypeScript аннотация переменной не уточняет вывод, а заменяет его, и чаще расширяет: `const d: string = 'up'` теряет тип `"up"`. Проверка — посмотреть выведенный тип до и после удаления аннотации: если он точнее, аннотация вредит. Параметры и возвращаемый тип — отдельный случай, там явность добавляет проверку.

**«`as const` делает объект неизменяемым.»** Возникает из того, что `readonly` в выведенном типе выглядит как рантайм-гарантия. `as const` существует только в типах. Проверка: посмотреть собранный бандл — `as const` в нём отсутствует.

**«`never` — то же, что `void`.»** Возникает из того, что обе функции «ничего не возвращают». Проверка: код после вызова `void`-функции достижим, после вызова `never`-функции компилятор считает его недостижимым.

**«Кортеж — это массив фиксированной длины и больше ничем не отличается.»** Возникает из того, что в рантайме это действительно массив. Отличие — в привязке типа к позиции: `const [value, set] = useState(0)` даёт `number` и функцию, а не `number | Function` в обеих переменных. Проверка: заменить тип на `(number | ((n: number) => void))[]` и посмотреть, что перестанет компилироваться у вызывающего.
