# 2.12 Runtime-валидация на границе и вывод типа из схемы — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **сколько существует описаний формы и кто их сверяет**, а не перечислить возможности библиотеки валидации.

---

**1. Почему предикат, написанный руками, расходится с типом, а схема — нет?**

<details>
<summary>Ответ</summary>

Потому что расходиться могут только два независимых описания, а схема — одно.

С предикатом форма описана дважды: в типе и в теле проверки. Связаны они намерением автора, компилятор их не сверяет (2.4) — он принимает сигнатуру `x is Lesson` как утверждение. Любое изменение модели требует двух правок, и пропуск любой из них не даёт ошибки:

- поправили тип, забыли предикат — проверка стала строже или слабее типа. Если строже, корректные данные отбрасываются; если слабее, непроверенное поле читается как проверенное;
- поправили предикат, забыли тип — то же самое в другую сторону.

Со схемой описание одно: тип выводится из неё вычислением (2.10). Правка схемы автоматически меняет тип, и места чтения, ставшие некорректными, немедленно перестают компилироваться. Расхождение невозможно **по построению**, а не благодаря дисциплине.

Проверяется это мысленным экспериментом на одно изменение: сделать поле необязательным и посчитать, сколько мест нужно поправить и сколько из пропусков заметит компилятор.

**Ответ «схема надёжнее, потому что её пишет библиотека»** вскрывает отнесение свойства к инструменту вместо устройства решения. Собственные комбинаторы, выводящие тип, дают то же свойство; библиотека удобна, но не она источник гарантии.

**Ответ «предикат может быть написан неправильно»** верен и описывает другую проблему. Неверно написанная схема тоже возможна — она может не соответствовать серверу. Разница не в вероятности ошибки при написании, а в том, что у схемы **нет второго описания**, с которым можно разойтись потом.

**Ответ «предикаты устарели, сейчас все используют схемы»** вскрывает отсутствие механизма в ответе. Предикат остаётся правильным выбором там, где зависимость не оправдана: единственная граница, простая форма, жёсткие требования к размеру бандла.
</details>

**2. Чем отличаются по цене и по диагностике три места установки границы: HTTP-клиент, слой API, компонент?**

<details>
<summary>Ответ</summary>

| Место | Цена | Диагностика при отказе |
|---|---|---|
| HTTP-клиент | разбирается каждый ответ целиком, включая части, которые никому не нужны | известен URL, неизвестно, какой экран и зачем запрашивал; сообщение общего вида |
| Слой API | разбирается то, что запрошено, по схеме конкретного эндпоинта | известны эндпоинт, параметры и ожидаемая форма — сообщение содержательно |
| Компонент | проверка повторяется при каждом обновлении данных | известен экран, но источник далеко: непонятно, виноват сервер, кэш или код |

Рабочий выбор — **слой API**, по схеме на эндпоинт. Там валидация встаёт ровно перед преобразованием DTO в домен (2.11): проверили форму чужих данных, превратили в свои. Там же максимум контекста для сообщения об отказе.

HTTP-клиент оправдан для общей обёртки ответа — конверта с `data` и `meta`: его форма одинакова для всех эндпоинтов, а содержимое `data` проверяется схемой эндпоинта.

Компонент — худший вариант по обоим критериям сразу, и дополнительно смешивает рендер с разбором данных.

**Ответ «чем раньше, тем лучше, значит HTTP-клиент»** вскрывает подмену критерия одним измерением. Раньше — лучше для расстояния до источника и хуже для содержательности сообщения: клиент не знает, что именно запрашивали.

**Ответ «в компоненте удобнее, он знает, что ему нужно»** вскрывает смешение «кто потребитель данных» с «где проходит граница». Потребителей много, граница одна; проверка в каждом потребителе — это повторение работы с худшей диагностикой.

**Ответ «не важно где, лишь бы была»** вскрывает отсутствие цены в модели. Место определяет и объём разбора, и качество отчёта об ошибке — то есть обнаружите вы расхождение с сервером или нет.
</details>

**3. Пришёл ответ, в котором одно необязательное поле имеет неверный тип: какой из трёх вариантов поведения вы выберете и по какому признаку?**

<details>
<summary>Ответ</summary>

Деградация: отбросить поле, оставить остальное, записать факт в отчёт.

Признак выбора один: **можно ли показать экран без этого поля**. Поле объявлено необязательным, значит код уже обязан работать, когда его нет, — ветка для этого случая существует и протестирована. Отказ от всего ответа из-за него означал бы, что необязательное поле на деле обязательно, и тогда схема описывает модель неверно.

Полное правило по видам несоответствия:

| Что сломано | Поведение | Почему |
|---|---|---|
| обязательное поле отсутствует или неверного типа | отказ | экран собрать не из чего: без `id` нельзя открыть, без `title` нечего показать |
| необязательное поле неверного типа | отбросить поле | ветка «поля нет» уже существует |
| один элемент коллекции невалиден | отбросить элемент, остальные показать | пустой экран хуже списка без одной строки |
| корень не той формы | отказ | признак несовпадения версий или ошибки бэкенда |
| лишнее поле | пропустить | иначе расширение API становится ломающим изменением |

Обязательное дополнение к любому варианту, кроме последнего: **след в отчёте** с эндпоинтом и именем поля. Без него деградация неотличима от нормальной работы, и расхождение с сервером не обнаружится, пока кто-нибудь не заметит отсутствующую строку вручную.

**Ответ «отказать, иначе данные неполные»** вскрывает потерю различия между обязательным и необязательным. Если поле действительно нужно для экрана, ошибка не в ответе, а в схеме: оно не должно быть необязательным.

**Ответ «подставить значение по умолчанию»** вскрывает пропущенный вопрос «будет ли умолчание выглядеть как настоящие данные». Для `durationMin: 0` — будет, и исказит расчёт длительности курса. Умолчание уместно только там, где оно само по себе осмысленное состояние, например в конфигурации.

**Ответ «залогировать и продолжить как есть»** вскрывает пропущенный шаг: «как есть» означает, что непроверенное значение неверного типа поедет дальше в код, который считает его типизированным. Отбрасывание поля — не то же самое, что его пропуск мимо проверки.
</details>

**4. Приложение полностью на TypeScript со `strict: true`, все предупреждения исправлены. Что это говорит о форме данных, с которыми оно работает?**

<details>
<summary>Ответ</summary>

Ничего. `strict` — набор проверок **кода** (2.8): что аннотации расставлены, что `null` учтён, что неявного `any` нет. Проверкой данных он не является и являться не может: компилятор завершает работу до того, как появятся данные.

Формулировка, которую стоит держать в голове буквально: тип — утверждение о коде, а не о данных. Внутри кодовой базы утверждение проверено. На входе оно декларировано.

Отсюда наблюдение, которое объясняет большую часть крашей в «полностью типизированных» приложениях: строгость компилятора и соответствие данных — две независимые характеристики. Проект может иметь `strict: true`, ноль `any` и при этом принимать ответ сервера через `as`, читать хранилище без проверки и доверять параметрам deep link. Именно такие проекты дают сообщение «cannot read property of undefined» в коде, где ни одного `any` нет.

Перечень мест, где это происходит, и что с каждым делать — следующий урок, 2.13.

**Ответ «это говорит, что данные типизированы»** вскрывает ровно то заблуждение, против которого ставится вопрос: наличие типа принимается за наличие проверки.

**Ответ «strict проверяет `null`, значит `undefined` не придёт»** вскрывает смешение проверки кода с гарантией данных. `strictNullChecks` требует обработать объявленный `null`; если сервер прислал `null` там, где тип обещает `string`, флаг об этом не узнает.

**Ответ «значит, проверять нужно только пользовательский ввод»** вскрывает слишком узкое понимание границы. Ввод пользователя — лишь одна из границ, и далеко не самая опасная: ответ сервера, хранилище и deep link приходят в приложение в том же качестве.
</details>

## Задание — схема как единственный источник

**Дано.** Слой API из урока 2.11: карта эндпоинтов, DTO и преобразование в домен. Формы описаны типами, проверок нет. Экран уроков в продакшене периодически показывает пустой список, в отчётах об ошибках ничего нет.

```ts
type LessonDto = {
  id: string;
  title: string;
  duration_min: number;
  completed_at: string | null;
  tags?: string[];
};
```

**Требуется.**

1. Перевести `LessonDto` на схему так, чтобы тип выводился из неё, а добавление поля на сервере требовало правки ровно в одном месте. Показать, где именно в слое API стоит вызов проверки и почему не раньше и не позже.
2. Подать на вход три некорректных ответа и описать выбранное поведение для каждого с обоснованием:
   - в одном уроке отсутствует `id`;
   - в одном уроке `tags` пришёл строкой вместо массива;
   - в ответе появилось новое поле `author`, которого нет в схеме.
3. Ответить, что изменится в поведении приложения, если ту же схему применить к значению из `AsyncStorage`, и чем эта граница отличается от сетевой.
4. Назвать, что осталось непроверенным после введения схем, и сказать, чем закрывается каждая позиция.

---

<details>
<summary>Разбор</summary>

**1. Схема и место вызова.**

```ts
const lessonDtoSchema = object({
  id: string().min(1),
  title: string(),
  duration_min: number().int().nonnegative(),
  completed_at: nullable(string().datetime()),
  tags: optional(array(string())),
});

type LessonDto = Infer<typeof lessonDtoSchema>;   // тип выводится, руками не пишется

const lessonsResponseSchema = array(lessonDtoSchema);
```

Обратите внимание на то, чего в схеме стало больше по сравнению с типом: `min(1)` у `id`, `int().nonnegative()` у `duration_min`, `datetime()` у даты. Тип не умеет выражать «непустая строка» и «неотрицательное целое», схема умеет — и это второй её эффект помимо проверки формы. Пустой `id` и отрицательная длительность компилировались бы при любом типе.

Место вызова — в функции эндпоинта, **между получением ответа и преобразованием в домен**:

```ts
export async function loadLessons(courseId: string): Promise<Lesson[]> {
  const raw: unknown = await request('GET /courses/:courseId/lessons', { params: { courseId } });

  const parsed = lessonsResponseSchema.safeParse(raw);
  if (!parsed.ok) throw new InvalidResponse('GET /courses/:courseId/lessons', parsed.issues);

  return parsed.data.map(toLesson);
}
```

Почему не раньше: в HTTP-клиенте неизвестно, какой эндпоинт вызывали, и сообщение об отказе теряет контекст; к тому же клиент разбирал бы целиком каждый ответ, включая те, из которых экрану нужна часть.

Почему не позже: после `toLesson` проверять уже поздно — преобразование читает поля, то есть работает с непроверенными данными; а в компоненте проверка повторялась бы на каждом обновлении и отказ был бы оторван от источника.

Добавление поля на сервере, которое нужно приложению, требует правки ровно в одном месте — в схеме. Тип пересчитается, `toLesson` перестанет компилироваться, если поле должно попасть в домен, и компилятор сам приведёт в нужную строку.

**2. Три некорректных ответа.**

**Отсутствует `id` в одном уроке.** Отбросить этот элемент, остальные показать, записать факт в отчёт:

```ts
const items = Array.isArray(raw) ? raw : null;   // корень — строго
if (items === null) throw new InvalidResponse('GET /courses/:courseId/lessons', 'ожидался массив');

const valid: LessonDto[] = [];
for (const item of items) {
  const r = lessonDtoSchema.safeParse(item);
  if (r.ok) valid.push(r.data);
  else report('lessons: элемент отброшен', { endpoint: 'GET /courses/:courseId/lessons', issues: r.issues });
}
```

Цикл здесь не для наглядности: готового комбинатора «отбросить невалидный элемент» в схемах обычно нет. `.catch` на элементе **заменяет** невалидный элемент значением на случай отказа, а не убирает его (в zod `array(lessonDtoSchema.catch(null))` даст `[null, { … }]`, проверено), так что после него всё равно нужен фильтр — и отчёт о том, что отфильтровано.

Обоснование: `id` обязателен — без него урок нельзя открыть, поэтому элемент непригоден. Но непригоден **элемент**, а не ответ: девятнадцать уроков из двадцати показать можно, и пустой экран был бы худшим решением из возможных. Строка отчёта обязательна — именно её отсутствие в исходной задаче объясняет, почему «пустой список в продакшене» никто не мог диагностировать.

Отдельно: корень ответа проверяется строго. Если вместо массива пришёл объект — отказ, потому что показывать нечего и это признак несовпадения версий API.

**`tags` пришёл строкой вместо массива.** Отбросить поле, урок показать:

```ts
tags: optional(array(string())).catch(undefined),
```

Обоснование: `tags` необязателен, значит ветка «тегов нет» в коде уже есть и протестирована. Отказ от урока целиком означал бы, что необязательное поле фактически обязательно. След в отчёте нужен и здесь: неверный тип необязательного поля — сигнал о расхождении с бэкендом, просто не срочный. Сам по себе `.catch(undefined)` подменяет значение молча; чтобы отчёт появился, значение на случай отказа задают функцией — в zod она получает исходное значение и ошибку: `.catch((ctx) => { report('lessons: tags отброшен', { input: ctx.input }); return undefined; })`.

**Новое поле `author`.** Пропустить молча. Схема объекта по умолчанию не отвергает неизвестные поля, а убирает их из результата (так ведут себя `object` и в zod, и в valibot): `author` в `parsed.data` не попадёт, и код не сможет случайно начать читать непроверенное поле. Это правильное поведение: сервер вправе расширять ответ, а старые версии приложения продолжают работать у пользователей месяцами. Строгая схема, запрещающая лишние поля, превратила бы любое расширение API в ломающее изменение — и сломала бы именно те версии, которые уже нельзя обновить принудительно.

**3. Та же схема для `AsyncStorage`.**

Применение техническое такое же — разобрать строку, проверить схемой, — а поведение при отказе другое:

```ts
const stored = await AsyncStorage.getItem(key);
if (stored === null) return initial;

let raw: unknown;
try { raw = JSON.parse(stored); } catch { return initial; }   // невалидный JSON

const parsed = progressSchema.safeParse(raw);
if (!parsed.ok) {
  report('storage: запись не прошла схему', { key, issues: parsed.issues });
  return initial;          // не ошибка наверх, а сброс к начальному состоянию
}
return parsed.data;
```

Три отличия границы хранилища от сетевой:

- **направление устаревания обратное.** В сети новый сервер отвечает старому коду; в хранилище старые данные приходят к новому коду. Запись сделана моделью, которой в кодовой базе уже нет;
- **чинить некому.** Неверный ответ сервера исправляется выкаткой бэкенда; неверная запись в хранилище лежит на устройстве пользователя, и исправить её может только код приложения;
- **отказ не должен быть видимым.** Экран обязан открыться: при невалидной записи приложение возвращается к начальному состоянию, а не показывает ошибку. Цена — потеря локальных данных, поэтому различать «повреждено» и «записано старой моделью» важно: во втором случае запись нужно не отбрасывать, а мигрировать. Версионирование и миграции — 6.6.

**4. Что осталось непроверенным.**

| Позиция | Чем закрывается |
|---|---|
| соответствие схемы реальному контракту сервера: схема — утверждение, написанное человеком | контрактным тестом или генерацией схем из спецификации API — блок 11 |
| смысл данных: `id` корректен как строка, но может указывать на чужой ресурс | проверками прав на сервере; клиентская схема этого не заменяет |
| параметры deep link и восстановленное состояние навигации | 2.13 — перечень границ, 4.18 — конфигурация linking |
| колбэки и аргументы нативных модулей | 2.13, контракт модуля — блок 09 |
| значения, записанные старой моделью и требующие миграции, а не отбрасывания | 6.6 |
| политика при повторяющихся отказах: retry, деградация, офлайн | 7.3 |

**Вклад в проект (P2).** Разбор входных данных курса переведён с ручного предиката из 2.4 на схему: тип домена выводится из неё, предикат удалён, расхождение проверки с типом стало невозможным. Зафиксирована политика проекта: валидация стоит в функции эндпоинта перед преобразованием в домен; корень ответа проверяется строго, элементы коллекции — поэлементно с отбрасыванием невалидных; любое отбрасывание и любая деградация оставляют строку в отчёте с эндпоинтом и именем поля; неизвестные поля игнорируются. Перечень границ, на которых эта политика должна применяться, составляется в 2.13.
