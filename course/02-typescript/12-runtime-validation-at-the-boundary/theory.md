# 2.12 Runtime-валидация на границе и вывод типа из схемы — theory

> 🔴 SENIOR. Семь углов разбора. Урок отвечает не на вопрос «какую библиотеку валидации взять» — а на вопрос, **кто и когда проверяет, что данные имеют ту форму, которую обещает тип**.

---

## 1. Что это

**Схема** — объект-описание формы данных, существующий в рантайме. Из него выводится тип, и он же выполняет проверку.

```ts
const lessonSchema = object({
  id: string(),
  title: string(),
  durationMin: number(),
  completedAt: nullable(string()),
});

type Lesson = Infer<typeof lessonSchema>;
// { id: string; title: string; durationMin: number; completedAt: string | null }

const result = lessonSchema.safeParse(raw);   // проверка той же схемой
```

> Код схемы в уроке — обобщённая запись, а не API конкретной библиотеки. В zod это `z.object(...)`, `schema.safeParse(raw)` и `z.infer<typeof schema>`; в valibot — `v.object(...)`, `v.safeParse(schema, raw)` и `v.InferOutput<typeof schema>`. Механизм одинаков, отличаются имена.

Два свойства, из которых следует весь урок. Первое: схема — **значение**, а не тип, поэтому она доживает до рантайма и способна проверять. Второе: тип получен **из неё** вычислением (2.10), а не написан рядом, — поэтому разойтись они не могут по построению.

Сравните с тем, что даёт предыдущая техника из 2.4:

```ts
type Lesson = { id: string; title: string; durationMin: number; completedAt: string | null };

function isLesson(x: unknown): x is Lesson { /* проверка руками */ }
```

Здесь два описания одной формы: тип и тело предиката. Они связаны только намерением автора — тем же, чем `request<T>(url)` был связан с путём в 2.11.

### Ключевая формулировка урока

> **Схема — единственное описание формы, которое существует в обоих мирах: компилятор выводит из неё тип, рантайм выполняет ею проверку. Всё остальное — два описания, которые расходятся.**

Инструмент (zod, valibot, собственные комбинаторы) — реализация. Ось урока — вопрос о том, кто и когда проверяет.

## 2. Как это работает

### Почему предикат расходится, а схема — нет

Разойтись могут только два независимых описания. Проследим одно изменение модели — на сервере поле `durationMin` стало необязательным.

**С предикатом.** Правка нужна в двух местах: в типе (`durationMin?: number`) и в теле предиката (убрать требование). Поправили тип, забыли предикат — предикат остался строже, чем нужно, и начал отбрасывать корректные данные. Поправили предикат, забыли тип — предикат стал слабее, и `durationMin` читается как `number`, будучи `undefined`. Компилятор не скажет ни в одном из двух случаев: он не знает, что тело предиката обязано соответствовать типу (2.4).

**Со схемой.** Правка одна: `durationMin: optional(number())`. Тип пересчитывается автоматически, и все места чтения, которые перестали быть корректными, немедленно дают ошибку компиляции. Расхождение невозможно не потому, что за ним следят, а потому, что описание одно.

Это и есть содержание урока в одном абзаце. Остальное — где поставить границу и что делать при несовпадении.

### Где поставить границу

Три места, и они отличаются ценой и качеством диагностики.

| Место | Что проверяется | Цена | Диагностика при отказе |
|---|---|---|---|
| HTTP-клиент | каждый ответ, единообразно | разбор всех ответов, включая те, что никому не нужны целиком | «ответ не прошёл схему» — без привязки к экрану |
| Слой API / функция эндпоинта | ответ конкретного эндпоинта | только то, что запрошено | известен эндпоинт, параметры и ожидаемая форма |
| Компонент или экран | данные, которые он рендерит | проверка повторяется при каждом рендере данных | известен экран, но причина уже далеко от источника |

Рабочий выбор — **слой API**, по одной схеме на эндпоинт. Там известно, что именно запрашивали, поэтому сообщение об отказе содержательно; там же находится преобразование DTO в домен (2.11), и валидация встаёт ровно перед ним: проверили форму чужих данных, превратили в свои.

HTTP-клиент как место валидации оправдан в одном случае — когда нужна общая для всех ответов обёртка (конверт с `data` и `meta`): её форма проверяется в клиенте, а содержимое `data` — схемой эндпоинта.

Компонент — худшее место: он далёк от источника, проверка повторяется, а при отказе непонятно, виноват сервер, кэш или код экрана.

### Стратегии при невалидных данных

Решение принимается не «вообще», а по тому, **что именно сломано** и **можно ли без этого показать экран**.

| Что сломано | Разумное поведение | Почему |
|---|---|---|
| обязательное поле отсутствует или неверного типа | отказ: ошибка наверх | без `id` элемент нельзя открыть, без `title` нечего показать — экран собрать не из чего |
| необязательное поле неверного типа | деградация: отбросить поле, оставить остальное | поле по определению необязательно, код уже обязан работать без него. Само это не произойдёт: по умолчанию схема отвергает **весь** объект из-за одного неверного поля, и деградацию нужно описать явно — значением на случай отказа для поля (`.catch(undefined)` в zod, `fallback` в valibot) |
| один элемент коллекции невалиден | отбросить элемент, остальные показать, факт отбрасывания отправить в отчёт (схема массива по умолчанию отвергает массив целиком, поэтому элементы проверяют по одному) | пустой экран хуже списка без одной строки; молчаливое отбрасывание хуже обоих |
| корень ответа не той формы (ожидался массив, пришёл объект) | отказ | показывать нечего, и это признак несовпадения версий или ошибки бэкенда |
| лишнее поле | пропустить | сервер вправе добавлять поля; падение на лишнем поле делает любое расширение API ломающим изменением |

Два правила поверх таблицы. Первое: **любая деградация обязана оставлять след** — строку в отчёте об ошибках с эндпоинтом и именем поля. Без неё расхождение между сервером и приложением не обнаружится никогда: пользователь просто не увидит урок (10.6). Второе: значение по умолчанию вместо отсутствующих данных допустимо только там, где оно не выглядит как настоящие данные. Подставленный `title: 'Без названия'` маскирует дефект бэкенда; `durationMin: 0` искажает расчёт длительности курса.

### Что схема не делает

Схема проверяет **форму и допустимые значения**. Она ничего не знает о смысле: `lessonId`, корректный как строка, может указывать на чужой урок; `url`, корректный как строка, может вести на недоверенный домен. Проверки смысла — это правила домена и серверные проверки, и схема их не заменяет (угол 3).

## 3. Почему это важно

### Threat

Клиент получает данные, форму которых не контролирует:

- **ответ сервера** — изменившегося, выкатившего новую мажорную версию API, или скомпрометированного;
- **значение из хранилища** — записанное другой версией приложения или подменённое на устройстве с root-доступом;
- **параметры deep link** — сформированные кем угодно, потому что ссылку создаёт не приложение;
- **конфигурация, приходящая с сервера** — feature flags, адреса, лимиты.

Последствия ранжируются от краша и пустого экрана до рендера чужого содержимого и перехода по подставленному адресу.

### Mitigation

Проверка формы и допустимых значений в одной точке на входе, с типом, выведенным из той же проверки. После границы код работает с данными, форма которых проверена, а не задекларирована. Это единственное, что отличает «типизированное приложение» от «приложения, в котором типы соответствуют данным».

### Limitations

Проверка формы не проверяет смысл: корректный по форме идентификатор может указывать на чужой ресурс, корректная строка может быть ссылкой на недоверенный домен, корректное число может быть вне допустимого диапазона, если диапазон не описан в схеме.

Валидация на клиенте **не заменяет проверок на сервере**: клиент контролирует только то, что показывает, а не то, что разрешено. И она не защищает от скомпрометированного устройства, где атакующий контролирует сам код приложения — там отключить валидацию так же просто, как её добавить.

### Trade-offs

Схемы увеличивают бандл и добавляют работу на разбор каждого ответа — заметно на больших коллекциях и на старте приложения. Схемы нужно поддерживать вместе с моделью. Валидация каждого внутреннего вызова даёт цену без выгоды: внутри кодовой базы форму уже проверил компилятор.

### Decision

Закрывать в первую очередь границы, где данные приходят извне кодовой базы и где последствия несоответствия видны пользователю. Для границ с низкой ценой ошибки допустимо осознанное решение не проверять — **при условии, что оно записано**, а не получилось само. Разницу между «решили не закрывать» и «не заметили» разбирает 2.13.

## 4. Где это в React Native

### Старые версии живут на устройствах месяцами

Главное отличие мобильного приложения от веба, и оно меняет расстановку приоритетов. В вебе новая версия кода доезжает до всех при перезагрузке; в мобильном приложении версия, выпущенная полгода назад, продолжает работать у части пользователей. Отсюда две границы разного характера:

- **ответ сервера** — новый сервер отвечает старому коду. Схема старой версии не знает о новых полях (и не должна на них падать), но может не пережить изменения формы существующих;
- **локальное хранилище** — старые данные приходят к новому коду. Запись сделана моделью, которой в коде уже нет, и никакого «сервера, который починит» здесь не существует.

Вторая граница опаснее первой, потому что чинится только кодом самого приложения — и именно поэтому миграции схемы персистентного стейта вынесены в отдельный урок 6.6.

### Ответ сервера

Схема на эндпоинт, валидация в слое API перед преобразованием в домен (2.11). Поле, появившееся на сервере и отсутствующее в схеме, игнорируется — это правильное поведение: иначе любое расширение API становилось бы ломающим.

### Значение из хранилища

Схема здесь нужна не менее, чем для сети, и применяется при чтении. Отказ означает не «показать ошибку», а «считать, что данных нет»: сбросить к начальному состоянию и записать факт в отчёт. Отдельный вопрос — версионирование записи, чтобы отличать «повреждено» от «записано старой моделью»; это 6.6.

### Параметры deep link

Ссылку формирует кто угодно: письмо, push, сторонний сайт, буфер обмена. Значения приходят строками, даже если параметр объявлен числом, и ни одно из них не проверено `ParamList` — типизация навигации описывает контракт между экранами приложения, а не содержимое внешней ссылки. Разбор ссылки — граница, и закрывается она схемой так же, как ответ сервера. Конфигурация linking и поведение при холодном старте — 4.18.

### Конфигурация с сервера

Feature flags, лимиты, адреса. Специфика в том, что отказ здесь не должен ломать запуск: при невалидной конфигурации приложение обязано стартовать на значениях по умолчанию и сообщить об этом в отчёт. Это тот случай, где «значение по умолчанию» — правильная стратегия, потому что умолчание и есть осмысленное состояние.

## 5. Типичные ошибки

**Валидация всего подряд.** Схемы на внутренние функции, на аргументы доменных методов, на данные, уже прошедшие границу. Причина — стремление к последовательности: «если валидируем, то везде». Внутри кодовой базы форму проверил компилятор, и повторная проверка даёт стоимость без выгоды. Валидируется то, что пересекает границу.

**Схема, продублированная типом.** Написали схему, рядом написали `type Lesson = { ... }` руками — и вернулись ровно к проблеме предиката, только с лишней зависимостью. Тип обязан выводиться из схемы.

**Отказ без сообщения.** Невалидный ответ превращается в пустой список, и экран выглядит как «данных нет». Пользователь не отличает это от пустого курса, разработчик не видит проблемы в отчётах, и расхождение живёт месяцами. Любой отказ и любая деградация оставляют след.

**Падение на лишнем поле.** Строгая схема, запрещающая неизвестные поля, применённая к ответу сервера. Любое расширение API становится ломающим изменением для старых версий приложения, которые ещё у пользователей.

**Валидация на компоненте.** Схема вызывается в рендере, проверка повторяется на каждом обновлении, а при отказе неясно, где источник.

**Схема как замена серверным проверкам.** Проверили на клиенте и решили, что данные безопасны. Клиент контролирует то, что показывает, а не то, что разрешено; проверки прав и бизнес-правил живут на сервере.

## 6. Trade-offs

### Размер бандла и время разбора против краша у пользователя

Схемы — это код, попадающий в бандл, и работа на JS-потоке при каждом разборе. На списке из тысячи элементов проверка заметна, на старте приложения при чтении большого кэша — заметна вдвойне, потому что конкурирует с TTI (блок 05).

Противоположная цена — краш у пользователя и пустой экран без следа в отчётах. Сопоставляются эти цены не в общем виде, а по границам: ответ, из которого строится весь экран, проверять стоит; словарь переводов на тысячу ключей, который ломает только одну подпись, — вероятно, нет.

### Стоимость поддержки схем

Схема живёт вместе с моделью, и каждое изменение формы — правка схемы. Это дешевле предиката (правка одна вместо двух), но не бесплатно. На проекте с сотней эндпоинтов схемы становятся самостоятельным артефактом, который кто-то обязан поддерживать; там уместно генерировать их из спецификации API, а не писать руками.

### Частичная проверка как осознанный компромисс

Схема не обязана описывать все поля ответа. Проверять можно то, на что опирается экран, игнорируя остальное, — и это часто лучшее соотношение цены и эффекта. Важно, чтобы решение было явным: комментарий «проверяем только поля, используемые экраном» отличает компромисс от недосмотра.

### Когда валидация избыточна

Три случая. Данные, которые не покидают приложение и не переживают его запуск (состояние в памяти). Границы с нулевой ценой ошибки — значение, от которого зависит только цвет подписи. Данные, форму которых контролирует та же команда в том же релизном цикле, — там дешевле контрактный тест, чем проверка в рантайме у каждого пользователя (блок 11).
