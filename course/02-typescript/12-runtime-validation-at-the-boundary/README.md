## Цель

Сделать так, чтобы на границе существовало одно описание формы данных, которое одновременно даёт тип и выполняет проверку.

## Что внутри

Схема как значение, доживающее до рантайма, и тип, выведенный из неё вычислением · почему предикат из 2.4 расходится с типом при первом изменении модели, а схема не может разойтись по построению · три места установки границы — HTTP-клиент, слой API, компонент — и чем они различаются по цене и по диагностике · стратегии при невалидных данных: отказ, деградация, отбрасывание элемента, значение по умолчанию, и признак выбора между ними · где это в RN: ответ сервера, хранилище, параметры deep link, конфигурация с сервера · ошибки: валидация всего подряд, схема рядом с продублированным типом, отказ без следа в отчёте, падение на лишнем поле · trade-offs: бандл и время разбора против краша у пользователя, стоимость поддержки схем, когда валидация избыточна.

## Ключевая формулировка урока

**Схема — единственное описание формы, которое существует в обоих мирах: компилятор выводит из неё тип, рантайм выполняет ею проверку. Всё остальное — два описания, которые расходятся.**

Инструмент (zod, valibot, собственные комбинаторы) — реализация. Ось урока — вопрос «кто и когда проверяет, что данные имеют ту форму, которую обещает тип».

## Security в этом уроке

Первое появление concern Security в курсе. Материал подаётся по схеме `threat → mitigation → limitations → trade-offs → decision`, а не как перечень обязательных практик, и угол 3 теории построен именно так. Ключевые ограничения названы прямо: проверка формы не проверяет смысл, валидация на клиенте не заменяет серверных проверок и не защищает от скомпрометированного устройства.
