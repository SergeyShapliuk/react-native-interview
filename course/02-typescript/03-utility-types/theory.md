# 2.3 Утилитарные типы — theory

> 🟢 REFRESH. Синтаксис `Partial<T>` аудитория знает. Урок — про то, где объявлен источник описания модели и где вывод типа хуже явного описания.

## Refresh

### Одна модель, остальные формы выводятся

У урока есть полная запись, DTO с сервера, тело запроса на создание, черновик формы и строка списка. Вопрос не «как короче записать», а **где объявлен источник**: либо один тип, из которого остальные вычислены, либо пять описаний, которые разойдутся при первом изменении поля.

```ts
type Lesson = {
  id: string;
  title: string;
  durationMin: number;
  completedAt: string | null;
};
```

Всё дальнейшее — операции над этим типом. Альтернатива — скопировать поля руками: сегодня копия совпадает с моделью, через три месяца в `Lesson` добавлено `tags`, а в копии нет. Компилятор молчит, потому что о связи ему не сообщили; `Pick` и `Omit` её объявляют, и расхождение становится ошибкой сборки.

### Mapped type как общий механизм

**Mapped type (отображённый тип)** — тип, который перебирает ключи другого типа и по каждому строит поле результата. Утилиты стандартной библиотеки собраны из него:

```ts
type Partial<T> = { [K in keyof T]?: T[K] };
```

Так же устроены `Required`, `Readonly` и `Pick`. Утилиты — не фиксированный набор, а примеры одного механизма; когда ни одна не подходит, пишется своя.

> **Не дублировать:** устройство mapped и conditional types, модификаторы `-?` и `+readonly`, `infer` — урок 2.10.

### `Partial`: цена «всё необязательно»

`Partial<T>` делает необязательным каждое поле. Точный тип для аргумента частичного обновления:

```ts
function updateLesson(id: string, patch: Partial<Lesson>): void;
```

И неверный — для **состояния**:

```ts
const [lesson] = useState<Partial<Lesson>>({});
lesson.title.toUpperCase(); // ошибка: title может быть undefined
```

Тип честен и потому неудобен: раз ни одного поля может не быть, проверка требуется при каждом чтении. Проверки размножаются по экранам, дальше их глушат через `!` или `as Lesson` — возврат к `any` другим путём. `Partial<Lesson>` — «набор изменений», а не «урок, который ещё не загрузился».

> **Не дублировать:** состояние «загружается / загружено / ошибка» и discriminated union — урок 2.5. Здесь важно лишь то, что `Partial` делает невозможное состояние выразимым, а не запрещённым.

`Partial` ставит `?`, а не `| null`: отсутствие ключа и значение `null` — разное. При `exactOptionalPropertyTypes` это наблюдаемо — `{ title: undefined }` под `Partial<Lesson>` не подходит.

### `Pick` и `Omit`: одна задача, разная устойчивость

```ts
type LessonListItem = Pick<Lesson, 'id' | 'title' | 'durationMin'>;
type LessonDraft = Omit<Lesson, 'id' | 'completedAt'>;
```

Симметрия кажущаяся. `Pick` требует, чтобы ключи были подмножеством `keyof T`; у `Omit` второй параметр — `keyof any`, то есть любая строка:

```ts
type A = Pick<Lesson, 'titel'>; // ошибка: 'titel' не ключ Lesson
type B = Omit<Lesson, 'titel'>; // компилируется, равен Lesson целиком
```

Следствие — не опечатка, а **переименование**. `completedAt` стал `finishedAt`: все `Pick` по старому имени перестанут компилироваться и будут найдены компилятором, все `Omit` молча перестанут что-либо исключать, и черновик формы приобретёт серверное поле.

Отсюда правило: при малом числе полей предпочтительнее `Pick` — он перечисляет нужное и проверяется. `Omit` оправдан при исключении одного-двух полей из большой модели; тогда список исключений стоит сделать проверяемым через `Extract<keyof Lesson, 'id' | 'completedAt'>`, который даст `never` при опечатке.

### `Record` против index signature

```ts
type ByPlatform = Record<'ios' | 'android', number>; // оба ключа обязательны
type AnyMap = { [key: string]: number };             // любые ключи, ни один не обязателен
```

`Record` с union литералов — **полная** карта: третий ключ запрещён, пропущенный не компилируется, места для правки перечисляет компилятор. `Record<string, number>` эквивалентен index signature: любой ключ допустим, `map['typo']` имеет тип `number` при `undefined` в рантайме.

Первое — для конфигурации с известным набором ключей, второе — для словаря, ключи которого известны только в рантайме. Строгость даёт не `Record`, а конечный union в позиции ключа.

### Остальной ряд

`Required<T>` снимает `?`; `Readonly<T>` добавляет `readonly` (проверка только при компиляции); `NonNullable<T>` убирает `null` и `undefined` из union; `ReturnType<typeof fn>` — тип возврата; `Parameters<typeof fn>` — кортеж параметров; `Awaited<T>` — тип, в который разрешается промис.

Последние три работают от **значения** через `typeof`: тип берётся из реализации и не может от неё отстать — например, `ReturnType<typeof useLessonState>` вместо ручного описания возврата кастомного хука (3.12).

### Когда цепочку пора назвать типом

```ts
type DraftPatch = Partial<Omit<Lesson, 'id' | 'completedAt'>>;      // ещё читается
type X = Partial<Record<keyof Omit<Lesson, 'id'>, string | null>>;  // уже нет
```

Критерий: если выражение приходится раскручивать изнутри наружу, у него должно быть имя — оно несёт то, чего в выражении нет, то есть зачем этот тип существует (`type LessonFormErrors = Partial<Record<keyof LessonDraft, string>>`). И если производный тип переопределяет половину полей через `&`, связи с моделью уже нет, и явные строки описывают больше.

## RN relevance

### Черновик формы, выведенный из сущности

`id` выдаёт сервер, `completedAt` появляется позже, форма работает с остальным:

```ts
type LessonDraft = Pick<Lesson, 'title' | 'durationMin'>;
```

При `LessonDraft` поле `title` обязательно и всегда строка — пустая строка валидна как начальное значение. При `Partial<Lesson>` каждый `TextInput` получает `string | undefined` и требует `?? ''`.

### DTO ответа и доменный тип

Ответ сервера и модель домена — два разных типа, даже если сегодня поля совпадают. Соблазн:

```ts
type Lesson = Pick<LessonDto, 'id' | 'title' | 'duration_min'>;
```

Так домен наследует форму ответа backend: имена полей, формат дат, признак «приходит строкой». Изменение контракта расходится по экранам, которые с сервером не разговаривают. Зависимость должна быть обратной: домен объявлен сам, DTO отображается в него в слое API.

> **Не дублировать:** типизация слоя API так, чтобы тип ответа выводился, — 2.11; изоляция от формы ответа backend — 8.5.

### Тело запроса на создание

```ts
type CreateLessonBody = Omit<Lesson, 'id' | 'completedAt'>;
```

Случай, где `Omit` оправдан и где его хрупкость вреднее всего: переименование `completedAt` добавит серверное поле в тело POST, и сервер его либо проигнорирует, либо отвергнет.

### `Record` для конфигурации по экранам

```ts
type ScreenName = 'Lessons' | 'LessonDetails' | 'Progress';
const titles: Record<ScreenName, string> = { /* три ключа, все обязательны */ };
```

Добавили экран в `ScreenName` — литерал перестал соответствовать типу, компилятор назвал недостающий ключ. С `Record<string, string>` неполная карта собралась бы, и заголовок оказался бы пустым в рантайме. Второй случай того же вида — платформенная карта `Record<'ios' | 'android', number>`.

### Поля, которые приходят не всегда

Если `description` приходит только в детальном ответе, у приложения два состояния сущности — и это два типа: `Omit<Lesson, 'description'>` для списка и `Lesson` для детали. Соблазн — один тип с `description?: string`; тогда экран детали тоже получает «описания может не быть» и обязан это обрабатывать, хотя в его контракте описание есть всегда.

### Где утилита ничего не решает

```ts
const dto = (await res.json()) as Partial<LessonDto>; // проверки не произошло
```

`Partial` здесь не защита от неполного ответа, а переименование неизвестного: `res.json()` вернёт что угодно, проверок не добавится — только `?.` по коду и впечатление, что данные обработаны аккуратно. Та же конструкция, что `getItem<Lesson>()` из 2.2: параметр типа ничем не связан с действительностью.

Правило: утилитарные типы преобразуют уже достоверный тип и не добывают достоверность. Разница между «тип проверен» и «тип обещан» — ось уроков 2.12 (валидация на границе и вывод типа из схемы) и 2.13 (границы системы целиком).

## Типичные заблуждения

**«`Omit` проверяет, что поле существует.»** Берётся из симметрии с `Pick`, который проверяет. Второй параметр `Omit` — `keyof any`, поэтому `Omit<Lesson, 'titel'>` компилируется и равен `Lesson`. Проверка: посмотреть в подсказке редактора результат `Omit<T, 'нет-такого-поля'>`.

**«`Partial<T>` делает поля `null`.»** Берётся из API и языков, где «необязательно» и «пусто» — одно и то же. `Partial` ставит `?`: ключа может не быть, `null` не появляется. Проверка: `{ ...base, ...patch }` при явном `undefined` затрёт значение, при отсутствующем ключе — сохранит.

**«`Partial` — нормальный тип для состояния, которое заполняется постепенно.»** Берётся из верного наблюдения, что на старте полей нет. Но «любое подмножество допустимо» означает, что допустима и любая невозможная комбинация. Проверка: посчитать `?.` и `!`, появившиеся в экранах после введения такого типа.

**«Доменная модель — это `Pick` от DTO.»** Берётся из того, что в первый день они совпадают. Утилита объявляет зависимость домена от формы ответа сервера. Проверка: что придётся менять при переименовании поля в API; если список длиннее одного модуля, зависимость направлена неверно.

**«Чем длиннее цепочка утилит, тем меньше дублирования.»** Дублирования меньше, но следующий разработчик не разбирает `Partial<Record<keyof Omit<...>, ...>>`, а пишет тип руками рядом — и дублирование возвращается, теперь незаметно.
