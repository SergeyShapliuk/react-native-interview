# 2.3 Утилитарные типы — practice

## Проверка понимания

Цель — не оценка, а обнаружение пробела. У каждого вопроса указано, что вскрывает неверный ответ.

---

**1. Что произойдёт при `Omit<Lesson, 'titel'>` и почему компилятор молчит?**

```ts
type Lesson = { id: string; title: string; durationMin: number };
type Draft = Omit<Lesson, 'titel'>;
```

<details>
<summary>Ответ</summary>

`Draft` окажется равен `Lesson` целиком: ни одно поле не убрано. Компилятор молчит, потому что второй параметр `Omit` не ограничен ключами `T` — в его сигнатуре стоит `keyof any`, то есть допустима любая строка. У `Pick` ограничение есть (`K extends keyof T`), и та же опечатка там не компилируется.

**Неверный ответ «будет ошибка, как у `Pick`»** вскрывает предположение о симметрии там, где её нет. Практическая цена проявляется не на опечатках, а на переименовании поля: все `Pick` по старому имени сломаются и будут найдены, все `Omit` по старому имени тихо перестанут что-либо исключать, и производный тип приобретёт поле, которого в нём быть не должно.

**Ответ «ничего страшного, в рантайме типов нет»** вскрывает смешение двух вопросов. Верно, что типов в рантайме нет; но молчащий `Omit` означает, что в тело POST-запроса попадёт серверное поле, а в черновик формы — поле, которого форма не заполняет. Ошибка реальна, просто обнаруживается не компилятором.
</details>

---

**2. Чем `Partial<T>` отличается от типа, где каждое поле объявлено как `| undefined`?**

```ts
type A = Partial<{ title: string }>;        // { title?: string }
type B = { title: string | undefined };
```

<details>
<summary>Ответ</summary>

`Partial` ставит модификатор `?` — ключа в объекте может не быть вовсе. В `B` ключ обязателен, просто его значением может быть `undefined`: `{}` под `B` не подходит, а под `A` подходит.

При включённом `exactOptionalPropertyTypes` расходится и обратное: `{ title: undefined }` перестаёт подходить под `A`, потому что `?` означает «ключа нет», а не «значение `undefined`». Без этого флага TypeScript считает `?` и `| undefined` почти взаимозаменяемыми, и разница не видна.

**Неверный ответ «это одно и то же»** вскрывает отсутствие различия между «ключа нет» и «значение пустое». В RN это различие наблюдаемо сразу: `Object.keys()` даст разные результаты, `JSON.stringify` выбросит поле со значением `undefined`, а `{ ...base, ...patch }` в случае явного `undefined` затрёт существующее значение, тогда как при отсутствующем ключе сохранит его. Последнее — типовой баг частичного обновления.

**Ответ «`Partial` делает поля `null`»** вскрывает перенос модели «необязательно = пусто» из API или из другого языка. `null` в типе не появляется ни при каких настройках.
</details>

---

**3. Чем `Record<'ios' | 'android', number>` отличается от `{ [key: string]: number }` и что из этого следует?**

<details>
<summary>Ответ</summary>

Первый требует ровно два ключа: оба обязательны, третий запрещён. Второй допускает любые ключи и не требует ни одного.

Следствие — направление, в котором движется ошибка. Добавление платформы в union ломает сборку во всех неполных картах, и компилятор перечисляет места для правки. С index signature неполная карта соберётся, а обращение по отсутствующему ключу будет иметь тип `number` при значении `undefined` в рантайме — ошибка доедет до устройства.

**Неверный ответ «разница только в синтаксисе»** вскрывает отношение к типу как к аннотации, а не как к утверждению, которое проверяется. Практическая цена: карта заголовков экранов, в которой забыт новый экран, собирается и падает в рантайме.

**Ответ «`Record` строже всегда»** вскрывает отсутствие второй половины картины: `Record<string, number>` — ровно та же index signature, строгость даёт не `Record`, а конечный union в позиции ключа.
</details>

**4. Почему вывод доменной модели из DTO через `Pick` связывает приложение с формой ответа сервера сильнее, чем явное описание?**

<details>
<summary>Ответ</summary>

Потому что `Pick<LessonDto, ...>` — это объявленная зависимость: доменный тип не существует отдельно, он вычисляется из серверного. Имена полей, формат значений (дата строкой, число строкой), признак необязательности — всё приходит из DTO. Изменение контракта API меняет доменный тип, и правки расходятся по экранам, которые с сервером не взаимодействуют.

Явное описание домена ставит точку преобразования в одно место — слой API, где DTO отображается в модель. Контракт сервера меняется — меняется мэппер; остальное приложение не замечает.

**Неверный ответ «так меньше дублирования, значит лучше»** вскрывает применение правила «не дублировать» без вопроса о направлении зависимости. Дублирование убирается всегда ценой связи, и вопрос в том, между чем эта связь возникает: между моделью и её производными — полезно, между доменом и внешним контрактом — вредно.

**Ответ «это нормально, пока поля совпадают»** вскрывает оценку решения по сегодняшнему состоянию. Поля совпадают в первый день; тип объявляет, что они будут совпадать всегда.
</details>

## Задание

**Дано.** RN Academy, стадия P2. В домене объявлен тип урока:

```ts
type Lesson = {
  id: string;
  courseId: string;
  title: string;
  description: string;
  durationMin: number;
  order: number;
  completedAt: string | null;
};
```

В коде сейчас существуют четыре типа, написанные руками и уже разошедшиеся с моделью:

```ts
type LessonListItem = {
  id: string;
  title: string;
  durationMin: number;
};

type LessonFormState = Partial<Lesson>;

type CreateLessonBody = {
  courseId: string;
  title: string;
  description: string;
  duration: number; // расхождение: в модели durationMin
};

type LessonTitles = { [screen: string]: string };
```

**Требуется.**

1. Переписать `LessonListItem` и `CreateLessonBody` так, чтобы они выводились из `Lesson`. Для каждого обосновать выбор между `Pick` и `Omit`, назвав, что сломается при переименовании поля в модели.
2. Заменить `LessonFormState` на тип, при котором экран формы не обязан проверять каждое поле при чтении. Сформулировать, какую именно задачу `Partial` здесь решал неверно и какому уроку принадлежит полное решение состояния «загружается / загружено / ошибка».
3. Привести `LessonTitles` к форме, в которой добавление нового экрана в приложение ломает сборку. Показать, где именно появится ошибка.
4. Проверить результат: добавить в `Lesson` поле `isFree: boolean` и перечислить, в скольких местах понадобится правка и каких именно. Если их больше одного — объяснить, почему связь не выведена до конца.

---

<details>
<summary>Разбор</summary>

**1. Производные типы.**

```ts
type LessonListItem = Pick<Lesson, 'id' | 'title' | 'durationMin'>;

type ServerOwned = 'id' | 'completedAt';
type CreateLessonBody = Omit<Lesson, ServerOwned>;
```

`Pick` для элемента списка: полей мало, они перечислены явно, и при переименовании `durationMin` в модели этот тип **перестанет компилироваться** — компилятор покажет точку правки.

`Omit` для тела запроса: исключаются поля, которыми владеет сервер, и их два, а остальных пять. Перечислять пять ради `Pick` хуже по смыслу — список «что сервер заполняет сам» и есть содержательное утверждение. Но хрупкость нужно назвать вслух: переименование `completedAt` в модели **не сломает сборку**, а добавит серверное поле в тело POST. Именованный `ServerOwned` этого не чинит, он только делает список исключений видимым в одном месте; проверяемым его делает `Extract<keyof Lesson, 'id' | 'completedAt'>`, который даст `never` при опечатке.

Заодно исчезло расхождение `duration` / `durationMin` — ровно тот класс ошибок, ради которого вывод и нужен.

**2. Состояние формы.**

```ts
type LessonFormState = Omit<Lesson, ServerOwned | 'order'>;
```

или, если полей для формы заметно меньше, — `Pick` с явным перечислением.

Что `Partial` решал неверно: он описывал не черновик, а «любое подмножество полей урока». Для экрана это означает, что `title` имеет тип `string | undefined` и каждое использование требует `?? ''` или `!`. Поля формы на самом деле обязательны — у них есть начальные значения (пустая строка, ноль), и состояние «пользователь ещё не ввёл» выражается значением, а не отсутствием ключа.

Отдельно: `Partial` часто берут не ради формы, а ради «урок ещё не загрузился». Это другая задача — различимые фазы состояния. `Partial` делает невозможную комбинацию (есть `title`, нет `id`) выразимой, вместо того чтобы её запретить; решение — discriminated union, урок 2.5.

**3. Карта заголовков.**

```ts
type ScreenName = 'Lessons' | 'LessonDetails' | 'Progress';
type LessonTitles = Record<ScreenName, string>;
```

Ошибка появится не в месте объявления типа, а в месте объявления **значения**: объект-литерал, присвоенный `LessonTitles`, перестанет ему соответствовать, и компилятор назовёт недостающий ключ. Это и есть цель — список мест для правки выдаёт сборка, а не память.

С прежним `{ [screen: string]: string }` неполный объект компилировался, а `titles['NewScreen']` имел тип `string` при `undefined` в рантайме — заголовок экрана оказывался пустым.

**4. Проверка добавлением поля.**

После добавления `isFree: boolean` в `Lesson`:

- `CreateLessonBody` получает поле автоматически — правка не нужна и это верно: сервер должен принять новое поле;
- `LessonFormState` получает поле автоматически — форма обязана его заполнить, и экран перестанет компилироваться, пока поле не появится в начальном значении. Ошибка полезная;
- `LessonListItem` **не изменится**, потому что `Pick` перечисляет поля явно. Если в карточке списка нужна отметка «бесплатно», правка нужна здесь — одна строка, и её местоположение очевидно.

Итого: одна осознанная правка, остальное выведено. Если правок оказалось больше — значит, где-то остался тип, написанный руками, либо производный тип переопределяет поля модели и связь с ней уже разорвана. Второй случай — сигнал, что производный тип проще объявить явно, чем выводить: вывод имеет смысл, пока он действительно передаёт изменения.

**Чего задание не проверяет.** Ни один из этих типов не гарантирует, что ответ сервера им соответствует. `LessonListItem` описывает, чего код ждёт, а не что пришло. Разрыв закрывается в 2.12.
</details>
