# 2.11 Типизация полиморфного API-слоя — theory

> 🔴 SENIOR. Семь углов разбора. Урок отвечает не на вопрос «как типизировать запрос» — а на вопрос, **кто отвечает за связь между путём, параметрами и ответом, и как убрать человека из этой связи**.

---

## 1. Что это

**Полиморфный API-слой** — слой доступа к данным, в котором одна функция обслуживает все эндпоинты, а типы параметров и ответа вычисляются из описания конкретного эндпоинта.

Начинать нужно с того, что в проектах стоит на этом месте сейчас:

```ts
const lesson = await api.get<LessonDto>('/lessons/1');
```

Эта запись даёт автодополнение и ничего не проверяет. Три утверждения в ней не связаны между собой ничем:

- что по пути `/lessons/1` вообще есть ресурс;
- что он отвечает формой `LessonDto`;
- что метод для него `GET`.

Параметр типа `T` здесь — не вывод, а **аннотация, которую выбрал человек в месте вызова**. Поставьте `CourseDto` вместо `LessonDto`, и компилятор промолчит: он не располагает ничем, с чем мог бы сверить этот выбор. Запись выглядит типизированной и является утверждением ровно того сорта, что `as` в 2.4.

**Описание эндпоинта** — данные, из которых выводятся типы: путь, метод, параметры пути, параметры запроса, тело, тип ответа.

### Ключевая формулировка урока

> **`request<T>(url)` не типобезопасен: `T` не связан ни с путём, ни с ответом и проверен только вниманием автора вызова. Полиморфный слой убирает человека из этой связи — и оставляет ровно одну непроверенную точку: соответствие описания реальному ответу сервера.**

Эту последнюю точку закрывает 2.12. Пока она открыта, слой даёт консистентность, а не гарантию, — и это честная формулировка его ценности.

## 2. Как это работает

### Набор эндпоинтов как одно описание

```ts
type Endpoints = {
  'GET /lessons': {
    query: { courseId: string; limit?: number };
    response: LessonDto[];
  };
  'GET /lessons/:lessonId': {
    params: { lessonId: string };
    response: LessonDto;
  };
  'POST /lessons/:lessonId/progress': {
    params: { lessonId: string };
    body: { percent: number };
    response: ProgressDto;
  };
};
```

Ключ — метод и путь вместе, потому что `GET /lessons/:id` и `DELETE /lessons/:id` — разные эндпоинты с разными ответами. Значение — всё, что об эндпоинте нужно знать слою.

Дальше типы вызова выводятся из этого описания условными типами (2.10):

```ts
type Key = keyof Endpoints;

type Config<K extends Key> =
  (Endpoints[K] extends { params: infer P } ? { params: P } : {}) &
  (Endpoints[K] extends { query: infer Q } ? { query: Q } : {}) &
  (Endpoints[K] extends { body: infer B } ? { body: B } : {});

type Response<K extends Key> = Endpoints[K] extends { response: infer R } ? R : never;

declare function request<K extends Key>(
  key: K,
  config: Config<K>,
): Promise<Response<K>>;
```

Что это меняет на стороне вызова:

```ts
const lessons = await request('GET /lessons', { query: { courseId: '7' } });
// LessonDto[] — выведено, не указано

await request('POST /lessons/:lessonId/progress', {
  params: { lessonId: '1' },
  body: { percent: 60 },
});

await request('GET /lessons/:lessonId', { params: { lesson_id: '1' } });
// ошибка: нет поля lessonId

await request('GET /lesson/:lessonId', { params: { lessonId: '1' } });
// ошибка: такого эндпоинта нет в описании
```

Человек больше не выбирает тип ответа. Он выбирает эндпоинт из конечного списка, и всё остальное вычисляется. Опечатка в пути перестала быть опечаткой в строке и стала ошибкой выбора из union.

### Параметры пути, выведенные из самого пути

Шаблонные литеральные типы (2.7) позволяют не описывать `params` руками, а извлечь их из строки пути:

```ts
type PathParams<S extends string> =
  S extends `${string}:${infer Param}/${infer Rest}`
    ? { [K in Param | keyof PathParams<`/${Rest}`> & string]: string }
    : S extends `${string}:${infer Param}`
      ? { [K in Param]: string }
      : {};

type P1 = PathParams<'GET /lessons/:lessonId'>;
// { lessonId: string }
```

Приём работает и выглядит убедительно. Он же — первый кандидат на вопрос из угла 6: выгода здесь в том, что `params` не нужно дублировать, цена — рекурсивный тип, который в проекте никто, кроме автора, не изменит. Для десятка эндпоинтов явное поле `params` дешевле.

### DTO и доменная модель

**DTO (data transfer object)** — тип, описывающий форму данных на границе: как их отдаёт сервер. **Доменная модель** — тип, которым пользуется приложение.

```ts
type LessonDto = {
  id: string;
  title: string;
  duration_min: number;
  completed_at: string | null;   // ISO-строка
  course: { id: string; title: string };
};

type Lesson = {
  id: string;
  title: string;
  durationMin: number;
  completedAt: Date | null;
  courseId: string;
};
```

Преобразование между ними — одна функция на сущность, живущая в слое API:

```ts
function toLesson(dto: LessonDto): Lesson {
  return {
    id: dto.id,
    title: dto.title,
    durationMin: dto.duration_min,
    completedAt: dto.completed_at === null ? null : new Date(dto.completed_at),
    courseId: dto.course.id,
  };
}
```

Смысл преобразования не в переименовании полей, а в том, **где сосредоточено знание о форме чужих данных**. С преобразованием оно в одной функции: сервер переименовал поле — правка в одной строке, компилятор укажет на неё сам. Без преобразования знание о форме сервера размазано по экранам, редьюсерам и компонентам: переименованное поле даёт ошибки в каждом месте чтения, и каждое приходится править.

Второй эффект того же решения: `Date` вместо ISO-строки, `courseId` вместо вложенного объекта — домен получает ту форму, которая удобна ему, а не ту, которая удобна бэкенду.

### Ошибка как часть результата или как исключение

Два способа, и выбор между ними виден в сигнатуре:

```ts
// исключение
declare function request<K extends Key>(key: K, config: Config<K>): Promise<Response<K>>;

// результат
type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: ApiError };

declare function requestSafe<K extends Key>(key: K, config: Config<K>): Promise<Result<Response<K>>>;
```

Первая сигнатура не сообщает вызывающему, что вызов может не удаться: `try/catch` вокруг него — дисциплина, а не требование компилятора. Вторая делает отказ частью типа (2.5): данные недоступны, пока не разобран `ok`.

Практический компромисс, который чаще всего и применяют: `Result` на границе слоя, исключения внутри него. Внутри слоя исключение удобно — оно проносит отказ через несколько уровней без ручной передачи; на выходе он превращается в значение, чтобы вызывающий не мог его проигнорировать. Классификация ошибок, retry и backoff — предмет 7.3; здесь только форма результата.

## 3. Почему это важно

Типизация в этой точке решает не задачу удобства, а задачу **распределения ответственности**.

С `api.get<LessonDto>(url)` ответственность на каждом вызове: автор обязан знать правильный путь, выбрать правильный DTO и не перепутать метод. Сто вызовов — сто мест, где это знание применяется по памяти. Компилятор при этом молчит во всех ста, потому что проверять ему нечего. Типизация существует, гарантии нет.

С полиморфным слоем ответственность сосредоточена в одном описании. Оно может быть неверным — тогда неверны все вызовы сразу, и это обнаруживается на первом же экране, а не выборочно. Разница ровно та же, что в 2.4 между `as` и предикатом: не в строгости, а в расстоянии между ошибкой и её обнаружением.

Отсюда и уровень урока. Решение здесь принимается при неполных данных: описание эндпоинтов нужно поддерживать синхронно с бэкендом, вывод типов стоит времени компиляции, а порог входа для команды растёт. Правильного ответа «всегда так» не существует — есть граница, за которой слой стоит дороже, чем приносит, и угол 6 о том, как её увидеть.

## 4. Где это в React Native

### Клиент данных

Библиотеки загрузки данных параметризуются ключом запроса и функцией-загрузчиком, и типы связываются через `Awaited<ReturnType<...>>`. Описание эндпоинтов встаёт под них естественно: ключ запроса собирается из ключа эндпоинта и параметров, тип данных выводится из описания. В сообщениях об ошибках после этого появляется `Awaited` — тип, которого в коде проекта нет (2.10).

### Слой загрузки экрана

Экран не вызывает `request` напрямую. Между ними — функция домена: `loadLessonScreen(lessonId)`, которая делает один или несколько запросов, преобразует DTO в домен и возвращает то, что экрану нужно. Типы этой функции описывают контракт экрана, а не контракт сервера, и именно поэтому экран не ломается от переименования поля на бэкенде.

### Мутации

Для мутаций описание полезнее, чем для чтения: у мутации есть тело, и его форма — самое частое место расхождения с бэкендом. Описание `body` в одном месте делает ошибку в составе тела ошибкой компиляции, а не ответом 400 в рантайме, который ещё нужно заметить.

### Многоплатформенные различия ответа

Отдельный случай, встречающийся в RN: один и тот же эндпоинт возвращает поле, которое приложение использует только на одной платформе, либо бэкенд отдаёт разный формат в зависимости от версии клиента. Описание эндпоинта — место, где это фиксируется один раз: поле помечается необязательным, и каждое чтение обязано проверить его наличие. Разложить такое знание по экранам означает получить краш на одной платформе из двух.

## 5. Типичные ошибки

**`request<T>(url)` принимается за типобезопасный вызов.** Самое дорогое заблуждение темы, потому что создаёт ложное чувство покрытия: проект «полностью типизирован», а связь между путём и ответом не проверена ни в одном месте. Причина в том, что параметр типа выглядит как вывод, хотя является аннотацией.

**Доменная модель, равная DTO.** `export type Lesson = LessonDto` или просто использование DTO по всему приложению. Преобразование кажется лишним слоем — ведь поля те же. Цена обнаруживается при первом изменении на бэкенде: знание о чужой форме оказывается в каждом компоненте, и правок столько, сколько мест чтения.

**`any` на границе клиента.** Один `any` в сигнатуре низкоуровневой функции запроса отменяет всю типизацию слоя, построенную над ним: выведенный `Response<K>` присваивается из `any` без проверки (2.4). Проверяется чтением сигнатуры самой нижней функции, а не описания эндпоинтов.

**Типизация, которая держится на дисциплине вызывающего.** Признак: правильность кода зависит от того, что автор вызова что-то помнит — поставить нужный DTO, не забыть `try/catch`, передать правильный метод. Любое такое требование — кандидат на перенос в тип.

**Описание, разошедшееся с бэкендом.** Типы сошлись, ответ имеет другую форму. Это не ошибка типизации, а её граница: описание — утверждение о сервере, и проверяет его только 2.12. Опасность в том, что консистентность слоя создаёт ощущение проверенности.

**Вывод ради вывода.** Рекурсивный разбор пути, вычисление ключей, условные типы на четыре уровня там, где эндпоинтов двенадцать. Экономия — десяток строк описания; плата — тип, который в команде может изменить один человек.

## 6. Trade-offs

### Точность против времени компиляции и читаемости ошибок

Описание из условных типов вычисляется при каждой проверке, и ошибка в месте вызова печатается развёрнутым результатом вычисления (2.6, 2.10). На двадцати эндпоинтах это незаметно, на двухстах — заметно и в CI, и в отзывчивости IDE. Измеряется диагностикой компилятора, а не оценивается на глаз.

### Порог входа для команды

Слой, который пишется один раз и используется всеми, становится частью повседневной работы каждого. Если его типы могут изменить два человека из восьми, то добавление эндпоинта превращается в задачу к этим двум, а остальные начинают обходить слой — вызывать нижнюю функцию напрямую с `as`. Это самый частый способ, которым хорошо типизированный слой умирает.

Практический вывод: сложность слоя ограничена не возможностями системы типов, а тем, сколько человек в команде способны его поддерживать.

### Где граница

Признаки того, что типизация слоя перешла границу:

- добавление эндпоинта требует правки типов, а не только данных описания;
- сообщение об ошибке при неверном вызове не позволяет понять причину без чтения исходников слоя;
- в проекте появились вызовы в обход слоя;
- типы слоя изменяет один человек.

Любой из четырёх — повод упростить, даже если потеряется часть вывода. Вручную описанный тип ответа, который виден в сигнатуре, иногда лучше выведенного, которого никто не может прочитать.

### Описание не заменяет проверку

Главный trade-off урока, и он не про типы. Полиморфный слой даёт консистентность: все вызовы согласованы с одним описанием. Он не даёт соответствия: описание и сервер связаны только намерением. Проект, который считает слой гарантией, падает там же, где падал раньше, — только с большей уверенностью в своей типизации. Закрывается это схемой (2.12), и до тех пор формулировка «типы сошлись» означает «вызовы согласованы между собой».
