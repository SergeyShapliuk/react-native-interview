## Цель

Связать URL, параметры и ответ одним описанием, из которого типы выводятся, а не повторяются.

## Что внутри

Набор эндпоинтов как одно описание: путь, метод, параметры, тело, ответ · вывод типов вызова из описания вместо повторного объявления на каждом обращении · почему `request<Response>(url)` не типобезопасен · параметры пути, извлечённые из самого пути шаблонным типом, и почему это первый кандидат на упрощение · DTO против доменной модели и место преобразования между ними · ошибка как часть типа результата против исключения, о котором типы молчат · где это в RN: клиент данных, слой загрузки экрана, мутации, платформенные различия ответа · ошибки: домен, равный DTO; `any` в нижней функции, отменяющий типизацию всего слоя; типизация, держащаяся на дисциплине вызывающего · trade-offs: время компиляции, читаемость сообщений, порог входа для команды и четыре признака перехода границы.

## Ключевая формулировка урока

**`request<T>(url)` не типобезопасен: `T` не связан ни с путём, ни с ответом и проверен только вниманием автора вызова. Полиморфный слой убирает человека из этой связи — и оставляет ровно одну непроверенную точку: соответствие описания реальному ответу сервера.**

Пока эта точка открыта, слой даёт консистентность, а не гарантию: «типы сошлись» означает «вызовы согласованы между собой». Закрывает её 2.12.

## Границы урока

Здесь только **типы вызова и их источник**. Устройство слоя как механизма — блок 07, его место в архитектуре — блок 08.
