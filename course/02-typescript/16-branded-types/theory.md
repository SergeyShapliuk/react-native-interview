# 2.16 Брендированные типы: номинальность в структурной системе — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как объявить бренд» — а на вопрос, **как сделать одинаковые по форме значения различимыми для компилятора и где их можно создавать, чтобы различие что-то гарантировало**.

Сообщения компилятора в уроке получены `tsc` 5.9 и 7.0 (на этих примерах они совпадают), примеры со схемами — на zod 4 и valibot 1.

---

## 1. Что это

TypeScript сравнивает типы **по структуре**: тип A присваивается в тип B, если у A есть всё, что требует B. Имя типа в этом сравнении не участвует. Поэтому

```ts
type LessonId = string;
type CourseId = string;

declare function loadLesson(id: LessonId): Promise<Lesson>;
declare const courseId: CourseId;

loadLesson(courseId);   // компилируется
```

компилируется: `LessonId` и `CourseId` — два имени одного типа `string`. Псевдоним документирует намерение, но компилятор его не проверяет.

**Брендированный тип** (branded type) добавляет к базовому типу метку, которой у значения в рантайме нет, но которую компилятор учитывает при сравнении:

```ts
declare const brand: unique symbol;
export type Brand<T, B extends string> = T & { readonly [brand]: B };

export type LessonId = Brand<string, 'LessonId'>;
export type CourseId = Brand<string, 'CourseId'>;
export type DurationMs = Brand<number, 'DurationMs'>;
```

```ts
loadLesson(courseId);
// Argument of type 'CourseId' is not assignable to parameter of type 'LessonId'.
//   Type 'CourseId' is not assignable to type '{ readonly [brand]: "LessonId"; }'.
//     Types of property '[brand]' are incompatible.
//       Type '"CourseId"' is not assignable to type '"LessonId"'.

loadLesson('l_42');
// Argument of type 'string' is not assignable to parameter of type 'LessonId'.
```

Это и есть номинальность в структурной системе: два типа с одной формой перестают быть взаимозаменяемыми, потому что у них разные метки.

### Ключевая формулировка урока

> **Бренд — это не проверка, а квитанция о проверке. Он существует только для компилятора и гарантирует ровно то, что гарантирует единственное место, где его выдают.**

---

## 2. Как это работает

### Пересечение с несуществующим свойством

`string & { readonly [brand]: 'LessonId' }` — строка, у которой якобы есть свойство с ключом `brand`. Такой строки в природе не бывает, и это не важно: компилятору достаточно, что тип **требует** это свойство. Отсюда три правила присваивания:

- `LessonId` → `string` — можно: пересечение является подтипом каждой своей части;
- `string` → `LessonId` — нельзя: у обычной строки нет свойства-метки;
- `CourseId` → `LessonId` — нельзя: метка есть, но значения `'CourseId'` и `'LessonId'` не совпадают.

Первое правило делает бренды дешёвыми в использовании: `LessonId` передаётся во всё, что ждёт `string`, — в шаблонную строку URL, в `keyExtractor`, в `Text`. Второе и третье — то, ради чего бренд вводится.

### Почему `unique symbol`, а не строковое поле

Часто бренд пишут проще: `string & { __brand: 'LessonId' }`. У такой записи две проблемы.

Первая — поле видно. Автодополнение предлагает `id.__brand`, и обращение компилируется, хотя в рантайме это `undefined`.

Вторая — совпадение меток. Если два модуля независимо объявили `string & { __brand: 'LessonId' }`, это **один и тот же тип**: структура совпала, и компилятор их не различает. С `unique symbol` метка привязана к конкретному объявлению символа: пока `Brand` объявлен в одном модуле и используется всеми, метки различаются только значениями, а символ из чужого модуля дал бы несовместимый тип.

`declare const brand: unique symbol` не порождает кода: Babel стирает объявление целиком (2.15). Символа в рантайме нет, как и свойства.

### Что бренд разрешает и что теряется

Методы базового типа доступны, но результат — уже базовый тип:

```ts
declare const lessonId: LessonId;
lessonId.length;              // number — работает
const up = lessonId.toUpperCase();   // string, бренд потерян
loadLesson(up);               // ошибка: string не LessonId
```

Это правильно: компилятор не знает, остаётся ли преобразованная строка корректным идентификатором.

Арифметика над брендированными числами даёт `number`:

```ts
declare const a: DurationMs, b: DurationMs;
const sum = a + b;                 // number
const total: DurationMs = sum;     // ошибка
```

Сумма двух длительностей — длительность, но разность длительности и позиции — может быть и отрицательной, а произведение двух длительностей — вообще не длительность. Компилятор не различает эти случаи и снимает бренд всегда; вернуть его можно только через функцию, которая это решение принимает явно.

Сравнение значений разных брендов — ошибка:

```ts
declare const courseId: CourseId;
lessonId === courseId;
// This comparison appears to be unintentional because the types
// 'LessonId' and 'CourseId' have no overlap.
```

Бренд ловит не только передачу не того аргумента, но и сравнение несравнимого — например, `lessons.find((l) => l.id === route.params.courseId)`.

Коллекции сохраняют различие: `Map<LessonId, Lesson>` не примет `CourseId` в `get`. А `Object.keys` у `Record<LessonId, Lesson>` возвращает `string[]` — ключи объекта в рантайме просто строки, и бренд теряется. Это одна из причин предпочитать `Map` для словарей по идентификатору, когда ключи нужно перебирать.

### Где бренд создаётся

Раз `string` в `LessonId` не присваивается, получить брендированное значение можно только утверждением `as`. Вопрос не в том, использовать ли `as`, а в том, **где**. Правильный ответ: в одном месте, которое перед утверждением проверяет значение.

Функция-конструктор:

```ts
// domain/ids.ts — единственный модуль, где пишется `as LessonId`
export function parseLessonId(raw: unknown): LessonId | null {
  return typeof raw === 'string' && /^l_[a-z0-9]+$/.test(raw) ? (raw as LessonId) : null;
}
```

То же в форме assertion function (2.4), если отсутствие значения — ошибка, а не ветка:

```ts
export function assertLessonId(raw: unknown): asserts raw is LessonId {
  if (parseLessonId(raw) === null) throw new InvalidId('LessonId', raw);
}
```

Схема (2.12) — тот же конструктор, у которого `as` спрятан в библиотеке:

```ts
// zod 4
export const LessonId = z.string().regex(/^l_[a-z0-9]+$/).brand<'LessonId'>();
export type LessonId = z.infer<typeof LessonId>;    // string & z.$brand<'LessonId'>

// valibot
export const LessonId = v.pipe(v.string(), v.regex(/^l_[a-z0-9]+$/), v.brand('LessonId'));
export type LessonId = v.InferOutput<typeof LessonId>;
```

Брендированное значение здесь получается только из `parse` или успешного `safeParse`. Схема-бренд встраивается в схему ответа как поле: `object({ id: LessonId, … })` — и тип объекта, выведенный из схемы, уже содержит `LessonId` (2.12).

Одна оговорка: бренд zod, бренд valibot и собственный `Brand` — три разные системы меток, и между собой они несовместимы (`string & $brand<'LessonId'>` не присваивается в собственный `LessonId`). В проекте выбирается одна.

### Бренд в рантайме

Его нет. Вот что остаётся от конструктора после сборки:

```ts
export const asLessonId = (s: string) => s as LessonId;
```

```js
var asLessonId = s => s;
```

Отсюда три следствия:

- **JSON.** `JSON.stringify` пишет обычную строку, `JSON.parse` возвращает обычную строку — и тип `any`, с которым бренд «появляется» без всякой проверки, если результат присвоить в брендированный тип.
- **Хранилище.** Значение, записанное с брендом и прочитанное обратно, — снова строка неизвестного происхождения. Тип записи в коде может обещать `LessonId`, но гарантию даёт только повторный разбор при чтении — та же граница, что и в 2.13.
- **Нативная граница.** Нативный модуль получает и возвращает обычные строки и числа. Колбэк плеера с позицией в секундах не знает о `DurationMs`.

## 3. Почему это важно

Есть класс ошибок, который не ловит ни один другой механизм TypeScript: **перепутанные значения одной формы**. Идентификатор курса вместо идентификатора урока, секунды вместо миллисекунд, рубли вместо копеек. Для компилятора это всё `string` и `number`, для ревьюера — правдоподобные имена в правдоподобных местах, для тестов — значения, которые часто совпадают с правильными в фикстурах (`'1'` и `'1'`).

Проявляются они поздно и далеко от причины: запрос с чужим идентификатором возвращает 404 или, хуже, чужой ресурс; таймер срабатывает в тысячу раз позже; сумма отличается в сто раз. Бренд переносит обнаружение в место смешения — туда, где `CourseId` передан вместо `LessonId`.

Второй эффект менее заметен, но не менее важен. Параметр типа `LessonId` — это **документированное требование**: функция ждёт значение, прошедшее проверку. Ей не нужно проверять его снова, и читателю не нужно гадать, проверено ли оно. Цепочка «проверили на границе → дальше работаем с проверенным» из 2.12 получает выражение в типе, которое не теряется при передаче значения через пять функций.

## 4. Где это в React Native

### Идентификаторы из навигации, deep link и push

Экран урока получает `lessonId` из трёх источников: из списка уроков, по deep link и из push-уведомления. Все три приходят строками. С брендом в `ParamList`

```ts
type RootParamList = {
  Course: { courseId: CourseId };
  Lesson: { lessonId: LessonId; courseId: CourseId };
};
```

переход из списка компилируется без изменений — `lesson.id` уже `LessonId`, потому что получен разбором ответа сервера. А переход из обработчика ссылки или уведомления требует пропустить строку через конструктор: `navigate('Lesson', { lessonId: url.split('/').pop() })` не компилируется. Ветка «идентификатор не прошёл разбор» появляется в коде принудительно.

Оговорка, которая следует из 2.13: бренд в `ParamList` — утверждение о том, что пришло в параметры. Для переходов внутри кода его проверяет компилятор. Для восстановленного состояния навигации не проверяет никто — библиотека навигации типов в рантайме не знает. Механика параметров и deep linking — 4.16.

### Ключи хранилища

Ключи `AsyncStorage` или MMKV, собранные строками по месту (`'progress:' + id`), расходятся опечатками и форматами. Тип `StorageKey` с брендом и функции, которые единственные его строят (`progressKey(lessonId)`), сводят все ключи в один модуль; хранилище принимает только `StorageKey`.

### Единицы измерения

- **Время.** Плеер сообщает позицию в секундах, `setTimeout` и большинство API JS ждут миллисекунды, сервер хранит длительность урока в минутах. `DurationMs` и функции `secondsToMs`, `minutesToMs` превращают перевод единиц в обязательный и видимый шаг.
- **Деньги.** Копейки против рублей (1.25): сумма из ответа сервера в минимальных единицах и значение для показа — разные типы.
- **Размеры.** Layout в RN работает в независимых от плотности единицах (dp), а `PixelRatio` и размеры изображений оперируют физическими пикселями. Смешение даёт картинки в два-три раза больше или меньше на разных устройствах.

### Нормализованный стейт

Словари сущностей по идентификатору — `Record<LessonId, Lesson>` или `Map<LessonId, Lesson>` — получают проверку на уровне ключа: в словарь уроков нельзя положить запись по `CourseId`. Нормализация как подход — 6.8.

## 5. Типичные ошибки

**`as LessonId` в любом месте кода.** В компоненте, в обработчике ссылки, в утилите — «тут точно урок». Каждое такое место выдаёт квитанцию без проверки, и бренд перестаёт гарантировать что-либо: значение типа `LessonId` может оказаться чем угодно. Правило — `as` к бренду пишется только в модуле конструкторов; его легко найти поиском и запретить правилом линтера для остальных файлов.

**Бренд вместо проверки.** `const toLessonId = (s: string) => s as LessonId` — конструктор, который ничего не проверяет. Он удобен, компилятор доволен, и это то же самое, что `as` по месту, только с именем. Конструктор оправдан, когда он отвечает на вопрос «это действительно идентификатор урока»: формат, префикс, непустота.

**Ожидание, что бренд переживёт JSON, хранилище или нативную границу.** `const saved: Lesson = JSON.parse(raw)` компилируется, потому что `JSON.parse` возвращает `any`, — и бренды в `saved` появились без всякой проверки. После любого выхода за пределы кодовой базы значение разбирается заново.

**Брендировать всё подряд.** `Title`, `Description`, `Email` для каждой строки домена — шум, за который платят конструкторами и конвертациями. Бренд окупается там, где значения одной формы встречаются вместе и перепутать их дорого: идентификаторы разных сущностей, которые передаются рядом, и единицы в арифметике и во времени.

**Смешивать системы брендов.** Схема с `.brand()` из zod и собственный `Brand` дают несовместимые типы с одинаковыми именами в сообщениях. Половина кода начинает конвертировать одно в другое через `as`, и это возвращает первую ошибку.

**Строковое поле-метку с одинаковым именем в двух модулях.** Два независимых `{ __brand: 'Id' }` — один тип; различие, на которое рассчитывали, не существует.

## 6. Trade-offs

### Цена бренда

Бренд ничего не стоит в рантайме, но стоит в коде:

- **конструктор или схема на каждой границе**, откуда приходит значение: ответ сервера, ссылка, уведомление, хранилище. Для сервера это почти бесплатно, если схема уже есть (2.12): бренд — одно поле в ней;
- **фабрики в тестах.** Тестовые данные тоже должны получать бренды — через те же конструкторы или фабрику в одном тестовом модуле, а не через `as` в каждом тесте;
- **трение с библиотеками.** Использовать брендированное значение там, где ждут `string`, можно всегда. Трудности появляются, когда библиотека **возвращает** обычную строку, а дальше нужен бренд: ключ из `onViewableItemsChanged`, параметр из конфигурации linking, значение из `onChangeText`. Каждое такое место — граница, где нужен разбор.

Основная цена — в местах создания, а не использования. Поэтому бренд дёшев в проекте, где значения создаются в немногих местах, и дорог там, где идентификаторы собираются из строк по всему коду, — но во втором случае он как раз и показывает проблему.

### Бренд против объекта-обёртки

Альтернатива — класс или объект `{ value: string }`. Он даёт настоящую номинальность в рантайме (`instanceof`), но платит за неё: объект не переходит нативную границу и JSON без преобразования (1.2), два одинаковых идентификатора — разные ссылки, и сравнение через `===` и зависимости хуков ломается (1.12). Бренд сохраняет примитив и все его свойства, отказываясь только от проверки в рантайме — которую на границе всё равно делает схема.

### Бренд против строкового `enum`

Номинальность строкового `enum` (нельзя передать `'lessons'` вместо `Tab.Lessons`) достигается ценой рантайм-кода и всех проблем `enum` в Babel-сборке (2.15). Для закрытого набора значений лучше union литералов; бренд — для открытого множества значений одной формы, вроде идентификаторов.

### Где остановиться

Рабочая граница: брендируются **идентификаторы сущностей**, которые встречаются вместе в сигнатурах, и **единицы**, которые участвуют в арифметике и в API времени. Остальные строки домена остаются строками до первого инцидента, в котором их перепутали.
