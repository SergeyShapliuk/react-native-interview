# 2.2 Generics — practice

## Проверка понимания

Цель — не оценка, а обнаружение пробела. У каждого вопроса указано, что вскрывает неверный ответ.

---

**1. Чем `function f<T>(x: T): T` отличается для вызывающего от `function f(x: unknown): unknown`?**

<details>
<summary>Ответ</summary>

Разница в том, что известно о результате. В первом случае тип результата равен типу аргумента: `f(1)` даёт `number`, `f(lesson)` даёт `Lesson`. Во втором результат — `unknown` при любом аргументе, и перед использованием его нужно сузить. Параметр типа связывает два места сигнатуры; `unknown` не связывает ничего — информация об аргументе до результата не доходит.

**Неверный ответ «разницы нет, оба принимают что угодно»** вскрывает чтение сигнатуры только по параметрам. Принимают они действительно одно и то же — различие целиком в возвращаемом типе, и именно он определяет, сколько кода придётся написать на вызывающей стороне.

**Ответ «generic безопаснее»** вскрывает отсутствие критерия: безопаснее в чём и за счёт чего. Если `T` стоит только в возвращаемом типе — как в `parse<T>(raw: string): T` — то `unknown` как раз строже, потому что требует сужения, а `T` его не требует.
</details>

---

**2. Что именно проверит `getItem<Lesson>('current-lesson')` в рантайме?**

```ts
async function getItem<T>(key: string): Promise<T | null> {
  const raw = await AsyncStorage.getItem(key);
  return raw ? (JSON.parse(raw) as T) : null;
}
```

<details>
<summary>Ответ</summary>

Ничего. В рантайме выполняются три действия: чтение строки по ключу, проверка на пустоту, `JSON.parse`. Параметр типа стёрт при компиляции, `as T` не производит инструкций. Если в хранилище лежит строка `"{}"`, функция вернёт `{}` с типом `Lesson`, и обращение к `lesson.title` даст `undefined`, а не ошибку. Проверяется единственное — что строка является корректным JSON; иначе `JSON.parse` бросит исключение, и к `Lesson` оно отношения не имеет.

**Неверный ответ «проверит, что объект соответствует `Lesson`»** вскрывает модель, в которой типы существуют в рантайме. Практическая цена: при расхождении формата данных (запись от прошлой версии приложения, изменившееся поле на сервере) ошибку будут искать на экране, обратившемся к отсутствующему полю, а не в месте чтения.

**Ответ «проверит, пока данные писали через ту же обёртку»** вскрывает подмену гарантии соглашением. Соглашение не проверяется компилятором и ломается при миграции формата, при ручной записи, при чтении ключа из другого места.
</details>

---

**3. По какому признаку видно, что параметр типа в сигнатуре лишний, и чем его следует заменить?**

<details>
<summary>Ответ</summary>

Признак — параметр типа встречается в сигнатуре один раз, то есть не связывает два места. Два случая и две замены:

- `T` только в параметре: `function logEvent<T>(payload: T): void` → `payload: unknown`. Эффект тот же, конструкций меньше;
- `T` только в возвращаемом типе: `function parse<T>(raw: string): T` → честнее объявить `unknown` и оставить сужение вызывающему. Такая сигнатура — приведение типа, оформленное как параметризация: значение `T` назначает вызывающий, и никто его не проверяет.

**Неверный ответ «лишний, если вызывается с одним типом»** вскрывает подсчёт вызовов вместо чтения сигнатуры. Количество вызовов — характеристика текущего кода; `pluck<T, K extends keyof T>` осмыслен и при единственном вызове, потому что связывает аргументы с типом результата.

**Ответ «лишний, если можно обойтись `any`»** вскрывает смешение двух разных решений: убрать параметр типа и отключить проверки. `unknown` сохраняет требование сузить тип, `any` снимает его — и снимает заодно у всего вызывающего кода.
</details>

**4. Почему `item[key]` компилируется в первом варианте и не компилируется во втором?**

```ts
function pluck<T, K extends keyof T>(items: T[], key: K) {
  return items.map((item) => item[key]);
}

function pluckLoose<T, K extends string>(items: T[], key: K) {
  return items.map((item) => item[key]);
}
```

<details>
<summary>Ответ</summary>

В первом варианте ограничение `K extends keyof T` сообщает компилятору, что `key` — одно из имён полей `T`, поэтому обращение допустимо, а его тип равен `T[K]`. Во втором `K` — произвольная строка, такого поля у `T` может не быть, и компилятор отказывается выводить тип обращения. Ограничение работает не как фильтр аргументов, а как источник информации внутри тела функции.

**Неверный ответ «во втором нужно добавить приведение типа»** вскрывает привычку закрывать сообщение компилятора вместо чтения его причины. Приведение уберёт ошибку и вместе с ней проверку: `pluckLoose(lessons, 'titel')` после него скомпилируется.

**Ответ «потому что `keyof` строже, чем `string`»** верен по факту и не отвечает на вопрос: нужно назвать, что становится известно о `key` и какой тип получает `item[key]`.
</details>

**5. Что получит `T` в каждой строке и где параметр придётся указать явно?**

```ts
function toSet<T>(items: T[]): Set<T> { return new Set(items); }

const a = toSet([1, 2, 3]);
const b = toSet([]);
const c = toSet(['draft', 'published']);
```

<details>
<summary>Ответ</summary>

- `a` — `T = number`, `Set<number>`;
- `b` — выводить не из чего, `T = never`. Добавить в такой `Set` ничего нельзя, и ошибка проявится на первом `b.add(...)`, а не на строке объявления;
- `c` — `T = string`: литералы в массиве расширяются. Если нужен `Set<'draft' | 'published'>`, параметр указывается явно.

Явное указание нужно в двух строках из трёх и по разным причинам: в `b` нет источника вывода, в `c` вывод шире нужного.

**Неверный ответ «`b` получит `any[]`»** вскрывает отсутствие модели вывода из пустого массива: `never[]` при `strict` ведёт себя иначе, чем `any[]`, и ошибка возникает не при чтении, а при записи.

**Ответ «в `c` всё верно, там и так строки»** вскрывает потерю литеральных типов как незамеченное событие. В RN-коде это тот же случай, что со статусом экрана или именем маршрута: `string` подходит куда угодно, и опечатка проходит проверку.
</details>

## Задание

**Дано.** RN Academy, стадия [P2](../../project/): домен типизирован, уроки и прогресс описаны типами. В проекте есть обёртка над `AsyncStorage` и два хелпера домена, написанные без параметров типа.

```ts
type LessonStatus = 'locked' | 'available' | 'done';

type Lesson = {
  id: string;
  courseId: string;
  title: string;
  duration: number;
  status: LessonStatus;
};

// хранилище
async function getStored(key: string): Promise<any> {
  const raw = await AsyncStorage.getItem(key);
  return raw ? JSON.parse(raw) : null;
}

// домен
function findById(items: any[], id: string): any {
  return items.find((item) => item.id === id);
}

function groupByStatus(lessons: Lesson[]): Record<string, Lesson[]> {
  return lessons.reduce((acc, lesson) => {
    acc[lesson.status] = [...(acc[lesson.status] ?? []), lesson];
    return acc;
  }, {} as Record<string, Lesson[]>);
}
```

**Требуется.**

1. Переписать `findById` и `groupByStatus` через параметры типа так, чтобы тип элемента сохранялся на выходе, а имя поля для группировки задавалось аргументом и проверялось компилятором. Ограничения выбрать минимально достаточные — не `T extends Lesson`, если хелпер не обязан знать про `Lesson`.
2. Привести вызов, который до правки компилировался, а после — нет, и назвать, какую ошибку в коде он содержал.
3. Типизировать `getStored` параметром типа и **отметить в коде комментарием точное место**, где тип перестаёт быть гарантией и становится обещанием. Решение этой проблемы не писать — оно в 2.12.
4. Для каждого из трёх хелперов ответить: связывает ли его параметр типа два места сигнатуры, или встречается один раз. Там, где один раз, сказать, что это означает для вызывающего.

---

<details>
<summary>Разбор</summary>

**1. Хелперы домена.**

```ts
function findById<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}

function groupBy<T, K extends keyof T>(items: T[], key: K): Map<T[K], T[]> {
  const out = new Map<T[K], T[]>();
  for (const item of items) {
    out.set(item[key], [...(out.get(item[key]) ?? []), item]);
  }
  return out;
}
```

Что изменилось по сравнению с исходным кодом:

- `findById` возвращает `T | undefined`, а не `any`. Исходная сигнатура теряла тип дважды — на входе (`any[]`) и на выходе. Ограничение `T extends { id: string }` минимально достаточное: хелпер требует только поля `id` и работает с курсом, уроком, записью прогресса. `T extends Lesson` сделало бы его непригодным для остальных сущностей, ничего не дав взамен;
- `| undefined` в возвращаемом типе — не придирка: `find` возвращает `undefined`, когда ничего не нашёл, и `any` это скрывал. При `strict` вызывающий обязан обработать отсутствие;
- `groupBy` параметризован и по типу элемента, и по ключу. `K extends keyof T` даёт проверку имени поля на вызове и допустимость `item[key]` внутри тела. Исходный `groupByStatus` был прибит к `Lesson` и к одному полю;
- `Record<string, Lesson[]>` заменён на `Map<T[K], T[]>`. `Record<string, ...>` утверждал, что ключом может быть любая строка, и обращение по опечатке компилировалось, возвращая `undefined` под типом `Lesson[]`. `T[K]` — точный тип значения поля, для `'status'` это `LessonStatus`.

Вызов остаётся без явных параметров типа, оба выводятся:

```ts
const lesson = findById(lessons, id);        // Lesson | undefined
const byStatus = groupBy(lessons, 'status'); // Map<LessonStatus, Lesson[]>
```

**2. Вызов, который перестал компилироваться.**

```ts
groupBy(lessons, 'statuz'); // ошибка: 'statuz' не является keyof Lesson
byStatus.get('Done');       // ошибка: 'Done' не входит в LessonStatus
```

До правки `Record<string, Lesson[]>` принимал любую строку, и `byStatus['Done']` возвращал `undefined` с типом `Lesson[]`. Ошибка в коде — опечатка в литерале статуса; наблюдалась она как пустой раздел на экране, и компилятор в её обнаружении не участвовал.

Второй пример — из `findById`: `render(findById(lessons, id).title)` теперь не компилируется, потому что результат может быть `undefined`. До правки `any` позволял это собрать, и экран падал на уроке, которого нет в загруженном списке.

**3. Хранилище.**

```ts
async function getStored<T>(key: string): Promise<T | null> {
  const raw = await AsyncStorage.getItem(key);
  if (!raw) return null;
  // ↓ здесь тип перестаёт быть гарантией: T назначил вызывающий,
  //   JSON.parse вернёт то, что лежало в хранилище, сверки нет
  return JSON.parse(raw) as T;
}
```

Переход с `Promise<any>` на `Promise<T | null>` — улучшение: `any` расползался на весь вызывающий код, `T | null` требует хотя бы обработать `null`. Но `T` здесь встречается только в возвращаемом типе, и `as T` — то же приведение, что и `any`, просто локализованное в одной строке. Что выиграно: место, где проверка отсутствует, стало одним и известным. Это условие для 2.12 — заменить `as T` на разбор по схеме, из которой выводится и тип, и рантайм-проверка.

**4. Связывает ли параметр типа два места.**

| Хелпер | `T` в параметрах | `T` в результате | Вывод |
|---|---|---|---|
| `findById` | да (`items: T[]`) | да (`T \| undefined`) | связывает; параметр типа осмыслен |
| `groupBy` | да (`items`, `key`) | да (`Map<T[K], T[]>`) | связывает; `K` дополнительно связан с `T` ограничением |
| `getStored` | нет | да (`Promise<T \| null>`) | встречается один раз |

Для вызывающего `getStored<Lesson>('current')` это означает: компилятор поверил указанному типу и не проверил его. Отсюда рабочий критерий для всего домена P2 — найти функции, где параметр типа стоит только в возвращаемом типе. Это полный список мест, где типы домена ничем не подкреплены.
</details>
