# 2.9 `.d.ts`, module augmentation и нетипизированные библиотеки — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как написать `.d.ts`» — а на вопрос, **сколько доверия заслуживает чужой тип и что делать, когда его нет или он неверен**.

---

## 1. Что это

**Declaration file (файл объявлений), `.d.ts`** — файл, содержащий только объявления типов, без исполняемого кода. Компилятор читает его как описание того, что существует в рантайме, и проверить это описание не может.

```ts
// api.d.ts
export declare function track(event: string, payload?: object): void;
```

**`declare`** — ключевое слово, означающее «эта сущность существует, её реализация находится не здесь». Отсюда главное свойство файла объявлений: **в бандл он не попадает**. После компиляции от него не остаётся ни строки, потому что компилировать нечего.

**Module augmentation (дополнение модуля)** — добавление объявлений в существующий модуль, своего или чужого. Опирается на declaration merging (2.6): дополняется `interface`, объявленный внутри этого модуля.

**Ambient declaration (внешнее объявление)** — объявление для модуля, у которого типов нет вовсе: `declare module 'untyped-lib'`.

### Ключевая формулировка урока

> **`.d.ts` — это утверждение о рантайме, которое никто не проверяет. Неверный тип опаснее отсутствующего: отсутствующий заставляет посмотреть в исходники, неверный позволяет написать вызов, который компилируется и падает.**

## 2. Как это работает

### Как компилятор находит типы

Порядок, в котором TypeScript ищет типы для `import x from 'lib'`:

1. **поле `types` или `typings` в `package.json`** библиотеки — путь к её собственному `.d.ts`. Современные пакеты поставляют типы с собой;
2. **`index.d.ts` рядом с точкой входа** — если поле не указано;
3. **`node_modules/@types/lib`** — типы, написанные сообществом отдельно от библиотеки;
4. **`typeRoots` и `paths` из `tsconfig.json`** — если проект настраивает поиск вручную;
5. **локальные `.d.ts` проекта**, попадающие в `include` — для внешних объявлений.

Из этого списка следуют два практических вывода. Первый: типы и реализация — **разные артефакты**, и у них разные версии. Пакет обновился мажорно, `@types/*` для него не обновился — компилятор проверяет вызовы по описанию, которого в рантайме больше нет. Второй: собственный `.d.ts` проекта способен переопределить ситуацию только добавлением, а не заменой — удалить чужое объявление нельзя.

### `declare module` для библиотеки без типов

Импорт пакета без типов даёт ошибку «Could not find a declaration file for module». Вариантов три, и они различаются не удобством, а тем, что известно о модуле:

```ts
// types/untyped.d.ts

// 1. Заглушка целиком: тип модуля — any
declare module 'rn-fancy-widget';

// 2. Явная заглушка: перечислены используемые функции
declare module 'rn-fancy-widget' {
  export function measure(tag: number): Promise<{ width: number; height: number }>;
  export function reset(): void;
}
```

Первый вариант делает весь модуль `any`: компилируется любое обращение. Второй описывает то, что проект действительно вызывает, и даёт проверку на этом подмножестве.

Второй лучше, и причина не в полноте, а в **области действия ошибки**. При заглушке-`any` ошибка расползается: значение, пришедшее из модуля, присваивается куда угодно и обнаруживается далеко от места использования (2.4). При явной заглушке неизвестное остаётся за пределами описанного: вызов неописанной функции не компилируется, и это сигнал дописать объявление, а не молчание.

Важно, чего явная заглушка не делает: она не проверяет, что библиотека действительно так устроена. Описание берётся из исходников или документации, и ошибка в нём — ровно тот неверный тип, о котором предупреждает ключевая формулировка.

### Module augmentation: дополнение, а не замена

```ts
// theme.d.ts
import type { AppTheme } from './src/theme';

declare module 'styled-components/native' {
  export interface DefaultTheme extends AppTheme {}
}
```

Библиотека экспортирует `DefaultTheme` как `interface` специально для этого: приложение добавляет свои токены, и `theme.colors.accent` оказывается типизированным внутри каждого компонента.

Три требования, нарушение каждого даёт молчаливую неудачу:

- **имя модуля совпадает в точности** с тем, что указано в `import`. Опечатка не даёт ошибки — она создаёт **новый** внешний модуль с этим именем, и дополнение уходит в пустоту;
- **дополняется `interface`**. Если библиотека объявила тип как `type`, дополнить его нельзя (2.6), и единственный выход — параллельный тип с кастом на границе;
- **файл с дополнением должен быть модулем или находиться внутри `declare module`**. Файл без единого `import` и `export` компилятор считает скриптом, и `declare module` в нём означает внешнее объявление, а не дополнение — то есть ровно противоположное.

Последнее требование — источник самого частого «augmentation не работает»: файл выглядит правильно, типы не появляются, причина в отсутствии `export` в файле.

### Глобальное пространство имён как отдельный случай

Не всякое расширение чужих типов — дополнение модуля. Библиотека вправе объявить точку расширения в **глобальном пространстве имён**, и тогда дополнять нужно его, а не модуль. Так устроена типизация навигации — пример ниже относится к React Navigation 6 и 7 с динамическим API, где список экранов описывается вручную:

```ts
// navigation.d.ts
import type { RootStackParamList } from './src/navigation/types';

declare global {
  namespace ReactNavigation {
    interface RootParamList extends RootStackParamList {}
  }
}
```

Приложение описывает список своих экранов обычным типом, а дополнением объявляет, что именно этот список библиотека должна считать списком экранов по умолчанию. После этого `navigate('Lesson', { lessonId })` проверяется по экранам приложения, а не по `string`.

Механизм тот же — declaration merging, — но **место другое**, и попытка дополнить вместо него модуль библиотеки даёт типичную молчаливую неудачу: файл компилируется, типы навигации не меняются.

> **Пример привязан к версии и к API — это часть материала, а не оговорка.** Дополнение `ReactNavigation.RootParamList` — механизм, общий для шестой и седьмой версий библиотеки. Различается то, **откуда берётся список экранов**: в динамическом API он пишется руками, как в примере выше; в статическом API седьмой версии он выводится из конфигурации навигатора утилитой библиотеки, и вручную описывать его не нужно. Поэтому код, скопированный из статьи без указания версии, может не сработать или сделать не то — точные имена типов и форму записи нужно смотреть в документации **своей** версии.
>
> Это общее свойство темы, а не особенность навигации: `.d.ts` чужой библиотеки — утверждение о конкретной её версии, и дополнение к нему тоже привязано к версии.

Отсюда практическое правило: прежде чем писать дополнение, нужно посмотреть, **где объявлена точка расширения** — в экспортируемом `interface` модуля или в глобальном namespace — и **для какой версии** библиотеки верно то, что вы нашли. Проверяется это чтением `.d.ts` установленной версии, и никакая общая форма записи этого вопроса не заменяет.

### `declare global`

Добавляет объявления в глобальную область. Оправдан там, где сущность действительно глобальна в рантайме:

```ts
// test-env.d.ts
import type { NativeModules } from 'react-native';

declare global {
  // eslint-disable-next-line no-var
  var __TEST_NATIVE_MOCKS__: Partial<typeof NativeModules>;

  namespace NodeJS {
    interface ProcessEnv {
      API_URL: string;
      SENTRY_DSN?: string;
    }
  }
}
```

Два законных случая в RN-проекте: переменные окружения и то, что тестовая среда или нативный слой кладут в глобальный объект. Во всех остальных `declare global` — способ не передавать зависимость явно, и цена этого — сущность, доступная из любого файла и не видимая в его импортах.

Отдельная ловушка `ProcessEnv`: объявление `API_URL: string` утверждает, что ключ есть всегда. В рантайме его подставляет сборка, и при неверной конфигурации окружения значением будет `undefined` при типе `string`. Честнее `API_URL?: string` плюс проверка на старте — тип описывает, что переменная может отсутствовать, а проверка превращает отсутствие в явный отказ.

### Типизация импорта ресурсов

Metro умеет импортировать то, что модулем JavaScript не является: изображения, svg, шрифты. Компилятор об этом не знает, и импорт не проходит проверку. Объявление даёт ему тип:

```ts
// assets.d.ts
declare module '*.png' {
  const content: number;   // в RN require к изображению даёт числовой идентификатор ресурса
  export default content;
}

declare module '*.svg' {
  import type { SvgProps } from 'react-native-svg';
  const content: React.FC<SvgProps>;
  export default content;
}
```

Тип здесь описывает поведение **сборщика**, а не библиотеки: `.svg` становится компонентом потому, что так настроен трансформер, и при смене трансформера объявление придётся менять. Это место стоит пометить комментарием: иначе через год непонятно, почему картинка — число.

### `@ts-expect-error` вместо `@ts-ignore`

Оба подавляют ошибку на следующей строке. Разница в том, что происходит, когда ошибка исчезает:

- `@ts-ignore` — ничего. Комментарий остаётся в коде навсегда и продолжает подавлять уже не существующую ошибку, а заодно и любую новую, которая появится на этой строке;
- `@ts-expect-error` — **сам становится ошибкой**: «Unused '@ts-expect-error' directive». То есть после обновления библиотеки компилятор перечислит все места, где обход больше не нужен.

Для подавления, связанного с чужими типами, это решающее свойство: обход живёт ровно до исправления библиотеки, и срок его жизни контролирует компилятор, а не память разработчика.

## 3. Почему это важно

Приложение на React Native состоит из своего кода и нескольких десятков зависимостей, часть из которых обращается к нативному слою. Типы этих зависимостей — не часть системы типов приложения, а **утверждения третьих лиц о рантайме**, и степень их достоверности различается:

- типы, поставляемые библиотекой вместе с кодом, обычно соответствуют версии — но описывают то, что автор считает публичным API, и часто расходятся с реальностью на платформенных различиях;
- типы из `@types/*` живут отдельной жизнью и отстают, иногда на мажорную версию;
- типов нет вовсе — и это честное состояние: оно заставляет открыть исходники.

Урок важен не потому, что `.d.ts` сложно написать, а потому, что здесь принимается решение о доверии. Приложение, где `strict: true` и ни одного `any` в своём коде, остаётся непроверенным ровно в тех местах, где доверилось чужому описанию. И обнаруживается это так же, как в 2.4: крашем вдалеке от причины.

## 4. Где это в React Native

### `ParamList` навигации

Главный пример augmentation в RN-проекте и самый полезный: после дополнения `navigate('Lesson', { lessonId })` проверяется по списку экранов приложения, а опечатка в имени экрана или в составе параметров перестаёт компилироваться. Без дополнения имя экрана — `string`, а параметры — `object`, и типизация навигации существует только на бумаге.

Механика навигации, вложенные навигаторы и deep linking — блок 04, урок 4.16. Здесь важно другое: точка расширения объявлена библиотекой в **глобальном пространстве имён**, а не в экспортируемом `interface` модуля, поэтому дополнять нужно `declare global { namespace ReactNavigation { ... } }`, а не `declare module '@react-navigation/native'`.

И вторая половина того же наблюдения: то, **откуда берётся список экранов**, зависит от версии и выбранного API. В динамическом API шестой и седьмой версий он описывается вручную; в статическом API седьмой версии выводится из конфигурации навигатора. Механизм дополнения при этом общий, а код из статьи без указания версии может не сработать — форму записи диктует библиотека конкретной версии, и выясняется она чтением её `.d.ts`.

### Тема styled-библиотеки

Библиотека объявляет тип темы как `interface` — иногда пустой — а приложение дополняет его своими токенами. После этого `theme.colors.accent` типизирован внутри каждого компонента, а опечатка в имени токена не компилируется. Без дополнения тема в хуке библиотеки остаётся либо пустым объектом, либо `any`, и каждый компонент приводит её к своему типу.

### Ключи конфигурации и переменные окружения

`process.env.API_URL` без объявления — `string | undefined` в лучшем случае. Дополнение `ProcessEnv` добавляет известные ключи; оговорка про `?` из угла 2 здесь существенна, потому что переменная окружения отсутствует не в типах, а в сборке конкретного окружения.

### Глобальные объекты тестовой среды

Моки нативных модулей, глобальные флаги тестов, расширения `expect` — всё это объявляется через `declare global` в `.d.ts`, попадающем только в тестовый `tsconfig`. Организация тестовой среды — блок 11; здесь только механизм объявления.

### Типы, описывающие одну платформу

Отдельный случай, который формально не является ошибкой типов и регулярно ломает приложение: метод нативного модуля существует на Android и отсутствует на iOS, а в `.d.ts` он объявлен один раз и выглядит одинаково доступным. Компилятор пропустит вызов на обеих платформах, краш произойдёт на одной.

Собственное объявление здесь способно описать реальность точнее, чем поставляемое библиотекой:

```ts
declare module 'rn-platform-widget' {
  export function commonMethod(): void;
  /** Только Android. На iOS отсутствует — проверять Platform.OS перед вызовом. */
  export const androidOnly: { enableOverlay(): void } | undefined;
}
```

Тип `| undefined` переводит платформенное различие из комментария в проверку: вызов без `if` не компилируется. Это тот редкий случай, когда свой `.d.ts` строго полезнее официального.

## 5. Типичные ошибки

**`.d.ts`, скопированный из чужого репозитория.** Выглядит подробным, написан для другой версии библиотеки и расходится с ней в деталях: переименованный параметр, изменившийся возвращаемый тип, удалённый метод. Причина популярности — он мгновенно убирает ошибку импорта и выглядит как «типы появились». На деле появилось подробное и неверное описание, то есть худший из трёх возможных исходов.

**`declare module 'x'` без тела там, где известно хотя бы три функции.** Пишется потому, что это одна строка. Отличие от явной заглушки — не полнота, а то, что `any` расползается по вызывающему коду и ошибка обнаруживается далеко от места использования.

**Опечатка в имени модуля при augmentation.** Создаёт новое внешнее объявление вместо дополнения существующего, ошибки не даёт. Симптом — «дополнение не применилось», и его начинают искать в синтаксисе `declare`, а не в имени.

**Файл дополнения без `import` и `export`.** Компилятор считает такой файл скриптом, и `declare module` в нём становится внешним объявлением, то есть **перекрывает** типы библиотеки вместо их дополнения. Лечится добавлением любого `export {}` в файл.

**Подавление комментарием вместо объявления.** `@ts-ignore` над каждым вызовом нетипизированной библиотеки вместо одного `.d.ts`. Количество подавлений растёт, объявления так и нет, и при обновлении библиотеки ни одно из них не станет ошибкой.

**Дополнение темы или `ParamList` в `.ts`-файле, который не импортируется ниоткуда.** Дополнение не применится, если файл не попадает в программу компиляции: он должен быть в `include` либо быть `.d.ts` в известном компилятору месте. Проверяется тем, что типы появляются в одном файле и отсутствуют в другом.

## 6. Trade-offs

### Свои типы нужно поддерживать

Собственный `.d.ts` для чужой библиотеки — ответственность на каждое обновление этой библиотеки. Компилятор не предупредит о расхождении: объявление и реализация связаны только именем модуля. Поэтому объём объявления стоит держать минимальным — описывать то, что проект вызывает, а не всю библиотеку. Описание из пяти функций пересматривается за минуту, описание из пятидесяти не пересматривается никогда.

### `any`-заглушка дешевле и честнее подробного вранья

Это неочевидный вывод урока, и он противоречит привычному «any — всегда плохо». Три варианта по возрастанию риска: явная заглушка на используемое подмножество; `any`-заглушка; подробный неверный `.d.ts`.

`any`-заглушка сообщает читателю правду: «типов нет, проверок нет, смотри документацию». Подробный неверный `.d.ts` сообщает ложь, и ложь проверяемую компилятором — то есть убеждает разработчика в том, чего нет. Если выбирать между `any` и описанием, достоверность которого не подтверждена, `any` безопаснее.

### Augmentation связывает проект с устройством библиотеки

Дополнение опирается на внутреннее решение автора: имя модуля, имя `interface`, факт что это `interface`, а не `type`. Любое из этих решений может измениться в новой мажорной версии, и тогда дополнение перестанет применяться — молча, потому что augmentation несуществующего интерфейса ошибкой не является. Отсюда практика: держать дополнения в одном-двух файлах, а не раскладывать по проекту, и при обновлении библиотеки проверять их первыми.

### Граница объёма типизации

Полная типизация нетипизированной библиотеки — работа, сравнимая с её чтением целиком. Она окупается, если библиотека ключевая для проекта и обновляется редко. Чаще дешевле обёртка: один свой модуль, который вызывает библиотеку и экспортирует наружу собственный типизированный интерфейс. Тогда непроверенным остаётся один файл, а не весь код, который библиотеку вызывает, — и этот файл становится естественным местом проверок из 2.4.
