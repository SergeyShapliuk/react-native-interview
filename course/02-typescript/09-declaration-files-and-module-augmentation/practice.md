# 2.9 `.d.ts`, module augmentation и нетипизированные библиотеки — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **кто утверждает тип и чем это утверждение подкреплено**, а не воспроизвести синтаксис `declare`.

---

**1. Чем `declare module 'lib'` отличается от расширения уже существующего объявления того же модуля?**

<details>
<summary>Ответ</summary>

Это две разные операции, которые пишутся почти одинаково.

**Внешнее объявление** — `declare module 'lib'` в файле, который сам не является модулем (нет ни одного `import` или `export`). Оно создаёт описание модуля с нуля и применяется тогда, когда своих типов у библиотеки нет.

**Дополнение** — `declare module 'lib'` в файле, который является модулем. Оно добавляет объявления к уже существующим типам библиотеки, опираясь на declaration merging (2.6).

Различает их не синтаксис, а **контекст файла**. Один и тот же текст в файле со `export {}` дополняет типы, а без него — объявляет модуль заново. Отсюда самая частая неудача: дополнение написано верно, типы не появились, причина в том, что файл не модуль.

Практическое следствие: дополнить можно только то, что объявлено как `interface` внутри модуля. Объявить заново можно что угодно — но заново объявленный модуль не добавляет к типам библиотеки, а подменяет собой ситуацию «типов нет».

**Ответ «разницы нет, это один и тот же синтаксис»** вскрывает отсутствие модели файла как единицы компиляции. Проверяется за минуту: добавить `export {}` в файл с дополнением и посмотреть, появились ли типы.

**Ответ «дополнение перезаписывает объявления библиотеки»** вскрывает модель замены вместо слияния. Перезаписать объявление нельзя: одноимённые свойства с несовместимыми типами в разных объявлениях дают ошибку, а не победу последнего. Поэтому «починить» неверный тип библиотеки через augmentation не удастся — только добавить к нему.

**Ответ «внешнее объявление нужно для JS-библиотек, дополнение — для TS-библиотек»** близок к практике и путает причину. Дело не в языке библиотеки, а в наличии её типов: JS-библиотека с `@types/*` дополняется, а TS-библиотека, не экспортирующая типы, требует внешнего объявления.
</details>

**2. Почему подробный `.d.ts`, найденный в чужом репозитории, может оказаться хуже, чем его отсутствие?**

<details>
<summary>Ответ</summary>

Потому что `.d.ts` — утверждение о рантайме, которое компилятор не проверяет, а лишь применяет. Достоверность утверждения определяется тем, откуда оно взято, и у скопированного описания она неизвестна: написано для другой версии, для другой платформы, по документации, которая успела измениться.

Сравнение трёх состояний по тому, что делает разработчик:

| Состояние | Что делает разработчик |
|---|---|
| типов нет | открывает исходники или документацию, пишет объявление на используемое подмножество |
| `any`-заглушка | знает, что проверок нет, и проверяет значения сам (2.4) |
| подробный неверный `.d.ts` | доверяет автодополнению и пишет вызов, который компилируется и падает |

Третье состояние хуже первых двух именно потому, что снимает вопрос. Отсутствие типов — заметное неудобство, оно побуждает к действию. Подробное описание выглядит как решённая задача, и несоответствие обнаруживается в рантайме — у пользователя, а не при сборке.

Добавочная сложность: расхождение не обнаруживается и при обновлении библиотеки. Объявление и реализация связаны только именем модуля, компилятор их не сверяет, и мажорное обновление библиотеки не вызовет ни одной ошибки типов.

**Ответ «он может быть неполным»** вскрывает подмену главного риска второстепенным. Неполное описание безопасно: отсутствующий метод не компилируется, и это видно сразу. Опасно описание **неверное** — там, где метод объявлен с другой сигнатурой или возвращает не то.

**Ответ «он устареет»** верен и недостаточен: важно, что устаревание происходит молча. Вопрос «как вы узнаете, что описание разошлось с библиотекой» в правильном ответе остаётся без хорошего ответа — узнать можно только из краша или из чтения changelog вручную.

**Ответ «надо просто проверить его перед использованием»** вскрывает недооценку объёма работы. Проверка подробного `.d.ts` — это сверка каждой сигнатуры с исходниками, то есть ровно та работа, которую копирование должно было сэкономить. Если её делать, дешевле написать объявление на используемое подмножество.
</details>

**3. Как расширить `ParamList` навигации, не форкая библиотеку, и за счёт какого свойства interface это работает?**

<details>
<summary>Ответ</summary>

Дополнением **глобального пространства имён**, которое библиотека объявила точкой расширения:

```ts
// navigation.d.ts
import type { RootStackParamList } from './src/navigation/types';

declare global {
  namespace ReactNavigation {
    interface RootParamList extends RootStackParamList {}
  }
}
```

Приложение описывает свои экраны обычным типом, а дополнением сообщает, что именно его библиотека должна считать списком экранов по умолчанию. После этого `navigate('Lesson', { lessonId })` проверяется по экранам приложения, а не по `string`.

Работает это за счёт **declaration merging** (2.6): несколько объявлений одного `interface` в одной области видимости сливаются в одно. Библиотека объявляет точку расширения как `interface` именно для этого — будь там `type`, расширение было бы невозможно, и каждому приложению пришлось бы описывать параллельный тип с кастом на границе.

Важная часть ответа — **где** находится точка расширения. Здесь это глобальный namespace, а не экспортируемый `interface` модуля, поэтому попытка написать `declare module '@react-navigation/native'` даёт типичную молчаливую неудачу: файл компилируется, типы навигации не меняются. Форма записи зависит от того, как библиотека объявила точку расширения, и узнаётся это чтением её `.d.ts`.

Условия, при нарушении которых дополнение не применится молча: точное имя модуля или namespace, файл должен попадать в программу компиляции, расширяемая сущность должна быть объявлена как `interface`.

Сама механика навигации — вложенные навигаторы, deep linking, типизация в конкретных хуках — разбирается в 4.16.

**Ответ «через `interface AppParamList extends RootParamList`»** вскрывает смешение двух операций: создания нового типа и дополнения существующего. Новый тип появится, но функции библиотеки продолжат принимать `RootParamList`, и каждый вызов `navigate` потребует каста.

**Ответ «за счёт того, что interface можно наследовать»** называет не то свойство. Наследовать можно и `type` через пересечение; уникально для `interface` именно **слияние объявлений одного имени**.

**Ответ «надо добавить тип в `tsconfig.json` через `paths`»** вскрывает смешение поиска типов с их содержанием. `paths` влияет на то, где компилятор ищет модуль, и не добавляет в него объявлений.
</details>

**4. Почему `@ts-expect-error` предпочтительнее `@ts-ignore` при обходе ошибок в чужих типах?**

<details>
<summary>Ответ</summary>

Потому что они по-разному ведут себя в момент, когда проблема исчезает.

`@ts-ignore` подавляет ошибку на следующей строке и продолжает делать это всегда. После обновления библиотеки, где типы исправлены, комментарий остаётся и подавляет уже не существующую ошибку — а заодно любую новую, которая появится на этой строке позже. То есть обход переживает причину и превращается в постоянную слепую зону.

`@ts-expect-error` подавляет ошибку и требует, чтобы она была: если на следующей строке ошибки нет, сам комментарий становится ошибкой «Unused '@ts-expect-error' directive». После обновления библиотеки компилятор перечислит все места, где обход больше не нужен.

Для работы с чужими типами это решающее свойство: срок жизни обхода контролирует компилятор, а не память разработчика. Обход, связанный с внешней причиной, должен исчезнуть вместе с причиной — и `@ts-expect-error` единственный из двух это обеспечивает.

Оговорка: ни один из них не является решением. Оба подавляют проверку в одной строке, тогда как объявление (`.d.ts`) описывает проблему один раз для всего проекта. Выбор между комментариями имеет смысл для единичного места; для третьего вызова той же библиотеки пора писать объявление.

**Ответ «они одинаковы, `expect-error` просто новее»** вскрывает чтение директивы как синонима. Проверяется удалением причины ошибки: `@ts-expect-error` станет ошибкой, `@ts-ignore` промолчит.

**Ответ «`@ts-expect-error` строже, потому что требует описать причину»** путает с соглашением команды. Описание причины — полезная практика и требование линтера, а не свойство директивы; сама она текста не требует.
</details>

## Задание — две стратегии работы с чужими типами

**Дано.** В проекте RN Academy две задачи, которые на первый взгляд решаются одинаково, а на деле требуют разных подходов.

**Задача А.** Библиотека `rn-course-player` (воспроизведение видео урока) типов не поставляет, в `@types` её нет. Проект использует из неё четыре вещи:

```js
import Player, { prefetch, clearCache } from 'rn-course-player';

// <Player source={{ uri }} autoplay onProgress={(e) => ...} onEnd={() => ...} />
await prefetch(uri, { priority: 'high' });
await clearCache();
// Player.setVolume(0.5) — метод есть только на Android
```

**Задача Б.** Библиотека навигации и styled-библиотека типы поставляют, но список экранов и тема в них пустые — приложение должно их дополнить.

**Требуется.**

1. Написать `.d.ts` для задачи А — ровно на используемое подмножество. Отдельно решить, как описать метод, существующий только на Android, чтобы вызов без проверки платформы не компилировался.
2. Написать дополнения для задачи Б. Для каждого указать, какое из трёх условий augmentation в нём легче всего нарушить и как это проявится.
3. Сравнить объём поддержки двух подходов: что придётся сделать при обновлении библиотеки в каждом случае и кто об этом напомнит.
4. Зафиксировать политику проекта по зависимостям без типов. Ответить, в каком случае политика допускает `declare module 'x';` без тела, а в каком требует обёртку вместо объявления.

---

<details>
<summary>Разбор</summary>

**1. Объявление для `rn-course-player`.**

```ts
// types/rn-course-player.d.ts
declare module 'rn-course-player' {
  import type { FC } from 'react';
  import type { StyleProp, ViewStyle } from 'react-native';

  export type PlayerProgress = { currentSec: number; durationSec: number };

  export type PlayerProps = {
    source: { uri: string };
    autoplay?: boolean;
    style?: StyleProp<ViewStyle>;
    onProgress?: (e: PlayerProgress) => void;
    onEnd?: () => void;
  };

  const Player: FC<PlayerProps> & {
    /**
     * Только Android: на iOS свойство отсутствует.
     * Источник: src/index.js@2.3.0 — метод объявлен внутри Platform.OS === 'android'.
     */
    setVolume?: (value: number) => void;
  };

  export default Player;

  export function prefetch(
    uri: string,
    options?: { priority?: 'low' | 'normal' | 'high' },
  ): Promise<void>;

  export function clearCache(): Promise<void>;
}
```

Решения, которые здесь приняты, и причина каждого:

- **описано только используемое.** У библиотеки есть и другие экспорты; их отсутствие в объявлении — не пробел, а решение: неописанный вызов не компилируется, и это сигнал дописать объявление осознанно, а не унаследовать чужое описание;
- **`priority` — union литералов, а не `string`.** Допустимые значения взяты из исходников, и опечатка `'hight'` перестаёт компилироваться. Это то место, где своё объявление даёт больше, чем формально полный `.d.ts` со `string`;
- **`setVolume` объявлен как опциональный.** Платформенное различие переведено из комментария в тип: при `strictNullChecks` вызов `Player.setVolume(0.5)` не компилируется, пока не проверено существование. Код становится таким:

```ts
if (Player.setVolume) Player.setVolume(0.5);
// или
Player.setVolume?.(0.5);
```

Проверка `Platform.OS === 'android'` компилятору ничего не доказывает — он не связывает платформу с составом объекта. Поэтому опциональность здесь честнее: она требует проверить то, что действительно проверяемо в рантайме;

- **в комментарии указан источник и версия.** Объявление — утверждение о рантайме, и ссылка на то, откуда оно взято, превращает его из догадки в проверяемое утверждение. Без этой строки следующий читатель не сможет пересмотреть объявление при обновлении библиотеки.

**2. Дополнения для задачи Б.**

```ts
// types/navigation.d.ts
import type { RootStackParamList } from '../src/navigation/types';

declare global {
  namespace ReactNavigation {
    interface RootParamList extends RootStackParamList {}
  }
}
```

```ts
// types/theme.d.ts
import type { AppTheme } from '../src/theme';

declare module 'styled-components/native' {
  export interface DefaultTheme extends AppTheme {}
}
```

Что легче всего нарушить в каждом:

| Дополнение | Самое хрупкое условие | Как проявится |
|---|---|---|
| `ParamList` | дополняется глобальный namespace, а не модуль библиотеки; файл при этом обязан быть модулем | экраны не появятся, `navigate` продолжит принимать `string`, ошибки не будет |
| тема | расширяемая сущность объявлена как `interface` | при `type` в библиотеке — ошибка дополнения; обойти можно только параллельным типом |
| оба | точное имя модуля или namespace | опечатка создаёт новое объявление вместо дополнения, и оно уходит в пустоту молча |

Общая черта всех трёх отказов — **молчание**. Augmentation несуществующего интерфейса или несуществующего модуля ошибкой не является, поэтому проверка здесь не «компилируется ли», а «появились ли типы»: навести курсор на `navigate` и убедиться, что имя экрана — union литералов, а не `string`.

**3. Объём поддержки.**

| | Своё объявление (А) | Дополнение (Б) |
|---|---|---|
| Что описано | чужое API целиком, на используемом подмножестве | только свои сущности, добавленные к чужому типу |
| При обновлении библиотеки | пересмотреть каждую сигнатуру по changelog вручную | ничего, если библиотека не переименовала `interface` или модуль |
| Кто напомнит | никто: объявление и реализация связаны только именем | компилятор, но только при переименовании с ошибкой; при исчезновении `interface` — никто |
| Что сломается незаметно | сигнатура разошлась — компилируется, падает в рантайме | дополнение перестало применяться — типы стали шире, ошибки нет |

Вывод: дополнение дешевле в поддержке на порядок, потому что описывает **свои** сущности. Своё объявление чужого API — долг, который возвращается при каждом обновлении, и единственный способ держать его малым — не описывать то, что не вызывается.

**4. Политика проекта по зависимостям без типов.**

1. **По умолчанию — явная заглушка на используемое подмножество**, в одном файле на библиотеку, в `types/`, с комментарием об источнике и версии.
2. **`declare module 'x';` без тела допустим** в двух случаях: библиотека вызывается в одном-двух местах и её значения не уходят дальше (например, разовая инициализация в точке входа); либо проект заводит заглушку как временный шаг и фиксирует это задачей. Во всех случаях — с комментарием, почему тела нет. Без тела модуль становится `any`, поэтому значения из него проверяются на месте использования по 2.4.
3. **Подавление комментарием — только `@ts-expect-error`**, с текстом причины, и только для единичного места. Третий вызов той же библиотеки означает, что пора писать объявление.
4. **Обёртка вместо объявления требуется, когда** библиотека вызывается из многих мест, её значения попадают в состояние или в домен, либо её API заметно шире используемого подмножества. Тогда проект пишет свой модуль, который вызывает библиотеку и экспортирует наружу собственный типизированный интерфейс; непроверенным остаётся один файл, он же становится местом проверок из 2.4 и точкой замены библиотеки.
5. **Запрещено:** копировать `.d.ts` из чужого репозитория без сверки с исходниками; описывать неиспользуемое API «на будущее»; `@ts-ignore` в любом виде.

**Вклад в проект (P2).** Зафиксирована политика по зависимостям без типов: явная заглушка с перечнем используемых функций вместо подавления ошибок, обёртка для библиотек с широким API, запрет на скопированные объявления. Дополнения `ParamList` и темы собраны в двух файлах `types/`, чтобы при обновлении библиотек проверять их первыми. Решение о том, где библиотека считается границей системы и что на этой границе проверяется, обобщается в 2.13; стоимость владения зависимостью и выбор «обёртка или прямые вызовы» как архитектурное решение — блок 08.
