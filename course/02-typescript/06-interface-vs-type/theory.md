# 2.6 `interface` vs `type` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что лучше» — а на вопрос, **какое свойство различает их на практике и в каком решении это свойство оказывается решающим**.

---

## 1. Что это

**`interface`** — объявление именованной формы объекта. Одно имя может быть объявлено несколько раз, и объявления сливаются.

**`type`** — псевдоним (alias) для любого типа: объекта, union, кортежа, примитива, результата вычисления над типами.

```ts
interface Lesson {
  id: string;
  title: string;
}

type LessonAlias = {
  id: string;
  title: string;
};
```

Для описания формы объекта это взаимозаменяемые записи. Объект подойдёт под оба, функция примет оба, расширить можно оба. Разница начинается там, где заканчивается «форма объекта».

**Declaration merging (слияние объявлений)** — свойство `interface`, при котором несколько объявлений одного имени в одной области видимости объединяются в одно. У `type` повторное объявление имени — ошибка «Duplicate identifier».

```ts
interface Theme { colors: Colors }
interface Theme { spacing: Spacing }
// Theme имеет и colors, и spacing

type T = { a: string };
type T = { b: string };   // Duplicate identifier 'T'
```

### Ключевая формулировка урока

> **`interface` — это открытое объявление, `type` — закрытое. Выбор между ними есть ответ на вопрос, вправе ли кто-то снаружи дополнить этот тип.**

Всё остальное — выразительность, сообщения об ошибках, стоимость проверки — следствия либо второстепенные детали.

---

## 2. Как это работает

### Что умеет только `type`

`interface` описывает форму объекта (включая вызываемые и индексируемые формы) — и больше ничего. Всё, что не является формой объекта, выражается только через `type`:

```ts
type Status = 'idle' | 'loading';              // union
type Pair = [string, number];                  // кортеж
type Id = string;                              // псевдоним примитива
type Keys = keyof Lesson;                      // результат вычисления
type Optional<T> = { [K in keyof T]?: T[K] };  // mapped type
type Unwrap<T> = T extends Promise<infer U> ? U : T;  // conditional type
```

Из этого следует практическая граница, которая закрывает большую часть выбора: **как только тип перестаёт быть простой формой объекта, `interface` неприменим**. Discriminated union из 2.5 нельзя объявить через `interface` — это union, а не объект.

### `extends` против пересечения

```ts
interface Base { id: string }
interface WithTitle extends Base { title: string }

type TBase = { id: string };
type TWithTitle = TBase & { title: string };
```

Для совместимых полей результат одинаков. Разница проявляется при **конфликте одноимённых свойств**.

`extends` требует совместимости и сообщает об ошибке в месте объявления:

```ts
interface A { id: string }
interface B extends A { id: number }
// Interface 'B' incorrectly extends interface 'A':
// Types of property 'id' are incompatible
```

Пересечение ошибки не даёт: оно вычисляет тип, который должен быть одновременно `string` и `number`, то есть `never`:

```ts
type A2 = { id: string };
type B2 = A2 & { id: number };

declare const b: B2;
b.id;   // never — присвоить сюда нечего
```

Объявление компилируется, и ошибка появляется позже — в месте, где этот тип пытаются использовать, с сообщением про `never`, которое не указывает на причину. Это главное наблюдаемое различие между двумя способами расширения: `extends` проверяет расширение, `&` его вычисляет.

### Структурная типизация и `implements`

**Structural typing (структурная типизация)** — совместимость типов определяется составом, а не именем или объявленным родством. Класс, случайно описавший все поля `Lesson`, совместим с `Lesson` без всякого `implements`.

```ts
class LessonModel {
  constructor(public id: string, public title: string) {}
}
const l: Lesson = new LessonModel('1', 'JSI');   // подходит
```

`implements` при этом не меняет тип класса — он только включает проверку: «убедись, что я описал всё необходимое». Работает и с `interface`, и с `type`, если `type` описывает форму объекта. С union `implements` невозможен, потому что реализовать «одно из двух» нельзя.

### Сообщения об ошибках

`interface` сохраняет имя: компилятор пишет `Type 'X' is not assignable to type 'Lesson'`. Псевдоним `type` компилятор часто разворачивает в тело, и в сообщении появляется структура целиком — для типа из двадцати полей, собранного пересечениями, это несколько экранов текста, в которых нужно найти одно несовпадающее поле.

Разница не абсолютная: простой `type` компилятор тоже показывает по имени. Но чем больше тип собран вычислениями, тем выше шанс увидеть его тело вместо имени.

### Стоимость проверки

Структура объявления может влиять на время проверки: именованная связь через `interface extends` и выражение над типами через `&` обрабатываются по-разному, и на длинных цепочках пересечений в большой кодовой базе разница бывает заметной.

Чего из этого **не** следует — общего правила «`interface` быстрее пересечения». Величина эффекта зависит от размера и формы типов, от того, сколько раз они участвуют в проверках, и от версии компилятора; на типах из нескольких полей разницы нет вовсе.

Формулировать это честно стоит так: разница существует, она проявляется на больших типах и длинных цепочках, и обнаруживается замером времени сборки на своём проекте, а не выбором из общих соображений. На типе из пяти полей разницы нет.

## 3. Почему это важно

Вопрос «interface или type» в большинстве статей сводится к списку различий. Для проекта он сводится к одному решению: **объявляя публичный тип модуля, вы решаете, сможет ли его дополнить кто-то снаружи.**

Если тип объявлен как `interface`, потребитель — другой модуль проекта, приложение, использующее вашу библиотеку, — добавит в него своё поле через module augmentation (2.9), и тип останется одним. Если тип объявлен как `type`, дополнить его нельзя: придётся описать рядом параллельный тип и поддерживать два описания одной сущности.

Обратная сторона того же свойства — `interface` нельзя закрыть. Любой файл в проекте вправе добавить поле в ваш `interface`, и обнаружить это по месту объявления невозможно: объявления разбросаны по файлам, и сливаются они молча. Для внутреннего типа приложения это скорее риск, чем польза.

Отсюда рабочее правило, которое стоит зафиксировать в проекте: **`interface` — для контрактов, которые предполагается расширять снаружи; `type` — для всего остального.** Правило даёт ответ в каждом конкретном случае и не требует помнить список различий.

> **Это соглашение проекта, а не правило языка.** TypeScript не придаёт `interface` смысла «публичный API», а `type` — смысла «внутренний тип»: оба участвуют в структурной типизации на равных, и ни один из них не обозначает уровень доступа. Соглашение полезно тем, что превращает выбор в один вопрос вместо списка различий, но оно именно соглашение — в чужом коде `interface` сплошь и рядом описывает внутренние структуры, и читать это как заявку на расширение не нужно. Работает и обратная сторона: возможность дополнить чужой тип определяется не формой записи вообще, а конкретным объявлением конкретной библиотеки (2.9).

## 4. Где это в React Native

### Типы, которые расширяет кто-то другой

Три места, где расширение чужого типа — норма ежедневной работы, и все три опираются на declaration merging:

- **`ReactNavigation.RootParamList`** — список экранов приложения, который библиотека навигации объявляет как `interface`, чтобы приложение дополнило его своими экранами. Благодаря этому `navigate('Lesson', { id })` проверяется по вашим экранам, а не по `string`;
- **тип темы в styled-библиотеке** — библиотека объявляет пустой или минимальный `interface`, приложение добавляет свои токены, и `theme.colors.accent` становится типизированным внутри каждого компонента;
- **`ProcessEnv`** — переменные окружения, куда проект добавляет свои ключи, чтобы `process.env.API_URL` не был `string | undefined` без всякой подсказки о наличии ключа.

Если бы любой из этих типов был объявлен как `type`, расширение стало бы невозможным, и каждое приложение описывало бы свой параллельный тип с кастом на границе. Это и есть решающий аргумент: не удобство, а наличие или отсутствие точки расширения.

### Пропсы компонента

Для пропсов чаще подходит `type`, и по двум причинам, обе из которых — следствие выразительности:

```ts
type BannerProps =
  | { kind: 'info'; text: string }
  | { kind: 'action'; text: string; onPress: () => void };

type ButtonProps = ComponentPropsWithoutRef<typeof Pressable> & {
  title: string;
};
```

Первое — варианты пропсов как union (2.5), и это невыразимо через `interface`. Второе — пересечение с пропсами библиотечного компонента, выведенными утилитой: `interface extends` от такого вычисленного типа работает не всегда, а пересечение работает всегда. Типизация пропсов целиком — урок 2.14.

Исключение — библиотечный компонент, чьи пропсы вы хотите дать расширить потребителю. Тогда снова `interface`.

### DTO и доменные сущности

DTO ответа сервера — закрытое описание того, что приходит снаружи: расширять его из другого файла незачем, и возможность это сделать скорее опасна. Доменные сущности проекта — тоже закрытые описания, если проект не библиотека.

Практическое следствие для `.d.ts` библиотек: прежде чем планировать расширение чужого типа, нужно посмотреть, как он объявлен. Тип, объявленный в библиотеке как `type`, расширить не удастся, и это обнаруживается в момент, когда augmentation молча не срабатывает (2.9).

## 5. Типичные ошибки

**«Interface быстрее» без уточнения.** Утверждение берётся из обсуждений производительности компилятора и переносится на любой случай. Оно верно для длинных цепочек пересечений на большой кодовой базе и бессмысленно для типа из пяти полей. Проверяется замером времени проверки типов на своём проекте.

**`A & B` вместо `interface A extends B` там, где нужна проверка.** Пересечение не проверяет совместимость: конфликт полей даёт `never`, и ошибка всплывает в месте использования с сообщением, не указывающим на причину. Причина ошибки — `&` читается как «и то, и другое», что верно для совместимых типов и неверно для конфликтующих.

**Попытка применить declaration merging к `type`.** Возникает из переноса приёма с interface. Результат — `Duplicate identifier`, и обход обычно выбирают неверный: вместо исправления объявления в библиотеке (или issue к ней) описывают параллельный тип и ставят `as` на границе.

**Публичный тип модуля как `type` без решения.** Самая дорогая из ошибок этого урока, потому что обнаруживается позже всех: тип выбран по привычке, а через полгода выясняется, что его нужно дополнить из двух мест. К этому моменту его использует десяток файлов, и замена объявления — отдельная задача.

**`interface` для union.** Не компилируется, и это хорошо: ошибка видна сразу. Хуже встречающийся обход — описать union как `interface` с опциональными полями, вернувшись к тому, от чего избавлял урок 2.5.

## 6. Trade-offs

### Открытость против закрытости

`interface` даёт точку расширения и отбирает контроль: любое объявление того же имени в области видимости дополняет тип, и место дополнения не видно по месту объявления. `type` даёт контроль и отбирает расширяемость. Одно свойство, две стороны — выбирается та, которая нужна этому типу.

### Выразительность против читаемости ошибок

`type` выражает всё, но чем сложнее выражение, тем хуже сообщения компилятора: вместо имени появляется развёрнутое тело. Приём, который это смягчает, — назвать промежуточные типы: вместо одного `type` из четырёх пересечений и двух условных типов объявить три именованных шага. Проверка типов от этого не ускорится, а читать ошибки станет возможно.

### Единое правило против выбора по случаю

Правило «interface для расширяемых контрактов, type для остального» стоит одного исключения: часть типов придётся объявить как `interface` только ради сообщений об ошибках или скорости проверки, не планируя расширения. Это нормально — важно, чтобы решение было записано рядом с типом, иначе следующий разработчик прочтёт его как точку расширения.

### Единообразие кодовой базы

Соглашение «всё через `type`, кроме расширяемых контрактов» дешевле в чтении, чем смешение без правила. Ценность единообразия здесь выше ценности локально оптимального выбора: тип, объявленный «как удобнее в этом файле», сообщает читателю меньше, чем тип, объявленный по правилу.
