# 2.6 `interface` vs `type` — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **вправе ли кто-то снаружи дополнить тип и в какой момент решение проявится**, а не перечислить различия двух конструкций.

---

**1. Что произойдёт при конфликте одноимённых свойств в `extends` и что — при `&`?**

<details>
<summary>Ответ</summary>

`extends` проверяет расширение, `&` его вычисляет. Отсюда расходятся и момент ошибки, и её текст.

`extends` требует совместимости свойства наследника со свойством родителя и сообщает об ошибке в месте объявления:

```ts
interface A { id: string }
interface B extends A { id: number }
// Interface 'B' incorrectly extends interface 'A':
// Types of property 'id' are incompatible
```

Пересечение ошибки не даёт — объявление компилируется. Оно вычисляет тип, который должен быть одновременно `string` и `number`, то есть `never`:

```ts
type A2 = { id: string };
type B2 = A2 & { id: number };

declare const b: B2;
b.id;   // never — присвоить сюда нечего
```

Ошибка появляется позже — там, где тип пытаются использовать. Сообщение будет про `never` и не укажет на причину: в месте использования её нет, она в объявлении, которое компилятор принял. Уточнение: `never` получается, когда конфликтующие свойства несовместимы как **примитивы**. Если оба свойства — объекты, пересечение вычисляется рекурсивно, и `never` уезжает на уровень вложенного поля — внешний тип выглядит нормально, непригодным оказывается `a.b.c`.

Практический вывод: нужна проверка в момент объявления — `extends`; тип собирается из частей, включая вычисленные, — остаётся `&`, и конфликт полей ловит только дисциплина автора.

**Ответ «`&` тоже даст ошибку, просто текст другой»** вскрывает ожидание, что обе записи что-то проверяют. Проверяется объявлением без использования: файл с `type B2 = A2 & { id: number }` компилируется чисто. Следствие: конфликт может приехать в проект вместе с изменением одного из операндов и не проявиться там, где его внесли.

**Ответ «`&` возьмёт тип из последнего операнда»** вскрывает модель перезаписи полей, перенесённую со `spread` и `Object.assign`. Проверяется наведением на `b.id`: там `never`, а не `number`. Следствие заблуждения — попытка «переопределить» поле записью `Base & { id: number }`; такого переопределения `&` не умеет, поле сначала удаляют (`Omit`, 2.3), потом добавляют.

</details>

---

**2. Почему тип темы в UI-библиотеке объявлен как interface, а не как `type`?**

<details>
<summary>Ответ</summary>

Потому что токены темы знает приложение, а не библиотека, и единственный способ отдать приложению право дополнить тип — объявить его открытым. Несколько объявлений `interface` с одним именем в одной области видимости сливаются (declaration merging), и тип остаётся одним: библиотека объявляет пустой или минимальный `interface`, приложение добавляет свои поля, и `theme.colors.accent` типизирован в каждом компоненте, не теряя связи с `useTheme()`.

С `type` добавить поле нельзя — повторное объявление имени даёт `Duplicate identifier`. Остаются две альтернативы, обе хуже: параллельный тип приложения с приведением на каждом обращении (`(useTheme() as AppTheme).colors.accent` — утверждение в каждом компоненте и никакой проверки темы, 2.4) либо параметризация (`ThemeProvider<T>`, `useTheme<T>()` — тип приходится пробрасывать в каждый вызов, иначе выводится база).

Решающий аргумент — не удобство записи и не скорость компилятора, а **наличие точки расширения**. Обратная сторона того же свойства: такой тип нельзя закрыть; для темы библиотеки это цель, для внутреннего типа приложения — риск. Сам приём дополнения — урок 2.9; он возможен исключительно благодаря declaration merging.

**Ответ «потому что interface лучше подходит для описания объектов»** вскрывает подмену причины общим предпочтением. Проверяется вопросом «что именно сломается при замене на `type`»: ответ должен быть конкретным — перестанет компилироваться дополнение темы в приложении. Если ответа нет, выбор сделан стилем, а не свойством.

**Ответ «потому что тему расширяют через `extends`»** вскрывает смешение двух операций: создания нового типа на основе старого и дополнения существующего. `interface AppTheme extends Theme { ... }` создаёт второе имя, а `useTheme()` библиотеки по-прежнему возвращает `Theme` — и на каждом вызове снова нужен каст.

**Ответ «это вопрос стиля, библиотека могла бы объявить и `type`»** вскрывает главное заблуждение темы — «выбор ничего не меняет». Здесь он меняет наблюдаемую возможность потребителя: с `type` тема приложения не типизируется вообще, и это проверяется одной попыткой дополнить тип.
</details>

**3. Какие конструкции принципиально недоступны interface и из чего это следует?**

<details>
<summary>Ответ</summary>

`interface` — объявление **именованной формы объекта**: поля, методы, вызываемая форма, индексная подпись. Ничего, что формой объекта не является, в него не входит, поэтому через `interface` нельзя выразить:

```ts
type Status = 'idle' | 'loading';              // union
type Pair = [string, number];                  // кортеж
type Id = string;                              // псевдоним примитива
type Keys = keyof Lesson;                      // результат вычисления
type Optional<T> = { [K in keyof T]?: T[K] };  // mapped type
type Unwrap<T> = T extends Promise<infer U> ? U : T;  // conditional type
```

Следует это из того же свойства, что и declaration merging. `interface` — не псевдоним выражения над типами, а объявление состава, и объявлений может быть несколько: компилятор обязан уметь сложить их в одно. Поля складываются; для union складывать нечего. Конструкции без состава не выражаются в `interface` в принципе, а не по недоработке.

Отсюда граница, закрывающая большую часть выбора: **как только тип перестаёт быть простой формой объекта, `interface` неприменим, и решение за вас уже принято механизмом**. Discriminated union из 2.5 — union, а не объект; варианты пропсов — тоже. Правило «interface для расширяемых контрактов, `type` для остального» применяется только к тому, что осталось.

**Ответ «union можно описать через interface с опциональными полями»** вскрывает обход, возвращающий код к тому, от чего избавлял урок 2.5. Форма с опциональными полями — не union: она разрешает и комбинацию полей из разных вариантов, и отсутствие всех. Проверяется попыткой написать `switch` по полю: сужения не произойдёт.

**Ответ «interface не поддерживает дженерики»** неверен: `interface Box<T> { value: T }` работает. Недоступно другое — **вычисление** над параметром: `keyof T`, перебор `[K in keyof T]`, условие `T extends ...`. Граница проходит не по наличию параметра типа, а по тому, является ли результат формой объекта.

**Ответ «ограничение обходится через `interface X extends SomeType`»** верен частично. Расширить `interface` от `type` можно, если тот описывает форму объекта со статически известными членами — так подключают результат утилитарного типа (2.3). От union, кортежа или примитива унаследоваться нельзя: `extends` требует состав, которого у них нет.
</details>

**4. Как обнаружить, что чужой `interface` уже кем-то дополнен?**

<details>
<summary>Ответ</summary>

По месту объявления — нельзя: объявления сливаются молча и лежат в любом файле области видимости, включая `.d.ts` в зависимостях. Остаются три способа:

- **состав собранного типа.** Hover на имени показывает итоговый набор полей; поле, которого нет в исходном объявлении, означает слияние. Переход к определению на таком имени предлагает список, а не одно место;
- **поиск по проекту и по зависимостям.** `interface <Имя>` плюс `declare module` и `declare global` — по `src`, `node_modules` и `@types`. Два последних каталога пропускают чаще всего, а дополнение из зависимости — обычное дело (2.9);
- **наблюдаемое поведение.** Обязательное поле, добавленное дополнением, ломает все места создания объекта: ошибка в вашем коде, причина — в чужом файле, который вы не меняли.

Практическое следствие важнее техники поиска: **`interface` нельзя закрыть**. Записи, запрещающей дополнять его снаружи, нет, поэтому решение «этот тип не дополняется» фиксируется не комментарием, а выбором `type`.

**Ответ «посмотреть определение типа в IDE»** вскрывает веру в единственное определение. Шаг верный, вывод из него — нет: переход на имя со слиянием предлагает выбор, а привычка брать первый пункт приводит к чтению одного объявления из трёх. Проверяется тем, что hover покажет поля, которых в открытом файле не видно.

**Ответ «TypeScript предупредит о повторном объявлении»** вскрывает перенос правила с `type` на `interface`. Для `type` повторное объявление — ошибка `Duplicate identifier`, для `interface` — штатный механизм, молчаливый по устройству. Диагностику он даёт только при несовместимости одноимённых полей в разных объявлениях.

</details>

## Задание — публичные типы модулей домена: кто и зачем будет их расширять

**Дано.** Стадия P2 проекта RN Academy: модули домена без React. Публичные типы объявлены вперемешку `interface` и `type` — по привычке автора файла, правила в проекте нет. Два типа планируется дополнять из других модулей, но какие именно — нигде не записано.

```ts
// src/domain/lesson/types.ts
export interface Lesson {
  id: string;
  title: string;
  level: LessonLevel;
}
export type LessonLevel = 'refresh' | 'deepDive' | 'senior';
export interface LessonDto { id: string; title: string; level: string }

// src/domain/progress/types.ts
export type ProgressEntry = { lessonId: string; completedAt: string | null };
export interface ProgressSummary { total: number; completed: number }

// src/ui/theme/types.ts — тема внутреннего ui-kit проекта
export type AppTheme = {
  colors: { background: string; text: string };
  spacing: { s: number; m: number };
};

// src/domain/analytics/types.ts — карта событий, которую заполняют модули домена
export type AnalyticsEventMap = {
  lesson_opened: { lessonId: string };
};
```

**Требуется.**

1. Для каждого экспортируемого типа ответить на вопрос «кто и зачем будет дополнять его снаружи модуля»: назвать конкретного потребителя или сказать «никто». Отдельно отметить типы, за которые решение принято механизмом, а не правилом.
2. Переобъявить типы по результату пункта 1 и записать решение рядом с каждым типом, объявленным не по общему правилу проекта.
3. Проверить гипотезу экспериментом: из другого файла попробовать дополнить один тип, объявленный как `interface`, и один — как `type`. Зафиксировать, что происходит и в какой момент — при объявлении или при использовании.
4. Разобрать `AnalyticsEventMap`: почему `type` ломает требование «каждый модуль домена добавляет свои события», что меняется в объявлении минимально и какую цену проект платит за открытость.

---

<details>
<summary>Разбор</summary>

**1–2. Решение по каждому типу.**

| Тип | Объявление | Почему |
|---|---|---|
| `Lesson` | `type` | Сущность приложения, не библиотеки; поля урока добавляет тот же модуль. Открытость тут не польза, а возможность молча изменить сущность из чужого файла |
| `LessonLevel` | `type` | Решено механизмом: union литералов через `interface` не выражается (вопрос 3) |
| `LessonDto` | `type` | Закрытое описание того, что пришло снаружи: тип обязан соответствовать ответу сервера, а не ожиданиям модуля |
| `ProgressEntry` | `type` | Внутренняя запись прогресса; потребителя нет |
| `ProgressSummary` | `type` | Результат агрегации внутри модуля; `interface` был выбран привычкой |
| `AppTheme` | `interface` | Потребитель назван конкретно: модули и будущий ui-kit добавляют свои токены, а `useTheme()` обязан возвращать один и тот же тип |
| `AnalyticsEventMap` | `interface` | Точка расширения по назначению: каждый модуль домена добавляет свои события (пункт 4) |

Итог: из семи типов `interface` оправдан у двух, за один решено механизмом, остальные четыре — `type` по правилу. Соотношение типичное: случаев расширения мало, и правило поэтому формулируется «`type` по умолчанию, `interface` при названном потребителе», а не наоборот.

Оба решения в пользу `interface` записываются рядом с объявлением:

```ts
// interface, а не type: тема дополняется модулями через declaration merging.
export interface AppTheme { /* ... */ }
```
**3. Эксперимент: что происходит при попытке дополнить.**

Первое наблюдение — не про `interface` против `type`, а про область видимости. Файл с `import`/`export` является модулем, и объявления в нём не видны другим файлам: `interface AppTheme { accent: string }` рядом с импортом того же имени даёт не слияние, а второе локальное имя и ошибку «Import declaration conflicts with local declaration». Дополнить тип из другого модуля позволяет только приём, объявляющий дополнение в нужной области видимости (`declare module`, 2.9):

```ts
// src/domain/progress/theme.d.ts
export {};   // файл обязан быть модулем, иначе это не дополнение (см. ниже)

declare module '../../ui/theme/types' {
  interface AppTheme { accentProgress: string }
}
```

Строка `export {}` не формальность. Без неё файл — скрипт, и `declare module` с относительным путём в скрипте запрещён: компилятор ответит «Ambient module declaration cannot specify relative module name», а `accentProgress` у темы не появится (проверено `tsc`). Правило «файл дополнения обязан быть модулем» подробно разобрано в 2.9.

После этого `useTheme().accentProgress` типизирован во всём проекте, и `AppTheme` по-прежнему **одно** имя.

Та же попытка для типа, объявленного через `type`, не проходит — это главный результат эксперимента:

```ts
export {};

declare module '../../ui/theme/types' {
  type AppTheme = { accentProgress: string };
  // Duplicate identifier 'AppTheme'
}
```

Повторное объявление псевдонима — ошибка, а не слияние; добавить поле к существующему `type` нечем. Момент отказа тоже важен: ошибка возникает **в объявлении дополнения**, сразу, а не в месте использования. Заблуждение «declaration merging работает и для `type`» обнаруживается быстро — в отличие от дополнения, написанного для типа из чужой библиотеки и молча ни на что не влияющего (2.9).

**4. `AnalyticsEventMap`: требование и цена.**

Требование `type` не выполняет по устройству: «каждый модуль домена добавляет свои события» означает, что имя заполняется из нескольких файлов, то есть ровно declaration merging. С `type` исходов два, и оба плохи. Либо `analytics` импортирует типы всех доменных модулей, чтобы собрать карту пересечением, — и модуль, который должен быть общим и ни от кого не зависеть, начинает зависеть от всех. Либо каждый модуль описывает свою карту, и на границе `track()` стоит `as`.

Минимальное изменение — объявить карту открытой:

```ts
// src/domain/analytics/types.ts
export interface AnalyticsEventMap {
  // модули домена добавляют свои события дополнением этого interface
}

export type AnalyticsEventName = keyof AnalyticsEventMap;

export function track<N extends AnalyticsEventName>(
  name: N,
  payload: AnalyticsEventMap[N],
): void;
```

Остальное не меняется: `AnalyticsEventName` и `payload` остаются вычислениями над формой, то есть `type`. Комбинация характерная — **открытое объявление формы плюс закрытые вычисления над ней**: `interface` даёт точку расширения, `keyof` и индексный доступ (2.3) превращают дополненную форму в типы имени и нагрузки, а зависимость направлена от доменных модулей к `analytics`, а не обратно.

Цена открытости — не гипотетическая:

- **объявление перестаёт отвечать на вопрос «какие события есть в приложении»** — исходный файл пуст, ответ собирается hover'ом по `AnalyticsEventName`;
- **конфликт имён обнаруживается не там, где мешает.** Два модуля, объявившие `lesson_opened` с разной полезной нагрузкой, дадут несовместимые объявления одного поля, и диагностика укажет на них, а не на сломавшийся вызов `track`;
- **любой файл вправе добавить событие,** и закрыть эту возможность нельзя. Соглашение о неймспейсах (`progress/*`, `lesson/*`) — не ограничение типа, а договорённость, которую проверяет ревью.

Та же пара «открытость против контроля», что и в теме, только здесь открытость выбрана сознательно и с перечисленной ценой.

**Вклад в проект (P2).** Публичные типы модулей домена перестают быть смесью двух записей: для каждого записан ответ на вопрос «кто и зачем будет его дополнять», и ответ закреплён самим объявлением. Фиксируется правило проекта: **`type` по умолчанию, `interface` — только там, где назван конкретный потребитель расширения, и решение записано рядом с типом.** Таких точек в проекте две — тема ui-kit и карта аналитических событий; остальные типы домена закрыты. Это и есть контракт между модулями: он задаёт не только форму данных, но и права на её изменение. Приём, которым дополнение выполняется, — 2.9; здесь зафиксирована разметка: что открыто, что закрыто и почему.
</details>
