# 2.7 `satisfies` и template literal types — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что делает оператор `satisfies`» — а на вопрос, **как проверить объект по типу, не потеряв точности вывода**.

---

## 1. Что это

До появления `satisfies` у объектного литерала было два способа связаться с типом, и оба что-то отнимали. Возьмём карту маршрутов — объект, от которого нужны обе вещи сразу: форма значений должна проверяться, а имена маршрутов — остаться именами, а не превратиться в `string`.

```ts
type Route = { path: string; auth: boolean };
```

### Вариант 1 — аннотация

```ts
const routes: Record<string, Route> = {
  lesson:     { path: '/lesson/:id', auth: true },
  courseList: { path: '/courses',    auth: false },
};

// keyof typeof routes  →  string
// routes.lessson       →  Route   ← опечатка компилируется, в рантайме undefined
```

Форма значений проверена: запись без `auth` даст ошибку. Но типом переменной стала аннотация, а не вывод из значения: объект с двумя ключами получил тип «любая строка → `Route`», и обращение по опечатке не отличается от обращения по имени.

### Вариант 2 — `as const` (или вообще без аннотации)

```ts
const routes = {
  lesson:     { path: '/lesson/:id', auth: true },
  courseList: { pathh: '/courses',   auth: false },   // ← компилируется
} as const;

// keyof typeof routes  →  "lesson" | "courseList"
// routes.lessson       →  ошибка
```

Точность максимальна, но `Route` здесь не упомянут, и соответствие ему никто не проверял. Опечатка в имени поля даёт просто другой ключ; ошибка появится не здесь, а в первом месте, которое прочитает `routes.courseList.path` — а если маршруты читаются циклом по `Object.values`, то нигде.

### Вариант 3 — `satisfies`

**`satisfies`** — оператор, который проверяет, что выражение соответствует типу, и оставляет выражению его собственный выведенный тип.

```ts
const routes = {
  lesson:     { path: '/lesson/:id', auth: true },
  courseList: { pathh: '/courses',   auth: false },   // ← ошибка ровно здесь
} satisfies Record<string, Route>;
```

Убрав опечатку:

```ts
// typeof routes        →  { lesson: { path: string; auth: boolean }; courseList: { ... } }
// keyof typeof routes  →  "lesson" | "courseList"
// routes.lessson       →  ошибка
```

Форма проверена, ключи сохранены. Значения выведены как `string` и `boolean`, а не как литералы: тип из `satisfies` работает контекстом, и `Route.path` объявлен как `string`.

### Ключевая формулировка урока

> **Аннотация проверяет и заменяет тип. `as` заменяет тип и не проверяет. `satisfies` проверяет и не заменяет.**

## 2. Как это работает

### Три операции над одним выражением

Две независимые оси: проверяется ли выражение по типу и становится ли этот тип типом выражения.

| Конструкция | Проверка по типу | Тип выражения |
|---|---|---|
| `const x: T = expr` | да | `T` |
| `const x = expr as T` | только совместимость | `T` |
| `const x = expr satisfies T` | да | выведенный из `expr` |

### Чего `satisfies` не делает

- **не приводит тип:** обратиться к `expr satisfies T` как к `T` нельзя, если выведенный тип этого не позволяет;
- **не подавляет ошибку:** проверка, которую `as` отключал, и есть то, что `satisfies` включает (2.4);
- **ничего не делает в рантайме:** как `as` и `as const`, удаляется при транспиляции.

### Лишнее поле находит `satisfies`, а не `as`

Проверка объектного литерала включает **excess property check (проверку лишних свойств)** — запрет на ключи, которых в целевом типе нет. `as` её не выполняет.

```ts
type ColorName = 'primary' | 'surface' | 'danger';
const base = { primary: '#1', surface: '#2', danger: '#3', sufrace: '#4' };

const a = base as Record<ColorName, string>;   // ошибки нет
const b = {
  primary: '#1', surface: '#2', danger: '#3', sufrace: '#4',
} satisfies Record<ColorName, string>;           // ошибка: 'sufrace' does not exist
```

`as` молчит, потому что утверждение о типе требует лишь совместимости, а объект с лишним полем совместим с типом без него. По той же причине `as` пропускает **недостающий** ключ: `{ primary: '#1' } as Record<ColorName, string>` компилируется, и `a.danger` имеет тип `string` при `undefined`.

Важная граница самой проверки лишних свойств: она работает только для свойств, **написанных в литерале прямо**. Свойства, пришедшие через spread или из готовой переменной, не проверяются — `{ ...base } satisfies Record<ColorName, string>` и `base satisfies ...` компилируются без ошибки, хотя `sufrace` там есть (проверено `tsc`). Поэтому `satisfies` ставят на сам литерал, в месте его объявления, а не на копию.

Лишнее поле видно тогда, когда у целевого типа **конечный набор ключей**. У `Record<string, Route>` индексная подпись, и проверка работает уровнем глубже — внутри значения (`pathh` лишний в `Route`).

### `as const satisfies T` и почему порядок важен

```ts
const routes = { lesson: { path: '/lesson/:id', auth: true } } as const satisfies Record<string, Route>;
// typeof routes.lesson.path  →  "/lesson/:id"

const bad = { lesson: { path: '/lesson/:id', auth: true } } satisfies Record<string, Route> as const;
// A 'const' assertion can only be applied to references to enum members,
// or string, number, boolean, array, or object literals
```

Читается слева направо: `as const` фиксирует литералы, затем `satisfies` сверяет результат с `Route`. Обратный порядок не компилируется — `as const` применим только к литералу, а после `satisfies` выражение литералом уже не является.

### `keyof typeof` как единственный источник union ключей

```ts
type RouteName = keyof typeof routes;   // "lesson" | "courseList"

function navigate(name: RouteName) { /* ... */ }
navigate('lessons');   // ошибка
```

Объект остаётся единственным местом, где перечислены имена. При аннотации `RouteName` равен `string`; при отдельно объявленном union имён появляется второй список, расходящийся с картой.

### Template literal types

**Template literal type (шаблонный литеральный тип)** — литеральный строковый тип, собранный из частей, где на месте подстановки стоит не значение, а тип. Синтаксис повторяет шаблонную строку JS, но вычисление происходит при проверке типов и результат — тип, а не строка.

```ts
type Prefixed = `rnacademy:${string}`;
const b: Prefixed = 'progress';             // ошибка
const a: Prefixed = 'rnacademy:progress';   // ок

type Domain = 'lesson' | 'course' | 'progress';
type EventName = `app.${Domain}_${'opened' | 'completed'}`;
// "app.lesson_opened" | "app.lesson_completed" | "app.course_opened" | ... — шесть членов
```

`${string}` подходит любой строке с таким префиксом. Если в подстановке стоит union литералов, шаблон по нему **распределяется**, и результат — декартово произведение: здесь шесть членов, и в этом же источник проблем с размером (угол 6).

### Преобразования регистра и производные ключи

`Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize` встроены в компилятор — средствами самого языка типов их не выразить. В позиции ключа mapped type шаблон даёт производные имена:

```ts
type Events = { lessonOpened: { lessonId: string }; lessonFailed: { reason: string } };
type Listeners = { [K in keyof Events as `on${Capitalize<K & string>}`]: (p: Events[K]) => void };
// { onLessonOpened: (p: { lessonId: string }) => void; onLessonFailed: ... }
```

Список обработчиков выведен из набора событий; mapped types — материал 2.3. Граница этих четырёх типов видна сразу: регистр поднимается посимвольно (`Uppercase<'courseList'>` → `"COURSELIST"`), а преобразование сложнее требует рекурсивного разбора строки (угол 5).

### `infer` в шаблоне — кратко

Шаблонный тип работает и в обратную сторону — из строкового литерала можно вытащить часть:

```ts
type DomainOf<E> = E extends `app.${infer D}_${string}` ? D : never;
type X = DomainOf<'app.lesson_opened'>;   // "lesson"
```

Механизм условных типов и `infer` — 2.10; здесь достаточно узнавать конструкцию в типах библиотеки навигации или клиента данных.

## 3. Почему это важно

**До `satisfies` приходилось выбирать между проверкой и точностью вывода**, и выбор делался не по существу задачи, а по тому, какая из двух потерь казалась менее заметной.

Выбор в пользу проверки (`Record<string, Route>`) давал уверенность в форме значений и забирал имена: типизированный `navigate`, union идентификаторов и исчерпывающий `switch` по ключу работали со `string`, и опечатка превращалась из ошибки сборки в `undefined` в рантайме. Выбор в пользу точности (`as const`) давал имена и забирал проверку формы: карта из сорока записей, собранная за год четырьмя людьми, содержит записи с пропущенным и с переименованным полем, и каждая живёт до того момента, когда её кто-нибудь прочитает.

Отсюда вывод урока: литеральная карта чего бы то ни было — маршрутов, событий, цветов, ключей хранилища — описывается через `satisfies`, потому что аннотация стирает ровно то, ради чего карта существует. Template literal types — та же задача с другой стороны: множество допустимых строк описывается правилом, и проверка переносится из рантайма в компиляцию.

## 4. Где это в React Native

### Карта маршрутов и union имён экранов

Имя экрана передаётся в `navigate` из произвольного места, включая обработчик push-уведомления и разбор deep link.

```ts
const screens = {
  lessonList: { component: LessonListScreen, title: 'Уроки' },
  lesson:     { component: LessonScreen,     title: 'Урок' },
} satisfies Record<string, { component: ComponentType; title: string }>;

type ScreenName = keyof typeof screens;   // "lessonList" | "lesson"
```

Экран добавляется в одном месте, union обновляется сам. Параметры навигации и связь `ScreenName` с `ParamList` — 4.16.

### Карта событий аналитики

Цена ошибки максимальна, обратная связь минимальна. Воронка строится по `lesson_opened`, приложение отправляет `lesson_open`, событие не ломает ничего и просто не совпадает ни с чем — а через месяц это выглядит как «просадка конверсии», причину которой ищут в продукте.

```ts
type Payload = Record<string, string | number | boolean>;

const events = {
  lesson_opened:   { payload: { lessonId: '' }, critical: false },
  progress_synced: { payload: { items: 0 },     critical: false },
} satisfies Record<`${'lesson' | 'progress'}_${string}`, { payload: Payload; critical: boolean }>;

type EventName = keyof typeof events;
```

Шаблонный тип ограничивает форму имени (домен, подчёркивание, действие), `satisfies` проверяет форму описания и сохраняет имена, из которых выводится `EventName`; после этого `track(name: EventName, ...)` не принимает незнакомую строку. Слой аналитики и доставка — блок 10.

### Палитра темы и словарь переводов

Нужны обе вещи: проверка формата значения и точные имена, чтобы `theme.colors.sufrace` не компилировался.

```ts
const colors = { primary: '#3366ff', textMuted: '#8a8a8e' } as const satisfies Record<string, `#${string}`>;
type ColorName = keyof typeof colors;

const ru = { 'lesson.start': 'Начать урок' } satisfies Record<`${string}.${string}`, string>;
type TranslationKey = keyof typeof ru;
```

`as const` у палитры даёт литеральные значения, от которых можно строить производные типы. Шаблон `` `#${string}` `` отсекает `'rgba(0,0,0,.5)'` и забытое `'#'`, но полной проверкой формата не является — `'#zzz'` под него подходит: шаблонный тип описывает соглашение, а не синтаксис. `TranslationKey` даёт второй выигрыш: второй язык — это `Record<TranslationKey, string>`, и недостающий перевод становится ошибкой сборки.

### Ключи хранилища с префиксом

Ключи `AsyncStorage` живут в плоском пространстве имён, общем для приложения и всех его библиотек, и соглашение о префиксе обычно есть только в договорённости.

```ts
type StorageKey = `rnacademy:${'progress' | 'draft' | 'session'}`;
declare function read(key: StorageKey): Promise<string | null>;

read('rnacademy:prgoress');   // ошибка: нет такого хвоста
read('progress');             // ошибка: нет префикса
```

Тип описывает ключ, а не значение: то, что лежит по этому ключу, остаётся непроверенным — это граница системы (2.13), и `StorageKey` её не закрывает.

### Объект стилей вне `StyleSheet.create`

Случай, в котором все три варианта из угла 1 проявляются буквально.

```ts
const s1 = { row: { flexDirection: 'row' } };
// flexDirection → string; <View style={s1.row} /> — ошибка

const s2: Record<string, Record<string, unknown>> = { row: { flexDirection: 'row' } };
// форма не проверена, ключи стёрты: s2.rwo компилируется

const s3 = { row: { flexDirection: 'rowe' } } as const;   // ошибки нет до первого использования

const s4 = { row: { flexDirection: 'row' } } satisfies Record<string, ViewStyle>;   // проверено и то, и другое
```

Расширение `'row'` до `string` — самая частая причина сообщения «Type 'string' is not assignable to type 'FlexDirection | undefined'», и объясняется она не стилями, а widening (2.1). `satisfies` закрывает оба конца: `ViewStyle` работает контекстом, поэтому `'row'` не расширяется, `'rowe'` даёт ошибку на месте, а ключи остаются литеральными. Пропсы и `StyleProp<ViewStyle>` — 2.14.

## 5. Типичные ошибки

**`Record<string, X>` поверх литеральной карты.** Выглядит как аккуратная типизация. Причина — аннотация воспринимается как добавление информации, тогда как здесь она информацию **снимает**: вывод по литералу был точнее написанного типа. Признак: `keyof typeof` даёт `string`.

**`as` вместо `satisfies` и пропущенное лишнее поле.** `as Record<ColorName, string>` даёт на вид тот же результат и не проверяет ни лишнего ключа, ни недостающего; причина — смешение утверждения о типе с проверкой по типу. `palette.danger` при этом имеет тип `string` при `undefined` в рантайме — комбинация, при которой краш случается не в месте дефекта.

**`satisfies` как замена `as` с удивлением, что ошибка не исчезла.** Его механически подставляют на место `as` — в том числе там, где `as` подавлял ошибку в приведении значения с границы. `JSON.parse(raw) satisfies Lesson` даёт ошибку, потому что `unknown` под `Lesson` не подходит. Причина — ожидание, что это два варианта одной операции; это две разные операции, и ни одна не проверяет данные в рантайме (2.4, 2.12).

**Попытка выразить произвольное строковое преобразование типом.** Начинается с удачного `Capitalize`, продолжается попыткой перевести snake_case в camelCase или разобрать путь с параметрами. Часть этого выразима рекурсивными условными типами (2.10), но цена нелинейна: тип нечитаем, сообщения об ошибках непригодны для диагностики, а на длинной строке компилятор упирается в предел глубины инстанцирования. Причина — перенос привычек рантайм-кода в язык типов, где нет ни отладчика, ни `console.log`.

## 6. Trade-offs

### Большие объединения строковых литералов не бесплатны

Union литералов существует в компиляторе как перечень членов, и операции над ним линейны или хуже по их числу. Шаблон с несколькими подстановками даёт произведение: `` `${Domain}_${Action}_${Platform}` `` при десяти доменах, десяти действиях и трёх платформах — триста членов, а четвёртая подстановка — тысячи. Растёт время `tsc --noEmit` в CI и, что заметнее, время отклика подсказок в редакторе. Дорого именно **перечисление**: `` `${A}_${B}` `` разворачивается в произведение, `` `${A}_${string}` `` — нет.

Вторая часть цены — диагностика. Когда значение не подходит под union из двухсот литералов, компилятор печатает union целиком, и причина — одна опечатка в одном сегменте — в экране текста не выделена. Поэтому тип стоит дробить на именованные части: объявленный `type EventName = ...` даёт в ошибке имя, тот же шаблон по месту — развёрнутое произведение.

### Граница, за которой дешевле оставить `string`

- **множество значений не известно на момент сборки.** Фича-флаги из remote config, идентификаторы экспериментов, ключи с сервера — перечень меняется без пересборки, и нужна проверка в рантайме;
- **перечень меняется чаще, чем код, который его читает.** Сорок членов за квартал при неизменных местах чтения — не защита от ошибок, а обязательная правка во втором месте;
- **ошибка дешева и видна сразу.** Имя события в аналитике стоит дорого — отчёт молча врёт месяц; ключ в словаре отладочных подписей виден при первом запуске.

Компромисс в промежуточных случаях — шаблон с правилом вместо перечисления: `` `lesson_${string}` `` ловит отсутствующий префикс и перепутанный домен и не разворачивается в произведение.

### Типовая акробатика, которую не прочтёт следующий разработчик

Сам `satisfies` дёшев — одно слово в конце литерала. Дорого обходится то, что он делает возможным: из точного вывода соблазнительно построить цепочку, где union ключей порождает шаблонные имена, те — mapped type, тот — ещё один union. Дублирование уходит, но при ошибке в любом звене сообщение указывает на вершину цепочки, а разбираться приходится во всей.

Критерий: сколько времени займёт у человека, впервые открывшего файл, ответ на вопрос «какие значения здесь допустимы». Читается из объекта — конструкция оправдана. Нужно разворачивать четыре типа в IDE — дешевле перечислить значения руками.
