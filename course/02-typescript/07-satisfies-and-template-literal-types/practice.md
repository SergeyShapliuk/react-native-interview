# 2.7 `satisfies` и template literal types — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует сказать, **что именно каждая конструкция делает с проверкой и с выведенным типом**, а не пересказать синтаксис.

---

**1. Чем вывод типа ключей после `satisfies Record<string, Route>` отличается от вывода после аннотации тем же типом?**

<details>
<summary>Ответ</summary>

Аннотация делает `Record<string, Route>` типом переменной, поэтому ключей в типе не остаётся; `satisfies` использует тот же тип только как критерий проверки:

```ts
const a: Record<string, Route> = { lesson: { path: '/l', auth: true } };
type KA = keyof typeof a;   // string
a.lessson;                  // Route — компилируется, в рантайме undefined

const b = { lesson: { path: '/l', auth: true } } satisfies Record<string, Route>;
type KB = keyof typeof b;   // "lesson"
b.lessson;                  // ошибка: свойства lessson не существует
```

Проверка формы значений в обоих случаях одинаковая: запись без `auth` даст ошибку и там, и там. Различие ровно в одном — **кто определяет тип переменной**: при аннотации написанный тип, при `satisfies` — значение.

Практическое следствие важнее формулировки: всё, что дальше строится на `keyof typeof` — union имён экранов, union имён событий, исчерпывающий `switch` по ключу, — при аннотации работает со `string` и не проверяет ничего.

**Ответ «`satisfies` строже, он дополнительно проверяет ключи»** вскрывает подмену оси. `satisfies` не добавляет строгости к проверке значений — она в обоих случаях одна и та же; он **не отнимает** точность вывода. Проверяется вопросом «что даст `keyof typeof` в каждом варианте»: ответ про строгость вместо типа переменной означает, что аннотация здесь воспринимается как добавление информации, а не её потеря.

**Ответ «разницы нет, это разный синтаксис одного и того же»** вскрывает чтение `satisfies` как косметики. Проверяется одной строкой: обращение по опечатке компилируется в первом варианте и не компилируется во втором.

**Ответ «после `satisfies` значения тоже остаются литеральными»** вскрывает смешение `satisfies` с `as const`. Тип из `satisfies` работает как контекст для литерала, поэтому `path` выводится как `string` — ровно так, как он объявлен в `Route`. Литеральными значения останутся только под `as const satisfies Record<string, Route>`.

**Ответ «надо написать `Record<RouteName, Route>`»** отвечает на другой вопрос и при этом полезен: с конечным набором ключей аннотация действительно ловит опечатку. Цена — второй список имён, который расходится с картой; `satisfies` снимает именно это дублирование.
</details>

**2. Почему `as` не находит лишнее поле в объекте, а `satisfies` находит?**

<details>
<summary>Ответ</summary>

Это разные операции над выражением. `as` — утверждение о типе: требуется лишь, чтобы два типа были совместимы, а объект с лишним полем совместим с типом без этого поля. `satisfies` — проверка присваиваемости литерала целевому типу, и для литералов дополнительно работает excess property check: ключ, которого в целевом типе нет, считается ошибкой.

```ts
type ColorName = 'primary' | 'surface' | 'danger';

const x = { primary: '#1', surface: '#2', danger: '#3', sufrace: '#4' } as Record<ColorName, string>;
//  ошибки нет

const y = { primary: '#1', surface: '#2', danger: '#3', sufrace: '#4' } satisfies Record<ColorName, string>;
//  ошибка: 'sufrace' does not exist in type 'Record<ColorName, string>'
```

По той же причине `as` пропускает и **недостающее** поле: `{ primary: '#1' } as Record<ColorName, string>` компилируется, а `x.danger` имеет тип `string` при значении `undefined` в рантайме.

Обязательная оговорка: лишнее поле обнаруживается только тогда, когда у целевого типа **конечный набор ключей**. Под `satisfies Record<string, Route>` лишних ключей не существует по определению индексной подписи, и проверка работает уровнем глубже — внутри каждого значения, где `Route` набор ключей фиксирует.

**Ответ «`as` вообще ничего не проверяет»** вскрывает упрощение, которое ломается на практике. `as` проверяет совместимость: `'строка' as number` даст ошибку и потребует двойного приведения через `unknown`. Он не проверяет **лишнее и недостающее** — а это не то же самое, что «ничего», и именно этим объясняется молчание на опечатке в имени ключа.

**Ответ «`satisfies` проверяет строже, потому что он новее»** вскрывает отсутствие механизма за ответом. Проверяется вопросом «что будет, если тип справа — `Record<string, X>`»: при индексной подписи `satisfies` лишнее поле не найдёт, и объяснение через «строже» этого не предсказывает, а объяснение через конечный набор ключей — предсказывает.

**Ответ «надо включить строгие флаги, и `as` начнёт проверять»** вскрывает ожидание от `strict`, которого там нет: ни один флаг не превращает утверждение о типе в проверку — назначение `as` в том, чтобы проверка не выполнялась (2.4).

**Ответ «лишнее поле найдёт и аннотация»** верен и ведёт к вопросу 1: `const y: Record<ColorName, string> = {...}` тоже даст ошибку на `sufrace`, потому что excess property check — свойство присваивания литерала, а не `satisfies`. Разница между аннотацией и `satisfies` не в этой проверке, а в типе переменной.
</details>

**3. В какой момент объединение строковых литералов перестаёт окупаться и чем это заметно в работе?**

<details>
<summary>Ответ</summary>

Окупаемость заканчивается в одном из четырёх случаев, и ни один не формулируется через размер:

1. **множество значений не известно на момент сборки** — фича-флаги из remote config, идентификаторы экспериментов, ключи с сервера: перечень меняется без пересборки, и нужна проверка в рантайме;
2. **перечень меняется чаще, чем код, который его читает** — сорок новых членов за квартал при неизменных местах чтения не предотвращают ошибок, а добавляют обязательную правку во втором месте;
3. **ошибка дешева и видна сразу** — неизвестное имя события в аналитике стоит дорого (отчёт молча врёт месяц), а неизвестный ключ в словаре отладочных подписей виден при первом запуске;
4. **union перестал читаться человеком** — выведенный из выведенного, он документирующую функцию уже не выполняет, а цену продолжает брать.

Заметно это по трём симптомам, в порядке появления: **редактор начинает задумываться** (подсказка отвечает с задержкой — самый ранний и честный сигнал); **сообщения об ошибках становятся непригодными** (при двухстах членах причина лежит внутри экрана текста); **растёт время `tsc --noEmit` в CI** (диагностируется труднее всего: причина — один тип, а время измеряется у всей проверки).

Дорого при этом именно **перечисление**: `` `${Domain}_${Action}` `` разворачивается в декартово произведение, а шаблон с правилом — `` `lesson_${string}` `` — не разворачивается ни во что и продолжает ловить отсутствующий префикс и перепутанный домен.

**Ответ «когда членов становится больше сотни»** вскрывает число вместо критерия. Сто членов плоского union — это дёшево; шестьдесят членов, полученных произведением трёх подстановок внутри рекурсивного типа, могут быть дороже. Проверяется вопросом «чем вы это измерили»: честное измерение — время отклика подсказки и время `tsc`, а не длина перечня.

**Ответ «такие типы всегда лучше, чем `string`»** вскрывает отсутствие ответа о цене. Контрпример называется сразу: ключ, приходящий с сервера, типизировать литералами нельзя в принципе — тип соберётся, а соответствие реальности не проверит никто.

**Ответ «можно оставить `string` и проверять в рантайме, разницы нет»** вскрывает обратную крайность. Разница измерима: в компиляции ошибка стоит минуту разработчика, в рантайме — испорченный отчёт аналитики или краш у пользователя.
</details>

**4. Почему `as const satisfies T` нельзя записать как `satisfies T as const`, и что `as const` меняет в самой проверке?**

<details>
<summary>Ответ</summary>

`as const` применим только к литералу — объектному, массивному, строковому, числовому или булеву. После `satisfies` выражение литералом уже не является:

```ts
const routes = { lesson: { path: '/l', auth: true } } satisfies Record<string, Route> as const;
// ошибка: A 'const' assertion can only be applied to references to enum members,
// or string, number, boolean, array, or object literals
```

Правильный порядок читается слева направо: `as const` фиксирует литералы, затем `satisfies` сверяет полученное с типом.

В проверке меняется то, что она идёт по более узкому типу: все свойства становятся `readonly`, все значения — литеральными. Для свойств это безразлично (`readonly` у свойства не учитывается при присваивании), для массивов — нет:

```ts
type Config = { tabs: string[] };

const c1 = { tabs: ['lessons', 'progress'] } satisfies Config;             // ок
const c2 = { tabs: ['lessons', 'progress'] } as const satisfies Config;    // ошибка
// readonly ["lessons", "progress"] не присваивается string[]
```

Выход — либо описать тип как `readonly string[]`, либо снять `as const`: если из `tabs` выводится union имён табов, нужны литеральные элементы и `readonly` в типе; если `tabs` просто передаётся дальше, `as const` лишний.

**Ответ «`as const` обязателен вместе с `satisfies`, иначе точность теряется»** вскрывает смешение двух видов точности. Ключи остаются литеральными и без `as const` — их сохраняет сам `satisfies`; `as const` нужен для литеральных **значений**.

**Ответ «порядок не важен, компилятор разберётся»** проверяется попыткой это написать: вторая форма не компилируется, и сообщение называет причину прямо.

**Ответ «`as const` делает объект иммутабельным, поэтому его надо ставить последним»** вскрывает два заблуждения сразу: `as const` существует только при компиляции (2.1), а порядок определяется не иммутабельностью, а тем, что `as const` требует литерал в качестве операнда.
</details>

## Задание — карта событий аналитики с проверяемыми именами

**Дано.** Слой аналитики RN Academy: события описаны картой, карта приведена через `as`, имя события собирается конкатенацией в месте отправки.

```ts
type Payload = Record<string, string | number | boolean>;

type AnalyticsEvent = { payload: Payload; critical: boolean };

const events = {
  lesson_opened:    { payload: { lessonId: '' },                critical: false },
  lesson_completed: { payload: { lessonId: '', durationMs: 0 }, critical: true  },
  progress_synced:  { payload: { items: 0 },                    ciritcal: false },
} as Record<string, AnalyticsEvent>;

export function track(name: string, payload: Payload) {
  const meta = events[name];
  send(`app.${name}`, payload, meta.critical);
}
```

Дефекты, обнаруженные после релиза: событие `lesson_open` (без `ed`) отправлялось три недели и ни во что не попало в отчётах; на одном событии приложение падало с `Cannot read property 'critical' of undefined`; в описании `progress_synced` поле `critical` фактически отсутствует.

**Требуется.**

1. Назвать для каждого дефекта конструкцию, которая его допустила, и сказать, что именно она отключает.
2. Переписать карту так, чтобы форма каждого события проверялась типом, имена ключей оставались литеральными, а допустимая форма имени задавалась шаблонным типом — домен из закрытого перечня плюс действие. Union имён вывести из карты, а не объявлять рядом.
3. Собрать полное имя события (`app.<домен>_<действие>`) шаблонным типом и типизировать `track` так, чтобы незнакомое имя не компилировалось, а `events[name]` не требовал проверки на `undefined`.
4. Добавить событие с опечаткой в домене и событие с опечаткой в поле описания; для каждого сказать, в какой строке компилятор укажет на ошибку и что произошло бы в исходном варианте.

---

<details>
<summary>Разбор</summary>

**1. Что допустило каждый дефект.**

| Дефект | Конструкция | Что она отключает |
|---|---|---|
| `lesson_open` ушло в отчёты | `name: string` в сигнатуре `track` | проверку имени: любая строка допустима, перечень имён в типе не участвует |
| краш `of undefined` | `as Record<string, AnalyticsEvent>` | вывод ключей: тип говорит «любая строка → `AnalyticsEvent`», поэтому `events[name]` имеет тип `AnalyticsEvent`, а не `AnalyticsEvent \| undefined` |
| `critical` отсутствует у `progress_synced` | `as` вместо `satisfies` | excess property check: `ciritcal` — лишний ключ, `critical` — недостающий, и утверждение о типе не проверяет ни того, ни другого |

Все три — один и тот же выбор, сделанный трижды: тип задан вручную там, где значение было точнее. Третий дефект стоит отметить отдельно: `meta.critical` имеет тип `boolean`, а в рантайме там `undefined`, и `send` получает третьим аргументом `undefined` вместо `false` — не падение, а тихое изменение поведения.

С `noUncheckedIndexedAccess` второй дефект был бы виден и в исходном варианте: `events[name]` получил бы тип `AnalyticsEvent | undefined`. Флаг в `strict` не входит (2.8), и решение ниже от него не зависит.

**2. Карта.**

```ts
type Domain = 'lesson' | 'course' | 'progress';

type EventKey = `${Domain}_${string}`;

type AnalyticsEvent = { payload: Payload; critical: boolean };

const events = {
  lesson_opened:    { payload: { lessonId: '' },                critical: false },
  lesson_completed: { payload: { lessonId: '', durationMs: 0 }, critical: true  },
  progress_synced:  { payload: { items: 0 },                    critical: false },
} satisfies Record<EventKey, AnalyticsEvent>;

type EventName = keyof typeof events;
// "lesson_opened" | "lesson_completed" | "progress_synced"
```

Три решения, которые здесь приняты явно:

- **домен перечислен, действие — нет.** `` `${Domain}_${string}` `` ловит отсутствие домена (`opened` без префикса) и перепутанный домен (`lessonn_opened`), не разворачивается в произведение и не требует правки при добавлении действия. Перечислить и действия — строже и дороже, оправдано при закрытом наборе (угол 6 теории);
- **ключ карты — `EventKey`, а не `string`.** Из-за индексной подписи excess property check на верхнем уровне не работает, и неизвестный ключ отсекается самим шаблоном;
- **`EventName` выведен, а не объявлен** — второго списка имён в проекте нет, и расходиться нечему.

`as const` здесь не нужен: от карты требуются литеральные **имена**, а не значения; он сделал бы `critical` типом `false` вместо `boolean`.

**3. Полное имя и `track`.**

```ts
type FullEventName = `app.${EventName}`;
// "app.lesson_opened" | "app.lesson_completed" | "app.progress_synced"

export function track(name: EventName, payload: Payload) {
  const meta = events[name];          // AnalyticsEvent, без undefined
  const full: FullEventName = `app.${name}`;
  send(full, payload, meta.critical);
}

track('lesson_opened', { lessonId: 'l-1' });   // ок
track('lesson_open',   { lessonId: 'l-1' });   // ошибка в этой строке
```

Что изменилось:

- **имя проверяется на вызове** — ошибка указывает на строку, где опечатка сделана, а не где она проявилась;
- **`events[name]` не требует проверки.** Индексация идёт по `EventName`, равному набору ключей карты, поэтому результат — `AnalyticsEvent`: проверка на `undefined` не убрана вручную, а стала ненужной;
- **`` `app.${name}` `` типизируется шаблоном.** Компилятор выводит тип `` `app.${EventName}` ``, присваивание проходит без `as`, а опечатка в префиксе (`` `ap.${name}` ``) не скомпилируется.

Чего решение **не** делает: `payload` никак не связан с конкретным событием. Связь «имя события → форма нагрузки» выражается индексированным доступом и generic (`track<N extends EventName>(name: N, payload: typeof events[N]['payload'])`), но для этого нагрузку сначала нужно описать типом, а не примерным значением. Та же задача, что карта эндпоинтов в 2.11.

**4. Две опечатки и место ошибки.**

```ts
const events = {
  lesson_opened:    { payload: { lessonId: '' },                critical: false },
  lesson_completed: { payload: { lessonId: '', durationMs: 0 }, critical: true  },
  progress_synced:  { payload: { items: 0 },                    critical: false },

  lessonn_failed:   { payload: { reason: '' },                  critical: true  },
  //  ↑ ошибка на этой строке: ключ не подходит под `${Domain}_${string}`

  course_started:   { payload: { courseId: '' },                ciritcal: false },
  //                                                            ↑ ошибка здесь:
  //  'ciritcal' does not exist in type 'AnalyticsEvent' + отсутствует 'critical'
};
```

Разбор по строкам:

- **опечатка в домене (`lessonn_failed`).** Компилятор указывает на ключ в карте: `lessonn` в перечень доменов не входит, и такого ключа у `Record<EventKey, AnalyticsEvent>` быть не может. В исходном варианте ошибки не было бы ни здесь, ни на вызове `track('lessonn_failed', ...)` — имя имело тип `string`, событие уходило бы в аналитику и не совпадало ни с чем (первый дефект);
- **опечатка в поле описания (`ciritcal`).** Компилятор указывает на поле внутри значения, причём дважды: `ciritcal` — лишнее свойство, `critical` — недостающее обязательное. Это excess property check внутри значения, где `AnalyticsEvent` фиксирует набор ключей. В исходном варианте `as` молчал, и событие тихо перестало быть критическим (третий дефект).

Асимметрию стоит удержать: на верхнем уровне карту защищает **шаблонный тип ключа**, внутри значения — **проверка лишних свойств**. Если бы ключ был типизирован как `string`, первая опечатка прошла бы, а вторая — нет.

**Вклад в проект (P2).** В RN Academy появляется каталог идентификаторов уроков и имён событий прогресса с точными литеральными ключами: одно описание, из которого выводятся и union имён, и допустимые значения. Зафиксированы два правила проекта: литеральная карта (маршруты, события, цвета, ключи хранилища) описывается через `satisfies`, а не через аннотацию; строка, собираемая по соглашению, описывается шаблонным типом, а не держится в договорённости. Сети и аналитики на P2 ещё нет — есть контракт имён, который на P6 станет контрактом отправки, а в блоке 10 — контрактом слоя аналитики.
</details>
