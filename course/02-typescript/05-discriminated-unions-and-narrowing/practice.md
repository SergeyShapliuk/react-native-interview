# 2.5 Discriminated unions и narrowing — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **какие состояния тип разрешает**, а не пересказать синтаксис union.

---

**1. Сколько комбинаций допускают четыре булевых флага состояния экрана и сколько из них вы готовы описать словами?**

<details>
<summary>Ответ</summary>

Шестнадцать — но важно, что именно считается. Речь о **четырёх бинарных признаках**: загрузка идёт или нет, ошибка есть или нет, данные есть или нет, обновление идёт или нет. Два в четвёртой степени даёт шестнадцать.

Сами значения счётными не являются: `error: string | null` содержит `null` и неограниченное множество строк, `lessons: Lesson[] | null` — `null` и любой массив. Для разговора о состояниях экрана это неважно: текст ошибки не меняет того, в каком состоянии находится экран, поэтому значения группируются в два класса — «есть ошибка» и «нет ошибки», и ровно эта группировка даёт шестнадцать комбинаций.

Описать словами удаётся четыре-пять: начальное состояние, загрузка, данные есть, ошибка, обновление поверх данных. Остальные одиннадцать названия не имеют, и это не придирка к арифметике — у безымянного состояния нет и правила отображения. Что должен показать экран при `isLoading: true` и непустом `error`? Ответа нет ни в коде, ни в голове автора, поэтому поведение определяется порядком проверок в рендере: что проверено первым, то и покажется.

Отсюда вывод урока: **безымянные состояния не обрабатываются — они случаются.** Union из четырёх членов допускает четыре состояния и требует правила для каждого.

**Ответ «шестнадцать, но невозможные просто не возникают»** вскрывает веру в договорённость вместо проверки. Возникают они ровно тогда, когда состояние пишется из двух мест: запрос установил `isLoading`, параллельный ответ установил `error`, сброс загрузки не выполнился. Проверяется поиском по коду мест, которые пишут состояние: если их больше одного, согласованность нигде не гарантирована.

**Ответ «пять, остальные комбинации бессмысленны»** вскрывает подмену того, что разрешает тип, тем, что имел в виду автор. Компилятор не знает, какие комбинации осмысленны, и `isRefreshing: true` при `lessons: null` пропустит.

**Ответ «комбинаций неограниченно много, потому что `error` — строка»** формально верен и останавливается на арифметике вместо вывода. Да, значений у типа бесконечно много; вопрос не про них, а про состояния экрана, и для них различимы два класса ошибки. Признак того, что рассуждение ушло не туда: из него не следует ни одного решения о том, что показывать пользователю.
</details>

---

**2. При добавлении пятого варианта в union — где компилятор укажет на незакрытый случай, а где промолчит, и от чего это зависит?**

<details>
<summary>Ответ</summary>

Укажет там, где ветвление обязано вернуть значение или где есть проверка исчерпанности:

- `switch` с присваиванием `const exhaustive: never = state` в `default` — ошибка на этой строке;
- функция с объявленным возвращаемым типом и без `default` — новый член проходит мимо всех `case`, функция неявно возвращает `undefined`, объявленный `string` этого не допускает;
- обращение к полю, которого у нового члена нет: `state.lessons` перестаёт компилироваться, если `lessons` есть не у всех членов.

Промолчит там, где для нового члена есть куда провалиться:

- `switch` с содержательным `default`;
- цепочка `if` с финальным `else`;
- функция, возвращающая `void` или `ReactNode` без проверки исчерпанности — `undefined` подходит под оба;
- тернарник по одному значению: `state.status === 'error' ? ... : ...` — новый член попадёт во вторую ветку.

Зависимость одна: **есть ли у необработанного случая законный путь**. Если есть — компилятор не видит проблемы, потому что формально код корректен. Проверка исчерпанности существует именно для того, чтобы законного пути не было.

**Ответ «компилятор всегда укажет, union для этого и нужен»** вскрывает ожидание, которое не выполняется ровно в самом частом случае: `default: return <Spinner />` присутствует почти в каждом экране.

**Ответ «надо просто не писать `default`»** вскрывает рецепт вместо механизма. Отсутствие `default` помогает только при объявленном возвращаемом типе, который `undefined` не допускает; у функции, возвращающей `ReactNode`, это не сработает — `undefined` является допустимым `ReactNode`.

**Ответ «укажет в местах, где читаются поля нового члена»** путает направление. Компилятор укажет там, где читаются поля, которых у нового члена **нет**. Поля самого нового члена нигде не читаются — он же не обработан.
</details>

**3. Зачем в ветке `default` присваивать значение переменной типа `never`, если эта ветка никогда не выполняется?**

<details>
<summary>Ответ</summary>

Потому что эта строка — не рантайм-защита, а утверждение для компилятора, и работает она в момент компиляции, а не выполнения.

Пока все члены union обработаны в `case`, в `default` тип значения сужен до `never`: ни одного необработанного варианта не осталось. Присваивание `never` в `never` корректно. Как только в union появляется новый член, в `default` попадает его тип, и присваивание перестаёт компилироваться — компилятор сообщает об этом на той самой строке.

То есть переменная нужна не для того, чтобы что-то делать во время выполнения, а чтобы **превратить пропущенный вариант из тихого поведения в ошибку сборки**. Выполняется эта ветка действительно никогда, и именно в этом смысл: если она выполнилась, значит, в рантайм пришло значение, невозможное по типам, — и тогда разумно бросить исключение с самим значением в сообщении.

**Ответ «чтобы обработать невозможное значение»** вскрывает чтение приёма как защиты в рантайме. Проверяется вопросом «что эта строка делает после компиляции»: присваивание, которое ни на что не влияет, — весь эффект достигается при проверке типов.

**Ответ «это нужно, чтобы TypeScript не жаловался на отсутствие `return`»** вскрывает смешение двух разных приёмов. Проблему отсутствующего `return` решает объявленный возвращаемый тип; `never` решает другую задачу — обнаружение нового члена union.

**Ответ «можно вместо этого бросить исключение»** вскрывает потерю различия между моментами. `throw` в `default` не даёт ошибки компиляции: новый член тихо дойдёт до рантайма и свалится у пользователя. Правильная комбинация — присваивание в `never` для сборки и `throw` для рантайма, причём первое важнее.
</details>

**4. Почему дискриминантом не может быть поле типа `string` и что при этом перестаёт работать?**

<details>
<summary>Ответ</summary>

Поле типа `string` одинаково у всех членов union, поэтому по его значению компилятор не может выбрать член. Сравнение `state.status === 'success'` остаётся корректным выражением, но не сужает тип: после него доступны по-прежнему только общие для всех членов поля, а `state.lessons` не компилируется.

Дискриминант обязан быть **union литеральных типов**, у каждого члена своим: `'idle' | 'loading' | 'success' | 'error'`, причём у конкретного члена — ровно один литерал.

Самый частый способ случайно получить `string` — расширение типа (2.1): состояние собирается в объектном литерале без `as const`, значение берётся из переменной, объявленной через `let`, или приходит из внешних данных как `string`. Симптом при этом выглядит обманчиво: «TypeScript не видит поле `lessons`», и чинить начинают обращение, а не тип дискриминанта.

**Ответ «можно, просто придётся приводить тип»** вскрывает готовность лечить симптом утверждением. `as` вернёт доступ к полям и снимет единственную гарантию, ради которой union вводился (2.4).

**Ответ «дискриминант должен быть строковым литералом»** почти верен и упускает существенное: литерал не обязан быть строкой. Числовые литералы и `enum` работают так же. Существенно то, что тип конечен и у каждого члена своё значение.
</details>

## Задание — состояние экрана уроков: от флагов к union

**Дано.** Экран списка уроков RN Academy. Состояние хранится четырьмя значениями, экран ведёт себя странно в двух зафиксированных тестированием случаях: после ошибки обновления пропадают уже загруженные уроки, а при быстром повторном pull-to-refresh спиннер иногда не исчезает.

```ts
type LessonsScreenState = {
  isLoading: boolean;
  isRefreshing: boolean;
  error: string | null;
  lessons: Lesson[] | null;
};

const initial: LessonsScreenState = {
  isLoading: false,
  isRefreshing: false,
  error: null,
  lessons: null,
};

function render(state: LessonsScreenState) {
  if (state.isLoading) return <Spinner />;
  if (state.error !== null) return <ErrorView text={state.error} />;
  if (state.lessons === null) return <Empty />;
  return <List data={state.lessons} refreshing={state.isRefreshing} />;
}
```

**Требуется.**

1. Выписать все комбинации, которые этот тип разрешает, и отметить те, у которых нет названия. Для двух зафиксированных дефектов указать, какая именно комбинация их вызывает.
2. Перевести состояние в discriminated union. Назвать каждое состояние и разместить поля так, чтобы недоступные в данном состоянии данные были недоступны и в коде.
3. Выписать комбинации, которые после перевода перестали быть выразимыми. Для каждой сказать, случалась ли она в исходном коде и как проявлялась.
4. Переписать `render` и добавить проверку исчерпанности. Затем добавить в union пятое состояние — подгрузку следующей страницы — и показать, в каких строках компилятор потребует правки.

---

<details>
<summary>Разбор</summary>

**1. Что разрешает тип.** Шестнадцать комбинаций; названия есть у пяти.

| `isLoading` | `isRefreshing` | `error` | `lessons` | Название |
|---|---|---|---|---|
| нет | нет | нет | нет | начальное |
| да | нет | нет | нет | первая загрузка |
| нет | нет | есть | нет | ошибка первой загрузки |
| нет | нет | нет | есть | данные показаны |
| нет | да | нет | есть | обновление поверх данных |
| нет | нет | есть | есть | **без названия** — ошибка при наличии данных |
| да | да | — | — | **без названия** — загрузка и обновление одновременно |
| да | — | есть | — | **без названия** — загрузка при наличии ошибки |
| нет | да | — | нет | **без названия** — обновление того, чего нет |

Остальные комбинации — варианты перечисленных безымянных.

**Дефект первый: после ошибки обновления пропадают уроки.** Комбинация `error !== null` при непустом `lessons` — шестая строка таблицы. Сама комбинация корректно описывает реальность: данные есть, обновление не удалось. Но `render` проверяет `error` **раньше** `lessons`, поэтому показывает экран ошибки вместо списка со сообщением. Дефект не в обработчике ошибки, а в том, что у состояния «ошибка поверх данных» нет названия, и порядок проверок в рендере стал его неявным определением.

**Дефект второй: спиннер не исчезает при быстром повторном refresh.** Обработчики обновления в «Дано» не показаны, поэтому точную последовательность восстановить по коду нельзя — можно назвать механизм и типичную форму. Флаг `isRefreshing` пишут несколько асинхронных обработчиков независимо друг от друга: старт ставит `true`, успешный ответ — `false`. При двух быстрых обновлениях появляются ветки, где сброс легко потерять. Типичная: обработчик отбрасывает «устаревший» ответ первого запроса (чтобы он не затёр свежие данные) и вместе с ответом отбрасывает и сброс флага, а второй запрос завершается ошибкой, и ветка ошибки выставляет `error`, но не `isRefreshing: false`. После этого флаг остаётся `true`, и сбрасывать его некому. Причина не в порядке выполнения, а в форме состояния: флаг — независимое значение, которое пишут из нескольких мест, и ничто не требует, чтобы каждая ветка его закрыла.

**2. Union.**

```ts
type LessonsScreenState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'failed'; message: string; retry: () => void }
  | {
      status: 'ready';
      lessons: Lesson[];
      refresh: { state: 'idle' } | { state: 'running' } | { state: 'failed'; message: string };
    };

const initial: LessonsScreenState = { status: 'idle' };
```

Решения, которые union заставил принять явно:

- **`lessons` живёт только в `ready`.** В остальных состояниях данных нет, и поля тоже нет — проверки `lessons === null` исчезают из кода;
- **ошибка существует в двух разных смыслах.** `failed` — первая загрузка не удалась, показывать нечего. Ошибка обновления — это `ready` с `refresh.state === 'failed'`: данные есть, сообщение показывается поверх них. Именно это различие было безымянным и дало первый дефект;
- **`refresh` — вложенный union, а не флаг.** Обновление возможно только при наличии данных, и вложенность это фиксирует. Состояние «обновление того, чего нет» стало невыразимым. Второй дефект union устраняет не полностью, но делает заметным: каждый переход обязан построить состояние целиком, и ветка ошибки обновления должна явно написать `refresh: { state: 'failed', … }` — «забыть сбросить флаг» превращается в «не указать обязательное поле», а это ошибка компиляции. Отдельно остаётся гонка двух обновлений: какой из ответов главный, решает не тип, а логика отмены (7.10).

**3. Что перестало быть выразимым.**

| Комбинация | Случалась | Как проявлялась |
|---|---|---|
| ошибка при наличии данных как состояние ошибки | да | дефект первый: список пропадал при неудачном обновлении |
| обновление без данных | да | спиннер pull-to-refresh на пустом экране в момент до первой загрузки |
| загрузка и обновление одновременно | не наблюдалась | допускалась типом |
| обновление, которое некому закрыть (`isRefreshing: true` после завершения всех запросов) | да | дефект второй: несбрасываемый спиннер. Невыразимой union эту ситуацию не делает, но требует явного `refresh` в каждом переходе |
| загрузка при непустой ошибке | нет | не наблюдалась, но допускалась типом |
| данные есть и ошибка первой загрузки есть | нет | не наблюдалась |

Часть комбинаций в продакшене не встречалась. Это обычное соотношение: union убирает и наблюдавшиеся дефекты, и те, что ещё не случились.

**4. `render` с проверкой исчерпанности.**

```ts
function render(state: LessonsScreenState) {
  switch (state.status) {
    case 'idle':
      return <Empty />;
    case 'loading':
      return <Spinner />;
    case 'failed':
      return <ErrorView text={state.message} onRetry={state.retry} />;
    case 'ready':
      return (
        <List
          data={state.lessons}
          refreshing={state.refresh.state === 'running'}
          banner={state.refresh.state === 'failed' ? state.refresh.message : null}
        />
      );
    default: {
      const exhaustive: never = state;
      return exhaustive;
    }
  }
}
```

Порядок ветвей перестал быть значимым: каждое состояние обрабатывается по своему имени, а не по тому, какая проверка стоит раньше. Это и есть устранение первого дефекта — не правкой порядка `if`, а исчезновением условия, при котором порядок что-то решал.

**Добавляем пятое состояние.** Подгрузка следующей страницы возможна только при наличии данных, поэтому она не новый член верхнего union, а поле внутри `ready`:

```ts
| {
    status: 'ready';
    lessons: Lesson[];
    refresh: { state: 'idle' } | { state: 'running' } | { state: 'failed'; message: string };
    nextPage: { state: 'none' } | { state: 'loading'; page: number } | { state: 'failed'; page: number };
  }
```

Компилятор потребует правки в двух местах: там, где объект `ready` создаётся (новое поле обязательно — каждый переход в `ready` должен сказать, что с подгрузкой), и там, где `ready` собирается из предыдущего состояния частичным обновлением. В `render` ошибки не будет: новое поле просто не читается, список отрендерится без индикатора подгрузки. Это ограничение приёма, которое стоит знать: проверка исчерпанности ловит новый **член union**, а не новое **поле члена**.

Если же подгрузку сделать отдельным членом верхнего уровня — `{ status: 'loadingMore'; lessons: Lesson[]; page: number }` — компилятор укажет на `default` в `render`. Цена: `lessons` придётся дублировать в двух членах, и переход между ними должен их переносить. Выбор между двумя вариантами — это выбор между «подгрузка есть свойство состояния с данными» и «подгрузка есть отдельное состояние»; первый вариант точнее описывает экран, второй лучше поддержан компилятором.

**Вклад в проект (P2).** Состояние урока и состояние экрана уроков описаны как discriminated union — ключевой артефакт стадии P2: именно здесь невозможное состояние перестаёт компилироваться. Зафиксировано правило проекта: состояние экрана описывается union'ом, а не набором булевых флагов, и каждое состояние имеет имя. Переходы между этими состояниями — уже тема React: механика `useReducer`, где тот же union становится типом состояния редьюсера, разбирается в 3.8.
