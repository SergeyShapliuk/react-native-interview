# 2.5 Discriminated unions и narrowing — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что такое union» — а на вопрос, **как описать состояние так, чтобы невозможная комбинация не компилировалась**.

---

## 1. Что это

**Discriminated union (дискриминированное объединение)** — union объектных типов, у которых есть общее поле с литеральным типом, и у каждого члена значение этого поля своё.

**Discriminant (дискриминант)** — это самое поле. Его значение однозначно указывает, каким именно членом union является значение.

```ts
type ScreenState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; lessons: Lesson[] }
  | { status: 'error'; message: string };
```

Сравните с тем, как то же состояние обычно выглядит в коде экрана:

```ts
type ScreenStateFlags = {
  isLoading: boolean;
  error: string | null;
  lessons: Lesson[] | null;
  isRefreshing: boolean;
};
```

Второй тип описывает **шестнадцать** комбинаций четырёх флагов. Осмысленны из них четыре-пять. Остальные одиннадцать не запрещены ничем: `isLoading` вместе с `error`, `error` вместе с `lessons`, `isRefreshing` без `lessons`. Они возникают не по решению разработчика, а по невнимательности — и выглядят как баг отображения, хотя причина в типе.

Первый тип описывает ровно четыре состояния, и пятого способа существовать у него нет.

### Ключевая формулировка урока

> **Дискриминант переводит состояние из набора независимых значений в перечень названных вариантов. Невыразимое состояние не нуждается в проверке.**

---

## 2. Как это работает

### Сужение по дискриминанту

Механизм — тот же анализ потока управления, что в 2.4. Новое здесь то, что сужает **одно сравнение с литералом**, и сужает сразу до конкретного члена union со всеми его полями:

```ts
function render(state: ScreenState) {
  if (state.status === 'success') {
    return <List data={state.lessons} />;   // lessons доступен
  }
  if (state.status === 'error') {
    return <Error text={state.message} />;  // message доступен, lessons — нет
  }
  return <Spinner />;
}
```

Обратите внимание на то, чего в этом коде нет: проверок `lessons !== null` и `error !== null`. Поле `lessons` существует только в том члене union, где данные действительно есть, поэтому защитная проверка не нужна — не потому, что о ней договорились, а потому, что в остальных ветках к этому полю нет доступа.

### Почему дискриминант обязан быть литералом

Сужение работает тогда, когда по значению поля компилятор способен отличить члены union друг от друга. Литеральный тип это позволяет: `'success'` принадлежит ровно одному члену.

`boolean` в роли дискриминанта работает только для union из двух членов и ломается на третьем:

```ts
type Bad =
  | { ok: true; data: Lesson[] }
  | { ok: false; message: string };   // пока работает: true и false различимы
```

Добавить третий вариант — «обновление поверх данных» — в эту схему уже нельзя: третьего значения у `boolean` нет, и приходится заводить второй флаг, то есть возвращаться к комбинациям.

`string` в роли дискриминанта не сужает вообще: поле типа `string` одинаково у всех членов, и компилятор не может по нему выбрать ветку. Дискриминант должен быть **union литералов**, а не `string`. Это частая ошибка при вынесении типа в переменную без `as const` (2.1): литерал расширяется до `string`, и сужение молча перестаёт работать.

### Проверка исчерпанности через `never`

**Exhaustiveness check (проверка исчерпанности)** — приём, при котором компилятор сообщает о необработанном члене union. Опирается на свойство `never`: значению типа `never` нельзя присвоить ничего.

```ts
function label(state: ScreenState): string {
  switch (state.status) {
    case 'idle':     return 'Готово к загрузке';
    case 'loading':  return 'Загрузка';
    case 'success':  return `Уроков: ${state.lessons.length}`;
    case 'error':    return state.message;
    default: {
      const exhaustive: never = state;   // ошибка, если член не обработан
      return exhaustive;
    }
  }
}
```

Пока все члены обработаны, в `default` тип `state` сужен до `never`, и присваивание корректно. Стоит добавить в union пятый член — `{ status: 'refreshing'; lessons: Lesson[] }` — и в `default` окажется тип `{ status: 'refreshing'; ... }`, который в `never` не присваивается. Компилятор укажет на эту строку.

Ценность приёма не в самой проверке, а в моменте, когда она срабатывает: **при добавлении варианта**. Без неё новый вариант молча попадает в `default`, и экран ведёт себя как при `idle` — без ошибки, без предупреждения, без следа в отчётах.

Тот же результат даёт аннотация возвращаемого типа у функции без `default`: если обработаны не все члены, функция неявно вернёт `undefined`, и объявленный `string` этого не допустит. Приём с `never` надёжнее, потому что работает и для функций, которые ничего не возвращают.

### Сужение в обе стороны

Дискриминант сужает не только тип по значению, но и значение по типу. После проверки поля компилятор знает состав объекта; после проверки состава — знает значение дискриминанта:

```ts
if ('message' in state) {
  state.status;   // 'error' — других членов с полем message нет
}
```

На практике полезнее первый вариант: он читается как перечень состояний, а не как проверка формы.

## 3. Почему это важно

Набор флагов и union описывают одну и ту же предметную область, но решают разные задачи. Флаги описывают **что известно о состоянии**: загружается ли, есть ли ошибка, есть ли данные. Union описывает **в каком состоянии находится экран**. Разница проявляется в том, кто обязан следить за согласованностью.

С флагами согласованность — договорённость между всеми местами, которые пишут состояние. Каждое место обязано помнить: при установке ошибки сбросить загрузку, при успехе сбросить ошибку, при обновлении не трогать данные. Договорённость нигде не записана, не проверяется и нарушается при добавлении пятого флага.

С union согласованность — свойство типа. Перейти в состояние ошибки, не выйдя из состояния загрузки, невозможно: это одно поле, у него одно значение.

Отсюда практическая польза, которая обычно и становится заметной первой: **union заставляет назвать состояния, которые при флагах появлялись сами**. Самый частый пример — «обновление поверх имеющихся данных». При флагах оно возникает как `isRefreshing: true` вместе с непустым `lessons` и выглядит случайным. При переводе в union его приходится либо назвать отдельным членом, либо отвергнуть — и это уже решение, а не побочный эффект.

## 4. Где это в React Native

### Состояние экрана

Канонический случай, и в RN он сложнее веб-варианта: к `idle / loading / success / error` почти всегда добавляются pull-to-refresh и подгрузка следующей страницы.

```ts
type LessonsState =
  | { status: 'loading' }
  | { status: 'error'; message: string; retry: () => void }
  | { status: 'ready'; lessons: Lesson[]; refreshing: boolean; nextPage: number | null };
```

Здесь важно решение, которое union делает явным: `refreshing` и `nextPage` живут **внутри** `ready`, а не рядом с ним. Обновление и подгрузка возможны только тогда, когда данные уже есть, и такая вложенность это фиксирует. При флагах это правило существовало бы в голове автора.

### Результат операции

Вместо пары «данные и ошибка», где оба поля опциональны:

```ts
type SubmitResult =
  | { type: 'ok'; lessonId: string }
  | { type: 'validation'; fields: Record<string, string> }
  | { type: 'network' }
  | { type: 'conflict'; serverVersion: number };
```

Вызывающий обязан разобрать варианты, и компилятор напомнит о появившемся `conflict`, когда бэкенд его добавит. Политика retry и классификация сетевых ошибок — предмет 7.3; здесь только форма результата.

### Разрешения

Результат запроса разрешения в RN — не булево, а union из нескольких состояний. У `react-native-permissions` их пять: `unavailable` (функции нет на устройстве), `denied` (можно спросить снова), `blocked` (пользователь запретил навсегда, диалог больше не покажется), `limited` (частичный доступ — например, выбранные фото на iOS) и `granted`. У встроенного `PermissionsAndroid` свой набор: `granted`, `denied`, `never_ask_again`. Булев флаг `isGranted` стирает разницу, которая определяет поведение: при `denied` имеет смысл объяснить и спросить снова, при `blocked` — только отправить в настройки системы, при `limited` — работать с тем, что разрешено, и предложить расширить доступ, при `unavailable` — скрыть функцию. Здесь же виден смысл проверки исчерпанности: код, написанный под три состояния, после добавления `limited` в новой версии iOS молча отнесёт его к `default` — а `never` в `default` превратит это в ошибку сборки. Платформенные различия и сам механизм permissions — блок 09.

### События нативного emitter'а

Поток событий от нативного модуля — естественный дискриминированный union: событие несёт поле `type`, и состав остальных полей зависит от него. Типизация такого потока union'ом даёт `switch` с проверкой исчерпанности, который перестанет компилироваться, когда модуль научится присылать новый тип события.

### Варианты пропсов компонента

Компонент, у которого часть пропсов имеет смысл только в одном режиме, описывается union'ом пропсов, а не набором опциональных полей:

```ts
type BannerProps =
  | { kind: 'info'; text: string }
  | { kind: 'progress'; text: string; percent: number }
  | { kind: 'action'; text: string; onPress: () => void; actionLabel: string };
```

`<Banner kind="info" percent={50} />` перестаёт компилироваться, а `percent` внутри ветки `progress` доступен без проверки на `undefined`. Типизация пропсов целиком — урок 2.14.

## 5. Типичные ошибки

**Union без общего поля.** `type State = Loading | Success | Error`, где у членов нет дискриминанта, а различаются они составом полей. Сужение приходится делать через `'lessons' in state`, что работает, но читается как проверка формы и ломается, когда два члена получают одинаковое поле. Причина ошибки — union воспринимается как «просто `|`», а дискриминант как необязательное украшение.

**`default`, молча проглатывающий новый вариант.** `default: return <Spinner />` выглядит как разумная защита и является главным способом обезвредить union: новый член попадает в `default`, компилятор молчит, экран показывает спиннер вечно. Либо `default` отсутствует, либо в нём стоит присваивание в `never`.

**Дискриминант, продублированный в двух местах.** Поле `status` в типе и отдельный `isLoading` рядом, оставленный «для совместимости». Два источника истины расходятся на первой же правке, и проверки в коде начинают опираться то на один, то на другой.

**Дискриминант типа `string`.** Возникает при выносе значения в переменную или при сборке состояния из внешних данных без `as const`: литерал расширяется до `string`, сужение пропадает, и ошибка выглядит как «TypeScript не видит поле», хотя причина в расширении типа (2.1).

**Четыре флага, оставленные как есть, но с типом сверху.** `type State = { isLoading: boolean; error: string | null; ... }` — тип есть, проверок компилятора по-прежнему нет. Это самый частый итог «мы типизировали экран»: аннотация добавлена, невозможные комбинации остались выразимыми.

**Опциональные поля вместо членов union.** `{ status: Status; lessons?: Lesson[]; message?: string }` — один объект с необязательными полями. Компилятор не связывает `status === 'success'` с наличием `lessons`, поэтому `state.lessons!.length` или `?.` остаются в каждом месте чтения. Связь между дискриминантом и составом полей существует только тогда, когда члены union — отдельные типы.

## 6. Trade-offs

### К данным нельзя обратиться без сужения

Это и есть цель, и это же — цена. Код чтения становится длиннее: вместо `state.lessons?.length` появляется ветвление по `status`. На экране с тремя местами чтения разница заметна, и первая реакция — «с флагами было короче». Короче было потому, что проверки не выполнялись вовсе: `?.` — не проверка состояния, а способ не упасть.

### Рефакторинг задевает каждое место чтения

Перевод существующего экрана с флагов на union — правка во всех местах, которые читают состояние, и обычно это десятки строк в нескольких файлах. Цена платится один раз, и компилятор при этом работает за вас: каждое неперенесённое место перестаёт компилироваться. Но оценивать работу надо честно — это не «добавить поле», а переписать чтение состояния.

### Дискриминант занимает место и добавляет косвенность

В сетевых структурах лишнее поле — байты в каждом элементе списка. Для внутреннего состояния это неважно, для формата обмена может иметь значение, и тогда дискриминант появляется на границе при разборе ответа, а не приходит с сервера.

Вторая часть цены — чтение: чтобы понять, какие поля доступны, нужно сопоставить значение дискриминанта с членом union. При трёх-четырёх членах это дешевле проверок на `null`, при двенадцати — union стоит разбить.

### Искусственный дискриминант

Там, где естественного различающего поля нет, дискриминант приходится вводить специально. Иногда это точное описание домена, иногда — лишний слой, появившийся ради типизации. Признак второго случая: значение дискриминанта нигде не используется, кроме `switch`, который его же и разбирает, а поля у всех членов одинаковые. Тогда union не нужен, достаточно одного типа.
