# 2.10 Conditional types и `infer` — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует **выполнить вычисление компилятора по шагам**, а не вспомнить правило.

---

**1. Почему `T extends string ? A : B` на union `string | number` возвращает union, а не одну ветку?**

<details>
<summary>Ответ</summary>

Потому что условный тип над **голым параметром типа** дистрибутивен: компилятор не проверяет union целиком, а раскладывает его по членам, вычисляет условие для каждого и объединяет результаты.

```ts
type Pick1<T> = T extends string ? 'строка' : 'не строка';

type R = Pick1<string | number>;
// шаг 1: Pick1<string> → 'строка'
// шаг 2: Pick1<number> → 'не строка'
// результат: 'строка' | 'не строка'
```

Условие при этом ни разу не проверялось для `string | number` как целого — такой проверки не было вообще.

Два практических следствия. Первое: `never` в одной из ветвей растворяется, потому что union с `never` равен union без него, — именно так работает `NonNullable`. Второе: `T[]` в ветке даёт `string[] | number[]`, а не `(string | number)[]`, и это разные типы: во второй можно положить и строку, и число, в первый — только однородный массив.

**Ответ «потому что `string | number` присваиваем к `string` частично»** вскрывает модель «условие проверяется один раз с каким-то промежуточным результатом». Частичной присваиваемости не существует: `string | number` к `string` не присваиваем, и будь условие проверено целиком, результат был бы `B`. Проверяется записью `[T] extends [string]` — она даст именно `B`.

**Ответ «дистрибутивность — свойство union»** вскрывает отнесение свойства не к тому участнику. Свойство принадлежит **позиции проверяемого типа**: голый параметр распределяет, выражение с параметром — нет. Один и тот же union в `[T] extends [string]` не распределяется.

**Ответ «так удобнее, TypeScript оптимизирует»** вскрывает отсутствие механизма в модели. Это не оптимизация, а определение: распределение по union закреплено как поведение условного типа над голым параметром, и от него зависит устройство встроенных утилит.
</details>

---

**2. Как запретить дистрибутивность и в каком случае это необходимо?**

<details>
<summary>Ответ</summary>

Обернуть обе стороны условия в кортеж из одного элемента: `[T] extends [U] ? A : B`. Параметр перестаёт быть голым, распределение не включается, условие проверяется для union целиком.

Необходимо это тогда, когда вопрос задан **про union как целое**:

```ts
// является ли T в точности never
type IsNever<T> = [T] extends [never] ? true : false;

type N1 = IsNever<never>;          // true
type N2 = IsNever<string>;         // false

// без кортежа результат бессмысленный
type Broken<T> = T extends never ? true : false;
type N3 = Broken<never>;           // never — ни одного члена для распределения
```

`Broken<never>` даёт `never`, а не `true`: распределять по пустому union нечего, поэтому результатов нет вовсе. Это самый наглядный случай, где дистрибутивность мешает.

Другие случаи той же природы: «содержит ли `T` только строки» (`[T] extends [string]`), «равны ли `T` и `U` с точностью до взаимной присваиваемости», «является ли `T` union'ом из более чем одного члена».

Обратную ошибку делают чаще: кортеж ставят по образцу, не разобравшись, и тип, который должен был разложиться по членам, обрабатывает union целиком. Такой дефект не даёт ошибки компиляции — он даёт другой результат, и проявляется на union из двух членов, а не на примере из одного.

**Ответ «обернуть в кортеж — это хак, есть способ лучше»** вскрывает отношение к приёму как к обходу. Приём стандартный, именно он используется в стандартной библиотеке и в типах популярных библиотек; альтернативы для той же задачи нет.

**Ответ «можно добавить ограничение `T extends unknown`»** вскрывает смешение ограничения параметра с проверкой в условии. Ограничение не влияет на распределение; более того, `T extends unknown ? ... : ...` — распространённый приём, чтобы распределение **включить** принудительно.
</details>

**3. В каких позициях допустим `infer` и что он делает с выводом, когда совпадений несколько?**

<details>
<summary>Ответ</summary>

`infer` допустим только внутри `extends`-условия условного типа, и только в позиции, которую компилятор умеет сопоставлять с проверяемым типом:

```ts
type E<T> = T extends Array<infer X> ? X : never;                  // аргумент дженерика
type R<T> = T extends (...a: never[]) => infer X ? X : never;      // возвращаемый тип
type P<T> = T extends (...a: infer X) => unknown ? X : never;      // список параметров
type H<T> = T extends [infer X, ...unknown[]] ? X : never;         // элемент кортежа
type S<T> = T extends `lesson_${infer X}` ? X : never;             // часть шаблона
```

Когда одна и та же переменная сопоставляется в нескольких местах, результат зависит от позиции:

- **ковариантные позиции** (возвращаемый тип, элемент массива, несколько членов union) — кандидаты, как правило, **объединяются** в union;
- **контравариантные позиции** (параметры функции) — кандидаты **пересекаются**.

Это рабочая модель для типичных случаев, а не полный алгоритм: вывод зависит ещё и от контекста, структуры сигнатуры, перегрузок и ограничений параметров типа. Проверять результат нужно у компилятора, а не вычислять по правилу.

```ts
type Ret<T> = T extends { a(): infer X; b(): infer X } ? X : never;
type U = Ret<{ a(): string; b(): number }>;      // string | number

type Arg<T> = T extends { a(x: infer X): void; b(x: infer X): void } ? X : never;
type I = Arg<{ a(x: string): void; b(x: number): void }>;   // string & number → never
```

Второй результат — `never`, и это не поломка, а следствие того, что функция, принимающая и `string`, и `number` в одной позиции, должна принимать значение, являющееся и тем, и другим.

Практическое правило: **одна переменная `infer` на одну позицию**; для разбора нескольких частей структуры объявляются разные переменные.

**Ответ «`infer` можно поставить где угодно в типе»** вскрывает модель `infer` как объявления переменной. Вне условного типа он не компилируется, а внутри — работает лишь там, где есть что сопоставлять.

**Ответ «при нескольких совпадениях берётся первое»** вскрывает модель «первый выигрывает», перенесённую из сопоставления с образцом в других языках. Проверяется примером выше: `string | number` вместо `string`.

**Ответ «несколько `infer` с одним именем — это ошибка»** неверен: такая запись допустима и имеет определённое поведение. Ошибкой было бы считать её эквивалентной одному совпадению.
</details>

**4. Почему для приложения этот урок полезнее в чтении, чем в письме?**

<details>
<summary>Ответ</summary>

Потому что условные типы в приложении почти всегда приходят извне, а не пишутся внутри.

Типы, с которыми RN-разработчик сталкивается ежедневно, построены на вычислениях: тип `route.params` выводится из `ParamList`, тип данных в клиенте — из функции-загрузчика через `Awaited<ReturnType<...>>`, тип из схемы валидации — вычислениями, которые библиотека выполняет при объявлении каждого узла схемы. Ни одно из этих вычислений разработчик не писал, и все три участвуют в сообщениях об ошибках, которые он читает.

Когда параметры экрана переданы неверно, компилятор печатает не «не тот объект», а результат вычисления: имя условного типа, подставленные аргументы, цепочку инстанцирований. Дальше два пути. Прочитать — и исправить причину. Не прочитать — и либо править код наугад до исчезновения ошибки, либо поставить `as`, то есть вернуть приложение в состояние из 2.4, где ошибка подавлена, а несоответствие осталось.

Письмо своих условных типов в коде экранов почти всегда означает, что задача решается не там: форма данных выводится вычислением, хотя её можно описать один раз на границе. Три случая, где писать оправдано, перечислены в угле 6 теории: обёртка над библиотекой, API-слой (2.11), схема (2.12).

**Ответ «такие типы нужны только авторам библиотек»** вскрывает ровно то заблуждение, против которого ставится вопрос: пользователю библиотеки они достаются в сообщениях об ошибках, и уметь читать их обязательно.

**Ответ «в приложении они не нужны вообще»** вскрывает пропущенный API-слой. Там вывод типа ответа из описания эндпоинта убирает второе описание той же формы, и это рабочее применение.
</details>

## Задание — прочитать типизацию навигации по шагам

**Дано.** Упрощённая до сути типизация навигации, повторяющая то, что делает библиотека.

```ts
type RootParamList = {
  CourseList: undefined;
  Lesson: { lessonId: string };
  Progress: { courseId: string; from?: 'push' | 'deeplink' };
};

type ScreenName = keyof RootParamList;

type NavigateArgs<Name extends ScreenName> =
  RootParamList[Name] extends undefined
    ? [screen: Name]
    : [screen: Name, params: RootParamList[Name]];

declare function navigate<Name extends ScreenName>(...args: NavigateArgs<Name>): void;

declare function useRoute<Name extends ScreenName>(): {
  name: Name;
  params: RootParamList[Name];
};
```

**Требуется.**

1. Вычислить `NavigateArgs<'CourseList'>`, `NavigateArgs<'Lesson'>` и `NavigateArgs<ScreenName>` — по шагам, с подстановкой. Для третьего объяснить результат через дистрибутивность.
2. Для каждого из четырёх вызовов ниже сказать, компилируется он или нет, и какое вычисление даёт этот ответ:

```ts
navigate('CourseList');
navigate('Lesson');
navigate('Progress', { courseId: '7' });
navigate('Lesson', { lessonId: 1 });
```

3. Объяснить построчно, что означает сообщение компилятора на последнем вызове, и сказать, какая его часть указывает на причину, а какая — на следствие.
4. Заменить условный тип в `NavigateArgs` на решение без условных типов. Сравнить два варианта по трём критериям: что ломается при добавлении экрана, какое сообщение об ошибке получает вызывающий, сколько описаний приходится поддерживать.

---

<details>
<summary>Разбор</summary>

**1. Вычисления.**

`NavigateArgs<'CourseList'>`:

```
RootParamList['CourseList']           → undefined
undefined extends undefined ? ... :   → истина
результат: [screen: 'CourseList']
```

`NavigateArgs<'Lesson'>`:

```
RootParamList['Lesson']                        → { lessonId: string }
{ lessonId: string } extends undefined ? ... : → ложь
результат: [screen: 'Lesson', params: { lessonId: string }]
```

`NavigateArgs<ScreenName>` — здесь включается дистрибутивность, но **не там, где её ожидают**. Проверяемый тип — `RootParamList[Name]`, то есть выражение с параметром, а не голый параметр. Однако `Name` внутри него подставляется как union, и `RootParamList['CourseList' | 'Lesson' | 'Progress']` даёт union значений: `undefined | { lessonId: string } | { courseId: string; from?: ... }`.

Условие проверяется для этого union целиком (голого параметра в позиции проверки нет), union к `undefined` не присваиваем, поэтому:

```
результат: [screen: ScreenName, params: undefined | { lessonId: string } | { courseId: string; from?: ... }]
```

Практический вывод из третьего вычисления важнее первых двух: **тип, вычисленный для union имён, слабее типа, вычисленного для конкретного имени**. Пока имя экрана известно литералом, проверка точная; стоит передать в `navigate` переменную типа `ScreenName`, и проверка превращается в «любые параметры любого экрана». Отсюда требование `as const` или литерала в месте вызова (2.1) — иначе типизация навигации тихо вырождается.

**2. Четыре вызова.**

| Вызов | Результат | Вычисление |
|---|---|---|
| `navigate('CourseList')` | компилируется | `Name` выведен как `'CourseList'`, кортеж — `[screen]`, передан один аргумент |
| `navigate('Lesson')` | **ошибка** | кортеж — `[screen, params]`, то есть ожидается два аргумента, передан один |
| `navigate('Progress', { courseId: '7' })` | компилируется | `from` необязателен, остальное совпадает |
| `navigate('Lesson', { lessonId: 1 })` | **ошибка** | кортеж верный, несовпадение внутри `params`: `number` не присваиваем к `string` |

Существенно, что вторая и четвёртая ошибки — **разного рода**: одна про количество аргументов (результат выбора ветки условного типа), другая про присваиваемость внутри параметра (результат подстановки `RootParamList[Name]`). Сообщения у них тоже разные, и различить их — первый шаг чтения.

**3. Чтение сообщения.**

Сообщение на `navigate('Lesson', { lessonId: 1 })` имеет такую структуру:

```
Argument of type '{ lessonId: number; }' is not assignable to
  parameter of type '{ lessonId: string; }'.        ← следствие: что не подошло
  Types of property 'lessonId' are incompatible.    ← сужение до поля
    Type 'number' is not assignable to type 'string'.  ← причина
```

Читается снизу вверх. Нижняя строка — причина: `number` вместо `string`. Средняя указывает, где именно: поле `lessonId`. Верхняя — следствие: целиком объект не подошёл к параметру.

Если бы `Name` не вывелся в литерал — например, имя экрана пришло переменной типа `string` — сообщение было бы другим и про другое: ошибка возникла бы на первом аргументе, потому что `string` не присваиваем к `ScreenName`. Это второй признак, по которому различаются два класса проблем: **ошибка на первом аргументе означает, что не определилось имя экрана, ошибка на втором — что не совпали параметры**.

Важное практическое замечание: в реальной библиотеке к этим строкам добавляется цепочка инстанцирований условных типов, иногда на десяток строк. Структура чтения не меняется — причина всё равно внизу.

**4. Вариант без условных типов.**

```ts
declare function navigate<Name extends ScreenNameWithoutParams>(screen: Name): void;
declare function navigate<Name extends ScreenNameWithParams>(
  screen: Name,
  params: RootParamList[Name],
): void;

type ScreenNameWithoutParams = 'CourseList';
type ScreenNameWithParams = 'Lesson' | 'Progress';
```

Сравнение по трём критериям:

| Критерий | Условный тип | Две перегрузки и два списка |
|---|---|---|
| Добавление экрана | ничего, кроме `RootParamList`: ветка вычислится сама | нужно вручную добавить имя в один из двух списков; забыли — экран не вызывается либо вызывается без проверки параметров, ошибки нет |
| Сообщение вызывающему | про количество аргументов, с цепочкой инстанцирований; требует чтения | «No overload matches this call» плюс перечисление перегрузок — короче, но не указывает, какая ближе |
| Поддержка | одно описание (`RootParamList`) | три описания: `RootParamList` и два списка имён, расходящиеся молча |

Условный тип здесь оправдан по критерию из теории: **дублирование плохо, когда описания расходятся молча**, и ровно это происходит со списками имён. Добавили экран с параметрами, забыли внести в `ScreenNameWithParams` — компилятор не скажет ничего, а вызов перестанет проверяться.

Это и есть граница применимости темы: вычисление уместно там, где оно пишется один раз в библиотеке или в своём слое навигации, а используется в каждом экране. В коде самого экрана условным типам делать нечего.

**Чего разбор сознательно не делает.** Не трогает вложенные навигаторы, union экранов из нескольких навигаторов и типизацию `navigation.navigate` внутри вложенного стека — реальная типизация библиотеки разбирается в 4.16. Не обсуждает, что делать с параметрами, пришедшими по deep link: они формируются вне приложения, и тип о них ничего не гарантирует — это граница из 2.13, и закрывается она проверкой, а не вычислением.
