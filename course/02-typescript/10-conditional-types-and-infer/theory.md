# 2.10 Conditional types и `infer` — theory

> 🔴 SENIOR. Семь углов разбора. Урок отвечает не на вопрос «как написать условный тип» — а на вопрос, **как прочитать чужой условный тип по сообщению об ошибке и когда писать свой дешевле, чем продублировать описание**.

---

## 1. Что это

**Conditional type (условный тип)** — выражение `T extends U ? A : B`, вычисляемое компилятором: если `T` присваиваем к `U`, результат `A`, иначе `B`.

```ts
type IsString<T> = T extends string ? true : false;

type A = IsString<'lesson'>;   // true
type B = IsString<number>;     // false
```

`extends` здесь означает «присваиваем к», а не «наследует». Это то же значение, что в ограничении параметра типа (2.2), но в другой роли: там оно требование, здесь — проверка.

**`infer`** — объявление переменной типа внутри условия, значение которой компилятор выводит из сопоставления:

```ts
type ElementOf<T> = T extends Array<infer E> ? E : never;

type L = ElementOf<Lesson[]>;   // Lesson
type N = ElementOf<string>;     // never
```

**Distributive conditional type (дистрибутивный условный тип)** — условный тип над **голым параметром**, который применяется к каждому члену union по отдельности, а результаты собираются в union.

### Ключевая формулировка урока

> **Условный тип — это вычисление, которое выполняет компилятор. Для RN-разработчика ценность этого урока в первую очередь в чтении чужих вычислений: сообщение об ошибке при неверных параметрах экрана есть результат такого вычисления, и прочитать его — единственная альтернатива правке наугад.**

---

## 2. Как это работает

### Дистрибутивность

Главная неочевидность темы. Условный тип над union не проверяет union целиком — он раскладывается по членам:

```ts
type ToArray<T> = T extends unknown ? T[] : never;

type R = ToArray<string | number>;
// не (string | number)[], а string[] | number[]
```

Компилятор подставил сначала `string`, потом `number`, и объединил результаты. Отсюда поведение, которое выглядит ошибкой, пока не знаешь механизма:

```ts
type NonNullableOwn<T> = T extends null | undefined ? never : T;

type X = NonNullableOwn<string | null>;
// string — ветка never для null просто исчезла из union
```

`never` в union растворяется, потому что union с `never` равен union без него. Именно так устроен встроенный `NonNullable`.

Дистрибутивность включается при одном условии: **проверяемый тип — голый параметр**, то есть `T`, а не выражение с ним. Обернули параметр — дистрибутивность выключилась:

```ts
type IsUnionOfStrings<T> = [T] extends [string] ? true : false;

type Y1 = IsUnionOfStrings<'a' | 'b'>;      // true — проверен весь union
type Y2 = IsUnionOfStrings<'a' | number>;   // false
```

Запись `[T] extends [U]` — приём с кортежем из одного элемента, стандартный способ отключить распределение. Он необходим там, где вопрос задан про union как целое: «является ли `T` в точности `never`», «содержит ли `T` только строки», «равны ли `T` и `U`».

Обратная сторона: потеря дистрибутивности там, где она была нужна, — тихий дефект. Тип компилируется, результат отличается, и обнаруживается это на конкретном union из двух членов, а не на тестовом примере из одного.

### Где допустим `infer`

`infer` объявляется только внутри `extends`-условия условного типа и только в позиции, которую компилятор способен сопоставить: элемент массива, аргумент дженерика, параметр или возвращаемый тип функции, часть кортежа, часть шаблонного литерального типа.

```ts
type Ret<T> = T extends (...args: never[]) => infer R ? R : never;
type Params<T> = T extends (...args: infer P) => unknown ? P : never;
type Awaited1<T> = T extends Promise<infer V> ? V : T;
type Head<T> = T extends [infer H, ...unknown[]] ? H : never;
type Suffix<S> = S extends `lesson_${infer Rest}` ? Rest : never;
```

Когда совпадений несколько, результат зависит от позиции. В ковариантных позициях — например, несколько элементов union — компилятор объединяет кандидатов в union; в контравариантных (параметры функции) — пересекает. Отсюда практическое правило: **одна переменная `infer` на одну позицию**, а для разбора нескольких частей — несколько переменных.

### Из чего собраны встроенные утилиты

Полезно один раз увидеть, что в стандартной библиотеке нет магии:

```ts
type MyReturnType<T extends (...a: never[]) => unknown> =
  T extends (...a: never[]) => infer R ? R : never;

type MyNonNullable<T> = T extends null | undefined ? never : T;

type MyAwaited<T> =
  T extends Promise<infer V> ? MyAwaited<V> : T;   // рекурсия разворачивает вложенные Promise
```

`Awaited` рекурсивен именно потому, что `Promise<Promise<T>>` в рантайме разворачивается до `T`, и тип обязан вести себя так же.

### Рекурсия и предел глубины

Условный тип может ссылаться на себя, и это основной способ обработать вложенную структуру:

```ts
type DeepReadonly<T> = T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T;
```

У рекурсии есть предел: компилятор прекращает работу с ошибкой «Type instantiation is excessively deep and possibly infinite». Предел существует для защиты от незавершающихся вычислений, и упираются в него обычно не глубиной данных, а случайной бесконечностью — типом, который на каждом шаге не уменьшается.

Практический признак опасного типа: рекурсия по структуре, у которой нет гарантированного дна. `DeepReadonly` над типом с циклической ссылкой (`type Node = { parent: Node }`) компилятор обрабатывает за счёт отложенного вычисления, а вот рекурсия, накапливающая кортеж на каждом шаге, упирается в предел быстро.

### Почему это становится нечитаемым

Условные типы комбинируются, и выражение из четырёх уровней вложенности читается хуже любого рантайм-кода: нет промежуточных значений, нет отладчика, нет имён. Два приёма, которые это смягчают:

- **именовать шаги.** Вместо одного типа из четырёх вложенных условий — три именованных типа по шагу. Проверка не ускорится, но ошибка укажет на имя;
- **читать сообщение снизу вверх.** Компилятор обычно печатает цепочку инстанцирований, и нижние строки ближе к причине, чем верхние.

## 3. Почему это важно

Для большинства RN-разработчиков ценность этого урока — **чтение**, а не письмо. Свои условные типы в продуктовом коде приложения появляются редко и чаще всего неоправданно. Чужие — ежедневно, потому что на них построены типы библиотек, которыми приложение пользуется:

- тип `route.params` для конкретного экрана выводится из `ParamList` условным типом;
- тип ключа запроса и тип данных в клиенте данных связаны вычислением;
- тип, выведенный из схемы валидации (2.12), — результат рекурсивного условного типа.

Когда разработчик передаёт неверные параметры экрана, компилятор печатает не «ты передал не то», а результат вычисления: имя условного типа, подставленные аргументы, несовпавшую ветку. Разработчик, не умеющий это прочитать, делает одно из двух — правит код наугад до исчезновения ошибки или ставит `as`, то есть возвращает приложение в состояние из 2.4: ошибка подавлена, несоответствие осталось.

Отсюда и уровень урока. Это 🔴 не из-за сложности синтаксиса, а потому, что решение «читать и понять» против «подавить и забыть» — решение об архитектуре доверия в приложении, и принимается оно каждый раз заново.

## 4. Где это в React Native

### Параметры экрана из `ParamList`

Упрощённая версия того, что делает библиотека навигации:

```ts
type RootParamList = {
  CourseList: undefined;
  Lesson: { lessonId: string };
};

type ScreenParams<Name extends keyof RootParamList> = RootParamList[Name];

type NavigateArgs<Name extends keyof RootParamList> =
  ScreenParams<Name> extends undefined
    ? [screen: Name]                          // параметров нет — второй аргумент запрещён
    : [screen: Name, params: ScreenParams<Name>];

declare function navigate<Name extends keyof RootParamList>(
  ...args: NavigateArgs<Name>
): void;

navigate('CourseList');                       // ок
navigate('Lesson', { lessonId: '1' });        // ок
navigate('Lesson');                           // ошибка: ожидалось 2 аргумента
navigate('CourseList', { lessonId: '1' });    // ошибка: ожидался 1 аргумент
```

Условный тип здесь решает задачу, которую иначе решают двумя перегрузками и ручным списком экранов без параметров. Сообщение об ошибке в последних двух строках — про количество аргументов, и чтобы понять, почему оно такое, нужно знать, что кортеж аргументов вычислен из `ParamList`.

Полная версия в библиотеке сложнее: учитывает вложенные навигаторы, необязательные параметры и union экранов. Разбор реальной типизации навигации — 4.16.

### Типы, выведенные из схемы

Схема валидации — объект, из которого тип данных выводится рекурсивным условным типом: `Infer<typeof lessonSchema>` обходит описание и собирает форму. Это наиболее полезное применение темы для приложения, и оно разбирается в 2.12; здесь важно, что сообщение «тип не присваиваем» при несоответствии схемы и использования — результат такого обхода, и читается он снизу вверх.

### Клиенты данных

Типизированный клиент связывает ключ запроса с типом данных: по ключу вычисляется тип функции-загрузчика, по загрузчику — тип результата через `Awaited<ReturnType<...>>`. Отсюда частое сообщение об ошибке, в котором упомянут `Awaited` — тип, который разработчик не писал.

### Собственные контракты нативных модулей

Для своего нативного модуля условный тип оправдан там, где метод возвращает разное в зависимости от аргумента: тип результата вычисляется из литерала, переданного первым параметром. Контракты нативных модулей — блок 09.

## 5. Типичные ошибки

**Сложный тип вместо простого дублирования.** Самая дорогая ошибка темы. Тип на четыре условия, который выводит форму из другой формы, экономит десять строк описания и добавляет: время проверки, нечитаемые сообщения об ошибках, зависимость всего кода от правильности этого вычисления и невозможность для коллеги его изменить. Причина — вывод типа из типа ощущается как более инженерное решение, чем написать два похожих типа рядом.

Критерий, который работает: **дублирование плохо, когда два описания расходятся молча**. Если расхождение немедленно даёт ошибку компиляции, дублирование безопасно и дешевле вычисления.

**Потеря дистрибутивности.** `[T] extends [U]` поставлено по образцу из статьи, без понимания — и тип, который должен был разложиться по членам union, обрабатывает union целиком. Тихий дефект: компилируется, результат другой.

**Лишняя дистрибутивность.** Обратный случай: вопрос задан про union целиком, а голый параметр разложил его по членам, и ответ получен для каждого члена отдельно. Классический пример — попытка проверить «является ли `T` типом `never`»: `T extends never ? true : false` на `never` даёт `never`, потому что распределение по пустому union не даёт ни одного результата. Корректно только `[T] extends [never] ? true : false`.

**Тип, который компилируется минуту.** Рекурсия по большой структуре, перебор union из сотен литералов, цепочка условий внутри mapped type. Обнаруживается не сразу: сначала IDE начинает подвисать на этом файле, и только потом замедляется проверка в CI. Диагностируется встроенной диагностикой компилятора по времени проверки, а не чтением кода.

**`infer` в позиции, где он не выводится.** Компилятор не сопоставляет произвольные выражения: `infer` в позиции результата вычисления или в типе, который сам является условным, даёт `unknown` или `never` вместо ожидаемого. Симптом — тип «работает», но выводит `unknown`, и дальше `unknown` расползается по вызывающему коду.

**Чтение сообщения сверху вниз.** Не ошибка типов, а ошибка работы: верхние строки сообщения описывают внешнее несоответствие, нижние — причину. Привычка читать с начала приводит к правке внешнего кода вместо устранения причины.

## 6. Trade-offs

### Вывод типа из типа убирает дублирование и оплачивается читаемостью

Один источник вместо двух описаний — реальная выгода: добавление поля в одном месте отражается везде. Цена платится не автором, а читателем: чтобы понять, какой тип получится, нужно выполнить вычисление в голове. На типе из одного условия это секунда, на типе из четырёх — задача.

Отсюда правило соотношения: условный тип оправдан, когда его **пишут один раз, а используют много**. Библиотека — да; экран приложения — почти никогда.

### Время проверки — реальная цена

Условные типы вычисляются при каждой проверке. На проекте из нескольких сотен файлов цепочка условий внутри часто используемого типа ощутимо увеличивает время проверки в CI и отзывчивость IDE. Измеряется это диагностикой компилятора, а не оценивается на глаз, и до измерения утверждать замедление не стоит.

### Сообщения об ошибках становятся хуже для всех

Тип, собранный вычислениями, компилятор печатает телом, а не именем (2.6). Ошибка в месте использования показывает развёрнутый результат вычисления — иногда на десятки строк. Это задевает не автора типа, а каждого, кто им пользуется, и смягчается только именованием промежуточных шагов.

### Граница применимости

Для приложения разумная граница такая: читать условные типы обязательно, писать — в трёх случаях. Первый: своя обёртка над библиотекой, где типы уже вычисляются и нужно их пронести. Второй: API-слой, где тип ответа выводится из описания эндпоинта (2.11). Третий: схема, из которой выводится тип (2.12). Во всех остальных случаях вопрос «а если просто описать это вторым типом» заслуживает честного ответа.
