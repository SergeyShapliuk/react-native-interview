# 2.8 `strict: true` по флагам — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что такое `strict: true`» — а на вопрос, **какую проверку включает каждый флаг, какой класс дефектов она ловит и чем за неё платят на живом проекте**.

---

## 1. Что это

`strict` — не уровень строгости и не отдельная проверка. Это **имя для набора независимых флагов**: `"strict": true` включает каждый, `false` — выключает каждый. Проверки между собой не связаны: срабатывают на разном коде, дают разные сообщения, требуют разных правок. Почти все флаги набора меняют то, **что компилируется**; `alwaysStrict` — то, **что генерируется**. Состав набора от версии к версии пополняется, поэтому опираться стоит не на его размер, а на вывод `tsc --showConfig` в своём проекте.

### Ключевая формулировка урока

> **`strict` — это не одна настройка, а набор независимых проверок. Включается не `strict`, а каждая проверка по отдельности: у каждой свой класс дефектов, своя цена и своё место в плане.**

### `noImplicitAny`

Значение, тип которого не выведен и не аннотирован, получает `any` неявно — с флагом это ошибка. Аннотаций везде флаг не требует: где тип приходит из контекста, она по-прежнему не нужна (2.1).

```ts
function byTitle(lesson) { return lesson.title; }   // ошибка: тип взять неоткуда
lessons.map(lesson => lesson.title);                // не ошибка: тип из сигнатуры map
```

**Ловит** остров без проверок внутри типизированного кода: неявный `any` распространяется, и один неаннотированный параметр в середине обработки данных отключает проверки до конца цепочки. **Болит** количеством однотипных ошибок, а опаснее то, что механическая правка легко делается как `(lesson: any)`: флаг формально включён, неявный `any` заменён явным.

### `strictNullChecks`

Без флага `null` и `undefined` присваиваются значению любого типа: `const title: string = null` компилируется. С флагом они входят в тип только явно, через union, и обращение без сужения не компилируется.

```ts
function label(lesson: Lesson | null) {
  return lesson.title;   // 'lesson' is possibly 'null'
}
```

**Ловит** обращение к отсутствующему значению — самый частый рантайм-отказ в JS-приложении. Без флага аннотация `title: string` фактически означает `string | null | undefined`.

**Болит** сильнее всех: это единственный флаг набора, который меняет **код, а не аннотации**. В каждом месте нужно решить, что делать при отсутствии значения — заглушка, значение по умолчанию, не рендерить, ошибка, — и таких мест сотни. Вторая часть цены: флаг меняет и **вывод** типов (`lessons.find(...)` становится `Lesson | undefined`), поэтому ошибки появляются и там, где нет ни одной аннотации.

### `strictFunctionTypes`

Совместимость функциональных типов. Без флага параметры сравниваются в обе стороны (bivariance), с флагом — **контравариантно**: подходит функция, принимающая тип шире ожидаемого, а не уже.

```ts
type Handler = (event: ScreenEvent) => void;   // ScreenEvent = Opened | Finished
const onFinished = (event: Finished) => markDone(event.lessonId);

const handler: Handler = onFinished;   // ошибка: Opened не присваивается Finished
```

`handler` обещает принимать любое `ScreenEvent`, а `onFinished` читает поля, которых у `Opened` нет. Исключение, из-за которого флаг кажется неработающим: правило **не применяется к параметрам методов**, объявленных сокращённым синтаксисом (`interface X { on(h: Handler): void }`) — они остались бивариантными ради совместимости с типами стандартной библиотеки.

**Ловит** колбэк, подписанный на событие, вариантов которого он не умеет обрабатывать; в RN это обработчик под один тип события emitter'а, присвоенный туда, где принимается union. **Болит** не количеством, а тем, что каждая ошибка требует решения: расширить параметр до union и разобрать варианты (2.5) либо признать тип места подписки слишком широким.

### Четыре дешёвых флага набора

Эти четыре на RN-проекте дают единицы ошибок или ноль, и откладывать их незачем.

| Флаг | Что проверяет | Класс дефектов | Что болит |
|---|---|---|---|
| `strictBindCallApply` | аргументы `bind`, `call`, `apply` по сигнатуре целевой функции (без флага они `any[]`) | неверный аргумент при косвенном вызове | ничего: единицы ошибок, чаще в классовых компонентах с `this.handler.bind(this)` |
| `strictPropertyInitialization` | поле класса, в тип которого не входит `undefined`, получает значение в объявлении или в конструкторе; работает только вместе с `strictNullChecks` | поле читается до того, как было записано — типично при инициализации в `init()` | в типичном RN-коде почти ничего: классов мало. Заметен там, где есть классы-сервисы: клиент API, обёртка над хранилищем или нативным модулем |
| `noImplicitThis` | `this` в функции, для которой его тип не выводится (без флага он `any`) | код, который о контексте вызова только предполагает (1.16); саму потерю контекста в рантайме флаг не обнаруживает | мало: лечится стрелочной функцией или параметром `this: T` в сигнатуре |
| `alwaysStrict` | файлы разбираются в strict mode языка, в вывод `tsc` добавляется `"use strict"`; системы типов не касается | конструкции, запрещённые strict mode (`with`, повторные имена параметров, восьмеричные литералы) | практически ничего — но и защиты в рантайме он в RN не даёт: JavaScript для бандла генерирует не `tsc`, а Babel, и пресет RN намеренно не добавляет `"use strict"` (1.16). Флаг меняет то, что проверяет компилятор, а не то, как код исполняется на устройстве |

У `strictPropertyInitialization` законных выходов три: инициализация значением, тип `Lesson[] | undefined` с проверками при чтении или `lessons!: Lesson[]` — последнее является утверждением и отменяет проверку.

> **Не дублировать:** механика `this`, правила определения контекста вызова и потеря контекста при передаче метода — [1.16](../../01-javascript/16-this/). Здесь — только то, что запрещает флаг.

### `useUnknownInCatchVariables`

Тип переменной в `catch`: без флага `any`, с флагом `unknown`.

```ts
try { await api.fetchLessons(); }
catch (error) { showToast(error.message); }   // 'error' is of type 'unknown'
```

Правка — сужение, то есть материал 2.4. Отказаться точечно можно аннотацией `catch (error: any)`: она допустима и видна в ревью, в отличие от глобального выключения флага.

**Ловит** обработчик, предполагающий форму ошибки, которая не гарантирована: в `catch` попадает `Error`, объект отказа от библиотеки, строка, `undefined` из `Promise.reject()`. Чтение `message` у значения без `message` даёт `undefined` в тосте — или второе исключение внутри обработчика ошибки, уже без обработчика. **Болит** в каждом `catch`, где читается хоть одно поле; чинится однообразно, но требует общего решения — обычно появляется одна функция `toErrorMessage(error: unknown): string`.

> **Не дублировать:** `unknown`, предикаты `x is T` и assertion functions — [2.4](../04-unknown-type-guards-assertions/); `try/catch` с `await` и непойманные rejection'ы — [1.11](../../01-javascript/11-error-handling/).

### Строгие флаги вне `strict`

В набор они не входят по общей причине: включение любого по умолчанию сломало бы компиляцию у слишком большой доли существующих проектов.

| Флаг | Что проверяет | Что ловит |
|---|---|---|
| `noUncheckedIndexedAccess` | доступ по индексу и по ключу индексной сигнатуры даёт `T \| undefined` | индекс за границей, отсутствующий ключ, `[0]` у пустого массива |
| `exactOptionalPropertyTypes` | `{ title?: string }` не допускает явного `{ title: undefined }` | частичное обновление, где `undefined` означает «не менять»; расхождение «ключа нет» и «ключ со значением `undefined`» |
| `noImplicitReturns` | если значение возвращается в одной ветке, то во всех | забытую ветку в `if`/`switch` |
| `noFallthroughCasesInSwitch` | `case` без `break`/`return`, кроме пустого | провал в следующую ветку при вставке нового `case` |
| `noPropertyAccessFromIndexSignature` | требует `obj['key']` вместо `obj.key` для типа с индексной сигнатурой | чтение по ключу, существование которого не гарантировано, замаскированное под обычное поле: скобки делают неуверенность видимой в коде |
| `noImplicitOverride` | переопределение метода базового класса требует `override` | переопределение метода, переименованного в базовом классе |
| `noUnusedLocals` / `noUnusedParameters` | неиспользуемую переменную или параметр | след незаконченной правки |

Главный из них для RN — `noUncheckedIndexedAccess`: он закрывает реальный класс падений (угол 4) и даёт больше всего ошибок. Его цена в том, что флаг **не учитывает проверку длины**: `if (i < lessons.length) lessons[i].title` всё равно ошибка, потому что связь между `length` и индексом компилятору недоступна.

Включать стоит ещё `noImplicitReturns` и `noFallthroughCasesInSwitch`: они почти бесплатны, а второй полезен там, где есть `switch` по дискриминанту (2.5). `exactOptionalPropertyTypes` и `noPropertyAccessFromIndexSignature` — по месту: первый оправдан там, где есть частичные обновления и сериализация, второй — там, где есть конфигурация с индексной сигнатурой. `noImplicitOverride`, как и `strictPropertyInitialization`, в коде на хуках почти не встречается.

Дороже пользы — `noUnusedLocals`: это ошибка **сборки** на том, что по сути замечание стиля, и закомментированная на минуту строка ломает `tsc`. Та же проверка есть в линтере, где даёт предупреждение и правится автоматически; там ей место.

## 2. Как это работает

### Где живут флаги и как они складываются

Флаги задаются в `compilerOptions` файла `tsconfig.json`, который может наследоваться через `extends` — путь к файлу или имя пакета:

```json
{
  "extends": "<базовый конфиг платформы>",
  "compilerOptions": {
    "strict": false,
    "noImplicitAny": true,
    "strictNullChecks": true
  }
}
```

Имя пакета с базовым конфигом в `extends` зависит от версии React Native и от того, чем создан проект, поэтому здесь оно не приводится: смотреть нужно в свой `tsconfig.json`, а итоговый набор флагов — в вывод `tsc --showConfig`.

Правило сложения: **свои `compilerOptions` переопределяют унаследованные по каждому ключу отдельно**. Отсюда два факта.

Первый: `strict` — обычный ключ и комбинируется с отдельными флагами в любую сторону. Можно выключить набор и включить две проверки, как выше, а можно включить набор и выключить одну: `{ "strict": true, "strictPropertyInitialization": false }`. Явно указанный флаг сильнее `strict` независимо от порядка ключей в файле.

Второй: конфигурация RN-проекта почти всегда унаследована, поэтому **состав флагов нельзя прочитать из своего `tsconfig.json`**. Действующий набор печатает `tsc --showConfig`, и это первое, что делается перед планированием.

### Что флаг делает с системой типов

Флаги не «добавляют предупреждения» — каждый меняет правило, по которому компилятор отвечает на вопрос «присваивается ли A в B». `strictNullChecks` убирает `null` и `undefined` из состава всех типов, кроме `any`, `unknown` и union'ов, где они написаны явно; это меняет и проверки, и вывод. `strictFunctionTypes` меняет сравнение параметров с бивариантного на контравариантное. `noImplicitAny` и `noImplicitThis` отношение присваивания не меняют: они запрещают молча подставлять `any`.

Отсюда разный характер ошибок: `strictNullChecks` даёт их в коде, которого никто не трогал, а `noImplicitAny` — только там, где не написана аннотация.

### Подавление: `@ts-expect-error` против `@ts-ignore`

Обе директивы подавляют ошибки в следующей строке. Разница в том, что происходит, **когда ошибка исчезает**. `// @ts-ignore` молчит всегда: библиотека обновила типы, код переписан — директива осталась и продолжает подавлять уже другие, новые ошибки в той же строке. `// @ts-expect-error` требует, чтобы ошибка была, и как только проблема исчезла, сам становится ошибкой («Unused '@ts-expect-error' directive»). То есть `@ts-expect-error` — проверяемое утверждение «здесь ошибка, и я знаю почему», а `@ts-ignore` — глушитель: подавления первого вида вычищаются из проекта по сигналу компилятора, второго — живут годами.

Обе требуют комментария с причиной рядом: без него через полгода нельзя решить, можно ли их снимать.

### `skipLibCheck` и чужие типы

`skipLibCheck: true` отключает проверку типов **внутри** `.d.ts`-файлов — своих и из `node_modules`. В базовых конфигах он обычно включён, и это оправдано: в проекте с десятками зависимостей всегда найдутся два пакета с конфликтующими декларациями, а ошибка в чужом файле не говорит ничего о своём коде. Проверка в местах **использования** библиотеки работает по-прежнему — чужие типы не превращаются в `any`, — поэтому цена низкая. Неточные типы библиотек — урок 2.9.

### Где проверка выполняется

Здесь нужно разделить две разные стадии, которые часто сливают в одну.

**Транспиляция.** Metro превращает TypeScript в JavaScript, **удаляя** типы, и не выполняет проверку: с точки зрения сборщика аннотации — синтаксис, который нужно стереть. Поэтому приложение с ошибками типов собирается, запускается и работает.

**Проверка типов.** Это отдельная стадия, и выполняет её `tsc --noEmit`. В сборку Metro она не входит, но в проекте обычно присутствует — скриптом `npm run typecheck`, хуком перед пушем, шагом CI. То есть неверно и «RN-сборка проверяет типы», и «в RN-проекте типы не проверяются никогда»: проверка есть ровно там, где её поставили явно.

```
Metro          →  транспиляция, типы удаляются, проверки нет
tsc --noEmit   →  отдельная стадия проверки, запускается сама по себе
```

Отсюда три точки проверки: **IDE** — быстрее всех, но видит открытые файлы; **`tsc --noEmit` локально** — единственный способ узнать реальное число ошибок; **`tsc --noEmit` в CI** — единственная точка, которая что-то гарантирует, потому что первые две зависят от того, запустил ли их человек.

> **Не дублировать:** Metro, трансформация и сборка — блок 04; `tsc --noEmit` как шаг пайплайна, кэширование и порядок шагов — блок 10.

### Почему `strict: false` с точечным включением — рабочая стратегия

Из трёх свойств механизма — флаги независимы, конфигурация складывается по ключам, подавление точечное — следует стратегия: держать `strict: false` и включать флаги по одному, каждый отдельным изменением, после того как предыдущий доведён до нуля ошибок. Это не компромисс и не «неполная строгость», а единственный способ, при котором каждая правка имеет понятный смысл: при одном включённом флаге все ошибки одного класса, и решение по ним принимается одно, а не тридцать разных.

> **Не дублировать:** миграция JS → TS как процесс — организация работы, порядок файлов, параллельные продуктовые задачи, код, который правят другие, — урок 8.7. Здесь только порядок включения флагов и его обоснование.

## 3. Почему это важно

Вопрос «включён ли у вас `strict`» не имеет содержания, и ответ «да» не говорит почти ничего. Содержание имеют два других: **какие проверки включены** и **что сделано с кодом, который их не прошёл**.

Первый — это разница между «тип написан» и «тип проверяется». При выключенном `strictNullChecks` аннотация `title: string` означает `string | null | undefined`: самая частая аннотация в проекте не утверждает того, что в ней написано.

Второй вопрос важнее. Флаг, включённый за счёт расстановки `!` и `as`, формально включён и не ловит ничего: `lesson!.title` — утверждение «здесь не `null`», которое компилятор принимает на слово, то есть ровно то, от чего флаг должен был защищать. Проект в таком состоянии хуже проекта с выключенным флагом: ошибок нет, строгость объявлена, гарантии нет, и причина не видна в `tsconfig.json`.

Отсюда третье: флаг — это **торг между классом дефектов и объёмом работы**, и торговать можно только по одному флагу за раз. `strictNullChecks` ловит самый частый рантайм-отказ и стоит недели; `alwaysStrict` не ловит почти ничего и стоит ноль; `noUncheckedIndexedAccess` ловит падения на пустых списках и делает код со списками многословным. «Включить `strict`» эти три решения не принимает, а смешивает.

## 4. Где это в React Native

### Базовый конфиг

RN-проект наследует конфигурацию компилятора от базового конфига платформы и обычно не задаёт её сам. В этом базовом конфиге `strict` чаще всего уже включён, вместе с `skipLibCheck` и настройками JSX, модулей и `lib`. Проверять нужно в своём проекте — `tsc --showConfig` — по двум причинам: версии базового конфига различаются, а в проекте, прошедшем миграцию с JS, `strict` часто выключен локальным файлом поверх базового. Для нового проекта это значит, что `strict` включён с первой строки кода и речь идёт только о второй группе флагов; для существующего — что сначала надо узнать, что включено на самом деле.

### `noUncheckedIndexedAccess` и доступ по индексу в списках

```ts
function renderItem({ index }: { index: number }) {
  const lesson = data[index];            // Lesson | undefined
  return <Row title={lesson.title} />;   // ошибка
}
```

Это не придирка компилятора. `renderItem` с индексом, разошедшимся с данными, — реальный случай: список перерисовывается после замены данных более коротким массивом, индекс сохранился от предыдущего рендера, падение выглядит как «undefined is not an object» без понятной причины. Тот же флаг вскрывает ещё две привычки RN-кода: `lessons.filter(l => l.isNew)[0]` и `settings[key]`. Первая — самая частая: массив после фильтра может оказаться пустым, и код, читающий `[0].title`, падает у пользователя, у которого нет ни одного нового урока.

Правка, которая **не** является `!`: получить элемент, проверить, вернуть ветку отсутствия. В `renderItem` это ранний `return null`; в домене — функция, возвращающая `Lesson | undefined`, и решение на уровне вызывающего.

### `strictNullChecks` против значений, приходящих извне

Два источника дают больше всего ошибок этого флага, потому что оба честно типизированы как «может не быть».

**Хранилище.** Чтение из `AsyncStorage` возвращает строку **или** `null`: ключа может не быть, он мог быть удалён, приложение могло быть переустановлено. Без флага `JSON.parse(await AsyncStorage.getItem(key))` компилируется; с флагом — нет, и выясняется, что штатный случай «значения нет» нигде не обработан.

**Параметры экрана.** Параметры маршрута приходят из навигации, а их источником может быть deep link, то есть внешний мир. При выключенном флаге объявление `{ lessonId?: string }` ничем не отличается от `{ lessonId: string }`: в оба случая `undefined` присваивается. С флагом разницу приходится решить — либо параметр обязателен и его отсутствие есть ошибка навигации, либо он опционален и у экрана есть состояние «урок не указан».

Оговорка, без которой флаг понимается неверно: `strictNullChecks` проверяет **код**, а не данные. Если тип объявлен как `{ lessonId: string }`, компилятор считает, что строка там есть, даже когда deep link привёл `undefined`. Проверка фактических данных — 2.12 и 2.13.

### Типы библиотек и проверка в CI

На включении флагов регулярно обнаруживается, что ошибка не в своём коде, а в чужих типах: сигнатура объявлена без `| null`, опциональный колбэк объявлен обязательным, метод, существующий только на Android, в декларации выглядит доступным всегда. Поведение в таком случае — не `@ts-ignore`, а module augmentation или свой `.d.ts` (2.9). Важно здесь одно: включение флага делает неточности чужих типов видимыми массово, и к этому стоит быть готовым, чтобы не принять чужую неточность за свою ошибку.

Поскольку Metro типы не проверяет, `tsc --noEmit` обязан быть отдельным шагом пайплайна, независимым от сборки; его отсутствие ничем не проявляется — всё собирается, тесты проходят, ошибки типов накапливаются. Отсюда требование к порядку включения: шаг проверки должен быть красным или зелёным. «36 ошибок, это известно» не работает: через неделю их 51 и новых никто не заметил. Поэтому флаг попадает в конфигурацию только тогда, когда ошибок по нему ноль, а до этого работа идёт на локальном запуске с временной конфигурацией.

> **Не дублировать:** устройство пайплайна, кэширование и порядок шагов — блок 10; Metro и сборка — блок 04.

## 5. Типичные ошибки

**Включить `strict: true` целиком на живом проекте.** Сотни или тысячи ошибок разных классов сразу. Разобрать за один заход невозможно, работа растягивается, конфликтует с продуктовыми задачами, через неделю изменение откатывается с выводом «нам это не подходит». Причина не в объёме кода, а в том, что смешаны несвязанные решения: ошибки `strictNullChecks` требуют думать о домене, `noImplicitAny` — дописывать аннотации, `strictFunctionTypes` — разбираться в вариантности.

**Залить код `!` и `as` ради прохождения проверки.** Формально флаг включён, фактически отменён в каждом месте, где должен был сработать. От предыдущей ошибки отличается тем, что выглядит как успех: сборка зелёная, `strict` в конфигурации. Надёжный признак — рост числа `!` и `as` в диффе миграции: если он сопоставим с числом исправленных ошибок, работа не сделана.

**`@ts-ignore` вместо `@ts-expect-error`.** Подавление, которое не умеет устареть. Через год оно скрывает ошибку, не имеющую отношения к исходной: библиотека обновилась, код переписан, причина исчезла, директива осталась и глушит следующую проблему в той же строке.

**Считать, что `strict` проверяет данные.** Самое дорогое заблуждение урока: «у нас `strict`, значит ответ сервера типизирован». Флаги проверяют **утверждения внутри кодовой базы** на согласованность друг с другом. Что приходит из сети, из хранилища, из deep link и от нативного модуля, компилятор не знает и узнать не может: `JSON.parse` возвращает `any`, и с этого места тип является предположением автора. Закрывается только проверкой в рантайме (2.12).

**Включить флаг раньше, чем предыдущий доведён до нуля.** Два включённых и не закрытых флага дают перемешанный список, в котором непонятно, какая ошибка к какому решению относится, и нельзя сказать, сколько работы осталось. Один флаг за раз — не аккуратность, а условие измеримости.

**Выключить `strictNullChecks` «на время», оставив остальные.** Выглядит разумно: убрать самое дорогое, оставить дешёвое. Цена в том, что `strictPropertyInitialization` без него не работает вообще, вывод типов остаётся нестрогим, и весь код, написанный за это время, пишется в предположении, что `null` допустим везде.

## 6. Trade-offs

### Цена включения против класса дефектов

Единица измерения для решения — не «строгость», а пара «сколько человеко-дней» и «какой дефект перестанет происходить». Порядок величин для проекта среднего размера, который писался без `strict`:

| Флаг | Объём работы | Что перестаёт происходить |
|---|---|---|
| `alwaysStrict`, `strictBindCallApply` | часы | почти ничего |
| `noImplicitThis`, `strictPropertyInitialization` | часы | потерянный контекст, непроинициализированное поле |
| `noImplicitReturns`, `noFallthroughCasesInSwitch` | часы | забытая ветка, провал в `case` |
| `strictFunctionTypes` | день | колбэк, не умеющий обработать все варианты |
| `useUnknownInCatchVariables` | день-два | обработчик ошибки, падающий на ошибке другой формы |
| `noImplicitAny` | дни | островá без проверок внутри типизированного кода |
| `noUncheckedIndexedAccess` | дни | падение на пустом списке и отсутствующем ключе |
| `strictNullChecks` | недели | обращение к отсутствующему значению |

Таблица — не норматив, а форма рассуждения: числа зависят от кодовой базы, и получить свои можно единственным способом — включить флаг локально и посчитать ошибки. Важно соотношение: первые три строки включаются почти бесплатно, последние две — проекты сами по себе.

### `noUncheckedIndexedAccess`: многословность против падений

Флаг платит лучше всех по отношению пользы к цене и при этом чаще всех отвергается. Причина — характер правок:

```ts
const title = lessons[index].title;   // было

const lesson = lessons[index];        // стало
if (!lesson) return null;
const title = lesson.title;
```

Три строки вместо одной, и так в каждом месте доступа по индексу; хуже всего в циклах, где флаг не понимает, что `i < lessons.length` уже проверено. Что это даёт: класс падений, который иначе не находится ни тестами, ни ревью, потому что проявляется на пустых и коротких данных — у нового пользователя, в офлайне, после фильтра без совпадений.

Осмысленный отказ выглядит так: код, где доступ по индексу идёт плотно и элемент гарантирован структурой данных (матрицы, парсеры, вычисления по буферу), получает десятки мёртвых проверок. Но и тогда правильнее не глобальный отказ, а изоляция: флаг включён на проект, а в таком модуле проверенный тип получают один раз через функцию доступа. Хуже всего промежуточный вариант — включить флаг и глушить его `!` в каждом месте: цена заплачена, польза отменена.

### Время проверки типов

Разница появляется не от флагов как таких, а от того, что строгий код обычно имеет больше ветвлений и больше union'ов; проявляется она в отзывчивости IDE на больших файлах и в длительности шага CI. Обычно проблема локальна — один-два файла с большими объединениями строк или сложными условными типами (2.7, 2.10), и найти их помогает `tsc --diagnostics`. Это аргумент не против флагов, а за то, чтобы знать время полной проверки своего проекта: если оно измеряется минутами, лечить нужно время проверки, а не отключать проверки.

### Порядок включения — это план, а не список

У плана есть обоснование порядка, и из него следует, что делать после каждого шага.

1. **Дешёвое и независимое — первым.** `alwaysStrict`, `strictBindCallApply`, `noImplicitThis`, `noFallthroughCasesInSwitch`, `noImplicitReturns`: часы работы, сразу в конфигурацию и в CI.
2. **`noImplicitAny` — до `strictNullChecks`, а не после.** Причина механическая: `any` поглощает проверки на `null`, и пока в проекте много неявных `any`, `strictNullChecks` даёт мало ошибок — не потому, что код корректен, а потому, что проверять нечего. В обратном порядке работа делается дважды: доведя `strictNullChecks` до нуля, вы включите `noImplicitAny`, выведете типы у прежних неявных `any` и получите новую волну ошибок `strictNullChecks` на тех же местах.
3. **`useUnknownInCatchVariables` и `strictFunctionTypes` — после `noImplicitAny`:** пока функции не типизированы, сравнивать их сигнатуры не на чем.
4. **`strictNullChecks` — последним из набора, отдельным проектом**, по модулям, а не по всему коду сразу.
5. **`strictPropertyInitialization`** — только после `strictNullChecks`: без него флаг недействующий.
6. **Вторая группа — после набора.** `noUncheckedIndexedAccess` включают, когда `strictNullChecks` закрыт: иначе ошибки про `| undefined` идут от двух флагов сразу, и причину каждой приходится выяснять отдельно.

После каждого шага состояние проекта определено: флаг в конфигурации, ошибок ноль, CI красит сборку при регрессии. Это и отличает план от списка «что хорошо бы включить»: нельзя оказаться в состоянии «включили четыре флага, ошибок триста, работаем».
