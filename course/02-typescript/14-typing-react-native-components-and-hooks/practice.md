# 2.14 Типизация React/RN-компонентов и хуков — practice

## Проверка понимания

Вопросы уровня собеседования. Правильный ответ требует назвать, **что увидит вызывающий**, а не процитировать сигнатуру утилиты.

---

**1. Компонент принимает `style?: ViewStyle`, вызывающий передаёт `style={[styles.a, cond && styles.b]}` — что скажет компилятор и почему `StyleProp<ViewStyle>` принимает это выражение?**

<details>
<summary>Ответ</summary>

Компилятор откажет: тип аргумента — массив, в котором к тому же возможен `false`, а `ViewStyle` описывает один объект стиля.

`StyleProp<ViewStyle>` принимает это выражение потому, что описывает все формы, которые реально допускает `style` в React Native: один объект, массив (в том числе вложенный), зарегистрированное значение, `null`, `undefined`, `false`. Условный стиль через `&&` даёт `false` в массиве — штатная запись, и тип обязан её покрывать.

Практическое следствие важнее формулировки. У `style?: ViewStyle` есть одно время жизни — до первого условного стиля, после чего правят **не тип, а место вызова**: ставят `as`, оборачивают в `StyleSheet.flatten` или переписывают условие. То есть неточный тип не просто бесполезен — он вынуждает портить код вызывающего.

Вариант `style?: object` хуже обоих: он компилируется всегда и не проверяет ни одного свойства, то есть делает вид, что типизация есть.

**Ответ «надо обернуть массив в `StyleSheet.flatten`»** вскрывает лечение симптома. Способ рабочий, но он подгоняет вызов под неверный тип, и так придётся делать в каждом месте использования компонента.

**Ответ «`ViewStyle` и `StyleProp<ViewStyle>` отличаются только строгостью»** вскрывает модель «один тип строже другого». Они описывают разные множества значений: второй включает формы, которых в первом нет в принципе.

**Ответ «можно поставить `style?: any`»** вскрывает готовность отключить проверку вместо того, чтобы её настроить. `any` в пропсе публичного компонента отменяет проверки у всех вызывающих (2.4).
</details>

**2. В каком случае `ComponentProps` и `ComponentPropsWithoutRef` дадут разный результат и к какой ошибке приведёт неверный выбор?**

<details>
<summary>Ответ</summary>

Разный результат они дают там, где `ref` входит в типизированный контракт компонента: `ComponentProps` берёт пропсы так, как они у него описаны, и `ref` в этом случае попадает в результат, а `ComponentPropsWithoutRef` его намеренно убирает. `ref` — особая часть компонентного API React, а не обычный пропс, поэтому результат зависит от типизации конкретного компонента, а не от общего правила.

Неверный выбор даёт **молчаливый** дефект. Собственная кнопка объявляет пропсы через `ComponentProps<typeof Pressable>`, но ref никуда не пробрасывает:

```ts
type ButtonProps = ComponentProps<typeof Pressable> & { title: string };

function Button({ title, ...rest }: ButtonProps) {
  return <Pressable {...rest}><Text>{title}</Text></Pressable>;
}

<Button ref={buttonRef} title="Открыть" />   // компилируется, ref не работает
```

Компонент объявил пропс, которого не поддерживает. Вызывающий передал `ref`, компилятор согласился, `buttonRef.current` остался `null` — и выяснится это в рантайме, при попытке вызвать метод узла.

Правило выбора: если компонент не оборачивается в `forwardRef`, нужен вариант **без** `ref`. Если оборачивается — тоже нужен вариант без `ref`, потому что тип ref задаётся первым параметром `forwardRef`, а не наследуется из пропсов. `ComponentProps` остаётся для случаев, когда тип пропсов нужен целиком «как есть» — например, чтобы передать его дальше или построить от него `Pick`.

**Ответ «они взаимозаменяемы, разница стилистическая»** вскрывает ровно то заблуждение, которое даёт неработающий ref.

**Ответ «`ComponentPropsWithoutRef` нужен для функциональных компонентов»** вскрывает привязку к виду компонента вместо поведения вашего кода. Значение имеет не то, как объявлен чужой компонент, а пробрасываете ли вы ref.
</details>

**3. Хук возвращает `[value, setValue]`: какой тип получит вызывающий без `as const`, и что изменится после него?**

<details>
<summary>Ответ</summary>

Без `as const` выводится тип массива с union элементов:

```ts
function useToggle(initial: boolean) {
  const [value, setValue] = useState(initial);
  const toggle = () => setValue((v) => !v);
  return [value, toggle];     // (boolean | (() => void))[]
}

const [on, switchIt] = useToggle(false);
// on       — boolean | (() => void)
// switchIt — boolean | (() => void)
```

Компилятор не связывает тип с позицией: для него это массив, длина которого неизвестна, а элементы — «или то, или другое». Вызывающий получает значения, с которыми ничего нельзя сделать без сужения, и на практике ставит `as` — то есть хук, написанный ради удобства, заставляет подавлять проверки.

`as const` превращает выражение в кортеж `readonly [boolean, () => void]`: тип привязан к позиции, деструктуризация даёт `boolean` и функцию. То же самое даёт явная аннотация возвращаемого типа кортежем — вариант многословнее, но заметнее при чтении сигнатуры.

Стоит помнить, что `as const` здесь работает только в типах (2.1): в рантайме это обычный массив, и `readonly` ничего не запрещает.

**Ответ «TypeScript выведет кортеж сам, если значений два»** вскрывает ожидание, что вывод зависит от длины литерала. Проверяется наведением на результат: без `as const` там массив.

**Ответ «это неважно, деструктуризация всё равно работает»** вскрывает остановку на синтаксисе. Деструктуризация действительно скомпилируется; непригодны **типы** полученных значений.

**Ответ «лучше всегда возвращать объект»** — рабочее решение, но как ответ на вопрос подменяет тему. Объект снимает проблему, не объясняя её; к тому же у кортежа есть преимущество, которое при этом теряется: вызывающий сам именует значения, что важно при двух экземплярах хука на одном экране.
</details>

**4. Почему обёртка над `FlatList` без параметра типа — более дорогая ошибка, чем неточный тип одного пропса?**

<details>
<summary>Ответ</summary>

Потому что она обрывает типизацию **внутри** замыкания, а не в одном месте.

```ts
type ListProps = {
  data: any[];
  renderItem: (item: any) => ReactElement;
};
```

`renderItem` получает `any`, и всё, что написано внутри ячейки, перестаёт проверяться: обращение к несуществующему полю, передача не того значения в дочерний компонент, опечатка в имени. Это не одна непроверенная строка, а весь код ячейки — то есть обычно самая содержательная часть экрана.

Второй множитель: обёртка над списком пишется один раз и используется на всех экранах со списками. Один `any` в её сигнатуре отключает проверки в каждом из них.

Третий: `any` не остаётся локальным. Значение из `renderItem` присваивается чему угодно без возражений (2.4), поэтому ошибка обнаружится далеко от списка.

Исправление — параметр типа, связывающий `data` с `renderItem` и `keyExtractor`:

```ts
type ListProps<T> = {
  data: readonly T[];
  renderItem: (item: T) => ReactElement;
  keyExtractor: (item: T) => string;
};
```

**Ответ «это одинаковые ошибки, просто в разных местах»** вскрывает подсчёт ошибок по числу неверных типов, а не по объёму непроверенного кода.

**Ответ «достаточно аннотировать параметр в месте вызова»** — `renderItem={(item: Lesson) => ...}` — вскрывает перенос ответственности на вызывающего. Работает, пока каждый автор помнит; и это ровно та типизация «на дисциплине», о которой 2.11.
</details>

## Задание — контракты компонентов и хука дизайн-системы

**Дано.** Три компонента и один хук из RN Academy. Всё компилируется, проверок почти нет.

```ts
// Button.tsx
type ButtonProps = {
  title: string;
  onPress: () => void;
  style?: object;
  disabled?: boolean;
};

// LessonList.tsx
type LessonListProps = {
  data: any[];
  renderItem: (item: any) => ReactElement;
};

// VideoPlayer.tsx — компонент с императивным API
// наружу нужны play(), pause(), seek(sec)

// useLessonProgress.ts
function useLessonProgress(lessonId: string) {
  const [percent, setPercent] = useState(0);
  const [isSaving, setSaving] = useState(false);
  const save = async () => { /* ... */ };
  return [percent, save, isSaving];
}
```

**Требуется.**

1. Переписать `ButtonProps` так, чтобы пропсы `Pressable` не дублировались руками, а стиль принимал массив условных стилей. Отдельно решить, открывать ли наружу все пропсы `Pressable`, и обосновать решение.
2. Типизировать `LessonList` так, чтобы тип элемента связывал `data`, `renderItem` и `keyExtractor`. Показать на примере, что перестало компилироваться.
3. Объявить контракт `VideoPlayer`: тип handle, `forwardRef`, `useImperativeHandle`. Сказать, почему handle вынесен в именованный тип и что будет, если перепутать параметры `forwardRef`.
4. Исправить возврат `useLessonProgress`. Выбрать форму — кортеж или объект — и обосновать выбор; сформулировать правило проекта для остальных хуков.

---

<details>
<summary>Разбор</summary>

**1. `Button`.**

```ts
type PressableProps = ComponentPropsWithoutRef<typeof Pressable>;

type ButtonProps = Pick<PressableProps, 'onPress' | 'disabled' | 'testID' | 'accessibilityLabel'> & {
  title: string;
  variant?: 'primary' | 'ghost';
  style?: StyleProp<ViewStyle>;
};
```

Два решения, которые стоит проговорить.

**Стиль** — `StyleProp<ViewStyle>` вместо `object`. `object` компилировался всегда и не проверял ни одного свойства; новый тип принимает массив с условными стилями и проверяет состав каждого.

**Открывать ли все пропсы `Pressable`.** Здесь выбран `Pick`, а не пересечение со всем типом, и это решение в пользу узкого контракта дизайн-системы. Полный `ComponentPropsWithoutRef<typeof Pressable>` не расходится с библиотекой и открывает наружу `onLongPress`, `hitSlop`, `delayLongPress` и остальное — после чего кнопка перестаёт быть кнопкой дизайн-системы и становится `Pressable` с заголовком. `Pick` оставляет список явным, но **проверяемым**: опечатка в имени пропса не компилируется, а исчезновение пропса из библиотеки даст ошибку при обновлении (2.3).

Обратная сторона решения записана сразу: каждый новый нужный пропс придётся добавлять в `Pick` руками. Для дизайн-системы это приемлемо — там добавление пропса и должно быть решением.

`ComponentPropsWithoutRef`, а не `ComponentProps`: компонент не пробрасывает `ref` внутрь, и объявлять пропс, которого он не поддерживает, означает молчаливо сломать вызывающего.

**2. `LessonList`.**

```ts
type LessonListProps<T> = {
  data: readonly T[];
  renderItem: (item: T) => ReactElement;
  keyExtractor: (item: T) => string;
  onEndReached?: () => void;
};

function LessonList<T>({ data, renderItem, keyExtractor, onEndReached }: LessonListProps<T>) {
  return <FlatList data={data} renderItem={({ item }) => renderItem(item)} keyExtractor={keyExtractor} onEndReached={onEndReached} />;
}
```

Что перестало компилироваться:

```ts
<LessonList
  data={lessons}                                   // T выведен как Lesson
  renderItem={(lesson) => <Text>{lesson.titel}</Text>}   // ошибка: нет поля titel
  keyExtractor={(lesson) => lesson.id}
/>

<LessonList
  data={lessons}
  renderItem={(lesson) => <Text>{lesson.title}</Text>}
  keyExtractor={(lesson) => lesson.duration_min}   // ошибка: number не string
/>
```

До правки обе строки компилировались: `item` был `any`, и внутри ячейки не проверялось ничего. Это главный эффект — проверки вернулись не в сигнатуру компонента, а **внутрь кода ячейки**, то есть в самую содержательную часть экрана.

`readonly T[]` позволяет передать результат `as const` и объявляет, что компонент массив не мутирует.

**3. `VideoPlayer`.**

```ts
export type VideoPlayerHandle = {
  play(): void;
  pause(): void;
  seek(sec: number): void;
};

type VideoPlayerProps = {
  uri: string;
  onProgress?: (sec: number) => void;
  style?: StyleProp<ViewStyle>;
};

export const VideoPlayer = forwardRef<VideoPlayerHandle, VideoPlayerProps>(
  function VideoPlayer({ uri, onProgress, style }, ref) {
    const inner = useRef<ElementRef<typeof NativePlayer>>(null);

    useImperativeHandle(ref, () => ({
      play: () => inner.current?.play(),
      pause: () => inner.current?.pause(),
      seek: (sec) => inner.current?.seekTo(sec),
    }), []);

    return <NativePlayer ref={inner} source={{ uri }} style={style} onProgress={onProgress} />;
  },
);
```

**Почему handle — именованный тип.** Это публичный API компонента, и он отличается от того, что компонент умеет внутри. Вызывающий получает три метода, а не весь нативный узел: внутренний `inner` остаётся деталью реализации, и замена нативной библиотеки не затронет вызывающих, пока три метода работают. Именованный тип при этом экспортируется — чтобы объявить `useRef<VideoPlayerHandle>(null)` на стороне экрана.

**Если перепутать параметры** — `forwardRef<VideoPlayerProps, VideoPlayerHandle>` — объявление скомпилируется: оба параметра являются типами, и компилятору нечего возразить в этой строке. Ошибка возникнет **на стороне вызова**: `ref` будет ожидать объект с полями `uri` и `onProgress`, а пропсы — объект с методами. Сообщение укажет на экран, использующий компонент, а причина останется в его объявлении — классический случай, когда читать нужно не то место, на которое указал компилятор.

Внутренний ref типизирован `ElementRef<typeof NativePlayer>`, а не описан руками: описание из одного метода скомпилируется и лишит доступа ко всем остальным, а при обновлении библиотеки устареет молча (2.9).

**4. `useLessonProgress`.**

Возвращаемых значений три, и одно из них — флаг, который нужен не всем вызывающим. Это случай объекта, а не кортежа:

```ts
type LessonProgress = {
  percent: number;
  isSaving: boolean;
  save: () => Promise<void>;
};

function useLessonProgress(lessonId: string): LessonProgress {
  const [percent, setPercent] = useState(0);
  const [isSaving, setSaving] = useState(false);
  const save = useCallback(async () => { /* ... */ }, [lessonId]);
  return { percent, isSaving, save };
}
```

Обоснование: при кортеже из трёх элементов вызывающий обязан помнить порядок, а пропуск ненужного значения требует дырки в деструктуризации (`const [percent, , isSaving] = ...`). Объект устойчив к расширению: добавление `error` не затронет ни одного существующего вызова, тогда как четвёртый элемент кортежа делает чтение ещё хрупче.

Заодно исправлено то, что было до правки: без `as const` возвращался `(number | boolean | (() => Promise<void>))[]`, и каждое из трёх значений приходилось приводить на стороне вызова.

**Правило проекта для хуков.** Два значения, имена которых очевидны по позиции (значение и его сеттер), — кортеж с `as const`, как у `useState`. Три и больше, либо значения необязательные, либо набор будет расти — объект с именованным экспортируемым типом возврата. Тип возврата хука объявляется явно: он публичный контракт, и его изменение должно быть видно в диффе.

**Вклад в проект (P2).** Контракты будущих компонентов описаны до того, как в проекте появился React-слой: типы пропсов карточки урока и кнопки, тип элемента типизированного списка, императивный контракт плеера и форма возврата хука прогресса — выведенные из доменных типов, построенных в 2.3 и 2.5. Зафиксированы правила проекта: стиль — только `StyleProp<T>`; пропсы чужого компонента — через `Pick` от `ComponentPropsWithoutRef`, а не руками; обёртки над списками параметризуются типом элемента; тип возврата хука объявляется явно. На стадии P3 эти контракты становятся сигнатурами реальных компонентов, а механика стоящих за ними React API разбирается в блоке 03.
