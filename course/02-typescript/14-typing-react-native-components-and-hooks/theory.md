# 2.14 Типизация React/RN-компонентов и хуков — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как объявить пропсы» — а на вопрос, **какие типы в компоненте выводятся из того, что уже описано, и какие приходится описывать второй раз**.

---

## 1. Что это

Урок собирает приёмы блока в одном месте — там, где RN-разработчик пишет код каждый день: пропсы компонента, его ref, стили и возврат кастомного хука.

**`ComponentProps<T>` и `ComponentPropsWithoutRef<T>`** — утилиты, извлекающие тип пропсов существующего компонента, чтобы не перечислять их заново.

**`PropsWithChildren<P>`** — утилита, добавляющая к пропсам необязательный `children`.

**`StyleProp<T>`** — тип стиля в React Native, описывающий все формы, которые допускает `style`: объект, массив, зарегистрированное значение, `null`, `false`.

```ts
type CardProps = {
  title: string;
  style?: StyleProp<ViewStyle>;
  children: ReactNode;
};
```

### Ключевая формулировка урока

> **Контракт компонента и контракт хука — это то, что видит вызывающий. Всё, что выведено из уже существующего описания, останется верным после изменения; всё, что описано вторым разом, разойдётся.**

Тот же критерий, что в 2.11 и 2.12, применённый к UI-слою.

### Граница урока

Здесь **только типы**. Механика React API разбирается в блоке 03: refs и `useImperativeHandle` — 3.9, кастомные хуки — 3.12, composition и `children` — 3.13, мемоизация — 3.11.

Урок стоит до блока 03 сознательно: аудитория курса пишет RN-компоненты каждый день, и опора идёт на этот практический опыт, а не на пройденный материал. То же допущение уже сделано в 2.9, где `ParamList` расширяется задолго до блока 04. Ни одно утверждение о том, **как работает** `forwardRef` или правило хуков, в этом уроке не формулируется.

## 2. Как это работает

### Пропсы: отдельный именованный тип

```ts
type LessonCardProps = {
  title: string;
  state: 'locked' | 'available' | 'done';
  onPress: (lessonId: string) => void;
};

function LessonCard({ title, state, onPress }: LessonCardProps) { /* ... */ }
```

Три решения в четырёх строках. Тип именован — он появляется в сообщениях об ошибках по имени (2.6) и доступен для переиспользования. `state` — union литералов, поэтому `state="Done"` с опечаткой не компилируется (2.1). Пропсы аннотированы в параметре, а не через тип функции-компонента: `React.FC` добавляет к контракту то, чего в нём может не быть, и ограничивает дженерики.

### Расширение чужого компонента

Собственный `Button` поверх `Pressable` обычно повторяет часть пропсов руками, и список расходится с библиотекой при первом обновлении. Утилита убирает второе описание:

```ts
type ButtonProps = ComponentPropsWithoutRef<typeof Pressable> & {
  title: string;
  variant?: 'primary' | 'ghost';
};
```

Разница между двумя утилитами наблюдаемая, а не стилистическая:

- **`ComponentProps<typeof X>`** — все пропсы, **включая** `ref`, если компонент его принимает;
- **`ComponentPropsWithoutRef<typeof X>`** — те же пропсы **без** `ref`.

Выбор определяется тем, что делает ваш компонент. Если он не пробрасывает `ref` дальше, `ComponentProps` объявит пропс, которого ваш компонент не поддерживает: вызывающий передаст `ref`, компилятор промолчит, ref не сработает. Если компонент оборачивается в `forwardRef` и ref пробрасывается, его тип задаётся вторым параметром `forwardRef`, а не наследуется из пропсов — и тогда снова нужен вариант без `ref`.

### `children`: явно или утилитой

```ts
type ScreenProps = PropsWithChildren<{ title: string }>;

type ScreenPropsExplicit = {
  title: string;
  children: ReactNode;
};
```

`PropsWithChildren` добавляет `children?: ReactNode` — **необязательный**. Явное объявление даёт три вещи, которых утилита не даёт: `children` можно сделать обязательным (компонент-обёртка без содержимого бессмыслен), сузить допустимое содержимое (`children: ReactElement<TabProps> | ReactElement<TabProps>[]`), и увидеть пропс прямо в сигнатуре при чтении.

Практическое правило: утилита — для совместимости и краткости, явное объявление — когда `children` часть контракта, а не деталь.

### Generic-компонент

Список, типизированный элементом:

```ts
type ListProps<T> = {
  data: readonly T[];
  renderItem: (item: T) => ReactElement;
  keyExtractor: (item: T) => string;
};

function TypedList<T>({ data, renderItem, keyExtractor }: ListProps<T>) { /* ... */ }

<TypedList
  data={lessons}
  renderItem={(lesson) => <LessonCard {...lesson} />}   // lesson — Lesson, выведен
  keyExtractor={(lesson) => lesson.id}
/>
```

`T` выводится из `data`, и этим же типом связаны `renderItem` и `keyExtractor`. Без параметра типа обёртка над списком превращает `renderItem` в функцию от `any`, и типизация экрана заканчивается там, где её ценность максимальна.

`readonly T[]` в `data` — мелочь с практическим следствием: компонент объявляет, что не мутирует массив, и принимает результат `as const` (2.1).

### `forwardRef` и императивный контракт

```ts
type PlayerHandle = {
  play(): void;
  seek(sec: number): void;
};

const Player = forwardRef<PlayerHandle, PlayerProps>((props, ref) => {
  useImperativeHandle(ref, () => ({ play, seek }), [play, seek]);
  return <View />;
});
```

Первый параметр `forwardRef` — тип того, что получит вызывающий через `ref`; второй — пропсы. Порядок обратен интуиции и является самой частой ошибкой в этом месте.

`PlayerHandle` объявлен отдельным именованным типом не ради стиля: **это и есть публичный API компонента** — узкий контракт вместо всего узла. Для ref на встроенный RN-компонент тип берётся утилитой, а не пишется руками: `ElementRef<typeof TextInput>` остаётся верным при изменении версии библиотеки.

### Стиль: почему не `object` и не `ViewStyle`

```ts
type CardProps = {
  style?: StyleProp<ViewStyle>;
};

<Card style={[styles.row, isActive && styles.active, null]} />
```

Допустимые формы `style` — объект, массив любой вложенности, зарегистрированное значение, `null`, `undefined`, `false`. `ViewStyle` описывает только первую, `object` не описывает ничего полезного. Поэтому `style?: ViewStyle` компилируется ровно до первого условного стиля в массиве, а `style?: object` компилируется всегда и не проверяет ни одного свойства.

### Возврат кастомного хука

```ts
function useToggle(initial: boolean) {
  const [value, setValue] = useState(initial);
  const toggle = useCallback(() => setValue((v) => !v), []);
  return [value, toggle] as const;   // readonly [boolean, () => void]
}
```

Без `as const` выводится `(boolean | (() => void))[]`: массив union-типа, где в обеих позициях лежит «или то, или другое». Вызывающий получает нечитаемый тип и ставит `as` — то есть хук, написанный ради удобства, заставляет подавлять проверки (2.4).

Выбор формы возврата — выбор контракта:

| Форма | Что даёт | Чем платит |
|---|---|---|
| кортеж с `as const` | вызывающий сам именует значения, удобно при нескольких экземплярах хука на экране | порядок значим; третье значение делает чтение хрупким |
| объект | имена фиксированы автором, порядок не важен, расширяется без ломания вызывающих | переименование на стороне вызова требует деструктуризации с `:` |

Правило, которое работает: два значения, где имена очевидны по позиции, — кортеж; три и больше либо необязательные — объект.

---

## 3. Почему это важно

Типы компонента и хука — это то, что видно **на стороне вызова**, и ошибка здесь тиражируется: один неверный тип пропса даёт непроверенный код в каждом месте использования компонента.

Второе: именно в UI-слое чаще всего возникает второе описание той же формы. Пропсы обёртки повторяют пропсы библиотечного компонента, тип элемента списка повторяется в `renderItem` и `keyExtractor`, возврат хука описывается на стороне вызова через `as`. Каждое такое повторение расходится при первом изменении — ровно по тому же механизму, что предикат и тип в 2.12.

Третье, специфичное для RN: граница с нативным слоем проходит через пропсы и стили. `style`, типизированный как `object`, пропустит свойство, которого на платформе нет; пропс нативного компонента, объявленный неточно (2.9), пропустит значение, которое нативная сторона не поймёт. Компилятор при этом молчит, а поведение различается по платформам.

## 4. Где это в React Native

### Стиль

Самое частое место, где типизация формально есть и не работает. `style?: object` в пропсах собственного компонента компилируется всегда — включая случай, когда в массив стилей попало поле с опечаткой или свойство, поддерживаемое только на одной платформе.

### Обёртка над компонентом библиотеки

Дизайн-система проекта — это обёртки: `Button` поверх `Pressable`, `Input` поверх `TextInput`, `Screen` поверх `SafeAreaView`. Каждая обёртка — место, где пропсы либо выводятся утилитой, либо переписываются руками и расходятся при обновлении библиотеки.

### Обёртка над `FlatList`

Собственный список без параметра типа — самый дорогой случай: `renderItem` получает `any`, и всё, что внутри ячейки, перестаёт проверяться. Экран при этом выглядит типизированным.

### Ref на нативный узел

`measure`, `scrollToIndex`, `focus` вызываются через ref, и тип ref определяет, какие методы доступны. `ElementRef<typeof TextInput>` выводит его из самой библиотеки; описанный руками объект с одним методом `focus` скомпилируется и не даст ни одного другого.

### Возврат хука в дизайн-системе проекта

`useTheme`, `useKeyboardHeight`, `useAppState` — хуки, вызываемые десятками компонентов. Их возвращаемый тип — публичный контракт: если он объявлен неточно, неточность тиражируется по всем вызовам сразу.

## 5. Типичные ошибки

**`React.FC` ради типизации `children`.** Утилита добавляет `children` всем компонентам, включая те, которые содержимое не принимают, и мешает параметризовать компонент дженериком. Причина популярности — привычка из старых кодовых баз.

**`style?: ViewStyle` вместо `StyleProp<ViewStyle>`.** Компилируется до первого массива стилей, после чего правится не тип, а место вызова — через `as` или снятие условного стиля.

**Ручное перечисление пропсов чужого компонента.** Список расходится с библиотекой при обновлении, и расхождение не обнаруживается: ваши пропсы остаются корректными сами по себе.

**`ComponentProps` там, где нужен `ComponentPropsWithoutRef`.** Компонент объявляет пропс `ref`, которого не поддерживает: вызывающий его передаёт, компилятор молчит, ref не работает.

**Обёртка над списком без параметра типа.** `renderItem` от `any`, и типизация обрывается на границе списка.

**Кортеж из хука без `as const`.** Вызывающий получает union в обеих позициях и ставит `as`.

**Перепутанный порядок параметров `forwardRef`.** `forwardRef<Props, Handle>` вместо `forwardRef<Handle, Props>`. Ошибка компиляции возникает не в объявлении, а на стороне вызова, и сообщение указывает не туда.

**Тип `ref`, описанный руками.** Объект с одним методом вместо `ElementRef<typeof X>`: остальные методы узла недоступны, а при изменении версии библиотеки описание устаревает молча.

## 6. Trade-offs

### Выведенные пропсы против явного списка

`ComponentPropsWithoutRef<typeof Pressable>` не даёт расхождения с библиотекой — и открывает наружу **все** её пропсы, включая те, что не входят в ваш контракт. Через вашу кнопку становится возможно передать `onLongPress`, `hitSlop` и десяток других. Для дизайн-системы, где контракт сознательно узкий, это может быть нежелательно, и тогда правильнее `Pick` по нужным пропсам (2.3): список явный, но проверяемый — опечатка в имени пропса не компилируется.

### Generic-компонент: точность против читаемости

Параметризованный список даёт сквозную типизацию и платит сигнатурой, которую сложнее прочитать, и сообщениями об ошибках, в которых участвует `T`. На одном списке в проекте выгода невелика; на собственной обёртке, используемой на двадцати экранах, — очевидна.

### Кортеж против объекта в хуке

Кортеж короче на стороне вызова и фиксирует порядок; объект устойчивее к расширению и самодокументируем. Менять решение после того, как хук используется в тридцати местах, дорого, поэтому выбирать стоит исходя из того, будет ли набор возвращаемых значений расти.

### Строгий `children` против совместимости

`children: ReactElement<TabProps>[]` даёт проверку состава и ломается на условном рендере (`{cond && <Tab />}` даёт `false` в массиве) и на фрагментах. Строгая типизация содержимого выглядит привлекательно и на практике чаще мешает, чем помогает; разумная граница — `ReactNode` плюс проверка в рантайме там, где состав действительно важен.
