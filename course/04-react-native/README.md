### Порядок 4.1 → 4.2 выбран сознательно

**New Architecture — это современная архитектура React Native, а не один из двух равнозначных вариантов.** Для нового проекта выбора между Legacy и New Architecture нет, поэтому урок про актуальное устройство идёт **первым**, а Legacy Architecture — вторым, как исторический контекст и как инструмент чтения старого кода.

Из этого следуют два требования к формулировкам:

- **4.1 не подаётся как «Bridge 2.0».** Нельзя оставлять модель «был старый мост — стал новый мост». JSI — прямой интерфейс между JS и native, допускающий синхронные вызовы и работу с нативными объектами по ссылке, вместо асинхронной сериализованной очереди сообщений; Fabric — другой рендер-пайплайн с другим владением Shadow Tree; TurboModules — другой контракт модулей с ленивой инициализацией и типизированным интерфейсом. Обязательный подраздел: **какие интуиции из старой модели здесь не работают** («любой вызов в native асинхронен», «данные всегда сериализуются в JSON», «UI обновляется только из конца очереди»).
- **4.2 не подаётся как описание того, как работает RN сегодня.** Урок нужен, чтобы читать legacy-код, понимать причину старых архитектурных решений в проекте и объяснять, почему появились JSI, Fabric и TurboModules. Разбирается: модель JS↔native взаимодействия в legacy-архитектуре, передача аргументов и результатов, callbacks и events, сериализация и конвертация данных **как свойство той модели, а не как определение Bridge**, и её ограничения (асинхронность всех вызовов, стоимость конвертации, невозможность синхронного доступа к нативным объектам, batching как вынужденная мера).

### Hermes и JSC

**Hermes — основной движок современного React Native.** JSC рассматривается как специальный, legacy или edge case (конкретные платформенные ограничения, legacy-проекты, редкие требования совместимости), а не как равнозначная альтернатива. Урок 4.6 поэтому отвечает не на вопрос «что выбрать», а на вопрос **почему движок вообще имеет значение**: startup и TTI, потребление памяти, precompiled bytecode вместо парсинга на устройстве, возможности отладки, совместимость синтаксиса и API, профиль производительности. Выбор JSC — редкое решение, которое нужно обосновывать.

### Build types (4.7)

```
Debug  →  Debug Optimized  →  Release
```

Обычная Debug-сборка даёт искажённое представление о производительности: включены dev-проверки, нет оптимизаций движка и бандлера, работает инструментирование. Поэтому выводы о performance из Debug-сборки некорректны, а Release плохо подходит для отладки. **Debug Optimized** — промежуточный тип сборки, который сохраняет возможность отладки, но убирает основные искажения; урок объясняет, что именно отличается в каждом типе и какие выводы допустимо делать на каком из них.

#### Урок 4.13 — современный набор инструментов

Основа workflow: **React Native DevTools** (инспектор компонентов, профайлер, отладчик JS), **Xcode** и **Android Studio** (нативная отладка, нативные логи, инструменты платформы), **native logs** как источник правды, когда JS-слой молчит, и **profiling tools** платформы.

Чего урок сознательно **не** делает:

- не позиционирует **Flipper** как основной инструмент — он упоминается только как исторический/legacy-контекст, который может встретиться в старом проекте;
- не делает `chrome://inspect` и отладку через Chrome DevTools основным workflow;
- не предлагает отлаживать performance в обычной Debug-сборке (см. 4.7).

Профилирование производительности разбирается в блоке [05](../05-performance/) (5.10), нативная отладка собственного кода — в блоке [09](../09-native/), чтение крашей из продакшена — в блоке [10](../10-production/).

## Что должно быть получено

- Объясняю, как устроено взаимодействие JS и native в современном RN, и чем это отличается от legacy-модели по сути, а не по версии.
- Читаю код, написанный под legacy-архитектуру, и понимаю, из каких её ограничений выросли его решения.
- Довожу deep link до экрана третьего уровня через вложенную навигацию и предсказываю поведение при холодном старте.
- Делаю экран доступным и проверяю это VoiceOver и TalkBack.
- Объясняю, почему движок имеет значение (startup, память, bytecode, отладка, совместимость), и какие выводы о performance нельзя делать из Debug-сборки.
- Выбираю инструмент отладки под слой, в котором ищу проблему.
