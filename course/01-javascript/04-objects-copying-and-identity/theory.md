# 1.4 Objects: копирование и идентичность — theory

> 🟢 REFRESH. Главная мысль урока одна: **идентичность объекта и его содержимое — два независимых свойства.** React смотрит на первое, а разработчик думает про второе, и отсюда растёт самый частый вопрос «я поменял данные, а экран не обновился».

## Refresh

### Идентичность как отдельное свойство

У каждого объекта есть содержимое (какие поля и значения) и **идентичность** — факт «это именно тот объект, а не другой такой же». Эти два свойства не связаны:

```js
const a = { id: 1 };
const b = { id: 1 };
const c = a;

a === b;  // false — содержимое одинаковое, объекты разные
a === c;  // true  — одна идентичность
```

Проверить идентичность можно только через `===` (или `Object.is`). Проверить равенство содержимого встроенного способа нет — нужна либо ручная проверка полей, либо сравнение, написанное самостоятельно или взятое из библиотеки.

Обратное тоже верно и менее очевидно: **содержимое может измениться, а идентичность — нет.**

```js
const user = { name: "Аня" };
const before = user;
user.name = "Борис";
before === user;  // true — объект тот же, содержимое другое
```

Эта асимметрия — источник обоих классов ошибок: «изменил, но никто не заметил» и «не изменил, но все пересчитали».

### Shallow copy

**Shallow copy (поверхностная копия)** — новый объект, в поля которого скопированы значения исходного. Для примитивов копируется значение, для объектов — **ссылка**.

```js
const source = { title: "Курс", meta: { tags: ["js"] } };

const copy = { ...source };
// или Object.assign({}, source)

copy === source;            // false — верхний уровень новый
copy.meta === source.meta;  // true  — вложенный объект тот же
```

Глубина копирования — **ровно один уровень**. Это не ограничение реализации, а определение: spread перебирает собственные перечислимые свойства (включая ключи-символы) и определяет их значения на новом объекте. Для вложенного объекта значение — это ссылка.

Практическое следствие: после `{...state}` изменение `copy.meta.tags.push(...)` изменит и `source.meta.tags`. Копия есть, защиты нет.

`Object.assign(target, source)` делает то же самое, но **мутирует первый аргумент**. `Object.assign({}, source)` — безопасная форма; `Object.assign(source, patch)` — мутация, и в коде, работающем с состоянием, это почти всегда дефект.

### Порядок перезаписи

При нескольких источниках побеждает последний:

```js
const result = { ...defaults, ...fromServer, ...overrides };
```

Правило простое, но у него есть неочевидная сторона: **ключ со значением `undefined` тоже перезаписывает.**

```js
const defaults = { limit: 20 };
const patch = { limit: undefined };
({ ...defaults, ...patch }).limit;  // undefined, а не 20
```

Это регулярно ломает слияние настроек: объект с неявно отсутствующим полем (`undefined`) затирает корректный дефолт. `Object.assign` ведёт себя так же.

### `Object.keys`, `values`, `entries`

Все три возвращают **только собственные перечислимые** свойства: унаследованное из прототипа не попадает (1.17), как и ключи-символы.

```js
Object.keys({ a: 1, b: 2 });     // ["a", "b"]
Object.values({ a: 1, b: 2 });   // [1, 2]
Object.entries({ a: 1, b: 2 });  // [["a", 1], ["b", 2]]
```

Важное для дальнейшего: каждый вызов создаёт **новый массив**. Поэтому `Object.keys(obj)` в теле компонента — новая ссылка на каждый рендер, даже если объект не менялся (1.6, 3.10).

Порядок ключей: сначала целочисленные ключи по возрастанию, затем строковые в порядке добавления. Полагаться на это в продуктовом коде не стоит — если порядок важен, нужен массив.

### `Object.freeze` и его границы

`Object.freeze` запрещает добавление, удаление и изменение свойств — **на одном уровне**.

```js
const config = Object.freeze({ retries: 3, nested: { a: 1 } });

config.retries = 5;    // молча не сработает (в strict mode — TypeError)
config.nested.a = 2;   // сработает: вложенный объект не заморожен
```

Две границы, о которых нужно помнить:

- **заморозка неглубокая** — для вложенных структур нужна рекурсия;
- **в нестрогом режиме ошибка не выбрасывается**, присваивание просто ничего не делает. Это худший вариант: код выглядит работающим.

`Object.freeze` не является способом добиться иммутабельности в приложении — он является способом **обнаружить** случайную мутацию в разработке. Именно для этого его применяют точечно, а не повсеместно.

> **В RN-приложении код по умолчанию нестрогий — и `freeze` молчит.** ES-модули строгие по спецификации, но в RN модуль до движка не доходит: `@react-native/babel-preset` переписывает `import`/`export` в CommonJS с опцией `strictMode: false` («prevent "use strict" injections»), а Metro добавляет `"use strict"` только тем файлам, которые после трансформации остались ES-модулями, — при настройках по умолчанию таких нет (проверено на RN 0.87.1 / Metro 0.87). Итог: в обычном `.ts`/`.tsx`-файле приложения запись в замороженный объект **молча игнорируется**, и «обнаружить мутацию через `freeze`» не получится. Исключения — тела классов (всегда строгие) и файлы с явной директивой `'use strict'` в первой строке. В Node и в браузере тот же модуль строгий и бросит `TypeError` — поэтому вывод «у меня freeze ловит мутации» нельзя переносить из веба в RN.

## RN relevance

### «Я поменял поле, а экран не обновился»

```js
const [course, setCourse] = useState({ title: "JS", progress: 0 });

function finish() {
  course.progress = 100;   // мутация
  setCourse(course);       // та же ссылка
}
```

Экран не обновится. React сравнивает предыдущее состояние с новым по идентичности (через алгоритм `Object.is`, см. 1.3), получает «то же самое» и не планирует рендер. Данные при этом изменились — то есть состояние приложения и состояние экрана разошлись.

Что делает это особенно неприятным: иногда экран **всё-таки** обновляется — если рендер случился по другой причине (другое состояние, родитель, навигация). Тогда мутация выглядит работающей, и опора на неё закрепляется. Это одна из главных причин, по которой иммутабельность в React — не стилистическое требование, а условие корректности (1.13).

Корректно: `setCourse({ ...course, progress: 100 })`.

### Частично обновившийся экран

Следующий уровень той же ошибки:

```js
setCourse({ ...course });          // новый верхний уровень
course.lessons[0].done = true;     // мутация вложенного
```

Верхний уровень новый — компонент экрана перерисуется. Вложенный объект тот же — мемоизированный дочерний компонент, получающий `lessons[0]`, сравнит ссылку, увидит «не менялось» и не перерисуется. Результат: **часть экрана обновилась, часть нет**, причём стабильно и воспроизводимо.

Такой дефект выглядит как баг React и им не является: каждая часть системы сработала точно по правилам сравнения ссылок.

### Обновление вложенной структуры

Для структуры «курс → урок → прогресс» корректное обновление меняет ссылки **ровно по пути изменения**:

```js
const next = {
  ...course,
  lessons: course.lessons.map((lesson) =>
    lesson.id === targetId
      ? { ...lesson, progress: { ...lesson.progress, done: true } }
      : lesson                       // остальные уроки — та же ссылка
  ),
};
```

Новые ссылки: `course`, массив `lessons`, изменённый `lesson`, его `progress`. Прежние ссылки: все остальные уроки. Именно это свойство — **structural sharing** — позволяет мемоизации работать: нетронутые элементы списка не перерисуются, потому что их ссылки не менялись. Механизм разбирается в 1.13, цена в кадрах — в 5.4.

### Стили и пропсы как объекты

Инлайн-объект в `style` создаётся заново на каждый рендер, то есть каждый раз имеет новую идентичность:

```jsx
<View style={{ padding: 16 }} />   // новый объект на каждый рендер
```

Содержимое то же, идентичность другая — и для любого потребителя, который сравнивает по ссылке, это «изменившийся пропс». Здесь мы только фиксируем механизм; что с этим делать (`StyleSheet.create`, вынос константы, мемоизация) и когда это действительно важно — 1.12 и блоки 03, 05.

## Типичные заблуждения

**«Spread делает глубокую копию.»** Возникает потому, что на плоских объектах spread ведёт себя как полная копия, а плоские объекты — большинство. Расхождение проявляется только на вложенности, то есть именно там, где находится состояние реального экрана.

**«Если содержимое одинаковое, объекты равны.»** Возникает из опыта языков, где равенство объектов определяется по значению полей. В JS равенства по содержимому нет ни у одного встроенного оператора, и это не упущение: сравнение содержимого произвольной структуры — операция неизвестной стоимости, и язык не берёт её на себя.

**«`Object.freeze` замораживает вложенные объекты.»** Возникает из названия: «заморозить объект» звучит как «заморозить всё, что внутри». Заморозка применяется к свойствам конкретного объекта, а значение-ссылка остаётся ссылкой на незамороженный объект.

**«Мутация плюс `setState` работает, просто это неаккуратно.»** Самое дорогое заблуждение урока. Оно держится на реальном наблюдении: иногда экран действительно обновляется — когда рендер случился по другой причине. Это делает поведение невоспроизводимым, и дефект появляется позже, в другом месте и без связи с причиной.
