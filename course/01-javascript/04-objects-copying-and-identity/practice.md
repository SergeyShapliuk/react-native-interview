# 1.4 Objects: копирование и идентичность — practice

## Проверка понимания

---

**1. Почему после `{ ...state }` вложенный объект остался тем же?**

<details>
<summary>Ответ</summary>

Потому что spread копирует **значения** собственных перечислимых свойств, а значение поля, содержащего объект, — это ссылка. Новый объект получает ту же ссылку, то есть указывает на тот же вложенный объект. Глубина копирования — ровно один уровень, по определению операции.

**Ответ «потому что spread работает только с первым уровнем, это ограничение»** близок, но вскрывает отношение к этому как к недоработке. Это не ограничение, которое когда-нибудь уберут: глубокое копирование требует обхода неизвестной по размеру структуры, и язык сознательно не делает его неявно.

**Ответ «он не остался тем же, spread копирует всё»** вскрывает пробел, который даёт самый неприятный дефект урока — частично обновившийся экран. Проверка на понимание: `({...a}).b === a.b` при объекте в `b` даёт `true`.
</details>

---

**2. Как проверить, что два объекта — один и тот же объект?**

<details>
<summary>Ответ</summary>

Только через `===` или `Object.is`. Встроенного способа сравнить содержимое не существует.

**Ответ «через `JSON.stringify` и сравнение строк»** вскрывает смешение двух разных вопросов. Такое сравнение проверяет похожесть содержимого, а не идентичность, и при этом ненадёжно: порядок ключей влияет на результат, `Date` превращается в строку, `Set` теряется, функции выбрасываются (1.2), а циклическая структура вызывает исключение.

**Ответ «через глубокое сравнение из библиотеки»** вскрывает то же смешение. Глубокое сравнение отвечает на вопрос «одинаковое ли содержимое», и это другой вопрос, чем «тот же ли это объект». React задаёт именно второй.
</details>

---

**3. Что делает `Object.freeze` с вложенной структурой?**

<details>
<summary>Ответ</summary>

Ничего. Замораживаются свойства самого объекта; значение-ссылка продолжает указывать на незамороженный вложенный объект, и его поля меняются свободно.

Дополнительно: в нестрогом режиме попытка изменить замороженное свойство не выбрасывает ошибку, а молча ничего не делает. Для RN это не экзотика, а режим по умолчанию: модули приложения после Babel-пресета выполняются без `"use strict"` (theory, врезка о `freeze` в RN), поэтому замороженный объект в RN-коде мутацию не «ловит», а тихо её отбрасывает.

**Ответ «замораживает всё дерево»** вскрывает ожидание, что `freeze` — инструмент иммутабельности. На самом деле это инструмент **обнаружения** случайной мутации, причём только на одном уровне, и применяется он точечно, а не как защита состояния.
</details>

## Задание

**Дано.** Структура данных экрана RN-приложения и функция, которая должна отмечать шаг урока выполненным.

```js
const course = {
  id: 1,
  title: "JavaScript для RN",
  meta: { updatedAt: "2026-10-01", tags: ["js", "rn"] },
  lessons: [
    { id: 11, title: "Замыкания",  progress: { steps: [true, false], done: false } },
    { id: 12, title: "Event loop", progress: { steps: [false, false], done: false } },
  ],
};
```

**Требуется.**

1. Написать функцию `completeStep(course, lessonId, stepIndex)`, которая возвращает новый `course` с отмеченным шагом и, если все шаги урока выполнены, с `done: true` у этого урока.
2. Функция должна менять ссылки **ровно по пути изменения** и не менять остальные. Перечислить, какие именно ссылки стали новыми и какие остались прежними.
3. Доказать корректность: написать набор проверок на идентичность, который падает при любой лишней или недостающей новой ссылке.
4. Объяснить, что именно сломается на экране, если реализовать функцию через `JSON.parse(JSON.stringify(course))`. Назвать два независимых последствия.
5. Объяснить, что сломается, если реализовать её через мутацию и вернуть тот же `course`. Назвать, почему такая реализация может выглядеть работающей.

---

<details>
<summary>Разбор</summary>

**1. Реализация.**

```js
function completeStep(course, lessonId, stepIndex) {
  return {
    ...course,
    lessons: course.lessons.map((lesson) => {
      if (lesson.id !== lessonId) return lesson;      // не наш урок — та же ссылка

      const steps = lesson.progress.steps.map((value, i) =>
        i === stepIndex ? true : value
      );

      return {
        ...lesson,
        progress: {
          ...lesson.progress,
          steps,
          done: steps.every(Boolean),
        },
      };
    }),
  };
}
```

Ключевая деталь — `if (lesson.id !== lessonId) return lesson;`. Возврат исходного элемента, а не его копии, это то, что делает structural sharing возможным: нетронутые уроки сохраняют идентичность.

**2. Что изменилось, а что нет.**

**Новые ссылки** — ровно по пути от корня до изменённого значения:

- сам `course`;
- массив `lessons` (его создаёт `map`);
- изменённый `lesson` с `id === lessonId`;
- его `progress`;
- его `progress.steps`.

**Прежние ссылки:**

- все остальные элементы `lessons`, включая их `progress` и `steps`;
- `course.meta` и `course.meta.tags` — их мы не трогали, и копировать их не нужно;
- примитивы (`id`, `title`) — к ним понятие идентичности не применяется.

Правило, которое стоит запомнить формулировкой: **новых ссылок должно быть столько, какова глубина пути к изменению, и ни одной больше.**

**3. Проверки.**

```js
const next = completeStep(course, 11, 1);

// изменилось по пути
next !== course;
next.lessons !== course.lessons;
next.lessons[0] !== course.lessons[0];
next.lessons[0].progress !== course.lessons[0].progress;
next.lessons[0].progress.steps !== course.lessons[0].progress.steps;

// не изменилось вне пути
next.lessons[1] === course.lessons[1];
next.meta === course.meta;
next.meta.tags === course.meta.tags;

// исходные данные не тронуты
course.lessons[0].progress.steps[1] === false;
course.lessons[0].progress.done === false;

// результат верный
next.lessons[0].progress.steps[1] === true;
next.lessons[0].progress.done === true;
```

Набор устроен так, что ловит обе ошибки сразу: первая группа падает при мутации (ссылки не изменились), вторая — при избыточном копировании (изменилось то, что не должно), третья — при мутации входа, четвёртая проверяет собственно логику.

Именно этот набор становится базовым unit-тестом домена в RN Academy P1 (Testing Progression).

**4. Реализация через `JSON.parse(JSON.stringify(...))`.**

Работать будет — и именно поэтому встречается в проектах. Два независимых последствия:

- **потеря мемоизации на всём экране.** Глубокое копирование создаёт новые объекты для **каждого** узла структуры, включая те, что не менялись. Все элементы `lessons` получат новые ссылки, `meta` тоже, и ни один мемоизированный дочерний компонент не сможет определить, что его данные не изменились. В длинном списке это означает перерисовку всех ячеек вместо одной — видимую в кадрах при скролле (5.4);

- **молчаливая порча данных.** Всё, что не описывается форматом JSON, потеряется (1.2): `Date` в `updatedAt` превратилась бы в строку, `Set` в полях — в пустой объект, `undefined`-поля исчезли бы. В текущей структуре таких полей нет, но функция вроде `completeStep` переживает структуру: как только в курс добавят `Date` или `Map`, обновление прогресса начнёт тихо портить данные, и связь с причиной будет потеряна.

Третий, менее важный пункт: стоимость обхода структуры целиком на каждое нажатие.

**5. Реализация через мутацию.**

```js
function completeStep(course, lessonId, stepIndex) {
  const lesson = course.lessons.find((l) => l.id === lessonId);
  lesson.progress.steps[stepIndex] = true;
  lesson.progress.done = lesson.progress.steps.every(Boolean);
  return course;                 // та же ссылка
}
```

Что сломается: React сравнит предыдущее состояние с новым, получит ту же идентичность и не запланирует рендер. Данные изменились, экран — нет.

**Почему это выглядит работающим.** Состояние экрана обновится, как только рендер случится по любой другой причине: другое изменение состояния, рендер родителя, возврат на экран, изменение навигации. В реальном приложении такие причины возникают часто, поэтому отметка шага «появляется», просто иногда с задержкой или после касания в другом месте. Разработчик видит работающую функцию и странное поведение, которое списывает на React.

Отсюда вывод, который этот урок должен оставить: **иммутабельность в React — не вопрос аккуратности, а условие корректности.** Мутация не делает код «менее чистым», она делает обновление экрана недетерминированным. Почему именно так устроено обнаружение изменений и чем за это платят — 1.13 и 3.10.
</details>
