# 1.15 Execution context и scope chain — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок разводит две структуры, которые в обсуждениях постоянно схлопываются в одну: **стек вызовов** отвечает «кто меня вызвал», **цепочка областей видимости** отвечает «где искать это имя». Из их смешения растут почти все заблуждения темы.

---

## 1. Что это

**Execution context (контекст исполнения)** — то, что движок создаёт при входе в исполняемый код: при вызове функции, при запуске модуля, при выполнении скрипта. В контексте есть всё, что нужно для исполнения: lexical environment, значение `this`, точка возврата.

**Call stack (стек вызовов)** — структура, в которой контексты лежат в порядке вложенности вызовов. Вызов функции кладёт контекст сверху, `return` снимает его. Стек существует только в рантайме и меняется постоянно.

**Lexical environment (лексическое окружение)** — хранилище связываний имён для одной области видимости: параметры, объявленные переменные, объявленные функции. У каждого окружения есть ссылка на **внешнее** окружение — то, внутри которого эта область видимости была объявлена.

**Scope chain (цепочка областей видимости)** — последовательность окружений, получаемая переходом по этим ссылкам наружу, от текущего до глобального. Это путь поиска имени.

### Две структуры, которые нельзя путать

| | Call stack | Scope chain |
|---|---|---|
| отвечает на вопрос | кто меня вызвал | где искать это имя |
| когда определяется | в рантайме, на каждом вызове | в момент написания кода |
| чем формируется | порядком **вызовов** | местом **объявления** |
| меняется ли для одной функции | да, при каждом вызове разный | нет, никогда |
| что видно в отладчике | список кадров | список областей видимости текущего кадра |

Одна и та же функция, вызванная из десяти разных мест, получит десять разных стеков и одну и ту же цепочку областей видимости. Это главное утверждение урока.

## 2. Как это работает

### Стек вызовов

```js
function third()  { throw new Error("boom"); }
function second() { third(); }
function first()  { second(); }
first();
```

На момент `throw` стек выглядит так (сверху — текущий кадр):

```
third      ← текущий
second
first
<module>
```

Именно этот снимок попадает в `error.stack`. Стектрейс — это **состояние стека на момент создания объекта ошибки**, а не на момент её обработки (1.11): если ошибку перебросить из `catch`, стек в новом объекте будет другим.

Когда `third` возвращает управление, её кадр снимается — безвозвратно. Отсюда свойство, важное для асинхронного кода: к моменту выполнения колбэка таймера стек, в котором таймер был запланирован, уже снят, и в стектрейсе колбэка его не будет (1.20).

### Цепочка областей видимости

```js
const appName = "RN Academy";              // окружение модуля

function makeFormatter(prefix) {           // окружение makeFormatter
  const separator = ": ";

  return function format(message) {        // окружение format
    return appName + separator + prefix + separator + message;
  };
}
```

Цепочка для `format`:

```
окружение format        → message
    ↓ внешнее
окружение makeFormatter → prefix, separator
    ↓ внешнее
окружение модуля        → appName, makeFormatter
    ↓ внешнее
глобальное окружение    → globalThis, console, ...
```

Поиск идёт строго снаружи некуда — только наружу, и останавливается на первом найденном связывании. Если имени нет нигде — `ReferenceError`.

Ключевое: эта цепочка выстроена ссылками, которые записаны при **создании** `format`, то есть в момент выполнения `makeFormatter`. Где и кем `format` будет вызвана потом — для цепочки не имеет значения.

### Scope определяется местом объявления

Это утверждение проверяется одним примером, где две модели дают разные ответы:

```js
const value = "module";

function read() {
  return value;              // какое value?
}

function caller() {
  const value = "caller";
  return read();
}

caller();   // "module"
```

**Lexical scope (лексическая область видимости)** — та, что в JavaScript: `read` объявлена на уровне модуля, её внешнее окружение — модуль, и `value` она найдёт там. Локальная `value` внутри `caller` для `read` не существует: `caller` находится в её **стеке вызовов**, но не в её **цепочке областей видимости**.

**Dynamic scope (динамическая область видимости)** — гипотетическая альтернатива, при которой `read` искала бы имена в окружении вызывающего и вернула бы `"caller"`. Так JavaScript не работает ни в одном случае.

Почему это выбор, а не случайность: при лексическом scope функцию можно прочитать локально. Чтобы понять, откуда она берёт каждое имя, достаточно посмотреть наружу по тексту программы. При динамическом — пришлось бы знать всех вызывающих, то есть статический анализ, автодополнение и минификация стали бы невозможны.

**Единственное исключение в языке — `this`.** Для обычных функций он определяется способом вызова, то есть динамически. Это и есть причина, по которой `this` вынесен в отдельный урок (1.16): он не подчиняется правилам этого урока.

### Окружение модуля

Модуль — тоже исполняемый код со своим контекстом, и выполняется он **один раз**, при первом включении в граф (1.10):

```js
// config.js
const startedAt = Date.now();
export const getStartedAt = () => startedAt;
```

Сколько бы модулей ни импортировали `config.js`, `startedAt` вычислится однажды, и все получат одно значение. Окружение модуля создаётся один раз и живёт всё время работы приложения — это **singleton по механизму**, а не по соглашению.

Следствие, которое пригодится дальше: функция, объявленная на верхнем уровне модуля, замыкает окружение, живущее до завершения процесса (1.14). Модульная переменная не освобождается никогда.

### Порядок инициализации

Окружение модуля создаётся до выполнения его кода (все объявления подняты), но **инициализируется** построчно. Отсюда поведение циклических импортов:

```js
// a.js
import { b } from "./b.js";
export const a = "A";
console.log(b);        // undefined, если цикл замкнулся через b.js

// b.js
import { a } from "./a.js";
export const b = a + "B";
```

Ошибки сборки нет: связывание `a` существует (поднято), но на момент выполнения `b.js` ещё не инициализировано. В рантайме это выглядит как `undefined` вместо импортированного значения — часто далеко от места настоящей причины (1.10).

### Что видно в отладчике

В точке останова отладчик показывает две панели, и теперь понятно, что это за структуры: список кадров — стек вызовов, список Scope (Local / Closure / Module / Global) — цепочка областей видимости текущего кадра. Раздел Closure в этом списке — это ровно те внешние окружения, которые удерживает функция (1.14).

## 3. Почему это важно

Вопрос «откуда функция берёт это имя» возникает в работе в трёх видах, и все три требуют одной модели.

**Чтение незнакомого кода.** Чтобы понять, что делает функция, нужно знать, что для неё означает каждое имя. При лексическом scope ответ находится чтением текста наружу, и это свойство языка, на которое можно опираться.

**Чтение стектрейса.** Стек показывает путь вызовов, а не путь доступа к данным. Ошибка «cannot read property of undefined» в кадре `third` означает, что неверное значение попало в `third` — но объявлено оно может быть где угодно, и стек этого не покажет. Понимание, что это разные структуры, экономит время поиска.

**Рассуждение о времени жизни.** Цепочка областей видимости — это одновременно цепочка удержания (1.14). Длина и состав цепочки определяют, что остаётся живым, пока жива функция. То есть scope chain — не академическое понятие, а то, что видно в снимке памяти.

Из смешения двух структур растёт конкретная ошибка в работе: разработчик пытается объяснить значение переменной через то, откуда функция вызвана, не находит объяснения и заключает, что «здесь какая-то магия». Магии нет — просто искали не в той структуре.

## 4. Где это в React Native

### Чтение стектрейса из crash-репорта

Стектрейс из Sentry или Crashlytics для release-сборки принадлежит **не тому коду, который вы писали**. Между ними два преобразования:

- **транспиляция** — Babel переписал современный синтаксис; `async`-функция превратилась в конечный автомат, стрелочные функции могли быть переименованы, классовые поля превратились в присваивания в конструкторе;
- **минификация** — имена функций и переменных заменены на короткие, границы модулей стёрты, часть функций встроена в вызывающие.

В результате кадры стека — это кадры трансформированного кода: вместо `loadCourseProgress` в отчёте `t`, вместо строки 142 исходника — строка 1 бандла. Восстановление соответствия называется **symbolication** и выполняется по source map, загруженной вместе со сборкой (10.6).

Что из этого урока нужно, чтобы читать такой отчёт:

- кадры читаются сверху вниз как путь вызовов: верхний — где бросило, нижний — откуда началось. Верхний кадр показывает место ошибки, но не обязательно её причину: неверное значение могло быть создано в любом кадре ниже;
- встроенные (inlined) функции в стеке отсутствуют — не потому что не вызывались, а потому что их код оказался внутри вызывающей;
- асинхронная граница рвёт стек: кадры, запланировавшие колбэк, уже сняты, и в отчёте их нет. Поэтому стектрейс из колбэка начинается «из ниоткуда» и состоит из кадров движка плюс ваш колбэк (1.20);
- «ошибка в `node_modules`» в верхнем кадре почти никогда не означает дефект библиотеки: обычно это библиотека, получившая от вашего кода значение, которого не ожидала.

### Модульный scope как singleton

Это самое практически значимое следствие урока для архитектуры RN-приложения:

```js
// api/client.js
let authToken = null;
export const setToken = (t) => { authToken = t; };
export const getToken = () => authToken;
```

`authToken` — одно значение на всё приложение, на всю сессию, для всех экранов. Положительно: именно так корректно хранить то, что по смыслу одно — сетевой клиент, конфигурация, инициализированный SDK. Отрицательно: любое состояние, положенное в модульный scope «чтобы было доступно», становится глобальным — не освобождается, не изолируется между экранами, не сбрасывается между тестами.

Последнее стоит отметить отдельно: тесты в одном файле делят окружение модуля, поэтому состояние, записанное одним тестом, видно следующему, и падение выглядит как зависимость тестов от порядка (11.3).

Отдельный RN-специфичный случай — **Fast Refresh**. При горячем обновлении модуль может быть переисполнен, и модульное состояние сбрасывается или, наоборот, сохраняется не так, как ожидается; поведение в dev и в production различается. Код, корректность которого зависит от модульного состояния, в dev ведёт себя иначе — и это источник расхождений «на устройстве работает по-другому».

### Порядок инициализации на старте

Код верхнего уровня всех модулей графа выполняется при загрузке бандла, до первого рендера. Два следствия для RN:

- тяжёлая работа на верхнем уровне модуля (разбор большого JSON, построение индекса, создание клиента с проверкой сети) напрямую удлиняет время до первого экрана, и это одна из причин TTI, которую видно не в профайлере React, а только в замере старта (5.1, 5.10);
- ошибка в коде верхнего уровня падает до того, как появился хоть один компонент — Error Boundary её не перехватит (3.11), и в release это краш на старте без видимого экрана.

Отсюда правило домена, зафиксированное в 1.10: никаких side effect на верхнем уровне модуля.

## 5. Типичные ошибки

**«Scope определяется тем, откуда функция вызвана».** Возникает по двум причинам. Первая — опыт `this`: в том же языке есть сущность, которая действительно зависит от вызова, и это создаёт ложное обобщение. Вторая — отладчик: в нём видны одновременно кадры стека и области видимости, и локальные переменные вызывающего кадра находятся буквально рядом с окружением текущего. Практическая цена: разработчик ищет объяснение значения в вызывающем коде, не находит и перестаёт доверять модели — а дальше объясняет поведение случайностью.

**«Стек вызовов и scope chain — одно и то же».** Возникает из того, что для вложенных функций они часто совпадают по форме: если `format` объявлена внутри `makeFormatter` и вызывается оттуда же, обе цепочки выглядят одинаково. Расхождение проявляется ровно там, где функция передана наружу — то есть в колбэках, подписках, обработчиках, то есть во всём асинхронном коде. Цена ошибки: неверные выводы из стектрейса («переменная пришла из этого кадра») и невозможность объяснить stale closure, где функция смотрит в окружение, которого в стеке давно нет.

**«Каждый импорт модуля создаёт новое окружение».** Возникает из аналогии с вызовом функции: `import` выглядит как операция получения чего-то, и кажется, что каждое получение даёт свой экземпляр. На самом деле модуль выполняется один раз, а `import` только связывает имя с уже существующим значением. Цена: модульная переменная используется как «локальная для фичи», и обнаруживается общей — утечка состояния между экранами, непредсказуемые тесты, значение, вычисленное на старте и не обновившееся за сутки работы приложения.

**Ожидание, что `this` подчиняется правилам scope.** Возникает потому, что `this` выглядит как обычное имя и находится «где-то снаружи». Правила у него другие — динамические, для обычных функций (1.16). Цена: попытка объяснить потерю `this` через область видимости, которая не объясняет ничего, и следующий за этим вывод, что «надо везде стрелочные функции».

**Чтение верхнего кадра стектрейса как причины.** Возникает из того, что верхний кадр всегда указан первым и выглядит как ответ. Он указывает место обнаружения ошибки. Причина — место, где было создано неверное значение, и находится она движением вниз по стеку, а иногда вообще не в стеке (значение пришло из состояния или из замыкания).

**Ожидание, что стектрейс из колбэка покажет, кто его запланировал.** Возникает из опыта синхронного кода, где стек полный. Кадры, запланировавшие асинхронный колбэк, сняты до его выполнения. Цена: поиск причины в кадрах движка вместо поиска места планирования по коду.

**Опора на «работающий» порядок инициализации модулей.** Возникает, когда циклическая зависимость случайно разрешается в рабочем порядке. Порядок определяется графом модулей и точкой входа, то есть изменится при любом изменении импортов — и сломается в другом месте (1.10).

## 6. Trade-offs

### Глубокая вложенность: читаемость против удержания

| | Вложенные функции | Плоские функции с параметрами |
|---|---|---|
| доступ к контексту | бесплатный: всё видно из цепочки | явный: нужно передавать |
| длина кода | короче | длиннее |
| что удерживается | все внешние окружения цепочки | только переданные аргументы |
| тестируемость | требует воссоздания контекста | вызывается напрямую |
| читаемость в точке объявления | контекст рядом | контекст в сигнатуре |

Вложенность выигрывает для короткоживущих функций: контекст рядом, кода меньше, окружение освободится сразу. Проигрывает для долгоживущих: по коду внутренней функции не видно, какой объём она держит, а держит она всю цепочку (1.14).

Рабочая формулировка: **чем дольше живёт функция, тем ближе к плоскому должно быть её объявление.** Обработчик нажатия — вкладывать; колбэк подписки уровня приложения — выносить и передавать нужное явно.

### Модульный scope против передачи аргументом

| | Модульное состояние | Передача аргументом |
|---|---|---|
| доступ | из любого модуля через импорт | только там, где передали |
| время жизни | вся работа приложения | вызов |
| тестируемость | требует сброса между тестами | подставляется в вызове |
| что видно в сигнатуре | ничего | все зависимости |

Модульный scope уместен для того, что по смыслу единственно: сетевой клиент, конфигурация сборки, инициализированный SDK, кэш с явной политикой (1.22). Неуместен для всего, что относится к экрану, пользователю или сессии: «удобно достать откуда угодно» оборачивается тем, что никто не знает, кто это записал.

### Стектрейс против логирования контекста

Стектрейс бесплатен и показывает путь вызовов, но не показывает значения. Логирование контекста показывает значения, но стоит кода и попадает в crash-репорт только если написано заранее.

Практический вывод для RN: стектрейс даёт форму ошибки, а чтобы по отчёту из production восстановить причину, нужны ещё и данные — поэтому breadcrumbs и контекст к ошибке добавляют осознанно (10.6). Выбор «что логировать» принимается до релиза: после краша добавить контекст в уже полученный отчёт невозможно.

**Главное, что должно остаться после урока.** Две структуры, две разные вопросы. «Кто меня вызвал» — стек, собирается в рантайме, меняется постоянно. «Где искать это имя» — цепочка областей видимости, определена местом объявления, не меняется никогда. Всё, что в языке выглядит как исключение из этого правила, сводится к одному — `this`, и это следующий урок.
