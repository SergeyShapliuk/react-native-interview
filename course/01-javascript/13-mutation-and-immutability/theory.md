# 1.13 Mutation и immutability — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как правильно писать обновление состояния» — а на вопрос, **почему обнаружение изменений вообще возможно только при иммутабельности, и какую цену за это платит приложение.**

---

## 1. Что это

**Mutation (мутация)** — изменение содержимого существующего объекта. Объект остаётся тем же, меняется то, что внутри.

**Immutability (иммутабельность)** — дисциплина, при которой существующий объект никогда не изменяется: вместо изменения создаётся новое значение, а старое остаётся прежним.

Ключевое различие между двумя операциями:

| | Мутация | Замена |
|---|---|---|
| что происходит | меняется содержимое объекта | создаётся новый объект |
| identity | остаётся прежней | новая |
| старое значение | перестало существовать | продолжает существовать |
| наблюдаемость через `===` | **не наблюдаема** | наблюдаема одной операцией |

```js
// мутация
const state = { count: 1 };
const before = state;
state.count = 2;
before === state;      // true — изменение произошло, identity та же

// замена
let next = { count: 1 };
const prev = next;
next = { ...next, count: 2 };
prev === next;         // false — изменение наблюдаемо
prev.count;            // 1 — старое значение цело
```

Иммутабельность в JavaScript — **соглашение, а не свойство языка**. Объекты изменяемы всегда; `Object.freeze` даёт поверхностную защиту и свою цену (разобрано в 1.4). То есть иммутабельность здесь не гарантируется средой, её обеспечивает код.

**Structural sharing (разделение структуры)** — приём, при котором новое значение собирается из нового узла и **прежних ссылок** на неизменившиеся части старого. Это не оптимизация поверх иммутабельности, а её рабочая форма: без structural sharing иммутабельное обновление означало бы копирование всего дерева.

## 2. Как это работает

### Правило пути

Возьмём структуру на три уровня и изменим одно поле в самом низу.

```js
const state = {
  user: { id: 1, name: "Serge" },
  course: {
    id: 42,
    title: "React Native",
    progress: { completed: ["1.1"], current: "1.12" },
  },
};
```

Нужно поменять `course.progress.current`. Путь от корня до изменения: `state` → `course` → `progress`. Три узла, значит три новых ссылки:

```js
const next = {
  ...state,
  course: {
    ...state.course,
    progress: { ...state.course.progress, current: "1.13" },
  },
};
```

Что получилось:

```js
next !== state;                            // новый — узел пути
next.course !== state.course;              // новый — узел пути
next.course.progress !== state.course.progress; // новый — узел пути

next.user === state.user;                  // ТОТ ЖЕ — вне пути
next.course.progress.completed === state.course.progress.completed; // ТОТ ЖЕ
```

> **Правило, которое стоит унести из урока: число новых ссылок равно длине пути от корня до изменения, и ни на одну больше.**

Отклонение в любую сторону — дефект, и дефекты эти разного рода:

- **меньше** новых ссылок, чем длина пути — значит где-то произошла мутация. Изменение не будет обнаружено: потребитель сравнит прежнюю ссылку с прежней и заключит, что обновлять нечего (1.12, угол 3);
- **больше** новых ссылок — значит скопированы ветви, которые не менялись. Их потребители получат «изменилось» на неизменившихся данных и выполнят работу зря.

Вторая ошибка не ломает корректность, но именно она даёт замедление, которое потом ищут профайлером.

### Почему новый корень обязателен всегда

Любое изменение внутри структуры требует новой ссылки на корень — даже если изменилось поле на пятом уровне. Причина простая: подписчик смотрит на корень. Если его идентичность не изменилась, он не узнает, что внутри что-то произошло, сколько бы новых ссылок ни появилось в глубине.

Отсюда следует и обратное: **новая ссылка на корень без новых ссылок по пути бесполезна наполовину.** Корневой подписчик обновится, а мемоизированный потребитель глубокой ветви — нет, потому что его ветвь осталась прежним объектом. Это даёт частично обновившийся экран — худший вид дефекта, потому что он выглядит как «иногда не работает».

### Массивы

Для массива правило то же, но узлов на один больше: сам массив и изменяемый элемент.

```js
const next = {
  ...state,
  lessons: state.lessons.map((lesson) =>
    lesson.id === id ? { ...lesson, done: true } : lesson
  ),
};
```

Критична ветка `: lesson` — возврат исходного элемента, а не его копии. Именно она делает structural sharing возможным: новую идентичность получают массив и один элемент, остальные элементы переносятся как есть. Замена этой ветки на `{ ...lesson }` даёт формально корректный, но катастрофический по последствиям результат — см. угол 4.

`map` всегда возвращает новый массив (1.6), поэтому отдельно копировать его через spread не нужно. А `[...state.lessons]` **сам по себе** не решает задачу: он даёт новую идентичность контейнеру и ничего не делает с элементами (1.12, задание 2).

### Immer: что он делает на самом деле

Immer — библиотека, которая позволяет писать обновление в виде мутации, не мутируя исходные данные.

```js
import { produce } from "immer";

const next = produce(state, (draft) => {
  draft.course.progress.current = "1.13";
});
```

Механизм, и здесь важна точность:

1. `produce` создаёт **draft (черновик)** — обёртку над исходным объектом через **Proxy**, объект-посредник, перехватывающий обращения к свойствам;
2. все чтения проксируются вниз, к исходным данным; все записи перехватываются и складываются в сторону, в исходный объект **не попадают**;
3. по завершении функции Immer собирает новое значение: создаёт новые объекты по пути сделанных изменений и переносит прежние ссылки на всё, что не трогали.

Три следствия, которые нужно знать точно:

- **исходный объект не мутируется.** `state` после `produce` побитово тот же, что до. Утверждение «Immer мутирует данные» неверно — мутируется draft, а он существует только внутри вызова;
- **результат имеет те же идентичности, что и ручное обновление по правилу пути.** Immer не «экономит» ссылки и не создаёт лишних — он реализует structural sharing;
- **если в `produce` ничего не изменено, возвращается исходный объект** — та же ссылка, не копия. Это свойство полезно: отсутствие изменений не создаёт ложного «изменилось».

Что Immer скрывает — не факт мутации, а **то, какие именно ссылки получились новыми**. Код выглядит как мутация, и по нему нельзя прочитать границу structural sharing. В ручном варианте каждая новая ссылка написана явно: видно, что `user` не копируется, а `progress` копируется. В варианте с Immer видна только одна строка присваивания, а набор новых идентичностей нужно вывести в голове. Это и есть его цена: краткость в обмен на предсказуемость идентичностей.

## 3. Почему это важно

Иммутабельность в React — не вопрос стиля. Это **предусловие работоспособности механизма обнаружения изменений.**

Логика целиком:

1. чтобы узнать, изменились ли данные, можно сравнить содержимое или сравнить идентичность;
2. сравнение содержимого стоит пропорционально размеру структуры, то есть неизвестно сколько; сравнение идентичности стоит одну операцию всегда (1.12, угол 3);
3. React выбрал второе — через `Object.is`;
4. из этого выбора следует требование: **изменение данных обязано сопровождаться изменением идентичности**;
5. мутация меняет данные, не меняя идентичности, то есть делает изменение принципиально ненаблюдаемым для выбранного механизма.

Шаг 5 — вся суть. Мутация не «нарушает конвенцию» — она производит изменение, о котором система не может узнать, потому что единственный доступный ей вопрос («та же ссылка?») даёт ответ «да».

### Почему мутация «иногда работает»

Это самое важное место урока на практике, потому что именно здесь ломается модель у опытных разработчиков.

```js
function markDone(lesson) {
  lesson.done = true;        // мутация
  setLessons(lessons);       // та же ссылка
}
```

Иногда после такого кода экран обновляется. Не потому, что мутация сработала, а потому что **рендер случился по другой причине**:

- в том же обработчике изменилось другое состояние, и этот рендер показал заодно и мутированные данные;
- перерисовался родитель — по своей причине, протащив за собой дочерние компоненты;
- экран ушёл и вернулся, и компонент смонтировался заново, прочитав данные свежими;
- сработал таймер, подписка, фокус навигации.

Во всех случаях мутированное значение попало в кадр **попутно**. Вывод, который отсюда следует, формулируется так:

> Проблема не в нарушении стиля. Проблема в том, что обновление экрана становится **недетерминированным** — оно происходит, когда рядом случилось что-то ещё.

Поэтому дефект проявляется поздно, у другого разработчика, после снятия лишнего рендера или добавления `memo` — то есть после «оптимизации», которая просто убрала случайный триггер. Правило «не мутируем состояние» существует ради детерминированности, а не ради чистоты.

### Почему избыточное копирование тоже важно

Зеркальная сторона. Deep copy ради одного поля даёт корректный результат: изменение обнаружится. Но новая идентичность появится у **каждого** узла, и каждый потребитель неизменившейся ветви получит ответ «изменилось». Мемоизация, построенная ровно на том, что неизменившееся сохраняет ссылку, перестаёт отсекать что-либо.

То есть корректность и стоимость здесь разведены: мутация ломает первое, избыточное копирование — второе. Правило пути закрывает обе ошибки одной формулировкой.

## 4. Где это в React Native

Четыре места, где разница между «новая ссылка по пути» и «новое всё» наблюдаема.

### Состояние компонента

```jsx
const [form, setForm] = useState({ email: "", profile: { name: "", city: "" } });

// не сработает
const onChange = (city) => {
  form.profile.city = city;
  setForm(form);
};

// сработает
const onChange = (city) =>
  setForm((prev) => ({ ...prev, profile: { ...prev.profile, city } }));
```

В первом варианте `setForm` получает ту же ссылку. React сравнивает через `Object.is`, получает равенство и имеет право не планировать рендер вообще. Поле в UI не обновится — ровно до следующего рендера по другой причине.

### Данные списка — здесь это видно в кадрах

Главный RN-специфичный случай, и он измерим.

```jsx
// плохо: новая ссылка у КАЖДОГО элемента
setLessons((prev) => prev.map((l) => ({ ...l, done: l.id === id })));

// правильно: новая ссылка у массива и у ОДНОГО элемента
setLessons((prev) =>
  prev.map((l) => (l.id === id ? { ...l, done: true } : l))
);
```

Разница не стилистическая. В первом варианте ни одна мемоизированная ячейка не может определить, что её данные те же, — перерисовывается **весь видимый список вместо одной ячейки**. На списке из десяти элементов это незаметно. На списке из нескольких сотен уроков при отметке одного завершённым это даёт просадку кадров, видимую как подвисание при тапе; при скролле поверх такого обновления — дроп кадров. Механика рециклинга ячеек и то, как её ломают, — 5.4; как доказать причину профайлером, а не рассуждением — 5.3.

Это тот случай, где «иммутабельность как стиль» и «иммутабельность как механизм» дают разный код: формально иммутабельны оба варианта.

### Редьюсеры

В редьюсере требование жёстче, потому что потребителей больше: подписчики стора, селекторы, мемоизированные компоненты. Правило пути то же; специфика — что `state` редьюсера нельзя мутировать даже «для скорости», а Redux Toolkit применяет Immer внутри, поэтому код в `createSlice` выглядит как мутация, будучи иммутабельным обновлением. Разбор — 6.4; селекторы как отдельный потребитель идентичности — 6.5; нормализация структуры, которая укорачивает путь обновления, — 6.8.

### Персистентный стейт

Сохранённое состояние — это снимок структуры, который переживёт перезапуск приложения и обновление версии. Два следствия именно для этого урока:

- мутация объекта, который уже попал в очередь на сериализацию, даёт запись значения, которого в состоянии не было ни в один момент времени;
- форма структуры становится контрактом с данными на устройстве пользователя: изменение формы требует миграции, а не просто новой ссылки (6.6).

### Optimistic update

Иммутабельность даёт то, без чего откат невозможен: предыдущее значение продолжает существовать. При мутации старого состояния нет — откатывать не к чему, остаётся повторный запрос. Это прямое практическое следствие того, что замена сохраняет старое значение (угол 1). Очередь мутаций, optimistic updates и откат — 7.14.

## 5. Типичные ошибки

**Глубокая мутация внутри «иммутабельного» обновления.** Самая частая и самая трудная в диагностике:

```js
const next = { ...state };
next.course.progress.current = "1.13";   // мутация ОБЩЕГО объекта
```

Верхний уровень скопирован, и код выглядит правильным. Но `next.course` — тот же объект, что `state.course` (1.4), поэтому запись изменила исходное состояние. Возникает из модели «spread делает копию» без различения уровней. Проявляется как частично обновившийся экран и как «состояние изменилось само».

**Копирование всего дерева ради одного поля.** `structuredClone(state)`, `JSON.parse(JSON.stringify(state))` или рекурсивный spread. Корректно и дорого вдвойне: аллокации пропорциональны размеру всей структуры, и мемоизация ломается у всех ветвей. Возникает из посылки «глубже — безопаснее»; разбор посылки — угол 6. У JSON-варианта есть отдельная цена: он теряет `undefined`, `Date` превращает в строку, `Map` и функции выбрасывает — то есть меняет данные, а не только ссылки.

**`sort` на массиве из состояния.** Отдельным пунктом, потому что ошибка выглядит безобидно:

```js
const sorted = lessons.sort((a, b) => a.order - b.order);
```

`sort` мутирует массив и возвращает **его же** (1.5). Значит `sorted === lessons`: состояние тихо переупорядочено на месте, а новой ссылки нет. Два дефекта сразу — незамеченное изменение и мутация состояния из кода отображения. То же с `reverse`, `splice`, `push`. Правильно — `[...lessons].sort(...)` или `lessons.toSorted(...)`; в компоненте такая сортировка ещё и выполняется на каждом рендере, создавая новую ссылку `data` для списка (1.12).

**Мутация элемента после копирования контейнера.** `const next = [...items]; next[0].done = true;` — контейнер новый, элемент общий. Изменение уходит в исходный массив.

**Мутация входного аргумента в функции домена.** Функция получает копию ссылки и может изменить объект вызывающего (1.12). Снаружи это читается как «данные испортились сами».

**Сборка нового объекта там, где ничего не изменилось.** Обновление, которое всегда возвращает новую структуру, даже если новое значение равно старому. Формально корректно, по факту — поток ложных «изменилось».

**Иммутабельность, применённая везде одинаково.** Структуры, у которых нет потребителя, сравнивающего по ссылке — локальный буфер, аккумулятор внутри `reduce`, массив, собираемый в приватной функции, — не требуют иммутабельного обновления. Мутация локального объекта, не покинувшего область видимости, никому не наблюдаема и ничего не ломает.

## 6. Trade-offs

### Иммутабельность стоит аллокаций и кода

| | Мутация | Иммутабельное обновление |
|---|---|---|
| стоимость операции | одна запись | аллокации по пути изменения |
| объём кода | одна строка | вложенные spread по глубине |
| обнаружение изменений | не работает | работает надёжно |
| старое значение | потеряно | доступно: отладка, откат, undo |
| риск ошибки | мутация общего объекта | избыточное или недостаточное копирование |

Выбор сделан не потому, что иммутабельность дешевле — она дороже. Он сделан потому, что обнаружение изменений по идентичности требует её как предусловия, а само это обнаружение стоит одну операцию вместо обхода структуры.

Про стоимость аллокаций стоит сказать точно, чтобы не породить обратную крайность: новые объекты по пути изменения — это несколько короткоживущих объектов на одно действие пользователя, и в современных движках они дёшевы (1.23). Дорого становится там, где путь длинный или обновления идут потоком — скролл, жесты, анимации.

### Глубина структуры — это цена каждого обновления

Чем глубже лежит поле, тем длиннее путь и тем больше новых объектов на одно изменение. Отсюда следствие, которое обычно формулируют как «нормализация»: плоская структура с сущностями по идентификатору превращает путь из пяти узлов в два. Цена — лишний уровень косвенности при чтении и код на сборку данных для экрана. Когда это окупается, а когда это оверинжиниринг — 6.8.

### Immer стоит понятности

| | Ручной spread | Immer |
|---|---|---|
| объём кода на глубокое обновление | растёт с глубиной | одна строка |
| видимость новых ссылок | явная, читается из кода | нужно выводить |
| ошибка «не скопировал уровень» | возможна | невозможна |
| ошибка «скопировал лишнее» | возможна | невозможна |
| стоимость в рантайме | только аллокации | Proxy на каждое обращение плюс сборка результата |
| порог входа в код | нулевой | нужно знать, что это не мутация |

Immer убирает оба отклонения от правила пути — и это его настоящая ценность, более важная, чем краткость. Платой становится то, что границу structural sharing больше не видно в коде: обсуждение «почему эта ячейка перерисовалась» требует восстановить набор новых идентичностей по тексту, который выглядит как мутация.

Практический вывод: Immer хорошо окупается на глубоких структурах и в редьюсерах, где обновлений много и они однотипны. На обновлении одного поля плоского объекта он добавляет зависимость и непрозрачность, не убирая ничего.

### Shallow copy против deep copy

Сравнение разобрано в 1.12 (угол 6) и 1.4. Здесь только вывод в терминах этого урока: deep copy — это способ получить гарантированно правильный ответ «изменилось» ценой потери всех ответов «не изменилось». В системе, где мемоизация построена на второй группе ответов, это плохой обмен. Правило пути даёт обе гарантии.

### Иммутабельность как контракт модуля

Можно обеспечивать иммутабельность только на границе состояния, а внутри функций домена работать как удобно. Можно объявить правилом всего кода. Первое дешевле и допускает локальные мутации там, где они не наблюдаемы; второе проще в проверке на code review, потому что не требует обсуждать, покинул ли объект область видимости. Выбор — архитектурное решение (8.2), а не следствие языка.

## 7. Связи с другими частями системы

**Назад:**

- **1.12** — identity, referential equality, pass-by-value: язык, на котором сформулирован весь этот урок;
- **1.4** — shallow copy и `Object.freeze`: механика копирования одного уровня;
- **1.5** — мутирующие методы массива: источник ошибки с `sort`;
- **1.6** — `map` / `filter`: инструменты обновления коллекции с сохранением ссылок на неизменившиеся элементы;
- **1.8** — spread: синтаксис, которым записывается путь;
- **1.3** — `Object.is`: алгоритм, который проверяет результат вашего обновления.

**Вперёд:**

- **1.14 Closures** — почему обработчик, замкнувший старое состояние, видит старое значение: ещё один способ получить несогласованные данные, уже не через мутацию;
- **1.22 Memory** — почему структуры, разделяющие части друг с другом, не удваивают память, и что держит старое значение живым;
- **1.23 Garbage collection** — что происходит с заменёнными узлами и почему короткоживущие объекты дёшевы;
- **1.24 Синтез** — сборка: references, closures, immutability, память — в одну модель ре-рендеров и утечек;
- **3.7 Referential equality** — что именно сравнивает React и чем это ограничено;
- **3.8 Memoization** — где мемоизация, которую сохраняет structural sharing, действительно окупается;
- **5.3 Диагностика лишних ре-рендеров** — как доказать, что перерисовался весь список, а не одна ячейка;
- **5.4 Списки и рециклинг** — почему именно на списке цена избыточных новых ссылок измеряется в кадрах;
- **6.4 Immutability в редьюсерах** — то же правило в контексте стора, с Immer внутри Redux Toolkit;
- **6.6 Персистентность и миграции схемы** — что происходит, когда форма иммутабельной структуры меняется между версиями приложения;
- **6.8 Нормализация** — как сократить длину пути обновления и чего это стоит;
- **7.14 Offline-first** — откат optimistic update как прямое применение того, что старое значение продолжает существовать.

**Главное, что должно остаться после урока.** Иммутабельность — не свойство хорошего кода, а условие, при котором изменение данных становится наблюдаемым. Правило одно и проверяемое: новых ссылок ровно столько, какова длина пути от корня до изменения. Меньше — изменение потеряно, больше — потеряна мемоизация. Immer выполняет это правило за вас, не показывая результат.
