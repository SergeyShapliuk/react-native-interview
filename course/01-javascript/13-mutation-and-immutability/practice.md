# 1.13 Mutation и immutability — practice

## Проверка понимания

Три вопроса уровня собеседования. Каждый проверяет не формулировку правила, а понимание того, **что произойдёт с системой обнаружения изменений** при том или ином обновлении.

---

**1. Какие ссылки должны измениться при обновлении одного поля в структуре на три уровня?**

<details>
<summary>Ответ</summary>

Ровно те, что лежат на пути от корня до изменённого поля, — то есть три: корень, промежуточный узел, узел с изменяемым полем. Всё, что вне пути, сохраняет прежние ссылки.

```js
const next = {
  ...state,
  course: {
    ...state.course,
    progress: { ...state.course.progress, current: "1.13" },
  },
};

next !== state;
next.course !== state.course;
next.course.progress !== state.course.progress;
next.user === state.user;                 // вне пути — та же ссылка
next.course.progress.completed === state.course.progress.completed;
```

Формулировка правила: **число новых ссылок равно длине пути от корня до изменения, и ни на одну больше.**

**Ответ «все ссылки в структуре, чтобы наверняка»** вскрывает понимание иммутабельности как защиты от мутации, а не как механизма обнаружения изменений. Deep copy действительно гарантирует, что изменение будет замечено, — но одновременно уничтожает все ответы «не изменилось», на которых стоит мемоизация. В системе, где эти ответы и есть выигрыш, обмен плохой.

**Ответ «только ссылку на корень — на неё же подписан компонент»** вскрывает то, что потребитель воспринимается как один. Потребителей много: корневой подписчик, мемоизированный компонент глубокой ветви, селектор, ячейка списка. Новый корень при прежнем `course.progress` означает, что подписчик корня обновится, а мемоизированный потребитель `progress` — нет, потому что для него это тот же объект. Результат — частично обновившийся экран, самый неприятный вид дефекта, потому что он выглядит как «иногда не работает».

**Ответ «только ссылку на самый глубокий узел, где поле»** вскрывает обратное: без нового корня никто не узнает, что внутри что-то произошло. Изменение в глубине невидимо снаружи, если путь к нему не обновлён.
</details>

---

**2. Почему мутация с последующим `setState` иногда «работает», и почему на это нельзя опираться?**

<details>
<summary>Ответ</summary>

```js
lesson.done = true;
setLessons(lessons);     // та же ссылка
```

`setLessons` получает ту же ссылку, что уже лежит в состоянии. React сравнивает через `Object.is`, получает равенство и имеет право не планировать рендер. Само это обновление не делает ничего.

Экран всё же меняется, когда рендер случается **по другой причине**:

- в том же обработчике изменилось другое состояние, и этот рендер показал заодно и мутированные данные;
- перерисовался родитель по своей причине, протащив за собой дочерние компоненты;
- экран ушёл и вернулся, компонент смонтировался заново и прочитал данные свежими;
- сработал таймер, подписка, фокус навигации.

Мутированное значение попало в кадр попутно. Отсюда вывод, и он важнее самого механизма:

> Проблема не в нарушении стиля. Проблема в том, что обновление экрана становится **недетерминированным** — оно происходит, когда рядом случилось что-то ещё.

Практическое следствие: дефект проявится позже, у другого разработчика, и обычно после «оптимизации» — добавления `memo`, снятия лишнего рендера родителя, замены навигационного стека. То есть после изменения, которое просто убрало случайный триггер.

**Ответ «работает, потому что React иногда рендерит дважды»** вскрывает подмену причины: приписывание эффекта особенностям React (StrictMode, батчинг) вместо внешнего триггера. Опасен тем, что ведёт к поиску решения в настройках React, а не в коде обновления.

**Ответ «не работает никогда, React всегда сравнивает ссылки»** формально ближе к истине, но вскрывает неполную модель — и на практике мешает. Разработчик с таким ответом не сможет объяснить наблюдаемое поведение («но у меня же обновилось») и потому не поверит собственному правилу. Понимать нужно именно механизм случайного срабатывания: только он объясняет, почему дефект находят не сразу.

**Ответ «работает, потому что данные всё равно изменились, React просто не успел заметить»** вскрывает модель, в которой React опрашивает состояние и может «заметить позже». Опроса нет: сравнение происходит в момент вызова сеттера, один раз, по `Object.is`. Если оно дало равенство, другой попытки не будет.
</details>

**3. Что Immer делает с исходным объектом?**

<details>
<summary>Ответ</summary>

**Ничего.** Исходный объект после `produce` в точности тот же, что до.

```js
const next = produce(state, (draft) => {
  draft.course.progress.current = "1.13";
});

state.course.progress.current;   // прежнее значение — не изменилось
```

Механизм: `produce` создаёт **draft (черновик)** — обёртку над исходными данными через **Proxy**, объект-посредник, перехватывающий обращения к свойствам. Чтения проксируются вниз, к исходным данным. Записи перехватываются и складываются в сторону, в исходный объект не попадают. По завершении функции Immer собирает новое значение: создаёт новые объекты по пути сделанных изменений и переносит прежние ссылки на всё, что не трогали, — то есть выполняет то же structural sharing, что ручное обновление по правилу пути.

Два следствия, о которых стоит знать:

- набор новых идентичностей совпадает с ручным вариантом: Immer не создаёт лишних ссылок и не экономит нужные;
- если в `produce` ничего не изменено, возвращается **исходный объект**, та же ссылка. Отсутствие изменений не создаёт ложного «изменилось».

Что Immer скрывает — не факт мутации, а **то, какие именно ссылки получились новыми.** Код выглядит как мутация, и границу structural sharing по нему не прочитать. Это и есть его цена: краткость и защита от ошибок в обмен на предсказуемость идентичностей.

**Ответ «Immer мутирует исходный объект, но делает это безопасно»** — неверный, и вскрывает модель «библиотека разрешает мутировать». Из неё следуют реальные дефекты: объект, полученный из состояния, начинают менять вне `produce`, считая, что мутация в принципе допустима в этом проекте.

**Ответ «Immer делает глубокую копию, а потом применяет изменения»** вскрывает непонимание того, зачем Immer вообще нужен. Если бы он копировал всё дерево, он давал бы новые ссылки у каждого узла — ровно ту ошибку, которой правило пути избегает, — и мемоизация ломалась бы везде. Проверяется это одной строкой: `next.user === state.user` даёт `true`.

**Ответ «Immer делает иммутабельность бесплатной»** вскрывает смешение двух видов стоимости. Immer убирает стоимость **кода** — вложенные spread и ошибки в них. Стоимость **рантайма** остаётся и растёт: Proxy на каждое обращение к свойству плюс сборка результата. Остаётся и стоимость **понятности**: набор новых идентичностей теперь нужно выводить, а не читать. На обновлении одного поля плоского объекта Immer не убирает ничего и добавляет зависимость.
</details>

## Задание — глубокое обновление двумя способами

**Дано.** Состояние экрана курса в RN Academy. Нужно отметить урок `1.3` в блоке `01` как завершённый.

```js
const state = {
  user: { id: 1, name: "Serge", avatar: { url: "a.png", size: 64 } },
  ui: { tab: "course", scrollOffset: 420 },
  course: {
    id: "rn-senior",
    title: "React Native: Senior",
    blocks: [
      {
        id: "01",
        title: "JavaScript",
        lessons: [
          { id: "1.1", title: "Variables и scope", done: true },
          { id: "1.2", title: "Data types", done: true },
          { id: "1.3", title: "Coercion и сравнения", done: false },
        ],
      },
      {
        id: "02",
        title: "TypeScript",
        lessons: [{ id: "2.1", title: "Типы vs интерфейсы", done: false }],
      },
    ],
  },
};
```

**Требуется.**

1. Реализовать `completeLesson(state, blockId, lessonId)` вручную, через spread, по правилу пути. До изменения — посчитать на структуре, сколько новых ссылок должно получиться, и обосновать число.
2. Реализовать ту же функцию через Immer.
3. Написать набор проверок через `===`, который падает и при мутации, и при избыточном копировании. Проверки должны проходить для **обеих** реализаций без изменений.
4. Ответить, совпали ли наборы новых идентичностей у двух реализаций, и объяснить, почему это так по механизму Immer, а не по совпадению.
5. Принять и обосновать решение: какой из двух вариантов оставить в этом проекте. Обоснование должно опираться на цену, а не на предпочтение.

---

<details>
<summary>Разбор</summary>

**1. Сколько новых ссылок и почему.**

Путь от корня до изменяемого поля `done`:

```
state → course → blocks → blocks[0] → blocks[0].lessons → lessons[2]
```

Шесть узлов, значит **шесть новых ссылок**. Каждая обязана быть новой по одной и той же причине: если узел на пути сохранит прежнюю ссылку, его потребитель сравнит старое значение с новым, получит равенство и заключит, что обновлять нечего, — и изменение будет потеряно на этом уровне.

Всё остальное обязано сохранить прежние ссылки: `user` со всем содержимым, `ui`, `blocks[1]` со своими уроками, `lessons[0]` и `lessons[1]`.

Реализация:

```js
function completeLesson(state, blockId, lessonId) {
  return {
    ...state,
    course: {
      ...state.course,
      blocks: state.course.blocks.map((block) =>
        block.id !== blockId
          ? block
          : {
              ...block,
              lessons: block.lessons.map((lesson) =>
                lesson.id !== lessonId ? lesson : { ...lesson, done: true }
              ),
            }
      ),
    },
  };
}
```

Две ветки `? block` и `? lesson` — возврат исходного объекта, а не копии — и есть то, что делает structural sharing. Без них функция осталась бы формально иммутабельной и дала бы новые ссылки всем блокам и всем урокам.

**2. Через Immer.**

```js
import { produce } from "immer";

const completeLesson = (state, blockId, lessonId) =>
  produce(state, (draft) => {
    const block = draft.course.blocks.find((b) => b.id === blockId);
    const lesson = block?.lessons.find((l) => l.id === lessonId);
    if (lesson) lesson.done = true;
  });
```

Обратите внимание, что в коде не видно ни одного из шести копирований. Их выполнит Immer, и именно это — предмет пункта 4.

**3. Проверки.**

```js
const next = completeLesson(state, "01", "1.3");

// обязаны стать новыми — шесть узлов пути
next !== state;
next.course !== state.course;
next.course.blocks !== state.course.blocks;
next.course.blocks[0] !== state.course.blocks[0];
next.course.blocks[0].lessons !== state.course.blocks[0].lessons;
next.course.blocks[0].lessons[2] !== state.course.blocks[0].lessons[2];

// обязаны остаться прежними — всё вне пути
next.user === state.user;
next.user.avatar === state.user.avatar;
next.ui === state.ui;
next.course.blocks[1] === state.course.blocks[1];
next.course.blocks[1].lessons === state.course.blocks[1].lessons;
next.course.blocks[0].lessons[0] === state.course.blocks[0].lessons[0];
next.course.blocks[0].lessons[1] === state.course.blocks[0].lessons[1];

// вход не тронут
state.course.blocks[0].lessons[2].done === false;

// результат верен
next.course.blocks[0].lessons[2].done === true;
```

Первая группа ловит мутацию: если какой-то узел пути не заменён, изменение на этом уровне ненаблюдаемо. Вторая ловит избыточное копирование: лишняя новая ссылка означает, что потребитель неизменившейся ветви получит «изменилось». Третья ловит мутацию входа. Четвёртая проверяет логику.

Набор проходит для обеих реализаций без единой правки. Это и есть содержательный результат задания: **проверка написана не на реализацию, а на идентичности** — она описывает контракт обновления, и ей безразлично, кто его выполнил.

**4. Совпали ли наборы, и почему это не совпадение.**

Совпали полностью: шесть новых ссылок, остальное разделяется.

Это следует из механизма, а не из удачи. `produce` оборачивает исходные данные в Proxy и **фиксирует, к каким узлам были записи**. При сборке результата он создаёт новый объект для каждого узла, через который прошла запись, и переносит прежнюю ссылку для всех остальных. Множество «узлов, через которые прошла запись» — это ровно путь от корня до изменённого поля. Поэтому Immer реализует то же правило, а не приближает его.

Два следствия, которые стоит проверить отдельно:

```js
// чтение без записи не создаёт новых ссылок
const same = produce(state, (draft) => {
  draft.course.blocks[0].lessons[2].done;   // только читаем
});
same === state;    // true — исходный объект, не копия
```

```js
// запись того же значения всё равно считается записью пути
const still = produce(state, (draft) => {
  draft.ui.tab = "course";                  // то же значение
});
still !== state;   // true — путь обновлён
```

Второе важно практически: Immer сравнивает по факту присваивания, а не по значению. Если нужно избежать ложного «изменилось», условие пишется руками — и в ручном варианте тоже.

Чего в этом коде не видно и почему это цена: по тексту с Immer **невозможно прочитать**, что `blocks[1]` разделяется, а `blocks[0]` нет. В ручном варианте это написано ветками `? block` и `? lesson`. Когда через полгода придёт вопрос «почему перерисовался весь список блоков», в ручном варианте ответ читается из кода, в варианте с Immer его нужно восстановить по механизму или проверить замером (5.3).

**5. Решение.**

Ответ зависит от двух измеримых обстоятельств, и формулировать его нужно через них.

**В пользу Immer здесь:** путь из шести узлов, обновлений прогресса в приложении много и они однотипны (отметить завершённым, сбросить, обновить позицию), ручной вариант занимает двенадцать строк вложенных spread на каждое такое обновление, и в нём возможны оба отклонения от правила — пропущенный уровень и лишняя копия. Immer делает оба невозможными. Если обновления состояния живут в редьюсерах, решение уже принято за вас: Redux Toolkit применяет Immer внутри `createSlice` (6.4).

**В пользу ручного варианта:** если таких обновлений в проекте два-три, Immer добавляет зависимость, Proxy в рантайме и необходимость объяснять новому разработчику, что код, выглядящий как мутация, мутацией не является. На плоских структурах — `{ ...state, tab: "course" }` — он не убирает ничего.

**Третий вариант, который стоит назвать, потому что он сильнее обоих:** сократить путь. Шесть узлов — это следствие формы данных, а не требование задачи. Нормализованная структура, где уроки лежат плоско по идентификатору, превращает обновление в путь из двух узлов:

```js
{ ...state, lessons: { ...state.lessons, "1.3": { ...state.lessons["1.3"], done: true } } }
```

Тогда вопрос «Immer или руками» теряет остроту: руками это одна строка. Цена нормализации — косвенность при чтении и код на сборку данных для экрана; когда она окупается, а когда это оверинжиниринг — 6.8.

**Чего разбор сознательно не делает.** Не обсуждает, как подписать компоненты на это состояние и где поставить `memo`: это 3.7 и 3.8. Не оценивает, во сколько кадров обойдётся лишнее копирование блоков, — это проверяется профайлером (5.3), а механика рециклинга ячеек списка разбирается в 5.4. Не трогает сохранение прогресса на устройство: форма структуры становится контрактом с данными пользователя, и изменение формы требует миграции (6.6).

> **RN Academy (P1).** Эта функция — рабочий код проекта: отметка урока завершённым не копирует весь курс. Зафиксированное здесь правило («новых ссылок ровно столько, какова длина пути») становится критерием приёмки для всех обновлений прогресса, а набор проверок из пункта 3 — шаблоном теста для них.
</details>
