# 1.22 Memory: что держит ссылку — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как освободить память» — а на вопрос, **почему конкретный объект всё ещё жив, и какая именно ссылка его держит.**

---

## 1. Что это

**Reachability (достижимость)** — свойство объекта: от одного из корней графа ссылок до него существует путь. Достижимость — **единственный** критерий, по которому объект остаётся в памяти.

**Roots (корни)** — набор значений, которые движок считает живыми без всяких условий, потому что к ним ведёт исполнение программы: глобальный объект, модульные области видимости загруженных модулей, переменные активных функций на стеке вызовов, значения, удерживаемые средой исполнения (таймеры, обработчики, host objects).

**Strong reference (сильная ссылка)** — обычная ссылка: свойство объекта, элемент массива, захваченная замыканием переменная, ключ или значение `Map`. Пока сильная ссылка существует и сама достижима, объект на её конце достижим тоже.

**Retained (удерживаемый)** — объект, который достижим только через чью-то конкретную ссылку. Говоря «этот listener retained всё дерево данных экрана», имеют в виду: если убрать listener, дерево станет недостижимым.

**Memory leak (утечка памяти)** — объект остаётся достижимым **дольше, чем предполагает его intended lifetime**, то есть срок жизни, заложенный в замысел: данные экрана должны были перестать быть достижимыми при уходе с экрана, запись кэша — при вытеснении, подписка — при размонтировании.

Определение важно именно в такой форме. Утечка — это **не** «объект не удалился»: ни один объект не обязан быть удалён в какой-то конкретный момент, и движок не даёт такой гарантии. И не «память выросла»: рост памяти сам по себе нормален (1.23). Утечка — расхождение между тем, сколько объект **должен** был оставаться достижимым, и тем, сколько он остаётся фактически. Отсюда следует практическое требование: утверждение «здесь утечка» неполно без ответа на вопрос, каким предполагался срок жизни и что именно продлевает его сверх этого.

Три формулировки стоит сразу развести, потому что в обсуждениях они схлопываются:

| Формулировка | Что на самом деле утверждает |
|---|---|
| «объект больше не нужен» | оценка разработчика; на память не влияет никак |
| «на объект нет ссылок» | обычно неверно: ссылок нет только из того места, которое разработчик помнит |
| «объект недостижим» | от корней до него нет ни одного пути — только это освобождает память |

### Чего в JavaScript нет

Нет API, которое освобождает конкретный объект. Нет `delete object`, нет `free(x)`, нет способа узнать размер объекта или получить список ссылающихся на него. Единственное, чем разработчик управляет, — **какие ссылки он создаёт и какие снимает**.

Отсюда и формат любого разговора о памяти: не «освободить объект», а «разорвать удерживающую цепочку». Что происходит после разрыва — тема 1.23.

## 2. Как это работает

### Граф ссылок

Память приложения — направленный граф. Узлы — объекты, массивы, функции, замкнутые окружения. Рёбра — сильные ссылки. Отдельно стоят корни: у них нет входящих рёбер, они живы по определению.

```
roots
  ├── globalThis ──────────► объект конфигурации
  ├── module scope (api.js) ► cache ──► response ──► items[] ──► item ──► author
  ├── stack frame fetchAll ─► promise
  └── среда исполнения ────► timer callback ──► [[Scope]] ──► screenData
```

Объект достижим, если в этом графе есть путь `root → … → объект`. Количество путей не важно: достаточно одного. Это немедленно даёт практическое правило — **снятие одной из нескольких удерживающих ссылок не освобождает ничего**. Отписались от emitter, но оставили `setInterval`, который замыкает тот же объект, — объект достижим.

### Что именно удерживает замыкание

Самый недооценённый источник удержания, потому что ссылка в коде не видна: её создаёт не присваивание, а факт объявления функции внутри области видимости (1.14, 1.15).

```js
function createHandler(response) {
  const items = response.items;          // большой массив
  const count = items.length;

  return () => count;                    // возвращаем функцию, использующую ТОЛЬКО count
}

const handler = createHandler(hugeResponse);
```

Функция использует одно число. Но она замыкает **окружение**, в котором живут `response` и `items`, и пока `handler` достижим, достижимо и окружение целиком. Конкретные движки умеют отбрасывать неиспользуемые переменные при оптимизации, но на это нельзя рассчитывать как на контракт: решение зависит от движка, от режима сборки и от того, не попадает ли в функцию `eval` или отладочный доступ к scope.

Инженерно корректная форма — не надеяться на оптимизацию, а не захватывать лишнее:

```js
function createHandler(response) {
  const count = response.items.length;   // response дальше не нужен
  return () => count;
}
```

Разница не в стиле. В первом варианте цепочка `handler → [[Scope]] → response → items` существует, во втором её нет.

### Что удерживает объект — полный список для RN

| Источник удержания | Как выглядит в RN-приложении |
|---|---|
| **closures** | колбэк замыкает весь scope, включая большие структуры данных |
| **listeners** | подписка на emitter нативного модуля, `AppState`, `Keyboard`, Linking |
| **timers** | `setInterval` без `clearInterval`, таймер, перезапускающий себя |
| **subscriptions** | подписки стора, навигации, сетевого клиента, стримов |
| **caches** | кэш изображений, кэш разобранных ответов, мемоизация без ограничения размера |
| **globals** | модульные переменные и объекты верхнего уровня: живут всё время работы приложения |
| **references from native layer** | нативная сторона держит ссылку на JS-объект или на host object — JS-сборщик такой объект не освободит, пока нативная ссылка жива |

Строки идут не в произвольном порядке: сверху вниз растёт срок жизни корня, который держит цепочку, и падает заметность ссылки в коде.

- **closures** — корень живёт, пока жива замыкающая функция; её срок жизни определяется тем, кто её держит, то есть одной из следующих строк;
- **listeners** и **subscriptions** — корнем выступает сам источник событий. Он обычно долгоживущий: emitter нативного модуля, стор приложения, объект навигации. Поэтому колбэк, переданный ему, переживает экран, с которого был зарегистрирован;
- **timers** — корнем выступает среда исполнения. `setInterval` держит колбэк до `clearInterval` безусловно, и у `setTimeout`, который перезапускает себя, конца нет вообще;
- **caches** — удержание здесь не ошибка, а назначение: кэш существует ровно для того, чтобы объект не исчез. Проблема не в факте удержания, а в отсутствии верхней границы;
- **globals** — модульная переменная (1.10) достижима от корня с момента выполнения модуля и до завершения процесса. Срок жизни такого объекта равен сроку жизни приложения — других вариантов нет;
- **references from native layer** — разобрано в угле 4; это строка, из-за которой список называется «для RN», а не «для JavaScript».

### Как выглядит цепочка в разборе

Полезная форма ответа на вопрос «почему объект жив» — одна строка на цепочку:

```
AppState (нативный emitter, жив всё время работы приложения)
    → listener (переданный из useEffect экрана)
        → [[Scope]] экрана
            → screenData (массив на 4000 элементов)
```

И сразу вторая строка — что её разрывает: «`remove()` подписки в cleanup». Если на вторую строку нечего написать, удерживающая цепочка не разрывается никогда, и это и есть диагноз.

### `WeakMap` и `WeakRef`

**`WeakMap`** — коллекция, которая держит ключ **слабо**: наличие объекта ключом в `WeakMap` не делает его достижимым. Как только объект-ключ стал недостижим по всем остальным путям, запись перестаёт существовать вместе с ним.

Отсюда и ограничения, которые у `WeakMap` не случайны: ключом может быть только объект (у примитива нет идентичности, за которой можно наблюдать), нет `size`, нет перебора. Перебор невозможен принципиально: его результат зависел бы от момента сборки, то есть был бы наблюдаемым недетерминизмом.

Рабочий случай — метаданные, привязанные к объекту, которым вы не владеете:

```js
const parsedBody = new WeakMap();

function getParsed(response) {
  if (!parsedBody.has(response)) {
    parsedBody.set(response, JSON.parse(response.raw));
  }
  return parsedBody.get(response);
}
```

Здесь `WeakMap` индексирует по идентичности объекта (1.12) и не продлевает его жизнь: исчез `response` — исчез и разобранный результат. С обычным `Map` этот код был бы утечкой по построению: `Map` держит ключ сильно, и каждый когда-либо обработанный ответ оставался бы в памяти навсегда.

**`WeakRef`** — обёртка над одной слабой ссылкой. `ref.deref()` возвращает объект или `undefined`, если объект уже недостижим.

```js
const cached = new WeakRef(bigImageData);
const value = cached.deref();
if (value === undefined) {
  // объекта больше нет — нужно получить данные заново
}
```

Ключевое свойство, определяющее область применения: **каждый вызов `deref()` может вернуть разный результат**, и момент, когда он начнёт возвращать `undefined`, не определён. Поэтому `WeakRef` уместен там, где потеря значения — штатная ветка (кэш, который можно пересобрать), и неуместен там, где значение требуется для корректности.

| | `Map` | `WeakMap` | `WeakRef` |
|---|---|---|---|
| держит объект | сильно | слабо (ключ) | слабо |
| перебор, `size` | есть | нет | не применимо |
| когда уместно | нужен контроль над содержимым и временем жизни | метаданные к чужому объекту | необязательный кэш, пересобираемый при потере |
| главный риск | удержание без границы | кажущаяся бесплатность, скрывающая обычное сильное удержание значений | недетерминированное поведение в коде, который на значение рассчитывает |

Оговорка, без которой `WeakMap` применяют неверно: **слабый только ключ**. Значение удерживается сильно, и если значение ссылается на свой ключ, цепочка замыкается и обе стороны живут. Это частая ошибка — «переписали на `WeakMap`, а память не изменилась».

## 3. Почему это важно

Неограниченное удержание — класс дефектов с двумя неприятными свойствами.

**Проявление отложено от причины.** Код, создающий удерживающую ссылку, выполняется один раз при монтировании экрана; последствие наступает через двадцать минут сессии, после десятого перехода на этот экран. Между причиной и симптомом нет ни временной, ни стековой связи, поэтому обычные приёмы отладки — стектрейс, логи вокруг падения — не работают. Вопрос «почему объект жив» решается не по стеку, а по графу.

**Симптом не похож на свою причину.** Удержание памяти проявляется не как «ошибка памяти», а как подтормаживание, затем как медленная работа после длительной сессии, затем как закрытие приложения без сообщения. Естественная гипотеза в таком случае — «тяжёлый экран» или «плохая сеть», и она ведёт в сторону.

Поэтому ценность урока утилитарна: умение назвать цепочку `root → … → объект` превращает догадку в проверяемое утверждение. Утверждение «тут утечка» опровергнуть нельзя, утверждение «`AppState` держит listener, который замыкает массив на 4000 элементов, и cleanup его не снимает» — можно, и именно это делает его инженерным.

## 4. Где это в React Native

### Граф достижимости не ограничен JS-кучей

Это главное, что отличает разговор о памяти в React Native от того же разговора в браузере.

**Host object** — объект, который доступен в JS, но представляет сущность, живущую вне JS-кучи: дескриптор нативного ресурса, буфер, объект, созданный через JSI (4.1). У него две стороны: JS-обёртка в куче движка и нативный ресурс за ней.

Отсюда два следствия, оба неочевидные.

**Нативная ссылка удерживает JS-объект.** Если нативная сторона зарегистрировала JS-функцию как колбэк или держит ссылку на JS-объект, этот объект достижим — независимо от того, что в JS-коде на него не ссылается никто. Поиск по JS-коду в таком случае ничего не даёт: ссылки там действительно нет, а объект жив, потому что корень лежит в нативном слое.

**Недостижимость JS-обёртки не означает освобождения нативного ресурса.** Обёртка маленькая — несколько десятков байт в куче; ресурс за ней может быть на десятки мегабайт. Если у ресурса есть явный метод освобождения (`close`, `release`, `stop` — конкретное имя зависит от библиотеки), его нужно вызвать. Потеря ссылки на обёртку не вызывает его за вас, а сам вызов — это не «освобождение памяти», а завершение работы с нативным ресурсом по его собственному контракту. Подробнее о контрактах нативных модулей — блок 09.

### Почему это не академический разговор

На устройстве с 2 ГБ памяти доля, доступная приложению, измеряется сотнями мегабайт, и операционная система не замедляет приложение при её исчерпании — она завершает процесс.

Отсюда следствие, важное для блока 10: такое завершение **не является крашем в обычном смысле**. Исключения не было, JS-код не падал, стектрейса нет. В отчётности это выглядит как обрыв сессии или как краш без стектрейса, и по отчёту неотличимо от нативного падения — пока не посмотреть на потребление памяти перед обрывом (10.6, 10.7). Поэтому растущий кэш изображений или неотписанные подписки дают не «приложение подтормаживает», а «приложение закрывается у части пользователей, и причина по отчёту не видна».

Второе следствие — про размеры. В RN удерживаемые объекты часто крупные: декодированное изображение занимает память, пропорциональную числу пикселей, а не размеру файла (5.5). Удержание сотни таких объектов съедает бюджет приложения целиком, при том что в JS-коде это сто записей в обычном объекте-кэше.

### Типовые места в RN-экране

| Место | Что создаёт удержание |
|---|---|
| `useEffect` с подпиской на нативный emitter | listener в долгоживущем emitter замыкает scope экрана |
| `setInterval` в эффекте | среда исполнения держит колбэк до `clearInterval` |
| модульный объект-кэш в сервисном слое | корень живёт всё время работы приложения |
| `useRef`, в который положили большую структуру | ref живёт, пока жив компонент; при долгоживущем экране в табах это вся сессия (3.9) |
| обёртка нативного модуля (камера, плеер, файловый стрим) | JS-обёртка + нативный ресурс со своим контрактом завершения |
| обработчик, переданный в навигацию или в сетевой клиент | корень — объект навигации или клиент, оба переживают экран |

Ни одно из этих мест не является ошибкой: все шесть конструкций нужны. Удержание становится дефектом только в одном случае — когда у ссылки нет момента снятия.

## 5. Типичные ошибки

**«Присваивание `null` освобождает память».** Возникает из верной, но неполной модели: присваивание `null` действительно снимает **одну** ссылку. Проблема в том, что снимается именно та, которую разработчик помнит, а удерживают остальные — замыкание, слушатель, запись в кэше. Отсюда и наблюдение «обнулил, а память не изменилась», которое обычно списывают на «движок не успел». Корректная постановка: достижимость определяется всеми путями, и снимать нужно последний из них.

**«Утечка — это всегда баг в библиотеке».** Возникает потому, что собственный код выглядит знакомым и безобидным, а чужой — нет. Усиливается тем, что ссылку действительно создаёт вызов библиотечной функции (`addListener`, `subscribe`). Но контракт у такого вызова двусторонний: он возвращает способ отписки, и ответственность за вызов этого способа лежит на вызывающей стороне. Цена ошибки — время, потраченное на чтение исходников библиотеки вместо чтения своего cleanup.

**«Если компонент размонтирован, его данные освободились».** Возникает из аналогии с жизненным циклом компонента: раз React убрал компонент из дерева, всё его содержимое должно исчезнуть. Размонтирование снимает ссылки React на компонент и его состояние — и ничего не знает о ссылках, которые код компонента отдал наружу. Переданный в долгоживущий emitter колбэк после размонтирования достижим ровно так же, как до него. Именно поэтому cleanup — не «хорошая практика», а вторая половина парной операции.

**Размонтирование без отписки.** Практическая форма предыдущего заблуждения. Отдельно стоит отметить, почему она так долго остаётся незамеченной: на одном открытии экрана последствий нет вообще, и профиль растёт только с числом переходов. Дефект обнаруживается длительной сессией, а не воспроизведением «шаг за шагом».

**«Утечка» как неограниченный рост кэша.** Здесь ошибка в диагнозе, и она ведёт к неверному исправлению. Кэш без границы — не потерянная ссылка, а отсутствие политики вытеснения: каждая запись достижима, объяснима и была добавлена намеренно. Попытка «найти, где теряется ссылка» не найдёт ничего. Исправление — верхняя граница и правило вытеснения, то есть проектное решение, а не исправление опечатки. Отличие и сходство двух случаев разбираются в practice.md, вопрос 2.

**Хранение данных экрана в глобальном объекте «чтобы не потерять».** Возникает из реальной задачи — сохранить состояние между переходами, — и решается самым коротким из доступных способов: модульной переменной. Проблема в том, что у модульной переменной нет момента очистки; «не потерять» превращается в «не отпускать никогда». Решение не в запрете глобального состояния, а в явном владельце и явном сроке жизни (блок 06, блок 08).

**Удержание host object после того, как нативный ресурс больше не нужен.** Возникает потому, что обёртка в JS выглядит как обычный объект, и к ней применяют обычную интуицию: «перестал ссылаться — всё». Для ресурса со своим контрактом завершения этого недостаточно, и цена ошибки непропорциональна размеру объекта в JS-куче.

**`WeakMap` как средство «сделать ссылку слабой».** Возникает из названия. Слабым является только ключ; значения удерживаются сильно, и если значение ссылается на ключ, слабость не даёт ничего. Проверяется легко: достаточно спросить, что ещё ссылается на объект-ключ — если сильная ссылка есть, `WeakMap` не изменит ничего.

## 6. Trade-offs

### Кэш ускоряет и держит память

Это один и тот же механизм, а не побочный эффект: кэш ускоряет именно потому, что удерживает объект. Выбор не между «кэшировать» и «не кэшировать», а между политиками.

| Политика | Что получаем | Чем платим |
|---|---|---|
| без кэша | постоянное потребление | повторная работа при каждом обращении |
| кэш без границы | максимум попаданий | потребление растёт со временем сессии |
| кэш с границей (по числу или по размеру) | предсказуемый потолок | промахи, вытеснение полезного, код политики |
| слабый кэш (`WeakRef`) | движок сам решает, что оставить | недетерминированные промахи, невозможность гарантировать попадание |

Инженерное требование, которое стоит унести: у кэша должна быть **названная верхняя граница**. «По ситуации» — не граница. Какая именно граница верна, определяется замером (5.10), но её отсутствие — дефект независимо от замера.

### Слабые ссылки освобождают и усложняют логику

`WeakMap` в своём случае — чистый выигрыш: ограничения (нет перебора, только объекты-ключи) совпадают с задачей «метаданные к чужому объекту», и кода он не усложняет.

`WeakRef` — другое дело. Он вводит ветку «значения больше нет», которую нужно обработать везде, где значение читается, и которая срабатывает недетерминированно, то есть почти никогда в разработке и иногда в продакшене. Это худший профиль надёжности: редкий путь, который не покрывается ни тестом, ни ручной проверкой. Поэтому `WeakRef` оправдан в небольшом числе случаев — когда объект крупный, пересоздаётся дёшево и его потеря не меняет наблюдаемое поведение. В остальных ситуациях ограниченный кэш с явной политикой проще, предсказуемее и обсуждаем на ревью.

### Удерживать намеренно — нормально

Симметричный trade-off, о котором забывают при разговоре об утечках: отпускать всё как можно раньше — не бесплатная добродетель. Отпущенный объект придётся восстановить, а восстановление может означать сетевой запрос, повторный разбор или декодирование изображения, то есть видимую пользователю задержку.

Поэтому правильный вопрос не «что можно отпустить», а «какой срок жизни у этих данных и кто им владеет». Данные на время экрана, на время сессии и на время работы приложения — три разных ответа, и каждый из них законен. Дефект появляется, когда ответа нет вообще.

### Явная отписка против автоматической

Можно складывать все снятия ссылок в один объект-владелец и снимать их одной операцией. Выигрыш — забыть одно снятие нельзя. Цена — абстракция, которую должна понимать вся команда, и риск того, что владение станет неочевидным: cleanup выполняется где-то ещё и уже не читается в месте подписки. Для одной подписки явная отписка яснее; для экрана с шестью подписками ручной список начинает ломаться. Решение зависит от масштаба и единообразия в проекте (блок 08).

Аргумент один: названная цепочка `root → … → объект` и названная операция, которая её разрывает. Если вторую часть назвать нечем, дефект найден.
