# 1.6 Array methods — practice

## Проверка понимания

---

**1. Сколько новых массивов создаёт `a.filter(...).map(...).slice(...)`?**

<details>
<summary>Ответ</summary>

Три. Каждое звено цепочки создаёт собственный массив; два из них промежуточные и становятся мусором сразу после использования. Исходный `a` не изменяется.

**Ответ «один, итоговый»** вскрывает модель ленивой цепочки из других языков. Практическое следствие ошибки — неверная оценка того, что происходит при каждом рендере.

**Ответ «три, значит это медленно и надо переписать в `reduce`»** вскрывает другую проблему: верный факт с неверным выводом. На списке в несколько сотен элементов три прохода вместо одного несущественны. Значение имеет частота вызова, а не количество проходов, и решение принимается по замеру (блок 05), а не по подсчёту звеньев.
</details>

---

**2. Почему массив из `filter` в зависимостях `useEffect` вызывает эффект каждый рендер?**

<details>
<summary>Ответ</summary>

Потому что `filter` создаёт новый массив при каждом вызове, даже если ни один элемент не отфильтрован и содержимое идентично. React сравнивает зависимости по идентичности, видит новую ссылку и считает, что зависимость изменилась.

Если эффект при этом обновляет состояние, получается бесконечный цикл: рендер создаёт новый массив, эффект срабатывает, обновляет состояние, вызывает рендер.

**Ответ «потому что содержимое пересчитывается»** вскрывает подмену: React не смотрит на содержимое вообще. Пересчёт сам по себе ничего бы не вызвал, если бы ссылка осталась прежней.

**Ответ «надо добавить массив в `useMemo`»** может быть правильным действием, но как ответ на вопрос «почему» он вскрывает рецепт вместо механизма. Без понимания причины тот же дефект не будет распознан в случае с инлайн-объектом или инлайн-функцией в зависимостях.
</details>

---

**3. Когда `reduce` уместнее цепочки?**

<details>
<summary>Ответ</summary>

Когда нужно получить **не массив**: сумма, индекс по ключу, группировка, несколько величин за один проход. И когда цепочка потребовала бы нескольких проходов по действительно большим данным, что подтверждено замером.

Не уместен там, где он выражает `map` или `filter`: результат тот же, читаемость хуже.

**Ответ «всегда, `reduce` эффективнее»** вскрывает оптимизацию без измерения. Читаемость — тоже инженерное свойство, и платить ею за неизмеренный выигрыш это плохая сделка.

**Ответ «никогда, он нечитаемый»** вскрывает обратную крайность. Построение индекса через `reduce` короче и понятнее, чем цикл с мутацией внешнего объекта, и именно оно убирает квадратичный поиск из рендера списка.
</details>

## Задание

**Дано.** Компонент экрана курса в RN-приложении. Код корректен: он ничего не мутирует, читается однозначно и проходит ревью. Тем не менее при скролле список заметно подтормаживает, а устройство греется при просто открытом экране.

```jsx
function CourseScreen({ course, authors, query }) {
  const lessons = course.lessons
    .filter((l) => l.title.toLowerCase().includes(query.toLowerCase()))
    .map((l) => ({
      ...l,
      label: `${l.order}. ${l.title}`,
      author: authors.find((a) => a.id === l.authorId),
    }));

  const completedIds = course.lessons.filter((l) => l.done).map((l) => l.id);

  const stats = {
    total: course.lessons.length,
    done: completedIds.length,
    percent: Math.round((completedIds.length / course.lessons.length) * 100),
  };

  useEffect(() => {
    syncProgress(completedIds);
  }, [completedIds]);

  return (
    <View>
      <Header stats={stats} />
      <FlatList
        data={lessons}
        keyExtractor={(l) => String(l.id)}
        renderItem={({ item }) => <LessonRow lesson={item} />}
      />
    </View>
  );
}
```

`LessonRow` обёрнут в мемоизацию.

**Требуется.**

1. Перечислить **все** выражения, создающие новую ссылку на каждый рендер. Для каждого указать, кто эту новую ссылку заметит.
2. Объяснить, почему устройство греется при открытом экране, когда пользователь ничего не делает. Назвать точную цепочку.
3. Объяснить, почему мемоизация `LessonRow` в этом коде не работает вообще — несмотря на стабильный `keyExtractor`.
4. Найти выражение с квадратичной сложностью и посчитать объём работы при 300 уроках и 40 авторах.
5. Найти место, которое упадёт или покажет неверное значение на пустом списке уроков.
6. **Решения не писать.** Составить таблицу «выражение → механизм → кто заметит → блок курса, где решается». Таблица пригодится как входной материал для 1.24 и для checkpoint блока 03.

<details>
<summary>Разбор</summary>

**1. Выражения с новой ссылкой на каждый рендер.**

| Выражение | Что создаётся | Кто заметит |
|---|---|---|
| `course.lessons.filter(...)` | новый массив | следующее звено цепочки |
| `.map((l) => ({ ...l, ... }))` | новый массив **и новый объект на каждый элемент** | `FlatList` (через `data`) и каждая ячейка (через `lesson`) |
| `authors.find(...)` | ничего нового | никто: `find` возвращает существующий объект, ссылка прежняя |
| `course.lessons.filter((l) => l.done)` | новый массив | следующее звено |
| `.map((l) => l.id)` → `completedIds` | новый массив | массив зависимостей `useEffect` |
| `stats = { ... }` | новый объект | `Header`, если он мемоизирован |
| `keyExtractor={(l) => ...}` | новая функция | `FlatList` (как пропс) |
| `renderItem={({ item }) => ...}` | новая функция | `FlatList` (как пропс) |

Отдельно отмечу `find`: это единственное место, где новой ссылки **нет**, и важно это заметить — не всякий вызов метода массива создаёт новое значение. У `find` другая проблема, см. пункт 4.

**2. Почему греется экран, на котором ничего не происходит.**

Цепочка замкнутая:

1. рендер вычисляет `completedIds` — **новый массив**;
2. `useEffect` сравнивает зависимость `[completedIds]` с предыдущей по идентичности, видит новую ссылку, считает зависимость изменившейся;
3. эффект выполняется, вызывает `syncProgress`;
4. `syncProgress` (прямо или через обновление стора) приводит к обновлению состояния;
5. обновление состояния вызывает рендер;
6. переход к шагу 1.

Это бесконечный цикл, который не останавливается, пока экран открыт. JS thread постоянно занят, выполняется сетевая или дисковая работа, устройство греется и расходует батарею. На экране при этом может не меняться ничего — поэтому дефект не выглядит как дефект UI.

Критично понять, что цикл существует **не из-за** содержимого `completedIds`: оно идентично на каждом витке. Цикл существует из-за того, что `filter` и `map` создают новую ссылку безусловно.

**3. Почему мемоизация `LessonRow` не работает.**

Мемоизация сравнивает пропсы по идентичности. `LessonRow` получает `lesson={item}`, а `item` — это элемент массива `lessons`, созданный выражением `.map((l) => ({ ...l, ... }))`. Spread создаёт **новый объект** для каждого урока при каждом рендере.

Поэтому для каждой ячейки пропс `lesson` всегда новый, сравнение всегда даёт «изменилось», и мемоизация никогда не отсекает рендер. Она при этом не бесплатна: сравнение пропсов выполняется, результат всегда отрицательный — то есть добавлена работа без выигрыша.

Стабильный `keyExtractor` здесь не помогает и не должен: `key` отвечает за сопоставление элементов между рендерами (3.2), а не за то, нужно ли перерисовывать ячейку. Это два разных механизма, и путать их — частая ошибка. `key` стабильный, данные новые — ячейка перерисуется.

Дополнительно свой вклад вносят `renderItem` и `keyExtractor` как инлайн-функции: они новые на каждый рендер, то есть `FlatList` получает изменившиеся пропсы и не может считать, что ничего не поменялось.

**4. Квадратичная сложность.**

Выражение `authors.find((a) => a.id === l.authorId)` внутри `.map(...)`.

`map` обходит все уроки, и для каждого `find` обходит массив авторов до совпадения. При 300 уроках и 40 авторах это до 300 умножить на 40 = **12 000 сравнений** на каждый рендер; в среднем, если совпадение находится в середине, порядка 6 000.

Само по себе это немного — но умножается на частоту рендеров, а частота в этом компоненте, как показал пункт 2, равна «постоянно». Именно сочетание квадратичной работы с бесконечным циклом даёт нагрев устройства, а не каждая из причин по отдельности.

Структурное решение — индекс `authorById`, построенный один раз: поиск становится обращением по ключу, и работа из 300 на 40 превращается в 300 плюс 40. Это та же идея, что нормализация данных (6.8), в самом простом виде.

**5. Пустой список уроков.**

```js
percent: Math.round((completedIds.length / course.lessons.length) * 100)
```

При пустом `course.lessons` это `0 / 0`, то есть `NaN` (1.2). `Math.round(NaN)` даёт `NaN`, и на экране появится «NaN%».

Не падение, а тихий неверный экран — то есть более дорогой класс дефекта (1.3). Пустой список уроков — абсолютно нормальное состояние: новый курс, не загрузившиеся данные, курс без контента.

Отдельно стоит заметить: `reduce` здесь не используется, но если бы процент считали через `reduce` без начального значения, на пустом массиве было бы падение с `TypeError`. Это полезный контраст: одна и та же пустота даёт в одном случае `NaN`, в другом — исключение.

**6. Итоговая таблица.**

| Выражение | Механизм языка | Кто заметит | Где решается |
|---|---|---|---|
| цепочка `filter().map()` для `lessons` | новая ссылка на каждый вызов | `FlatList` через `data` | 3.8 мемоизация, 5.3 диагностика |
| `{ ...l, label, author }` в `map` | новый объект на каждый элемент | мемоизированная ячейка | 3.8, 5.4 списки |
| `completedIds` в зависимостях эффекта | новая ссылка в сравнении зависимостей | React при сравнении deps | 3.4 зависимости хуков |
| `stats` как инлайн-объект | новый объект | мемоизированный `Header` | 3.8 |
| `keyExtractor`, `renderItem` инлайн | новая функция на рендер | `FlatList` как пропсы | 3.8, 5.4 |
| `authors.find` внутри `map` | не ссылка — алгоритмическая сложность | пользователь, через кадры | 5.4 списки, 6.8 нормализация |
| `0 / 0` на пустом списке | приведение и `NaN` | пользователь, через экран | 1.3 (уже), 2.12 валидация данных |

**Что эта таблица показывает.** Из семи строк только одна (`find`) не про идентичность ссылок, и только одна (`NaN`) не про рендер. Остальные пять — один и тот же механизм, проявившийся в пяти местах. Это и есть причина, по которой блок 01 тратит на references отдельный урок (1.12), а не ограничивается упоминанием: один механизм объясняет большинство проблем производительности React Native, и ни одна из них не является «ошибкой React».
</details>
