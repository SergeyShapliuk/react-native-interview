# 1.6 Array methods: map / filter / reduce — theory

> 🟢 REFRESH. Этими методами вы пользуетесь ежедневно. Урок не про то, как они работают, а про один факт, который меняет отношение к ним в React Native: **каждый вызов создаёт новую ссылку, и это происходит на каждый рендер.**

## Refresh

### Что возвращает каждый метод

| Метод | Возвращает | Длина результата |
|---|---|---|
| `map` | новый массив | всегда равна исходной |
| `filter` | новый массив | меньше или равна исходной |
| `reduce` | что угодно | — |
| `find` | элемент или `undefined` | — |
| `findIndex` | индекс или `-1` | — |
| `some` / `every` | булево | — |
| `flat` / `flatMap` | новый массив | зависит от вложенности |

Ни один из них не мутирует исходный массив — в отличие от методов из 1.5. Но **элементы** они не копируют: `map`, возвращающий тот же объект, отдаёт ту же ссылку (это и используется для structural sharing, 1.5).

### `map` сохраняет длину, `filter` — нет

Частая путаница в коде: `map` используют для отбора, возвращая `null` для ненужных элементов.

```js
lessons.map((l) => (l.done ? l : null));   // длина та же, на месте отброшенных — null
lessons.filter((l) => l.done);             // корректный отбор
```

В JSX первый вариант «работает», потому что React не рендерит `null`. Но данные при этом содержат `null`, и любая последующая операция (`length`, `reduce`, обращение к полю) обязана это учитывать. Выбор метода — это решение о том, какой длины результат нужен.

### Колбэк и возвращаемое значение

`map` без `return` даёт массив из `undefined` — самая частая опечатка в этом семействе:

```js
items.map((item) => { item.title });     // [undefined, undefined, ...]
items.map((item) => ({ title: item.title })); // объект нужно обернуть в скобки
items.map((item) => item.title);         // корректно
```

Фигурные скобки после стрелки — это тело функции, а не объектный литерал. Чтобы вернуть объект, его оборачивают в круглые скобки. Линтер (`array-callback-return`) ловит отсутствие `return` в `map`, `filter` и `reduce`.

Второй аргумент колбэка — индекс, третий — сам массив. Отсюда классическая ловушка:

```js
["1", "2", "3"].map(parseInt);   // [1, NaN, NaN]
```

`parseInt` принимает второй аргумент — основание системы счисления, и получает в него индекс. Правило: передавать в `map` функцию, арность которой вы знаете, или оборачивать явно — `map((x) => parseInt(x, 10))`.

### `forEach` не для преобразования

`forEach` возвращает `undefined`. Он нужен только для побочных эффектов, и попытка собрать результат через него выглядит так:

```js
const titles = [];
items.forEach((item) => titles.push(item.title));  // работает, но лишнее
const titles = items.map((item) => item.title);    // то же самое
```

Второй вариант не «красивее» — он короче на одну мутируемую переменную, и его результат нельзя случайно изменить между созданием и использованием.

### Цепочки и количество проходов

Каждое звено цепочки — отдельный полный проход и отдельный новый массив:

```js
data
  .filter((x) => x.active)   // проход 1, массив 1
  .map((x) => x.title)       // проход 2, массив 2
  .slice(0, 10);             // проход 3, массив 3
```

Три прохода, три массива, из которых два — промежуточные и сразу становятся мусором.

Важно не сделать из этого неверный вывод. Для списка из сотен элементов разница между тремя проходами и одним незаметна: это десятки микросекунд, и переписывать цепочку в `reduce` ради них — ухудшение читаемости без выигрыша. Значение имеет не количество проходов, а **частота вызова**: цепочка, выполняемая на каждый рендер списка при скролле, — совсем другая история, чем та же цепочка, выполняемая один раз. Как это измерить, а не угадать, — блок 05.

Порядок звеньев, напротив, имеет значение всегда: `filter` перед `map` обрабатывает меньше элементов, чем `map` перед `filter`, — и даёт тот же результат, если `map` не меняет поле, по которому фильтруют. Если меняет, перестановка звеньев меняет и результат.

### `reduce` — универсальный, но не всегда читаемый

`reduce` выражает и `map`, и `filter`, и агрегацию, и группировку:

```js
const total = lessons.reduce((sum, l) => sum + l.duration, 0);

const byId = lessons.reduce((acc, l) => {
  acc[l.id] = l;
  return acc;
}, {});
```

Начальное значение (второй аргумент) стоит передавать всегда: без него `reduce` берёт первым аккумулятором первый элемент, и на **пустом массиве бросает `TypeError`**. Пустой массив в мобильном приложении — норма (нет данных, не загрузилось, пользователь всё отфильтровал), поэтому отсутствие начального значения это дефект, ждущий своих данных.

Когда `reduce` уместен: агрегация в одно значение, построение индекса, группировка, одновременный подсчёт нескольких величин за один проход. Когда не уместен: там, где он выражает `map` или `filter` — тогда читается хуже без выигрыша.

Отдельно о мутации аккумулятора: в примере с `byId` аккумулятор мутируется, и это нормально — объект создан внутри функции и наружу не виден никому, кроме результата. Запрет на мутацию относится к **чужим** данным, а не ко всему подряд (1.13).

### Новая ссылка на каждый вызов

Центральный факт урока:

```js
const a = [1, 2, 3];
a.map((x) => x) === a.map((x) => x);   // false
a.filter(() => true) === a;            // false — даже если ничего не отфильтровано
```

`filter`, не отбросивший ни одного элемента, всё равно возвращает **новый** массив. Содержимое одинаковое, идентичность другая — и для любого, кто сравнивает по ссылке, это «изменившиеся данные» (1.4).

То же относится к `Object.keys`, `Object.values`, `Object.entries` и `Array.from` — все создают новый массив на каждый вызов.

## RN relevance

### Цепочка в теле компонента

```jsx
function LessonList({ lessons, query }) {
  const visible = lessons
    .filter((l) => l.title.includes(query))
    .map((l) => ({ ...l, label: `${l.order}. ${l.title}` }));

  return <FlatList data={visible} ... />;
}
```

Код корректный: ничего не мутирует, читается однозначно. И при этом на **каждый** рендер компонента он создаёт новый массив `visible`, в котором ещё и каждый элемент — новый объект.

Три следствия, и все три самостоятельные:

1. **`FlatList` получает новый `data`** и вынужден считать, что данные изменились, даже когда `query` и `lessons` те же;
2. **каждый элемент — новый объект**, поэтому ни одна мемоизированная ячейка не распознает свои данные как неизменившиеся: перерисуется весь видимый список;
3. **работа выполняется заново** при любом рендере, включая вызванные причинами, не связанными с этим списком.

Ни одно из следствий не является ошибкой React или `FlatList`. Все три — прямое следствие того, что `filter` и `map` создают новые ссылки.

> **Решения в этом уроке сознательно не даются.** `useMemo`, стабильные ссылки, вынос вычисления за пределы компонента, селекторы — всё это блоки 03 и 06, и там же разбирается, **когда это оправдано, а когда мемоизация дороже самой работы**. Сейчас задача одна: научиться видеть, где создаются новые ссылки.

### Новый массив в зависимостях эффекта

```jsx
const ids = lessons.map((l) => l.id);

useEffect(() => {
  syncProgress(ids);
}, [ids]);          // новый массив на каждый рендер
```

`ids` — новая ссылка при каждом рендере. React сравнивает зависимости по идентичности, видит «изменилось» и выполняет эффект **после каждого рендера**, а не только при изменении уроков. Само по себе это лишняя работа. Цикл возникает, когда эффект прямо или косвенно обновляет состояние (например, `syncProgress` по завершении записывает результат через `setState` или в стор, на который подписан этот компонент): обновление вызывает рендер, рендер создаёт новый `ids`, эффект выполняется снова — **бесконечный цикл**.

В React Native это выглядит как приложение, которое греет устройство и расходует батарею при открытом экране, иногда без видимых изменений на экране. Это один из немногих дефектов этого урока, который проявляется громко.

Тот же механизм срабатывает с инлайн-объектом и инлайн-функцией в зависимостях. Почему это одна и та же проблема — 1.12.

### `find` в рендере списка

```jsx
{lessons.map((lesson) => (
  <Row
    key={lesson.id}
    author={authors.find((a) => a.id === lesson.authorId)}
  />
))}
```

`find` возвращает **существующий** объект, то есть ту же ссылку — с идентичностью здесь проблемы нет. Проблема другая: для каждого из N уроков выполняется поиск по массиву авторов, то есть до N умножить на M сравнений. На 500 уроках и 50 авторах это до 25 000 сравнений на каждый рендер.

Решение — индекс вместо поиска, построенный один раз:

```js
const authorById = authors.reduce((acc, a) => { acc[a.id] = a; return acc; }, {});
```

Это та же идея, что нормализация данных в блоке 06 (6.8), и здесь полезно увидеть её в самом простом виде: поиск по массиву в цикле — это квадратичная работа, а индекс превращает её в линейную.

## Типичные заблуждения

**«`map` оптимизирует цепочку сам.»** Возникает из опыта языков с ленивыми последовательностями, где цепочка собирается в один проход. В JS методы массива энергичные: каждое звено честно создаёт массив. Ленивость появляется только с итераторами и библиотеками, построенными на них.

**«Одинаковый результат — одинаковая ссылка.»** Возникает из разумного ожидания, что функция, не изменившая данных, вернёт то же значение. `filter(() => true)` возвращает новый массив именно потому, что метод не анализирует, изменилось ли что-то, — он всегда строит результат.

**«`forEach` можно использовать для преобразования.»** Возникает потому, что это работает: внешний массив заполняется через `push`. Цена — мутируемая переменная и ручное управление тем, что `map` делает одним выражением.

**«Цепочка медленная, надо переписать в `reduce`.»** Возникает из верного наблюдения о количестве проходов, из которого сделан неверный вывод о значимости. На типичных размерах списков разница несущественна, а читаемость падает заметно. Значение имеет частота вызова и размер данных, и то и другое надо измерять (блок 05), а не предполагать.

**«`reduce` без начального значения работает так же.»** Возникает потому, что на непустом массиве разницы действительно нет. На пустом — `TypeError`, и пустой массив в мобильном приложении это нормальное состояние, а не исключение.
