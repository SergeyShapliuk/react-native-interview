# 1.3 Coercion и сравнения — theory

> 🟢 REFRESH. Правила приведения вы применяете каждый день. Ось урока — те два места, где они дают видимый дефект на экране мобильного приложения: условный рендер и значения по умолчанию.

## Refresh

### Coercion

**Coercion (приведение типов)** — автоматическое преобразование значения к другому типу, которое язык делает сам, когда операция требует типа, отличного от того, что ей дали.

Три контекста, в которых это происходит:

- **к булеву** — в условии `if`, в `&&`, `||`, `!`;
- **к числу** — в арифметике, кроме `+` со строкой;
- **к строке** — в конкатенации через `+`, в шаблонной строке.

```js
1 + "2";      // "12"  — + со строкой конкатенирует
1 - "2";      // -1    — минус работает только с числами
"3" * "4";    // 12    — оба приводятся к числу
[] + {};      // "[object Object]"
```

Оператор `+` — единственный перегруженный: если хоть один операнд строка, он конкатенирует. Все остальные арифметические операторы приводят к числу. Отсюда вся неинтуитивность `+`.

### Truthy и falsy

**Falsy** — значения, приводящиеся к `false`. Их ровно восемь, и список стоит знать точно:

```
false · 0 · -0 · 0n · "" · null · undefined · NaN
```

Всё остальное truthy. Включая то, что интуитивно ожидается falsy:

```js
Boolean([]);        // true — пустой массив truthy
Boolean({});        // true — пустой объект truthy
Boolean("0");       // true — непустая строка
Boolean("false");   // true — непустая строка
```

Пустой массив truthy потому, что это объект, а все объекты truthy — содержимое не рассматривается. Это регулярно ломает проверки вида `if (items)` там, где имелось в виду `if (items.length)`.

### `==` vs `===`

`===` сравнивает без приведения: разные типы — сразу `false`.

`==` при разных типах приводит операнды и только потом сравнивает. Правила приведения для `==` достаточно запутаны, чтобы не держать их в голове целиком, но два факта нужны:

```js
null == undefined;  // true  — единственная полезная пара
null === undefined; // false
0 == "";            // true
0 == "0";           // true
"" == "0";          // false  — и вот здесь транзитивность ломается
```

Практическое правило: `===` всюду, `== null` — допустимое исключение, если нужно одной проверкой поймать и `null`, и `undefined`. Остальные случаи `==` в современном коде — повод насторожиться при ревью.

### `Object.is`

Строгое сравнение с двумя исправлениями:

```js
NaN === NaN;            // false
Object.is(NaN, NaN);    // true

0 === -0;               // true
Object.is(0, -0);       // false
```

В продуктовом коде `Object.is` нужен редко, но знать его стоит по другой причине: **именно он используется внутри React** при сравнении состояния и значений в зависимостях хуков. Поэтому `setState(NaN)` при текущем значении `NaN` не вызовет ре-рендер, а переход от `0` к `-0` — вызовет. Подробнее — в 3.10.

### `??` vs `||`

Оба подставляют альтернативу, но реагируют на разное:

- **`||`** срабатывает на любое falsy-значение;
- **`??`** срабатывает только на `null` и `undefined`.

```js
0 || 10;     // 10  — ноль falsy, подставилась альтернатива
0 ?? 10;     // 0   — ноль не null и не undefined
"" || "n/a"; // "n/a"
"" ?? "n/a"; // ""
```

Это не вопрос стиля. `||` затирает корректные `0` и `""`, и ровно это даёт класс дефектов «правильное значение заменилось дефолтом».

## RN relevance

### Условный рендер на нуле — самая частая ошибка в RN

```jsx
{count && <Text>Непрочитанных: {count}</Text>}
```

При `count === 0` выражение `count && ...` возвращает `0`, а не `false`. React рендерит `0` (это валидная нода), и в React Native это даёт один из двух исходов:

- **видимый ноль на экране** там, где ничего быть не должно;
- **падение** с ошибкой вида «text strings must be rendered within a `<Text>` component», если `0` оказался вне `Text`.

Второй исход — специфика React Native, которой нет в веб-разработке: в браузере лишний `0` просто отрисуется в DOM. В RN любой текстовый узел обязан находиться внутри `Text`, и голый `0` нарушает это требование.

Та же ошибка с массивом:

```jsx
{items.length && <List items={items} />}   // при пустом массиве отрендерит 0
{items.length > 0 && <List items={items} />} // корректно
{!!items.length && <List items={items} />}   // корректно
```

Работающее правило: **в условном рендере слева от `&&` должно стоять булево значение**, а не число и не строка. Явное сравнение или `!!` — не украшение, а защита от рендера значения.

### `value || defaultValue` затирает валидные данные

```js
const progress = serverProgress || 100;   // прогресс 0 превратится в 100
const label = title || "Без названия";    // пустая строка станет заглушкой
const limit = settings.limit || 20;       // limit: 0 станет 20
```

В мобильном приложении это выглядит как «прогресс нового курса показан как завершённый» или «настройка не применяется». Дефект тихий: значение не пустое, оно подменено.

Исправление — `??`, но с условием: нужно решить, действительно ли `0` и `""` валидны в этом месте. Если пустая строка в заголовке — признак битых данных, `||` корректен, и это осознанное решение, а не случайность.

### `==` в условиях рендера

Сравнение через `==` в RN-коде чаще всего встречается в проверках идентификаторов, пришедших из разных источников: `id` из параметров навигации приходит строкой, а `id` из состояния — числом, и `==` «чинит» несовпадение.

Проблема не в приведении, а в том, что оно скрывает настоящий дефект: **идентификатор имеет два разных типа в одном приложении**. Исправляется это не оператором сравнения, а приведением типа на границе — в месте, где параметр читается из навигации (2.13).

### Сравнение объектов

`===` для объектов сравнивает ссылку, а не содержимое, и приведение здесь не участвует:

```js
{ a: 1 } === { a: 1 }   // false
[1, 2] == [1, 2]        // false — == тоже не помогает
```

Это не имеет отношения к coercion и является отдельной темой (1.12) — но упомянуть здесь нужно, потому что вопрос «почему `==` не сравнил содержимое» возникает именно в этом месте.

## Типичные заблуждения

**«`??` — это синоним `||`.»** Возникает потому, что в большинстве случаев они дают одинаковый результат: значения обычно либо осмысленные, либо `null`. Расхождение проявляется только на `0`, `""` и `false` — то есть на валидных значениях, которые выглядят как пустые. Именно поэтому заблуждение живёт долго и выстреливает поздно.

**«Falsy и `null`-подобное — одно и то же.»** Прямое следствие предыдущего: восемь falsy-значений против двух nullish. Разработчик, для которого это один список, не может выбрать между `||` и `??` осознанно.

**«`===` сравнивает содержимое объектов.»** Возникает из опыта языков, где оператор равенства для объектов перегружается или сравнивает поля. В JS содержимое не сравнивает ни `==`, ни `===`.

**«Пустой массив falsy.»** Возникает по аналогии с другими языками, где пустая коллекция ложна. В JS truthy всё, что объект, — и проверка `if (items)` на пустом массиве проходит, что даёт дефект «блок выполнился на пустых данных».

**«`{count && ...}` безопасно, потому что React не рендерит ложные значения.»** React действительно не рендерит `false`, `null` и `undefined` — но `0` рендерит, потому что это осмысленное значение. Заблуждение держится на верном наблюдении, из которого сделан слишком широкий вывод.
