# 1.3 Coercion и сравнения — practice

## Проверка понимания

---

**1. Что отрендерит `{items.length && <List/>}` при пустом массиве?**

<details>
<summary>Ответ</summary>

Отрендерит `0`. `items.length` равна нулю, `0 && ...` возвращает `0`, и React получает `0` как дочернюю ноду. В React Native это либо видимый ноль на экране, либо падение с ошибкой о тексте вне компонента `Text` — в зависимости от того, где находится выражение.

Корректно: `items.length > 0 && ...` или `!!items.length && ...`.

**Ответ «ничего не отрендерит»** вскрывает модель «`&&` возвращает булево». `&&` возвращает **операнд**, а не `true`/`false`: при falsy левом операнде — левый, иначе правый. Без этого факта предсказать поведение условного рендера невозможно.

**Ответ «упадёт»** частично верен, но вскрывает незнание того, от чего зависит исход. Падение происходит только если `0` оказался вне `Text`; внутри `Text` будет тихий видимый ноль, который найти труднее.
</details>

---

**2. Чем `??` отличается от `||` на значении `0`?**

<details>
<summary>Ответ</summary>

`0 || 10` даёт `10`: ноль falsy, и `||` подставляет альтернативу. `0 ?? 10` даёт `0`: ноль не `null` и не `undefined`, и `??` альтернативу не подставляет.

**Ответ «ничем, оба вернут 10»** вскрывает именно то заблуждение, которое даёт дефект «валидный ноль заменён дефолтом». Это самая дорогая ошибка урока, потому что данные не пустые, а подменённые, и отличить одно от другого на экране нельзя.

**Ответ «`??` безопаснее, надо всегда использовать его»** вскрывает замену одного рецепта другим. `||` корректен там, где пустая строка или ноль действительно означают отсутствие данных, — и выбор между операторами это решение о смысле данных, а не о безопасности.
</details>

---

**3. Где `Object.is` расходится с `===`?**

<details>
<summary>Ответ</summary>

В двух случаях: `Object.is(NaN, NaN)` даёт `true` (а `===` — `false`), и `Object.is(0, -0)` даёт `false` (а `===` — `true`).

Практическая важность не в самих значениях, а в том, что `Object.is` — это алгоритм сравнения, который использует React при сравнении состояния и зависимостей хуков. Поэтому обновление состояния с `NaN` на `NaN` не вызовет ре-рендер, а с `0` на `-0` — вызовет.

**Ответ «нигде, это одно и то же»** вскрывает пробел, который всплывёт в 3.10: без понимания того, каким именно алгоритмом React сравнивает значения, рассуждения о причинах ре-рендера опираются на интуицию.
</details>

## Задание

**Дано.** Фрагмент экрана курса в RN-приложении. На экране несколько дефектов, связанных с приведением типов. Приложение не падает в большинстве случаев — именно поэтому дефекты дожили до продакшена.

```jsx
function CourseScreen({ route }) {
  const { courseId } = route.params;          // приходит строкой из deep link
  const course = useCourse(courseId);

  const progress = course.progress || 100;
  const title = course.title || "Без названия";
  const lessons = course.lessons ?? [];
  const activeLesson = lessons.find((l) => l.id == course.activeLessonId);

  return (
    <View>
      <Text>{title}</Text>
      <Text>Прогресс: {progress}%</Text>

      {lessons.length && <LessonList lessons={lessons} />}

      {course.certificate && <Text>Сертификат получен</Text>}

      {activeLesson && (
        <Text>Текущий урок: {activeLesson.title}</Text>
      )}

      {course.rating && <Rating value={course.rating} />}
    </View>
  );
}
```

**Требуется.**

1. Найти **все** места, где условный рендер сломается на нуле или пустой строке. Для каждого сказать, что именно увидит пользователь.
2. Найти места, где валидное значение подменяется значением по умолчанию, и объяснить, почему это опаснее отсутствия значения.
3. Объяснить, почему `l.id == course.activeLessonId` «работает», и почему его нельзя просто заменить на `===`.
4. Для каждого найденного места сказать, какое из них проявится **падением**, а какое — тихим неверным экраном. Объяснить, какой класс дефектов дороже и почему.
5. Исправить все найденные места. Для каждого исправления назвать решение о данных, которое за ним стоит.

---

<details>
<summary>Разбор</summary>

**1. Условный рендер, сломанный на нуле и пустой строке.**

| Строка | Что произойдёт |
|---|---|
| `{lessons.length && <LessonList .../>}` | при пустом списке `0` окажется прямо в `View` — **падение** с ошибкой о тексте вне `Text` |
| `{course.rating && <Rating .../>}` | при рейтинге `0` — тот же `0` в `View`, то же **падение**; при `rating === 0` вместо «нет оценок» получаем краш |
| `{course.certificate && <Text>...</Text>}` | если `certificate` — пустая строка, отрендерится `""`, то есть ничего видимого; дефекта на экране нет, но и проверка не означает того, что написано |

Отдельно `{activeLesson && ...}`: здесь ошибки нет. `activeLesson` — результат `find`, то есть объект или `undefined`; объект всегда truthy, `undefined` React не рендерит. Это важный контраст: проблема не в самой конструкции `x && <JSX/>`, а в типе левого операнда.

**2. Подмена валидных значений.**

- **`course.progress || 100`** — прогресс `0` превращается в `100`. Пользователь, только что открывший курс, видит «Прогресс: 100%». Опаснее отсутствия значения потому, что отсутствие видно: пустое место или заглушка заставляют искать причину. Подменённое значение выглядит как настоящее, и дефект обнаруживается только через жалобу пользователя — причём жалобу, которую трудно воспроизвести, ведь на курсах с прогрессом всё верно.

  Кроме того, `100` как дефолт — ещё и неверно по смыслу: отсутствие данных подменяется самым оптимистичным значением. Если дефолт нужен, им должен быть `0`.

- **`course.title || "Без названия"`** — здесь решение может быть **верным**: если пустой заголовок означает битые данные, заглушка лучше пустой строки. Это осознанный выбор, и в разборе важно его таковым и назвать: не всякий `||` — дефект.

- **`course.lessons ?? []`** — корректно. `??` здесь именно то, что нужно: пустой массив, пришедший с сервера, не должен подменяться, а отсутствующее поле должно.

**3. Про `l.id == course.activeLessonId`.**

«Работает» потому, что `==` приводит типы: `"12" == 12` даёт `true`. Раз автор написал `==`, значит, типы расходятся: `l.id` в списке уроков — число, а `course.activeLessonId` — строка. Обратите внимание, откуда он берётся: не из навигации, а из **ответа сервера** — поле объекта курса. Типичная причина — бэкенд отдаёт идентификаторы в разных эндпоинтах по-разному или поле сериализуется строкой ради больших id (1.2).

Заменить на `===` нельзя напрямую: сравнение станет корректным оператором и начнёт возвращать `false`, то есть **текущий урок перестанет находиться**. Это тот случай, когда исправление оператора ломает работающий экран, и именно поэтому такие `==` живут в проектах годами.

Настоящий дефект — не оператор, а то, что **идентификатор имеет два типа в одном приложении**. И границ, через которые строка попадает внутрь, здесь две: параметр навигации (`courseId` из deep link) и поле ответа сервера (`activeLessonId`). Исправлять нужно обе, каждую в своём месте: параметр — там, где он читается из навигации, поле — там, где разбирается ответ сервера (внутри `useCourse` или слоя API, 2.12). Приведение `courseId` в экране само по себе не меняет тип `activeLessonId` — это частая ошибка «исправили одну границу и решили, что закрыли обе». Это прямой выход на тему 2.13: тип объявлен, но на границе не проверяется, поэтому `string` приходит туда, где заявлен `number`.

**4. Падение против тихого неверного экрана.**

**Падением проявятся:** `lessons.length &&` на пустом списке и `course.rating &&` при нулевом рейтинге.

**Тихим неверным экраном проявятся:** `progress || 100`, пустая строка в `certificate`, и — потенциально — сравнение через `==`, если типы однажды совпадут иначе, чем ожидалось.

**Дороже тихий дефект**, и это главный вывод задания. Падение попадает в crash reporting (10.6), имеет стектрейс, воспроизводится и чинится за часы. Тихий неверный экран не попадает никуда: метрики в порядке, крашей нет, пользователь видит «Прогресс: 100%» и делает неверный вывод о продукте. Такой дефект обнаруживается через поддержку, живёт месяцами и обходится дороже, хотя выглядит безобиднее.

Отсюда практическое следствие: падение на `0` в React Native — неприятное, но **полезное** поведение. Оно превращает часть тихих дефектов приведения в громкие.

**5. Исправления и решения за ними.**

```jsx
function CourseScreen({ route }) {
  // решение: тип идентификатора фиксируется на границе, один раз
  const courseId = Number(route.params.courseId);
  const course = useCourse(courseId);

  // решение: отсутствие прогресса — это ноль, а не сто
  const progress = course.progress ?? 0;

  // решение: пустой заголовок считаем битыми данными, заглушка осознанна
  const title = course.title || "Без названия";

  const lessons = course.lessons ?? [];

  // решение: activeLessonId приводится к number при разборе ответа внутри useCourse
  // (вторая граница); здесь оба идентификатора уже числа, и === честен
  const activeLesson = lessons.find((l) => l.id === course.activeLessonId);

  return (
    <View>
      <Text>{title}</Text>
      <Text>Прогресс: {progress}%</Text>

      {lessons.length > 0 && <LessonList lessons={lessons} />}

      {/* решение: сертификат — это наличие, а не непустая строка */}
      {course.certificate != null && <Text>Сертификат получен</Text>}

      {activeLesson && <Text>Текущий урок: {activeLesson.title}</Text>}

      {/* решение: ноль — валидный рейтинг, его надо показать, а не скрыть */}
      {course.rating != null && <Rating value={course.rating} />}
    </View>
  );
}
```

**Что здесь принципиально.** Ни одно исправление не является заменой оператора на «более правильный». Каждое — ответ на вопрос о данных:

- является ли `0` валидным значением прогресса? Да — значит `??`;
- является ли `0` валидным рейтингом? Да — значит проверка на наличие, а не на truthy;
- является ли пустая строка валидным заголовком? Нет — значит `||` остаётся;
- какого типа идентификатор? Числового — значит приводим один раз на **каждой** границе, через которую он входит (навигация и ответ сервера), а не маскируем `==` в каждом сравнении.

**Чего разбор сознательно не делает.** Не предлагает защититься от этого класса ошибок типами: `course.progress` может быть объявлен как `number`, и это не помешает серверу прислать `null`. Почему тип на границе не является гарантией и что с этим делать — блок 02 (2.12, 2.13).
</details>
