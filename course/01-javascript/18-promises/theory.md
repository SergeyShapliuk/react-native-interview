# 1.18 Promises — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как написать асинхронный код» — а на вопрос, **что за объект появляется в памяти в момент создания промиса, какие у него состояния и кто от этих состояний зависит.**

---

## 1. Что это

**Promise** — объект, представляющий результат операции, которая уже запущена, но ещё не обязательно завершена.

Три состояния:

| Состояние | Что означает |
|---|---|
| **pending** | результата пока нет |
| **fulfilled** | операция завершилась успешно, у промиса есть значение |
| **rejected** | операция завершилась отказом, у промиса есть причина отказа |

**settled** — общее название для `fulfilled` и `rejected`: «завершился, неважно как». Это понятие понадобится при разборе `allSettled` и `race`.

Два свойства состояния, из которых выводится почти всё остальное:

1. **Переход происходит один раз и необратим.** Из `pending` можно уйти в `fulfilled` или `rejected`, и всё. Повторный вызов `resolve` или `reject` не делает ничего — не ошибка, а молчаливое игнорирование.
2. **Состояние существует независимо от того, подписан ли кто-нибудь.** Промис может завершиться отказом, когда у него нет ни одного обработчика — именно отсюда растёт `unhandledRejection` (1.11).

### Чем промис не является

- **Не задача.** Промис не содержит кода операции и не умеет её запускать, повторять или отменять. Код живёт в функции-исполнителе, переданной в `new Promise`, или внутри API, который промис вернул.
- **Не контейнер, который можно опустошить.** Прочитать значение синхронно нельзя: доступ к результату возможен только через колбэк.
- **Не способ сделать код «не блокирующим».** Если внутри промиса выполняется тяжёлый синхронный цикл, он заблокирует всё ровно так же (1.20).

## 2. Как это работает

### Работа начинается при создании

Это главный факт урока.

```js
const p = fetch("https://api.example.com/course/1"); // запрос ушёл здесь
// ... сто строк другого кода ...
const res = await p;                                  // здесь только ожидание результата
```

Функция-исполнитель `new Promise((resolve, reject) => { ... })` вызывается **синхронно**, внутри самого вызова `new Promise`. Не позже, не лениво, не при подписке.

```js
console.log("A");
const p = new Promise((resolve) => {
  console.log("B");          // выполнится прямо здесь
  setTimeout(() => resolve("C"), 1000);
});
console.log("D");
// A, B, D
```

Проверить это на реальном API можно без таймеров: создайте два промиса сетевых запросов, затем сделайте `await` по очереди — в сетевой панели видно, что оба запроса ушли сразу, а не один за другим. Это и есть механика параллельной загрузки: `Promise.all` ничего не распараллеливает — он только ждёт уже запущенное.

### `then` создаёт новый промис

`then`, `catch` и `finally` не «навешивают обработчик на промис» — каждый из них **возвращает новый промис**, состояние которого определяется тем, что сделал обработчик.

```js
const a = loadCourse();            // Promise<Course>
const b = a.then((c) => c.title);  // Promise<string> — другой объект
a === b;                           // false
```

Правила, по которым определяется состояние нового промиса:

| Что сделал обработчик | Состояние нового промиса |
|---|---|
| вернул обычное значение | `fulfilled` с этим значением |
| вернул промис | ждёт его и перенимает его состояние |
| бросил исключение | `rejected` с этим исключением |
| ничего не вернул | `fulfilled` со значением `undefined` |

Последняя строка — источник одного из самых частых дефектов: обработчик, который что-то делает, но забывает `return`, превращает цепочку в `Promise<undefined>`.

`catch(fn)` — это ровно `then(undefined, fn)`. Отсюда важное следствие: **`catch` не завершает цепочку, а продолжает её.** Если обработчик `catch` вернул значение, следующий `then` увидит успех:

```js
loadCourse()
  .catch(() => null)              // ошибка «поглощена», состояние снова fulfilled
  .then((course) => render(course)); // получит null, а не ошибку
```

Это нормальный приём (деградация с заглушкой), но его надо выбирать осознанно, а не получать случайно.

`finally` отличается от обоих: его обработчик не получает ни значения, ни причины отказа и **не меняет** состояние — результат проходит сквозь него. Исключение одно: если сам `finally` бросит, новое исключение заменит прежний результат.

### Цепочка против ветвления

Разница, которую легко не заметить:

```js
// цепочка: catch покрывает обе предыдущие операции
load().then(parse).catch(report);

// ветвление: catch покрывает только load, ошибка в parse никем не обработана
const p = load();
p.then(parse);
p.catch(report);
```

Во втором случае у `p` два независимых подписчика, и промис, созданный `p.then(parse)`, не имеет обработчика отказа вообще. Если `parse` бросит — это `unhandledRejection` (1.11).

### Комбинаторы

Все четыре принимают iterable промисов (или обычных значений — те оборачиваются автоматически) и возвращают один новый промис. Ни один из них **не запускает** операции: к моменту вызова они уже запущены.

| Комбинатор | Успех, когда | Отказ, когда | Результат при успехе |
|---|---|---|---|
| `Promise.all` | все `fulfilled` | **первый** `rejected` | массив значений, в порядке входа |
| `Promise.allSettled` | **всегда** (когда все `settled`) | никогда | массив `{status, value \| reason}` |
| `Promise.race` | первый `settled` — `fulfilled` | первый `settled` — `rejected` | значение первого завершившегося |
| `Promise.any` | первый `fulfilled` | **все** `rejected` | значение первого успешного |

Три уточнения, которые обычно и проверяют:

- **`all` — fail-fast по результату, но не по работе.** Он отвергает результат при первом отказе, однако остальные операции продолжаются: отменить их он не может и не пытается. Запросы уйдут, ответы придут, обработчики не вызовутся. Отсюда — ошибочное ощущение «`all` отменил остальные».
- **`race` реагирует на первый `settled`, а не на первый успешный.** Если самый быстрый промис завершился отказом, `race` отвергает — даже если все остальные успешны. Отсюда его основное применение: таймаут (гонка запроса с промисом, который отвергает через N мс).
- **`any` отвергает `AggregateError`** — объект с полем `errors`, содержащим все причины отказа. Это не обычный `Error`, и код, который читает `err.message`, получит бесполезную строку.

Пустой вход: `all([])` и `allSettled([])` немедленно успешны, `any([])` немедленно отвергает, `race([])` остаётся `pending` навсегда.

## 3. Почему это важно

Промис — это точка, где асинхронность становится **значением**, которое можно передать, сохранить, передать в комбинатор и обработать позже. До промисов этого не было: колбэк нельзя сохранить в переменную и спросить «ты уже завершился?».

Но практическая важность урока в другом — в **семантике отказа**. Выбор комбинатора это не вопрос стиля, а продуктовое решение, записанное в коде:

```
Promise.all        → «без всех этих данных экран не имеет смысла»
Promise.allSettled → «покажем то, что получилось»
Promise.race       → «нужен ответ за N мс, иначе считаем провалом»
Promise.any        → «любой из источников подойдёт»
```

Эти четыре формулировки — продуктовые требования. Если они не сформулированы, комбинатор выбирается по привычке, и обычно это `all` — то есть по умолчанию выбирается самая строгая политика: «любой сбой любого запроса означает пустой экран».

### DEEP DIVE: почему `all` — опасная настройка по умолчанию

```
один необязательный запрос отказал
    ↓
Promise.all отвергает немедленно
    ↓
await в загрузчике экрана бросает
    ↓
catch выставляет состояние ошибки
    ↓
пользователь видит пустой экран с кнопкой «Повторить»
    ↓
хотя главные данные пришли и лежат в завершившихся промисах
```

Данные **есть** — они в `fulfilled`-промисах, которые никто не прочитал, потому что `all` отбросил весь результат. Это не баг `all`: это буквально то, о чём его попросили. Ошибка в том, что его попросили об этом не задумываясь.

Вторая сторона: надёжность комбинированного результата падает с числом участников. Если каждый из пяти запросов успешен в 99 % случаев, `all` из пяти успешен примерно в 95 % — то есть один из двадцати открытий экрана заканчивается ничем, причём на мобильной сети «99 %» слишком оптимистично.

## 4. Где это в React Native

Промис в RN — не «одна из возможностей», а **основной способ, которым платформа возвращает результат**. Практически всё, что пересекает границу JS↔native (1.2), возвращает промис.

### Любой сетевой запрос

`fetch` и любая обёртка над ним. На мобильной сети отказ — не исключительная ситуация, а штатный режим: переключение Wi-Fi → LTE, туннель, лифт, отозванный токен.

### API нативных модулей

Метод TurboModule, объявленный как асинхронный, возвращает промис. Результат приходит с нативной стороны и ограничен тем, что способно пересечь границу (1.2): получить обратно `Map`, экземпляр класса или функцию нельзя. Детали контракта — 4.1 и блок 09.

### `AsyncStorage` и локальное хранилище

```js
const raw = await AsyncStorage.getItem("progress");
```

Каждое чтение и запись — промис. Частая ошибка проектирования: последовательная вычитка десяти ключей вместо `multiGet` или `Promise.all` — десять раздельных ожиданий в момент старта экрана (1.19, 5.6).

### Разрешения

```js
const status = await request(PERMISSIONS.IOS.CAMERA);
```

Промис, который может оставаться `pending` **минуты** — пока пользователь не ответит на системный диалог, свернув приложение и вернувшись. Код, который предполагает «промис завершается быстро», здесь ломается: экран всё это время в состоянии загрузки.

### Загрузка данных экрана — главный сюжет урока

```jsx
// Экран курса: заголовок обязателен, отзывы и рекомендации — нет
const [course, reviews, recommended] = await Promise.all([
  api.getCourse(id),      // без этого экрана нет
  api.getReviews(id),     // блок можно скрыть
  api.getRecommended(id), // блок можно скрыть
]);
```

Отказ `getRecommended` — самого необязательного из трёх — даёт пустой экран. Это разбирается в задании practice.md, и та же развилка вернётся в блоке 07, когда речь пойдёт об экране с несколькими источниками, кэшем (7.7) и offline (7.14).

### Промис, созданный в теле компонента

```jsx
function CourseScreen({ id }) {
  const data = api.getCourse(id); // новый запрос на каждый рендер
  // ...
}
```

Тело компонента выполняется при каждом рендере, а промис запускает работу при создании (угол 2) — значит, каждый рендер отправляет новый запрос. При этом результат предыдущего никому не нужен, но ответ придёт и будет обработан: отсюда гонки (7.10). Механизм здесь двойной — создание промиса и идентичность объекта (1.12): каждый рендер получает **другой** промис, поэтому никакое сравнение по ссылке его не отсечёт.

## 5. Типичные ошибки

**`Promise.all` там, где нужен `allSettled`.** Возникает из того, что `all` — первое, что узнают, и единственное, что помнят; плюс в счастливом сценарии оба ведут себя одинаково, а расхождение проявляется только при отказе — то есть на устройстве пользователя, а не на машине разработчика с хорошей сетью.

**Ожидание, что `all` отменит остальные операции.** Возникает из слова «fail-fast», которое описывает поведение результата, а не работы. Промис не владеет операцией и не умеет её прекращать; отмена — отдельный механизм (`AbortController`, 7.10).

**Потерянный `catch`.** Две формы. Первая — ветвление вместо цепочки (угол 2): обработчик повешен на исходный промис, а отказ происходит в производном. Вторая — `catch` в середине цепочки, после которого добавили новые `then`: они снова без обработчика. Возникает потому, что `catch` читается как «конец», хотя это обычное звено.

**`catch`, который поглощает ошибку молча.** `catch(() => {})` возвращает `fulfilled`-промис со значением `undefined`, и дальше код работает с `undefined` как с данными — падая позже и в другом месте (1.11, «проглоченная ошибка»).

**Создание промиса в рендере.** Возникает из привычки писать «получение данных рядом с их использованием» и из невидимости проблемы в dev: один лишний запрос в логе не бросается в глаза. В release на медленной сети это серия запросов, гонка ответов и греющееся устройство.

**`race` для «кто быстрее успеет».** Возникает из названия. `race` берёт первый `settled` — быстрый отказ (например, мгновенный `ECONNREFUSED` от одного из хостов) выигрывает гонку у медленного успеха. Для «любой, кто успеет» существует `any`.

**Создание промиса-обёртки вокруг промиса.** `new Promise((res, rej) => api.get().then(res).catch(rej))` — лишний объект, который воспроизводит поведение исходного промиса и при этом теряет часть ошибок (например, синхронное исключение из `api.get()` до возврата промиса). Возникает из привычки «привести к промису то, что уже промис».

**Чтение значения промиса синхронно.** `const data = api.get(); data.title` даёт `undefined`, потому что `data` — промис, а не результат. Чаще всего это следствие забытого `await` (1.19), и в TypeScript отсекается типами (блок 02).

## 6. Trade-offs

### `all` против `allSettled`

| | `Promise.all` | `Promise.allSettled` |
|---|---|---|
| код | короткий, деструктуризация массива | обработка каждого элемента по `status` |
| поведение при отказе | нет результата вообще | есть частичный результат |
| что видит пользователь | экран ошибки | экран с деградацией |
| типизация результата | кортеж значений | union по `status`, нужен разбор |
| когда уместен | данные бессмысленны по отдельности | есть главное и второстепенное |

`all` не «хуже» — он дешевле по коду и честнее, когда данные действительно неразделимы (нет смысла рисовать корзину без цен). Цена `allSettled` — разбор результата и необходимость решить, что показывать на месте каждого отказавшего блока, то есть **дизайн-решение**, а не только код.

### Частичный результат стоит проектирования

Деградация не бесплатна: для каждого необязательного блока нужно решить, что будет на его месте (пустота, скелет, прошлое значение из кэша, сообщение), нужно ли уведомить пользователя и нужно ли повторить запрос. Это несколько состояний экрана вместо двух. Поэтому `allSettled` не является «правильным ответом по умолчанию» — он правильный ответ там, где деградация **спроектирована**.

### Параллельность против нагрузки

Запустить все запросы сразу — быстрее по времени до экрана, но даёт пик нагрузки: на слабой сети десять одновременных запросов конкурируют и в сумме завершаются медленнее, чем пять и пять. Промисы к этому отношения не имеют — ограничение параллелизма делается отдельно (пул, очередь), и это материал блока 07.

### Таймаут через `race` против отмены

`race` с таймаутом даёт результат за гарантированное время, но операция продолжается: соединение живёт, ответ придёт, трафик потрачен. Это приемлемо как быстрое решение и неприемлемо как постоянное — настоящая отмена требует `AbortController` (7.10).

## 7. Связи с другими частями системы

**Назад:**

- **1.11 Error handling** — куда уходит ошибка из асинхронного кода и что такое `unhandledRejection`. Этот урок добавляет к той картине состояние: отказ промиса — не «ошибка в воздухе», а зафиксированное состояние объекта, у которого может не быть подписчиков;
- **1.12 References** — промис это объект с идентичностью: каждый вызов `then` создаёт новый, а промис, созданный в рендере, каждый раз другой;
- **1.2 Data types** — что способно вернуться из нативного API через промис.

**Вперёд — внутри цепочки блока:**

- **[1.19 async/await](../19-async-await/)** — синтаксис над объектом, который разобран здесь. Весь разговор о «забытом `await`» и о сериализации независимых запросов опирается на один факт этого урока: работа началась при создании, а `await` только ждёт;
- **[1.20 Event loop](../20-event-loop/)** — **когда** выполнится то, что здесь запланировано. Здесь зафиксировано, что обработчик `then` не вызывается синхронно; почему именно так и в какой момент — там;
- **[1.21 Microtasks и macrotasks](../21-microtasks-and-macrotasks/)** — точный порядок: обработчики промисов попадают в очередь микротасков, и этим объясняется их приоритет над таймерами;
- **1.22 Memory** — `pending`-промис удерживает свои обработчики, а обработчики удерживают замкнутое окружение (1.14): промис, который никогда не завершится, это удержание.

**Вперёд — за пределы блока:**

- **3.3 Путь обновления** — обработчик `then`, вызывающий `setState`, попадает в путь обновления React, и от момента его вызова зависит батчинг;
- **7.3 Ошибки, retry, backoff, таймауты** — здесь выбран комбинатор, там решается, что делать с отказом: повторять, с какой задержкой, сколько раз;
- **7.7 TanStack Query / RTK Query** — слой, который снимает с экрана и выбор комбинатора, и дедупликацию запросов, и состояния загрузки. Чтобы им пользоваться осознанно, нужно знать, что он делает за вас — то есть этот урок;
- **7.10 Race conditions и отмена** — продолжение сюжета «промис в рендере» и «`all` не отменяет остальные»;
- **7.14 Offline-first** — предельный случай частичного результата: правды нет ни для одного блока экрана;
- **11.3 Тестирование асинхронного кода** — тест видит ровно те состояния, которые разобраны здесь.

**Главное, что должно остаться после урока.** Промис — объект состояния над **уже запущенной** работой. Он не запускает, не откладывает и не отменяет. Единственное решение, которое разработчик принимает на этом уровне, — какую семантику отказа выбрать для группы операций, и это решение продуктовое.
