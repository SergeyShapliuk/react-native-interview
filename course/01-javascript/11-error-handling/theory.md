# 1.11 Error handling: try/catch и асинхронность — theory

> 🟢 REFRESH. Ось урока: `try/catch` ловит только то, что выброшено в пределах его **синхронного** выполнения. Всё, что выполняется позже — колбэк таймера, колбэк промиса, вызванная и не ожидаемая `async`-функция, — летит мимо, и в React Native это заканчивается либо тихим провалом, либо красным экраном в dev и крашем без контекста в release.

## Refresh

### `throw` и объект `Error`

`throw` немедленно прекращает нормальное выполнение и начинает раскручивать стек вызовов вверх, пока не найдёт ближайший `catch`. Бросить можно любое значение, но осмысленно бросать только `Error` — объект, который помимо текста несёт информацию о месте возникновения.

**`Error`** — встроенный класс, у экземпляра которого есть три значимых поля:

| Поле | Что в нём | Кто им пользуется |
|---|---|---|
| `message` | текст, который передали в конструктор | логи, UI, отчёт о краше |
| `name` | имя класса ошибки (`"Error"`, `"TypeError"`, своё) | фильтрация и группировка |
| `stack` | снимок стека вызовов на момент **создания** объекта | поиск причины |

```js
const e = new Error('payload is not an object');
e.name;    // 'Error'
e.message; // 'payload is not an object'
e.stack;   // 'Error: payload is not an object\n    at parsePayload (...)\n    at ...'
```

Важная деталь: `stack` заполняется в момент `new Error(...)`, а не в момент `throw`. Поэтому `const e = new Error(...)` на верхнем уровне модуля с последующим `throw e` из глубины даёт бесполезный стектрейс.

У `Error` есть и поле `cause` — ссылка на исходную ошибку: `new Error('не удалось обновить профиль', { cause: err })`. Это способ добавить контекст, не потеряв первопричину.

### `try` / `catch` / `finally`

```js
try {
  const data = parsePayload(raw);   // защищённый участок
  return data;
} catch (err) {
  report(err);                      // сюда попадает всё, что выброшено ВНУТРИ try
  return null;
} finally {
  setLoading(false);                // выполнится и при успехе, и при ошибке, и при return
}
```

Три факта, которые стоит держать в голове:

- `catch` получает **значение**, а не обязательно `Error`. Поэтому `err.message` может быть `undefined`, а `err instanceof Error` — `false`;
- `finally` выполняется в любом случае, включая выход через `return` или `throw` из `try`. Это место для освобождения ресурсов и сброса флагов загрузки, а не для логики;
- `return` или `throw` внутри `finally` **перекрывает** то, что собирался вернуть или бросить `try`. Так ошибки теряются молча.

### Почему `try/catch` не ловит ошибку из колбэка, выполненного позже

Это главный механизм урока.

`try` — не огороженная область кода, а **запись в текущем кадре стека вызовов**: «пока выполняется этот кадр, ошибки перенаправляй сюда». Защита действует столько, сколько живёт этот кадр.

```js
try {
  setTimeout(() => {
    throw new Error('boom');   // НЕ попадёт в catch ниже
  }, 1000);
} catch (err) {
  // сюда попадёт только ошибка самого вызова setTimeout
}
```

Что происходит по шагам:

1. `setTimeout` вызван и мгновенно вернул управление — он только зарегистрировал функцию;
2. `try`-блок закончился, функция, в которой он был, вернула управление, **стек, содержавший `try`, размотался**;
3. через секунду рантайм вызывает колбэк — с чистого стека, в котором никакого `try` уже нет;
4. ошибка доходит до верха этого нового стека и становится необработанной.

Ровно то же справедливо для колбэка в `.then()`, для обработчика события, для колбэка нативного модуля и для функции, переданной в `requestIdleCallback` (или в `InteractionManager.runAfterInteractions` в старом коде — в RN 0.87 этот API удалён из ядра). Вопрос не в том, «внутри» ли колбэк текстуально, а в том, **из какого стека он вызван**.

> Почему колбэк получает собственный стек и чем отличаются очереди таймеров и промисов, разбирается в 1.15 (execution context) и 1.20 (event loop). Для этого урока достаточно формулировки: **стек, в котором стоял `try`, к моменту вызова колбэка уже завершился.**

Следствие: защищать надо не точку регистрации, а тело колбэка.

```js
setTimeout(() => {
  try {
    doWork();
  } catch (err) {
    report(err);
  }
}, 1000);
```

### Ошибка в промисе и `unhandledRejection`

Промис не бросает исключение — он **переходит в состояние rejected**. Для `try/catch` это не ошибка, а обычное возвращённое значение.

```js
try {
  fetchProfile();        // вернул promise и сразу отдал управление
} catch (err) {
  // не вызовется никогда, даже если запрос упадёт
}
```

Отказ промиса обрабатывается только двумя способами: `.catch()` на цепочке или `await` внутри `try` (1.19). Если ни одного из них нет, рантайм через некоторое время фиксирует **unhandledRejection** — отказ промиса, который никто не стал обрабатывать.

Поведение в этом случае зависит от рантайма, и это важно: в браузере и в Hermes это не обязательно останавливает приложение. Приложение продолжает работать, экран остаётся в состоянии загрузки, спиннер крутится — а причина существует только в виде предупреждения в консоли, которого в release-сборке никто не увидит.

```js
// отказ обработан — цепочка завершена
fetchProfile()
  .then(setProfile)
  .catch(report);

// отказ обработан не до конца: .catch стоит до .then, а .then создаёт
// НОВЫЙ промис — если setProfile бросит, его отказ никто не обработает
fetchProfile().catch(report).then(setProfile);
```

### Ошибка в `setTimeout`

Отдельный случай того же механизма, но с другим исходом. Колбэк таймера вызывается из рантайма, и ошибка из него не отдаётся вашему коду: нет ни вызывающей функции, которая могла бы её поймать, ни промиса, который мог бы перейти в rejected. Это необработанное исключение на верхнем уровне.

В React Native такое исключение попадает в **глобальный обработчик ошибок** (`ErrorUtils`), и по умолчанию он считает его фатальным: красный экран в dev, закрытие приложения в release. Это громкий исход — и именно его перехватывают Sentry и Crashlytics, подключая свой глобальный обработчик. Сравните с отказом промиса выше: тот по умолчанию не роняет приложение и не попадает никуда.

| Что произошло | dev | release | Попадёт ли в crash reporting |
|---|---|---|---|
| исключение в колбэке таймера, события, нативного колбэка | красный экран | закрытие приложения | да — как краш, если SDK подключён |
| отказ промиса без `catch` | предупреждение в LogBox | ничего | только если SDK отслеживает отказы промисов; по умолчанию RN в release их не отслеживает |

Любой код внутри `setTimeout`, `setInterval`, `requestAnimationFrame` и подобного несёт свою обработку ошибок сам: глобальный обработчик сообщит о падении, но не спасёт экран от закрытия.

### Своя иерархия ошибок вместо строк

Строка в `throw` технически работает:

```js
throw 'profile not found';   // работает и вредит
```

Чего она лишает:

- **нет `stack`** — отчёт из продакшена не содержит места возникновения;
- **нет `name`** — ошибки невозможно сгруппировать в crash reporting;
- `err.message` в обработчике равен `undefined`, и логи наполняются строкой `undefined`;
- `err instanceof Error` ложно, и универсальный обработчик с проверкой типа её не распознает.

Вместо строк — свои классы, отличающиеся по типу, а не по тексту:

```js
class AppError extends Error {
  constructor(message, options) {
    super(message, options);
    this.name = new.target.name;    // 'ValidationError', а не 'Error'
  }
}

class ValidationError extends AppError {
  constructor(field, message) {
    super(message);
    this.field = field;
  }
}

class NetworkError extends AppError {
  constructor(message, status, options) {
    super(message, options);
    this.status = status;
  }
}
```

Это даёт обработчику возможность принимать решение по типу, а не разбирать текст:

```js
catch (err) {
  if (err instanceof ValidationError) return showFieldError(err.field, err.message);
  if (err instanceof NetworkError && err.status >= 500) return scheduleRetry();   // 7.3
  throw err;   // чужую ошибку не глотаем — пробрасываем выше
}
```

Ограничение, о котором нужно знать заранее: `instanceof` работает только пока объект не пересёк границу сериализации. Прототип не сериализуется никогда, а что останется от полей, зависит от способа:

- **`JSON.stringify(error)`** теряет главное: `message` и `stack` — неперечислимые свойства, и в результат они не попадают. Остаются только собственные перечислимые поля — то, что вы присвоили сами (`this.name = ...`, `this.field = ...`). Для голого `new Error('x')` результат — `{}`;
- **SDK crash reporting** читает `name`, `message` и `stack` явно, по соглашению, — они в отчёт попадут. Собственные поля вроде `status` или `field` — только если SDK настроен их собирать или вы передали их как контекст (1.17, 10.6).

Поэтому `name` надо выставлять явно, как выше: в отчёте оно будет единственным, что укажет на тип ошибки, а для логирования ошибку сериализуют функцией, которая берёт `name`, `message` и `stack` явно, а не через `JSON.stringify`. Механика прототипов и то, почему они не переживают сериализацию, — 1.17.

### Что значит «ошибка проглочена»

Проглоченная (swallowed) ошибка — та, которую код перехватил и не оставил о ней никакого следа. Типичные формы:

```js
try { await save(); } catch (e) {}                      // пустой catch

try { await save(); } catch (e) { console.log('ошибка'); } // лог без самой ошибки

try { await save(); } catch (e) { return null; }        // ошибка превращена в валидное значение

fetchProfile().catch(() => {});                          // гашение rejection «чтобы не ругался»
```

Цена всегда одна и та же: дефект перемещается из точки возникновения в точку, где отсутствие данных наконец становится заметным, — обычно в другой файл и в другую фичу. Отладка идёт не там, где причина.

Правило, с которым дальше живёт весь курс: `catch` обязан сделать одно из трёх — **обработать** ошибку (показать пользователю, уйти на fallback, запустить retry), **обогатить контекстом и пробросить** (`throw new Error('...', { cause: err })`), или **сообщить** (crash reporting, 10.6). Пустой `catch` допустим только с комментарием, объясняющим, почему ошибка здесь действительно неинтересна.

## RN relevance

### Красный экран в dev, краш без контекста в release

Это ключевой сюжет урока. Необработанная ошибка в асинхронном коде ведёт себя в двух сборках по-разному — и по-разному в зависимости от того, **брошено ли исключение или отклонён промис**:

| Что произошло | dev (Metro, LogBox) | release |
|---|---|---|
| исключение в колбэке (таймер, событие, нативный колбэк) | красный экран с сообщением и стеком | приложение закрывается без диалога; глобальный обработчик успевает передать краш в Sentry / Crashlytics, если они подключены |
| отказ промиса без `catch` | предупреждение в LogBox, приложение работает | **ничего**: приложение работает, экран не наполняется данными, отчётов нет |

Опасная часть здесь — не краш, а **привычка**. В dev обе строки заметны: красный экран и предупреждение всегда с текстом. В release первая строка превращается в краш, который хотя бы виден в отчётах, а вторая — в полную тишину: LogBox выключен, отслеживание отказов промисов RN включает только в dev, и об отказе знает лишь то, что код сам отправил в Sentry или Crashlytics (или SDK, который умеет отслеживать отказы промисов сам). Отказ промиса, который никто не обработал и не сообщил, в продакшене не существует как событие: есть только жалоба «не загружается профиль» и ноль записей в отчётах.

Отсюда практический вывод для RN: обработка ошибок в асинхронных границах — не защита от красного экрана, а **единственный способ узнать о проблеме в продакшене**. Как настраивается глобальный перехват и почему стектрейс из release-сборки нечитаем без symbolication — 10.6; как отличить JS-краш от нативного по отчёту — 10.7.

### Типичные асинхронные границы в RN-экране

Места, где ошибка гарантированно уходит мимо внешнего `try/catch`:

- **`useEffect` с асинхронной работой.** `useEffect(() => { load(); }, [])` — вызов `async`-функции без `await`; её отказ становится unhandledRejection, экран остаётся в состоянии загрузки;
- **обработчик нажатия.** `onPress={handleSubmit}` с `async handleSubmit` — промис возвращается в React, который его не обрабатывает; отказ теряется;
- **колбэк нативного модуля.** Ошибка, брошенная в колбэке, который вызвал нативный код, летит с чужого стека (контракт нативного модуля — блок 09);
- **таймеры и анимации.** Колбэк `setTimeout`, `setInterval`, обработчик завершения анимации;
- **подписки на события.** Листенер эмиттера вызывается рантаймом, а не вашим кодом.

Общий признак: функция передана куда-то, чтобы быть вызванной позже. Как только это произошло, внешний `try/catch` к ней не относится.

### `Error Boundary` ловит не всё

**Error Boundary** — React-компонент, перехватывающий ошибки, выброшенные дочерним деревом в те моменты, когда React сам выполняет ваш код: при рендере, в методах жизненного цикла и в синхронном теле эффектов (`useEffect`, `useLayoutEffect`). Ошибка из колбэка нажатия, из асинхронной работы, **запущенной** эффектом (продолжение после `await`, колбэк таймера), или из отказавшего промиса мимо него проходит: этот код вызывает не React, а рантайм — то же самое ограничение стека, что у `try/catch`. Подробно — 3.16.

Практическое следствие: Error Boundary не отменяет необходимость обрабатывать ошибки в асинхронном коде. Это два разных уровня защиты, покрывающие разные множества ошибок.

### Разбор входных данных с сервера

Самый частый источник ошибок на экране RN — не падение сети, а данные, которые пришли, но не той формы. Запрос успешен, `response.ok === true`, а поле, которое экран считает обязательным, отсутствует, и падение случается при рендере, в другом компоненте и с сообщением про `undefined`.

Правило для P1: разбор входных данных — это место, где ошибка должна возникать **явно и рано**, с типом и контекстом:

```js
function parseProfile(raw) {
  if (typeof raw !== 'object' || raw === null) {
    throw new ValidationError('profile', 'ожидался объект профиля');
  }
  if (typeof raw.id !== 'string') {
    throw new ValidationError('profile.id', 'id профиля отсутствует или не строка');
  }
  return { id: raw.id, name: raw.name ?? null };
}
```

Такая ошибка возникает в точке разбора, несёт имя поля и стек, и до рендера не доходит. Альтернатива — вернуть частично собранный объект — переносит падение в UI и лишает отчёт информации о том, что именно пришло не так. Классификация сетевых ошибок и решение о том, какие из них можно повторять, — 7.3.

## Типичные заблуждения

**«`try/catch` вокруг вызова поймает всё, что внутри.»** Возникает из визуальной модели: `try { ... }` выглядит как ограда вокруг участка кода, и кажется, что всё, что оттуда стартовало, остаётся «внутри». Но `try` — свойство кадра стека, а не географии кода. Асинхронный колбэк текстуально внутри, а по стеку — снаружи, потому что вызывается позже и с другого стека (1.15, 1.20). Проверка одной строкой: `try { setTimeout(() => { throw new Error('x'); }, 0); } catch (e) { console.log('поймал'); }` — слова «поймал» не будет.

**«Необработанный rejected-промис безвреден.»** Возникает потому, что приложение после него **действительно продолжает работать**: нет красного экрана, нет закрытия, в dev — только предупреждение в консоли. Вывод «значит, ничего не случилось» ошибочен: случилось то, что операция не выполнилась, а состояние экрана об этом не узнало. Спиннер остаётся навсегда, список пустой, кнопка «Сохранить» заблокирована. Для пользователя это полный отказ фичи, для отчётов — тишина. Безвредность путают с отсутствием видимого сигнала.

**«Строка в `throw` эквивалентна `Error`.»** Возникает из того, что в консоли dev-сборки `throw 'profile not found'` выглядит даже чище: короткая строка вместо многострочного стека. Эквивалентности нет: строка не несёт `stack`, то есть в отчёте из продакшена не останется места возникновения — главной информации для разбора (и symbolication в 10.6 нечего будет восстанавливать); не несёт `name`, поэтому одинаковые ошибки не сгруппируются; и не проходит `instanceof Error`, поэтому общий обработчик обойдёт её, читая `err.message === undefined`. Заблуждение держится до первого расследования краша по отчёту, в котором нет стека.
