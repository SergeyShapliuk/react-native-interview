# 1.21 Microtasks и macrotasks — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок 1.20 дал модель «задача выполняется до конца». Этот урок уточняет её в одном месте — **между задачами цикл опустошает отдельную очередь, и опустошает её полностью.** Из этого одного правила выводится весь наблюдаемый порядок выполнения.

---

## 1. Что это

В цикле обработки не одна очередь, а две — с разными правилами обслуживания.

| | Task queue (macrotask) | Microtask queue |
|---|---|---|
| что в неё попадает | колбэки таймеров, события, сообщения извне, работа от нативной стороны | обработчики промисов (`then` / `catch` / `finally`), продолжения после `await`, `queueMicrotask` |
| сколько берётся за раз | **одна** | **все, до полного опустошения** |
| когда обслуживается | в каждом обороте цикла | после каждой задачи, до того как будет взята следующая |
| можно ли добавить во время обслуживания | да, попадёт в следующий оборот | да, и будет выполнено **в этом же** опустошении |

**Macrotask (задача)** — то, что в 1.20 называлось task: единица работы, которую цикл берёт из очереди целиком.

**Microtask** — работа, которая обязана завершиться до того, как цикл возьмёт следующую задачу.

Главное правило, из которого следует всё остальное:

> **Очередь микротасков опустошается полностью — включая микротаски, добавленные во время опустошения.**

Последняя часть — не деталь, а суть. Именно она отличает микротаск от «задачи с высоким приоритетом» и делает возможным как корректную работу промисных цепочек, так и голодание очереди задач.

### Чем микротаск не является

- **Не более быстрой задачей.** Микротаск не выполняется быстрее — он выполняется **раньше**, и это разные утверждения. Его код может занимать сколько угодно времени.
- **Не передышкой для движка.** Это самое вредное заблуждение урока: запланировать микротаск — значит не дать движку сделать ничего другого до его выполнения.
- **Не вопросом приоритета.** Внутри каждой очереди порядок строго FIFO: кто встал раньше, выполнится раньше. Приоритетов внутри очереди нет.

## 2. Как это работает

### Один оборот цикла, уточнённый

```
1. взять ОДНУ задачу из task queue
2. выполнить её до конца (run-to-completion, 1.20)
3. опустошить microtask queue ПОЛНОСТЬЮ:
      пока очередь не пуста:
          взять микротаск, выполнить
          (микротаски, добавленные здесь, попадают в эту же очередь
           и будут выполнены в этом же шаге 3)
4. вернуться к шагу 1
```

Синхронный код верхнего уровня (или внутри одной задачи) — это шаг 2. Поэтому любой `console.log` без обёрток выполняется раньше любого микротаска: он часть текущей задачи, а микротаски обслуживаются после её завершения.

### Канонический пример

```js
console.log("1");                              // синхронно
setTimeout(() => console.log("2"), 0);         // macrotask
Promise.resolve().then(() => console.log("3")); // microtask
queueMicrotask(() => console.log("4"));         // microtask
console.log("5");                              // синхронно

// 1, 5, 3, 4, 2
```

Разбор по шагам:

1. текущая задача — весь этот код. Выполняется до конца: выводит `1`, планирует таймер, планирует два микротаска, выводит `5`;
2. задача завершилась → опустошение очереди микротасков: `3`, затем `4` (порядок постановки, FIFO);
3. очередь микротасков пуста → цикл берёт следующую задачу: таймер выводит `2`.

`Promise.resolve().then(fn)` и `queueMicrotask(fn)` попадают в одну и ту же очередь и соревнуются только порядком постановки — никакого приоритета у одного над другим нет.

### Цепочка промисов — это несколько микротасков

Каждое звено цепочки планирует **отдельный** микротаск:

```js
Promise.resolve()
  .then(() => console.log("A"))
  .then(() => console.log("B"));

Promise.resolve()
  .then(() => console.log("C"))
  .then(() => console.log("D"));

// A, C, B, D
```

Почему не `A, B, C, D`: обработчик `A` планируется сразу, `B` — только когда выполнится `A`. То есть первое опустошение содержит `A` и `C`; в процессе их выполнения добавляются `B` и `D`, которые выполняются в том же опустошении, но после. Две цепочки «переплетаются».

Это и есть практическое следствие правила «включая добавленные во время опустошения»: порядок внутри опустошения определяется не цепочками, а тем, в какой момент каждый обработчик встал в очередь.

### `await` — это микротаск

Продолжение после `await` планируется как микротаск (1.19):

```js
async function f() {
  console.log("1");
  await null;            // даже без промиса: значение оборачивается
  console.log("2");      // микротаск
}

f();
console.log("3");
// 1, 3, 2
```

`await null` не «пропускается», потому что ждать нечего: значение оборачивается в завершённый промис, и продолжение всё равно планируется как микротаск. Отсюда приём «отдать управление на один микротаск» — `await null` или `await Promise.resolve()`. Он даёт ровно то, что даёт микротаск: текущая задача завершится, продолжение выполнится до следующей задачи. Для «пропустить кадр» он не годится (угол 5).

Из этого же следует, что `return await p` вместо `return p` добавляет один лишний шаг в очереди микротасков. На практике это пренебрежимо, и аргументы за `return await` — другие (1.19).

### Голодание очереди задач

Микротаск, планирующий микротаск, создаёт очередь, которая никогда не опустошается:

```js
function loop() {
  queueMicrotask(loop);
}
loop();
```

Шаг 3 цикла не завершится никогда. Это не «медленно» — это полная остановка: ни один таймер не сработает, ни одно событие не обработается, приложение не отвечает навсегда. **Starvation (голодание)** — ситуация, когда очередь задач не получает управления, потому что очередь микротасков не пустеет.

Разница с бесконечным синхронным циклом (`while(true)`) только в форме: по последствиям то же самое, но диагностировать сложнее — стек вызовов при этом короткий и каждый отдельный микротаск мгновенный, поэтому «подозрительной длинной функции» в профиле не видно.

Аналог с `setTimeout(loop, 0)` ведёт себя совершенно иначе: каждая итерация — отдельная **задача**, между ними цикл обслуживает всё остальное. Приложение будет работать (хотя и с постоянной нагрузкой). Это самая наглядная демонстрация того, что микротаск и задача — не «быстрее / медленнее», а разные позиции в цикле.

## 3. Почему это важно

Знание очередей отвечает на три вопроса, которые без него выглядят как случайности.

**Почему код «работает», а потом перестаёт.** Если в коде есть зависимость от порядка, которая не выражена явно (а выражена только через количество `then` в цепочке), она соблюдается ровно до момента, когда кто-то добавит одно звено — в вашем коде или в библиотеке, которую вы обновили. Внешне ничего не менялось: номер версии, те же вызовы. Сломался порядок, на который никто не договаривался опираться.

**Почему два обновления состояния дают то один рендер, то два.** Обновления, попавшие в одну задачу, обрабатываются вместе; попавшие в разные — порознь. Это механизм, лежащий под батчингом (устройство — 3.3).

**Почему асинхронный тест падает.** Тест выполняет синхронную часть, проверяет результат — а результат появится в микротаске, то есть после завершения текущей задачи, то есть после проверки (11.3).

### DEEP DIVE: порядок как неявный контракт

```
код содержит зависимость от порядка выполнения
    ↓
порядок обеспечивается количеством шагов в очереди микротасков
    ↓
это количество нигде не записано и ничем не проверяется
    ↓
библиотека добавляет один then внутри своей реализации
    ↓
порядок меняется
    ↓
дефект появляется после обновления версии, без изменений в вашем коде
```

Такой дефект крайне дорог в диагностике: он не локализуется в изменениях (их не было), не воспроизводится в упрощённом примере (там цепочки короче) и выглядит как «баг в библиотеке».

Вывод урока отсюда получается ограничительный, а не разрешительный: порядок внутри очередей надо **знать**, чтобы читать и отлаживать код, и **не использовать** как средство синхронизации. Если шаг B должен произойти после шага A, это выражается зависимостью — `await`, цепочкой, явной передачей значения, — а не тем, что A оказался в очереди раньше.

## 4. Где это в React Native

### Почему два обновления состояния иногда дают один рендер, а иногда два

```jsx
function onPress() {
  setA(1);
  setB(2);            // оба в одной задаче → один рендер
}

async function onSubmit() {
  setLoading(true);
  const data = await api.save();  // граница: дальше другая задача
  setData(data);
  setLoading(false);  // эти два — в другой задаче, чем первый
}
```

В первом случае оба обновления попадают в одну задачу, обрабатываются вместе и дают один рендер. Во втором `setLoading(true)` остаётся в задаче нажатия, а два последних выполняются в продолжении после `await` — то есть минимум два прохода вместо одного.

**Важная оговорка про границы знания.** Группировка обновлений — поведение React, а не языка, и оно менялось между версиями: в старых версиях обновления вне обработчиков событий не группировались вообще, в современных группируются шире. Этот урок даёт только **механизм очередей**, который делает такое поведение возможным и объяснимым. Что именно делает React, при каких условиях и что из этого гарантировано, — **3.3**. Опираться на группировку как на гарантию до прочтения 3.3 не нужно.

### Код, «работающий» за счёт порядка промисов

```js
// в модуле авторизации
let token = null;
auth.refresh().then((t) => { token = t; });     // микротаск

// в модуле запросов, в том же обороте
Promise.resolve().then(() => api.get("/me", token));  // микротаск, встал позже
```

Работает: обработчик, присваивающий `token`, встал в очередь раньше. Но между постановкой и выполнением нет никакой связи, кроме порядка. Достаточно, чтобы `auth.refresh()` внутри получил на одно звено больше (добавили логирование, валидацию ответа, обновили библиотеку HTTP-клиента) — и `token` в запросе окажется `null`.

Симптом при этом будет выглядеть как проблема авторизации на старте: воспроизводится не всегда, зависит от сети, исчезает при добавлении логов (логирование меняет порядок). Это один из самых дорогих классов дефектов в RN-проектах.

### Старт приложения

На старте в очередях одновременно оказываются: инициализация модулей, восстановление состояния из хранилища, проверка токена, запрос конфигурации, первый рендер. Если между ними есть неявные зависимости по порядку, приложение «иногда стартует неправильно» — показывает экран логина авторизованному пользователю, теряет deep link, не применяет сохранённые настройки. Диагностика без модели очередей здесь практически невозможна.

### Тестирование асинхронных хуков

```js
// тест падает
const { result } = renderHook(() => useCourse(1));
expect(result.current.data).toEqual(course);  // ещё null
```

Хук вызвал промис; его обработчик — микротаск, который выполнится после завершения текущей задачи, то есть после `expect`. Тест проверяет состояние, которого ещё нет.

Решения существуют (`await` в тесте, утилиты вида `waitFor`, прокрутка очередей), и все они делают одно: завершают текущую задачу, чтобы очереди успели обслужиться. Какие именно инструменты и почему `waitFor` надёжнее ручной прокрутки — **11.3**. Здесь важно понимать причину: это не «флаки-тест», а точное следствие модели.

### Попытка «пропустить кадр» через промис

```js
setState(heavyData);
await Promise.resolve();    // не даёт ничего
measureLayout();            // по-прежнему до отрисовки
```

Микротаск выполняется до того, как цикл возьмёт следующую задачу, — значит, до любой работы по отрисовке. Движку не дано сделать ничего. Задачи этого рода (дождаться кадра, измерить после отрисовки) решаются другими механизмами, привязанными к отрисовке, и разбираются в блоке 05 (5.2 — бюджет кадра, 5.7 — работа на UI-потоке).

### Длинная цепочка микротасков в JS thread

Очередь микротасков не даёт циклу взять следующую задачу, а задачами в RN приходит **всё**, включая сообщения от нативной стороны и обработку нажатий (1.20). Поэтому серия из тысяч микротасков блокирует JS-поток не хуже синхронного цикла — с тем отличием, что в профиле это выглядит как множество мелких операций, а не как одна длинная функция. Такое бывает при обработке большой коллекции, где на каждый элемент создаётся промис.

## 5. Типичные ошибки

**«`setTimeout(0)` и `Promise.resolve().then` эквивалентны».** Возникает из того, что оба «откладывают на потом», и в простом примере без нагрузки оба выглядят мгновенными. Расхождение принципиальное: микротаск выполнится до следующей задачи, а таймер — как отдельная задача, после всех микротасков и после всего, что стоит в очереди задач впереди. Отсюда неверные предсказания порядка и, что хуже, попытки заменить одно другим «для надёжности».

**«Микротаск даёт движку передышку».** Возникает из слова «микро» и ассоциации «маленький, значит щадящий». Ровно наоборот: микротаск занимает позицию **перед** следующей задачей, то есть не даёт выполниться ничему другому. Если цель — уступить, нужна задача, а не микротаск. Из этой ошибки растёт попытка разбить тяжёлую работу на микротаски: суммарно получается тот же блокирующий отрезок, только теперь невидимый в профиле как единая функция.

**«Порядок внутри одной очереди зависит от приоритета».** Возникает из переноса модели планировщиков ОС и из опыта с приоритизацией в React (3.12), где приоритеты действительно есть — но на другом уровне. Внутри очереди строгий FIFO: кто встал раньше, выполнится раньше. Никакого способа повлиять на это нет.

**Опора на порядок, который не гарантирован.** Самая дорогая ошибка урока. Возникает потому, что порядок **воспроизводим**: код работает стабильно, тесты проходят, и ничто не указывает на хрупкость. Ломается при добавлении одного звена в чужой цепочке. Признак такого кода: присваивание в одном обработчике и чтение в другом, без передачи значения между ними.

**«Промисы быстрее таймеров».** Возникает из наблюдения, что `then` всегда выполняется раньше `setTimeout(0)`. Верно наблюдение, неверен вывод: дело не в скорости, а в позиции в цикле. Код внутри микротаска может работать сколь угодно долго, и пока он работает, не выполняется ничто другое.

**Попытка «пропустить кадр» через промис.** Возникает из верной мысли «нужно дать системе что-то сделать» и неверного выбора средства. Микротаск — единственное, что гарантированно **не** даёт системе ничего сделать.

**Вывод «надо знать порядок, чтобы им управлять».** Обратное истине и потому стоит отдельно: порядок надо знать, чтобы читать и отлаживать код. Управлять надо зависимостями (`await`, цепочка, явная передача значения), а не позициями в очереди.

## 6. Trade-offs

### Микротаск быстрее, но не даёт движку выполнить другую работу

Это главный trade-off урока и единственное, что нужно из него унести, если забудется всё остальное.

| | Микротаск | Задача (macrotask) |
|---|---|---|
| задержка до выполнения | минимальная: до следующей задачи | зависит от очереди и таймера |
| что успевает движок между планированием и выполнением | **ничего** | всё, что стоит в очереди впереди |
| подходит для | завершить начатое: обработать результат, продолжить после `await` | уступить управление: разбить работу, дать обработать события |
| риск при злоупотреблении | starvation очереди задач | ненужная задержка, дробление логики |

Формулировка для выбора: **микротаск — чтобы завершить, задача — чтобы уступить.** Если нужен быстрый отклик на уже полученный результат — микротаск (и промисы это делают сами). Если нужно дать обработаться нажатиям и обновлениям — только задача.

### Знание порядка против опоры на порядок

| | Знать | Опираться |
|---|---|---|
| зачем | читать код, отлаживать, объяснять поведение | синхронизировать шаги |
| надёжность | знание не ломается | ломается при добавлении звена где угодно по цепочке |
| видимость проблемы | — | нулевая: нет ни теста, ни линтера, ни комментария |
| альтернатива | — | явная зависимость: `await`, цепочка, передача значения |

Опора на порядок бесплатна в момент написания (кода не требуется вообще) и очень дорога в момент поломки. Явная зависимость стоит одной строки.

### Дробление работы: микротаски против задач

Разбить тяжёлую обработку на микротаски технически возможно, и это выглядит дешевле, чем через таймеры (меньше накладных расходов). Но это **не решает** задачу, для которой разбивка делается: интерфейс не станет отзывчивым, потому что между микротасками цикл не берёт задачи. Выигрыш по накладным расходам при нулевом выигрыше по отзывчивости — то есть чистая потеря, плюс труднодиагностируемый профиль.

Если цель разбивки — отзывчивость (а других целей у неё обычно нет), границы частей обязаны быть **задачами** (1.20).

## 7. Связи с другими частями системы

**Назад — цепочка асинхронности блока, которую этот урок завершает:**

- **[1.18 Promises](../18-promises/)** — что планируется: промис как объект состояния, чьи обработчики попадают в очередь микротасков. Здесь становится понятно, почему обработчик `then` не вызывается синхронно и когда именно он вызывается;
- **[1.19 async/await](../19-async-await/)** — чем это планируется из кода: продолжение после `await` — микротаск. Отсюда и точный порядок в смешанном коде, и граница между задачами внутри одной `async`-функции;
- **[1.20 Event loop](../20-event-loop/)** — модель, которую этот урок уточняет. Там: задача выполняется до конца. Здесь: между задачами есть шаг, который опустошает отдельную очередь полностью. Вместе это полная модель порядка выполнения в JS;
- **1.15 Execution context** — каждая задача и каждый микротаск начинаются с пустого стека, и этим объясняется, почему стектрейс асинхронной ошибки не содержит исходного вызывающего;
- **1.11 Error handling** — исключение в микротаске не попадает в `try/catch`, оставшийся в предыдущей задаче.

**Вперёд:**

- **3.3 Путь обновления: setState → batching → scheduling** — главное продолжение урока. Здесь механизм очередей, там — что на нём строит React: когда обновления группируются, что гарантировано, а что является деталью реализации;
- **3.12 Suspense и concurrent features** — приоритизация работы рендера. Важно не спутать уровни: приоритеты там существуют внутри работы React, а внутри очередей языка их нет;
- **4.5 Hermes** — очереди обслуживает конкретный движок, и пауза сборки мусора — ещё один фактор, которого в модели очередей нет;
- **5.2 Бюджет кадра** — переход от порядка к времени: сколько миллисекунд есть, чтобы кадр успел, и почему серия микротасков расходует этот бюджет так же, как одна длинная функция;
- **5.7 Reanimated и Gesture Handler** — работа, привязанная к отрисовке, вместо попыток «пропустить кадр» через промис;
- **5.10 Профилирование** — как выглядит в профиле серия микротасков и почему её сложнее заметить, чем одну длинную задачу;
- **11.3 Тестирование хуков и асинхронного кода** — прямое применение урока: тест падает, потому что проверка стоит в той же задаче, что и вызов, а результат появится в микротаске;
- **12.8 Performance investigation в инциденте** — полная модель исполнения как инструмент диагностики под давлением времени.

**Главное, что должно остаться после урока.** Очередь микротасков опустошается полностью между задачами — это одно правило объясняет и порядок вывода в любом смешанном коде, и батчинг обновлений, и падающий асинхронный тест, и невозможность «пропустить кадр» через промис. И следствие, которое важнее самого правила: порядок надо знать, чтобы отлаживать, и не использовать, чтобы синхронизировать.
