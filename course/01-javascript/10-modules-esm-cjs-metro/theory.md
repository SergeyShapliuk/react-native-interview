# 1.10 Modules: ESM, CJS и как это видит Metro — theory

> 🟢 REFRESH. Синтаксис `import` / `export` вы пишете каждый день. Урок не про синтаксис, а про то, что происходит между моментом, когда вы написали строку импорта, и моментом, когда в бандле появился файл. Три самых дорогих класса дефектов блока — `undefined` вместо импорта, незамеченный рост бандла и «на iOS работает, на Android падает» — начинаются именно здесь.

## Refresh

### Два формата модулей, которые живут в одном проекте

**ESM (ECMAScript Modules)** — стандартный формат языка: `import` / `export`. **CommonJS (CJS)** — формат, пришедший из Node.js: `require()` / `module.exports`. В реальном RN-проекте оба присутствуют одновременно: ваш код и большинство современных библиотек — ESM, но значительная часть `node_modules`, конфиги (`metro.config.js`, `babel.config.js`) и часть RN-инфраструктуры — CJS.

| Свойство | ESM | CommonJS |
|---|---|---|
| Синтаксис | `import` / `export` | `require()` / `module.exports` |
| Где разрешено объявление | только верхний уровень | где угодно, в том числе внутри функции |
| Когда известен список зависимостей | до выполнения, статически | в момент выполнения строки `require` |
| Что получает импортирующий | живую связь с экспортом | значение `module.exports` на момент вызова |
| Разрешение циклов | частично инициализированный модуль | частично заполненный `module.exports` |

Главное различие практически значимо только в одном: **ESM анализируется статически**. Сборщик может прочитать файл и узнать весь список его зависимостей, не выполняя код. `require('./' + name)` такой возможности не даёт — строка известна только в рантайме.

### Named и default экспорт

```js
// named
export function formatDuration(ms) { /* ... */ }
export const DEFAULT_TIMEOUT = 5000;

// default — ровно один на модуль
export default function LessonScreen() { /* ... */ }
```

Named-экспорт фиксирует имя: `import { formatDuration } from './format'`. Опечатка в имени — ошибка на этапе сборки или проверки типов. Default-экспорт имени не несёт: `import whatever from './format'` корректно синтаксически при любом имени, и переименование default-экспорта в источнике никак не отражается в местах импорта. Для кода, который рефакторят, это ощутимая разница в том, насколько громко ломается сборка.

### Статический импорт и динамический `require`

```js
import { heavyParser } from './heavy-parser';          // статически, всегда в графе

function onRareAction() {
  const { heavyParser } = require('./heavy-parser');   // в рантайме
}
```

Оба варианта в RN-бандле приведут к тому, что модуль окажется включён: Metro видит литеральную строку в `require` и добавит её в граф. Разница в том, **когда выполнится код модуля**: при статическом импорте — при загрузке бандла, при `require` внутри функции — при первом вызове этой функции. Это инструмент не уменьшения бандла, а сдвига стоимости инициализации (подробнее в 5.6).

А вот `require(somethingComputed)` — другое дело: такую зависимость сборщик вывести не может, в граф она не попадёт, и в рантайме будет ошибка разрешения модуля.

### Модуль — singleton

Код верхнего уровня модуля выполняется **один раз** за время жизни приложения, при первом его импорте. Все последующие импорты получают уже готовый результат из кэша модулей.

```js
// analytics.js
console.log('analytics init');          // выполнится ровно один раз
let eventQueue = [];                    // одна очередь на всё приложение
export function track(e) { eventQueue.push(e); }
```

Три разных экрана, импортирующих `analytics`, видят **одну и ту же** `eventQueue`. Это полезное свойство, когда вы его используете осознанно (клиент API, конфиг, кэш), и источник утечек, когда нет: модульная переменная не очищается при размонтировании экрана и живёт до перезапуска приложения. Что именно она удерживает в памяти — тема 1.22.

Отсюда же правило «никаких side effect на верхнем уровне». Строка `const client = createSocketConnection()` на верхнем уровне модуля выполнится в момент, когда модуль впервые попал в граф исполнения — возможно, на старте приложения, задолго до экрана, которому соединение нужно.

### Циклические зависимости

**Цикл** — ситуация, когда модуль A импортирует B, B импортирует C, а C импортирует A (цикл любой длины, включая прямой A ↔ B).

```js
// user.js
import { formatRole } from './role';
export const ROLES = ['admin', 'student'];
export function describeUser(u) { return formatRole(u.role); }

// role.js
import { ROLES } from './user';
export function formatRole(r) { return ROLES.includes(r) ? r : 'unknown'; }
```

Сборка проходит. Выполнение зависит от того, кто из двух модулей начал исполняться первым. Если первым выполняется `role.js`, то в момент его выполнения `user.js` ещё не дошёл до строки `export const ROLES`, и `ROLES` будет `undefined`. Ошибки в этот момент не возникает — она возникнет позже, при первом вызове `formatRole`, в виде `Cannot read property 'includes' of undefined`, то есть в файле, который к настоящей причине отношения не имеет.

Это главный факт про циклы в RN: **цикл не ломает сборку, он подменяет значение на `undefined` и переносит падение в другое место**.

### Barrel-файлы

**Barrel-файл** — `index.ts`, который реэкспортирует содержимое папки, чтобы снаружи импортировать одной строкой.

```ts
// features/lessons/index.ts
export * from './LessonScreen';
export * from './LessonList';
export * from './useLessonProgress';
export * from './lessonAnalytics';
```

```ts
import { formatLessonTitle } from '@app/features/lessons';   // нужна одна функция
```

Импортирующий получил одну функцию. Граф получил всё: `LessonScreen` с его компонентами, `lessonAnalytics` с его клиентом аналитики, и транзитивно всё, что импортируют они. Barrel-файл — не просто удобство записи, это решение о том, что входит в граф.

## Как файл становится частью бандла

```
resolver  →  module resolution  →  transformation  →  dependency graph  →  bundling
```

Цепочка выполняется Metro — сборщиком React Native. Каждый этап отвечает на свой вопрос, и дефекты каждого этапа выглядят по-своему.

### resolver

**Resolver** — компонент, который превращает строку из вашего импорта в путь к конкретному файлу на диске. Строка `'@app/features/lessons'` или `'react-native'` сама по себе не файл; resolver отвечает на вопрос «какой файл имеется в виду».

Это не поиск по имени. Resolver применяет набор правил: является ли строка относительным путём, зарегистрированным алиасом, или именем пакета; что об этом говорит конфигурация. Отсюда класс проблем «импорт работает в редакторе, но падает в сборке»: TypeScript разрешил путь по `tsconfig.json`, а Metro про этот алиас не знает. Синхронизация алиасов между TS, Babel, Jest и Metro — отдельный урок 8.6, потому что это четыре независимых набора правил, которые должны совпадать.

### module resolution

Когда resolver определил, что речь о пакете или о каталоге, вступают правила поиска конкретного файла:

- **`package.json` пакета** и его поля входных точек, включая поле **`exports`**. `exports` описывает карту того, что пакет вообще разрешает импортировать, и условия выбора файла (`import`, `require`, `react-native`, `default`). Пакет с `exports` может физически содержать файл, но не отдавать его: глубокий импорт `'some-lib/internal/util'` будет отклонён, даже если файл на месте;
- **platform extensions** — платформенные расширения. Metro при импорте `'./storage'` проверяет `storage.ios.ts`, `storage.android.ts`, `storage.native.ts`, `storage.ts` в порядке приоритета для текущей платформы. Расширение `.native` выбирается на обеих мобильных платформах, но не в web-сборке;
- **порядок расширений** — при импорте без расширения выбирается первый подошедший вариант из настроенного списка (`.tsx`, `.ts`, `.js`, …);
- **`node_modules` по цепочке вверх** — имя пакета ищется в ближайшем `node_modules`, затем в родительском каталоге, и так до корня. В монорепозитории это означает, что один и тот же импорт из двух разных пакетов может разрешиться в две разные копии библиотеки.

Практический вывод этого этапа: **какой именно файл попадёт в бандл, решается здесь, а не в вашем коде**. Строка импорта одинакова для iOS и Android, файл — разный.

### transformation

Каждый найденный файл проходит преобразование: Babel применяет пресеты и плагины (синтаксис, JSX, трансформации), в release-сборке добавляется минификация. Важное свойство: это работа **на каждый файл графа**, а не на бандл в целом. Результаты кэшируются, но первая сборка, сборка после изменения конфигурации Babel и сборка в CI с холодным кэшем платят полную стоимость.

Отсюда следует, что число файлов в графе — величина, которая напрямую конвертируется во время сборки, а не только в размер результата.

### dependency graph

**Dependency graph** — граф модулей, который Metro строит от точки входа (обычно `index.js`), идя по статическим импортам: для каждого модуля разрешаются его зависимости, для них — их зависимости, и так в глубину. Получается не список файлов проекта, а множество файлов, **достижимых из точки входа**.

Файл, который лежит в проекте, но никем не импортируется, в графе отсутствует — его как будто нет. И наоборот: один `export *` на границе фичи может добавить в граф десятки файлов, которых в коде экрана никто не упоминал.

Динамический `require` с вычисляемой строкой в граф этим способом не попадает — разрешать нечего до выполнения.

### bundling

В бандл попадает то, что есть в графе. Модули получают идентификаторы, оборачиваются в фабрики регистрации и складываются в один файл с реализацией `require` в рантайме.

Ключевое: шага «а теперь выбросим то, что не используется» здесь нет. Metro не выполняет tree shaking в том смысле, в каком его делает Webpack с ESM: он не анализирует, какие именно из импортированных имён реально задействованы, чтобы удалить остальные. Включён модуль — включён целиком.

## RN relevance

Metro включает в бандл всё, до чего дотянулся импорт, и не делает tree shaking так, как это делает Webpack. Три практических следствия.

### 1. Barrel-файл втягивает в граф весь модуль

```ts
import { formatLessonTitle } from '@app/features/lessons';    // через barrel
import { formatLessonTitle } from '@app/features/lessons/format';  // напрямую
```

Первая строка добавляет в граф `features/lessons/index.ts`, а через него — все реэкспортированные модули и всё, что импортируют они. Если среди них есть экран, тянущий навигацию, библиотеку графиков и клиент аналитики, всё это оказывается в бандле ради одной функции форматирования.

Платится дважды: размером бандла (а значит, временем парсинга и TTI — 5.6) и объёмом работы Metro на этапах resolution и transformation.

Из этого не следует «barrel-файлы запрещены». Из этого следует, что barrel на **границе фичи** — архитектурное решение с ценой, а barrel внутри небольшого модуля с однородным содержимым обычно безвреден. Политика по границам модулей — 8.2.

### 2. Циклы проявляются как `undefined` в рантайме, а не как ошибка сборки

Сборка зелёная, линтер молчит (если правило `import/no-cycle` не включено), тесты на изолированном модуле проходят. Приложение падает на устройстве с сообщением вида `undefined is not a function` в файле, который цикл не образует — он всего лишь первым вызвал функцию, получившую `undefined`.

Диагностический признак: падение зависит от порядка импортов и от того, какой экран открыли первым. «Воспроизводится только при холодном старте с deep link» — типичная формулировка такого багрепорта. Исправление почти всегда означает извлечение общей части (типы, константы) в третий модуль, а не перестановку строк импорта.

### 3. Платформенные расширения и `exports` определяют, какой файл в бандле

```
src/services/
  storage.ts          общая реализация
  storage.ios.ts      версия для iOS
```

Импорт `'./storage'` из любого места даёт на iOS `storage.ios.ts`, на Android — `storage.ts`. Разработчик, который добавил поле в `storage.ios.ts` и проверил на симуляторе, на Android получит отсутствующий метод. Тот же механизм в обратную сторону: `.native`-файл не подхватится в web-сборке.

Поле `exports` в `package.json` библиотеки добавляет своё: обновление библиотеки, в котором добавили `exports`, может сломать глубокий импорт, работавший годами, без изменений в вашем коде. «Работает на iOS, падает на Android» и «сломалось после обновления пакета без изменений кода» часто начинаются на этапе module resolution, а не в прикладной логике.

### Production-кейс: почему большой `node_modules` не означает большой бандл, но тормозит Metro

Ситуация, которая регулярно порождает неверные решения: в проекте `node_modules` на несколько гигабайт, сборка идёт долго, hot reload ощутимо задумывается. Напрашивается вывод «надо выкинуть зависимости, бандл распух». Вывод частично неверен, и важно понимать, в какой именно части.

**Что на размер бандла не влияет.** В бандл попадает только достижимое по графу от точки входа. Пакет, установленный в `node_modules` и никем не импортированный, в графе отсутствует и в бандл не входит. Его удаление уменьшит `node_modules` на диске и не изменит размер бандла ни на байт. Поэтому «размер `node_modules`» и «размер JS-бандла» — величины, между которыми нет прямой зависимости: `node_modules` содержит исходники всех платформ, типы, тесты, документацию, dev-зависимости и дублирующиеся транзитивные копии, а в бандл идут только достижимые модули после преобразования.

**Что на время работы Metro влияет.** Resolver и transformation работают с файлами, которые **встретились на пути**. Время сборки определяется не каталогом на диске, а графом:

| Фактор | На что влияет |
|---|---|
| Число достижимых пакетов | количество разрешений имён и чтений `package.json` |
| Глубина дерева зависимостей | длина цепочек resolution, число транзитивных входов в граф |
| Число файлов внутри достижимых модулей | объём работы transformation, размер кэша |
| Barrel-файлы и широкие реэкспорты (`export *`) | расширение графа без соответствующего использования |
| Дублирующиеся копии библиотеки в монорепозитории | один и тот же код проходит цепочку несколько раз |

Эти же факторы определяют время прогрева кэша (первая сборка, CI, сборка после изменения конфигурации Babel) и задержку hot reload: при изменении файла Metro пересобирает затронутую часть графа, и чем шире связи, тем больше затронутая часть. Barrel-файл здесь вредит отдельно: он создаёт зависимость экрана от всех модулей фичи, поэтому изменение любого из них касается всех импортирующих.

**Вывод урока.** Размер `node_modules` сам по себе — не метрика. Значение имеют граф модулей и работа resolver/bundler. Правильные вопросы: какие модули достижимы из точки входа, какой вклад в граф даёт каждая граница фичи, и где широкий реэкспорт добавляет в граф то, что не используется. Как это измеряют инструментами — 4.4 и 5.6; здесь важно, что мерить нужно граф, а не каталог.

## Типичные заблуждения

**«Metro делает tree shaking как Webpack.»** Возникает из переноса опыта web-сборки: в экосистеме бандлеров tree shaking давно считается чем-то, что «есть по умолчанию», а статичность ESM создаёт впечатление, что устранение неиспользуемого следует из формата автоматически. Metro устроен иначе: он оптимизирован под быструю инкрементальную пересборку, а не под минимальный размер артефакта, и исходит из того, что включённый в граф модуль включается целиком. Практическая цена заблуждения — уверенность, что «неиспользуемый импорт ничего не стоит», и отсутствие политики по barrel-файлам.

**«Циклический импорт вызовет ошибку сборки.»** Возникает из опыта языков со статической компиляцией, где циклическая зависимость модулей — ошибка компилятора, и из общего ожидания «серьёзная проблема заметна громко». Модульная система JS циклы допускает: она отдаёт импортирующему то, что есть на момент обращения, а на момент обращения это может быть `undefined`. Заблуждение дорого именно тем, что из зелёной сборки делается вывод «циклов нет», и настоящая причина ищется в месте падения, где её нет.

**«Barrel-файл — это просто удобство без последствий.»** Возникает из того, что последствия не видны в коде: строка импорта стала короче, поведение не изменилось, ревью проходит. Цена проявляется в величинах, которые на ревью не смотрят — размер бандла, время сборки, время hot reload — и проявляется постепенно, по мере роста фичи, поэтому не связывается с решением, принятым полгода назад. Усиливает заблуждение и то, что в проектах с tree shaking цена действительно меньше, а советы переносятся из web-экосистемы без поправки на Metro.

**«Большой `node_modules` = большой бандл.»** Возникает из естественного отождествления «установленных зависимостей» и «кода приложения»: оба растут вместе, и интуиция связывает их напрямую. В `node_modules` лежат исходники всех платформ, типы, тесты, dev-инструменты и транзитивные дубликаты — ничего из этого в бандл не идёт, а в бандл идёт только достижимое по графу после преобразования. Заблуждение приводит к работе не над тем: удаляется неиспользуемый пакет (бандл не меняется) вместо разрыва широкого реэкспорта (меняется и бандл, и время сборки).

**«Resolver просто ищет файл по имени.»** Возникает из того, что в 95 % случаев resolver действительно ведёт себя как ожидается, и его работа незаметна. Но ищет он по правилам: алиасы, `package.json` и поле `exports`, платформенные расширения и `.native`, порядок расширений, подъём по `node_modules`. Пока правила совпадают с ожиданием, их не видно; расходятся они в самых дорогих ситуациях — отличие iOS от Android, обновление библиотеки с `exports`, монорепозиторий с двумя копиями пакета, алиас, который знает TypeScript и не знает Metro. Заблуждение стоит того, что такие дефекты ищут в прикладном коде, где их нет.
