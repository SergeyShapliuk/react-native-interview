# 1.5 Arrays: порядок, идентичность, мутирующие методы — theory

> 🟢 REFRESH. Массив — главная структура данных экрана мобильного приложения, и половина проблем со списками начинается с вопроса, который не задают: этот метод вернул новый массив или тот же?

## Refresh

### Массив — это объект

У массива нет собственного типа: `typeof []` даёт `object`, проверка — `Array.isArray`. Отсюда всё поведение из 1.4 переносится без изменений:

```js
[1, 2] === [1, 2];  // false — разные объекты
const a = [1, 2];
const b = a;
b.push(3);
a.length;           // 3 — один массив, две переменные
```

Индексы — это свойства объекта, приведённые к строкам. Поэтому `arr["0"]` и `arr[0]` обращаются к одному и тому же, и поэтому массиву можно присвоить произвольное свойство (`arr.total = 5`), которое не попадёт ни в `length`, ни в перебор по индексам, ни в `map`.

### Мутирующие методы против возвращающих новый

Главная таблица урока. Делить методы надо не по смыслу, а по тому, что они делают с исходным массивом:

| Мутирует исходный | Возвращает новый |
|---|---|
| `push`, `pop`, `shift`, `unshift` | `concat`, `slice` |
| `splice` | `toSpliced` |
| `sort` | `toSorted` |
| `reverse` | `toReversed` |
| `fill`, `copyWithin` | `map`, `filter`, `flat` |
| присваивание по индексу, `arr[i] = x` | `with` |
| изменение `length` | spread `[...arr]` |

Что здесь важно удержать:

- **`sort` и `reverse` мутируют** — это два самых неожиданных элемента списка, потому что они возвращают массив, и возвращают они **тот же самый**;
- **`slice` и `splice` различаются одной буквой и противоположны**: `slice` берёт часть и ничего не трогает, `splice` вырезает из исходного;
- **методы семейства `toSorted` / `toReversed` / `toSpliced` / `with`** — немутирующие версии, появившиеся в языке позже. В React Native их доступность зависит от версии движка и настройки сборки; перед использованием стоит проверить, что текущая конфигурация Hermes их поддерживает (4.5). Если нет — работает `[...arr].sort()`. Вторая проверка — типы: базовый `@react-native/typescript-config` 0.87.1 не включает в `lib` раздел `es2023.array`, и `tsc` сообщит, что свойства `toSorted` у массива нет, пока `lib` не расширен явно (2.15).

### `sort` возвращает тот же массив

```js
const items = [3, 1, 2];
const sorted = items.sort();

sorted === items;  // true — это один массив
items;             // [1, 2, 3] — исходный изменён
```

Два факта одновременно: массив отсортирован **на месте**, и возвращена **та же ссылка**. Это делает `sort` самым коварным методом в контексте React: результат выглядит как новое значение, но идентичность не изменилась.

Отдельно: `sort` без компаратора приводит элементы к строкам. Поэтому `[10, 9, 1].sort()` даёт `[1, 10, 9]`. Для чисел компаратор обязателен.

### Разреженные массивы

**Разреженный (sparse) массив** — массив с «дырами», то есть индексами, которым не присвоено значение.

```js
const sparse = [1, , 3];     // дыра на индексе 1
sparse.length;               // 3
1 in sparse;                 // false — свойства нет
sparse[1];                   // undefined — но это не значение, а отсутствие

new Array(3);                // [ , , ] — три дыры, не три undefined
new Array(3).fill(null);     // [null, null, null] — так создают заполненный
```

Почему это важно: методы перебора ведут себя по-разному. `map` и `forEach` **пропускают дыры**, сохраняя их в результате; `Object.keys` их не видит; а `for` по индексу и spread обрабатывают как `undefined`.

```js
[1, , 3].map((x) => x * 2);   // [2, , 6] — дыра осталась дырой
[...[1, , 3]];                // [1, undefined, 3] — дыра стала значением
```

Специально разреженные массивы в продуктовом коде не создают. Появляются они случайно: из `new Array(n)` без заполнения, из присваивания по индексу за пределами длины (`arr[10] = x` на массиве из двух элементов), из `delete arr[i]`. Последнее — частая ошибка: `delete` оставляет дыру и не меняет `length`, нужный метод — `splice` или `filter`.

### `length` изменяемо

```js
const arr = [1, 2, 3, 4, 5];
arr.length = 2;   // [1, 2] — элементы удалены
arr.length = 5;   // [1, 2, , , ] — добавлены дыры
```

Присваивание `length = 0` — быстрый способ очистить массив на месте, который иногда встречается в коде. В работе с состоянием это мутация, то есть ровно то, чего мы избегаем.

## RN relevance

### `sort` на массиве из состояния

Самый частый дефект урока:

```jsx
function LessonList({ lessons }) {
  const sorted = lessons.sort((a, b) => a.order - b.order);
  return <FlatList data={sorted} ... />;
}
```

Здесь три проблемы одновременно, и каждая самостоятельна:

1. **мутация пропса.** `lessons` принадлежит не этому компоненту — он пришёл из состояния родителя или из стора. Сортировка изменила исходные данные, и теперь порядок в сторе отличается от того, что туда положили;

2. **идентичность не изменилась.** `sorted === lessons`. Если родитель после этого вызовет обновление состояния тем же массивом, React не увидит изменения (1.4);

3. **сортировка на каждый рендер.** При каждом рендере массив сортируется заново — и, поскольку он уже отсортирован, это чаще всего бесполезная работа. Что с этим делать — мемоизация в 3.11, диагностика в 5.3.

Корректно — не мутировать источник:

```js
const sorted = [...lessons].sort((a, b) => a.order - b.order);
// или, если движок поддерживает:
const sorted = lessons.toSorted((a, b) => a.order - b.order);
```

### «Прыгающие» элементы в длинном списке

Сценарий, который на коротком списке не виден. Порядок на экране «плавает» в двух случаях, и механизмы у них разные:

- **несогласованный компаратор** — например, сортировка `a.order - b.order` по полю, которое у части элементов отсутствует: `undefined - 1` даёт `NaN`, компаратор перестаёт задавать порядок, и спецификация оставляет результат на усмотрение реализации. На практике такой «отсортированный» массив часто остаётся почти в исходном порядке (`[{o:2},{},{o:1},{o:3},{}]` в Node и Hermes не переставился вовсе), а при другом входе или другом движке — переставляется иначе;
- **равные элементы** — компаратор возвращает `0` для разных элементов. Начиная с ES2019, `sort` обязан быть **стабильным**: равные элементы сохраняют порядок входа (это выполняют и V8, и Hermes). Значит, порядок равных элементов определяется входом — и если вход приходит в разном порядке (ответ сервера без гарантии порядка, слияние двух источников), строки с одинаковым ключом сортировки меняются местами от загрузки к загрузке.

В `FlatList` с переиспользованием ячеек это выглядит как элементы, меняющиеся местами при обновлении данных.

Усиливается это `index` в роли ключа: если порядок изменился, ключи «переехали» на другие данные, и React переиспользует состояние ячейки для другого элемента — отсюда введённый текст, оказавшийся в чужой строке. Механизм ключей разбирается в 3.2, здесь важно, что **источник проблемы — нестабильный порядок, а не сам ключ**.

### `push` в состояние

```js
const [items, setItems] = useState([]);

function add(item) {
  items.push(item);   // мутация
  setItems(items);    // та же ссылка — рендера не будет
}
```

Корректно: `setItems([...items, item])` или `setItems((prev) => [...prev, item])`. Вторая форма предпочтительнее, когда обновлений может быть несколько в одном такте — почему именно, разбирается в 3.3.

### Данные для `FlatList` и идентичность

`FlatList` принимает `data` и решает, нужна ли переоценка, в том числе по идентичности этого массива. Из этого следуют два симметричных дефекта:

- **новый массив при неизменных данных** (`lessons.filter(...)` прямо в пропсе) — лишняя работа на каждый рендер (1.6);
- **тот же массив при изменившихся данных** (мутация через `push` или `sort`) — обновление, которого не произошло.

Оба — про идентичность, и ни один не является особенностью `FlatList`.

## Типичные заблуждения

**«`sort` возвращает новый массив.»** Возникает из того, что метод **возвращает** массив: всё, что возвращает значение, интуитивно воспринимается как чистая функция. Плюс сравнение с `map` и `filter`, которые рядом по смыслу и действительно создают новый. Проверка одной строкой: `const a = [2,1]; a.sort() === a` даёт `true`.

**«`push` в состояние сработает, если потом вызвать `setState`.»** Возникает потому, что иногда срабатывает — когда рендер случился по другой причине (1.4). Невоспроизводимость и есть главная опасность.

**«Массив — это не объект.»** Возникает из того, что массив ведёт себя иначе: индексы, `length`, методы перебора. Но все правила идентичности, копирования и сравнения к нему применяются без исключений, и забывать об этом — значит потерять половину выводов урока 1.4.

**«`delete arr[i]` удаляет элемент.»** Возникает по аналогии с объектами, где `delete` действительно убирает свойство. В массиве он убирает свойство, но не сдвигает остальные и не меняет `length` — остаётся дыра, и дальше поведение зависит от того, какой метод перебора встретит её первым.

**«`new Array(5)` создаёт массив из пяти `undefined`.»** Возникает из того, что чтение любого элемента даёт `undefined`. Но это отсутствие свойства, а не значение: `map` по такому массиву не вызовет колбэк ни разу, и попытка «заполнить через `map`» молча не сработает.
