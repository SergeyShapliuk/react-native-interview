# 1.5 Arrays: порядок, идентичность, мутирующие методы — practice

## Проверка понимания

---

**1. Какие из `push` / `concat` / `splice` / `slice` / `sort` мутируют исходный массив?**

<details>
<summary>Ответ</summary>

Мутируют: `push`, `splice`, `sort`. Не мутируют: `concat`, `slice`.

**Ответ, в котором `sort` отнесён к немутирующим,** вскрывает главный пробел урока. Цена ошибки: мутация пропса или данных из стора, которую никто не замечает, потому что сортировка «выглядит как вычисление».

**Ответ, в котором `splice` и `slice` перепутаны,** вскрывает опору на похожесть имён. Эти два метода противоположны по действию, и различать их надо не по памяти, а по смыслу: `slice` — «взять срез», `splice` — «вырезать из».
</details>

---

**2. Почему `setItems(items.sort())` может не обновить экран?**

<details>
<summary>Ответ</summary>

Потому что `items.sort()` возвращает **тот же** массив, что и `items`. React сравнит предыдущее состояние с новым по идентичности, получит «то же самое» и не запланирует рендер. При этом массив действительно отсортирован — то есть данные изменились, а экран нет.

**Ответ «обновит, ведь массив изменился»** вскрывает подмену вопроса: React спрашивает «другой ли это объект», а не «изменилось ли содержимое» (1.4).

**Ответ «не обновит, потому что sort асинхронный»** вскрывает выдуманный механизм. `sort` полностью синхронен; дело исключительно в возвращаемой ссылке.
</details>

---

**3. Что вернёт `sort` — новый массив или тот же?**

<details>
<summary>Ответ</summary>

Тот же. `const a = [2, 1]; a.sort() === a` даёт `true`.

**Любой другой ответ** вскрывает тот же пробел, что и в вопросе 1, но вопрос задан отдельно сознательно: знать, что `sort` мутирует, и знать, что он возвращает ту же ссылку, — два разных факта. Первый предупреждает о порче данных, второй объясняет отсутствие ре-рендера. Разработчик, знающий только первый, исправит мутацию копией и не поймёт, почему до исправления экран иногда обновлялся.
</details>

## Задание

**Дано.** Модуль, готовящий данные для списка уроков на экране RN-приложения. Все пять функций работают с данными, которые приходят из стора и принадлежат не этому модулю.

```js
export function sortByOrder(lessons) {
  return lessons.sort((a, b) => a.order - b.order);
}

export function addLesson(lessons, lesson) {
  lessons.push(lesson);
  return lessons;
}

export function removeLesson(lessons, index) {
  delete lessons[index];
  return lessons;
}

export function takeFirstThree(lessons) {
  return lessons.splice(0, 3);
}

export function markAllSeen(lessons) {
  lessons.forEach((lesson) => {
    lesson.seen = true;
  });
  return lessons;
}
```

**Требуется.**

1. Для каждой функции указать: мутирует ли она вход, и какую ссылку возвращает — новую или прежнюю.
2. Переписать все пять функций так, чтобы исходные данные не менялись. Для каждой назвать метод, который вы выбрали, и почему именно он.
3. Для `removeLesson` объяснить, что именно не так с `delete`, помимо мутации, и что увидит `FlatList`.
4. Для `takeFirstThree` объяснить, почему дефект здесь **двойной** и почему его труднее всего заметить по коду.
5. `markAllSeen` после исправления обязана сохранить идентичность тех элементов, которые уже имели `seen: true`. Объяснить, зачем это нужно и что произойдёт в длинном списке, если этого не сделать.

---

<details>
<summary>Разбор</summary>

**1. Что делает каждая функция.**

| Функция | Мутирует вход | Возвращает |
|---|---|---|
| `sortByOrder` | да, сортирует на месте | **прежнюю** ссылку |
| `addLesson` | да, `push` | **прежнюю** ссылку |
| `removeLesson` | да, оставляет дыру | **прежнюю** ссылку |
| `takeFirstThree` | да, вырезает из исходного | новую (но исходный испорчен) |
| `markAllSeen` | да, мутирует **элементы**, не массив | прежнюю ссылку массива и прежние ссылки элементов |

Общая картина: ни одна функция не пригодна для работы с состоянием, и четыре из пяти возвращают ту же ссылку — то есть обновление экрана после них недетерминировано.

**2. Исправленные функции.**

```js
export function sortByOrder(lessons) {
  return [...lessons].sort((a, b) => a.order - b.order);
}

export function addLesson(lessons, lesson) {
  return [...lessons, lesson];
}

export function removeLesson(lessons, index) {
  return lessons.filter((_, i) => i !== index);
}

export function takeFirstThree(lessons) {
  return lessons.slice(0, 3);
}

export function markAllSeen(lessons) {
  return lessons.map((lesson) =>
    lesson.seen ? lesson : { ...lesson, seen: true }
  );
}
```

Почему выбраны именно эти методы:

- **`[...lessons].sort(...)`** — копия создаётся до сортировки, поэтому мутируется копия. Альтернатива `lessons.toSorted(...)` короче и выразительнее, но её доступность зависит от версии движка и настройки сборки (4.5), поэтому в коде, который должен работать на любой поддерживаемой конфигурации, spread надёжнее;
- **`[...lessons, lesson]`** вместо `concat` — результат идентичен, spread читается однозначнее и не создаёт вопроса, что произойдёт при передаче массива (`concat` его развернёт, spread — нет);
- **`filter` по индексу** вместо `splice` или `delete` — удаляет элемент и сдвигает остальные, не оставляя дыр;
- **`slice`** вместо `splice` — буквально то же намерение без побочного эффекта;
- **`map` с условием** — см. пункт 5.

**3. Про `delete` в `removeLesson`.**

Помимо мутации, `delete` делает нечто худшее: он убирает свойство, но **не сдвигает остальные элементы и не меняет `length`**. На месте удалённого остаётся дыра (1.5, раздел о разреженных массивах).

Что увидит `FlatList`: его `data` сохранит прежнюю длину, то есть список будет считать, что элементов столько же. Для индекса с дырой `data[index]` даст `undefined`, и дальше исход зависит от кода ячейки — чаще всего падение при обращении к полю (`lesson.title` от `undefined`), иногда пустая ячейка нужной высоты. При этом `length` остался прежним, поэтому и `getItemLayout`, и индикатор прокрутки продолжают считать удалённый элемент существующим.

Отдельно стоит отметить: поскольку ссылка массива не изменилась, обновление может и не дойти до экрана — и тогда дефект проявится позже, при следующем рендере по другой причине.

**4. Почему дефект в `takeFirstThree` двойной.**

Первый: `splice(0, 3)` **вырезает** первые три элемента из исходного массива. После вызова в сторе осталось на три урока меньше.

Второй: функция при этом **возвращает корректный результат** — массив из трёх первых уроков, новый и правильный. Вызывающий код получает ровно то, что просил.

Именно комбинация делает дефект трудным для обнаружения по коду: подпись функции честная, возвращаемое значение верное, имя отражает намерение. Ошибка видна не в этой функции, а в другом месте приложения — где через некоторое время обнаруживается, что список уроков укоротился. Причём если `takeFirstThree` вызывается при каждом рендере превью, список будет убывать по три элемента, то есть симптомом станет «уроки пропадают», а место причины — функция с правильным результатом.

Это хорошая иллюстрация общего правила: **корректность возвращаемого значения ничего не говорит об отсутствии побочного эффекта.**

**5. Почему `markAllSeen` должна сохранять идентичность уже отмеченных.**

```js
lessons.map((lesson) => (lesson.seen ? lesson : { ...lesson, seen: true }))
```

Вариант без условия — `map((lesson) => ({ ...lesson, seen: true }))` — тоже иммутабелен и тоже корректен по данным. Разница в идентичности: он создаёт **новый объект для каждого** элемента, включая те, которые уже имели `seen: true` и не изменились.

Что из этого следует в длинном списке: каждая ячейка получит новую ссылку на свои данные, мемоизированный компонент ячейки сравнит пропсы, увидит «изменилось» и перерисуется. То есть при отметке одного непрочитанного урока перерисуется весь список целиком вместо одной ячейки.

С условием новые ссылки получат **только фактически изменившиеся** элементы, и перерисуются только их ячейки. Это и есть structural sharing на уровне массива: нетронутые элементы сохраняют идентичность, и это единственное, на что может опереться мемоизация (1.13, 3.11).

Цена условия — одна проверка на элемент. Цена отказа от него — перерисовка списка. На списке из 500 уроков разница видна в кадрах при скролле (5.4).

**Важная оговорка.** Это не означает, что подобное условие нужно писать всегда и везде: на списке из десяти элементов оно ничего не меняет и только добавляет кода. Решение зависит от размера списка и от того, мемоизированы ли ячейки. Урок здесь в том, чтобы **видеть** эту разницу и принимать решение осознанно, а не в том, чтобы применять правило механически.
</details>
