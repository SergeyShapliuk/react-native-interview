# 1.24 Синтез — theory

> 🔴 SENIOR. Семь подозрительных фрагментов в одном компоненте: шесть настоящих проблем, ни одна из которых не является ошибкой React, и одна ложная тревога. Урок строит карту «фрагмент → механизм → наблюдатель → блок курса» и сознательно не даёт решений.

---

## 1. Что это

Синтез — не урок новой темы, а **смена масштаба**. Блок 01 разбирал механизмы по одному: ссылки отдельно, замыкания отдельно, очереди отдельно. В реальном коде они появляются вместе, в одном файле, и симптомы у них перепутаны: «экран лагает» может быть следствием любого из четырёх разных механизмов, а «экран не обновился» — двух.

Задача урока — научиться задавать вопрос в правильном порядке:

```
симптом  →  какой механизм языка за ним стоит  →  кто его наблюдает  →  где решается
```

Третий шаг — тот, который чаще всего пропускают. У каждой проблемы есть конкретный **наблюдатель**: React (через сравнение идентичности), сборщик мусора (через достижимость), пользователь (через кадры и экран). Проблема без наблюдателя не является проблемой — и это не формальность, а защита от оптимизации того, что никому не мешает (1.12, угол 3).

### Компонент

Всё дальнейшее разбирает этот код. Он написан так, как пишут в реальных проектах: ничего нарочито плохого, каждое решение по отдельности объяснимо.

```jsx
function CourseScreen({ route, emitter }) {
  const { courseId } = route.params;
  const [course, setCourse] = useState(null);
  const [author, setAuthor] = useState(null);

  useEffect(() => {
    emitter.addListener("progress", (payload) => {
      if (payload.courseId === courseId) {
        setCourse((prev) => {
          prev.lessons[payload.index].done = true;      // [E]
          return prev;
        });
      }
    });
  }, [courseId]);                                       // [C]

  useEffect(() => {
    async function load() {
      const c = await api.getCourse(courseId);          // [D]
      const a = await api.getAuthor(c.authorId);        // [D]
      setCourse(c);
      setAuthor(a);
    }
    load();
  }, [courseId]);

  if (!course) return <Spinner />;

  const visible = course.lessons
    .filter((l) => l.published)
    .map((l) => ({ ...l, label: `${l.order}. ${l.title}` }));   // [B]

  const stats = course.lessons.reduce((acc, l) => {             // [G]
    const words = l.transcript.split(/\s+/);
    return {
      total: acc.total + words.length,
      done: acc.done + (l.done ? 1 : 0),
    };
  }, { total: 0, done: 0 });

  return (
    <View style={{ padding: 16 }}>                              {/* [A] */}
      <Text>{author?.profile?.displayName}</Text>               {/* [F] */}
      <Text>Слов: {stats.total}</Text>
      <FlatList
        data={visible}
        keyExtractor={(l) => String(l.id)}
        renderItem={({ item }) => <LessonRow lesson={item} />}
      />
    </View>
  );
}
```

`LessonRow` мемоизирован. `emitter` — обёртка нативного модуля.

## 2. Как это работает

Разбор по фрагментам. Для каждого — четыре одинаковых вопроса.

### [A] Инлайн-объект в `style`

**Механизм языка:** литерал объекта создаёт новый объект при каждом вычислении, и идентичность у него новая (1.12).

**Что произойдёт в рантайме:** `style` — новый объект на каждый рендер, хотя содержимое всегда одно и то же.

**Кто заметит:** здесь — **никто**, и это намеренная проверка урока. Потребитель, сравнивающий по ссылке, должен быть мемоизированным компонентом, а `View` — встроенный: React Native сравнивает его пропсы и стиль по значению, и одинаковое содержимое не порождает ни перерисовки нативного view, ни трафика через границу JS↔native (1.12). По правилу из угла 1 — «проблема без наблюдателя не является проблемой» — [A] в этом компоненте **ложная тревога**.

Проблемой этот же фрагмент становится в другом месте: если инлайн-стиль уходит пропсом в мемоизированный компонент (`<LessonRow style={{...}} />`), он обнуляет его мемоизацию так же, как [B].

**Где решается:** 3.11 (когда стабилизация ссылки оправдана). Структурное решение — вынести стиль на уровень модуля — доступно уже сейчас (1.10, 1.12) и стоит одной строки, но в этом компоненте оно ничего не изменит, и честный ответ на ревью — «не трогать».

### [B] Цепочка `filter().map()` в теле

**Механизм:** каждый вызов создаёт новый массив; spread внутри `map` создаёт новый объект на каждый элемент (1.6).

**Что произойдёт:** `visible` — новый массив при каждом рендере, и каждый его элемент — новый объект, даже если данные не менялись.

**Кто заметит:** `FlatList` через `data` (новая идентичность), и — что важнее — **каждая мемоизированная ячейка** через пропс `lesson`. Сравнение пропсов всегда даёт «изменилось», поэтому мемоизация `LessonRow` не отсекает ничего и при этом продолжает выполнять сравнение.

**Где решается:** 3.11, 5.3 (доказать профайлером), 6.5 (то же в виде селектора).

### [C] Подписка без cleanup

**Механизм:** замыкание удерживает окружение, в котором объявлено, а не копию значений; пока жива подписка, жив и колбэк вместе со всем захваченным (1.14). Объект жив, пока достижим (1.22).

**Что произойдёт:** эффект не возвращает функцию очистки. При каждом изменении `courseId` добавляется **ещё одна** подписка, старая остаётся. После размонтирования экрана подписки живут, потому что на них ссылается `emitter` — долгоживущий JS-объект, через который нативный модуль сообщает о событиях; список слушателей хранится в нём.

**Кто заметит:** сборщик мусора — точнее, не заметит: объекты достижимы, и освободить их он не может (1.23). Плюс пользователь — через рост потребления памяти и, на слабом устройстве, через принудительное завершение приложения системой. В crash-репорте это выглядит как краш без стектрейса (10.7).

Дополнительно: каждая лишняя подписка вызовет свой колбэк, то есть `setCourse` будет вызван N раз на одно событие.

**Где решается:** 5.8 (утечки в RN), 3.5 (зависимости и cleanup как часть контракта эффекта), блок 09 (подписки на нативные события).

### [D] Два последовательных `await`

**Механизм:** `await` — точка приостановки; второй запрос не начинается, пока не завершился первый (1.19). Промис начинает работу в момент создания, а не в момент `await` (1.18).

**Что произойдёт:** время до наполнения экрана равно сумме двух запросов, хотя второй зависит от первого только через `c.authorId`.

Здесь важная честность: **это не всегда ошибка.** `api.getAuthor` требует `authorId` из ответа первого запроса, то есть зависимость подлинная, и параллелить напрямую нельзя. Ошибкой это становится, если `authorId` известен заранее (например, пришёл в параметрах навигации) — тогда последовательность искусственная.

**Кто заметит:** пользователь — через время до первого осмысленного экрана (TTI).

**Где решается:** 5.6 (TTI), 7.9 и 7.10 (устройство загрузки экрана, гонки и отмена). Сюда же относится вторая проблема этого фрагмента: `setCourse` может быть вызван после размонтирования экрана, и отмена — тема 7.10.

### [E] Мутация массива из состояния

**Механизм:** мутация меняет содержимое, не меняя идентичность (1.4, 1.13).

**Что произойдёт:** `prev.lessons[i].done = true` изменяет объект урока на месте, и функция возвращает **тот же** `prev`. React сравнит предыдущее состояние с новым, получит «равны» и не запланирует рендер.

**Кто заметит:** никто — и это ровно проблема. Данные изменились, экран нет; состояние приложения и состояние экрана разошлись.

Отдельно: это **не** просто «не обновится». Иногда обновится — когда рендер случится по другой причине (второй эффект, навигация, другое состояние). Отсюда недетерминированность: отметка выполнения появляется «иногда с задержкой», и воспроизвести это целенаправленно трудно.

**Где решается:** 6.4 (иммутабельность в редьюсерах), 3.3 (почему `setState` не означает немедленный рендер). Правило пути уже известно из 1.13.

### [F] `?.`, прячущий ошибку контракта

**Механизм:** короткое замыкание цепочки: при `null` или `undefined` слева вся цепочка возвращает `undefined` вместо выброса ошибки (1.9).

**Что произойдёт:** если `author` ещё не загружен — это законный случай, и `?.` уместен. Но если `author` загружен, а `profile` в ответе отсутствует, потому что контракт с бэкендом другой, — на экране будет пустая строка, и больше ничего: ни ошибки, ни записи в crash reporting, ни метрики.

**Кто заметит:** пользователь — через пустое место на экране. Система наблюдаемости — никак.

**Где решается:** 2.12 (валидация на границе, где схема даёт и тип, и проверку), 2.13 (границы системы), 7.2 (разбор ответа в одном месте). Это единственная из семи проблем, решение которой лежит в блоке 02.

### [G] Тяжёлая синхронная агрегация

**Механизм:** JS thread выполняет одну задачу за раз; пока синхронный код не завершился, цикл обработки событий не переходит к следующей задаче (1.20).

**Что произойдёт:** `reduce` со `split` по транскрипту каждого урока выполняется **в теле компонента**, то есть при каждом рендере. На курсе из 200 уроков с длинными транскриптами это десятки миллисекунд и больше. На это время JS thread занят: не обрабатываются нажатия, не применяются обновления состояния, не работает навигация.

**Кто заметит:** пользователь — через неотзывчивость интерфейса. При этом анимация, выполняемая на UI-потоке, может продолжать идти гладко — и это сбивает диагностику: «анимация не тормозит, значит с производительностью всё нормально».

**Где решается:** 5.1 (что именно занято и чем), 5.2 (бюджет кадра), 5.11 (методика: симптом → слой → замер).

## 3. Почему это важно

Шесть проблем дают шесть разных симптомов, а седьмой фрагмент в этом компоненте не даёт симптома вовсе — и соответствие между фрагментами и симптомами не взаимно однозначное:

| Симптом | Какие фрагменты его дают |
|---|---|
| экран не обновился | [E] |
| экран обновляется лишний раз / список перерисовывается целиком | [B]; [A] — только если стиль уходит в мемоизированный компонент, а здесь это не так |
| интерфейс не отвечает | [G] |
| приложение растёт в памяти и падает без стектрейса | [C] |
| пустое место на экране вместо данных или ошибки | [F] |
| экран наполняется дольше, чем нужно | [D] |

Отсюда главный вывод урока: **по симптому нельзя назвать причину.** «Лагает» — это как минимум два разных механизма с разными инструментами диагностики и разными решениями. Поэтому блок 05 начинается не со списка советов, а с методики, и поэтому checkpoint этого блока требует назвать механизм, а не симптом.

Второй вывод, менее очевидный: **ни одна из шести проблем не является ошибкой React или React Native.** Каждая — прямое следствие того, как в JavaScript работают ссылки, замыкания, очереди и достижимость. React только последовательно применяет сравнение идентичности; сборщик мусора только последовательно применяет критерий достижимости. Это снимает целый класс рассуждений вида «React неоптимален» и переводит разговор в область, где у разработчика есть управление.

## 4. Где это в React Native

Весь урок — это RN relevance: компонент реальный, проблемы реальные. Но три вещи существуют именно в React Native и в веб-приложении выглядели бы иначе.

**Удержание через объекты уровня приложения.** В [C] подписки живы потому, что на колбэк ссылается эмиттер нативного модуля — JS-объект, который живёт всю сессию, в отличие от экрана. Если бы колбэк держал сам нативный код (обработчик, сохранённый нативной библиотекой, колбэк в аргументе метода TurboModule), картина была бы ещё хуже: корень удержания лежал бы вне JS-кучи, и снимок памяти JS не показал бы его явно (1.22). Для веб-приложения с подпиской на DOM-событие, которое умирает вместе со страницей, картина проще.

**Исход «краш без стектрейса».** Рост памяти в мобильном приложении заканчивается не деградацией, а принудительным завершением процесса системой. В отчёте это выглядит как краш без JS-стектрейса, и отличить его от нативного краша — отдельный навык (10.7).

**Разделение потоков как источник ложного диагноза.** В [G] анимация на UI-потоке продолжает идти, пока JS thread занят. Это регулярно приводит к неверному выводу «производительность в порядке» и является одной из причин, по которой курс отказывается от модели «в RN ровно три потока» и привязывает разговор к инструментам измерения (5.1).

Плюс два фрагмента имеют RN-специфику в цене, и в противоположные стороны. Новые объекты элементов из [B] попадают в список с переиспользованием ячеек, где цена перерисовки выше, чем у обычного списка (5.4). А `style` из [A], наоборот, дешевле, чем подсказывает интуиция: встроенный `View` сравнивает стиль по значению перед отправкой на нативную сторону, и одинаковое содержимое через границу не уходит (1.12).

## 5. Типичные ошибки

### Ошибки в самом компоненте

Разобраны выше как [A]–[G]. Здесь — ошибки **диагностики**, то есть то, что мешает найти причину.

**«Это всё лечится `React.memo`.»** Возникает потому, что `memo` действительно связан с несколькими из семи проблем и упоминается в каждом обсуждении производительности. Но из семи он не решает ни одной полностью: [B] делает его бесполезным (пропсы всегда новые), [C], [E], [F], [G] к нему вообще не относятся, а в [A] он только перенесёт проблему на уровень выше. Хуже того: добавленный в такой компонент `memo` создаст видимость работы и сделает дальнейшую диагностику труднее.

**«Проблемы независимы друг от друга.»** Возникает из того, что механизмы действительно разные. Но последствия складываются и усиливаются: [G] выполняется при каждом рендере, а [A] и [B] увеличивают количество рендеров — то есть тяжёлая агрегация запускается чаще. [C] умножает число вызовов `setCourse` на одно событие, каждый из которых — ещё один рендер, в котором снова выполняется [G]. Исправление одной проблемы может существенно изменить проявление другой, и это аргумент за то, чтобы сначала составить карту целиком, а потом чинить.

**«В dev-режиме всё видно.»** Возникает из того, что dev действительно показывает многое: предупреждения, красный экран, двойные вызовы эффектов. Но [G] в dev-сборке медленнее у **всего** кода, поэтому относительный вклад агрегации неразличим; [C] проявляется только на времени и на реальной навигации; [F] не проявляется никак, если в тестовых данных `profile` присутствует; а `setCourse` после размонтирования в [D] с React 18 не даёт предупреждения ни в dev, ни в release — проблема невидима везде. Вывод: dev-сборка не является средой для выводов о производительности и о утечках (4.7).

**Поиск одной причины.** Самая дорогая ошибка диагностики: найдя одно объяснение симптома, прекратить искать. В этом компоненте «список тормозит при скролле» объясняется одновременно [B] и [G], и исправление только одного даст частичное улучшение, которое легко принять за решение.

## 6. Trade-offs

### Диагностика до исправления

Соблазн — чинить по ходу чтения. Цена такого подхода: после трёх правок непонятно, какая из них что изменила, а часть правок окажется лишней (как `memo` из угла 5). Карта стоит времени и не даёт немедленного результата — но делает каждую последующую правку проверяемой.

### Чинить всё против чинить по приоритету

Шесть проблем не равны по цене, а седьмой фрагмент не стоит ничего. [E] ломает **корректность** — экран показывает не то, что в данных. [C] заканчивается падением приложения. [F] даёт тихий неверный экран, не видимый в метриках. [B], [G] и [D] стоят производительности и времени загрузки.

Порядок, который следует из этого: сначала корректность ([E]), потом то, что приводит к падению ([C]), потом тихие дефекты данных ([F]), и только потом производительность ([B], [G]) — и она требует замера, а не рассуждения. [A] в списке нет: правка, которая ничего не меняет, — тоже цена. [D] решается по факту: если `authorId` известен заранее — это дешёвая правка, если нет — зависимость подлинная и трогать нечего.

### Карта без решений

Урок оставляет читателя со списком проблем и без ответов. Это неприятно и сделано сознательно: решение каждой требует знаний, которых на выходе из блока 01 нет. Мемоизация без модели фаз рендера — расстановка обёрток по интуиции; отмена асинхронной операции без модели гонок — флаг, который закрывает не тот случай. Цена честного «решение будет в блоке 05» — дискомфорт сейчас; цена преждевременного ответа — рецепт без понимания границ применимости, то есть именно то, против чего построен весь курс.

## 7. Связи с другими частями системы

**Назад — какой урок отвечает за какой фрагмент:**

| Фрагмент | Механизм | Урок блока 01 |
|---|---|---|
| [A] | новая идентичность литерала | 1.12, 1.4 |
