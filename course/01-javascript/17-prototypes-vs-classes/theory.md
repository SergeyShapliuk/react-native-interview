# 1.17 Prototypes vs классы — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «классы или прототипы лучше» — а на вопрос, **что именно остаётся от объекта, когда он пересекает границу: сериализацию, хранилище, crash-репорт, нативный слой.** Ответ на этот вопрос и определяет решение по домену.

---

## 1. Что это

**Prototype (прототип)** — объект, к которому обращаются за свойством, если его нет у самого объекта. У каждого объекта есть внутренняя ссылка на свой прототип.

**Prototype chain (цепочка прототипов)** — последовательность объектов, получаемая переходом по этим ссылкам, до `null`. Это путь поиска **свойства**.

Здесь полезно сопоставление с предыдущим уроком: в языке две цепочки поиска, и их легко спутать.

| | Scope chain (1.15) | Prototype chain |
|---|---|---|
| что ищет | **имена** переменных | **свойства** объектов |
| чем определяется | местом объявления в коде | значением внутренней ссылки объекта |
| можно ли изменить в рантайме | нет | да (`Object.setPrototypeOf`) |
| где заканчивается | глобальное окружение | `null` |
| что при ненахождении | `ReferenceError` | `undefined` |

Последняя строка практически важна: отсутствие свойства — не ошибка, а `undefined`. Поэтому опечатка в имени метода даёт не «нет такого метода», а `TypeError: ... is not a function` — на шаг позже и в другом месте.

**Delegation (делегирование)** — модель, в которой объект не содержит поведение, а перенаправляет запрос другому объекту. Это и есть наследование в JavaScript: **делегирование в рантайме, а не копирование структуры при создании.**

Разница наблюдаема: добавление метода в прототип после создания экземпляров делает его доступным **всем уже созданным** экземплярам. При копировании структуры это было бы невозможно.

## 2. Как это работает

### `__proto__` против `prototype`

Два имени, которые постоянно смешиваются, хотя относятся к разным вещам.

- **`prototype`** — свойство **функции**. Оно существует только у функций и содержит объект, который станет прототипом экземпляров, созданных через `new` эту функцию. Сама функция свой `prototype` не использует для поиска своих свойств.
- **`__proto__`** (точнее `Object.getPrototypeOf(obj)`) — ссылка **самого объекта** на свой прототип. Есть у любого объекта.

```js
function Lesson(title) { this.title = title; }
Lesson.prototype.describe = function () { return this.title; };

const l = new Lesson("Closures");

Object.getPrototypeOf(l) === Lesson.prototype;   // true
l.prototype;                                      // undefined — у экземпляра нет prototype
Lesson.__proto__ === Function.prototype;          // true — функция тоже объект
```

Формулировка, снимающая путаницу: **`prototype` — это то, что функция даёт своим экземплярам; `__proto__` — это то, чем объект пользуется сам.**

Цепочка для `l`:

```
l                   → title
  ↓
Lesson.prototype    → describe, constructor
  ↓
Object.prototype    → toString, hasOwnProperty, ...
  ↓
null
```

### Что делает `new` по шагам

```js
const l = new Lesson("Closures");
```

1. Создаётся новый пустой объект.
2. Его внутренняя ссылка на прототип устанавливается в `Lesson.prototype`.
3. Функция `Lesson` вызывается с `this`, равным этому объекту (1.16, правило 2), и с переданными аргументами.
4. Если функция вернула объект — результатом выражения становится он; иначе — созданный на шаге 1 объект.

Шаг 4 — та деталь, которую обычно не знают, и из неё следует, что фабрика и конструктор взаимозаменяемы снаружи: функция, возвращающая объект, через `new` вернёт именно его, а не экземпляр.

Шаг 2 — ядро всей темы: экземпляр получает **ссылку**, а не копию методов. Поэтому методы существуют в единственном экземпляре на класс, и поэтому их нет в самом объекте — что и определяет поведение на границе сериализации (угол 4).

### `class` как синтаксический сахар — и чем он всё же отличается

```js
class Lesson {
  constructor(title) { this.title = title; }
  describe() { return this.title; }
}
```

Результат по структуре тот же: `describe` лежит в `Lesson.prototype`, экземпляр содержит только `title`. Проверяется напрямую:

```js
Object.keys(new Lesson("x"));                         // ["title"] — метода нет
Object.getPrototypeOf(new Lesson("x")).describe;      // функция — он в прототипе
```

Но «сахар» — неточное слово: есть различия, которые видны в поведении.

| Отличие | Поведение `class` | Поведение функции-конструктора |
|---|---|---|
| вызов без `new` | `TypeError` | без strict mode (обычный RN-модуль, 1.16) `this` — `globalThis`, и поля тихо записываются в глобальный объект; в strict mode — `TypeError` на первом `this.x = …` |
| hoisting | нет: до объявления — TDZ (1.1) | объявление функции поднимается, вызов до него работает |
| strict mode | тело всегда strict | зависит от окружения |
| методы в `for...in` | не перечисляются | перечисляются, если добавлены присваиванием |
| приватные поля `#x` | есть, недостижимы извне на уровне языка | нет, только соглашение или замыкание (1.14) |
| поля класса `x = 1` | присваиваются экземпляру при создании | эквивалент — присваивание в конструкторе |
| `extends` от чего угодно | можно наследовать от любого выражения | требует ручной настройки цепочки |

Два отличия заслуживают отдельного внимания.

**Отсутствие hoisting.** `new Lesson()` до строки `class Lesson {}` **в том же модуле** по спецификации даёт `ReferenceError`, в отличие от функции-конструктора: класс находится в temporal dead zone (1.1). В RN пресет сохраняет `class` как есть (в отличие от `let`/`const`, которые он переписывает в `var` без проверки TDZ), поэтому проверка остаётся за движком. В Node это `ReferenceError`; поведение Hermes V1 здесь стоит проверить на своей версии — TDZ исторически не была сильной стороной Hermes, и опираться на неё как на защиту не стоит. Чего это **не** меняет в RN — циклических импортов. Через границу модулей Metro читает класс как свойство объекта экспортов (1.10), и недоинициализированный экспорт там — просто `undefined`, независимо от того, класс это или функция. Поэтому в цикле `new Lesson()` даст `TypeError: … is not a constructor`, а не `ReferenceError`, и «классы защищают от циклов» в RN неверно.

**Поля класса.** Поле — это присваивание **свойства экземпляра**, а не запись в прототип. Поэтому стрелочное свойство создаётся на каждый экземпляр (1.16, угол 6), а обычное поле попадает в `Object.keys` и в `JSON.stringify` — в отличие от метода.

### `extends` и цепочка

```js
class AppError extends Error {
  constructor(message, code) {
    super(message);
    this.name = "AppError";
    this.code = code;
  }
}
```

`extends` делает две вещи: связывает `AppError.prototype` с `Error.prototype` (цепочка для экземпляров) и связывает сам `AppError` с `Error` (наследование статических свойств). `super(message)` вызывает конструктор родителя с текущим `this`.

Цепочка экземпляра:

```
экземпляр AppError      → message, name, code, stack
  ↓
AppError.prototype      → constructor
  ↓
Error.prototype         → toString
  ↓
Object.prototype
  ↓
null
```

Обратите внимание, где лежат `message` и `code`: это **собственные свойства экземпляра**, а не прототипа. Это то, что отличает их судьбу при сериализации от судьбы методов.

### Делегирование в рантайме

```js
const l = new Lesson("Closures");
Lesson.prototype.toSlug = function () { return this.title.toLowerCase(); };
l.toSlug();     // работает — хотя l создан до добавления метода
```

Поиск свойства происходит **при каждом обращении**, а не фиксируется при создании. Это и есть делегирование, и из него следуют два практических вывода: методы можно добавлять и подменять после создания объектов (основа моков в тестах — 11.3), и обращение к методу всегда идёт на шаг дальше, чем к собственному свойству.

### Что происходит на границе сериализации

```js
class Lesson {
  constructor(title, done) { this.title = title; this.done = done; }
  get label() { return `${this.title}${this.done ? " (завершён)" : ""}`; }
  complete() { return new Lesson(this.title, true); }
}

const l = new Lesson("Closures", false);
const restored = JSON.parse(JSON.stringify(l));

restored;                        // { title: "Closures", done: false }
restored instanceof Lesson;      // false
restored.complete;               // undefined
restored.label;                  // undefined
```

`JSON.stringify` обходит **собственные перечислимые свойства**. Методы в прототипе, геттеры в прототипе, приватные поля — ничего из этого не является собственным свойством экземпляра, и ничего из этого не сериализуется. На другой стороне окажется простой объект с данными.

Это не особенность JSON. То же верно для любого способа передать объект через границу, где он превращается в данные: хранилище, сетевой запрос, `postMessage`, кэш, граница JS↔native (1.2), payload crash-репорта. Прототип не передаётся, потому что он не является частью значения — он является ссылкой на объект в той же куче.

Формулировка, которую стоит унести: **границу пересекают данные; поведение остаётся на той стороне, где объявлено.**

## 3. Почему это важно

Не для того, чтобы выбрать «правильную парадигму». Для трёх конкретных вещей.

**Чтение кода.** Классы приходят из библиотек, из legacy-кода и из нативных обёрток. Без модели прототипов непонятно, где живёт метод, почему его нет в `Object.keys`, почему его можно подменить в тесте и почему он исчезает после сериализации.

**Решения по домену.** Выбор между классом и «тип + чистые функции» для сущности домена — это решение, которое принимается один раз и определяет работу с данными во всём приложении. Принимать его надо по поведению на границах, а не по привычке. Разбор — угол 6, задание в practice.

**Диагностика.** Три характерных дефекта имеют одну причину, и она в этом уроке: `instanceof` вернул `false` для «того же» объекта; метод исчез после чтения из хранилища; в crash-репорте от собственного класса ошибки остались только `name` и `message`. Все три — следствие того, что прототип не пересекает границу.

## 4. Где это в React Native

### Объект с методами не проходит границу JS↔native

На нативной стороне окажутся только данные — то, что контракт границы способен представить (1.2). Экземпляр класса пересечёт её как простой объект: поля на месте, методы, геттеры и прототип отсутствуют. Обратно он вернётся тоже простым объектом — и `instanceof` по нему вернёт `false`.

Это не ограничение, которое обходят: поведение по определению не является данными. Попытка «восстановить класс» на обратном пути требует явного шага — фабрики, которая принимает данные и возвращает экземпляр. Этот шаг нужно написать, поддерживать и не забыть вызвать в каждой точке входа данных: ответ сервера, чтение из хранилища, нативный колбэк, восстановление состояния после перезапуска.

Отсюда и практика, сложившаяся в RN-проектах: **доменные модели чаще описывают типами и чистыми функциями, а не классами.** Данные остаются простыми объектами на всём пути — от ответа сервера до хранилища и обратно, — и ни одна граница не требует восстановления. Поведение живёт в функциях, которые принимают данные параметром. Решение по RN Academy (P1) именно такое; обоснование — угол 6.

### Собственные классы ошибок — и что от них остаётся

Иерархия ошибок классами полезна (1.11): `instanceof AppError` работает в пределах JS, `name` и `code` несут смысл, `catch` может различать виды ошибок.

Но после сериализации в crash-репорт от такого класса остаётся немного:

```js
class ApiError extends Error {
  constructor(message, status, endpoint) {
    super(message);
    this.name = "ApiError";
    this.status = status;
    this.endpoint = endpoint;
  }
}
```

В отчёт попадут `name`, `message` и `stack` — это то, что инструменты крашей читают по соглашению. Собственные поля (`status`, `endpoint`) **не попадут автоматически**: они не входят в стандартный набор, который собирает SDK. Чтобы они оказались в отчёте, их нужно добавить явно — как контекст, теги или extra-данные при отправке (10.6).

Практический вывод: класс ошибки полезен для логики внутри JS и почти ничего не даёт для диагностики по отчёту, если контекст не передан отдельно. И принимается это решение до релиза — после получения отчёта добавить в него данные невозможно (1.15).

Отдельно: `stack` в release-сборке принадлежит минифицированному коду и требует symbolication (10.6); классовая природа ошибки на это не влияет никак.

### Классы в библиотеках и нативных обёртках

Библиотеки отдают объекты с методами: клиенты баз данных, плееры, карты, SDK аналитики. С ними работают как есть — и там же возникает проблема потери `this` при передаче метода колбэком (1.16). Два правила для таких объектов: не сериализовать их и не хранить в состоянии, которое персистится.

### Классовые компоненты

Встречаются в проектах с историей. Для этого урока существенно одно: методы такого компонента лежат в прототипе, стрелочные свойства — в экземпляре, и отсюда разница в количестве создаваемых функций и в возможности подмены (1.16, угол 6).

### Структуры с прототипом в состоянии

Отдельный RN-сюжет: состояние, которое персистится между запусками приложения. Если в нём лежат экземпляры классов, после перезапуска из хранилища вернутся простые объекты — и код, вызывающий на них методы, упадёт **только при холодном старте**. В dev-сессии с горячими перезагрузками состояние живёт в памяти, и дефект не воспроизводится. Это типичная форма «работает у меня, падает у пользователя».

## 5. Типичные ошибки

**`instanceof` для данных, пришедших извне.** Возникает потому, что внутри JS `instanceof` надёжен, и привычка переносится на данные из-за границы. Но `instanceof` проверяет наличие `Constructor.prototype` в цепочке прототипов — а у объекта, полученного из `JSON.parse`, из хранилища или из нативного колбэка, прототип это `Object.prototype`. Проверка возвращает `false` для объекта, который по смыслу «тот же». Цена: ветка кода молча не выполняется, и дефект проявляется как отсутствие поведения, а не как ошибка. Проверять принадлежность данных нужно по содержимому — полю-дискриминанту, — а не по прототипу.

**Ожидание, что `instanceof` различит ошибки после границы.** Частный случай предыдущей, но с более высокой ценой: `catch (e) { if (e instanceof ApiError) ... }` работает, пока ошибка не прошла через сериализацию. После передачи ошибки через слой, который её сериализует (например, из воркера или из нативного модуля), это обычный объект, и обработка пойдёт по ветке «неизвестная ошибка».

**Потеря прототипа при spread.** Возникает из модели «spread копирует объект». Spread копирует **собственные перечислимые свойства** (1.8); прототип не копируется, методы и геттеры не переносятся:

```js
const copy = { ...lessonInstance };
copy instanceof Lesson;    // false
copy.complete;             // undefined
```

Коварство в том, что данные на месте и объект выглядит правильным. Ошибка обнаруживается при первом вызове метода, то есть, возможно, намного позже места копирования. Это же касается любого иммутабельного обновления через spread: **иммутабельность и классы плохо совмещаются** — обновление «как принято» уничтожает прототип (1.13, 6.4).

**Расширение встроенных типов.** `Array.prototype.last = function () {...}` возникает из желания получить удобный синтаксис. Три проблемы: добавленное свойство перечислимо и попадает в `for...in` по всем массивам приложения; имя может совпасть с будущим методом стандарта или с методом, который добавит библиотека; поведение становится глобальным, то есть зависит от порядка загрузки модулей. В RN-приложении, где полифиллы и библиотеки грузятся вместе с вашим кодом, последствия непредсказуемы и диагностируются плохо.

**Глубокие иерархии наследования.** Возникает из переноса опыта ООП-языков, где иерархия — основной инструмент организации кода. В JS каждый уровень — ещё одно звено в цепочке поиска и ещё один слой, в котором может быть переопределён метод. Практическая цена не в скорости, а в читаемости: чтобы понять, что делает `obj.method()`, нужно проверить все уровни. Композиция функций в этом смысле честнее — что вызвано, видно по коду.

**«`class` — это просто сахар, отличий нет».** Возникает из верного наблюдения про структуру (методы оказываются в прототипе в обоих случаях) с неверным обобщением. Отличия перечислены в угле 2, и два из них меняют поведение: вызов без `new` даёт `TypeError` вместо тихого мусора, и отсутствие hoisting даёт явный `ReferenceError` при обращении к классу до объявления в том же модуле (но не через циклический импорт в RN — там по-прежнему `undefined`, 1.10).

**Хранение экземпляров в персистентном состоянии.** Возникает потому, что в dev-сессии это работает: состояние живёт в памяти, и прототипы на месте. Ломается при холодном старте, когда состояние читается из хранилища. Худшая форма ошибки из этого урока — она не воспроизводится в среде разработки по самой своей природе.

## 6. Trade-offs

### Классы дают знакомую модель, но плохо проходят границы сериализации

Центральный trade-off урока.

| | Класс | Тип + чистые функции |
|---|---|---|
| где живёт поведение | в прототипе, вместе с данными | в отдельных функциях, принимающих данные |
| знакомость модели | высокая для пришедших из ООП | ниже, требует привычки |
| связность данных и операций | в одном месте, видно через автодополнение | операции надо найти в модуле |
| после `JSON.parse` | данные без поведения, `instanceof` ложен | ничего не теряется: данные и есть вся модель |
| после чтения из хранилища | требуется восстановление через фабрику | ничего не требуется |
| через границу JS↔native | только данные | только данные — и этого достаточно |
| иммутабельное обновление | spread уничтожает прототип | spread — штатная операция |
| `this` при передаче метода колбэком | теряется (1.16) | проблемы нет |
| тестирование | требует создания экземпляра | вызов с литералом данных |
| инкапсуляция | `#`-поля на уровне языка | нет |

Решение для домена RN-приложения: **типы и чистые функции.** Обоснование — число границ, которые данные пересекают в мобильном приложении. Ответ сервера, персистентное хранилище, кэш, граница JS↔native, payload аналитики, состояние, восстанавливаемое после перезапуска. На каждой из них класс требует явного шага восстановления, а пропущенный шаг даёт дефект, который не воспроизводится в dev.

Исключение, где класс выигрывает: **ошибки.** Иерархия через `extends Error` даёт работающий `instanceof` внутри JS, совместимость с `catch`, корректный `stack` и `name`, которые инструменты читают по соглашению (1.11). Ошибки не персистятся, не передаются в нативный слой как данные и живут один цикл обработки — то есть ни одна причина против классов к ним не относится.

Это и есть решение RN Academy (P1): **типы и чистые функции для домена, классы только для ошибок.** Оно фиксируется документированно, потому что это первое решение, которое определяет форму всех данных в приложении.

### Прототипные методы против полей-функций

Разобрано в 1.16, угол 6. Здесь добавляется один аргумент: метод прототипа существует в единственном экземпляре и может быть подменён или обёрнут (мок в тесте, инструментирование, декоратор) — поле экземпляра нельзя (11.3).

### Наследование против композиции

| | `extends` | Композиция функций |
|---|---|---|
| переиспользование | через иерархию | через вызов |
| что выполнится при `obj.m()` | зависит от всех уровней цепочки | видно в коде |
| изменение общего поведения | в одном месте, затрагивает всех потомков | в одном месте, затрагивает вызывающих |
| жёсткость | высокая: иерархия фиксирует отношения | низкая |

В JS композиция обычно дешевле, потому что функции — значения первого класса и передаются без церемоний. `extends` оправдан там, где он задан извне: `extends Error`, `extends React.Component` в legacy-коде, базовые классы библиотек.

### Делегирование: стоимость и выигрыш

Поиск по цепочке прототипов — не бесплатная операция, но движки кэшируют формы объектов, и в продуктовом коде это не та величина, из которой принимают решения. Содержательный выигрыш делегирования другой: один экземпляр метода на класс вместо копии на объект, и возможность подмены в рантайме. Содержательная цена — чтобы понять, что выполнится, нужно знать цепочку.

Единственное место, где это стоит упомянуть как производительность: `Object.setPrototypeOf` на существующем объекте ломает оптимизации движка и дорог. Менять прототип готового объекта не надо — это относится и к Hermes (4.5).

## 7. Связи с другими частями системы

**Назад:**

- **1.16** — `this` в методе и в вызове через `new`; потеря получателя при передаче метода колбэком — ровно та цена класса, которая платится на каждой передаче;
- **1.15** — вторая цепочка поиска в языке: scope chain ищет имена, prototype chain ищет свойства; структуры похожи, области применения не пересекаются;
- **1.2** — сериализуемость как свойство значения: почему объект с методами не пересекает границу JS↔native в том виде, в котором существует в JS;
- **1.11** — иерархия ошибок как инструмент и единственное место, где класс в RN-проекте оправдан почти всегда;
- **1.8** — spread копирует собственные перечислимые свойства: отсюда потеря прототипа при копировании экземпляра;
- **1.12** — идентичность: `instanceof` отвечает на вопрос о прототипе, `===` — о идентичности, и ни один не отвечает на вопрос о содержимом.

**Вперёд:**

- **1.18 Promises** — объект состояния, с которым работают по контракту, а не как с классом; и ещё одна граница, где данные отделяются от поведения;
- **блок 02** — типы для домена вместо классов: решение этого урока получает инструмент, который его проверяет;
- **6.4 Иммутабельность в редьюсерах** — почему spread как штатная операция обновления плохо совмещается с экземплярами классов;
- **блок 09** — контракт нативного модуля: что именно можно описать на границе и почему поведение туда не передаётся;
- **10.6 Sentry / Crashlytics** — что из собственного класса ошибки попадёт в отчёт автоматически (`name`, `message`, `stack`) и что требуется добавить явно;
- **10.7 JS-краш vs нативный краш** — почему по отчёту не видно классовой структуры JS-кода;
- **11.3 Тестирование** — подмена метода прототипа как инструмент и её недоступность для полей экземпляра.

**Главное, что должно остаться после урока.** Наследование в JavaScript — делегирование в рантайме: экземпляр содержит данные и ссылку на объект, где искать поведение. Границу пересекают данные, ссылка остаётся. Поэтому вопрос «класс или тип с функциями» для домена решается не парадигмой, а подсчётом границ, которые данные пересекают в мобильном приложении — и в RN-проекте их достаточно, чтобы ответ был «типы и чистые функции», с исключением для ошибок.
