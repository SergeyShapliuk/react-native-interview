# 1.16 `this` — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает на вопрос «чему равен `this` в этом вызове» — и сразу говорит, зачем это нужно знать разработчику, который пишет функциональные компоненты и хуки: **для чтения чужого кода и для границ с библиотеками и нативным слоем.** Писать новый код с `this` урок не предлагает.

---

## 1. Что это

**`this`** — часть контекста исполнения (1.15), значение, которое движок устанавливает при входе в функцию. Для обычных функций оно определяется **способом вызова**, а не местом объявления.

Это делает `this` единственным исключением в языке из правил предыдущего урока. Имена ищутся лексически — по месту объявления; `this` для обычных функций определяется динамически — по форме вызова. Отсюда практический вывод: **нельзя посмотреть на объявление функции и сказать, чему будет равен её `this`.** Нужно смотреть на вызов.

```js
function who() {
  return this;
}

const obj = { who };

who();        // в strict mode — undefined; в обычном RN-модуле — globalThis (см. правило 4)
obj.who();    // obj — та же функция, другой this
```

Одна функция, два вызова, два разных `this`. Ничего в объявлении `who` не изменилось.

Стрелочные функции работают иначе: у них **нет собственного `this`**, они берут его из окружения лексически — то есть по правилам 1.15. Это не «правило пятое», а отсутствие правил: в стрелочной функции `this` — такое же внешнее имя, как любое другое.

## 2. Как это работает

### Четыре правила определения `this`

Правила проверяются в этом порядке; первое подходящее выигрывает.

**1. Явная привязка — `call` / `apply` / `bind`.** `this` — то, что передано первым аргументом.

```js
function greet() { return this.name; }
greet.call({ name: "Serge" });     // "Serge"
greet.apply({ name: "Serge" });    // "Serge" — отличие только в форме передачи аргументов
const bound = greet.bind({ name: "Serge" });
bound();                            // "Serge" — привязка зафиксирована навсегда
```

`call` и `apply` вызывают функцию сразу; разница между ними только в том, перечисляются аргументы списком или передаются массивом. `bind` ничего не вызывает — он **создаёт новую функцию** с зафиксированным `this`. Это важно дважды: привязку нельзя переопределить повторным `bind` или `call`, и каждый вызов `bind` даёт новый объект-функцию с новой идентичностью (1.12).

**2. Вызов через `new`.** `this` — новый создаваемый объект.

```js
function Client(url) { this.url = url; }
const c = new Client("/api");      // this внутри Client — новый объект
```

Что `new` делает по шагам целиком — 1.17; здесь существенно только то, что `this` при таком вызове — это создаваемый экземпляр.

**3. Вызов методом — есть точка перед именем.** `this` — объект **слева от точки** в момент вызова.

```js
const client = {
  url: "/api",
  load() { return this.url; },
};
client.load();                      // "/api" — this это client
```

Ключевая формулировка: `this` определяется не тем, где метод объявлен, а тем, **что стоит слева от точки в выражении вызова**. Отсюда вся линейка ошибок с потерей `this`.

```js
const nested = { inner: client };
nested.inner.load();                // this это client, не nested — слева от точки стоит nested.inner
```

**4. Обычный вызов — точки нет.** В strict mode `this` равен `undefined`; без strict mode — глобальный объект (`globalThis`).

```js
const load = client.load;
load();   // strict mode: TypeError — Cannot read property 'url' of undefined
          // без strict mode: undefined — globalThis.url не существует, ошибки нет
```

Какой из двух вариантов действует в RN, неочевидно — и интуиция из веба здесь ошибается. Нативные ES-модули всегда исполняются в strict mode, но **RN-бандл не состоит из ES-модулей**: Babel-пресет React Native переписывает `import` / `export` в CommonJS и **намеренно не добавляет** `"use strict"` (в его конфигурации так и написано: `strictMode: false`, проверено на `@react-native/babel-preset` 0.87). Поэтому:

- **обычная функция вне класса** в RN-коде исполняется без strict mode: потерянный `this` — это `globalThis`;
- **метод класса** исполняется в strict mode, потому что тело класса строгое по спецификации, — `this` будет `undefined`. Это верно, пока классы не транспилированы: актуальный пресет с Hermes сохраняет их как есть, а старые версии превращали классы в функции и вместе с этим теряли строгость;
- файл, начинающийся с `"use strict"`, строгий целиком.

Практическое следствие хуже, чем принято думать: потеря `this` в RN **не всегда** даёт немедленную ошибку. Обращение `this.label` к `globalThis` тихо вернёт `undefined` и уедет дальше по коду; ошибка случится только там, где от этого `undefined` ещё раз возьмут свойство или вызовут метод (`this.queue.push(...)`) — уже с сообщением про `undefined`, а не про `this`.

### Стрелочные функции: лексический `this`

```js
const timer = {
  label: "sync",
  startBroken() {
    setTimeout(function () {
      console.log(this.label);      // обычный вызов колбэка: this — globalThis в RN-модуле
    }, 1000);                       // (undefined.label и TypeError — в strict mode)
  },
  startOk() {
    setTimeout(() => {
      console.log(this.label);      // "sync" — this взят из startOk лексически
    }, 1000);
  },
};
```

В `startBroken` колбэк вызывается движком таймера как обычная функция — правило 4: `this` равен `globalThis` (в RN-модуле) или `undefined` (в strict mode), и в обоих случаях это не `timer`. В `startOk` стрелочная функция не имеет своего `this` и берёт его из окружения, где объявлена, то есть из вызова `startOk`, где он равен `timer`.

Следствия, которые стоит зафиксировать:

- `bind`, `call` и `apply` на стрелочной функции **не меняют `this`** — менять нечего. Переданный аргумент просто игнорируется;
- стрелочная функция не может быть вызвана через `new`;
- стрелочный метод объекта — почти всегда ошибка: `const o = { name: "x", get: () => this.name }` возьмёт `this` из места объявления объекта, а не из `o`.

### Потеря `this` при передаче метода как колбэка

Это главный практический сюжет урока, и он один и тот же в legacy-коде и в современном.

```js
class NativeBridge {
  constructor(emitter) {
    this.emitter = emitter;
    this.queue = [];
  }

  handleEvent(event) {
    this.queue.push(event);         // this — тот, что определит вызов
  }

  subscribe() {
    this.emitter.addListener("data", this.handleEvent);   // метод оторван от объекта
  }
}
```

`this.handleEvent` — это **выражение доступа к свойству**, результат которого обычная функция. Объект, из которого её достали, в ней никак не сохраняется: связь «метод — получатель» создаётся только формой вызова. Emitter вызовет её как `callback(event)`, то есть по правилу 4, и `this` будет `undefined`.

Формулировка, которая закрывает тему: **метод в JavaScript не принадлежит объекту. Принадлежность возникает в момент вызова и живёт только этот вызов.**

### Четыре способа не потерять `this`

```js
// 1. bind в конструкторе — одна функция на экземпляр, стабильная ссылка
constructor() { this.handleEvent = this.handleEvent.bind(this); }

// 2. стрелочное свойство класса — одна функция на экземпляр, стабильная ссылка
handleEvent = (event) => { this.queue.push(event); };

// 3. стрелка-обёртка в месте передачи — новая функция на каждую передачу
emitter.addListener("data", (e) => this.handleEvent(e));

// 4. bind в месте передачи — новая функция на каждую передачу
emitter.addListener("data", this.handleEvent.bind(this));
```

| Способ | Функций создаётся | Ссылка стабильна | Пригоден для снятия подписки |
|---|---|---|---|
| `bind` в конструкторе | одна на экземпляр | да | да |
| стрелочное свойство | одна на экземпляр | да | да |
| стрелка в месте передачи | по одной на каждую передачу | нет | только если сохранить ссылку |
| `bind` в месте передачи | по одной на каждую передачу | нет | только если сохранить ссылку |

Последняя колонка практически важнее остальных: `emitter.removeListener("data", this.handleEvent.bind(this))` **не снимает подписку**, потому что `bind` создал другую функцию, чем та, которую добавляли. Подписка остаётся живой, и вместе с ней — всё, что она удерживает (1.14). Это тихий дефект: ошибки нет, снятие просто не происходит.

## 3. Почему это важно

Не для того, чтобы писать код с `this`. Для трёх других вещей.

**Чтение.** В любом проекте с историей есть классовые компоненты, классовые сервисы и библиотеки на классах. Прочитать их невозможно, не умея ответить, чему равен `this` в каждом вызове. Без этого поведение кода выглядит произвольным, а правка — рискованной.

**Границы.** Библиотеки и обёртки нативных модулей отдают объекты с методами. Как только метод такого объекта передаётся куда-то колбэком, возникает ровно та ошибка, что в угле 2 — в коде, написанном сегодня и без единого класса со стороны разработчика.

**Диагностика.** `TypeError: Cannot read property 'x' of undefined` в кадре, который выглядит корректным, — типичная подпись потери `this`. Узнавать её по форме быстрее, чем выяснять заново.

Чего из этого **не следует**: что `this` надо избегать как опасной конструкции, и что классы — плохой код. Из урока следует только, что принадлежность метода объекту в JavaScript не является свойством метода, и это нужно учитывать на каждой передаче.

## 4. Где это в React Native

### Где `this` сегодня не нужен

**В функциональных компонентах, хуках и чистых функциях** — то есть в основной массе кода современного RN-приложения. У функционального компонента нет `this`; состояние живёт в хуках, зависимости приходят параметрами, контекст — через замыкание (1.14). Специально искать применение `this` в новом коде не нужно, и этот урок этого не предлагает.

Более того: там, где в классовом коде нужен `this`, в функциональном обычно достаточно замыкания — и получается явнее, потому что видно, что захвачено. Единственное, что приходит взамен, — вопрос свежести захваченного значения, и он разобран в 1.14 и 3.5.

### Где `this` всё ещё встречается

- **classes** — классовые сервисы (сетевой клиент, аналитика, менеджер подписок), доменные модели, собственные классы ошибок (1.17);
- **legacy code** — классовые компоненты в проектах с историей, вместе с `bind` в конструкторе и в `render`;
- **libraries** — API сторонних библиотек, построенные на классах и методах: клиенты баз данных, плееры, карты, SDK аналитики;
- **native callbacks** — обёртки нативных модулей и emitter-ы, где колбэк вызывается не как метод объекта;
- **event handlers** — метод объекта, переданный обработчиком, теряет получателя;
- **методы объектов** — любой объект с методами, когда метод «отрывается» от объекта.

### Классовый компонент из legacy-кода

```jsx
class LessonScreen extends React.Component {
  handlePress() {
    this.props.onOpen(this.props.lesson.id);
  }

  render() {
    return <LessonRow onPress={this.handlePress.bind(this)} />;   // две проблемы
  }
}
```

Первая проблема решена — `bind` вернул функцию с правильным `this`. Вторая создана: `bind` в `render` создаёт **новую функцию на каждый рендер**, то есть `onPress` — всегда новый пропс. Если `LessonRow` мемоизирован, мемоизация не отсекает ничего: один нестабильный пропс обнуляет её эффект целиком (1.12). При этом сравнение пропсов всё равно выполняется — то есть добавлена работа без выигрыша.

То же относится к `onPress={() => this.handlePress()}`: стрелка в `render` создаётся заново так же, как `bind`. Правильное место для привязки — конструктор или стрелочное свойство класса, то есть один раз на экземпляр.

### Обёртка нативного модуля

```js
class ProgressSync {
  constructor() {
    this.buffer = [];
  }

  onNativeEvent(event) {
    this.buffer.push(event.value);
  }

  start(emitter) {
    this.sub = emitter.addListener("ProgressChanged", this.onNativeEvent);
  }

  stop() {
    this.sub?.remove();
  }
}
```

Ошибка та же, что в угле 2, и обнаруживается она уже на устройстве: эмулятор может не генерировать нативное событие, а на устройстве первое же событие даёт `TypeError` в колбэке. Специфика RN добавляет две детали:

- колбэк вызывает эмиттер — JS-объект, которому нативная сторона сообщила о событии, — как обычную функцию, то есть точно не как метод объекта: правило 4 здесь гарантировано;
- ошибка возникает **внутри** колбэка, который вызван не из вашего стека, поэтому `try/catch` вокруг `start` её не поймает (1.11), а в стектрейсе не будет кадров, где подписка создавалась (1.15).

### Снятие подписки и идентичность

RN-специфичное последствие таблицы из угла 2: если подписка добавлена с `bind` в месте передачи, снять её по тому же выражению невозможно. Подписка живёт, удерживает окружение, и приложение накапливает обработчики при каждом переходе между экранами (1.14, 1.22, 5.8). Ошибки при этом нет нигде — только рост памяти и дублирование обработки событий.

Современные API самого RN (`AppState`, `Keyboard`, `NativeEventEmitter`, `Linking`) от этой ловушки уже защищены: `addListener` возвращает объект подписки, снятие идёт через его `remove()`, а парные `removeEventListener` / `removeListener` из API удалены. Ловушка жива в сторонних эмиттерах с парой `on` / `off`, в шинах событий проекта и в legacy-коде на старых версиях RN — и именно туда переносится привычка «отписаться тем же выражением».

### Классы ошибок

Единственное место, где классы в RN-проектах оправданы почти всегда, — иерархия ошибок (1.11). Там `this` появляется в конструкторе и больше нигде, и никакой проблемы с привязкой не создаёт: ошибку не передают колбэком. Решение по домену — 1.17.

## 5. Типичные ошибки

**Передача метода без привязки.** Возникает из модели «метод принадлежит объекту», перенесённой из языков, где это действительно так. В Java или C# ссылка на метод несёт получателя; в JavaScript `obj.method` — это чтение свойства, результат которого обычная функция без всякой памяти о том, откуда её взяли. Пока модель неверна, ошибка воспроизводится в новом коде постоянно, потому что выглядит безупречно: `addListener("data", this.handleEvent)` читается как «подписать мой обработчик».

**`bind` в рендере.** Возникает потому, что это работает: `this` привязан, код функционирует, дефекта в поведении нет. Цена невидима — новая идентичность колбэка на каждый рендер, то есть сломанная мемоизация у получателя (1.12, 3.11). Так появляется самый трудный для обнаружения класс проблем: код корректен и при этом систематически создаёт лишнюю работу. Отдельно стоит отметить, что `() => this.handle()` в `render` — та же ошибка; визуальное отличие от `bind` не меняет механизма.

**«Стрелочные функции всегда правильнее».** Возникает как вывод из того, что стрелка решает самую частую проблему — потерю `this` в колбэке. Обобщение неверно в трёх точках: стрелочный метод объекта берёт `this` не из объекта и обычно просто не работает; стрелочную функцию нельзя вызвать через `new`; `bind` и `call` на ней не действуют, то есть библиотека, вызывающая ваш колбэк с нужным `this`, передаст его в пустоту. Последний случай встречается именно в библиотеках со старым API — там, где стрелка кажется безопасным выбором.

**«`this` определяется местом объявления».** Возникает из опыта стрелочных функций: если весь код написан на стрелках, модель «лексический `this`» работает и кажется общей. Она верна только для стрелок. Для обычных функций и методов `this` определяется вызовом, и ровно это расхождение делает поведение legacy-кода непонятным: там стрелок нет, и модель не объясняет ничего.

**Стрелочное свойство класса без понимания цены.** Возникает как рецепт «так короче и всегда работает». Это верно, но свойство создаётся **на каждый экземпляр**: класс с восемью стрелочными методами создаёт восемь функций при каждом `new`. Для компонента, у которого экземпляров единицы, — несущественно; для объекта, создаваемого на элемент списка, — измеримо. Разбор — угол 6.

**Снятие подписки по новому результату `bind`.** Возникает из симметричного написания: добавляли с `.bind(this)`, снимаем с `.bind(this)`. Выражения выглядят одинаково, функции — разные объекты. Снятие молча не происходит. Это самая дорогая ошибка урока, потому что единственный её симптом — рост памяти.

**Попытка объяснить потерю `this` через область видимости.** Возникает естественно после 1.15: механизм поиска имён только что разобран, и `this` кажется ещё одним внешним именем. Он им не является (кроме стрелок), и рассуждение о scope не даёт ответа. Следующий шаг обычно — вывод «надо везде стрелочные функции», то есть рецепт вместо модели.

## 6. Trade-offs

### Стрелочное свойство класса против метода прототипа

| | Метод прототипа | Стрелочное свойство |
|---|---|---|
| где живёт функция | одна на класс, в прототипе | по одной на каждый экземпляр |
| память | не зависит от числа экземпляров | растёт линейно с числом экземпляров |
| `this` | определяется вызовом — можно потерять | лексический — потерять нельзя |
| переопределение в наследнике | обычное | поле наследника перезаписывает поле родителя, `super.method()` недоступен |
| видимость в прототипе | есть: виден в `Object.getPrototypeOf` | нет: обычное свойство экземпляра |

Решение по времени и количеству: экземпляров единицы (экран, сервис, клиент) — стрелочные свойства дешевле в сопровождении и цена памяти неизмерима. Экземпляров много (объект на элемент списка, модель на запись из ответа сервера) — методы прототипа, а привязка решается в месте передачи или не нужна вовсе.

Отдельный аргумент за прототип, не связанный с памятью: стрелочное свойство не видно в прототипе, поэтому его нельзя подменить или обернуть обычными средствами — ни в тесте, ни в декораторе. Для сервиса, который приходится мокать, это ощутимо (11.3).

### `bind` в конструкторе против стрелочного свойства

Практически эквивалентны: обе дают одну стабильную функцию на экземпляр. `bind` в конструкторе более явен (видно, что привязка произошла) и требует строки на каждый метод. Стрелочное свойство короче и прячет факт привязки. В существующем коде стоит следовать тому, что уже принято: смешение двух стилей в одном классе хуже любого из них.

### Класс против замыкания

| | Класс с `this` | Фабрика с замыканием |
|---|---|---|
| приватность | `#поля` или соглашение | настоящая: переменная недостижима извне (1.14) |
| проблема потери получателя | есть на каждой передаче метода | нет: функция не зависит от получателя |
| память на экземпляр | методы в прототипе — общие | каждая функция своя |
| знакомость модели | высокая | ниже для пришедших из ООП-языков |
| что удерживается | явные поля экземпляра | окружение целиком (1.14) |

Для кода, который будет передаваться колбэками, замыкание устраняет целый класс ошибок. Для объекта с большим числом методов и многими экземплярами класс экономнее по памяти. Для домена решение другое и обосновывается не этим, а поведением на границе сериализации — 1.17.

### Знание `this` против его использования

Содержательный trade-off этого урока: тема обязательна к **пониманию** и не обязательна к **применению**. Время, вложенное в чтение классового кода, окупается один раз; время, вложенное в написание нового кода на классах с `this`, в RN-проекте обычно не окупается — потому что приходит с проблемой привязки на каждой передаче и с плохим прохождением границ сериализации (1.17). Это не запрет: исключения — классы ошибок и обёртки вокруг API, которые сами построены на классах.

## 7. Связи с другими частями системы

**Назад:**

- **1.15** — `this` как часть контекста исполнения и единственное исключение из лексических правил; без этого противопоставления тема не читается;
- **1.14** — замыкание как альтернатива `this`: то же состояние, явный захват, нет получателя, который можно потерять;
- **1.12** — `bind` создаёт новую функцию, то есть новую идентичность: отсюда и сломанная мемоизация, и неработающее снятие подписки;
- **1.11** — классы ошибок как единственное место, где класс в RN-проекте оправдан почти всегда.

**Вперёд:**

- **1.17 Prototypes vs классы** — что делает `new` по шагам, где живут методы прототипа и почему доменные модели в RN лучше описывать типами и функциями;
- **3.11 Мемоизация** — цена нестабильного колбэка и где её стоит платить;
- **5.3 Диагностика лишних ре-рендеров** — как доказать, что причина в новой идентичности пропса;
- **5.8 Утечки памяти в RN** — неснятая подписка из-за несовпадения идентичности колбэка;
- **блок 09** — обёртки нативных модулей и emitter-ы: место, где потеря `this` встречается в новом коде;
- **11.3 Тестирование** — почему стрелочное свойство класса труднее подменить, чем метод прототипа.

**Главное, что должно остаться после урока.** Метод в JavaScript не принадлежит объекту: принадлежность создаётся формой вызова и живёт один вызов. Из этого следует и потеря `this` при передаче колбэком, и то, что любое решение проблемы — это создание функции, а значит вопрос о том, сколько функций и с какой идентичностью создаётся. Писать новый код с `this` для этого не требуется.
