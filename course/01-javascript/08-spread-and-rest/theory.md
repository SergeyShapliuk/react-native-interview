# 1.8 Spread и rest — theory

> 🟢 REFRESH. Spread — главный инструмент иммутабельных обновлений, и именно поэтому его границы надо знать точно. Две из них дают дефекты в React Native: глубина копирования и то, что уходит в компонент через `{...props}`.

## Refresh

### Spread объектов и массивов

```js
const next = { ...prev, done: true };
const list = [...items, newItem];
const merged = [...a, ...b];
```

Для объекта spread перебирает **собственные перечислимые** свойства и присваивает их значения в новый объект. Для массива — перебирает элементы по протоколу итератора.

Отсюда первое различие, о котором редко думают: spread массива работает с любым итерируемым значением, spread объекта — нет.

```js
[..."abc"];                // ["a", "b", "c"] — строка итерируема
[...new Set([1, 1, 2])];   // [1, 2] — Set итерируем
[...new Map([["a", 1]])];  // [["a", 1]] — пары
{ ...new Set([1, 2]) };    // {} — Set не имеет собственных перечислимых свойств
```

Последняя строка — рабочий способ потерять данные молча: `Set` в объектном spread превращается в пустой объект.

### Порядок перезаписи

Побеждает последний:

```js
{ ...defaults, ...fromServer, ...overrides }
```

Ключ со значением `undefined` **тоже перезаписывает** — это разобрано в 1.4 и стоит повторить, потому что на слиянии настроек это самая частая ошибка:

```js
({ ...{ limit: 20 }, ...{ limit: undefined } }).limit;  // undefined, не 20
```

Если нужно «не перезаписывать отсутствующим», spread для этого не подходит — нужна фильтрация ключей или слияние по полям с `??`.

### Глубина копирования — одна

```js
const copy = { ...course };
copy.meta === course.meta;   // true
```

Это определение операции, а не ограничение (1.4). Практически это значит: spread защищает от мутации **того уровня, который скопировал**, и ни одного уровня глубже.

### Rest

Rest собирает «всё остальное». Два места применения:

```js
// в деструктуризации объекта
const { id, ...rest } = lesson;      // rest — новый объект без id

// в деструктуризации массива
const [first, ...tail] = items;      // tail — новый массив

// в параметрах функции
function log(level, ...args) { }     // args — всегда настоящий массив
```

Два факта о rest в деструктуризации:

- **исходный объект не изменяется.** `const { id, ...rest } = lesson` не удаляет `id` из `lesson`; создаётся новый объект без этого ключа;
- **rest обязан быть последним.** `const { ...rest, id }` — синтаксическая ошибка.

Rest в параметрах заменил `arguments`, и это не косметика: `arguments` — не массив, у него нет методов массива, и в стрелочных функциях его нет вовсе. `...args` всегда настоящий массив.

### Spread и прототипы

Самая неочевидная граница. Spread копирует **собственные** свойства, то есть:

```js
class Lesson {
  constructor(id) { this.id = id; }
  isFinished() { return false; }
}

const lesson = new Lesson(1);
const copy = { ...lesson };

copy.id;                        // 1 — собственное свойство скопировано
copy.isFinished;                // undefined — метод живёт в прототипе
copy instanceof Lesson;         // false — прототип не скопирован
Object.keys(lesson);            // ["id"] — метода тут нет изначально
```

Экземпляр класса после spread превращается в обычный объект с теми же данными и без поведения. То же касается `Object.assign`, `JSON`-обхода и деструктуризации с rest.

Это ровно тот факт, из которого в 1.17 вырастет вывод: доменные модели в RN-проектах чаще описывают типами и чистыми функциями, а не классами. И он же объясняет, почему `instanceof` ненадёжен для данных, прошедших копирование или границу (1.2).

Геттеры spread **выполняет**, а не копирует: в новом объекте окажется вычисленное значение, а не геттер.

## RN relevance

### `{...props}` передаёт то, что не предполагалось

```jsx
function Card(props) {
  return <View {...props} />;
}
```

Удобно и опасно. В `View` уйдёт всё, что передал вызывающий, включая пропсы, которые этому компоненту не адресованы.

Что из этого следует в React Native:

- **лишние пропсы доходят до нативного view.** Часть игнорируется, часть вызывает предупреждение, а часть меняет поведение неожиданно: `onLayout`, `collapsable`, `testID`, `pointerEvents`, переданные «транзитом», начинают работать;
- **неявный контракт компонента.** По сигнатуре нельзя понять, что компонент принимает. Это ломается при рефакторинге: добавление пропса в вызове меняет поведение `View`, а не `Card`;
- **конфликт с собственными пропсами.** Порядок решает: `<View {...props} style={style} />` и `<View style={style} {...props} />` ведут себя по-разному, и второй вариант позволяет вызывающему случайно затереть внутренний стиль.

Это не означает «никогда не использовать spread пропсов». Для компонента-обёртки, который сознательно прозрачен (кнопка над `Pressable`, поле над `TextInput`), это правильный инструмент. Рабочее правило: **явный список для компонентов с собственным поведением, spread с `rest` после вытаскивания своих пропсов — для обёрток.**

```jsx
function Card({ title, onPress, ...rest }) {
  return (
    <Pressable onPress={onPress} {...rest}>
      <Text>{title}</Text>
    </Pressable>
  );
}
```

### Порядок в стилях решает, какой стиль победит

```jsx
<View style={{ ...base, ...overrides }} />
```

Последний побеждает — то же правило, что для объектов. Отсюда класс дефектов «стиль не применяется»: переопределение написано раньше базового стиля.

Специфика React Native: `style` принимает ещё и массив, и там правило то же (последний элемент выигрывает), но слияние выполняет сам RN, и отсутствующие значения не затирают предыдущие:

```jsx
<View style={[base, overrides]} />        // RN сливает сам
<View style={{ ...base, ...overrides }} /> // сливаем мы, и undefined затирает
```

Второй вариант опаснее именно из-за `undefined`: `{ ...base, ...{ padding: undefined } }` даст `padding: undefined` и уберёт отступ из `base`. В варианте с массивом такого не произойдёт.

Отдельно: `{ ...base }` создаёт **новый объект на каждый рендер** (1.4, 1.6), то есть новый пропс `style` для нативного компонента. Что с этим делать — `StyleSheet.create`, константы, мемоизация — блоки 03 и 05.

### Иммутабельные обновления и structural sharing

Spread — основной инструмент обновления состояния именно потому, что меняет ссылки только там, где его применили:

```js
const next = { ...course, lessons: [...course.lessons, newLesson] };
```

Новые: `course` и массив `lessons`. Прежние: все существующие элементы. Это то свойство, на которое опирается мемоизация (1.4, 1.13).

Обратная сторона — соблазн скопировать дерево целиком «на всякий случай». Каждый лишний уровень spread это лишние новые ссылки, то есть лишние перерисовки (разбор в 1.6, задание 1.5).

## Типичные заблуждения

**«Spread делает глубокую копию.»** Возникает потому, что на плоских объектах он от глубокой копии неотличим, а плоские объекты составляют большинство примеров. Расхождение проявляется на вложенности — то есть именно на состоянии реального экрана.

**«Порядок ключей в spread не важен.»** Возникает из того, что в большинстве слияний ключи не пересекаются, и порядок действительно не влияет. Как только появляется переопределение, порядок становится единственным, что определяет результат, — и ошибка выглядит как «стиль не применился» или «настройка не сработала», то есть не как ошибка порядка.

**«`...rest` исключает поля из исходного объекта.»** Возникает из формулировки «всё остальное», которая звучит как изъятие. Исходный объект не меняется; создаётся новый без перечисленных ключей. Заблуждение безвредно само по себе, но мешает понять, что rest — это ещё одна операция копирования со своей ценой.

**«Spread сохраняет методы.»** Возникает потому, что после spread объект выглядит так же в отладчике — поля на месте. Методы живут в прототипе и в число собственных свойств не входят, поэтому пропадают молча, и обнаруживается это при вызове метода на «копии».

**«Spread пропсов — это просто удобно.»** Возникает из того, что он действительно экономит код и в момент написания проблем не создаёт. Цена платится позже и другим человеком: контракт компонента перестаёт быть видимым по его сигнатуре, и предсказать последствия добавления пропса в одном месте становится невозможно без чтения всей цепочки.
