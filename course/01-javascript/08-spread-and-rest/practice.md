# 1.8 Spread и rest — practice

## Проверка понимания

---

**1. Что победит при `{ ...a, ...b }` на пересекающихся ключах?**

<details>
<summary>Ответ</summary>

Значение из `b`: при перезаписи побеждает последний источник. Важное дополнение — ключ со значением `undefined` в `b` тоже перезаписывает, то есть затирает корректное значение из `a`.

**Ответ «значение из `a`, оно же было первым»** вскрывает модель «первый выигрывает», которая встречается в некоторых системах слияния конфигов. Цена ошибки — переопределения, написанные не в том порядке, и дефект «стиль не применяется».

**Ответ «победит `b`, но `undefined` не затрёт»** вскрывает самый практически важный пробел. Именно на нём ломается слияние настроек: объект с явно отсутствующим полем уничтожает дефолт, и причина не видна в месте проявления.
</details>

---

**2. Что станет с вложенным объектом после spread?**

<details>
<summary>Ответ</summary>

Останется тем же объектом: `({ ...course }).meta === course.meta` даёт `true`. Spread копирует значения свойств, а значение поля с объектом — это ссылка. Глубина копирования — ровно один уровень.

**Ответ «скопируется тоже»** вскрывает пробел, дающий самый неприятный дефект в React: верхний уровень новый, вложенный тот же, и экран обновляется частично (1.4).

**Ответ «останется тем же, поэтому нужно глубокое копирование»** вскрывает неверный вывод из верного факта. Глубокое копирование создаёт новые ссылки для всех узлов, включая неизменившиеся, и ломает мемоизацию по всему дереву. Нужно не глубокое копирование, а новые ссылки **по пути изменения** (1.4, задание 1.5).
</details>

---

**3. Какие пропсы уйдут в нативный компонент при `{...props}`?**

<details>
<summary>Ответ</summary>

Все, которые передал вызывающий, — включая те, что адресованы не этому компоненту. Часть будет проигнорирована, часть вызовет предупреждение, а часть реально заработает: `onLayout`, `testID`, `pointerEvents`, `collapsable`, переданные транзитом, изменят поведение нативного view.

**Ответ «только те, которые компонент понимает»** вскрывает ожидание фильтрации, которой нет. Spread не знает, какие пропсы валидны для получателя, — он просто передаёт объект целиком.

**Ответ «все, и это нормально, так делают все обёртки»** частично верен для сознательно прозрачных обёрток, но вскрывает отсутствие различия между обёрткой и компонентом с собственным поведением. Во втором случае spread делает контракт невидимым по сигнатуре, и добавление пропса в вызове начинает менять поведение внутреннего `View`, а не самого компонента.
</details>

## Задание

**Дано.** Компонент карточки урока в RN-приложении и его использование. Карточка должна иметь собственный отступ и фон, а также передавать специфичные для нажатия пропсы дальше. На практике поведение не соответствует намерению.

```jsx
const baseStyle = { padding: 16, backgroundColor: "#fff", borderRadius: 8 };

function LessonCard(props) {
  const { lesson, theme } = props;

  return (
    <Pressable
      {...props}
      style={{ ...baseStyle, ...theme.card, ...props.style }}
    >
      <Text>{lesson.title}</Text>
    </Pressable>
  );
}
```

```jsx
<LessonCard
  lesson={lesson}
  theme={theme}
  onPress={open}
  style={{ padding: undefined }}
  analyticsId="lesson_card"
  testID="lesson-42"
/>
```

Дополнительно известно: `theme.card` для светлой темы равен `{}`, а `lesson` — экземпляр класса `Lesson` с методом `isFinished()`, и в карточке планируют его вызвать.

**Требуется.**

1. Перечислить все пропсы, которые дойдут до `Pressable`, и для каждого сказать, должны ли они там быть.
2. Объяснить, почему у карточки исчезает отступ, и назвать точную причину — не «переопределение», а механизм.
3. Объяснить, что произойдёт при попытке вызвать `lesson.isFinished()` внутри карточки, если `lesson` был получен не напрямую, а через `{ ...lessonFromStore }` где-то выше по цепочке.
4. Найти пропс, который приведёт к предупреждению или неожиданному поведению нативного view, и объяснить, почему он туда попал.
5. Переписать компонент. Для каждого решения назвать, что именно оно исправляет, и сказать, в каком случае исходный вариант со spread всех пропсов был бы корректным.

---

<details>
<summary>Разбор</summary>

**1. Что дойдёт до `Pressable`.**

| Пропс | Доходит | Должен ли |
|---|---|---|
| `onPress` | да | **да** — это и есть назначение `Pressable` |
| `testID` | да | **да** — валидный пропс, передача осмысленна |
| `style` | да, но затем переопределяется явным `style` ниже | см. пункт 2 |
| `lesson` | **да** | **нет** — доменный объект, `Pressable` о нём ничего не знает |
| `theme` | **да** | **нет** — объект темы, не пропс компонента |
| `analyticsId` | **да** | **нет** — собственный пропс приложения, см. пункт 4 |

Ключевое наблюдение: `const { lesson, theme } = props` **не удаляет** эти поля из `props` (1.7 — деструктуризация не изменяет источник). Разработчик вытащил их для использования и уверен, что «забрал» — а `{...props}` всё равно передаёт их дальше.

Это самая частая ошибка этого урока: деструктуризация читается как изъятие, а для исключения полей нужен rest.

**2. Почему исчезает отступ.**

```jsx
style={{ ...baseStyle, ...theme.card, ...props.style }}
```

`props.style` равен `{ padding: undefined }`. Spread присваивает **значение** ключа `padding`, и это значение равно `undefined`. Последний источник побеждает, поэтому в итоговом объекте окажется `padding: undefined`, затирая `padding: 16` из `baseStyle`.

Механизм, который нужно назвать точно: **spread не пропускает ключи с `undefined`, он их присваивает.** Отсутствие ключа и ключ со значением `undefined` для spread — разные вещи, хотя при чтении оба дают `undefined`.

Почему это особенно коварно в React Native: вариант с массивом стилей ведёт себя иначе.

```jsx
style={[baseStyle, theme.card, props.style]}
```

Слияние выполняет сам RN, и там `undefined` не затирает предыдущее значение. То есть замена объектного spread на массив не просто «другой синтаксис» — она меняет поведение на `undefined`.

**3. Про `lesson.isFinished()`.**

Если выше по цепочке `lesson` прошёл через `{ ...lessonFromStore }`, метода у него нет: `isFinished` объявлен в прототипе класса, а spread копирует только собственные свойства. Вызов даст `TypeError: lesson.isFinished is not a function`.

Что делает этот дефект трудным: в отладчике объект выглядит правильно — все поля на месте. Отсутствует только поведение, и обнаруживается это в момент вызова, то есть потенциально далеко от места копирования. Проверка `lesson instanceof Lesson` при этом вернёт `false`, хотя данные корректны.

Это прямой выход на 1.17: как только доменная модель проходит через spread, границу JS↔native (1.2) или персистентное хранилище, от класса остаются данные без поведения. Поэтому домен описывают типами и чистыми функциями — тогда «потеря методов» структурно невозможна.

**4. Пропс, вызывающий проблему на нативной стороне.**

`analyticsId`. Это собственный пропс приложения, у `Pressable` и у нативного view такого пропса нет. Он попал туда транзитом через `{...props}`, потому что компонент не отфильтровал свои пропсы.

Исход зависит от компонента и версии RN: в лучшем случае он будет проигнорирован, в типичном — вызовет предупреждение о неизвестном пропсе, в худшем — доедет до нативного view как неизвестный атрибут.

Отдельно стоит отметить `lesson` и `theme`: это объекты, и передача объекта в нативный компонент означает, что он попадёт на границу JS↔native. Доменный объект там не нужен и, если бы его попытались применить, частично потерялся бы (1.2). Здесь он просто бесполезен — но он создаёт лишнюю работу на каждый рендер и мешает понять, что компонент действительно принимает.

**5. Переписанный компонент.**

```jsx
const baseStyle = StyleSheet.create({
  card: { padding: 16, backgroundColor: "#fff", borderRadius: 8 },
});

function LessonCard({ lesson, theme, analyticsId, style, ...pressableProps }) {
  return (
    <Pressable
      {...pressableProps}
      style={[baseStyle.card, theme.card, style]}
    >
      <Text>{lesson.title}</Text>
    </Pressable>
  );
}
```

Что исправляет каждое решение:

- **rest вместо деструктуризации из `props`** — `lesson`, `theme` и `analyticsId` действительно исключены из того, что уходит дальше. Исправляет пункты 1 и 4;
- **`style` вытащен в отдельный параметр** — он больше не попадает в `pressableProps` дважды и применяется один раз, в контролируемом месте;
- **массив стилей вместо объектного spread** — `undefined` в `style` больше не затирает базовый отступ, потому что слияние выполняет RN. Исправляет пункт 2. Это именно исправление механизма, а не изменение порядка: порядок остался тем же;
- **`StyleSheet.create`** — стиль перестаёт быть новым объектом на каждый рендер. К теме урока это относится косвенно, но раз мы трогаем стили, оставлять инлайн-объект было бы непоследовательно (мемоизация и её цена — 3.8, 5.4);
- **`{...pressableProps}` перед `style`** — собственный `style` компонента применяется после, и вызывающий не может случайно затереть его целиком. Если прозрачность нужна, порядок меняют сознательно.

**Когда исходный вариант был бы корректным.** Если `LessonCard` — сознательно прозрачная обёртка без собственных пропсов и без собственного стиля, то есть компонент, вся задача которого — добавить одно поведение и передать остальное дальше. Например, кнопка над `Pressable`, добавляющая только haptic feedback:

```jsx
function HapticPressable(props) {
  return <Pressable {...props} onPress={withHaptic(props.onPress)} />;
}
```

Здесь spread всех пропсов правильный: контракт компонента совпадает с контрактом `Pressable`, и перечислять его заново значит дублировать чужой API и отставать от него при обновлении.

**Правило, которое стоит вывести:** spread всех пропсов корректен ровно тогда, когда компонент не имеет собственного контракта. Как только появляется хотя бы один собственный пропс или собственный стиль — нужен rest, иначе контракт перестаёт быть видимым по сигнатуре, и цену этого платит тот, кто будет менять компонент через полгода.
</details>
