# 1.1 Variables и scope — practice

## Проверка понимания

Цель — не оценка, а обнаружение пробела. У каждого вопроса указано, что вскрывает неверный ответ.

---

**1. Что выведет этот цикл и что изменится при замене `var` на `let`?**

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

<details>
<summary>Ответ</summary>

С `var` — `3, 3, 3`. `var i` — одна переменная на всю окружающую функцию; к моменту выполнения колбэков цикл закончен и `i === 3`.

С `let` — `0, 1, 2`. На каждой итерации создаётся новое связывание `i`, и колбэк каждой итерации видит своё.

**Неверный ответ `0, 1, 2` для `var`** вскрывает отсутствие модели «одна переменная vs новое связывание на итерацию» — то есть непонимание того, что колбэк не копирует значение, а смотрит на переменную. Это предпосылка для 1.14, и без неё stale closure в хуках будет выглядеть магией.

**Ответ «не помню, но знаю, что `let` правильнее»** вскрывает рецепт вместо механизма: правило применяется, но причина неизвестна, и в чуть другой формулировке задачи (цикл с `const` внутри, цикл с `forEach`) оно не сработает.
</details>

---

**2. Почему `const obj = {}; obj.a = 1` работает, а `obj = {}` — нет?**

<details>
<summary>Ответ</summary>

`const` фиксирует связь имени со значением. В переменной лежит ссылка на объект; присваивание `obj = {}` меняет саму эту связь и запрещено. `obj.a = 1` меняет содержимое объекта, на который ссылка указывает, — связь не затронута.

**Неверный ответ «`const` должен был запретить и это»** вскрывает перенос семантики `const` из другого языка. Практическое следствие ошибки — ожидание, что `const` защитит состояние от мутации, и отсутствие настоящей защиты там, где она нужна (1.13).

**Ответ «потому что объекты передаются по ссылке»** формально близок, но вскрывает смешение двух тем: передача по ссылке — про аргументы функций (1.12), а здесь дело в том, что именно фиксирует `const`.
</details>

---

**3. В чём разница между «переменная не объявлена» и «переменная в TDZ»?**

<details>
<summary>Ответ</summary>

«Не объявлена» — имени нет ни в одном доступном scope; `ReferenceError: x is not defined`. «В TDZ» — имя объявлено через `let` или `const` ниже в этом же блоке, уже поднято, но ещё не инициализировано; `ReferenceError: Cannot access 'x' before initialization`.

**Неверный ответ «это одно и то же, просто разные сообщения»** вскрывает то, что сообщения об ошибках читаются как шум. Практическая цена: при первой ошибке разработчик ищет опечатку в имени, при второй нужно искать порядок объявлений — это разные действия, и путаница стоит времени.
</details>

## Задание

**Дано.** Фрагмент из экрана RN-приложения. Он подписывается на набор событий и ведёт себя неверно: в лог всегда попадает имя последнего события, независимо от того, какое сработало.

```js
function subscribeAll(events, emitter) {
  const subscriptions = [];
  for (var i = 0; i < events.length; i++) {
    var name = events[i];
    subscriptions.push(
      emitter.addListener(name, (payload) => {
        console.log('событие:', name, payload);
      })
    );
  }
  return subscriptions;
}
```

**Требуется.**

1. Объяснить, почему в лог попадает последнее имя, а не имя сработавшего события. Ответ должен называть механизм, а не симптом.
2. Исправить двумя способами: заменой объявления и через явное создание отдельной области видимости (без `let`).
3. Объяснить, почему **оба** способа работают, и сказать, что у них общего.
4. Ответить: изменилось ли что-нибудь в том, когда освобождается память под `name`? Полный ответ — после 1.22, но гипотезу сформулировать сейчас.

---

<details>
<summary>Разбор</summary>

**1. Механизм.** `var name` — одна переменная на всю функцию `subscribeAll`, а не по одной на итерацию. Все колбэки, переданные в `addListener`, ссылаются на **одну и ту же** переменную. Цикл завершается до того, как сработает любое событие, и к этому моменту `name` хранит последнее значение. Колбэк не получил копию строки при создании — он смотрит в переменную в момент вызова.

Ключевая формулировка: проблема не в том, что значение «потерялось», а в том, что переменная **одна**.

**2. Способ первый — объявление.**

```js
for (let i = 0; i < events.length; i++) {
  const name = events[i];
  // ...
}
```

`let` в заголовке цикла создаёт новое связывание `i` на каждую итерацию, `const name` внутри блока — новое связывание `name` на каждую итерацию. Каждый колбэк смотрит в свою переменную.

**Способ второй — своя область видимости без `let`.**

```js
for (var i = 0; i < events.length; i++) {
  (function (name) {
    subscriptions.push(
      emitter.addListener(name, (payload) => {
        console.log('событие:', name, payload);
      })
    );
  })(events[i]);
}
```

Каждый вызов функции создаёт собственную область видимости, и параметр `name` в ней свой. Именно так эту задачу решали до 2015 года, и именно это встречается в старом коде проектов — узнавать конструкцию полезно.

**3. Что общего.** Оба способа делают одно и то же: обеспечивают **по одному связыванию на итерацию** вместо одного на всю функцию. `let` делает это на уровне языка, IIFE — через вызов функции. Отсюда вывод, который пригодится в 1.14: лечится не «асинхронность», а количество переменных.

**4. Память.** Гипотеза: в варианте с `var` все колбэки удерживают одно окружение, в варианте с `let` — каждый своё, и таких окружений столько, сколько подписок. Само по себе это не хуже и не лучше: пока подписки живы, живо и то, что они захватили, в обоих случаях. Значение имеет другое — **снимается ли подписка**. Возвращённый массив `subscriptions` существует именно для этого, и если вызывающая сторона его проигнорирует, окружения не освободятся при размонтировании экрана. Цепочку ссылок целиком разбираем в 1.22, снятие подписки в `useEffect` — в 1.14.
</details>
