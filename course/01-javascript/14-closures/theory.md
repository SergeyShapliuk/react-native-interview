# 1.14 Closures — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что такое замыкание» — а на вопрос, **что именно остаётся живым в памяти, пока жива функция, и какое значение она увидит в момент вызова.**

---

## 1. Что это

**Closure (замыкание)** — механизм, благодаря которому функция может обращаться к **lexical bindings** (связываниям имён) из внешних областей видимости и после того, как внешний вызов завершился. Не «функция, которая использует внешнюю переменную», а свойство самой функции: она сохраняет доступ к области, в которой была объявлена.

> **Рабочая модель урока:** «функция вместе с окружением, в котором объявлена» — код функции плюс доступ к окружению. Это удобная модель для рассуждений о свежести значений и об удержании памяти, и дальше в уроке используется она. Но это модель, а не описание реализации: движок вправе захватывать только те связывания, которые функция действительно использует, и физически удерживаемый объём может быть меньше «всего окружения». На выводы урока это не влияет, на чтение профиля памяти — влияет.

**Lexical environment (лексическое окружение)** — структура, в которой движок хранит связывания имён, созданные при входе в область видимости: параметры, объявленные переменные, внутренние функции.

Замыкание создаётся **в момент создания функции**, а не в момент первого обращения к внешней переменной и не при вызове. Любая функция, объявленная внутри другой области видимости, уже является замыканием — вопрос только в том, что именно в этом окружении есть.

```js
function makeCounter() {
  let count = 0;
  return () => ++count;      // замыкание создано здесь
}

const next = makeCounter();
next();   // 1
next();   // 2
```

`makeCounter` завершилась, её кадр в стеке снят, но `count` жив: на окружение ссылается возвращённая функция. Это первое наблюдение урока — **время жизни окружения определяется не завершением вызова, а наличием ссылок на него**.

### Чего замыкание не делает

Оно не копирует значения. В функции не лежит снимок `count === 0`; в ней лежит ссылка на окружение, где есть связывание `count`. Каждое обращение — чтение текущего состояния этого связывания.

Это различие — вся суть урока. Формулировка «замыкание запоминает значение» даёт неверные предсказания в обе стороны: и для stale closure, и для памяти.

## 2. Как это работает

### Ссылка на окружение, а не копия значений

```js
let value = 1;
const read = () => value;

value = 2;
read();     // 2 — не 1
```

Если бы замыкание копировало значение в момент создания, `read()` вернула бы `1`. Она возвращает `2`, потому что читает связывание в момент вызова.

Обратный случай, который кажется противоречием:

```js
function makeReaders() {
  const result = [];
  for (let i = 0; i < 3; i++) {
    result.push(() => i);
  }
  return result;
}
makeReaders().map((f) => f());   // [0, 1, 2]
```

Здесь каждая функция видит своё значение — но не потому, что скопировала его, а потому, что `let` в заголовке цикла создаёт **новое связывание на каждую итерацию** (1.1). Три функции — три разных окружения. С `var` окружение было бы одно, и результат был бы `[3, 3, 3]`.

Правило, которое снимает путаницу: **количество разных значений, которые видят замыкания, равно количеству связываний, а не количеству функций.**

### Что попадает в захваченное окружение

Замыкание удерживает окружение, а не перечисленные им переменные. Практически это значит: функция, использующая одно поле большого объекта, может удерживать весь объект, если он лежит в том же окружении связыванием.

```js
function createHandler(response) {
  const id = response.user.id;         // нужен только id
  return () => send(id);               // но в окружении есть и response
}
```

Насколько агрессивно движок обрезает неиспользуемые связывания — деталь реализации, и разная у разных движков (у Hermes своя, 4.5). Опираться на эту оптимизацию нельзя: правильная модель для принятия решений — «захвачено окружение целиком», и явный выход — не держать большой объект в том же окружении, что и долгоживущую функцию.

### Приватность через замыкание

```js
function createCache(limit) {
  const store = new Map();                    // недостижим извне

  return {
    get: (key) => store.get(key),
    set: (key, value) => {
      if (store.size >= limit) store.delete(store.keys().next().value);
      store.set(key, value);
    },
  };
}
```

`store` не является свойством возвращённого объекта: добраться до него можно только через методы. Это настоящая инкапсуляция на уровне языка, а не соглашение об именовании — и до приватных полей классов (1.17) это был основной способ её получить.

Цена: приватное состояние живёт, пока жив **любой** из возвращённых методов. Достаточно одной сохранённой ссылки на `get`, чтобы весь `store` остался в памяти.

### Два окружения с одинаковым кодом

```js
const a = createCounter();
const b = createCounter();
```

`a` и `b` — разные функции (разная идентичность, 1.12) с разными окружениями. Отсюда и ответ на вопрос из 1.12, почему идентичность функций нельзя выводить из кода: один и тот же код с разными окружениями — это разное поведение.

### Stale closure

**Stale closure (устаревшее замыкание)** — ситуация, когда функция читает связывание, которое для неё больше не обновляется, потому что окружение, где она была объявлена, относится к прошлому выполнению.

```jsx
function Screen() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);           // всегда 0
    }, 1000);
    return () => clearInterval(id);
  }, []);                           // окружение зафиксировано на первом рендере
}
```

Механизм без упоминания React: тело компонента — функция, которая выполняется заново; каждое выполнение создаёт **новое** окружение с новым связыванием `count`. Колбэк интервала был создан внутри первого выполнения и ссылается на первое окружение. Он не «видит старое значение» — он видит **актуальное значение своего связывания**, а оно больше никем не меняется.

Это важная переформулировка: stale closure — не ошибка замыкания, а следствие того, что функция живёт дольше, чем выполнение, в котором её создали.

### Замыкание удерживает память

```jsx
useEffect(() => {
  const sub = Keyboard.addListener("keyboardDidShow", () => {
    analytics.track("kbd", lessons.length);
  });
  // нет cleanup
}, []);
```

Цепочка достижимости:

```
нативный emitter (живёт всё время работы приложения)
    └─> запись о подписке
          └─> JS-колбэк
                └─> окружение эффекта
                      ├─> lessons (весь массив)
                      ├─> все пропсы и состояние этого рендера
                      └─> замкнутые функции и объекты
```

Компонент размонтирован, экран закрыт — но ни одно звено этой цепочки не разорвано. Пока emitter держит колбэк, живо всё окружение. Это и есть «утечка через замыкание»: утекает не функция, а то, до чего от неё можно дойти.

`cleanup` в эффекте разрывает первое звено — и дальше вся цепочка становится недостижимой целиком, одним действием. Полная модель достижимости — 1.22, сборка — 1.23.

## 3. Почему это важно

Замыкание — единственный механизм, которым функция может иметь состояние, не будучи методом объекта. Поэтому на нём стоит почти всё, что в современном JS-коде не написано классами: фабрики, обработчики с контекстом, частичное применение, модули-синглтоны, вся модель хуков.

И тот же механизм — главный источник двух классов дефектов, которые выглядят совершенно по-разному:

| Симптом | Что происходит на самом деле |
|---|---|
| колбэк ведёт себя по данным, которых уже нет на экране | функция жива дольше, чем выполнение, создавшее её окружение |
| потребление памяти растёт при переходах между экранами | живая ссылка на функцию делает достижимым всё захваченное окружение |

Это **один** механизм с двух сторон, и именно поэтому их разбирают вместе. Разработчик, который видит только первую сторону, исправляет stale closure добавлением зависимостей и не замечает, что подписка по-прежнему не снимается. Видящий только вторую — аккуратно пишет cleanup и не понимает, почему колбэк считает неверно.

## 4. Где это в React Native

Замыкание становится проблемой там, где функция живёт дольше, чем выполнение, её создавшее. В RN таких мест немного, и они все известны.

### Подписки на события платформы

```jsx
useEffect(() => {
  const show = Keyboard.addListener("keyboardDidShow", onShow);
  const state = AppState.addEventListener("change", onAppState);
  return () => {
    show.remove();
    state.remove();
  };
}, []);
```

`Keyboard` и `AppState` — объекты уровня приложения: они существуют с момента загрузки JS-бандла и до завершения процесса. Подписка на них — это передача ссылки на ваш колбэк в структуру, которая переживёт любой экран. Отсюда правило: **каждая подписка на объект уровня приложения обязана иметь снятие**, и это не стилистика, а арифметика времени жизни.

### Emitter нативного модуля

```jsx
useEffect(() => {
  const sub = NativeEventEmitter.addListener("ProgressChanged", (e) => {
    setProgress(e.value);
  });
  return () => sub.remove();
}, []);
```

Здесь добавляется специфика RN: ссылка на колбэк может удерживаться **нативной стороной**, а не JS-структурой. Для JS-сборщика это означает корень достижимости вне JS-кучи — объект жив, хотя ни один JS-модуль на него не ссылается (1.22, блок 09). В дереве снимка памяти такая ссылка не всегда выглядит очевидно, и именно поэтому утечки такого рода находят последними.

### Таймеры

```jsx
const id = setInterval(tick, 1000);
```

`setInterval` без `clearInterval` — живой колбэк навсегда: интервал сам по себе не завершается. Хуже — таймер, перезапускающий себя из колбэка: отменять нужно последний запланированный идентификатор, и забыть это легко.

### Колбэки сетевого слоя и промисы

Промис, который ещё не разрешился, удерживает свои колбэки, а они — окружение. Запрос, стартовавший при открытии экрана, после ухода с экрана продолжает удерживать всё, что замкнул его `.then`, пока не завершится (1.18, отмена — 7.3).

### Обработчики жестов и анимаций

Колбэк, переданный в нативный gesture handler или в драйвер анимации, живёт в структуре, принадлежащей не компоненту. Размонтирование компонента само по себе эту ссылку не снимает.

### Почему в RN цена выше, чем в веб-приложении

В браузере закрытие таба освобождает всё. Мобильное приложение живёт днями: пользователь открывает и закрывает десятки экранов за сессию, и каждый неснятый обработчик накапливается. На устройстве с 2 ГБ памяти это заканчивается не «медленно», а принудительным завершением приложения системой — и в crash-репорте выглядит как краш без стектрейса (1.22, 10.7).

## 5. Типичные ошибки

**«Замыкание копирует значения в момент создания».** Возникает из опыта языков с явным захватом по значению и из того, что на большинстве примеров модель даёт тот же ответ: если захваченная переменная больше не меняется, копия и ссылка неразличимы. Расхождение появляется ровно там, где она меняется — то есть в асинхронном коде. Практическая цена двойная: предсказания про stale closure оказываются неверными, и рассуждение о памяти ломается полностью — «копия значения» освобождается, а живое окружение нет.

**«После размонтирования компонента его замыкания освобождаются».** Возникает из привязки времени жизни к компоненту: размонтирование воспринимается как освобождение всего, что относилось к экрану. Но достижимость не знает про компоненты. Если ссылка на колбэк лежит в emitter-е уровня приложения, размонтирование не меняет ничего: колбэк по-прежнему достижим из корня, и всё захваченное окружение вместе с ним. Освобождает не размонтирование, а **снятие ссылки**.

**«Проблема stale closure решается добавлением зависимости».** Возникает потому, что в большинстве случаев это действительно работает, и совет легко запоминается как универсальный. Он неверен в двух ситуациях. Первая: пересоздание эффекта обходится дорого само по себе — подписку надо снять и создать заново, таймер сбросить, запрос повторить; если зависимость меняется часто, цена пересоздания превышает выгоду. Вторая, более важная: колбэку нужно **актуальное** значение, но его изменение **не должно** приводить к пересозданию подписки. Эти два требования взаимно исключают друг друга в рамках массива зависимостей, и тогда правильный ответ — не зависимость, а ref (угол 6; рецептура — 3.5 и 3.9).

**Захват большого объекта в долгоживущем колбэке.** Возникает из естественного стиля: внутри эффекта используется то, что лежит в области видимости, и нет повода думать о размере. Долгоживущий колбэк превращает «удобно» в «удерживается до конца сессии». Выход — замыкать минимум: не объект, а вычисленное из него значение, и не в том же окружении, где лежит сам объект.

**Подписка без снятия.** Возникает чаще всего не от незнания, а от структуры кода: подписка создаётся в одном месте, а cleanup — в другом, и при правке первого про второе забывают. Отдельный источник — подписка, созданная условно (`if (enabled) subscribe()`): cleanup написан, но снимает не то, что было создано, или не вызывается на той ветке.

**Опора на то, что движок обрежет неиспользуемые связывания.** Возникает из прочитанного про оптимизации движков. Обрезка существует, но она не является контрактом языка и различается между движками и версиями. Решение, корректность которого зависит от оптимизации, — не решение.

## 6. Trade-offs

### `useRef` против замыкания: свежесть против предсказуемости

Два способа дать долгоживущему колбэку доступ к меняющимся данным.

| | Замыкание с зависимостями | Значение через ref |
|---|---|---|
| что видит колбэк | значение того выполнения, в котором он создан | текущее значение на момент вызова |
| предсказуемость | высокая: «что замкнуто, то и видно» | ниже: результат зависит от момента вызова |
| цена изменения данных | пересоздание колбэка и всего, что на нём держится | ничего не пересоздаётся |
| где ломается | частые изменения → частое пересоздание подписок | чтение ref в теле рендера даёт несогласованный UI |

Содержательная формулировка выбора: **замыкание даёт согласованный снимок, ref даёт актуальное значение.** Это разные гарантии, и ни одна не «лучше».

Снимок нужен там, где важна согласованность: колбэк должен отработать по тем данным, при которых был создан — иначе обработчик нажатия отправит одно, а пользователь видел другое. Актуальное значение нужно там, где колбэк — долгоживущий слушатель, которому нужно последнее состояние, а пересоздавать подписку на каждое изменение нельзя.

Цена ref — потеря согласованности как свойства: два чтения в одном колбэке могут дать разные значения, если между ними есть `await`. Эта цена реальна, и поэтому ref — не упрощение, а другой контракт. Применение в React — 3.9.

### Приватность через замыкание стоит памяти

Фабрика с приватным состоянием даёт настоящую инкапсуляцию, но связывает время жизни состояния с временем жизни **любого** возвращённого метода. Альтернатива — явная структура данных, передаваемая в чистые функции: время жизни видно в коде, приватности нет. Для домена второе обычно предпочтительнее (1.17), для кэша и соединения — первое.

### Глубокая вложенность функций

Каждый уровень вложенности — ещё одно окружение в цепочке. Плюс: контекст доступен без передачи параметров. Минус: удерживается больше, и непонятно, что именно — по коду внутренней функции не видно, какой объём она держит. Практическое следствие: чем длиннее живёт функция, тем ближе к плоскому должно быть её объявление.

### Явный захват вместо неявного

```js
// неявно: захвачено окружение, где лежит response целиком
const handler = () => send(response.user.id);

// явно: захвачено одно число, response в окружении колбэка нет
const { id } = response.user;
const handler = () => send(id);
```

Второй вариант добавляет строку и убирает неопределённость в том, что удерживается. Для короткоживущего колбэка это лишний код; для подписки, живущей всю сессию, — разница между удержанием числа и удержанием ответа сервера.

## 7. Связи с другими частями системы

**Назад:**

- **1.1** — связывания и область видимости: «одна переменная на функцию» против «новое связывание на итерацию» — тот же механизм, что здесь определяет, сколько окружений создано;
- **1.12** — функция как объект с идентичностью; теперь видно, почему идентичность нельзя выводить из кода: окружения разные;
- **1.10** — модуль как singleton: окружение модуля создаётся один раз, и функция, объявленная на верхнем уровне, замыкает окружение, живущее всё время работы приложения.

**Вперёд:**

**Главное, что должно остаться после урока.** Функция обращается к связываниям внешних областей видимости, а не к копиям значений, снятым при её создании. Из этого следует всё: и то, какое значение она увидит при вызове, и то, что останется достижимым в памяти, пока на неё кто-то ссылается (1.22). Вопрос «почему колбэк считает неверно» и вопрос «почему память растёт» — два вопроса об одном механизме.
