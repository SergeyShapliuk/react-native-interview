# 1.25 Числа, даты и строки на устройстве — theory

> 🟢 REFRESH. Числа, даты и строки вы используете каждый день. Ось урока — три места, где они теряют смысл **молча**: сумма расходится с сервером на копейку, дата сдвигается на день у пользователя в другом часовом поясе, лимит поля считает не то, что видит человек. Ни одно из них не падает, поэтому все три доживают до продакшена.

Все результаты в примерах получены в Node (V8). Там, где поведение на устройстве может отличаться, это сказано отдельно.

## Refresh

### Числа: двоичная плавающая точка

`number` — 64-битное число с плавающей точкой (IEEE 754). Дробная часть хранится в двоичном виде, и большинство десятичных дробей в нём точно не представимы — так же, как 1/3 не записывается конечной десятичной дробью.

```js
0.1 + 0.2;            // 0.30000000000000004
0.1 + 0.2 === 0.3;    // false
1.1 * 3;              // 3.3000000000000003
4.35 * 100;           // 434.99999999999994
```

Это не особенность JavaScript: так ведёт себя `double` в любом языке. Особенность JavaScript в том, что другого числового типа для дробей в языке нет, и значение с копейками по умолчанию оказывается в `number`.

Ошибка маленькая, но она **накапливается и меняет результат округления** — а в деньгах важен именно результат округления.

### `toFixed` — форматирование, а не округление

```js
(1.005).toFixed(2);              // "1.00", а не "1.01"
Math.round(1.005 * 100) / 100;   // 1 — тот же эффект
1.005 * 100;                     // 100.49999999999999
typeof (1).toFixed(2);           // "string"
```

Литерал `1.005` в памяти — чуть меньше, чем 1.005, и `toFixed` честно округляет то, что хранится. Отсюда два факта:

- `toFixed` возвращает **строку**. Результат пригоден для показа, а не для дальнейшей арифметики: `parseFloat(x.toFixed(2))` возвращает обратно в `number` с той же проблемой;
- округление «половина вверх» на дробях вида `x.xx5` работает непредсказуемо: в одних случаях число хранится чуть больше границы, в других — чуть меньше.

### Деньги — в минимальных единицах

Целые числа в `number` точны (до границы ниже), поэтому деньги хранят **целым числом минимальных единиц**: копеек, центов.

```js
const priceMinor = 29990;                         // 299,90 ₽
const discountedMinor = Math.round(priceMinor * 85 / 100);   // 25492 — 254,92 ₽
```

Сравните с расчётом в рублях:

```js
(299.90 * (1 - 15 / 100)).toFixed(2);   // "254.91"
```

Правильный ответ при округлении половины вверх — 254,92: точное значение 254,915, а в `number` оно хранится как 254,91499999999996. Копейка разницы — это уже не отображение, а сумма платежа.

Даже в целых единицах остаётся решение, которое нельзя принять на клиенте в одиночку: **правило округления**. Половина вверх, банковское округление, округление вниз в пользу покупателя — это бизнес-правило, и оно должно совпадать с сервером. Поэтому надёжная схема для денег: сумму считает сервер и присылает её в минимальных единицах (или строкой десятичного числа), клиент только показывает.

### Граница точности целых

Целые точны до `Number.MAX_SAFE_INTEGER` — 2⁵³ − 1, то есть 9007199254740991. Выше часть целых непредставима:

```js
9007199254740993;                                // 9007199254740992
Number.isSafeInteger(9007199254740993);          // false
JSON.parse('{"id":9007199254740993}').id;        // 9007199254740992 — молча
```

Последняя строка — то, как это встречается в RN: бэкенд отдаёт 64-битный идентификатор числом, `JSON.parse` превращает его в соседний, и приложение запрашивает чужую запись. Ошибки нет ни на одном шаге. Большие идентификаторы передают строкой (1.2).

### Разбор пользовательского ввода

```js
Number('1,5');        // NaN
parseFloat('1,5');    // 1 — молча отбросил всё после запятой
Number('');           // 0
Number(' ');          // 0
parseFloat('1.5abc'); // 1.5
Number('1 000');      // NaN
```

Два способа ошибиться в противоположные стороны. `Number` строгий, но превращает пустое поле в `0`. `parseFloat` разбирает префикс и тихо теряет всё, что не понял, — в том числе дробную часть, введённую через запятую.

В русской локали десятичный разделитель — запятая, и цифровая клавиатура с дробной частью на устройстве обычно показывает именно её. Разбор ввода поэтому начинается с нормализации:

```js
function parseAmount(input) {
  const s = input.replace(/[\s ]/g, '').replace(',', '.');
  if (s === '') return null;               // пустое поле — не ноль
  const n = Number(s);
  return Number.isFinite(n) ? n : null;
}

parseAmount('1,5');          // 1.5
parseAmount(' 1 000,25 ');   // 1000.25
parseAmount('');             // null
parseAmount('1,5,2');        // null
```

### Даты: `Date` — это момент, а не день

`Date` хранит одно число — миллисекунды от 1 января 1970 года по UTC. Это **момент времени**, одинаковый для всех на планете. «Какое это число месяца» — уже не свойство значения, а вопрос «в каком часовом поясе смотреть»: методы `getDate`, `getHours`, `toLocaleDateString` отвечают на него по поясу устройства, `getUTCDate` — по UTC.

### ISO-строка с временем и без

Стандарт задаёт правило, которое помнят немногие:

```js
new Date('2026-10-06');        // полночь по UTC
new Date('2026-10-06T00:00');  // полночь по местному времени устройства
```

Это **разные моменты**. На устройстве в Москве (UTC+3):

```js
new Date('2026-10-06').toISOString();        // "2026-10-06T00:00:00.000Z"
new Date('2026-10-06T00:00').toISOString();  // "2026-10-05T21:00:00.000Z"
```

А на устройстве в Нью-Йорке первая строка — это 20:00 **пятого** октября по местному времени, и `toLocaleDateString` покажет 5 октября. Дата, пришедшая с сервера строкой `YYYY-MM-DD`, у всех пользователей западнее Гринвича показывается предыдущим днём.

Строки не в ISO-формате (`'06.10.2026'`, `'2026/10/06'`, `'2026-10-06 10:00'` с пробелом) стандарт не описывает, и движки разбирают их по-разному. То, что разобрал V8 в браузере или в Node, Hermes может вернуть как `Invalid Date`. Разбирать стоит только ISO-строки — или вручную.

### Часовой пояс и летнее время

В поясах с переходом на летнее время сутки бывают длиной 23 и 25 часов. Устройство в Нью-Йорке, 1 ноября 2026 года — день перехода на зимнее время:

```js
const a = new Date(2026, 9, 31, 12);                  // 31 октября, 12:00
new Date(a.getTime() + 24 * 60 * 60 * 1000);           // 1 ноября, 11:00
const b = new Date(a); b.setDate(b.getDate() + 1);     // 1 ноября, 12:00
(b - a) / 3600000;                                     // 25
```

«Плюс 24 часа» и «то же время завтра» — разные операции. Первая — арифметика моментов, вторая — арифметика календаря. Напоминание «каждый день в 9:00», посчитанное прибавлением 24 часов, после перехода начнёт приходить в 8:00 или в 10:00.

В России сезонного перевода часов нет с 2011 года (в 2014-м был один разовый переход на постоянное зимнее время), поэтому команда с устройствами в московском поясе этот класс ошибок не увидит никогда — его увидят пользователи в других странах.

### Календарная дата — отдельный тип данных

День рождения, дедлайн дня, «день урока» — не моменты. У них нет времени и нет пояса: 6 октября должно оставаться 6 октября у любого пользователя. Хранить такое значение в `Date` — значит выбирать произвольный момент внутри дня и потом бороться с тем, что в другом поясе он попадает в другой день.

Рабочее представление — строка `YYYY-MM-DD` или тройка чисел, отдельно от моментов:

```js
// сегодняшний день по часам устройства
function todayLocal(d = new Date()) {
  const mm = String(d.getMonth() + 1).padStart(2, '0');
  const dd = String(d.getDate()).padStart(2, '0');
  return `${d.getFullYear()}-${mm}-${dd}`;
}

// типичная ошибка: это день по UTC, а не по часам устройства
new Date().toISOString().slice(0, 10);
// в Москве в 01:00 шестого октября вернёт "2026-10-05"
```

У формата с нулями есть приятное свойство: строки сравниваются как даты (`'2026-10-06' < '2026-10-10'`). Без нулей — уже нет: `'2026-9-6' < '2026-10-10'` даёт `false`.

Разницу в днях между календарными датами считают через `Date.UTC`, где летнего времени нет, а не делением разницы местных моментов на 86400000.

### Арифметика и сравнение моментов

`d1 === d2` сравнивает ссылки на объекты (1.12), а не моменты. `d1 < d2` работает, потому что `<` приводит оба `Date` к числу (1.3). Надёжная запись — сравнивать `getTime()`, а хранить и передавать момент — числом epoch-миллисекунд или ISO-строкой с `Z` или явным смещением.

### Строки: UTF-16 и `length`

Строка в JavaScript — последовательность **кодовых единиц UTF-16**. Символы за пределами первых 65536 (эмодзи, часть иероглифов) занимают две единицы — суррогатную пару. Эмодзи с модификатором тона кожи, флаги и «семьи» — это несколько кодовых точек, которые пользователь видит одним знаком.

| Строка | `length` (кодовые единицы) | `[...s].length` (кодовые точки) | Видимых символов (графем) |
|---|---|---|---|
| `'👍🏽'` | 4 | 2 | 1 |
| `'🇷🇺'` | 4 | 2 | 1 |
| `'👨‍👩‍👧'` | 8 | 5 | 1 |

`length` не считает ни то, ни другое из того, что имеет в виду человек.

### Разрезание посреди символа

`slice` режет по кодовым единицам и не знает, где кончается символ:

```js
'Ок👍'.slice(0, 3);     // "Ок\ud83d" — половина суррогатной пары
'Ок👍🏽'.slice(0, 4);    // "Ок👍" — тон кожи молча потерян
```

Одинокая половина пары рисуется знаком замены `�`, а `encodeURIComponent` на такой строке бросает `URIError: URI malformed` — то есть обрезанный комментарий может сломать запрос.

`Array.from(s)` или `[...s]` режут по кодовым точкам: половин пар не бывает, но составной символ всё равно можно разрезать (`Array.from('Ок👍🏽').slice(0, 3).join('')` снова даёт `'Ок👍'`).

### Графемы

То, что пользователь воспринимает как один символ, называется **графемой** (grapheme cluster). Стандартный способ их посчитать — `Intl.Segmenter`:

```js
const seg = new Intl.Segmenter('ru', { granularity: 'grapheme' });
[...seg.segment('👨‍👩‍👧')].length;   // 1
```

В RN с ним две оговорки. По документации Hermes `Intl.Segmenter` не входит в список реализованных API, а базовый `tsconfig` React Native не включает в `lib` его описание — `tsc` сообщит, что свойства `Segmenter` у `Intl` нет. Поэтому код, использующий его, проверяет наличие (`typeof Intl.Segmenter === 'function'`) на своей версии движка и имеет запасной вариант — библиотеку сегментации или подсчёт по кодовым точкам как приближение.

### Сравнение и сортировка по локали

`sort()` без компаратора сравнивает кодовые единицы, а это порядок таблицы Unicode, а не алфавита:

```js
['яблоко', 'ёж', 'Банан', 'арбуз'].sort();
// ['Банан', 'арбуз', 'яблоко', 'ёж'] — заглавные раньше строчных, «ё» после «я»

['яблоко', 'ёж', 'Банан', 'арбуз'].sort((a, b) => a.localeCompare(b, 'ru'));
// ['арбуз', 'Банан', 'ёж', 'яблоко']
```

Для сортировки большого списка удобнее один `Intl.Collator`, созданный заранее: `localeCompare` с локалью на каждом сравнении делает ту же работу заново. У `Collator` есть полезная опция `numeric: true` — с ней «Урок 2» стоит перед «Урок 10».

### Нормализация

Одна и та же буква может быть записана по-разному: `'й'` — одной кодовой точкой или парой «и» + комбинируемая кратка.

```js
const composed = 'й';
const decomposed = 'й';
composed === decomposed;                                     // false
composed.normalize('NFC') === decomposed.normalize('NFC');   // true
```

Разложенная форма приходит из вставленного текста, из имён файлов, из других приложений. Поиск, который не нормализует обе стороны, не находит то, что пользователь видит на экране. Отдельно — «ё» и «е»: для поиска их обычно приравнивают явно, потому что `includes` их различает, а `localeCompare` с `sensitivity: 'base'` считает равными.

### `Intl` в Hermes

Hermes не встраивает собственную библиотеку ICU, а использует средства платформы: на Android — Java-API, на iOS — Foundation. Документация движка прямо называет цену решения: поведение на Android и iOS может различаться, а на Android — ещё и между версиями системы. По той же документации реализованы `Intl.Collator`, `Intl.NumberFormat`, `Intl.DateTimeFormat`, `localeCompare` и методы `toLocale*String`; `formatToParts` у `NumberFormat` — только на Android; `Intl.Segmenter`, `Intl.PluralRules`, `Intl.RelativeTimeFormat` и `Intl.ListFormat` в списке поддерживаемых не значатся.

Практическое правило: наличие API и формат результата проверяются на устройствах своей версии движка, а не по таблице браузеров и не в Jest — тесты идут в Node с полной ICU, и там всё работает.

Отдельная ловушка форматирования: в русской локали группы разрядов разделяет неразрывный пробел (`new Intl.NumberFormat('ru-RU').format(1234567)` в Node — `"1 234 567"`, где между группами `U+00A0`), а на конкретной платформе разделитель может отличаться. Отформатированную строку нельзя сравнивать с литералом в тесте и нельзя разбирать обратно в число.

## RN relevance

### Лимит поля считает не то, что видит пользователь

`maxLength` у `TextInput` ограничивает длину нативной строки, а она на обеих платформах считается в кодовых единицах UTF-16 — так же, как `length` в JS. Поле с `maxLength={140}` примет 140 букв, 70 простых эмодзи и 35 эмодзи с тоном кожи. Пользователь видит «я ввёл 40 знаков, а поле больше не пишет».

Счётчик `{text.length}/140` с этим лимитом согласован, но с восприятием человека — нет. Счётчик графем, наоборот, согласован с человеком, но не с `maxLength`. Решение начинается с вопроса, **что считает сервер**: многие серверные языки и базы данных считают длину строки в кодовых точках, и это третья мера. Лимит, счётчик и проверка на сервере должны использовать одну меру, иначе одно из трёх мест откажет там, где другие пропускают.

Обрезка превью — та же проблема: `text.slice(0, 100) + '…'` оставляет в конце знак замены или теряет модификатор эмодзи.

### Дата из ответа сервера сдвигается на день

Дедлайн, дата следующего списания, день урока приходят строкой `'2026-11-01'`. `new Date(s).toLocaleDateString()` у пользователя в Европе и Азии восточнее Гринвича покажет 1 ноября, в Америке — 31 октября. В команде, где все устройства в московском поясе, этот дефект не воспроизводится: его находят пользователи или тест со сменой часового пояса на устройстве.

### Сумма расходится с сервером

Цена со скидкой, посчитанная на клиенте в `number` с дробной частью, расходится с суммой на сервере на копейку на части тарифов. Если клиент отправляет эту сумму в платёж, это отказ или несовпадение суммы в чеке с суммой на экране. Если показывает — пользователь видит одну цену, а платит другую.

### Сортировка и поиск

Список курсов, отсортированный `sort()`, ставит курсы с заглавной буквы раньше всех строчных, а «Ёлочные игрушки» — после «Я». Поиск без нормализации не находит текст, вставленный из другого приложения.

### `Intl` на устройстве

Форматирование цены, даты и сортировка зависят от того, как их реализует Hermes на конкретной платформе. Тест в Jest, проверяющий формат строки, проходит в Node и ничего не говорит об устройстве. Хуже того — он может закрепить формат, которого на устройстве не будет.

### Нативная граница

`Date` нативную границу не переходит (1.2): момент передают epoch-миллисекундами или ISO-строкой со смещением, календарную дату — строкой `YYYY-MM-DD`. Выбор представления — часть контракта модуля, а не деталь реализации.

> **Не дублировать:** какие значения переходят нативную границу — [1.2](../02-data-types-and-the-js-native-boundary/); приведение в арифметике и сравнениях — [1.3](../03-coercion-and-comparison/); проверка формата дат и денег в ответе сервера — 2.12; единицы измерения как типы — 2.16; Hermes как движок — 4.5; длина строк и dynamic type в accessibility — 4.11.

## Типичные заблуждения

**«`toFixed(2)` правильно округляет деньги.»** Возникает потому, что на большинстве значений результат совпадает с ожидаемым. `toFixed` округляет значение, которое хранится в памяти, а оно на дробях вида `x.xx5` бывает чуть меньше записанного. И главное — `toFixed` возвращает строку для показа; сумма для платежа должна быть целым числом минимальных единиц и, в идеале, посчитана сервером.

**«`new Date('2026-10-06')` — это шестое октября у всех пользователей.»** Это полночь по UTC, то есть момент, который в западных часовых поясах приходится на пятое октября. Заблуждение держится потому, что разработчик проверяет на устройстве в своём поясе, где всё совпадает.

**«`length` строки — это число символов.»** Это число кодовых единиц UTF-16. Для кириллицы и латиницы они совпадают с символами, поэтому ошибка не видна до первого эмодзи, флага или составной буквы.

**«`sort()` подходит для сортировки названий на русском.»** `sort()` сравнивает коды символов: заглавные идут раньше строчных, «ё» — после «я». Для текста, который читает человек, нужен `localeCompare` или `Intl.Collator`.

**«Если в браузере `Intl` работает, то и в RN работает так же.»** Hermes реализует `Intl` через средства платформы, часть API в нём отсутствует, а формат результата может различаться между Android и iOS. Проверять нужно на устройстве — не в браузере и не в Jest.
