# 1.19 async/await — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «как дождаться результата» — а на вопрос, **что именно происходит с функцией в точке `await`, что в это время делает поток и почему последовательный на вид код теряет параллельность и ошибки.**

---

## 1. Что это

`async` и `await` — синтаксис над промисами (1.18). Нового механизма асинхронности они не добавляют: любой `async/await`-код выразим через `then`, и наоборот.

**`async` перед функцией** делает две вещи:

1. функция **всегда** возвращает промис — даже если внутри нет ни одного `await` и ни одной асинхронной операции;
2. внутри функции разрешён `await`.

```js
async function f() {
  return 1;
}
f();          // Promise { 1 }, не 1
f() === 1;    // false
```

Если `async`-функция бросает исключение, она не бросает его наружу — она **возвращает rejected-промис**. Это ключевое отличие от обычной функции, и из него растёт половина ошибок урока.

```js
async function f() {
  throw new Error("boom");
}
// наружу ничего не вылетает; f() — это Promise в состоянии rejected
```

**`await` перед выражением** — точка приостановки. Он:

1. вычисляет выражение (если это не промис — оборачивает значение в уже завершённый промис);
2. приостанавливает выполнение **этой функции**;
3. возвращает управление вызывающему коду;
4. когда промис станет `fulfilled` — возобновляет функцию, подставляя значение;
5. когда промис станет `rejected` — возобновляет функцию, бросая причину в точке `await`.

Пункт 5 — то, что позволяет писать `try/catch` вокруг асинхронного кода: отказ промиса превращается в обычное исключение **в этом месте этой функции**.

### Чем `await` не является

**Не блокировкой** — поток не простаивает, он выполняет всё остальное, что у него есть (угол 2). **Не запуском работы** — она началась при создании промиса (1.18), `await` только ждёт. **Не потоком и не сопрограммой ОС** — приостановка функции это работа движка, а не планировщика системы.

## 2. Как это работает

### `await` разрезает функцию на части

До первого `await` тело `async`-функции выполняется **синхронно**, как обычный код. В точке `await` функция возвращает управление, а всё, что идёт после, превращается в продолжение — колбэк, подписанный на промис.

```js
async function load() {
  console.log("1");             // синхронно, прямо при вызове load()
  const a = await getA();       // точка приостановки
  console.log("2");             // продолжение — выполнится позже
  return a;
}

console.log("0");
load();
console.log("3");
// 0, 1, 3, 2
```

Эквивалент через `then`, показывающий, что именно произошло:

```js
function load() {
  console.log("1");
  return getA().then((a) => {
    console.log("2");
    return a;
  });
}
```

Отсюда следует то, из-за чего `await` так часто понимают неверно: **между строкой `const a = await getA()` и следующей строкой проходит время, в течение которого выполнялся другой код.** Состояние мира между ними могло измениться: компонент размонтировался, пользователь ушёл на другой экран, данные обновились, токен истёк.

Продолжение — это замыкание (1.14): оно удерживает все локальные переменные функции и всё, что они держат. Пока промис `pending`, продолжение живо и держит окружение. Стек вызовов при приостановке раскручивается, и восстановить его нельзя — поэтому в стектрейсе ошибки из асинхронного кода не видно того, кто вызвал функцию изначально (1.15, и практические следствия в 10.6).

### Независимые `await` подряд теряют параллельность

```js
// последовательно: суммарное время = t1 + t2
const course = await api.getCourse(id);
const progress = await api.getProgress(id);
```

Второй запрос **создаётся** только после возобновления функции, то есть после завершения первого. Параллельности нет, хотя запросы друг от друга не зависят.

```js
// параллельно: суммарное время = max(t1, t2)
const coursePromise = api.getCourse(id);      // работа началась
const progressPromise = api.getProgress(id);  // работа началась
const course = await coursePromise;
const progress = await progressPromise;
```

Оба промиса созданы до первого `await` — значит, обе операции уже выполняются, и `await` только собирает результаты. Это та же мысль, что и в 1.18: комбинатор или `await` не распараллеливают работу, они ждут уже запущенную.

Эквивалентная и более читаемая форма:

```js
const [course, progress] = await Promise.all([api.getCourse(id), api.getProgress(id)]);
```

Разница между этими двумя параллельными вариантами **не стилистическая** — она в обработке ошибок, и это тема угла 6.

Когда последовательность обязательна: второй вызов использует результат первого.

```js
const user = await api.getMe();
const courses = await api.getCourses(user.orgId); // нужен orgId — распараллелить нельзя
```

### `try/catch` вокруг `await`

Ловит ровно то, что `await` бросил в этой точке, — то есть отказ промиса, который ждали. Плюс обычные синхронные исключения внутри блока.

```js
try {
  const data = await api.get();   // отказ промиса попадёт сюда
  render(data);                   // синхронное исключение попадёт сюда
} catch (e) {
  // оба случая
}
```

Не ловит:

```js
try {
  api.get();            // нет await — промис никем не ожидается
  save();               // нет await, если save() асинхронна
} catch (e) {
  // не сработает: к моменту отказа этот try уже завершился
}
```

Причина та же, что в 1.11 для колбэков: `try/catch` действует во время выполнения блока, а отказ происходит позже, когда блока уже нет. `await` — единственное, что связывает отказ промиса с конкретным местом в коде.

### Забытый `await` перед `return` внутри `try`

Отдельный случай, потому что выглядит безобидно:

```js
async function save(data) {
  try {
    return api.write(data);       // нет await
  } catch (e) {
    log(e);                       // никогда не выполнится
    return null;
  }
}
```

`return api.write(data)` возвращает промис, и `async`-функция перенимает его состояние — но **выход из `try` уже произошёл** к моменту, когда промис отвергается. `catch` относится к блоку, а не к промису. Вызывающий получит отказ, которого здесь не ждали.

С `return await api.write(data)` функция приостанавливается внутри `try`, и отказ попадает в `catch`. Это единственный случай, когда `return await` имеет смысл; без `try/catch` рядом он лишний (и, кстати, добавляет один лишний шаг в очереди — 1.21).

### Floating promise

**Floating promise** — промис, у которого нет подписчиков: никто не вызвал ни `await`, ни `then`, ни `catch`.

```js
function onPress() {
  saveProgress(lessonId);  // async-функция вызвана без await
  navigate("Next");
}
```

Работа выполняется — промис запущен (1.18) — но результат никому не адресован. При отказе это необработанный rejection: в dev предупреждение, в release поведение зависит от настроек и может быть полным молчанием (1.11). И вызывающий код не знает, завершилась ли операция: здесь навигация произойдёт до сохранения, и если сохранение провалится, пользователь уже на другом экране и ничего не узнает.

Floating promise не всегда ошибка: «запустить и не ждать» — законный приём (отправка аналитики, прогрев кэша). Но в этом случае у промиса должен быть хотя бы `catch`, иначе провал становится невидимым:

```js
void saveProgress(lessonId).catch(report);
```

### `await` в цикле

```js
for (const id of ids) {
  const lesson = await api.getLesson(id);  // каждая итерация ждёт предыдущую
  lessons.push(lesson);
}
```

Это последовательная обработка: для 20 элементов по 150 мс — 3 секунды. Параллельный вариант:

```js
const lessons = await Promise.all(ids.map((id) => api.getLesson(id)));
```

Здесь `map` создаёт все промисы сразу (работа началась для всех), а `all` ждёт. Время — не сумма, а максимум.

Две оговорки, из-за которых `await` в цикле не является автоматически ошибкой:

- **зависимость между итерациями** — если следующий запрос использует результат предыдущего (курсорная пагинация), последовательность обязательна;
- **ограничение параллелизма** — 500 одновременных запросов хуже, чем 500 последовательных: они конкурируют за сеть, упираются в лимиты сервера и могут получить 429. Нужен пул или батчи; это 7.3.

Отдельная ловушка: `forEach` с асинхронным колбэком **не ждёт ничего**. `ids.forEach(async (id) => { await api.getLesson(id) })` создаёт N floating promise и возвращает `undefined` немедленно — цикл завершается до первого результата.

## 3. Почему это важно

`async/await` дал асинхронному коду форму последовательного: линейное чтение, обычный `try/catch`, обычный `return`. Это большая выгода в читаемости — и источник двух системных потерь.

**Потеря параллельности.** Последовательная форма выглядит естественно, поэтому вопрос «а эти две операции вообще зависят друг от друга?» не задаётся. Код, который читается правильно, работает вдвое дольше необходимого, и ничто в нём не выглядит ошибкой — нет ни предупреждения линтера, ни падения теста.

**Потеря ошибок.** Обычная функция, которая бросает, обрушивает вызывающий код — ошибку невозможно не заметить. `async`-функция возвращает rejected-промис, и если его никто не ждёт, не происходит **ничего**: ни исключения, ни остановки, ни лога. Молчание — это худший вид отказа, потому что он не попадает ни в мониторинг, ни в отчёты пользователей (они видят «не сохранилось», а не ошибку).

### DEEP DIVE: цена последовательности

```
3 независимых запроса по 300 мс
    ↓
последовательно: 900 мс · параллельно: 300 мс
    ↓
600 мс разницы на каждом открытии экрана
```

600 мс — это не «чуть медленнее»: на экране, который открывают несколько раз за сеанс, это разница между «приложение отзывчивое» и «подтормаживает» — суждение, которое пользователь выносит один раз и не меняет (измеримая часть — TTI, 5.6). И это при хорошей сети: на LTE с высокой задержкой последовательность умножает именно задержку — три RTT вместо одного.

## 4. Где это в React Native

### Загрузка экрана — главный сюжет

```jsx
useEffect(() => {
  async function load() {
    const course = await api.getCourse(id);       // 300 мс
    const progress = await storage.getProgress(id); // 50 мс
    setState({ course, progress });
  }
  load();
}, [id]);
```

350 мс вместо 300, при полной независимости источников. На практике таких `await` в загрузчике экрана бывает четыре-пять, и тогда разница измеряется секундой.

Отдельно стоит заметить: `useEffect` не может быть `async` (он должен возвращать функцию очистки или `undefined`, а `async`-функция возвращает промис), поэтому внутрь всегда попадает объявление функции и её вызов — то есть **floating promise по конструкции**. Это нормально, но означает, что обработка ошибок обязана быть внутри: снаружи её повесить некуда.

### Последовательность «разрешение → нативный вызов → запись»

```js
const status = await request(PERMISSIONS.IOS.PHOTO_LIBRARY); // минуты, пока пользователь не ответит
if (status !== "granted") return;
const photo = await launchImageLibrary();                     // пока пользователь выбирает
await uploadPhoto(photo);                                     // сеть
```

Здесь последовательность **обязательна** — каждый шаг зависит от предыдущего. Важно другое: функция приостановлена между шагами на неопределённое время, и за это время приложение могло быть свёрнуто, экран закрыт, а компонент размонтирован. Продолжение всё это время живо и держит окружение.

### Асинхронная операция после размонтирования

Второй главный сюжет урока.

```jsx
useEffect(() => {
  async function load() {
    const data = await api.getCourse(id);  // 2 секунды на плохой сети
    setState(data);                        // пользователь уже ушёл с экрана
  }
  load();
}, [id]);
```

Пользователь открывает экран, запрос уходит; через полсекунды он нажимает «назад», компонент размонтируется. Запрос при этом продолжается: промис не знает ни про компонент, ни про навигацию и отменить себя не может (1.18). Через две секунды он завершается, продолжение возобновляется и вызывает `setState`, который уже ничего не обновляет.

Последствия в RN:

- **в dev** — предупреждение (в части версий React уже убранное, что делает проблему тише, а не меньше);
- **в release** — молча. Но продолжение всё это время удерживало окружение компонента: пропсы, состояние, захваченные данные (1.14, 1.22). На экране, который открывают и закрывают в цикле, это накопление;
- **в сочетании с навигацией** — на экране, открытом повторно, может сработать продолжение от прошлого открытия: устаревший ответ перезаписывает свежий. Это уже гонка (7.10).

> Решение здесь сознательно не разбирается: флаг `cancelled`, `AbortController`, отмена на уровне библиотеки запросов — **7.10**. В этом уроке нужно понимать, почему операция продолжается и что именно удерживается в памяти.

### Обработчик нажатия

```jsx
<Button onPress={async () => {
  await submit(form);
  navigate("Done");
}} />
```

Колбэк `onPress` — floating promise: его результата никто не ждёт. Если `submit` отвергнет, навигации не будет и пользователь останется на экране без всякого объяснения. Это тот случай, где `try/catch` внутри обработчика обязателен — снаружи его повесить невозможно.

Второй слой: обработчик приостановлен на время `submit`, кнопка при этом активна, и повторное нажатие запускает вторую отправку. Защита от повторного нажатия — не косметика, а следствие того, что `await` не блокирует интерфейс.

## 5. Типичные ошибки

**Сериализация независимых запросов.** Возникает из линейной формы кода: `await` на каждой строке выглядит как естественный способ получить несколько значений, и вопрос о зависимости между ними не возникает. Усиливается тем, что в dev на быстром Wi-Fi разница незаметна — проблема живёт только на устройствах пользователей.

**Уверенность, что `await` блокирует поток.** Возникает из аналогии с блокирующим вводом-выводом в других языках и из самого слова «ждать». Даёт сразу два неверных вывода: что `await` вредит производительности (нет — вредит последовательность независимых операций) и что во время `await` ничего другого не происходит (происходит всё остальное, включая рендер, обработку нажатий и другие продолжения).

**Ожидание, что `try/catch` вокруг вызова `async`-функции без `await` поймает ошибку.** Возникает из того, что синтаксис не отличает `async`-функцию от обычной в месте вызова: `save(data)` выглядит как обычный вызов. Ключ в том, что `async`-функция ошибку **не бросает** — она возвращает rejected-промис, а промис не имеет отношения к `try`.

**Забытый `await` перед `return` внутри `try`.** Возникает из общего и верного совета «`return await` избыточен»: он действительно избыточен — кроме случая, когда рядом `try/catch`. Ошибка тихая: функция работает, но её `catch` мёртв.

**Незавершённая операция после размонтирования.** Возникает из того, что `useEffect` даёт cleanup для подписок, и кажется, что он симметрично «отменяет» всё, что эффект начал. Он не отменяет: cleanup — это ваш код, и если в нём не предусмотрена отмена, операция продолжается.

**`forEach` с `async`-колбэком.** Возникает из привычки, что `forEach` взаимозаменяем с `for...of`. Он не умеет ждать колбэк: результат — N floating promise и мгновенный переход к следующей строке, то есть код работает с данными, которых ещё нет.

**`await` в цикле без причины.** Возникает из того, что `for...of` с `await` — самая очевидная форма обработки массива, а разница видна только на длине. На трёх элементах в dev незаметна, на двадцати на устройстве — секунды.

**Избыточная параллельность.** Обратная ошибка, появляющаяся после первого прочтения этого урока: `Promise.all` по массиву из 500 элементов. Запросы конкурируют, сервер отвечает 429, суммарное время хуже последовательного. Параллельность нужно ограничивать (7.3).

**`async`-функция, переданная туда, где её результат не ждут.** `onPress`, `useEffect`, колбэк эмиттера, `setTimeout` — все они игнорируют возвращаемое значение. Ошибки обязаны обрабатываться внутри; снаружи их перехватить нечем.

## 6. Trade-offs

### Читаемость последовательного кода против скорости параллельного

| | Последовательные `await` | Параллельный запуск |
|---|---|---|
| чтение | линейное, порядок явный | нужно увидеть, где создаются промисы и где собираются |
| время | сумма | максимум |
| обработка ошибок | естественная, по шагам | требует решения (см. ниже) |
| поведение при отказе первого шага | остальное не запускается | запущено всё |
| уместно | есть зависимость между шагами | шаги независимы |

Важная сторона, которую обычно забывают: последовательность **экономит работу** при отказе. Если первый шаг провалился, второй запрос не отправлен. При параллельном запуске отправлено всё, и трафик потрачен. На экране с обязательной авторизацией это ощутимо.

### `Promise.all` против раздельных `await` — это выбор обработки ошибок

Два параллельных варианта не эквивалентны:

```js
// A: один catch на всё — неизвестно, что именно упало
try {
  const [a, b] = await Promise.all([getA(), getB()]);
} catch (e) { /* который из двух? */ }

// B: промисы созданы сразу (параллельно), ошибки разделены
const pa = getA();
const pb = getB();
const a = await pa.catch(() => null);
const b = await pb.catch(() => null);
```

Вариант A короче и теряет информацию: `all` отвергает первой причиной, остальные недоступны. Вариант B сохраняет параллельность и даёт отдельное решение по каждому источнику — ценой кода. Промежуточный вариант — `allSettled` (1.18), который даёт и параллельность, и полную картину, ценой разбора результата.

Выбор здесь — не про скорость, а про то, **нужно ли различать отказы**. Если нужно (один источник обязательный, другой нет — ровно задание 1.18), `all` не подходит.

### `return await` против `return` и floating promise как решение

`return await p` добавляет один шаг в очереди микротасков (1.21) — пренебрежимо. Но он нужен в двух случаях: внутри `try` (иначе `catch` мёртв) и когда важен читаемый стектрейс. Вне этих случаев `return p` короче и честнее.

«Запустить и не ждать» уместно для аналитики, прогрева кэша, фоновой синхронизации — там, где результат не влияет на интерфейс. Цена: отказ становится невидимым, если не повесить `catch`. Рабочее правило: floating promise допустим, но **всегда с `catch`**; без `catch` это класс ошибок, которого не будет ни в логах, ни в Sentry (10.6).

## 7. Связи с другими частями системы

**Назад:**

- **[1.18 Promises](../18-promises/)** — основание всего урока. Без факта «работа начинается при создании» объяснение параллельного запуска превращается в заклинание: непонятно, почему перестановка `await` что-то меняет;
- **[1.11 Error handling](../11-error-handling/)** — та же асимметрия, что здесь: `try/catch` действует во время выполнения блока, а отказ происходит позже. `await` — механизм, который возвращает отказ в блок;
- **1.14 Closures** — продолжение после `await` это замыкание: оно держит локальные переменные функции всё время ожидания;
- **1.15 Execution context** — при приостановке стек раскручивается, и в стектрейсе асинхронной ошибки не видно исходного вызывающего.

**Вперёд — внутри цепочки блока:**

- **[1.20 Event loop](../20-event-loop/)** — **когда** выполняется продолжение. Этот урок говорит «поток в это время занят другим»; что именно он делает и как решает, что делать дальше, — там;
- **[1.21 Microtasks и macrotasks](../21-microtasks-and-macrotasks/)** — продолжение после `await` планируется как микротаск, поэтому выполняется раньше любого таймера. Отсюда точный порядок вывода в смешанном коде;
- **1.22 Memory** — `pending`-промис и его продолжение удерживают окружение: механизм удержания при незавершённой операции;
- **1.24 Синтез** — два последовательных `await` входят в компонент-пример как один из семи дефектов.

**Вперёд — за пределы блока:**

- **3.3 Путь обновления** — `setState` в продолжении после `await` происходит вне синхронного цикла обновления, и это влияет на батчинг;
- **3.4 Правила хуков и зависимостей** — `async`-функция внутри `useEffect`, cleanup и честный массив зависимостей;
- **5.6 Bundle size и TTI** — последовательные `await` в загрузчике экрана как измеримая часть времени до первого содержательного кадра;
- **7.3 Ошибки, retry, таймауты** — что делать с отказом и как ограничивать параллелизм;
- **7.10 Race conditions и отмена** — продолжение сюжета про размонтирование: там решение, здесь механизм;
- **10.6 Sentry и symbolication** — почему стектрейс асинхронной ошибки короче ожидаемого и чего в нём нет;
- **11.3 Тестирование асинхронного кода** — floating promise в тесте даёт прошедший тест при сломанном коде: проверка выполняется до того, как операция завершилась.

**Главное, что должно остаться после урока.** `await` — это место, куда функция вернётся; в промежутке работает весь остальной код. Отсюда оба вывода урока: параллельность определяется тем, **где созданы промисы**, а не где стоит `await`; а ошибка `async`-функции существует только как состояние промиса — и исчезает бесследно, если этот промис никто не слушает.
