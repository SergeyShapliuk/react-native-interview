# 1.2 Data types и граница JS↔native — theory

> 🟢 REFRESH. Типы данных как справочник вы знаете. Ось урока другая: какие значения способны существовать **за пределами** JS-мира, и почему контракты нативных модулей выглядят беднее обычного JS-кода.

## Refresh

### Два класса значений

**Примитивы:** `string`, `number`, `boolean`, `undefined`, `null`, `symbol`, `bigint`. Хранятся как значение, сравниваются по значению, неизменяемы — у строки нельзя поменять символ, можно только получить новую строку.

**Объекты:** всё остальное, включая массивы, функции, `Date`, `Map`, `Set`, `RegExp`, экземпляры классов. Хранятся как ссылка, сравниваются по ссылке (1.12), изменяемы.

Граница между двумя классами — не формальность: от неё зависит, что произойдёт при передаче значения куда угодно, включая нативный слой.

### `undefined` vs `null`

Технически оба означают «значения нет». По смыслу различие устойчивое и полезное:

- **`undefined`** — значения не задавали. Так выглядит отсутствующее поле объекта, параметр без аргумента, функция без `return`;
- **`null`** — значение явно задали как «ничего». Так выглядит поле, которое кто-то (чаще всего бэкенд) сознательно заполнил пустотой.

Различие практическое, а не философское: значения по умолчанию при деструктуризации срабатывают на `undefined` и не срабатывают на `null` (1.7), а оператор `??` реагирует на оба (1.3).

### `NaN`

`NaN` (not a number) — это `number`, результат арифметики, которая не дала числа.

```js
typeof NaN;        // number
NaN === NaN;       // false
Number.isNaN(NaN); // true  — корректная проверка
```

`NaN` не равен ничему, включая себя: по стандарту это маркер «результата нет», а не одно конкретное не-число. Поэтому сравнение через `===` для него не работает, и существует `Object.is(NaN, NaN) === true` (1.3). Отдельно: глобальный `isNaN` сначала приводит аргумент к числу, поэтому `isNaN` от нечисловой строки тоже даёт `true` — это не проверка на `NaN`, а проверка «не приводится к числу».

### `Symbol` и `BigInt`

**`Symbol`** — уникальный неперечислимый ключ. Применяется в библиотеках для скрытых полей и well-known протоколов вроде итератора. В продуктовом RN-коде почти не встречается.

**`BigInt`** — целые произвольной длины, литерал `10n`. Нужен там, где `number` теряет точность (выше 2 в 53-й степени). В мобильной разработке возникает в идентификаторах, которые бэкенд отдаёт как большие целые.

Оба упоминаются по одной причине: **ни тот, ни другой не являются допустимыми значениями в контракте нативного модуля.** У `Symbol` вне JS нет представления в принципе, `BigInt` не соответствует ни одному числовому типу платформенной стороны. Большой идентификатор на границе передают строкой — и это не обходной путь, а правильное решение.

### `typeof` и его ловушки

```js
typeof null;           // object    — историческая ошибка, зафиксирована навсегда
typeof [];             // object    — массив не отдельный тип
typeof function () {}; // function  — единственный объект со своим typeof
typeof NaN;            // number
typeof undeclared;     // undefined — не бросает ошибку
```

Проверки, которые действительно работают: `Array.isArray(x)` для массива, `x === null` для `null`, `Number.isNaN(x)` для `NaN`, `Object.prototype.toString.call(x)` когда нужно различить `Date`, `Map` и обычный объект.

Результат `typeof` для `null` — не «баг, который исправят»: исправление сломало бы существующий код в масштабе всего веба, и предложение было отклонено. Это постоянное свойство языка, его надо знать как факт.

### Сериализуемость как свойство значения

**Сериализуемость** — способность значения быть представленным как данные, без привязки к коду и памяти текущего рантайма.

Сериализуемы: примитивы (кроме `Symbol` и `BigInt`), массивы, простые объекты из сериализуемых значений.

Не сериализуемы — и это важнее:

| Значение | Что теряется |
|---|---|
| функция | код нельзя передать как данные |
| экземпляр класса | методы и прототип; остаются только поля (1.17) |
| `Map`, `Set` | структура целиком: превращаются в пустой объект |
| `Date` | тип; остаётся строка или число |
| `RegExp` | остаётся пустой объект |
| циклическая структура | представления нет вообще |

```js
JSON.parse(JSON.stringify({ when: new Date(), tags: new Set([1, 2]) }));
// { when: "2026-10-05T...", tags: {} }  — Date стала строкой, Set исчез
```

## RN relevance

### Что значит «значение пересекает границу»

У React Native есть граница между JS-кодом и нативным слоем платформы. У этой границы есть **контракт** — набор типов, которые обе стороны понимают одинаково: числа, строки, булевы значения, `null`, массивы и простые объекты из них.

Отсюда прямое следствие: **значение переходит границу ровно настолько, насколько оно описывается этим контрактом.** Функция, `Map`, `Set`, `Date`, экземпляр класса с методами не переходят границу в том виде, в котором существуют в JS. Не потому, что «что-то не поддерживается», а потому, что на другой стороне нет понятия, которому они соответствуют: у платформенного кода нет JS-функции и нет вашего класса.

> **Как устроена сама граница — тема блока 04, не этого урока.** В современном RN работает JSI: возможны синхронные вызовы и работа с нативными объектами по ссылке. Модель «JS сериализует всё в JSON и отправляет в очередь» описывает legacy-архитектуру и неверна как описание границы вообще (4.1, 4.2). Здесь нас интересует только одно: какие **значения** имеют смысл на обеих сторонах.

### Почему контракты нативных модулей выглядят бедно

Открыв типизацию нативного модуля, разработчик видит методы, принимающие строки, числа и плоские объекты, и никогда — доменную модель с методами. Это не лень автора библиотеки: богаче контракт быть не может. Понимание этого снимает целый класс вопросов «почему нельзя просто передать мой объект».

### Колбэк в нативный модуль — это не передача функции

Функция не пересекает границу. Когда вы передаёте колбэк в нативный метод, на другую сторону уходит **идентификатор**, по которому нативная сторона позже просит вызвать вашу функцию, оставшуюся в JS. Функция всё время живёт в JS-мире.

Из этого следуют два практических факта:

- **в контракте старой модели модулей колбэк одноразовый** — повторный вызов по тому же идентификатору не предусмотрен, и ошибка «callback was already invoked» возникает именно здесь;
- **пока идентификатор жив на нативной стороне, жива и функция вместе со всем, что она захватила** (1.14). Это механизм утечки, не видимый из JS-кода, — цепочку ссылок разбираем в 1.22.

### `Date` и большие идентификаторы на границе

Две самые частые практические ошибки:

- **`Date` передают как есть** и получают на другой стороне строку или число, а при обратной передаче в JS это уже не `Date`. Работающее решение: договориться о представлении (ISO-строка или epoch в миллисекундах) и конвертировать явно на своей стороне;
- **большой числовой идентификатор** приходит с бэкенда, не влезает в `number` без потери точности, и после пути через границу последние цифры «меняются». Решение то же: строка на всём пути, от бэкенда до экрана.

### Почему проверка через `JSON.stringify` не годится

`JSON.stringify` молча портит данные вместо того, чтобы отказать: `Date` превратит в строку, `Set` — в пустой объект, функцию и `undefined` в поле объекта просто выбросит. Успех вызова не означает, что значение сохранило смысл. Поэтому пригодность значения для границы проверяют по контракту, а не по тому, что `stringify` не бросил исключение.

## Типичные заблуждения

**«Результат `typeof` для `null` — баг, который когда-нибудь исправят.»** Возникает из разумного ожидания, что явные дефекты исправляют. Исправление отклонено сознательно: оно ломает существующий код повсеместно.

**«`Date` передаётся как есть.»** Возникает потому, что внутри JS `Date` ведёт себя как полноценное значение, и граница незаметна до первой ошибки. На границе `Date` — объект с методами, то есть ровно тот класс значений, который контракт не описывает.

**«Если `JSON.stringify` работает, значение пройдёт куда угодно.»** Возникает из того, что вызов не падает. Он не проверяет пригодность — он делает что может и молчит о потерях.

**«Любое взаимодействие с нативным слоем — это JSON.»** Самое дорогое заблуждение этого урока, потому что оно переносится в рассуждения о производительности. Сериализация в JSON — свойство конкретной (legacy) модели взаимодействия, а не определение границы. В современной архитектуре это не так, и выводы вида «любой вызов в native дорог, потому что JSON» неверны (4.1).

**«Ограничение типов на границе — недостаток React Native.»** Возникает из сравнения с JS-кодом, где передать можно что угодно. Но ограничение есть у любой границы между двумя рантаймами с разными моделями памяти и типов; RN здесь не исключение, а обычный случай.
