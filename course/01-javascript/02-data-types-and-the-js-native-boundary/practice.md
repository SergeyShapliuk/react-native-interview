# 1.2 Data types и граница JS↔native — practice

## Проверка понимания

---

**1. Чем `undefined` отличается от `null` по смыслу, а не по значению?**

<details>
<summary>Ответ</summary>

`undefined` — значения не задавали: поле отсутствует, аргумент не передан, функция ничего не вернула. `null` — значение задали явно как «ничего»: чаще всего так приходит поле, которое бэкенд сознательно заполнил пустотой.

**Ответ «разницы нет, оба означают отсутствие»** вскрывает пробел, который выстрелит в 1.7: значения по умолчанию при деструктуризации применяются только к `undefined`. Разработчик, для которого эти два значения одинаковы, напишет дефолт и будет уверен, что защитился от пустого поля, — а на `null` с бэкенда дефолт не сработает.

**Ответ «`null` для объектов, `undefined` для примитивов»** вскрывает выдуманное правило. Такого разделения в языке нет, и опора на него даёт неверные предсказания.
</details>

---

**2. Почему `NaN !== NaN`?**

<details>
<summary>Ответ</summary>

Потому что по стандарту `NaN` — маркер «результата нет», а не конкретное значение. Два отсутствующих результата не обязаны быть «одним и тем же числом», и сравнение возвращает `false`. Проверять нужно через `Number.isNaN`, а сравнивать с учётом `NaN` — через `Object.is`.

**Ответ «потому что это разные объекты в памяти»** вскрывает смешение с идентичностью объектов (1.12). `NaN` — примитив, никаких «разных объектов» здесь нет, и объяснение через ссылки даёт неверную модель.

**Ответ «не знаю, но проверяю через `isNaN`»** частично рабочий, но вскрывает незнание разницы между глобальным `isNaN` (приводит аргумент к числу) и `Number.isNaN` (проверяет именно `NaN`). Первый вернёт `true` для нечисловой строки, и проверка окажется шире, чем задумано.
</details>

---

**3. Какие из этих значений пройдут границу JS↔native без потери смысла, а какие нет и почему?**

```
42 · "abc" · true · null · undefined · [1, 2, 3] · { id: 1, title: "x" }
new Date() · new Map() · () => {} · new Lesson({ id: 1 }) · 9007199254740993n
```

<details>
<summary>Ответ</summary>

**Проходят:** `42`, `"abc"`, `true`, `null`, массив из сериализуемых значений, простой объект из сериализуемых значений.

**Не проходят в том виде, в котором существуют в JS:**

- `undefined` — в объекте поле с таким значением просто исчезает; договариваться нужно явно, обычно через `null`;
- `new Date()` — объект с методами; на другой стороне окажется строка или число, и обратно это уже не `Date`;
- `new Map()` — структура не описывается контрактом; превращается в пустой объект, то есть данные теряются молча;
- `() => {}` — функция не передаётся; передаётся идентификатор, по которому нативная сторона просит вызвать функцию, оставшуюся в JS;
- `new Lesson(...)` — остаются только поля, методы и прототип теряются (1.17);
- `9007199254740993n` — `BigInt` не соответствует числовому типу платформенной стороны; передаётся строкой.

**Ответ, в котором `Map` и `Date` отнесены к проходящим,** вскрывает модель «объект есть объект». Практическая цена: потеря данных без ошибки — самый дорогой вид дефекта, потому что он обнаруживается далеко от причины.

**Ответ «не проходят, потому что JSON их не поддерживает»** вскрывает подмену причины. Ограничение задаёт контракт границы, а не формат JSON; JSON — свойство одной конкретной модели взаимодействия (4.2), и опора на него ведёт к неверным выводам о производительности в современной архитектуре.
</details>

## Задание

**Дано.** Модуль домена RN-приложения отдаёт данные урока в нативный модуль аналитики и в нативный модуль локального хранилища.

```js
class Lesson {
  constructor({ id, title, finishedAt, tags }) {
    this.id = id;
    this.title = title;
    this.finishedAt = finishedAt; // Date | null
    this.tags = tags;             // Set<string>
  }
  isFinished() {
    return this.finishedAt !== null;
  }
}

const lesson = new Lesson({
  id: 9007199254740993,
  title: "Замыкания",
  finishedAt: new Date(),
  tags: new Set(["js", "closures"]),
});

Analytics.track("lesson_finished", lesson);
Storage.save("lesson:last", lesson);
```

**Требуется.**

1. Для каждого поля предсказать, что от него останется на другой стороне границы, и назвать причину.
2. Назвать поле, которое потеряется **молча**, без ошибки и без предупреждения, и объяснить, почему это опаснее падения.
3. Объяснить, что произойдёт с методом `isFinished` и почему вызов его на другой стороне невозможен в принципе.
4. Предложить представление данных урока, пригодное для границы. Представление должно быть описано как решение с ценой, а не как «правильный способ».
5. Ответить: что из перечисленного сломается одинаково и в legacy-архитектуре, и в современной, а что — нет? Полный разбор в 4.1, здесь нужна гипотеза с обоснованием.

---

<details>
<summary>Разбор</summary>

**1. Поле за полем.**

| Поле | Что останется | Причина |
|---|---|---|
| `id: 9007199254740993` | **испорченное число** | значение выше предела точности `number`; последняя цифра изменится ещё до границы, в самом JS |
| `title: "Замыкания"` | строка без изменений | строка описывается контрактом |
| `finishedAt: new Date()` | строка или число | `Date` — объект с методами; тип теряется, остаётся представление |
| `tags: new Set([...])` | пустой объект | `Set` не описывается контрактом; элементы не попадут никуда |
| `isFinished` | ничего | метод живёт в прототипе (1.17), на границу идут только данные |

**2. Молчаливая потеря — `tags`.** Ни ошибки, ни предупреждения: на другой стороне окажется объект без полей, и всё продолжит работать. Опаснее падения по двум причинам: дефект обнаруживается не в момент передачи, а когда кто-то обнаружит пустую аналитику или пропавшие теги после перезапуска приложения; и к этому моменту связь с местом причины уже потеряна.

Второй кандидат — `id`: он портится тихо и ещё раньше, в литерале. Это худший случай из двух, потому что данные неверны уже внутри JS.

**3. Про `isFinished`.** Метод определён в прототипе класса, а не в самом объекте. На границу уходят данные, то есть собственные поля; прототип не уходит. Но важнее другое: даже если бы метод оказался на другой стороне, вызвать его было бы нечем — JS-функция требует JS-движка и того окружения, в котором она объявлена (1.15). Нативная сторона не может «выполнить JS-метод»; она может только попросить JS вызвать функцию, которую JS сам держит, — и это уже другой механизм, механизм колбэка.

**4. Представление, пригодное для границы.**

```js
function toTransferable(lesson) {
  return {
    id: String(lesson.id),                               // строка, а не число
    title: lesson.title,
    finishedAt: lesson.finishedAt ? lesson.finishedAt.toISOString() : null,
    tags: Array.from(lesson.tags),                       // массив, а не Set
  };
}
```

**Цена решения, которую надо назвать явно:**

- появляется **второе представление** одних и тех же данных, и его надо поддерживать: при добавлении поля в домен о функции легко забыть;
- нужна **обратная конвертация** при чтении из хранилища, и она так же легко расходится с прямой;
- `id` строкой означает, что все сравнения и ключи работают со строками: смешение строки и числа в ключах даёт дефект, который не ловится типами, если `id` объявлен как `string | number`;
- `finishedAt` строкой означает, что сортировка по дате требует обратного разбора, и делать её нужно до конвертации, а не после.

**Чем это лучше альтернативы:** альтернатива — передавать домен как есть и надеяться. Она дешевле на одну функцию и дороже на каждый молчаливо потерянный `Set`. Решение принимается в пользу явной конвертации именно потому, что потери на границе не сигнализируют о себе.

**Отдельный вывод для домена** (его фиксируем в RN Academy, см. 1.17): если данные домена регулярно уходят за границу, класс с методами — плохое представление. Тип плюс чистые функции даёт то же поведение без проблемы «на другой стороне остались только поля».

**5. Что зависит от архитектуры, а что нет.**

Не зависит — всё, что перечислено выше. `Set` не станет передаваемым, `Date` не сохранит тип, метод прототипа не уйдёт на другую сторону, а `BigInt` не впишется в платформенный числовой тип. Это свойства **значений** и контракта границы, и они одинаковы в обеих архитектурах.

Зависит от архитектуры — не «что можно передать», а **как** передача устроена: синхронно или асинхронно, с конвертацией через очередь сообщений или прямым доступом, можно ли держать нативный объект по ссылке. Именно это меняется между legacy-моделью и JSI, и именно из этого следуют выводы о производительности. Отсюда практический вывод урока: перенос архитектуры на список допустимых типов — ошибка, и рассуждения «в новой архитектуре можно передавать что угодно, ведь JSON больше нет» неверны.
</details>
