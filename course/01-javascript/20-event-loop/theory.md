# 1.20 Event loop — theory

> 🟡 DEEP DIVE. Семь углов разбора. Уроки 1.18 и 1.19 показали, что планируется к выполнению. Этот урок отвечает, **когда** это выполняется, — и из ответа следует точный смысл фразы «JS thread заблокирован»: не «поток занят», а «текущая задача не завершилась, поэтому следующая не началась».

## 1. Что это

**Event loop** — цикл, который берёт по одной задаче из очереди, выполняет её до конца и переходит к следующей.

Три составляющие:

| Часть | Что это |
|---|---|
| **call stack** (стек вызовов) | где исполняется код прямо сейчас: кадры вложенных вызовов (1.15) |
| **task queue** (очередь задач) | очередь работы, запланированной к выполнению: колбэки таймеров, события, сообщения извне |
| **event loop** | цикл: пока есть задачи — взять первую, выполнить до конца, повторить |

**Task (задача, также macrotask)** — единица работы, которую цикл берёт из очереди целиком. Колбэк `setTimeout`, обработчик события, сообщение от нативной стороны — каждое это одна задача.

Правило, из которого вытекает весь урок:

> **Run-to-completion: задача выполняется до конца. Цикл не может прервать её, чтобы заняться другой.**

Нет вытеснения, нет приоритетов внутри очереди, нет способа «уступить» на середине функции. Любая следующая задача ждёт, пока текущая не вернёт управление.

### Что означает «однопоточность» для JS

Точная формулировка: **JS-код исполняется в одном потоке, и в любой момент времени выполняется ровно одна задача.**

Из этого НЕ следует, что:

- приложение однопоточное — у него есть другие потоки, просто JS в них не исполняется;
- асинхронные операции выполняются в JS-потоке — сетевой запрос, чтение файла, таймер ведутся вне него, а в очередь попадает только результат;
- параллельности нет вообще — её нет **внутри JS**, но операции, которые JS запустил, идут параллельно (именно поэтому два промиса, созданных рядом, выполняются одновременно — 1.18).

Однопоточность JS — это не ограничение производительности, а **гарантия**: пока выполняется задача, никто не изменит данные под ней. Отсюда отсутствие в JS мьютексов и race condition в их классическом смысле. Гонки в JS есть, но другого рода — между завершением асинхронных операций (7.10), а не между потоками, одновременно пишущими в одну память.

## 2. Как это работает

### Один оборот цикла

```
очередь не пуста?
    ↓ да
взять первую задачу
    ↓
выполнить её ДО КОНЦА (стек заполняется и опустошается)
    ↓
[опустошить очередь микротасков — 1.21]
    ↓
вернуться к началу
```

Шаг в квадратных скобках — предмет урока 1.21. Здесь важно только то, что он существует и происходит **между** задачами, а не во время их выполнения.

### Таймеры: `setTimeout(fn, 0)` не означает «сразу»

`setTimeout(fn, delay)` не планирует выполнение через `delay` миллисекунд. Он означает: **«не раньше, чем через `delay` мс, поставить `fn` в очередь задач»**. Между постановкой в очередь и выполнением проходит ещё неопределённое время — столько, сколько нужно, чтобы доработали все задачи, стоящие впереди.

Три независимые причины задержки:

```js
setTimeout(() => console.log("таймер"), 0);
heavySyncWork(300);                  // 300 мс синхронной работы
// "таймер" выведется примерно через 300 мс, а не через 0
```

1. **текущая задача не завершена** — таймер физически не может начаться, пока выполняется код выше (run-to-completion). Это главная причина и самая частая;
2. **в очереди есть задачи впереди** — они выполнятся первыми, в порядке постановки;
3. **минимальный порог** — вложенные таймеры глубже определённого уровня принудительно получают задержку около 4 мс (деталь спецификации; в RN значение зависит от реализации — не опирайтесь на конкретное число).

Отсюда рабочая формулировка: **`delay` — это минимум, не обещание.** Код, точность которого зависит от срабатывания таймера ровно в срок, неверен независимо от того, работает ли он сегодня.

Обратная сторона: `setTimeout(fn, 0)` даёт одну полезную гарантию — `fn` выполнится **не в текущей задаче**. Текущая завершится, стек опустеет, и только потом начнётся `fn`. Это единственное, на что он годится, и именно для этого его используют осознанно.

### Что значит «JS thread заблокирован»

Точный смысл: **выполняется задача, которая ещё не завершилась, поэтому ни одна другая задача не началась.**

```js
function onPress() {
  const result = processItems(lessons);  // 400 мс синхронной работы
  setState(result);
}
```

Во время этих 400 мс в очередь продолжают поступать задачи: нажатия, сообщения от нативной стороны, колбэки таймеров, продолжения промисов. Ни одна не выполняется. Когда `onPress` завершится, цикл начнёт разгребать накопленное — и пользователь увидит, как интерфейс «догоняет»: срабатывают нажатия, сделанные полсекунды назад, причём иногда не те, что ожидались (пользователь уже на другом экране).

Важно, что блокирует **только синхронная работа**. `await` не блокирует (1.19): в точке приостановки функция возвращает управление, и цикл свободен. Долгий сетевой запрос не блокирует вообще — он идёт вне JS-потока.

| Что делает код | Блокирует цикл |
|---|---|
| цикл по 100 000 элементов | да |
| `JSON.parse` большой строки | да — это один синхронный вызов, и прервать его нельзя |
| синхронная криптография, сортировка, вычисление хэша | да |
| `await fetch(...)` | нет |
| `setTimeout` с большой задержкой | нет |
| ожидание результата от нативного модуля | нет, если вызов асинхронный |
| синхронный вызов нативного модуля через JSI | да — пока он не вернёт, JS-поток занят (4.1) |

Последняя строка — специфика RN, которой нет в вебе: JSI делает возможным синхронный вызов в нативный код, и такой вызов блокирует JS-поток на всё своё время.

### Разбивка работы на части

Единственный способ сделать долгую работу неблокирующей в одном потоке — разрезать её на несколько задач, вернув управление между ними:

```js
function processInChunks(items, chunkSize, onDone, acc = [], i = 0) {
  const end = Math.min(i + chunkSize, items.length);
  for (let j = i; j < end; j++) acc.push(transform(items[j]));

  if (end < items.length) {
    setTimeout(() => processInChunks(items, chunkSize, onDone, acc, end), 0);
  } else {
    onDone(acc);
  }
}
```

Что произошло: одна задача на 400 мс превратилась в 40 задач по 10 мс. Между ними цикл обрабатывает накопившееся — нажатия доходят, состояние обновляется. **Суммарное время стало больше** (добавились накладные расходы на планирование), но интерфейс остался отзывчивым.

Это принципиальный компромисс, а не оптимизация: мы обменяли общую длительность на отзывчивость. Цена обсуждается в угле 6.

Чего разбивка **не** делает: она не ускоряет работу и не переносит её в другой поток. Если задача по природе требует 400 мс вычислений, она их потребует — вопрос только в том, одним куском или сорока.

## 3. Почему это важно

Event loop — это ответ на вопрос «почему приложение не реагирует», и ответ всегда один и тот же по форме: **выполняется задача, которая не завершилась**.

Ценность модели в том, что она делает диагностику конечной. Вместо «приложение подвисает иногда» появляется проверяемая гипотеза: какая задача сейчас выполняется и почему она длинная. Дальше это вопрос измерения (5.10), а не догадок.

Второе: модель задаёт границу возможного. В одном потоке нельзя «выполнить в фоне» и нельзя «прервать на середине» — можно только не начинать длинную задачу или разрезать её. Все существующие решения (разбивка, `InteractionManager`, перенос в нативный поток, worklet, воркер) — это варианты одного из двух, и зная модель, их легко классифицировать вместо запоминания.

### DEEP DIVE: как длинная задача превращается в жалобу пользователя

```
одна синхронная задача на 400 мс
    ↓
очередь задач не обрабатывается 400 мс
    ↓
нажатие пользователя лежит в очереди и не доходит до JS
    ↓
состояние не обновляется, навигация не происходит
    ↓
пользователь нажимает второй раз
    ↓
обе задачи выполняются подряд после освобождения потока
    ↓
двойной переход, двойная отправка формы, экран «проскочил»
```

Последняя строка — то, из-за чего это не только про «медленно». Задержка обработки нажатия превращается в **неверное поведение**: пользователь, не получивший отклика, повторяет действие, и приложение выполняет его дважды. Защита от двойного нажатия существует именно потому, что отклик не мгновенен.

## 4. Где это в React Native

### JS thread — отдельный поток со своим циклом

Главный факт, который отличает RN от веба: **JS-код выполняется не в том потоке, в котором система рисует интерфейс.** JS thread — отдельный поток с собственным event loop; интерфейсом занимается UI/main thread, у которого свой цикл и свои обязанности.

> **Осторожно с моделью.** Не стоит заучивать «в RN три потока». Число и роли потоков зависят от архитектуры, версии и набора библиотек, и упрощённая схема приводит к неверным выводам при встрече с реальностью. Для этого урока достаточно одного различения: **JS thread ≠ UI thread**. Точная модель исполнения и то, какой инструмент показывает какой слой, — **5.1** и **5.10**.

### Главное следствие: анимация не обязана замирать

Это тот результат, из-за которого урок стоит в курсе.

```js
const sorted = lessons.slice().sort(byProgress);  // 8 000 элементов, ~250 мс в JS thread
```

Во время этих 250 мс:

| Останавливается | Продолжается |
|---|---|
| обработка нажатий (колбэк приходит в JS) | анимация, выполняемая на UI-потоке |
| обновления состояния и рендер | скролл нативного списка в пределах уже отрисованного |
| навигация | отрисовка уже отправленного на нативную сторону |
| продолжения промисов и таймеры | работа нативных модулей |

То есть пользователь может видеть **крутящийся спиннер на фоне полностью неработающего экрана** — и это нормальная, объяснимая картина, а не странность. Спиннер идёт по нативной анимации, его кадры UI-поток считает сам; нажатия при этом доходят до нативной стороны, но колбэк в JS попадает в очередь и ждёт.

Обратный случай столь же важен: анимация **замрёт**, если её кадры считаются в JS. Анимация, управляемая состоянием React (`setState` на каждом кадре), или `Animated` без `useNativeDriver` зависит от JS-потока и останавливается вместе с ним. С `useNativeDriver: true` или в worklet Reanimated кадры считаются на UI-потоке и переживают блокировку JS (5.7).

Поэтому вопрос «замрёт ли анимация при тяжёлой работе» не имеет общего ответа. Правильный ответ — встречный вопрос: **где считаются её кадры?**

### Что чаще всего блокирует JS thread в реальном RN-приложении

- **разбор большого ответа** — `JSON.parse` на нескольких мегабайтах. Один синхронный вызов, прервать нельзя; при этом спрятан внутри `await res.json()`, и `await` создаёт ложное впечатление неблокирующей операции (сетевая часть неблокирующая, разбор — нет);
- **сортировка и агрегация больших коллекций** в теле компонента или в селекторе;
- **синхронная работа в обработчике нажатия** — самый заметный случай, потому что блокировка начинается ровно в момент, когда пользователь ждёт отклика;
- **тяжёлое дерево в одном рендере** — рендер это синхронная задача, и чем больше работы в ней, тем дольше поток занят;
- **шифрование, подписывание, хэширование** в JS;
- **первый запуск** — разбор и исполнение бандла это одна длинная серия задач, во время которой JS недоступен (5.6).

### `InteractionManager`

```js
InteractionManager.runAfterInteractions(() => {
  const stats = computeStats(allLessons);
  setStats(stats);
});
```

`InteractionManager` позволяет отложить работу до момента, когда завершатся текущие взаимодействия и анимации. Практический смысл: тяжёлое вычисление не стартует во время перехода между экранами, где каждый кадр заметен.

Что он **не** делает, и это важнее того, что делает:

- не переносит работу в другой поток — она по-прежнему в JS thread;
- не разрезает её — задача на 300 мс останется задачей на 300 мс, просто начнётся позже;
- не гарантирует момента — только «не раньше, чем закончатся взаимодействия».

То есть `InteractionManager` — это **выбор момента**, а не решение проблемы длинной задачи. Если работа длинная, она заблокирует поток и после перехода.

### Куда можно деть работу, если её нельзя разрезать

Полный список направлений, с указанием, где они разбираются:

| Направление | Суть | Где в курсе |
|---|---|---|
| разбивка на задачи | та же работа, много коротких задач | этот урок |
| выбор момента | `InteractionManager`, запуск после анимации | этот урок |
| перенос в нативный слой | вычисление в нативном модуле, вне JS-потока | 4.1, блок 09 |
| перенос на UI thread | worklet Reanimated — для анимаций и жестов | 5.7 |
| перенос на сервер | агрегация выполняется до отдачи клиенту | блок 07 |
| отказ от работы | ленивость, пагинация, виртуализация списка | 5.4 |

Последняя строка — чаще всего правильный ответ, и её легко пропустить, увлёкшись техниками: сортировать 8 000 элементов, чтобы показать 10, не нужно вообще.

## 5. Типичные ошибки

**«JS однопоточный, значит в RN один поток».** Возникает из переноса веб-модели, где JS-поток и поток рендеринга тесно связаны и упоминаются как одно целое. В RN это даёт две неверные диагностики: «анимация тормозит, потому что JS занят» (может быть неверно — зависит от того, где считаются кадры) и «вынести в `setTimeout`, чтобы не мешать интерфейсу» (не поможет: тот же поток, та же задача, другой момент).

**«`setTimeout(fn, 0)` выполнится немедленно».** Возникает из буквального чтения аргумента и из того, что в простых примерах без нагрузки так и выглядит. Отсюда «оптимизация» через `setTimeout(0)`, которая только сдвигает работу, и код, зависящий от точного времени таймера.

**«Анимация замрёт при любой тяжёлой работе».** Возникает из веб-опыта, где это верно. В RN ответ зависит от того, где считаются кадры: нативная анимация и worklet переживают блокировку JS, анимация через состояние React — нет. Ошибка опасна тем, что ведёт к ложным выводам при диагностике: видим живой спиннер, заключаем «JS свободен», ищем проблему не там.

**Оборачивание тяжёлой работы в `async`-функцию «чтобы не блокировало».** Возникает из ассоциации «async = не блокирует». `async` меняет только возвращаемое значение (1.19); синхронный цикл внутри `async`-функции блокирует поток точно так же. Проверка: до первого `await` тело `async`-функции выполняется синхронно.

**`setTimeout` как способ дождаться завершения чего-то.** `setTimeout(() => читаем результат, 100)` в надежде, что за 100 мс всё успеет. Возникает из того, что локально срабатывает. На устройстве пользователя не срабатывает, и дефект невоспроизводим. Правильный механизм для ожидания — промис (1.18), и ровно та же ошибка в тестах разбирается в 11.3.

**Ожидание точного интервала от `setInterval`.** Возникает из названия. Если задача длиннее интервала, срабатывания накапливаются или сливаются, и за минуту «секундный» таймер отсчитает не 60 тиков. Для измерения времени нужны часы, а не счётчик срабатываний.

**Тяжёлая синхронная работа в обработчике нажатия.** Возникает из естественности формы «нажали — посчитали — показали». Это худший момент для блокировки: пользователь ждёт отклика именно сейчас, и отсутствие реакции ведёт к повторному нажатию.

**Вывод «нужно всё разбивать на части».** Возникает после первого прочтения этого урока. Разбивка усложняет код, добавляет промежуточные состояния и увеличивает суммарное время; она оправдана там, где длинная задача **измерена** и мешает. До измерения — преждевременно (5.10).

## 6. Trade-offs

### Разбивка работы: отзывчивость против простоты и суммарного времени

| | Одна задача | Разбивка на части |
|---|---|---|
| отзывчивость интерфейса | нет на всё время работы | сохраняется |
| суммарное время | минимальное | больше: накладные расходы на планирование |
| код | линейный, читаемый | состояние между частями, прогресс, отмена |
| промежуточные состояния | нет | есть — и их видит пользователь |
| отладка | обычный стектрейс | работа размазана по задачам, стек у каждой свой |

Неочевидная цена — промежуточные состояния. Пока работа идёт частями, данные частично обработаны, и интерфейс может их отрисовать: список, который достраивается на глазах. Иногда это лучше (виден прогресс), иногда хуже (мелькание, прыгающий контент).

Вторая неочевидная цена — отмена. Разрезанная работа должна уметь прекратиться, если пользователь ушёл с экрана, иначе она продолжает занимать поток, когда уже никому не нужна.

### Отложить или не начинать

| | `InteractionManager` / отложить | Не делать работу |
|---|---|---|
| что меняется | момент начала | объём |
| помогает при | работа мешает конкретному моменту (переход, анимация) | работа длинная сама по себе |
| цена | работа всё равно случится и заблокирует | нужно изменить требования или архитектуру данных |

Правильный порядок рассмотрения — обратный привычному: сначала «а нужна ли эта работа вообще» (пагинация, агрегация на сервере, виртуализация), и только потом «как её лучше запланировать». Техники планирования соблазнительны тем, что локальны и не требуют переговоров с продуктом; из-за этого ими часто подпирают решения, которые надо менять на уровне данных.

### Точность таймеров против простоты

Таймер даёт «не раньше чем», и для анимаций, опросов, debounce этого достаточно. Там, где важна точность (отсчёт, синхронизация, измерение длительности), нужно опираться на показания часов, а не на число срабатываний. Цена точного подхода — дополнительный код; цена неточного — расхождение, которое накапливается и проявляется у пользователей, продержавших экран открытым дольше, чем разработчик.

## 7. Связи с другими частями системы

**Назад:**

- **[1.18 Promises](../18-promises/)** — промис планирует работу; этот урок объясняет, когда выполнится запланированное. Вместе они дают полный ответ: операция началась при создании, её результат попадёт в очередь, обработчик выполнится, когда цикл до него дойдёт;
- **[1.19 async/await](../19-async-await/)** — `await` возвращает управление циклу, и теперь понятно, **чем** цикл в это время занят: всем остальным, что есть в очереди. Фраза «`await` не блокирует» получает здесь механизм, а не просто утверждение;
- **1.15 Execution context** — стек вызовов как часть модели: задача выполняется, пока стек не опустеет;
- **1.11 Error handling** — ошибка, выброшенная в колбэке таймера, оказывается в другой задаче, чем `try/catch`, который её «должен был» поймать. Здесь видно, почему: другая задача — другой стек.

**Вперёд — внутри цепочки блока:**

- **[1.21 Microtasks и macrotasks](../21-microtasks-and-macrotasks/)** — уточнение этой модели. Здесь зафиксировано, что между задачами есть отдельный шаг; там он разбирается, и из него выводится точный порядок между `Promise.then`, `setTimeout` и синхронным кодом;
- **1.22 Memory** — задачи в очереди удерживают свои колбэки, а колбэки — замкнутое окружение: очередь это тоже источник удержания;
- **1.24 Синтез** — тяжёлая синхронная агрегация входит в компонент-пример как один из семи дефектов.

**Вперёд — за пределы блока:**

- **4.1 New Architecture** — JSI делает возможным синхронный вызов в нативный код; такой вызов блокирует JS-поток, и это новая по сравнению с вебом причина блокировки;
- **4.5 Hermes** — пауза сборки мусора — ещё один источник остановки JS-потока, которого нет в этой модели;
- **5.1 Модель исполнения** — главное продолжение урока: точная картина потоков вместо различения «JS thread ≠ UI thread» и привязка к тому, какой инструмент показывает какой слой;
- **5.2 Бюджет кадра** — переход от «поток занят» к «кадр не успел»: сколько миллисекунд есть на задачу, чтобы интерфейс остался плавным;
- **5.4 Списки** — виртуализация как главный способ не делать работу;
- **5.7 Reanimated и Gesture Handler** — worklet на UI-потоке: почему там анимация переживает блокировку JS;
- **5.10 Профилирование** — как доказать, что блокирует именно эта задача, вместо того чтобы рассуждать;
- **7.3 Таймауты** — таймер как «не раньше чем» и что из этого следует для сетевых таймаутов;
- **11.3 Тестирование асинхронного кода** — тесты, «работающие» за счёт `setTimeout`, и почему они нестабильны;
- **12.8 Performance investigation в инциденте** — та же модель под давлением времени: гипотеза о длинной задаче, замер, вывод.

**Главное, что должно остаться после урока.** Задача выполняется до конца, и «заблокировано» означает ровно это. В React Native к модели добавляется одно различение, меняющее все выводы: JS-поток — не тот поток, который рисует интерфейс, поэтому вопрос «что именно перестанет работать» всегда требует встречного вопроса — **где это выполняется**.
