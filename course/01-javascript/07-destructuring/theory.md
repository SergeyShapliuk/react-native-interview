# 1.7 Destructuring — theory

> 🟢 REFRESH. Синтаксис вы знаете. Два места, где он подводит: значение по умолчанию не срабатывает на `null`, который приходит с бэкенда, и деструктуризация не создаёт стабильных ссылок, хотя выглядит как «вытащить значение».

## Refresh

### Объекты и массивы

```js
const { id, title } = lesson;          // по имени свойства
const [first, second] = lessons;       // по позиции
```

Разница принципиальная: для объекта имя переменной обязано совпадать с именем свойства (или быть переименовано явно), для массива значение имеет только позиция, а имена произвольны.

Пропуск позиции в массиве — запятая без имени:

```js
const [, second] = lessons;            // первый элемент не нужен
const [current, , third] = lessons;
```

### Переименование

```js
const { id: lessonId, title: lessonTitle } = lesson;
```

Слева от двоеточия — имя свойства в объекте, справа — имя создаваемой переменной. Порядок обратный интуиции (ожидается «новое: старое»), и это стабильный источник путаницы при чтении.

### Значения по умолчанию применяются только к `undefined`

Главный факт урока:

```js
const { limit = 20 } = { limit: undefined };  // 20 — дефолт применился
const { limit = 20 } = { limit: null };       // null — дефолт НЕ применился
const { limit = 20 } = {};                    // 20 — свойства нет, значит undefined
const { limit = 20 } = { limit: 0 };          // 0 — ноль валидное значение
```

Правило: дефолт срабатывает ровно тогда, когда значение равно `undefined`. `null`, `0`, `""` и `false` — значения, и они проходят.

Это полностью согласуется со смыслом `undefined` и `null` из 1.2: `undefined` означает «не задано», и именно его дефолт замещает. `null` означает «задано как ничто» — то есть решение уже принято, и дефолт его не отменяет.

С `??` сравнение полезно держать рядом: `??` реагирует на **оба** nullish-значения, дефолт деструктуризации — только на `undefined`. Поэтому они не взаимозаменяемы:

```js
const { limit = 20 } = settings;              // null пройдёт
const limit = settings.limit ?? 20;           // null заменится на 20
```

### Вложенная деструктуризация

```js
const { progress: { done, steps } } = lesson;
```

Работает, пока промежуточный объект существует. Если `lesson.progress` равен `undefined` или `null` — `TypeError`, потому что происходит обращение к свойству отсутствующего значения.

Защита — дефолт на промежуточном уровне:

```js
const { progress: { done } = {} } = lesson;         // спасает от undefined
const { progress: { done } = {} } = { progress: null };  // TypeError: null прошёл
```

Второй случай показывает границу: дефолт на промежуточном уровне защищает от отсутствия, но не от `null`. А `null` — ровно то, что приходит с бэкенда чаще всего.

Отсюда практический вывод: **вложенная деструктуризация данных из внешнего источника требует либо гарантии на границе, либо отказа от вложенности в пользу явных шагов.** Второе читается хуже и падает реже.

### Деструктуризация в параметрах

```js
function LessonRow({ lesson, onPress, compact = false }) { ... }
```

Самая частая форма в React-коде. Две детали:

```js
function f({ a } = {}) { ... }   // вызов f() не упадёт
function f({ a }) { ... }        // вызов f() упадёт: нельзя деструктурировать undefined
```

Дефолт на весь параметр нужен тогда, когда функция может быть вызвана без аргумента, — например, если это колбэк, который вызывает чужой код.

### Деструктуризация не копирует объект

```js
const { progress } = lesson;
progress.done = true;          // изменён lesson.progress — тот же объект
progress === lesson.progress;  // true
```

Деструктуризация читает значение свойства и присваивает его новой переменной. Для объекта значение — ссылка (1.4). Никакой копии не возникает, и мутация через полученную переменную меняет исходные данные.

## RN relevance

### `null` с бэкенда и дефолты, которые не сработали

```js
const { title = "Без названия", duration = 0, tags = [] } = lessonFromApi;
```

Код выглядит защищённым. Если бэкенд прислал `{ title: null, duration: null, tags: null }`, то после деструктуризации в переменных окажутся три `null`, и дальше:

- `title` типа `null` в `<Text>{title}</Text>` отрендерится как ничего — тихий пустой заголовок;
- `duration` типа `null` в арифметике приведётся к `0`, и это случайно совпадёт с ожиданием — дефект останется незамеченным;
- `tags` типа `null` при вызове `tags.map(...)` даст **падение**: `Cannot read property 'map' of null`.

Все три из одного корня. И заметить это по коду трудно именно потому, что дефолты написаны: читающий видит защиту там, где её нет.

Что здесь важно для RN: `null` в полях — норма для многих бэкендов (так выражается «поле есть в схеме, значения нет»), а мобильный клиент не может на это влиять. Поэтому политика по `null` — проектное решение, а не частный случай (см. 1.9 и задание этого урока).

### Деструктуризация пропсов и мемоизация

```jsx
function LessonRow({ lesson }) {
  const { progress } = lesson;        // вытащили вложенный объект
  return <ProgressBar progress={progress} />;
}
```

Частое ожидание: «я деструктурировал пропс, значит зависимость стала точнее, и компонент будет перерисовываться реже». Это неверно.

Деструктуризация происходит **внутри** рендера, то есть уже после того, как React решил компонент перерисовать. Решение о рендере принимается по пропсам, которые пришли снаружи (`lesson`), а не по переменным, которые созданы внутри. Если родитель передал новый объект `lesson`, компонент перерисуется независимо от того, какие поля из него извлечены.

И наоборот: `progress`, полученный деструктуризацией, имеет ту же идентичность, что `lesson.progress`. Если `lesson` — новый объект, собранный через spread, а `progress` внутри него тот же — `ProgressBar` увидит прежнюю ссылку, и мемоизация сработает. Решает это идентичность вложенного объекта (1.4), а не наличие деструктуризации.

Вывод: деструктуризация — инструмент читаемости, а не инструмент оптимизации. Она ничего не делает со ссылками.

### Деструктуризация параметров навигации

```jsx
function LessonScreen({ route }) {
  const { lessonId, courseId } = route.params;   // упадёт, если params отсутствуют
}
```

`route.params` может быть `undefined`: экран открыт без параметров, открыт по deep link с неполным URL, открыт как начальный экран стека. Падение произойдёт на самой строке деструктуризации, то есть до любой проверки внутри компонента.

Форма, которая не падает: `const { lessonId } = route.params ?? {};`. Но важнее другое — отсутствие параметра это состояние, которое нужно обработать осознанно (показать ошибку, увести назад, загрузить по умолчанию), и `?? {}` только переносит проблему на строку ниже, где `lessonId` окажется `undefined`. Типизация параметров экрана — 4.16, проверка на границе — 2.13.

## Типичные заблуждения

**«Дефолт применится и к `null`.»** Возникает из того, что `null` и `undefined` воспринимаются как одно (1.3). Это самое дорогое заблуждение урока, потому что написанный дефолт создаёт ложное чувство защищённости: код выглядит проверенным, а падает на первых же данных с `null`.

**«Деструктуризация копирует объект.»** Возникает из формулировки «вытащить значение из объекта», которая звучит как извлечение, то есть создание чего-то нового. Копии нет: для объектов копируется ссылка, и мутация через новую переменную меняет исходные данные.

**«Вложенная деструктуризация безопасна при отсутствии промежуточного объекта.»** Возникает потому, что дефолт на промежуточном уровне действительно защищает — но только от `undefined`. На `null` обращение к свойству всё равно происходит, и это `TypeError`.

**«Деструктуризация пропсов улучшает мемоизацию.»** Возникает из верного наблюдения, что узкие зависимости лучше широких, применённого не к тому месту. Деструктуризация выполняется внутри рендера, то есть после решения о рендере; на это решение она повлиять не может.

**«Переименование работает как `новое: старое`.»** Возникает из аналогии с присваиванием, где слева новое имя. В деструктуризации слева — имя свойства в источнике. Ошибка даёт `undefined` в переменной и путаницу при чтении чужого кода.
