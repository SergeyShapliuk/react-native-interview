# 1.7 Destructuring — practice

## Проверка понимания

---

**1. Что будет при деструктуризации с дефолтом, если пришёл `null`?**

```js
const { limit = 20 } = { limit: null };
```

<details>
<summary>Ответ</summary>

`limit` будет равен `null`. Дефолт применяется ровно тогда, когда значение равно `undefined`; `null` — это значение, и оно проходит.

**Ответ «будет 20»** вскрывает самое дорогое заблуждение урока. Опасность не в самой ошибке, а в том, что написанный дефолт создаёт ложное чувство защищённости: код выглядит проверенным. Практическая цена — падение на `tags.map(...)`, когда бэкенд присылает `tags: null`.

**Ответ «будет 20, потому что `null` falsy»** вскрывает смешение двух механизмов. Falsy-правила работают в условиях и в `||` (1.3), а дефолт деструктуризации сравнивает именно с `undefined`. Разработчик, объясняющий дефолты через truthy/falsy, не сможет предсказать поведение на `0` и `""`: они falsy, но дефолт к ним не применится.
</details>

---

**2. Что произойдёт при `const { a: { b } } = obj`, если `obj.a` отсутствует?**

<details>
<summary>Ответ</summary>

`TypeError`: происходит обращение к свойству `b` у значения `undefined`.

Дефолт на промежуточном уровне спасает от отсутствия: `const { a: { b } = {} } = obj`. Но он **не** спасает от `obj.a === null` — там обращение к свойству всё равно произойдёт, и это снова `TypeError`.

**Ответ «`b` будет `undefined`»** вскрывает ожидание, что деструктуризация ведёт себя как optional chaining. Это разные вещи: `?.` прерывает цепочку (1.9), деструктуризация — нет.

**Ответ «упадёт, поэтому надо всегда ставить `= {}`»** частично верен, но вскрывает рецепт вместо решения. Дефолт `= {}` закрывает только `undefined`, а приходящее с бэкенда `null` остаётся. И главное: он переносит проблему на строку ниже, где `b` окажется `undefined` и поедет дальше по коду.
</details>

---

**3. Создаёт ли деструктуризация копию объекта?**

<details>
<summary>Ответ</summary>

Нет. Деструктуризация читает значение свойства и присваивает его новой переменной. Для объекта значение — ссылка, поэтому `progress === lesson.progress` даёт `true`, и мутация через полученную переменную меняет исходные данные.

**Ответ «да, создаёт»** вскрывает влияние формулировки «вытащить значение из объекта», которая звучит как извлечение чего-то нового. Практическое следствие ошибки — уверенность, что после деструктуризации данные можно свободно менять.

**Ответ «нет, но она улучшает мемоизацию, потому что зависимость стала точнее»** вскрывает отдельное заблуждение, разобранное в теории: деструктуризация выполняется внутри рендера, то есть после того, как React уже решил компонент перерисовать. На это решение она повлиять не может.
</details>

## Задание

**Дано.** Функция разбора ответа API в RN-приложении и компонент, который использует результат. Бэкенд выражает «значения нет» через `null`, а не через отсутствие поля, — это его нормальное поведение, и изменить его нельзя.

```js
// ответ сервера, типичный случай
const response = {
  id: 42,
  title: null,
  duration: null,
  tags: null,
  author: null,
  progress: { done: null, steps: null },
};

export function parseLesson(raw) {
  const {
    id,
    title = "Без названия",
    duration = 0,
    tags = [],
    author: { name: authorName = "Неизвестен" } = {},
    progress: { done = false, steps = [] } = {},
  } = raw;

  return { id, title, duration, tags, authorName, done, steps };
}
```

```jsx
function LessonCard({ raw }) {
  const { title, duration, tags, authorName, steps } = parseLesson(raw);

  return (
    <View>
      <Text>{title}</Text>
      <Text>{authorName}</Text>
      <Text>{duration} мин</Text>
      {tags.map((t) => (
        <Tag key={t} label={t} />
      ))}
      <Text>Шагов: {steps.length}</Text>
    </View>
  );
}
```

**Требуется.**

1. Для каждого из шести полей ответа предсказать, что окажется в результате `parseLesson`. Дефолт применился или нет — и почему.
2. Указать строку, на которой `parseLesson` **упадёт**, и объяснить, почему падение происходит внутри самой деструктуризации, а не позже.
3. Указать два места в `LessonCard`, которые упадут или покажут неверное значение, если убрать падение из пункта 2.
4. Переписать `parseLesson` так, чтобы она корректно работала и с отсутствующим полем, и с `null`. Назвать механизм, который вы выбрали, и объяснить, почему дефолты деструктуризации для этой задачи не подходят в принципе.
5. Сформулировать **политику по `null`** для домена как проектное решение: где отсутствие поля это нормальное значение с заглушкой, а где признак битых данных, на котором разбор должен отказать. Решение обосновать, а не выбрать «безопасный» вариант.

---

<details>
<summary>Разбор</summary>

**1. Что окажется в результате.**

| Поле ответа | Результат | Почему |
|---|---|---|
| `id: 42` | `42` | дефолта нет, значение прошло |
| `title: null` | **`null`** | дефолт применяется только к `undefined` |
| `duration: null` | **`null`** | то же |
| `tags: null` | **`null`** | то же |
| `author: null` | **`TypeError`** | дефолт `= {}` не применился (значение есть), и происходит обращение к свойству `name` у `null` |
| `progress: { done: null, steps: null }` | `done: null`, `steps: null` | промежуточный объект существует, дефолт `= {}` не нужен; внутренние дефолты не применились к `null` |

Из шести полей дефолт не применился ни разу. Функция написана так, как будто она защищена, и не защищена ни от чего, кроме отсутствующих полей, — а их в ответе нет.

**2. Где падает и почему именно там.**

```js
author: { name: authorName = "Неизвестен" } = {},
```

Дефолт `= {}` справа применяется только если `raw.author` равен `undefined`. Здесь `raw.author` равен `null` — значение есть, дефолт не нужен, и выполняется обращение `null.name`. Это `TypeError: Cannot read property 'name' of null`.

Почему падение происходит **внутри деструктуризации**, а не позже: деструктуризация это не объявление переменных с отложенным чтением, а выполняемая операция чтения свойств. Она разворачивается в последовательность обращений прямо в этой строке. Поэтому никакая проверка внутри функции ниже или внутри компонента не успеет сработать — стек обрывается на строке разбора.

Практическое следствие: такой код нельзя «подстраховать» проверкой после деструктуризации. Защита должна быть до или вместо неё.

**3. Что сломается в `LessonCard`, если `author` не был бы `null`.**

- **`tags.map((t) => ...)`** — `tags` окажется `null`, вызов `map` у `null` это `TypeError`. **Падение**, видимое сразу;
- **`steps.length`** — `steps` окажется `null`, обращение к `length` у `null` тоже `TypeError`. Второе падение по тому же механизму.

Тихие дефекты, которые при этом не упадут:

- **`<Text>{title}</Text>`** — `title` равен `null`, React не рендерит `null`: заголовок просто пустой. Никакой ошибки, просто карточка без названия;
- **`<Text>{duration} мин</Text>`** — React не рендерит `null`, поэтому на экране окажется « мин» без числа (а не «0 мин», как было задумано дефолтом). Обратите внимание: в шаблонной строке было бы иначе — `` `${duration} мин` `` даёт «null мин». Один и тот же `null` по-разному выглядит в JSX и в строке, и это ещё одна причина решать его на границе, а не в разметке.

Это хорошая иллюстрация к 1.3: одна причина (`null` вместо дефолта) даёт и громкие падения, и тихие неверные экраны, причём тихие опаснее.

**4. Переписанный разбор.**

```js
export function parseLesson(raw) {
  if (raw == null || typeof raw !== "object") {
    throw new LessonParseError("ответ не является объектом");
  }

  if (raw.id == null) {
    throw new LessonParseError("отсутствует обязательное поле id");
  }

  const author = raw.author ?? {};
  const progress = raw.progress ?? {};

  return {
    id: raw.id,
    title: raw.title ?? "Без названия",
    duration: raw.duration ?? 0,
    tags: raw.tags ?? [],
    authorName: author.name ?? "Неизвестен",
    done: progress.done ?? false,
    steps: progress.steps ?? [],
  };
}
```

**Выбранный механизм — `??`.** Он реагирует и на `undefined`, и на `null`, то есть покрывает оба способа выразить «значения нет».

**Почему дефолты деструктуризации для этой задачи не подходят в принципе.** Не потому, что они написаны неудачно, а потому, что они отвечают на другой вопрос. Дефолт деструктуризации означает «если значение **не задавали**». Данные из внешнего источника — это как раз тот случай, когда «не задавали» и «задали как ничто» приходят вперемешку, и различать их клиент не может и не должен. Инструмент, срабатывающий только на один из двух вариантов, здесь структурно не подходит — независимо от того, насколько аккуратно его применить.

Второй аргумент: вложенная деструктуризация с дефолтами на каждом уровне падает на `null` в промежуточном узле, и это падение нельзя перехватить внутри той же функции. Явные шаги (`raw.author ?? {}`) читаются хуже, но дают контролируемое поведение — и это осознанный обмен читаемости на предсказуемость.

Отдельно отмечу `raw.id == null`: это единственное место, где `==` оправдан — одной проверкой ловятся и `null`, и `undefined` (1.3).

**5. Политика по `null` как проектное решение.**

Политика не выводится из «безопасности» — она выводится из того, что приложение должно делать, когда данных нет. Решение для домена RN Academy:

| Поле | Политика | Обоснование |
|---|---|---|
| `id` | **отказ разбора** | без идентификатора урок невозможно сохранить, открыть по deep link, связать с прогрессом. Заглушка здесь создала бы запись-призрак, которая сломается позже и далеко от причины |
| `title` | заглушка | пустое название портит экран, но не делает данные бессмысленными; пользователь видит карточку и может её открыть |
| `duration` | `0` | отсутствие длительности это нормальное состояние (урок без видео), и `0` корректно участвует в агрегации |
| `tags`, `steps` | пустой массив | отсутствие коллекции и пустая коллекция семантически совпадают; код, перебирающий их, не нуждается в особом случае |
| `author` | заглушка | автор это метаданные, их отсутствие не мешает пройти урок |
| `progress.done` | `false` | отсутствие отметки означает «не завершён», и это не предположение, а определение |

**Правило, которое стоит из этого вывести:** отказ разбора оправдан там, где отсутствие поля делает невозможными **последующие операции** над сущностью, а не там, где оно просто неприятно. Для всего остального заглушка дешевле, потому что приложение продолжает работать.

**Чем платит эта политика.** Заглушки скрывают проблему на стороне бэкенда: если `title` приходит `null` для половины уроков, экран будет выглядеть сносно, и дефект никто не заметит. Поэтому политика заглушек должна сопровождаться наблюдаемостью — счётчиком того, как часто заглушка применилась. Это уже тема блока 10 (10.8), и здесь важно зафиксировать саму связь: **решение «подставить заглушку» это решение «не узнать о проблеме», если его не дополнить метрикой.**

**Куда это ведёт дальше.** Такой разбор, написанный руками, расходится с типами через несколько месяцев: тип говорит `title: string`, а проверки живут отдельно и о типе ничего не знают. Решение — схема как единственный источник и типа, и проверки (2.12). Эта функция — та самая мотивация, из которой тот урок растёт.
</details>
