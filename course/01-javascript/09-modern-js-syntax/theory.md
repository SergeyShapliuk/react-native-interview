# 1.9 Modern JS syntax — theory

> 🟢 REFRESH. Ось урока — не сам синтаксис, который вы пишете каждый день, а цена его применения: `?.` превращает ошибку в тихий `undefined`, и решение о том, где это допустимо, принимается не оператором, а знанием контракта данных.

## Refresh

### Optional chaining: что именно проверяется

**Optional chaining (`?.`, опциональная цепочка)** — синтаксис, который прерывает вычисление цепочки и возвращает `undefined`, если значение слева от `?.` равно `null` или `undefined`.

Ключевое слово здесь — **слева**. `?.` не проверяет то, к чему обращается, он проверяет то, от чего обращается:

```js
user?.profile.avatar
```

Проверен `user`. `profile` не проверен: если `user` существует, но `profile` отсутствует, обращение к `avatar` бросит `TypeError`. Защита каждого звена требует `?.` на каждом звене: `user?.profile?.avatar`.

Второй ключевой факт: условие — именно **nullish**, то есть `null` или `undefined`, и ничего больше. Разница с falsy разобрана в 1.3 и здесь не повторяется, но она ровно та же: `0?.toFixed(2)` работает, `""?.length` даёт `0`.

### Три формы

| Форма | Запись | Что проверяется |
|---|---|---|
| Свойство | `a?.b` | `a` на nullish |
| Индекс | `a?.[key]` | `a` на nullish |
| Вызов | `a.b?.()` | `a.b` на nullish |

Формы различаются тем, какое значение попадает под проверку, и из этого следует практическое различие:

```js
listeners.onChange?.(value);  // проверен onChange — метода может не быть
listeners?.onChange(value);   // проверен listeners — объекта может не быть
```

Первая запись защищает от «колбэк не передан». Вторая — от «объекта нет», но если объект есть, а `onChange` в нём нет, будет `TypeError: listeners.onChange is not a function`. Это не стилистический выбор, а два разных утверждения о том, что в данных необязательно.

Отдельно: `a?.b` защищает от nullish `a`, но **не** от того, что `a` — число или строка. `(5)?.foo.bar` падает, потому что `5` не nullish, `5.foo` даёт `undefined`, и дальше идёт обращение к свойству `undefined`.

### Короткое замыкание всей цепочки

`?.` замыкает не одно звено, а **весь остаток цепочки**, включая вызовы и индексы:

```js
const r = a?.b.c.d();   // a === null → undefined, b/c/d не вычисляются вообще
```

Из этого следует неочевидное: аргументы не вычисляются тоже.

```js
obj?.method(getExpensiveArg());  // obj === null → getExpensiveArg() НЕ вызовется
```

Если в аргументе есть побочный эффект — инкремент счётчика, логирование, запись в стор — он не произойдёт. Это тот же механизм короткого замыкания, что у `&&` и `||`: правый операнд не вычисляется, если результат уже известен.

Замыкание ограничено **своей** цепочкой. Скобки её разрывают:

```js
(a?.b).c    // a === null → TypeError: Cannot read property 'c' of undefined
a?.b.c      // a === null → undefined
```

### Что `?.` не делает

- **не защищает от падения ниже по коду.** `const n = user?.name` при отсутствии `user` даёт `undefined`, и `n.trim()` на следующей строке падает. Ошибка просто переехала на строку вниз;
- **не работает на присваивание.** `a?.b = 1` — синтаксическая ошибка;
- **не создаёт промежуточные объекты.** Это чтение, не запись;
- **не делает значение безопасным для React.** `undefined` React не рендерит, но и ничего не показывает — отсюда весь сюжет раздела RN relevance.

### Nullish coalescing и logical assignment

**Nullish coalescing (`??`)** — подстановка альтернативы, если левая часть nullish. Отличие от `||` — тема 1.3; здесь нужно только одно следствие: `?.` и `??` работают на одном и том же условии, поэтому связка `a?.b ?? fallback` однородна, а `a?.b || fallback` смешивает два разных условия в одном выражении.

Приоритет: `??` нельзя смешивать с `||` и `&&` без скобок — это синтаксическая ошибка, а не предупреждение линтера.

```js
a || b ?? c      // SyntaxError
(a || b) ?? c    // ок
```

Запрет сделан намеренно: порядок здесь неинтуитивен, и язык требует указать его явно.

**Logical assignment (логическое присваивание)** — три оператора, объединяющие проверку и присваивание:

| Оператор | Присваивает, если левая часть... | Эквивалент |
|---|---|---|
| `a ??= b` | nullish | `a ?? (a = b)` |
| `a \|\|= b` | falsy | `a \|\| (a = b)` |
| `a &&= b` | truthy | `a && (a = b)` |

Эквивалент важнее самой записи. Все три **замыкают присваивание**: если условие не выполнено, присваивания не происходит вовсе. Это не то же самое, что `a = a ?? b`:

```js
obj.count ??= 0;      // при существующем count сеттер не вызывается
obj.count = obj.count ?? 0;  // сеттер вызывается всегда
```

Для обычного объекта разницы не видно. Она видна там, где присваивание наблюдаемо: сеттер, прокси, объект под наблюдением MobX, поле в объекте, на который подписан ре-рендер. Лишняя запись того же значения может вызвать уведомление об изменении.

### Транспиляция

**Transpilation (транспиляция)** — преобразование исходного кода в код на том же языке, но в синтаксисе, который понимает целевой движок. В React Native это делает Babel в составе Metro.

Во что превращается `?.`: во временную переменную и условие.

```js
// было
const city = user?.address?.city;

// примерно во что превращается
var _user$address;
const city =
  user === null || user === void 0
    ? void 0
    : (_user$address = user.address) === null || _user$address === void 0
      ? void 0
      : _user$address.city;
```

Три наблюдения, которые стоит удержать:

- проверка — именно на `null` и `undefined` (`void 0`), а не на truthy. Транспилированный код подтверждает семантику;
- появляются временные переменные. Длинная цепочка `a?.b?.c?.d?.e` разворачивается в соответствующее число проверок и переменных — это не бесплатная конструкция, хотя цена и мала;
- вычисление левой части происходит **один раз** — она сохраняется в переменную. Поэтому `getUser()?.name` вызывает `getUser` однократно.

`??` разворачивается аналогично, `??=` — в условие плюс присваивание.

Нужна ли транспиляция — зависит от движка и от целевого синтаксиса в конфигурации Babel. И здесь начинается вторая половина урока.

## RN relevance

### `?.` превращает дефект данных в пустое место на экране

Главный сюжет урока. Рассмотрим карточку курса:

```jsx
<Text>{course?.title}</Text>
<Text>{course?.author?.name}</Text>
```

Если `course` не пришёл, экран отрендерится. Без падения, без сообщения, без записи в crash reporting. Пользователь увидит карточку с пустыми строками, решит, что приложение сломано, и закроет его. Метрики при этом чистые: крашей нет, запрос прошёл, экран отрисован.

Это принципиально хуже падения. Падение попадает в crash reporting со стектрейсом, воспроизводится и чинится. Тихое пустое место не попадает никуда и обнаруживается через поддержку — тот же вывод, что в 1.3 про подмену валидных значений, но механизм другой: там значение подменялось, здесь оно исчезает.

### Где `?.` уместен, а где прячет неверный контракт

Решение принимается не по виду кода, а по ответу на один вопрос: **может ли это поле законно отсутствовать?**

```jsx
// Уместно: аватар — необязательное поле, его отсутствие нормально
{user.avatarUrl && <Image source={{ uri: user.avatarUrl }} />}
<Text>{user.bio ?? "Нет описания"}</Text>

// Прячет проблему: у курса обязан быть заголовок
<Text>{course?.title}</Text>
```

Во втором случае `?.` отвечает не на вопрос «что показать, если заголовка нет», а на вопрос «как не упасть». Это разные вопросы, и ответ на второй не является ответом на первый.

Если обязательное поле отсутствует — **контракт с бэкендом нарушен**, и это событие, о котором нужно узнать. Варианты обработки есть, и ни один из них не `?.`:

```js
// 1. Явная ошибка разбора на границе
function parseCourse(raw) {
  if (raw?.title == null) {
    throw new Error(`Курс ${raw?.id}: отсутствует title`);
  }
  return { id: raw.id, title: raw.title, author: raw.author ?? null };
}

// 2. Экран ошибки вместо пустого экрана
if (!course) return <ErrorState onRetry={refetch} />;

// 3. Отчёт в мониторинг с продолжением работы, если экран важнее поля
if (course.title == null) {
  reportIssue("course.title missing", { courseId: course.id });
}
```

Третий вариант — компромисс, и он законен: иногда показать экран важнее, чем упасть. Важно то, что отсутствие поля при этом **зафиксировано**, а не проглочено.

Практическое следствие: `?.` в коде экрана — обычно симптом того, что разбор данных не сделан на границе. Поле либо обязательно (тогда проверка принадлежит границе, 2.12), либо необязательно (тогда дефолт проставляется при разборе, и в экране `?.` не нужен). Единое место разбора ответа сервера — тема 7.2.

### Длинная цепочка `?.` — сигнал о неверной структуре

```js
const name = response?.data?.items?.[0]?.author?.profile?.displayName;
```

Такая строка сообщает: **никто не знает, что приходит с сервера**. Каждый `?.` добавлен в ответ на отдельное падение в проде. Строка не падает, но и не работает: при любом нарушении структуры получается `undefined`, и причину найти невозможно — неизвестно, на каком звене цепочка оборвалась.

Отладочная техника на такой случай: развернуть цепочку и проверить звенья по одному, либо залогировать `response` целиком. Но системное решение — валидация на границе.

### `?.` и условный рендер

Знакомая ловушка из 1.3 в новой форме:

```jsx
{items?.length && <List items={items} />}
```

`?.` здесь не помогает. При `items === undefined` выражение даёт `undefined` — React не отрендерит, нормально. Но при пустом массиве даёт `0`, и в React Native это падение «text strings must be rendered within a `<Text>` component». `?.` защитил от одного исхода и не затронул второй:

```jsx
{(items?.length ?? 0) > 0 && <List items={items} />}
```

### `?.()` и колбэки в пропсах

Наиболее бесспорно уместное применение в RN-коде:

```jsx
function Row({ onPress, onLongPress }) {
  return (
    <Pressable
      onPress={() => onPress?.(item.id)}
      onLongPress={() => onLongPress?.(item.id)}
    />
  );
}
```

Необязательный колбэк — именно та ситуация, для которой `?.()` создан: отсутствие обработчика не дефект, а штатный случай, и альтернативы (`onPress && onPress(id)`, дефолтное значение `() => {}`) хуже либо по читаемости, либо по числу созданных функций.

Та же форма в вызовах нативных модулей — где метода может не быть на одной из платформ или в старой версии нативной части:

```js
NativeModules.Analytics?.setUserId?.(id);
```

Здесь две проверки отвечают на два разных вопроса: модуль мог не слинковаться, и метод мог отсутствовать в этой версии нативного кода. Это тот редкий случай, когда цепочка из двух `?.` описывает реальную неопределённость, а не маскирует незнание.

### Hermes и поддержка синтаксиса

**Hermes** — JS-движок, на котором по умолчанию работает React Native; подробно — в 4.5. Для этого урока важны два факта.

**Первый: Hermes поддерживает `?.`, `??` и логическое присваивание нативно.** Это значит, что Babel может их не транспилировать, и в бандл попадёт исходный синтаксис — короче, без временных переменных, и для Hermes быстрее, потому что он исполняет это как собственную операцию, а не как развёрнутое условие.

**Второй: включается это конфигурацией, а не само.** Пресет `@react-native/babel-preset` знает про целевой движок, но результат зависит от версии пресета, от версии RN и от того, что добавлено в `babel.config.js` руками. Типичная ситуация в проекте с историей: кто-то когда-то добавил `@babel/plugin-proposal-optional-chaining` или собственный `targets`, и теперь синтаксис транспилируется без надобности во всём приложении.

Практические следствия, из-за которых это вообще стоит знать:

- **размер бандла.** Транспилированный `?.` заметно длиннее исходного, и при массовом применении разница в бандле измерима. Hermes компилирует бандл в **bytecode** (заранее подготовленное представление кода, которое не нужно парсить на устройстве, 4.5) — и чем меньше исходного кода, тем меньше bytecode и быстрее startup;
- **отладка.** Транспилированный код в стектрейсах и в отладчике выглядит как сгенерированные `_user$address` вместо исходных имён. Source maps это обычно скрывают, но не всегда — и тогда непонятно, на что вообще смотришь;
- **расхождение dev и release.** Конфигурация Babel может отличаться по окружениям. Синтаксис, который работает в dev, в release-сборке проходит через другой набор плагинов — и редкие, но болезненные расхождения поведения живут здесь;
- **библиотеки приходят уже собранными.** Пакет из npm транспилирован под свои targets, а не под ваши. Его код в бандле может содержать развёрнутые проверки, даже если ваш — нет.

Проверить фактическое состояние можно: собрать бандл и посмотреть, есть ли в нём `?.` или `=== void 0`.

## Типичные заблуждения

**«`?.` защищает от любых ошибок доступа.»** Возникает из названия: «опциональная цепочка» звучит как «цепочка целиком необязательна». На самом деле каждый `?.` проверяет ровно одно значение — то, что слева от него, — и ровно на два условия, `null` и `undefined`. `user?.profile.avatar` не защищён от отсутствующего `profile`, а `data?.value.toFixed()` не защищён от того, что `value` — строка. Заблуждение подкрепляется тем, что в большинстве случаев первого звена действительно достаточно, и ошибка проявляется редко.

**«`??` и `||` взаимозаменяемы.»** Разобрано в 1.3; в контексте этого урока добавляется новая форма — смешивание в одном выражении: `a?.b || fallback`. Здесь `?.` реагирует на nullish, а `||` — на falsy, то есть выражение проверяет данные по двум разным критериям. Валидный `0`, полученный через `?.`, будет затёрт дефолтом. Однородная запись — `a?.b ?? fallback`.

**«Современный синтаксис всегда работает нативно без транспиляции.»** Возникает из верного наблюдения, что код работает. Он работает в любом случае — транспилированный тоже, и отличить нельзя по поведению, только по бандлу. Отсюда ощущение, что вопрос несущественный. Существенным он становится в трёх точках: размер бандла и startup на слабых устройствах, читаемость стектрейсов, расхождение dev и release. Плюс обратное заблуждение той же природы: «Hermes поддерживает всё» — нативная поддержка у каждой версии движка своя, и именно поэтому Babel в цепочке сборки остаётся.

**«`a ??= b` — это сокращение для `a = a ?? b`.»** Возникает по аналогии с `+=`, которое действительно является сокращением. Логическое присваивание дополнительно замыкает саму операцию записи: при не выполненном условии присваивания нет. Разница незаметна для обычного поля объекта и заметна там, где запись наблюдаема — сеттер, прокси, реактивное состояние: лишнее присваивание того же значения вызывает уведомление об изменении.

**«`?.` ничего не стоит, можно ставить везде.»** Возникает потому, что цена действительно мала и в профайлере не видна. Настоящая цена не в производительности, а в том, что каждый `?.` — утверждение «это поле может отсутствовать», и когда утверждение неверно, код сообщает читателю ложь о структуре данных. Экран, где `?.` стоит на всех обращениях, не содержит информации о том, что обязательно, а что нет, — и следующий разработчик вынужден выяснять это заново по бэкенду.

**«Если `?.` вернул `undefined`, значит данных нет.»** Возникает из того, что это самая частая причина. Но `undefined` на выходе цепочки может означать и «поле есть, в нём лежит `undefined`», и «цепочка оборвалась на первом звене», и «оборвалась на третьем». Результат одинаков, причины разные, и по результату их не различить. Это прямая причина того, почему отладка длинных цепочек тяжела, и ещё один аргумент за проверку на границе (2.12), где причина ещё известна.
