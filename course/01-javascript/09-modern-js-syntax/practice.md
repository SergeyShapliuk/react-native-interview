# 1.9 Modern JS syntax — practice

## Проверка понимания

Цель — не оценка, а обнаружение пробела. У каждого вопроса указано, что вскрывает неверный ответ.

---

**1. Чем `a?.b()` отличается от `a.b?.()`?**

<details>
<summary>Ответ</summary>

Разные операнды под проверкой.

`a?.b()` проверяет **`a`**. Если `a` nullish — результат `undefined`, `b` не читается, вызова нет. Если `a` существует, но `b` в нём отсутствует — `TypeError: a.b is not a function`.

`a.b?.()` проверяет **`a.b`**. Если `a` nullish — `TypeError` немедленно, на чтении `b`. Если `a` есть, а `b` нет — результат `undefined`, вызова нет.

То есть каждая запись защищает ровно от одного из двух отказов и никак не прикрывает другой. Защита от обоих — `a?.b?.()`.

Практически это выбор утверждения о данных: `a?.b()` говорит «объекта может не быть, но если он есть — метод в нём обязан быть»; `a.b?.()` говорит «объект обязателен, метод необязателен» (типичный необязательный колбэк в пропсах).

**Неверный ответ «ничем, обе формы защищают вызов»** вскрывает отсутствие модели «`?.` проверяет то, что слева». Это корневое заблуждение урока: из него следует и вера в то, что `user?.profile.avatar` защищает весь путь. Цена — падение в проде на цепочке, которая выглядит защищённой.

**Ответ «вторая форма — это то же самое, просто вызов функции»** вскрывает чтение `?.` как пометки «эта строка безопасна», без разбора на операнды. Проверка: предсказать поведение обеих форм при `a = {}` — результаты противоположные (`TypeError` против `undefined`).

**Ответ «разница в том, что первая форма работает, а вторая синтаксически странная»** вскрывает незнакомство с формой `?.()` как таковой. Она не экзотика: это основной способ вызвать необязательный колбэк из пропсов, и в коде RN-проектов встречается чаще, чем `?.` на свойствах.
</details>

---

**2. Что вернёт `0 ?? 5` и `0 || 5`?**

<details>
<summary>Ответ</summary>

`0 ?? 5` даёт `0` — ноль не `null` и не `undefined`, альтернатива не подставляется. `0 || 5` даёт `5` — ноль falsy.

Механизм разобран в 1.3. Здесь важно следствие для этого урока: `?.` и `??` срабатывают **на одном и том же условии** (nullish), поэтому `a?.b ?? d` — однородное выражение, а `a?.b || d` смешивает два разных критерия в одной строке и затирает валидный `0`, добытый через `?.`.

**Ответ «оба вернут 5»** вскрывает слияние falsy и nullish в один список — ровно то заблуждение, которое даёт дефект «валидное значение подменено дефолтом». Самый дорогой класс ошибок, потому что данные не пустые, а подменённые, и на экране это неразличимо.

**Ответ «оба вернут 0, ведь ноль — это значение»** вскрывает обратную ошибку: перенос семантики `??` на `||`. Следствие на практике — уверенность, что `settings.limit || 20` корректен, тогда как `limit: 0` там превратится в `20`.

**Ответ «верну правильно, но зачем это, если я всегда пишу `??`»** вскрывает рецепт вместо решения. `||` корректен там, где `0` или `""` действительно означают отсутствие данных. Выбор между операторами — решение о смысле поля, и «всегда `??`» ошибается в тех местах, где пустая строка должна заменяться заглушкой.
</details>

---

**3. Где `?.` скрывает ошибку контракта, а не отсутствие данных?**

<details>
<summary>Ответ</summary>

Там, где поле по контракту **обязательно**. `course?.title` в карточке курса: заголовок обязан быть у каждого курса. Если его нет, произошло одно из двух — бэкенд прислал не то, что обещал, либо разбор ответа потерял поле. И то и другое — событие, о котором нужно узнать; `?.` это событие уничтожает, оставляя пустую строку на экране.

Отличие от законного применения: `user.avatarUrl` может отсутствовать по контракту, и обработка отсутствия — часть нормальной логики экрана. Критерий ровно один: **может ли это поле законно отсутствовать?** Ответ берётся из контракта API, а не из вида кода.

Признаки маскировки контракта: цепочки из трёх и более `?.`; `?.` на корневом объекте экрана, без которого экран бессмысленен; `?.` появившийся в ответ на падение в проде, а не по решению о данных.

**Ответ «везде, `?.` всегда плохо»** вскрывает подмену решения запретом. `?.()` для необязательного колбэка, `?.` для необязательного поля, `NativeModules.X?.method?.()` для платформенной разницы — законные применения, которых ни один линтер не должен запрещать.

**Ответ «нигде, `?.` просто защищает от падения»** вскрывает отождествление «не упало» с «работает». Экран без падения и с пустыми полями хуже падения: он не попадает в crash reporting, метрики остаются чистыми, и дефект обнаруживается через поддержку спустя недели.

**Ответ «там, где надо было поставить `??` с дефолтом»** вскрывает смещение проблемы на один шаг. Дефолт вместо `undefined` убирает пустое место на экране, но нарушение контракта по-прежнему остаётся незамеченным — только теперь оно выглядит как настоящие данные. Для обязательного поля нужна не подстановка, а ошибка разбора или отчёт в мониторинг (2.12, 7.2).
</details>

## Задание

**Дано.** Экран профиля подписки в RN-приложении. Он не падает — и именно поэтому попал в продакшен. Поддержка жалуется: часть пользователей видит экран, на котором «ничего не написано», а кнопка продления иногда не реагирует на нажатие.

Контракт API, который обещает бэкенд:

- `subscription` — объект, присутствует всегда (для пользователей без подписки `plan` равен `"none"`);
- `subscription.plan`, `subscription.renewsAt` — обязательные;
- `subscription.discountPercent` — необязательное, отсутствует при отсутствии скидки;
- `subscription.paymentMethod` — необязательное, отсутствует до привязки карты.

```jsx
function SubscriptionScreen({ route, navigation }) {
  const userId = route.params?.userId;
  const { data, error } = useSubscription(userId);

  const subscription = data?.subscription;
  const plan = subscription?.plan ?? "none";
  const discount = subscription?.discountPercent || 0;
  const cardLast4 = subscription?.paymentMethod?.card?.last4;
  const renewsAt = subscription?.renewsAt;

  const handleRenew = () => {
    analytics?.track?.("renew_pressed", { plan, userId });
    navigation?.navigate?.("Checkout", { plan });
  };

  return (
    <View>
      <Text>{PLAN_TITLES?.[plan]}</Text>
      <Text>Продление: {renewsAt ? formatDate(renewsAt) : ""}</Text>

      {discount && <Text>Скидка {discount}%</Text>}

      <Text>Карта: •••• {cardLast4 ?? "не привязана"}</Text>

      <Pressable onPress={() => subscription?.canRenew && handleRenew()}>
        <Text>Продлить</Text>
      </Pressable>
    </View>
  );
}
```

**Требуется.**

1. Разделить все `?.` в этом коде на три группы: уместные (поле необязательно по контракту), маскирующие нарушение контракта, и бессмысленные (проверяется то, что не может быть nullish). Для каждого из второй группы сказать, какое именно событие остаётся незамеченным.
2. Объяснить, почему пользователь видит «экран, на котором ничего не написано», и почему этот исход хуже падения.
3. Найти причину того, что кнопка продления иногда не реагирует. Ответ должен называть механизм, а не предлагать исправление.
4. Найти два места, где условный рендер или подстановка дефолта сломаются на валидном значении. Для каждого сказать, что увидит пользователь.
5. Переписать экран. Для каждого изменения назвать решение о данных, которое за ним стоит, и сказать, где это решение должно приниматься — в экране или на границе разбора ответа.

---

<details>
<summary>Разбор</summary>

**1. Три группы.**

| Выражение | Группа | Почему |
|---|---|---|
| `route.params?.userId` | уместно с оговоркой | параметры навигации могут отсутствовать при некорректном deep link; но `userId` для этого экрана обязателен, и его отсутствие — отдельная ветка, а не `undefined` |
| `data?.subscription` | маскирует | `data` отсутствует, пока запрос не завершён, — это законно. Но ниже результат используется так, будто загрузка уже кончилась: состояния loading и error на экране нет вообще |
| `subscription?.plan` | маскирует | по контракту `subscription` присутствует всегда. Если его нет — бэкенд нарушил контракт либо запрос упал, и `?.` стирает оба события |
| `subscription?.discountPercent` | уместно | поле необязательное по контракту |
| `subscription?.paymentMethod?.card?.last4` | смешанное | `paymentMethod?.` уместно (необязательное поле). `card?.` и `last4` в контракте не описаны вообще — это цепочка, добавленная наугад |
| `subscription?.renewsAt` | маскирует | поле обязательное |
| `analytics?.track?.()` | уместно | аналитика может быть не инициализирована или выключена в dev; её отсутствие не должно ломать экран |
| `navigation?.navigate?.()` | бессмысленно | внутри экрана, отрендеренного навигатором, `navigation` есть по определению. Проверка не защищает ни от чего и сообщает читателю ложь: «этот экран может рендериться вне навигатора» |
| `PLAN_TITLES?.[plan]` | бессмысленно | модульная константа. Если она nullish, это ошибка импорта или циклическая зависимость (1.10), которую нужно видеть, а не глотать |
| `subscription?.canRenew` | маскирует вдвойне | `canRenew` в контракте не существует. `?.` маскирует отсутствие `subscription`, а само поле — опечатка или остаток от прежней версии API |

**Какие события остаются незамеченными:** «запрос не вернул данные» (`data?.`), «бэкенд не прислал обязательный объект подписки» (`subscription?.plan`, `subscription?.renewsAt`), «ответ не соответствует контракту по форме» (`card?.last4`, `canRenew`). Ни одно из них не попадает ни в логи, ни в crash reporting.

**2. Пустой экран.**

`data` равен `undefined` — на время загрузки, при ошибке сети, при неверном `userId`. Дальше все производные значения получают `undefined` или дефолт, и экран рендерится целиком:

- `PLAN_TITLES?.[plan]` при `plan === "none"` — вероятно `undefined`, пустой `Text`;
- `renewsAt ? ... : ""` — пустая строка после «Продление:»;
- `cardLast4 ?? "не привязана"` — «Карта: •••• не привязана»;
- кнопка на месте и нажимается.

Получается работающий с виду экран, утверждающий неверные факты о подписке пользователя. Переменная `error` из хука **получена и не использована** — это и есть корень: данных об ошибке достаточно, но `?.` сделал ветку обработки ненужной с точки зрения компилятора и человека.

Почему хуже падения: падение попадает в crash reporting со стектрейсом, воспроизводится, чинится за часы. Этот экран не попадает никуда — крашей нет, запросы в метриках проходят, экран отрисован. Дефект живёт до жалобы в поддержку, а жалоба звучит как «ничего не написано» и не воспроизводится у разработчика с валидной подпиской. Тот же вывод, что в 1.3, но здесь ошибку стёр не `||`, а `?.`.

**3. Кнопка.**

```jsx
onPress={() => subscription?.canRenew && handleRenew()}
```

Механизм: поля `canRenew` в ответе нет — ни по контракту, ни фактически. `subscription?.canRenew` всегда `undefined`, `undefined && handleRenew()` замыкается по короткому замыканию, и `handleRenew` **не вызывается никогда**. Нажатие обрабатывается, `Pressable` даёт визуальный отклик, ничего не происходит.

«Иногда не реагирует» — неточное описание от поддержки: не реагирует всегда. Пользователи, у которых переход всё же случался, попадали в Checkout другим путём — из другого экрана или по deep link.

Почему это не нашли раньше: ошибки нет, лог чист, кнопка визуально работает. Если бы вместо `?.` стояло прямое обращение `subscription.canRenew`, оно тоже дало бы `undefined` и то же поведение — но тогда отсутствие `subscription` падало бы заметно, и до `canRenew` дело дошло бы при отладке.

**4. Два места на валидном значении.**

**`subscription?.discountPercent || 0`** — здесь `||` вместо `??`. Скидка `0` и отсутствующая скидка дают одно и то же, что в этом месте случайно безвредно (оба исхода означают «скидки нет»). Настоящая проблема строкой ниже.

**`{discount && <Text>Скидка {discount}%</Text>}`** — при `discount === 0` выражение возвращает `0`, и `0` попадает прямо в `View`. В React Native это ошибка «Text strings must be rendered within a `<Text>` component» в LogBox в dev-сборке; в release ни ошибки, ни нуля — узел молча не отображается (1.3). То есть экран, напичканный `?.` ради защиты от ошибок, ломается на самом обычном случае — пользователь без скидки, — и в release этого даже не видно. Это главная ирония задания: `?.` защищает от nullish и ничего не знает про falsy.

Корректно: `{discount > 0 && ...}`.

**`{renewsAt ? formatDate(renewsAt) : ""}`** — третье место, если считать строго. Пустая строка в условии вместо явного «нет данных» означает, что отсутствие обязательного поля выглядит как нормальная отрисовка. Пользователь видит «Продление: » без значения.

**5. Переписанный экран.**

```jsx
function SubscriptionScreen({ route, navigation }) {
  // решение: userId обязателен для экрана; его отсутствие — некорректный deep link,
  // а не пустое состояние. Решение принимается в экране: это его входной контракт
  const userId = route.params?.userId;

  // хук вызывается ДО любого раннего return: правила хуков требуют одинакового
  // порядка вызовов на каждом рендере (3.5). Поэтому хук обязан принимать
  // отсутствующий userId и в этом случае не делать запрос
  const { data, error, isLoading, refetch } = useSubscription(userId, {
    enabled: userId != null,
  });

  if (userId == null) return <ErrorState message="Некорректная ссылка" />;

  // решение: три состояния экрана различимы и обработаны явно
  if (isLoading) return <LoadingState />;
  if (error) return <ErrorState onRetry={refetch} />;

  // решение: subscription обязателен по контракту. Отсутствие — нарушение контракта,
  // а не пустое состояние. Проверка здесь — временная мера; место ей на границе (2.12)
  const subscription = data?.subscription;
  if (subscription == null) {
    reportIssue("subscription missing in response", { userId });
    return <ErrorState onRetry={refetch} />;
  }

  // решение: обязательные поля читаются напрямую, без ?. — код честно говорит,
  // что они обязательны. Но деструктуризация отсутствующего поля НЕ падает:
  // plan и renewsAt окажутся undefined и уйдут дальше. Гарантию даёт только
  // проверка на границе (2.12), до которой этот экран не должен получить ответ
  const { plan, renewsAt } = subscription;

  // решение: скидка необязательна, её отсутствие и ноль значат одно и то же;
  // ?? однороден с ?. выше
  const discount = subscription.discountPercent ?? 0;

  // решение: способ оплаты необязателен; наугад угаданная вложенность card.last4
  // убрана — форма поля уточняется по контракту, а не перебором ?.
  const cardLast4 = subscription.paymentMethod?.last4;

  const handleRenew = () => {
    // решение: аналитика необязательна, её отсутствие не ломает экран
    analytics?.track?.("renew_pressed", { plan, userId });
    // решение: navigation внутри навигатора существует всегда — проверка убрана
    navigation.navigate("Checkout", { plan });
  };

  // решение: отсутствие названия тарифа — расхождение словаря и API, не данных
  const planTitle = PLAN_TITLES[plan] ?? plan;

  return (
    <View>
      <Text>{planTitle}</Text>
      <Text>Продление: {formatDate(renewsAt)}</Text>

      {/* решение: ноль — валидная скидка, сравнение явное */}
      {discount > 0 && <Text>Скидка {discount}%</Text>}

      <Text>
        {cardLast4 != null ? `Карта: •••• ${cardLast4}` : "Карта не привязана"}
      </Text>

      {/* решение: право на продление выводится из тарифа, а не из поля,
          которого в контракте нет */}
      <Pressable disabled={plan === "none"} onPress={handleRenew}>
        <Text>Продлить</Text>
      </Pressable>
    </View>
  );
}
```

**Где какое решение принимается.**

| Решение | Место |
|---|---|
| `userId` обязателен для экрана | в экране — это его входной контракт |
| три состояния: loading / error / данные | в экране — это его UI-логика |
| `subscription` присутствует всегда | **на границе** (2.12): схема ответа отвергает ответ без него, и экран получает уже проверенные данные |
| `plan`, `renewsAt` обязательны | **на границе** — по той же причине |
| `discountPercent` отсутствует → `0` | **на границе**: дефолт для необязательного поля проставляется при разборе, и экран не повторяет это решение |
| форма `paymentMethod` | **на границе** — именно там выясняется, `last4` лежит в `paymentMethod` или в `paymentMethod.card` |
| `canRenew` не существует | в контракте — поле либо добавляется бэкендом, либо право выводится из `plan` |

После переноса проверок на границу `?.` в экране остаётся в двух местах: `route.params?.userId` и `analytics?.track?.()`. Оба — настоящая необязательность, а не незнание структуры. Это и есть рабочий критерий: **если `?.` можно убрать, усилив разбор на границе, значит он маскировал контракт, а не описывал его.**

**Чего разбор сознательно не делает.**

Не предлагает закрыть класс дефектов типами. Тип `Subscription` с обязательным `title: string` не мешает серверу прислать `null` — тип проверяется при сборке, данные приходят в рантайме. Почему объявленный тип не является гарантией и что ставить на границу вместо него — 2.12. Где физически живёт разбор ответа, чтобы он был один на приложение, — 7.2.

Не обсуждает, во что всё это транспилируется: для разобранных дефектов это не имеет значения. Транспиляция важна в других вопросах — размер бандла, startup, читаемость стектрейсов (4.5), — и смешивать два сюжета в одном разборе не нужно.

Не предлагает запретить `?.` линтером. Из таблицы в пункте 1 видно, что уместных применений в этом же файле несколько, и правило «не использовать» отбросило бы их вместе с проблемными.
</details>
