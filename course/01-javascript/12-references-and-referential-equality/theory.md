# 1.12 References и referential equality — theory

> 🟡 DEEP DIVE. Семь углов разбора. Урок отвечает не на вопрос «что такое ссылка» — а на вопрос, **кто в системе задаёт вопрос «тот же это объект или другой» и что он делает с ответом.**

---

## 1. Что это

**Reference (ссылка)** — значение, которое указывает на объект в памяти, а не содержит сам объект.

**Object identity (идентичность объекта)** — факт «это именно тот объект, а не другой такой же». Идентичность не выводится из содержимого и не меняется при изменении содержимого.

**Referential equality (равенство по ссылке)** — проверка, что два значения указывают на один и тот же объект. В JavaScript это то, что делает `===` для объектов.

Три понятия стоит сразу развести, потому что в обсуждениях они схлопываются в одно:

| Понятие | Вопрос, на который отвечает |
|---|---|
| value equality | одинаковое ли **содержимое**? |
| referential equality | это **один и тот же** объект? |
| identity | свойство объекта быть собой, независимо от содержимого |

В JavaScript встроенной проверки value equality для объектов **нет вообще**. Ни `==`, ни `===` её не выполняют. Это не упущение: сравнение содержимого произвольной структуры — операция неизвестной стоимости и неоднозначной семантики (сравнивать ли прототип, порядок ключей, `Date` по времени или по объекту), и язык её не берёт на себя.

### Чего в JavaScript нет

Идентичность **не доступна как значение**. Нельзя получить «адрес объекта» или стабильный числовой id:

```js
const a = { x: 1 };
// нет ни a.__id__, ни Object.addressOf(a)
```

Единственные операции, работающие с идентичностью напрямую, — это `===`, `Object.is` и ключи `WeakMap` / `WeakSet`. Последнее важно: `WeakMap` индексирует **по идентичности объекта**, и именно поэтому он может служить внешним хранилищем метаданных для объекта, которым вы не владеете (связь с 1.22).

## 2. Как это работает

### Примитивы и объекты хранятся по-разному

Примитив (`number`, `string`, `boolean`, `undefined`, `null`, `symbol`, `bigint`) — это само значение. Объект — это ссылка на структуру, живущую отдельно.

```js
let n = 1;
let m = n;      // m получил копию значения 1
m = 2;
n;              // 1 — переменные независимы

const a = { x: 1 };
const b = a;    // b получил копию ССЫЛКИ — обе указывают на один объект
b.x = 2;
a.x;            // 2 — объект один
```

Во второй паре скопировалась ссылка, а не объект. `a` и `b` — две переменные, один объект. Это и есть **alias (псевдоним)**: два имени для одного значения.

Проверить всегда можно одним сравнением: `a === b` даёт `true`, то есть объект действительно один.

### Одинаковое содержимое — разные объекты

```js
const a = { x: 1 };
const b = { x: 1 };
a === b;        // false
```

Здесь выполнились **два литерала объекта**, и каждый создал свой объект. Содержимое совпадает, идентичность разная, и `===` отвечает именно на второй вопрос. Никакого способа заставить `===` сравнить поля не существует.

То же — после копирования:

```js
const a = { x: 1 };
const b = { ...a };
a === b;        // false — spread СОЗДАЁТ объект
b.x === a.x;    // true  — содержимое перенесено
```

Spread не «передаёт объект», он собирает новый объект из значений свойств старого (1.4). Данные похожи, identity другая — и это ровно то, ради чего spread применяют при обновлении состояния.

### Pass-by-value — ключевая формулировка урока

Распространённая формулировка «примитивы передаются по значению, объекты по ссылке» даёт неверные предсказания. Корректно так:

> **JavaScript всегда использует pass-by-value. При передаче объекта значением является ссылка на объект.**

Разница между формулировками наблюдаемая, а не терминологическая. Сравните два случая на двух независимых объектах:

```js
function mutate(user) {
  user.name = "Alex";       // меняем объект, на который указывает ссылка
}

function reassign(user) {
  user = { name: "Alex" };  // меняем локальную копию ссылки
}

const first = { name: "Serge" };
mutate(first);
first.name;     // "Alex"  — изменение видно снаружи

const second = { name: "Serge" };
reassign(second);
second.name;    // "Serge" — снаружи не изменилось ничего
```

Если бы объекты передавались «по ссылке» в строгом смысле (как `ref` в C#), `reassign` переназначил бы переменную вызывающего, и `second.name` стало бы `"Alex"`. Этого не происходит: функция получила **копию ссылки**. Через эту копию можно дойти до объекта и изменить его, но нельзя заставить переменную вызывающего указывать на другой объект.

Точный термин для этой модели — **call by sharing**: вызывающий и вызываемый разделяют объект, но не переменную.

Практический вывод, который переживёт этот урок: **функция может изменить ваш объект, но не может заменить его.** Отсюда и правило домена «не мутируем вход» — потому что мутация это единственный способ, которым функция может повлиять на данные вызывающего, и значит единственный, от которого нужно защищаться.

### Shallow copy с точки зрения ссылок

Механика spread разобрана в 1.4. Здесь важен другой срез — **какие идентичности остались прежними**:

```js
const source = { user: { name: "Serge" }, theme: "dark" };
const copy = { ...source };

copy === source;             // false — новый объект верхнего уровня
copy.user === source.user;   // true  — вложенный объект ТОТ ЖЕ
copy.theme === source.theme; // true  — но это примитив, идентичность к нему не применяется

copy.user.name = "Alex";
source.user.name;            // "Alex" — изменили общий вложенный объект
```

Spread скопировал **значения** свойств. Для `theme` значение — строка, и копия строки неотличима от оригинала. Для `user` значение — ссылка, и копия ссылки указывает на тот же объект.

Поэтому spread **не является deep clone**: он создаёт новую идентичность ровно на одном уровне — том, к которому применён. Всё глубже остаётся общим, и мутация там видна через оба объекта.

Deep copy создаёт новую идентичность для **каждого** узла структуры. Это не «более правильная» операция, а другая, с другой ценой — см. угол 6.

### Массивы и функции — тоже объекты

У массива нет отдельного типа (1.5), поэтому все правила переносятся без изменений:

```js
const a = [1, 2, 3];
const b = [1, 2, 3];
a === b;        // false — два литерала, два массива

const c = a;
c.push(4);
a.length;       // 4 — один массив, два имени
a === c;        // true
```

Важный для React случай — новый массив с прежними элементами:

```js
const next = [...items];
next === items;        // false — новый массив
next[0] === items[0];  // true  — элементы те же объекты
```

Это нормальная и желательная ситуация: контейнер новый, содержимое разделяется. Именно на этом стоит structural sharing (1.4, 1.13).

Функции — тоже объекты, и у них есть идентичность:

```js
const fn1 = () => {};
const fn2 = () => {};
fn1 === fn2;    // false — два разных объекта-функции, хотя код идентичен

const fn = () => {};
const a = fn;
const b = fn;
a === b;        // true — одна функция, два имени
```

Каждое вычисление выражения-функции создаёт новую функцию. Тело не сравнивается и сравниваться не может: две функции с одинаковым кодом замыкают разные окружения (1.14) и поэтому не взаимозаменяемы в принципе.

### `===` по типам значений

| Что сравнивается | Что делает `===` | Пример |
|---|---|---|
| примитивы | сравнивает **значение** | `1 === 1` → `true`, `"a" === "a"` → `true` |
| объекты | сравнивает **идентичность** | `{x:1} === {x:1}` → `false` |
| массивы | сравнивает идентичность | `[1] === [1]` → `false` |
| функции | сравнивает идентичность | `(()=>{}) === (()=>{})` → `false` |
| `NaN` | `false` даже с собой | `NaN === NaN` → `false` |
| `0` и `-0` | `true` | `0 === -0` → `true` |

### `Object.is`

`Object.is` — тот же алгоритм, что `===`, с двумя исправлениями: `Object.is(NaN, NaN)` даёт `true`, `Object.is(0, -0)` даёт `false`. Подробно разобрано в 1.3.

Здесь он нужен по одной причине, и она важная: **именно `Object.is` React использует**, когда решает, изменилось ли состояние или значение в зависимостях. То есть вопрос «заметит ли React моё изменение» — это буквально вопрос «что вернёт `Object.is` на старом и новом значении». Для объектов `Object.is` и `===` совпадают, поэтому дальше в уроке мы говорим про `===`.

## 3. Почему это важно

Идентичность — это **механизм обнаружения изменений**, и причина его существования экономическая.

Чтобы узнать, изменились ли данные, есть два способа:

| Способ | Стоимость | Надёжность |
|---|---|---|
| сравнить содержимое | зависит от размера структуры, то есть неизвестна заранее | точный ответ |
| сравнить идентичность | одна операция, всегда | ответ приблизительный |

React выбрал второй: сравнение по ссылке стоит одинаково для объекта из двух полей и для дерева из тысячи узлов. Это делает проверку «изменилось ли» бесплатной — но платой становится **приблизительность**, и у неё две стороны:

- **новая ссылка при тех же данных** → система считает, что изменилось, хотя нет → лишняя работа;
- **прежняя ссылка при изменённых данных** (мутация) → система считает, что не изменилось, хотя изменилось → **пропущенное обновление**.

Первая ошибка стоит производительности. Вторая стоит корректности, и поэтому она хуже: лишний рендер пользователь не увидит, а не обновившийся экран — увидит.

Именно эта асимметрия объясняет, почему иммутабельность в React не стилистическое требование, а условие корректности (1.4, 1.13): она гарантирует, что изменение данных **всегда** сопровождается изменением идентичности.

### DEEP DIVE: цепочка от новой ссылки к лишней работе

```
новый объект
    ↓
новая ссылка
    ↓
referential inequality
    ↓
потребитель (компонент, селектор, эффект) считает значение изменившимся
    ↓
дополнительная работа
```

**И сразу оговорка, без которой цепочка вредна: новая ссылка сама по себе не является проблемой.**

Приложение создаёт тысячи объектов за кадр, и это нормально: короткоживущие объекты в современных движках дёшевы (1.23). Новая ссылка превращается в проблему только при выполнении **двух** условий одновременно:

1. у этого значения есть потребитель, который сравнивает по ссылке — мемоизированный компонент, массив зависимостей, селектор, `data` списка;
2. работа, которую этот потребитель выполнит, заметно дороже самой проверки.

Если нет потребителя — новая ссылка не наблюдаема никем. Если работа дешёвая — выигрыш от её отсечения меньше стоимости кода, который это отсечение обеспечивает.

Отсюда рабочее правило, которое стоит унести из урока: **стабилизировать ссылку осмысленно только в контексте** rendering, memoization, selectors, дорогих вычислений — и после профилирования, а не вместо него (5.3, 5.11). Вывод «надо избегать создания объектов» из этого урока не следует и является его неверным прочтением.

## 4. Где это в React Native

Три самых частых источника лишней работы в RN-приложении. Все три — про ссылки, и ни один не является ошибкой React.

### Инлайн-объект в `style`

```jsx
<Child style={{ margin: 10 }} />
```

Литерал объекта вычисляется при каждом выполнении компонента, то есть `style` — новый объект на каждый рендер. Содержимое идентично, идентичность новая.

В React Native у этого есть дополнительный адресат, которого нет в веб-разработке: `style` в итоге превращается в данные для нативного view, и граница JS↔native (1.2) — ещё один потребитель, для которого «новое значение» и «то же значение» различаются.

### Инлайн-функция в `onPress`

```jsx
<Child onPress={() => open(lesson.id)} />
```

Новая функция на каждый рендер (угол 2). Для мемоизированного дочернего компонента это изменившийся пропс — всегда, при любом рендере родителя.

Это та же проблема, что с объектом, и важно увидеть, что механизм один: функция — объект, у объекта идентичность, литерал создаёт новый объект.

### Новый массив `data` для списка

```jsx
<FlatList data={lessons.filter((l) => l.visible)} />
```

`filter` возвращает новый массив всегда — даже если не отфильтровал ничего (1.6). Список получает новую идентичность `data` и обязан считать, что данные изменились.

### Зависимости хуков

```jsx
const ids = lessons.map((l) => l.id);
useEffect(() => { sync(ids); }, [ids]);
```

Массив зависимостей сравнивается поэлементно через `Object.is`. `ids` — новая ссылка каждый рендер, значит эффект выполняется каждый рендер; если он обновляет состояние — бесконечный цикл (разобрано в 1.6). В RN это выглядит как греющееся устройство при открытом экране.

### Элементы списка

```jsx
lessons.map((l) => ({ ...l, label: `${l.order}. ${l.title}` }))
```

Новая идентичность у **каждого** элемента, то есть ни одна мемоизированная ячейка не распознает свои данные как неизменившиеся. Это худший из пяти случаев по последствиям: перерисовывается весь видимый список вместо одной ячейки.

### Данные для нативных компонентов

Отдельная специфика RN: пропсы доходят до нативной стороны. Новая идентичность значения, уходящего в нативный компонент, означает не только работу в JS, но и работу на границе — и там цена зависит от архитектуры (4.1, 4.2). Поэтому «лишняя новая ссылка» в RN в общем случае дороже, чем в веб-приложении, хотя механизм тот же.

## 5. Типичные ошибки

**Сравнение объектов через `===` как сравнение содержимого.** Возникает из опыта языков, где оператор равенства для объектов перегружается или сравнивает поля. Проявляется в проверках вида `if (prevUser === nextUser)`, которые «не работают» на структурно одинаковых данных. Исправляется не оператором, а решением: нужно сравнивать содержимое — пишем явную проверку полей; нужно обнаружить изменение — опираемся на идентичность и обеспечиваем иммутабельность.

**Предположение, что spread делает deep clone.** На плоских объектах spread неотличим от глубокой копии, а плоские объекты составляют большинство примеров. Расхождение проявляется на вложенности, то есть именно на состоянии реального экрана, и даёт частично обновившийся экран (1.4).

**Мутация через alias.** `const b = a; b.x = 2` — изменение видно через `a`. Ошибка часто неумышленная: объект присвоили локальной переменной «чтобы было короче», и дальше работают с ним как со своим.

**Случайное изменение вложенного объекта.** Самая частая форма предыдущей ошибки: верхний уровень аккуратно скопирован через spread, а изменение сделано на два уровня глубже — в объекте, который остался общим.

**Стабильная ссылка на изменившиеся данные.** Зеркальная ошибка, и более дорогая: мутация объекта без замены ссылки. Система не видит изменения, экран не обновляется. Опасна тем, что иногда «работает» — когда рендер случился по другой причине (1.4).

**Создание новых объектов без необходимости.** Не ошибка сама по себе, а ошибка в месте, где у значения есть потребитель, сравнивающий по ссылке: инлайн-объект в пропсе мемоизированного компонента, цепочка в зависимостях эффекта.

**Оптимизация identity без измерений.** `useMemo` и `useCallback`, расставленные «на всякий случай», добавляют код, память под сохранённые значения и сравнение зависимостей — и отсекают работу, которая могла быть дешевле этой проверки. Разбор — 3.8, методика измерения — 5.3.

**Путаница между value equality и referential equality.** Корень большинства перечисленного: вопросы «одинаковые ли данные» и «тот же ли это объект» смешиваются в один, и тогда поведение системы выглядит произвольным.

**Формулировка «объект передаётся по ссылке» без уточнения.** Даёт неверное предсказание про переприсваивание параметра (угол 2). Корректно: pass-by-value, где значением является ссылка.

## 6. Trade-offs

### Стабильная ссылка стоит кода — и может скрывать устаревшие данные

Стабилизация ссылки не бесплатна:

- **код и чтение.** Каждая стабилизация — дополнительная конструкция, которую нужно понять и поддерживать; зависимости надо перечислить верно, и ошибка в них даёт дефект, а не просто неоптимальность;
- **память.** Сохранённое значение живёт, пока живёт компонент или кэш;
- **риск устаревших данных.** Это главное. Ссылка, сохранённая «стабильной» при изменившихся данных, — это ровно та ошибка из угла 5, которая стоит корректности. Неверно перечисленные зависимости приводят к тому, что потребитель видит прежнее значение, хотя данные изменились.

Поэтому стабильность ссылки — не цель, а инструмент с ценой. Решение принимается там, где измерен выигрыш.

### Иммутабельность против мутации

| | Мутация | Иммутабельное обновление |
|---|---|---|
| стоимость операции | минимальная | аллокации по пути изменения |
| обнаружение изменений | не работает | работает надёжно |
| отладка | состояние меняется незаметно | каждое изменение — новое значение |
| корректность в React | не гарантирована | гарантирована |

Выбор в пользу иммутабельности сделан не потому, что она дешевле, а потому, что обнаружение изменений по идентичности требует её как предусловия.

### Shallow copy против deep copy

| | Shallow copy | Deep copy |
|---|---|---|
| новых идентичностей | одна, на верхнем уровне | для каждого узла структуры |
| стоимость | пропорциональна числу свойств уровня | пропорциональна размеру всей структуры |
| мемоизация потребителей | сохраняется для неизменившихся ветвей | **ломается везде** |
| защита от мутации | один уровень | полная |

Deep copy выглядит безопаснее и в контексте React почти всегда хуже: новая идентичность у каждого узла означает, что ни один потребитель не может определить, что его данные не изменились. Нужны новые ссылки **по пути изменения**, а не везде (1.4, 1.13).

### Сравнение по содержимому как альтернатива

Можно отказаться от идентичности и сравнивать содержимое — так работают кастомные компараторы и глубокое сравнение в селекторах. Цена: стоимость сравнения становится функцией размера данных и платится **на каждой** проверке, а не только при изменении. Иногда это оправдано (маленький объект, очень дорогой потребитель), чаще — нет. Решение требует замера; возвращаемся к этому в 6.5.

## 7. Связи с другими частями системы

**Назад:**

- **1.4** — shallow copy и то, что идентичность не зависит от содержимого: механика, на которой стоит этот урок;
- **1.5** — идентичность массива и мутирующие методы, из-за которых данные меняются без смены ссылки;
- **1.6** — `map` / `filter` как источник новой ссылки на каждый вызов;
- **1.3** — `Object.is`: алгоритм, которым выполняется сравнение в React;
- **1.2** — границы: что сохраняет смысл при переходе JS↔native, где идентичность JS-объекта вообще не существует как понятие.

**Вперёд:**

- **1.13 Mutation и immutability** — как обновлять структуры так, чтобы менялись ссылки только по пути изменения, и чего это стоит;
- **1.14 Closures** — почему две функции с одинаковым кодом не взаимозаменяемы: они замыкают разные окружения;
- **1.22 Memory** — идентичность и достижимость: `WeakMap` как хранилище, индексированное по идентичности;
- **3.7 Referential equality** — что именно сравнивает shallow compare в React и чем это ограничено;
- **3.8 Memoization** — где мемоизация помогает, а где только добавляет работу;
- **5.3 Диагностика лишних ре-рендеров** — как доказать причину профайлером, а не рассуждением;
- **6.5 Селекторы** — как селектор превращается в источник ре-рендеров;
- **8.2 Границы модулей** — та же идея на уровне архитектуры: что считать «тем же» и кто имеет право это знать.

**Главное, что должно остаться после урока.** Вопрос «тот же это объект или другой» задаёт не разработчик — его задаёт система обнаружения изменений, и ответ определяет, будет ли выполнена работа. Разработчик управляет только тем, какие ссылки создаёт и какие сохраняет. Всё остальное — следствие.
