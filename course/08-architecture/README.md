## Что должно быть получено

- Рисую карту модулей проекта и правила зависимостей, которые можно проверить автоматически.
- Провожу миграцию JS → TS по шагам, не останавливая разработку.
- Пишу ADR, по которому решение можно принять и пересмотреть без автора.
- Решаю, нужен ли нативный модуль, и защищаю решение числами, а не предпочтением.

## Checkpoint (входит в stage gate G4)

«Приложение выросло до 40 feature-модулей.» Предложить план изменения архитектуры: что меняется в первую очередь, какие этапы, что делать с тестами и CI на каждом этапе, какие риски, какой критерий отката, как измерить, что стало лучше. Отдельно — что сознательно не меняется и почему.

## Упражнения

- **Architecture case studies:** миграция layer-based → feature-based в живом проекте.
- **Refactoring exercise:** вынести фичу в модуль с явными границами, не ломая остальной код.
- **Code review exercise:** PR, нарушающий правила зависимостей — объяснить последствия, а не процитировать правило.
- **System design exercise:** абстракция над FCM + APNs с единым JS API (совместно с блоком 07).
